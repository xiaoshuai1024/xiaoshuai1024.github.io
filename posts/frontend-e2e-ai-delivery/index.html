git diff 一改就要补 E2E：我用一张注册表管住前端交付

我维护着一个多端全栈项目：一个小程序承载 C 端交易，外加商家后台和运营后台两个 Web 端。所有代码由 AI 在我的工作流里产出，人负责提需求、定方案、做验收。这个形态下最尖锐的问题不是「AI 写得快不快」，是「改完了」这三个字怎么证明。

口号式的回答是加测试。但测试覆盖有个恼人的灰区：改了支付回调的一个分支，单元测试全绿，端到端的小程序下单流程挂没挂，没人知道。传统团队靠人肉回归，一个人维护三端，回归是奢侈品。

我的答案是一张九百五十行的 YAML 注册表，加上一套围绕它运转的交付管线。核心机制是一台自动追责机：git diff 里的每个文件都会被映射到业务域，命中的业务流去注册表里查端到端测试，查不到就拒绝提交。改哪，就必须测哪。这篇把整条管线从设计到验证到收口逐环拆开，附真实的取舍和教训。

一、管线全景：八环相扣

先把整条管线摆出来，每一环消费上一环的产物：

  1. 设计源头：一份设计规范 PDF，人定的视觉基准。
  2. 可执行单源：把 PDF 落成 HTML 实现稿，色板、圆角、栅格、控件全部定义成 Token。
  3. Agent 摘要：一份给 AI 的规范摘要，指明阅读顺序和裁决规则。
  4. 工单创建：每次功能开发先在项目管理系统建工作项，MCP 直连。
  5. 四步工作流：方案讨论、写计划、实现、验证，每步产物落盘。
  6. E2E 门禁：git diff 反查注册表，强制测试对应。
  7. 多端验证：小程序自动化加两个后台的 Playwright 测试。
  8. PoW 收口：一键脚本跑构建和测试，退出码非零即未完成。

八环里前两环管「做什么样子」，中间四环管「怎么做到、怎么证明」，最后两环管「怎么交付」。为什么是八环，不是三环？因为每一环都是上一环产物的一次「改写」：设计 PDF 被改写成 Token 表，Token 表被改写成 Agent 摘要，需求被改写成工单，方案被改写成计划，计划被改写成代码和测试，最后全部改写成一条合并请求。改写链上任何一环缺失，下游就会拿含糊的输入自行脑补，脑补的误差逐环放大，到交付那一环已经是指数级。逐环展开之前记住这个结构，后面每一环讲的都是「它消费什么、生产什么」。

下面按顺序展开，每一环都讲清楚「为什么需要它」和「不做会怎样」。

二、设计这一环：不解析设计稿，指定单源

行业里处理设计稿的主流思路是解析：把设计文件里的画板、图层、样式抽成结构化数据喂给 AI。思路是对的，但解析管线本身就是一个需要持续维护的工程，个人项目养不起，也不必养。

我的替代方案绕开解析，直接指定单源。设计源头是设计师给的 PDF，我不动它，而是把它翻译成一份 HTML 实现稿：所有视觉决策——色板、圆角半径、间距栅格、玻璃拟态控件的参数——在 HTML 里定义成设计 Token，再按业务组件分章节平铺。这份 HTML 是唯一可执行真源，PDF 降级为存档。

然后是给 AI 的接口：一份摘要文档，内容短得出奇，主要是一张表——规范来源的阅读顺序，HTML 各章节的锚点索引，外加一条裁决规则：PDF 和 HTML 冲突时，以 HTML 里的 Token 为准。

为什么这样分层？因为三种载体各司其职，失效形态也不同。PDF 服务人：存档、溯源、和设计师对争议，它的失效形态是「找不到某一版」，所以文件名带版本号。HTML 服务机器：它是参数表，色值、间距、层级全部 Token 化，AI 查询它像查配置文件并非读散文；它的失效形态是「被绕过」，有人图快直接写死样式值，Token 表就成了摆设，对应的对策是规范里明文写死「样式值必须来自 Token」。摘要服务上下文：它防的是把三百 KB 的实现稿整份塞进会话；它的失效形态是「过期」，摘要指向的锚点和 HTML 实际章节对不上，对策是锚点命名跟组件名走，组件不改名锚点就不用动。三种载体三种失效，各自的对策都写在摘要文档的裁决规则里。

AI 实现界面时不需要理解设计意图的来龙去脉，它需要的是「这个组件圆角几个像素、主色是什么」，锚点一点就到。曾经踩过的坑是只给 PDF：AI 从设计稿里猜出来的圆角和间距，十次里有八次是「看起来像」，剩下两次直接用了不存在的色值。指定单源之后，样式类的返工基本归零。

三、原型快照：写代码前先钉住「长什么样」

设计规范解决「控件长什么样」，解决不了「页面长什么样」。我的做法是为每个关键页面先做一份静态 HTML 原型，配上截图脚本：原型完成后先截一张图存档，AI 实现完真实页面再截一张，两张对照，布局漂移一眼可见，返工依据从「我觉得不对」变成「图上这里不一样」。

这一步的价值在异步协作里最明显。AI 的实现会话和我的验收时间永远错开，等我发现「这个卡片列表怎么变成了单列」，会话早已关闭，返工要重建全部上下文。有一张原型快照在，返工对话也变得极短：贴两张图，指出差异，AI 自己就能照图修正，返工成本接近于零。原型快照把「验收标准」从口头描述变成了两张可以 diff 的图，返工从「重建上下文的争论」降级为「对照图片的微调」。

原型还有一个隐藏职能：它是 Token 的第一次消费。原型本身用同一套设计 Token 写成，做原型时如果发现某个 Token 不够用——比如缺少某类禁用态的颜色——就说明 Token 表有缺口，要在真实开发前补齐。这样原型成了 Token 表的验收环节，比等实现阶段才发现缺 Token 便宜得多。

成本控制上也克制：只有交易、社区这类核心页面做原型，长尾页面直接靠摘要文档加组件库约束。全覆盖是理想，核心覆盖是现实，靠门禁补齐灰区。

四、验证这一环：注册表，管住「改了就得测」

这是整条管线的心脏。先看注册表里一条记录长什么样：

- id: "trade-order-purchase"
  domain: "trade"
  name: "标准商品下单购买"
  trigger: "用户在商品详情页点击立即购买"
  endpoints: ["POST /api/trade/order/create"]
  e2eTests:
    - "frontend/e2e/miniprogram/standard-goods-purchase.e2e.test.ts"
  e2eRunners:
    - "frontend/e2e/miniprogram/run-p0-trade.mjs"

每个业务流一条记录，业务域、用户动作、涉及的接口、对应的 E2E 测试文件和运行器，全部绑死。文件头部还有一段门禁配置：commit 阶段增量覆盖率不低于 85，PR 阶段 88，release 阶段 90，外加质量分门槛，全部只算增量。另一段是路径映射：正则把文件路径映射到业务域，比如后端交易目录的改动自动归入 trade 域。

门禁脚本的工作流因此变得机械：拿 git diff 的文件清单，跑一遍路径映射得出受影响的业务域集合，再去注册表里查这些域下的业务流，任何一条的 e2eTests 为空，提交直接拒绝。整个过程零判断、零解释空间，AI 再快，快不过这张表。执行细节上还有一个缓冲设计：域命中但没有对应注册记录的目录改动（比如纯脚本和文档），门禁放行但打一行提示，避免表外的改动把门禁搞成狼来了。

为什么选「反向追责」，不走「正向生成」？正向的做法是需求阶段就把验收用例定好，它依赖写 Spec 时的自律和远见，而实践里总会漏。反向追责不预测什么该测，它只回答一个机械的问题：你改了这里的代码，这里的业务流有没有测试兜着。没有，先补测试再回来。这个机制对 AI 尤其重要——AI 不会偷懒，但它会诚实地只做被要求的事；你要求了代码，它就只给代码，除非门禁要求更多。

误伤的情况存在：新增一个业务流，注册表里还没有它的记录，第一次提交会被拒。这不算误伤，这是有意的设计。新业务流的第一项任务就是把记录补进表里，登记本身成为开发流程的一部分，表和代码从此不分叉。

注册表自身的治理有三条。其一，维护权随开发走：谁新增业务流谁登记，登记和代码走同一个合并请求，评审时一眼可见「加了功能没加测试」。其二，记录有生命周期：业务下线的流标记废弃而不删除，历史用例的来龙去脉保留可查，注册表因此也是业务演进的编年史。其三，域映射的扩容有仪式：新目录要映射到新域时，正则、域名、注册表分节三处同步改，改动必须单独提交，这是表里少数需要人专门操心的地方。至于为什么用 YAML，放弃数据库：表要进版本管理，diff 可审、评审可见、AI 可读，这三条数据库一条都给不了。

五、真机这一环：一台手机的自动化玩法

端到端测试对前端项目有个特殊要求：真机。小程序尤其如此，开发者工具里的表现和真机运行总有差异，样式、授权、支付回调都可能在真机上才暴露。

我的真机环节由三件东西组成。预检脚本：跑测试前先检查设备连接、开发者工具端口、登录态有效性，任何一项不满足直接报明确的原因，不让测试跑到一半死在环境上。登录态保活：微信登录的可见化测试用例，专门验证登录链路，登录态过期时最先失败的就是它，错误信息直指原因，保护后面几十条业务用例不被连带误报。业务用例分层：P0 交易流程全设备必跑，P1 的社区浏览、P2 的低频功能按需跑，一台手机也跑得起。

两个 Web 后台的验证没有真机问题，用 Playwright 做路由级渲染、DOM 断言和截图，走 Docker Compose 拉起的隔离环境，数据库和缓存全新初始化，跑真实的 HTTP 接口。小程序和后台的测试互不阻塞，并行跑，单轮全量验证压在可接受的时间内。

执行策略也是分层的。每次提交只跑受影响业务域的 P0 用例，几分钟出结果；每晚定时全量一轮，覆盖当天所有改动叠加后的组合；发版前全量加冒烟，冒烟是从 P0 里再挑出来的最小集，十分钟内走完交易主链。三层频率保证问题被拦截的位置尽量靠前，也保证全量测试的机时开销压在夜间闲置时段。

这一环的教训是：环境检查值得比测试本身写得更认真。早期最烦人的失败不是断言失败，是「测试跑到第三步发现没登录」这类环境性死亡，失败信息还和业务失败混在一起。环境预检独立出来之后，业务用例的红就只剩业务原因，可信度完全不同。剩余的偶发环境失败（网络抖动、设备瞬断）有一条约定：任何用例失败先跑一遍预检确认环境健康，健康则定性为业务失败进入修复，不健康则环境失败重跑，定性流程固定，避免每次失败都先争论半小时「是不是环境问题」。

六、长任务与证据链：退出码是唯一的裁决

一个功能从工单到合并要跨越几十分钟和上百次工具调用，长任务的管理靠两样东西：状态外置和证据链。

状态外置：每次开发先经 MCP 在项目管理系统建工作项，Agent 的工作流固定四步——方案讨论、写计划、实现、验证——每一步的产物都落盘成文档，工单状态跟着走。任何时刻中断，新会话读工单加落盘产物就能续上，不依赖聊天记录。MCP 这一层的接口刻意收窄：只开放建单、改状态、加评论三个写动作，读不限。曾经考虑过让 Agent 自由调全量接口，想想「半路改坏单据状态」的场景就放弃了，写接口的白名单越短，夜间无人值守的批次越敢跑。至于为什么状态放磁盘，不指望会话恢复：会话压缩会丢细节，磁盘产物无损；前者是尽力而为，后者是确定性。

证据链：Agent 声称完成时，必须先过一键验证脚本。脚本自动做两端的构建和测试：后端编译加全量测试，前端构建加组件测试，任何一步失败退出码非零，流程当场终止。脚本过关后还有三项人工补核：增量覆盖率达标、接口文档同步、E2E 用例齐备。全部通过，才创建合并请求，工作项更新状态，评论里附上证据摘要。

这套设计的哲学只有一条：不信声明，只认落盘。值得强调的是它防的不只是 AI：人也会在连续加班后说「应该没问题」，也会跳过一步自认为不重要的验证。证据链对人同样有效，验收材料按固定结构落盘后，谁来收尾都跳不出这张单子。AI 说「我做完了」没有价值，「脚本退出码为零、构建产物存在、测试报告生成」才有价值。甚至可以说，退出码是这条管线里唯一的裁决依据：它是唯一一个由机器产生、无法被口头修饰、结构上无法造假的信号。所有其他信号——聊天里的自信表述、界面的成功提示、汇报文档的措辞——都只配当线索，不配当结论。

七、知识复用：极简索引制

管线跑久了会积累大量规范和经验，知识管理的失败形态也见过很多：要么全堆在一个巨型文档里没人读完，要么散落各处没人找到。

我的做法是极简索引制。仓库根的规范文档只承担入口角色： 最高频的规则直接写在索引页，其余正文通过引用组织，改到哪一层的代码，AI 按索引跳到对应文档，只读该读的那一份。文档目录按业务域组织，和注册表里的域一一对应，找交易相关的规范就去交易目录。事故的处理结果一律回写：每次线上问题或审核判罚复盘完，对应规范文档里就多一条「为什么这里是这么定的」。

索引制有两个反模式要防。一是索引爆炸：每条引用都想附摘要，索引页越写越长，最后索引自己变成巨型文档，解法是引用只带一行说明，详情留给正文。二是孤儿文档：一篇规范谁都不引用，等于不存在，我的做法是跑一个脚本扫无引用的文档，孤儿要么挂上索引要么归档。索引制的收益在上下文管理上：AI 每次会话只需要加载索引加当前任务相关的少数文档，规范再厚也不挤占工作记忆。它还顺带解决了一个组织问题：文档的更新是局部的，改交易的规范不会牵动整个文档体系。

八、单人维护的取舍：自动化投在哪、省在哪

一个人管三端，自动化投入必须有分寸。我的分寸是：P0 交易链路全覆盖，每个关键步骤都有断言；长尾功能靠门禁拦住，改动即触发，不追求主动覆盖；测试数据管理走配置化，涉及特定城市、订单、账号的场景，测试数据提前写进用例，执行时不允许临时发挥。

明确不做的也有清单，每项都有理由。视觉回归测试：像素级 diff 的维护成本对单人过高，原型快照加人工验收够用。多设备矩阵：一台主力真机加开发者工具的多机型模拟，覆盖八成问题，剩下两成等用户反馈再进清单。全量接口自动化：接口层有后端单测兜着，前端 E2E 只打关键路径，重复覆盖是浪费。

取舍的总原则是看「失败的可发现性」：门禁和注册表能兜住的，可以省；只有真机能暴露的，必须投。钱和精力花在别处发现不了的地方，才是自动化的本职。

九、收束

回到标题那句话。这张注册表真正的价值，不是让测试变多，是把「改了就得测」从一种自觉变成一条机器可查的规则。AI 写码的时代，自觉是最不可靠的东西——不是 AI 不自觉，是任何人包括人在高频产出时都靠不住自觉。

整条管线拆下来，每一环都在做同一种动作：把「应该」翻译成「必须」，把「记得」翻译成「落盘」，把「口头确认」翻译成「退出码和表格」。翻译完成之后，一个人和一支团队走的是同一条交付管线，剩下的差别只是速度。

最后回答一个被问过多次的问题：这套管线会不会太重？拆开看它的日常运行成本——每次提交多跑几条本地脚本和一部分 P0 用例，分钟级；每晚上一轮全量，无人值守；工单和证据链是顺手落盘，无额外动作。真正重的从来是人力回归和线上事故，管线替你省的正是这两样。如果某天它重了，那说明某个环节退化成了纯手工，按文中的取舍原则砍掉重估即可。这篇里所有机制的起源清单也交代一下：Token 单源源于样式返工，原型快照源于布局漂移，注册表源于灰区测试缺位，真机预检源于环境性死亡，PoW 源于「口头完成」的不可信。没有一个机制是凭空设计的，全是坑的倒影——这也意味着任何人的管线都该长成不同的样子，因为坑的位置各不相同。照抄结构没意义，照抄「从自己的事故里长机制」这个方法才有。

九个环节，三张图，一张注册表，就是这套管线的全部。它不依赖任何团队级的基础设施，每一环的初始版本都是普通文件加普通脚本，剩下的演进交给事故和时间。如果你也在一个人扛多端交付，照着第八节的取舍原则先给 P0 链路配上门禁，一周之内就能感觉到「改完了」这三个字终于有了凭证。
