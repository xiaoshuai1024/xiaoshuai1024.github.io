三个人要删会话，DeepSeek Harness 为什么就是不做

About 200 words One minute

在 DeepSeek Harness 的 GitHub Discussions 里搜「删会话」，能同时翻出三条独立请求。三个互不相识的用户先后开口，要的都是让某个会话从磁盘上彻底消失。维护者三次都没有交出一个删除命令。

结论我直接放在前面：删不掉排在模型约束那一栏，backlog 上等不来它的修复。合理出路是给管理诉求另开一个出口，这个出口眼下还没出现。依据是我把会话当 git 用那篇拆过的设计重新读了一遍，下面从头讲。

一、同一条请求为什么会来三次？

出处可以自己核对（github.com/deepseek-ai/deepseek-harness/discussions）：#3339 要一条原生 /delete 命令，把会话永久删掉；#2861 提议加 session.delete RPC；#2642 提议 workspace.deleteSession。三个编号彼此隔着相当长的距离，提的人互不相识，要点的东西一模一样。

时间跨度本身就带着信息量。三条讨论横跨了好几个 rc 版本的开发期，短期的热度撑不了这么久；隔那么长时间还有人说出一模一样的诉求，说明它长在真实的使用路径上。测试期攒下的垃圾会话越积越多、共享机器上不想留对话痕迹、项目收尾想清场，每一种都是正当的管理诉求。

更难得的是三条请求的措辞各不相同、抽象层级互补：命令面的 /delete、协议层的 RPC、工作区对象的方法，从用户入口到内部接口各来了一票，最后撞的却是同一扇门。需求表达得这么完整，回应却始终缺席，这才值得往下挖。

它们从不同方向涌向同一个动作，又一起撞上同一堵墙：仓库里找得到 resume、fork、replay，唯独找不到 remove。

二、不给删除按钮的系统长什么样？

要看清墙在哪，得先看地基。dsh 的核心设定只有一条：Session 是一份由类型化 SessionEvent 组成的仅追加日志，同时是智能体完整交互历史的唯一真源。模型每轮看到的消息历史、界面渲染的对话、调试用的记录，全部从这条日志当场派生。写入方向只留了 append 一个，seq 单调递增，修改旧事件的路径从来就没开过——这层校验做在持久化层，细节我在源码深读里逐段核过。

「派生」两个字值得多看一眼。界面上的一切既然都来自日志的当场投影，「删掉会话里的某段内容」在这个模型里就失去了句法位置：改事件的字段？事件不可变。改投影里的显示？那叫隐藏，数据还躺在磁盘上。唯一真源的设定换来了确定性重放能力，代价是「删除」这个词在接口词汇表里没有对应动词。

标题子系统把这个原则演得很彻底。会话标题本身就是一条 log-only 的 session/title 事件：自动生成也好，用户手动改名也好，都只是往后追加一条新记录，折叠规则取最新一条；显式改名还会钉住标题，让自动生成停摆。标题改得掉，靠的却是对旧数据的零次写入。

工具层同样如此。todo 插件的待办列表没有一个可变的「当前状态」字段，它的最新值从历史里的每条 todo/write 事件现场推导出来；要看现在的清单，系统就把事件流重新折一遍。整个系统里，「现在」永远是日志的函数。

三、删掉一个事件，会破什么？

推演一下维护者的视角。假如给 session.delete 开口子，真删掉一段事件，日志中间会出现空洞，后面所有事件的 seq 和内容仍指向被删段落。resume、fork、replay 三个核心操作都以「同一组事件可以逐条重演」为前提：fork 从第 k 个事件处截种子，回放要求复盘时的上下文和当时模型看到的完全一致。允许删除，等于让这三个保证在生产环境里悄悄失效。

回放的严格程度放在事故复盘的场景里最容易体会。你想证明某个 bug 在当时的上下文里必然发生，前提就是模型当时看到的那串输入能够一字不差地重建；任何一次事后修补都让这份证明降级成推测。

压缩功能的选型最能说明问题。上下文窗口要省空间，直觉做法是把旧对话抹掉，dsh 给出的却是投影 replace：

{ op: 'replace', start, end }

区间 [start, end) 的事件被折进替换结果，原始事件原封不动移入 shadowedSeqs 影子区。看起来像删除，实际是换视界：审计时原文照样翻得出来。宁可多花一份存储也要留住原文，守的就是上一节那条确定性底线。

查询子系统还给这片影子区发了正式身份。事件在表面上的位置在类型定义里分成三种：current 还在当前模型上下文里，shadowed 被替换压进影子区，log-only 只存在于原始日志；折叠用的是和模型历史推导同一个 foldSurface 状态机。「看起来消失了」的内容拥有精确的类别名，原文完好，随时可审计。事故复盘时这份存档最值钱：模型在某一轮到底看见了什么，翻影子区就能拿到当时的原文，省掉全部事后考古。

四、出口其实不少，只是没有一条通向销毁

删按钮缺席并不代表管理面荒芜。把会话家族的兄弟子系统逐个数一遍，出口比直觉富余得多，这是我在核对文档之前没料到的发现。数之前先立一个分类标准：这条出口是消费日志，还是改动日志？按这个标准衡量，下面每一件都干干净净落在消费一侧。

查询子系统把全部会话组织成一个逻辑语料库：记录头区分 live 与 persisted 两种可用性，过滤器支持按目录、创建时间、父会话谱系组合筛选；消息、推理、工具调用与结果这些语义文本都能进正则扫描和全文索引，被拦下的提示词、待办与失败详情也在收录之列，结构事件和流式分片则有意排除在外。跨语料库和单会话内部两个搜索范围配了独立的游标分页，SQLite provider 专门负责索引的生命周期。海量为患的担忧在这套词汇面前大半失效，东西还在，但找到想要的那条从来不是问题。

遥测子系统负责往外送。ledger 渠道把会话事件一比一镜像给 OpenTelemetry 后端，接收端按会话 id 加 seq 去重；ops 渠道单独承载错误与停机信号，严重级别在捕获时就映射完毕，带错误标志的工具响应和运行时故障直接落进 error 档，接收方零配置即可告警；每个回合只保留第一条流式开始信号，其余分片在捕获点丢弃。企业级的留存、合规导出、监控接入，通道都是现成的，姿态依旧清晰：搬运可以，抹除不行。

存储侧还有一个更大的旋钮：持久化后端可替换。JSONL 后端给每个会话一份仅追加文件，默认是带校验和的 Zstandard 压缩，原子写、中断轮恢复齐全；SQLite 后端用 node:sqlite 把每个事件落成一行，自己的 schema 版本参数守着整个库的结构。想知道某个会话存在哪也有接口，locate 返回工件路径提示，共享数据库的后端按设计返回空值。换介质、换格式都欢迎，但两份后端的文档词汇里同样找不到删除动词，契约写的正是持久的仅追加存储。后端换了面孔，append-only 的约束原样跟着走。

最能表明立场的选择在隔壁子系统。KV 存储的管辖范围被明文划成一切不属于会话事件日志的数据，它的接口里有 deleteRecord 这样的记录级删除原语，删一个不存在的键返回什么都规定好了语义。可见这个团队做删除毫无技术与工程障碍，是这个数据模型不收这件商品。

五、对照 git 找 GC，结论是没有等价物

拿 git 做最后一次对照，可以把这份坚持盘得更透。git 自己同样是只增不改的设计，却为回收准备了整套词汇：reflog 会过期，gc 有 prune 期限配置，可达性分析跑完之后，不可达对象真的从包文件里物理消失。

我把会话持久化相关的文档翻了一遍找这套机制的影子，结论如实写下：持久化层没有 expire，没有 prune，没有任何 GC 条目；版本治理靠格式版本号拒绝读不懂的日志并讲明升级方向，损坏恢复靠中断尾部的无损平衡读取。每一条机制都服务于保住数据，没有一条服务于丢弃。

所以「有没有等价物」的答案是：没有。我把它当成本文最重要的深度发现来交代。这不是遗漏清单上的一个缺项，是同一立场的自然延伸：git 回收的是版本库里不再需要的对象，而会话日志在设计者眼里不存在「不再需要」这个类别，审计、复盘、归因随时可能回头翻任何一段历史。模型不给出去，边界自然也画不出来。

把 append-only 家族在这篇里出现过的成员拢在一起看，对象感会更强：事件日志本体、压缩产生的影子区、标题的历次记录、todo 的写入流，整个家族共享同一条纪律——任何一份看起来像状态的东西都能追溯成串只增的事件。回收机制处理的对象是「确认不需要的历史」，而这个家族里没有任何一位成员满足这个前提。

六、管理诉求没有消失，缺的是通向销毁的那个出口

写到这得诚实一点：存储持续增长的压力和隐私场景的清场需求是真实的，官方目前确实没提供任何删除命令或清除 RPC。已有的手段全部停在「让它不被看见」这一层：投影让压缩掉的旧内容退出模型视界，可用性标记让不同来源的会话在检索中可区分，没有人碰「存不存在」本身。

所以我把这一票投给等待加推动：这是产品开放问题，够格排进 roadmap。合理的终局应该长在 append-only 约束之内，比如整段导出配合分档清理；导出物满足迁移与备份，日志的自洽性证明原地不动地留着，两边各得其所。仓促上线一个破坏不变量的 API，比功能缺席更糟。在官方表态之前，敏感工作可以先挪进沙箱这类隔离环境跑。

七、先分清欠账和约束，再决定要不要催

判断一个缺失的功能该不该催着补，第一步看它属于哪一类：实现欠账还是模型约束。欠账类的 issue 有人交作业，社区追着讨论就能等到实现；约束类的 issue 在筛选用户。删除会话落在第二类：你要么接受会话只能生长、无法收缩，要么把敏感工作挪去隔离环境，两种选择都成立。

举个例子把区分方法用熟。假如有人开 issue 要求调整日志文件的压缩格式，被搁置多半是排期问题，追问和补充场景都有意义；要求删除会话被搁置，原因写在第二节的模型里，追问多少遍得到的都是同一个答案。表面相似的两类「不做」，内核差着一整个层级，先把形状看清，能省下双方的时间。

你的数据要不要为「可复算」负责，直接决定你站哪边。在乎复盘、审计、事故归因的人，会觉得这份「不能删」买得太值；拿它当聊天面板用的人，每一条积压会话都是纯负担。同一个空缺，两种体感。下次再遇到「这么简单的功能他们怎么不做」，先去看一眼数据模型的形状，答案往往已经写在那里了。
