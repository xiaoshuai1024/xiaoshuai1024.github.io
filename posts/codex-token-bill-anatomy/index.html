翻开 ~/.codex/sessions 里我自己的会话记录，有一条让我坐直了：2026-08-20 16:45:36（UTC+8）开始的那个 session，54 次模型调用，总输入 952 万 token，总输出 6.6 万。输入是输出的 144 倍。这中间我没换模型、没改配置，就是正常干了一个下午的活。

起因说来简单：我给频道挑选题，把市面上省 token 的攻略翻了一遍，清一色是「关思考、开压缩、勤开新会话」的口诀，没有一篇贴过自己每一轮的真实流水。口诀对不对、在自己的通道上灵不灵，全靠信。我不太想信，就想亲眼看，于是有了这篇逐轮拆解。

这篇文章就是把这 952 万拆到每一轮，看它从哪来、被什么放大、怎么砍。全部数据来自我本机的 codex-cli 0.140.0（deepseek-v4-flash 通道），8 个真实会话加一组受控 A/B 实验，没有任何估算。

这套方法适用谁，不适用谁

适用：用 Codex CLI 干活、按 token 计费或被限额卡脖子的人。不管你走官方 API 还是像我一样用 cc-switch 切到 DeepSeek，下面讲的机制一模一样。团队协作的仓库更该看——AGENTS.md 是随仓库分发的，你写在里面的每一个字，都会乘以全组每个人的每一轮会话，一份松散的文档就是全组的持续成本。

不适用：纯订阅制（ChatGPT Plus 内的 Codex 用量）的用户——你不直接付 token 钱，但限额消耗是同一套逻辑，看懂机制一样能少撞墙。

先交底数据来源，这也是本文的方法论价值：Codex 的每个会话都在本地存了一份 JSONL 流水（~/.codex/sessions/年/月/日/rollout-*.jsonl），每次模型调用都记录了 token_count 事件，输入、缓存命中、输出、思考 token 四项分開记。你不依赖任何后台报表，就能把自己的账单拆到每一轮。文末清单里有现成的挖掘脚本核心逻辑，十行以内。

三条原则，先记住再往下看

一、上下文是复利负债。 模型不记得你，Codex 每一轮都把全量历史重新发给它。你在第 30 轮为第 3 轮的文件内容付钱，这是账单的结构性来源。操作口径：会话按任务切，文档按「违背会出错」删。

二、缓存是放大器，不是免单。 重发的大头会被供应商的上下文缓存按折扣价接住——但命中率取决于你的前缀稳不稳定。同样 952 万的重发量，命中率 98% 和 46%，实付差出一个数量级。管缓存，比重发本身更值得花精力。操作口径：AGENTS.md 进稳定期后上锁，要改集中批量改。

三、开关要先验证再信任。 我把推理档位从 high 调到 low，一分钱没省，思考 token 反而更多——这个通道根本没把参数透传给模型。配置文件里写了不等于生效，省钱的动作必须用数据验证过才算数。操作口径：任何参数改动，当周跑一次 A/B 对账。

把仪表盘接上：五分钟挖出自己的账单

先教你怎么挖，后面每个数字你都能自己复现，这是这篇文章和「省 token 攻略」最大的差别。

会话流水的结构不复杂：~/.codex/sessions/年/月/日/ 下每个 rollout-*.jsonl 文件是一个会话，逐行 JSON。四种行最重要——session_meta 记录模型和工作目录；turn_context 记录每一轮的推理档位和沙箱模式；response_item 是发给模型的原始消息，其中第一条 user 消息里能看到被注入的 AGENTS.md 全文；event_msg 里的 token_count 事件就是计费流水，last_token_usage 对应本次调用，total_token_usage 是会话累计。

四个字段直接对应你的钱：input_tokens 是这次调用重发的全部输入；cached_input_tokens 是其中命中缓存、按折扣价计费的部分；output_tokens 是模型吐出的正文；reasoning_output_tokens 是正文里的思考段，按输出价计费。输入、缓存、输出、思考，账单的全部四个变量都在这了。

还有一个口径要先校准：CLI 跑完打印的 tokens used，我拿两组数据验证过，它约等于非缓存输入加输出——胖组总输入 40,005、缓存命中 46%，40,005 × 54% + 411 ≈ 21,984，和 CLI 打印的数字正好对上。所以别拿总输入吓自己，也别拿 tokens used 当总消耗，两个口径之间隔着缓存这一层。看懂这个，后面所有数字才有意义。

文件按日期分目录滚动，定位很容易；老会话归档后在 ~/.codex/archived_sessions/，格式相同一样能挖。别删这些流水——它是你手里唯一的一手账本，后台报表给不了这个粒度。

第一笔账：每一轮都在重发全部历史

先看一句话是怎么变成账单的。我在终端敲「改下这个 bug」，Codex 发给模型的不是这一句，而是四样东西的整包：系统提示、AGENTS.md、前面所有轮次的对话、每一轮的工具输出。模型是无状态的，它对你的全部记忆，就是这一次请求里装的东西。

这意味着输入随轮次单调上涨。那条 952 万的会话，真实的每轮输入序列是这样的：20,611 → 21,006 → 33,133 → 51,782 → 61,699 → 81,676 → 91,452 → 120,852 → 153,921 → 164,729 …… 到第 54 次调用时是 226,262。第一轮的两万，到最后一轮涨了 11 倍，而且中间没有任何一次「重复劳动」——就是同一个任务正常往下推。

为什么非这样不可？因为对话式模型的 HTTP 接口是无状态的：服务端不保存任何会话，你这次请求里装了多少上下文，模型就「记得」多少。Codex 客户端能做的，只是每轮把「系统提示 + 全部历史 + 你新说的话」重新打包。很多人把供应商的「上下文缓存」理解成「模型记得我，所以不用重发」——这是两回事。缓存不减少重发，它只是让服务端对重复的前缀少收点钱；从客户端看，每一轮的请求体积该多大还是多大。分清这两层，后面的账单才不会算糊涂。

把柱子加起来就是 952 万。对照输出 6.6 万，这个 144:1 才是 Codex 类编程 Agent 的真实形状：你花的钱大部分不在「模型写了多少代码」，在「模型每轮重新读了多少遍你俩的对话」。

八个会话的全景放在这张表里，两组基线的对比比单看一条曲线更有说服力——同样是我这台机器、同一个模型，blog-src 仓库（6KB 的 AGENTS.md）首轮输入稳定在 20,277 到 20,847，而接近裸奔的 demo 目录首轮只有 16,056 上下：

三个规律直接读出来：首轮输入由「系统提示 + AGENTS.md + 环境上下文」决定，跟任务无关，换任务它也不降；末轮和调用次数正相关，曲线只涨不降；思考占输出的 45% 到 64%——这批会话我全局开着 high 档，这个占比就是高档位的租金。

顺带一提上下文压缩：快满的时候 Codex 会自动把历史摘要成一段，压缩能救上下文窗口，但压缩那一下本身就是一次按当时全量上下文计费的大请求。所以我的用法是两码事分开：任务边界到了直接 /new 归零；任务确实需要长会话推进，才把压缩当作窗口管理工具用。指望压缩省钱，方向就错了——它救窗口，不救钱。

第二笔账：AGENTS.md 是每轮计费的

AGENTS.md 的注入方式决定了它的成本属性：它被拼进每一轮请求的指令区，一轮不落。我在受控实验里量出了它的单价。

实验设计：两个空目录，各放同一份 300 行的 Python 文件，唯一的差别是 AGENTS.md——一个 3.5KB 的「团队规范大全书」，一个三行的「命令 + 禁区」。用同一个只读任务各跑一遍 codex exec：

codex exec --skip-git-repo-check -s read-only "阅读 sample.py，三句话总结它做什么"

结果：胖目录首轮输入 18,281，瘦目录 17,350，差 931 token。这 931 不是一次性成本，它挂在每一轮请求里。跑 50 轮，就是 4.6 万 token 的重复输入——只为告诉模型一堆它这个任务根本用不上的提交规范。

这个数字也和存量数据对得上：我 blog-src 仓库的会话（6KB AGENTS.md）首轮输入稳定在 20,277 到 20,847，而一个几乎裸奔的 demo 目录首轮只有 16,056。文档差多少，首轮就差多少，之后每一轮乘以调用次数。

注入的结构可以在流水里直接看到。打开任一会话第一条 user 消息，它是三段拼起来的：~/.codex/AGENTS.md 的全局说明在最上面（我这里是一段通知钩子的注意事项），中间一段 project-doc 是当前仓库的 AGENTS.md 原文，结尾是 <environment_context> 环境块。也就是说你的项目文档一个字不落、原样进了指令区，然后跟着每一轮请求跑完全程。看过这个结构，「AGENTS.md 是合约不是笔记」就不再是修辞——它逐字逐句地参与每一次计费。

第三笔账：缓存命中率，被忽视的放大器

到这里有个反问：既然每轮重发，为什么我没破产？因为缓存。DeepSeek 这类供应商对重复前缀按缓存折扣价计费，我的长会话命中率 92% 到 98%，重发的大头被折扣接住了。

但缓存有脾气，值得单独讲清楚。它的工作方式是前缀匹配：服务端记住你上次请求开头的那一长串，这次请求只要开头部分和上次完全一致，命中就成立，不一致的位置之后全部按原价。这带来三个推论：一，会话内命中率高是天然的——历史只追加不修改，前缀稳定；二，AGENTS.md 和全局配置站在前缀最顶端，改动一个字，后面全部作废，这是「配置稳定本身就是优化」的机制依据；三，首轮永远没有缓存，文档越大，首轮的原价部分越大。我长会话 92% 到 98% 的命中率，靠的就是前缀纪律，不是运气。

看受控实验的计费口径（tokens used，它统计的是非缓存输入 + 输出，不是总输入）：胖目录那次命中率只有 46%，计费 21,984；瘦目录 98%，计费 3,989。同样的任务，差出 5.5 倍。

单次运行有波动，我不把 5.5 倍当成稳定结论。但结构性的事实够清楚了：文档越胖、独有前缀越大，缓存越接不住；前缀一变（比如你随手改了 AGENTS.md 或全局配置），缓存整体失效，下一轮按原价重来。缓存把「重发」从成本项变成了「前缀稳定性」指标——你的账单，一半掌握在供应商的缓存策略手里，另一半掌握在你前缀的纪律里。

想把 token 数换成钱，公式就一行：命中价 × cached_input_tokens + 原价 ×（input_tokens − cached_input_tokens）+ 输出价 × output_tokens。三个单价去你通道的定价页拿，流水从 session 文件里读。拿我那条 952 万的会话套一下：命中 98%，意味着九成多的重发走了折扣价——这就是为什么重发量吓人、账单却没有爆炸。但别因此觉得重发无所谓：命中率是脆弱的，换个任务、改个配置、换个通道，同样的重发量就会按原价砸下来。

第四笔账：那个没生效的开关

推理档位（reasoning effort）是各路省 token 攻略的标准答案：简单任务调 low，难题再上 high。我在瘦目录上做了 high/low 对照，结果 low 档思考 token 占输出 51%，high 档只有 22% 到 39%——开关拨了，方向反了。

原因不难猜：我走的是 DeepSeek 的 responses 兼容通道，model_reasoning_effort 参数疑似根本没透传到模型，档位拨了个寂寞。这不是 DeepSeek 的错，是「兼容层 + 自定义通道」这类架构的通病——参数在每个环节都可能被静默吞掉。

验证方法很简单，流水里都留着证据：turn_context 行记录了每轮下发的档位值，token_count 里的 reasoning_output_tokens 记录了模型实际的思考量。两边一对，参数有没有变成行为，一目了然。我的对照组里档位值确实变了（high → low），思考占比却从 22% 到 39% 涨到 51%——下发了，没执行。反过来看那八个真实会话，全局 high 档下思考 token 占输出的 45% 到 64%，这就是高档位在这条通道上的真实租金，而且是我验证过确实在计费的部分。

这条教训比省 token 本身值钱：配置文件里写了，不等于模型收到了。 任何优化动作，先跑一次 A/B 用 session 流水验证生效，再谈坚持。

三条省法

以下每条我都给了做法、理由和反例，可以直接抄进团队规范。先给一张决策图，日常拿它过一遍就够了：

省法一：AGENTS.md 分层瘦身

  • ✅ 推荐：仓库强相关规则（构建命令、目录约定、禁区）放项目根的 AGENTS.md；跨项目通用习惯（回复语言、代码风格偏好）放 ~/.codex/AGENTS.md 全局层。每层只留「模型不知道就会做错」的事。
  • ❌ 避免：把 AGENTS.md 当团队 wiki——提交规范、协作流程、价值观全塞进去。
  • 理由：实测单价 931 token/轮起步（3.5KB 文档），50 轮 4.6 万；且胖文档拉低缓存命中，计费端被再放大一次。提交规范这类模型执行不了的内容，进了指令区只是纯成本。

我的判断标准就一句话：这一条规则，模型违背了会产出错误结果吗？会，留下；不会（它只是「最好知道」），挪去人类文档。

配套一个审计流程，三十分钟给自己的 AGENTS.md 做完体检：第一步，用文末脚本看你最近几个会话的首轮输入，和裸目录基线相减，得到你文档的真实单价——我的 blog-src 文档 6KB，基线差 4,200 token/轮，这就是我的起点数字；第二步，打开第一条 user 消息里的 project-doc 段，逐条过「违背会出错吗」；第三步，删完在一个空目录跑一次 codex exec 对照首轮输入，确认降下来了。单价乘上你平时的会话轮数，值不值得做这一轮，自己就有答案了。

省法二：会话纪律，该 /new 就 /new

  • ✅ 推荐：任务边界一到立刻 /new 开新会话。修 bug、写脚本、重构，是三个会话不是三个阶段。
  • ❌ 避免：一个会话从早跑到晚，「反正上下文还没满」。
  • 理由：输入曲线只涨不降，54 轮滚到 22.6 万。任务切走后，旧任务的全部历史变成纯负载——它对新任务几乎零贡献，但每一轮都全额重发。压缩不解决问题，它只是把负债重组了一下。

有个成本要交代：/new 之后新会话首轮没有缓存，原价起步。这笔账算下来依然划算——旧上下文是每一轮都要付的持续成本，新会话的原价首轮是一次性成本，轮数一多必然反超。别因为心疼第一轮的原价，把二十万历史拖进下一个任务。

判断「任务边界」有个简单信号：当你开始给模型贴无关文件、解释和当前目标无关的背景时，这个会话该结束了。

省法三：前缀纪律 + 通道验证

  • ✅ 推荐：AGENTS.md 和全局配置进入稳定期后别频繁改；换模型通道后，先跑一组 A/B 确认档位参数真的生效，再按攻略调参。
  • ❌ 避免：一边调着 model_reasoning_effort 一边看后台总消耗，「感觉省了」。
  • 理由：前缀一变缓存全失效（省法三的第一半）；参数被兼容层吞掉时，开关是装饰（第二半）。两个都是「动作做了、钱没省」的典型。

换通道的验证 SOP 两步：第一步，同一个只读提示词跑两遍，一遍带参数覆盖一遍不带；第二步，翻各自最新的 rollout-*.jsonl，对照 turn_context 的档位值和 reasoning_output_tokens 占比。两边对得上，参数才是活的；对不上，先把通道的问题解决了再谈优化，否则你优化的是想象中的账单。

反模式集

胖 AGENTS.md 当笔记本。 最常见，也最贵。注入结构决定了文档每个字都进指令区，每轮重发一遍，50 轮就是几十倍的自乘；更糟的是它站在前缀顶端，把缓存命中率一起拖下水。写进去之前问一句：模型违背这条会产出错误结果吗？

一个会话跑一天。 上午的 bug、下午的重构、晚上的文档，全在一个 session 里。每一条新指令都拖着全天历史跑，输入曲线只会更陡。这类用法还有个隐蔽代价：上下文越杂，模型对你当前任务的注意力越稀，答非所问的概率跟着涨——账单和答案质量一起恶化。

迷信档位开关。 攻略说调 low 就调 low，从不验证。我这个通道实测参数没透传——你调的可能和我的一样，是个空开关。验证只要两分钟：对照 turn_context 的档位值和 reasoning_output_tokens 的占比，下发了没执行，数据不会说谎。

频繁改全局配置。 全局 AGENTS.md 是所有会话的公共前缀，改动一次，所有会话的缓存链一起断。全局层的纪律应该是「季度级稳定」：只放长期不变的习惯，拿不准的先放项目层试跑一段时间。

贴图不看大小。 一张截图的输入成本顶得上一大段文字，而信息密度往往更低。值得贴的是报错对话框、关键的那一行日志；不值得贴的是整屏 IDE。贴之前裁一下，省的是每一轮的重复输入，这笔钱同样按调用次数复利。

两个常见问题

订阅制用户需要管这些吗？ 钱上不敏感，但机制完全一样——重发消耗的是你的限额和速率窗口，长会话照样把你顶到限流。流水里的 rate_limits 字段在官方通道下会给出窗口用量，订阅制把它当仪表盘看，判断「该不该 /new」比凭体感准。

换别的模型通道，结论还成立吗？ 每轮全量重发是 Codex 客户端的行为，跟通道无关，一定成立；缓存折扣和档位透传是通道行为，换了就要重新验证——方法就是本文的受控 A/B，两个目录各跑一遍，看 token_count 流水。这套流程本身比任何一条具体结论都耐用，通道年年换，流水永远诚实。

结尾

952 万那个会话，最后压缩、重置、瘦身三招下来，同规模任务的计费 token 降了一半还多。但回头看，真正值钱的不是省下的钱，是我第一次看清了钱的去向：144:1 的输入输出比告诉我，编程 Agent 的成本大头根本不在生成，在记忆——在你允许什么东西每一轮都重新进一次上下文。

AGENTS.md 每轮计费，所以它是合约不是笔记；历史只涨不降，所以会话是耗材不是容器；缓存认前缀，所以稳定本身就是优化。至于那些开关和参数，在验证生效之前，一律当它不存在。

管住进上下文的每一样东西，账单自己会下来。
