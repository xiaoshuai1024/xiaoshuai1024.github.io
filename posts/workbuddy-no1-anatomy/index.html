拆完 WorkBuddy 的 1GB 客户端,看懂了腾讯做 AI 办公的打法

WorkBuddy 是腾讯 2026 年 3 月发布的 AI 办公工作台,上线四个月就坐上了国内 AI 办公智能体桌面端月活第一的位置:第三方榜单给它的数字是 1115 万,第二名百度搭子是 674 万。围绕这个第一,争议同样热闹:有港股报道说它月活 2000 万,知乎上有文章专门质疑这个数字的统计口径,36氪则泼了盆冷水:离腾讯想要的十亿级超级应用,还差 70 倍。

吵数据的人很多,拆产品的人很少。质疑派没拆过客户端,捧场派也拿不出机制层面的证据,争论停留在表态层面。

我把国内版 WorkBuddy 5.5.6 的 macOS 客户端完整拆了一遍:安装包、进程结构、打包代码、依赖清单,能看的地方都看了。这篇文章把拆到的东西按机制摆出来,最后回答标题里那个问题——这个第一,含金量到底怎么算。

先给一个判断框架:看懂执行型 AI,先看它的工具箱

大多数人第一次用 WorkBuddy 都有个错觉:这不就是个聊天窗口吗,和网页版大模型有什么区别?

区别在于:网页版大模型只能「说」,WorkBuddy 能「做」。你说「帮我把这个季度的数据整理成周报」,它真的会去打开文件、读内容、算数字、写文档、存到你指定的位置。这一类产品现在叫执行型 AI,或者叫 AI Agent(智能体):它和大模型聊天的部分只是入口,真正值钱的是后面那条执行链。

判断一个执行型 AI 靠不靠谱,我有个简单框架,三步:

第一步看工具箱:它能实际操作什么?是只能读写文件,还是能跨应用、能上网、能跑命令?工具箱的深度决定了它能替你干的活的上限。

第二步看连接方式:它和微信、飞书、钉钉这些办公软件是怎么对接的?接口是谁做的,权限怎么给,这条链路决定了它是在你的工作流里干活,还是只能在你眼前表演。

第三步看数据去了哪:你的文件、聊天记录、任务内容,哪些留在本机,哪些上了云?这决定了你敢把多少真实工作交给它。

下面按这三步逐层拆。结论的方向是:WorkBuddy 的工具箱和连接方式,做得比大多数人以为的认真;但它的第一,同样离不开一条别人拿不到的连接。

第一层解剖:1GB 的客户端里装了什么

动手拆之前,先交代版本和环境,所有证据都基于以下事实,你可以自己复现:

  • 国内版:官网 workbuddy.cn,dmg 安装包 509MB,版本 5.5.6(build 38337834),应用装完后占 1.0GB 磁盘
  • 国际版:官网 workbuddy.ai,5.5.2,dmg 490MB,com.workbuddy.workbuddy-ai——和国内版(com.tencent.workbuddy.mac)是两个完全独立的应用,连版本号都不同步
  • macOS 最低要求 11.0,Apple Silicon 优先

第一眼就值得说的数字:1.0GB。作为对比,我之前拆过 Claude Code 的 307MB 二进制,当时觉得已经够重了,WorkBuddy 直接是这个体积的三倍多。多出来的体积是什么?往下看。

启动后开进程列表,能看到一条很有信息量的东西:除了正常的界面进程,WorkBuddy 还跑了一个常驻守护进程,命令行是 daemon-app-server-entry.js --stdio。也就是说你关掉窗口它还在后台活着,像微信一样挂着,随时等任务、等推送。这是消费级产品的设计——没人希望 AI 同事「下班」。

渲染层进程的启动参数里还有个细节:自定义协议列表里有 vscode-file。这个协议是 VSCode 系产品的指纹,说明它的界面层和腾讯自家的 CodeBuddy(代码助手)共享了同一套技术框架。办公工具和编程工具同源,这就是官方说的「同源底座」——一个技术团队,两条产品线,边际成本很低。这是腾讯做这款产品的第一个打法:不重新造轮子。

第二层解剖:它给 AI 配了一整套工具箱,连 zsh 都自带

这是整篇文章里我认为很值得展开的一个设计。前面说 WorkBuddy 能「执行任务」,那执行靠什么?靠调用命令行工具。但这里有个所有同类产品都会撞上的墙:普通白领的电脑上,根本没有开发环境。

一台典型的 Windows 办公电脑,没有 grep,没有 shell 脚本环境,什么都没有。如果 WorkBuddy 依赖用户机器上的工具,那它对 90% 的目标用户直接不可用。

腾讯的解法是:把工具箱打包,随安装包分发。拆开它的代码包,资源目录下有一个 cli 文件夹,里面是这样几样东西:

  • zsh-macos:一个完整的 zsh shell。用户电脑上不需要有终端环境,它自带一个
  • toybox-macos:Toybox 是一个把上百个 Linux 基础命令(ls、cp、grep、find 这些)打包在一起的开源项目,塞进一个可执行文件。Linux 世界里它常用于嵌入式设备,这里被用来给 AI 凑齐全套命令行工具
  • ripgrep:Rust 写的高速文本搜索工具,代码圈公认速度领先的 grep 替代品
  • node-pty:伪终端库,让 AI 能像人开终端一样开一个真实的 shell 会话
  • sandbox 和 shim:沙箱与垫片层,给这些工具的活动范围上锁

这一套组合的意思是:AI 执行任务所需的全部「手和脚」,和产品一起安装,零依赖。用户双击安装包的那一刻,就拥有一台「AI 可操作的电脑」,不管那台电脑原本多么干净。

对比一下这个领域其他玩家的做法:Claude Code 和 DeepSeek Harness 这类开发者向产品,默认你的机器上什么都有,工具是「借用」用户环境的;WorkBuddy 是「自带」环境。前者省事但对用户有门槛,后者安装包膨胀到 1GB 但把门槛压到零。四个多月冲到千万月活的产品决策,和它 1GB 的体积,是同一个决定的两面。

工具箱之外,还有两个文件夹值得点名:

native/turing-sdk:腾讯图灵平台的 SDK,负责客户端侧的安全与风控上报。配合进程参数里的 --enable-sandbox(macOS 沙箱),执行引擎的活动半径被框住了——AI 能跑命令,但跑在哪、能碰什么,有一层壳约束着。

native/wechat-copydata-decoder:名字直译是「微信拷贝数据解码器」。这个 native 模块的存在说明,它和微信之间有一条应用层的直通管道;走的不是公开的剪贴板协议。微信数据怎么进工作台、边界在哪,这段代码没有文档,但它证明了两边对接的深度——这是后面第三步的前哨证据。

第三层解剖:连接器不是插件市场,是三套企业级 SDK

聊 WorkBuddy 绕不开「连接器」。官方把「能连微信、飞书、钉钉」当作核心卖点,很多报道把它写成「装了个插件」。拆完依赖清单,我要纠正这个理解:连接器的含金量,看它的依赖列表就知道了。

在它的依赖声明里,同时出现了三个大厂的企业级 SDK:

  • @wecom/aibot-node-sdk:企业微信 AI 机器人 SDK
  • @larksuiteoapi/node-sdk:飞书(Lark)开放平台官方 Node SDK
  • dingtalk-stream:钉钉开放平台的流式订阅 SDK

这三个不是简单的「发送消息接口」。企业 IM 的开放平台 SDK 意味着:消息事件订阅、身份与权限体系、回调验签、文件传输这一整套企业级通道。也就是说,WorkBuddy 在你的飞书群里不以「模拟人在打字」的方式干活;它以一个合法应用的身份注册进去,收消息、回消息、拿文件、发文件,走的全是官方协议。

对接用的协议标准叫 MCP(Model Context Protocol,模型上下文协议)——一个让大模型安全调用外部工具的开放标准,它依赖清单里明确写着 @modelcontextprotocol/sdk 1.24.3,这是目前该协议的较新版本。你可以把 MCP 理解成 AI 和应用之间的「国标插头」:应用按标准暴露能力,AI 按标准发起调用,中间不用逐家定制。

连接器商店里的几百个连接器,背后大部分是这套机制的复用:标准协议管「怎么调」,各家的开放平台 SDK 管「调到哪」,剩下的长尾应用才用 HTTP 接口补充。这就是我说的「第二步看连接方式」的答案:它不在浏览器里表演自动化;它在你的工作流里占了一个正式编制。

还有一个容易被忽略的证据,装完应用就有了:macOS 的扩展目录里躺着一个 WechatShare.appex——微信分享扩展。你在微信里看到的内容可以直接分享进 WorkBuddy 处理,这条入口是系统级的。

到这里,「工具箱」和「连接方式」两步拆完了。该回答那个争议问题了。

数据口径:1115 万、2000 万、1300 万,哪个是真的

把三步框架的第三步(数据去哪了)放一放,先处理标题里的悬念——因为这个悬念的答案,就藏在数据口径里。

围绕 WorkBuddy 的月活,市面上至少流传着三个数字:

「月活 2000 万」:出自 7 月的港股行情报道,后来被知乎文章质疑「以讹传讹」。这个数字找不到官方出处,大概率是「桌面端 + App + 在线版」的某个宽口径,或者是转述走样。

「桌面端月活 1115 万」:出自第三方机构 8 月的 AI 办公智能体榜单,同榜显示第二名百度搭子 674 万、全行业桌面端月活总量突破 3000 万。口径清晰,可横向对比,是我认为最扎实的一个数字。

「日活 1300 万」:同样是行情报道口径,对应「日活/月活比 65%」的说法。如果成立,这个黏性数据非常惊人——对比一下,微信的日活/月活比大约是 80%,65% 意味着用户天天在用,装了就吃灰的成分很低。

三个数字都可能「真」,但说的不是同一个东西。宽口径的数字有它的含混,窄口径的数字有它的扎实,混着引用只会越吵越乱。36氪那篇「还差 70 倍」讲的就是这个:腾讯拿它对标十亿级超级应用,千万级月活只是起跑线。

公开数据里还有一个更硬的事实:2026 年 3 月上线当月,WorkBuddy 拿下 885 万次访问,环比暴涨 831%,上线首周用量触发了十倍扩容。7 月 5 日,「WorkBuddy 火爆」甚至把腾讯股价当天拉起来超过 5%。一个产品的增长曲线能在二级市场激起水花,这在近两年的 AI 应用里是独一份。

第三步的答案:记忆、连接器、账本,都在本机看得见

框架的第三步「数据去哪了」,登录之后有了实测答案。我把它的本地数据目录(~/.workbuddy,552MB)翻了一遍,三个发现:

记忆是本地明文文件。memory/ 目录下按用户 ID 存着一个 Markdown 文件,开头写着「User Memory Profile」,正文是一个 Memory Block,尾部挂着 JSON 元数据。所谓「越用越懂你」,机制上就是往这个块里持续写入用户偏好。对用户是好事:记忆看得见、可删除,不是黑箱。

**连接器是一份 MCP 服务器清单。**用户目录下的 mcp.json 里,每个连接器对应一个腾讯系业务的 MCP 端点:QQ 邮箱是 api.mail.qq.com/mcp,自选股是 txmcp.tdx.com.cn,证券行情是 stockbuddy.qq.com,知识库是 ima.qq.com,协议全是 streamableHttp。前文说的「连接器商店」,落到磁盘上就是这份配置文件;旁边还躺着一个 .master.key,对应依赖里的静态加密模块——连接器的凭证是加密存放的。

**任务和额度,各有各的表。**本地数据库 workbuddy.db 里,sessions 表给每个会话绑定了工作目录(cwd)字段,automations 表带着 rrule 规则(定时任务的调度配置),session_usage 表里有一个 credit_json 字段——免费额度不是一笔糊涂账,是逐会话记账的。

这层发现的含义比技术细节大:一个拿着你文件、连着你微信的 AI,把记忆、连接器凭证、用量账本都放在用户看得见的地方,并且允许你删——这是把「数据去哪了」的答案写在了磁盘上。

所以,第一的含金量怎么算:一半引擎,一半入口

拆到这里,可以正面回答标题的问题了。

**引擎那一半,是真的。**把办公场景需要的执行环境完整打包、零依赖分发,同时接通三家办公平台的企业级协议,这两件事都是重工程。同类的执行型 AI 里,开发者向的产品(Claude Code、DeepSeek Harness)解决的是「有环境的人怎么更高效」,WorkBuddy 解决的是「没环境的人怎么用得上」——后者的用户基数大一个数量级,工程上的迁就也多一个数量级。1GB 的体积就是它替用户交的学费。

**入口那一半,也是真的,而且别人学不了。**飞书和钉钉的连接器,理论上每家 AI 产品都能接;但企业微信和微信的连接器,只有腾讯自己能给到这个深度——WechatShare.appex 系统级分享、微信数据的直通管道、以官方身份入驻企业微信群。这是生态位的优势,不是工程能追平的。同样一份周报任务,别的工具要你把文件传给它,WorkBuddy 直接在你聊微信的地方接活。对普通用户来说,「不用改变习惯」这一条,比引擎里多几个工具重要得多。

一半引擎,一半入口,合起来才是 1115 万月活的完整解释。只夸引擎的人没看到生态,只骂入口的人没看到工程。这也是我拆完之后对「国产 AI 应用竞争力」这个大问题的一点新认识:模型能力大家都在追,真正拉开差距的,是分发位和工程完成度。这两样,恰好都烧钱也烧时间。

运行时实测:一份周报的全过程

机制讲完了,最后跑一个真任务收尾。我发给它的是一句典型的办公请求:「帮我在桌面新建一份周报文档,文件名 周报.docx,分三部分:本周完成、下周计划、风险与需要的支持,每部分放两条示例内容。」

界面上,执行过程是一条可见的链:深度思考 → tencent-docs-routing(腾讯文档路由)→ tencent-docx(文档引擎)→ 已读取 SKILL.md(技能说明)→ 交付文件。从回车到桌面出现文件,一共 1 分 22 秒。

三个细节值得单独说。

**它的「脑子」在云端,「手」在本地。**等待生成时,界面上写着:「我在线,只是脑子在缓冲。」这大概是全产品里把自己架构说得最透彻的一行文案:执行器装在你电脑上,推理跑在腾讯的服务器上。

**每一步都先记账。**任务开始前就给出积分预估区间(◇0.27 到 12.18),结束后显示实际消耗 ◇1.47。本地数据库里记得更细:这个会话用了 48,064 个 token,总额度 30 万,逐会话过秤。

**连文件的「出身证明」都是精心准备的。**解包生成的 周报.docx,元数据里 Application 字段写着「Microsoft Macintosh Word」,而实际生成它的是腾讯文档引擎。按 Word 的规格填写出身,是为了你把文件发给谁、用什么打开都不弹兼容警告。细节不起眼,但处处都是。

交付完成后我顺手翻了它的会话档案:这条任务自动落库,分到了自己的工作目录(~/WorkBuddy/ 下一个带时间戳的文件夹,每个会话一个)。顺带一提,我先前误发过一条乱码消息,它的反应是明确说看不懂、列出两个可能的意图、请我重发——收到垃圾输入不硬猜,这比很多聊天产品体面。

边界:三盆冷水

好的部分讲完了,冷水也得泼,不然这篇就成了软文。

**免费窗口不会一直开。**参考字节豆包的路径:先免费冲量,后按用量计费收费。WorkBuddy 当前对个人用户的慷慨是获客成本,不是慈善。它已经上线了付费档,免费额度能撑多久,取决于竞争对手什么时候跟进收费。想先用起来的人,现在是体验最完整的时候。

**分发体验有粗糙的边角。**国内版 dmg 里附带了一份 Fix-Damage.txt,教用户在 macOS 提示「应用已损坏」时用命令行清除隔离标记。这类提示通常意味着分发没走 Mac App Store、公证链路偶有缺口。产品本身没问题,但「下载后可能打不开」对小白用户是一道真实的劝退坎,官方选择发文档,没去改流程,取舍很务实。

**国际版和国内版是两个产品。**版本号不同步(5.5.2 对 5.5.6)、包名不同、登录方式不同(国际版走浏览器跳转登录)。这说明了它的海外化还在早期,两条产品线没有合并基础设施——对用户是小事,对判断腾讯的全球化投入是个参考信号。

带走三句话

如果只记三句话,我建议是这三句:

执行型 AI 好不好,先看工具箱——工具是自带的还是借用的,决定了谁能用它。

连接器是不是真对接,看它走没走官方协议——有企业级 SDK 的是编制内,靠模拟操作的是临时工。

判断增长数字,先问口径:月活、日活、访问量是三个物种,混着说的大概率在讲故事。

WorkBuddy 的登顶不是玄学:一套为零基础用户准备的执行引擎,加上一条对手拿不到的微信入口。至于这个第一能守多久,答案不在客户端里,在字节和百度下一版产品发布的时间里。
