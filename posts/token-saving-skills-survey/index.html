10 万星 Caveman 领衔：五个省 token 的开源 skill，从输出砍 65% 到上下文换血

2026-08-26 我拆过一个会话吃掉 952 万 token 的 Codex 账单，拆完的结论比账单本身更扎心：大头不是写代码花掉的，是重复读入的文件、来回贴的背景和 agent 的碎嘴。那次的补救是给自己立家规，属于纪律层。纪律管住人之后，剩下的浪费得靠工具管，社区恰好已经把工具做成了一个小生态。

我按「治哪一段浪费」把 GitHub 上的省 token skill 盘了一遍，挑出五个各有绝活的，star 数全部经 2026-09-05 的 GitHub API 重新核实，数据不写印象流。先建一个判断框架，五个 skill 正好各占一格：agent 的 token 浪费发生在四个环节，说得多（输出冗长）、想得吵（思考独白外溢）、记性差（重复喂上下文）、过程留痕多（长任务的中间步骤全量滞留）。挑 skill 先问自己浪费在哪一环，别五个全装，省 token 的工具自己也要吃 token。

这个问题是最近一年才长成主体的。此前 agent 是问答工具，一个会话十来轮，废话再多也只是零头；现在 agent 是常驻劳动力，一个任务三百轮起步，前面每一轮的冗余都被后面几百轮放大着驮。浪费的复利，是会话长度拉起来之后才显形的，这也是省 token 工具集中在这个时间点爆发的原因。

四个环节各有典型症状，开自己的会话记录对号入座就行。说得多：agent 回复动辄十行，有效信息三行。想得吵：开工前先演讲三百字思路，做完再写两百字总结，每步操作还有旁白。记性差：/clear 或新开会话之后，同样的项目背景已经贴到第三遍。过程留痕多：任务跑完滚动条回不到头，翻十个屏幕才找到最终结论。症状对上号，药方在下面五节里挑。

动手前还有个常识要垫底：agent 会话的输入 token 通常远大于输出，因为上下文每一轮都整体重发一次，聊到第 30 轮时，前面 29 轮的全部内容都在陪跑。这也是为什么省 token 的工具分成了两个战场，一头治「模型说出来的」，一头治「喂进去的」，下面五节里的每一味药都标明了战场。

Caveman：输出砍 65% 的祖师爷（103,664★）

如果你只装一个，装这个。口号是语法错误级的：「why use many token when few token do trick」。它让 agent 用穴居人腔说话：代码、命令、报错原样保留，纯聊天输出砍 65%（官方实测口径）。效果什么样，拿同一个意思的两种说法对比就懂。平常 agent 会说：「我已完成对配置文件的修改，接下来我将运行测试以验证更改是否生效。」caveman 档说的是：「Config 修好。跑 test 验证。」信息一点没少，字数去了六成。

10 万星之后它进化成了全家桶。caveman shrink 压缩命令输出的噪音，字节级可还原；caveman mem 做持久记忆，原始字节可恢复；还有一个 proxy 层，在 Claude Code 实测基准里省下 33.2% 的输入 token（官方 54 轮 pinned benchmark）。最有想象力的玩法叫 pixel mode：把 SKILL.md 正文渲染成 PNG 让模型看图，frontmatter 保持文本不影响触发，正文用图读。它的理由值得念一遍：「每个 skill 都在每次调用时重新加载完整 prompt，这笔税你永远在缴。」解法是把税基变成图片，模型读图的 token 远少于读文本。

pixel mode 的代价也直白：图里的文字没法 grep，diff 和版本对比都不方便，适合承载稳定不变的说明性内容，频繁改动的规则别放图。

真正值得抄的不是口号，是它 README 里那套压缩纪律，四条规则条条有 tokenizer 层面的理由。**第一，不造缩写。**cfg、impl、req 这类自创缩写，tokenizer 会拆成多块，一个 token 都不省，读的人还要解码；写全词反而更便宜也更清楚。**第二，不丢否定词。**not、never、no、only、except 一个都不能省，否定丢了意思直接反转，修复一次误解的代价远超省下的 token。

**第三，同价保留原形。**sees 和 see 消耗相同，就保留正确的 sees，为了装穴居人把语法改错是纯亏。**第四，风格不许倒涨输出。**压缩只减不增，不许为了「看起来像穴居人」往句子里加词。

四条纪律合起来是一个立场：压缩是工程，靠规则不靠语气，换任何模型都成立。

强度分六档：lite、full、ultra 三档英文，再加 wenyan-lite、wenyan-full、wenyan-ultra 三档文言，一条命令切换。日常我挂在 full 档，省得够多，又不至于 terse 到要看三遍才懂；ultra 档留给长批处理，反正没人盯过程，越狠越好。

挂档的诀窍是让它常驻：它对会话的持久性做得足，开一次就一直生效，不会过几轮自己漂移回废话模式。

常驻这点比听起来重要。直接在 system prompt 里写「请精简回答」的省法，前几轮有效，十几轮之后模型的服从会衰减，啰嗦悄悄回潮。skill 的持久化机制解决的正是这个：压缩规则挂在每次响应上都算激活，第 1 轮和第 40 轮一个口径。省 token 要省的是全程，不是开场。

装法本身两分钟：skill 目录放进 ~/.claude/skills/，会话里 /caveman 一敲生效，prompt 里出现「less tokens」「be brief」这类字眼也会自动挂档。读入侧的省法靠 caveman shrink，把长命令输出压成密集摘要再进上下文，要原文时字节级还原。输出侧省的是模型说话，输入侧省的是喂给模型的东西，两头一起掐，才对得起「祖师爷」这个名号。

两个月的实装体感：它的存在感是「车轱辘话少了一半」，该有的追问照常，只是回答从十行变五行；要适应的就一处，偶尔 terse 到省略主语，读的时候默认省掉的都是 agent 自己。写博客和回邮件前记得 off，这两个场景的语气是有价值的 token。

边界也要说清。写给人看的文档、对外邮件、教程正文，别开 caveman：压缩砍的是废话，也砍掉了语气和铺垫，这些在「人读」的场景里不是废话。它治的是 agent 对你说车轱辘话的那一段。覆盖 30+ agent，MIT 加 BSL 双协议。输出冗长这个所有人的第一痛点，它确实是这条赛道拿捏得最狠的。

pi-boomerang：过程换摘要，像回旋镖一样扔出去再飞回来

长自主任务是吞金兽。修一个登录 bug：读 10 个文件，改 5 处，跑两轮测试，50k token 起步，这些过程记录全量滞留在主对话里，后续每一轮都要陪着它们进位。300★ 的 pi-boomerang（nicobailon/pi-boomerang，给开源编码 agent pi 写的 skill，TypeScript）思路并不复杂：任务照常跑，跑完把原始历史整体换成一份展开式交接摘要。

作者给这个机制起了个中二但精准的名字：反向 D-Mail。《命运石之门》里 D-Mail 改写世界而观察者保留记忆，boomerang 反过来，改写观察者（历史折叠成摘要）而世界（已完成的工作成果）不变，会话树就是你的 Reading Steiner。玩梗归玩梗，机制扎实：orchestrator 拿到的是自包含的后续回合，缺什么背景摘要里就补什么，中间那 5 万 token 不再随对话滚动。

和 compaction 放在一起看差别更清楚。同样面对 50k 过程记录，compaction 是攒到阈值后被动压成一团，时机和颗粒度都不由你控制；boomerang 是在任务边界处主动折叠，折叠粒度是完整的子任务，摘要里该有什么由结构约定。止损和规划，差在一个「主动」上。

折叠时机也有讲究：摘要放在任务收口处一次性生成，不做边跑边写——边写摘要，写摘要本身就成了新的过程税。

摘要里放什么，是有讲究的。它要承载的是下一回合接手所需的全部现场，比「做完了什么」的流水账多三样东西：改了哪些文件、每个文件为什么改、验证跑到哪一步、下一个动作从哪里接。按这个思路，一份合格的交接摘要长这样：

## 交接摘要（给下一个回合的自己）
- 目标：修复 login 模块 401 循环
- 已改：auth/token.go（刷新逻辑去重）
       api/middleware.go（白名单路径）
- 已验证：go test ./auth/... 12/12 通过
- 未完成：压测脚本未跑；fallback 分支未覆盖
- 现场：改动未 commit，分支 fix/401-loop

缺了「现场」那一行，下一回合就得重新翻文件找进度，省下的 token 又从别处漏回去。五条里最值钱的恰是最后一条：没有现场行，下一回合全靠猜。凡是有子任务派发机制的 agent 都值得抄这个模式。用 Claude Code 的话不用装它，同构做法是子代理干脏活，只把结论写回主对话：派发时在任务描述里约定返回格式，收尾报告固定四项，结论、改动文件清单、验证状态、下一步。派出去的任务在子代理自己的上下文里烧，主对话只收几十行收尾，子上下文随任务销毁，烧完即弃正是我们要的性质。pi-boomerang 的价值在于把这个模式做成了 pi 上的标准件，顺手把摘要结构也调好了。

边界同样存在。三五分钟收尾的小任务别用，摘要本身的生成成本可能比省下的过程记录还贵；结对式高频互动也不合适，你要的就是盯着它每一步干了什么。它的主场是无人值守的长任务：派出去二十分钟，收回来一屏结论，过程留在子上下文里烧完即弃。

planning-with-files：把工作记忆搬到磁盘上

26,635★（OthmanAdi/planning-with-files，MIT，Shell），卖点就一行：「你的 context 会死，计划不会。」它把工作记忆拆成三个文件放上磁盘：task_plan.md 管目标与拆解，findings.md 管已确认的事实和结论，progress.md 管进度游标。每回合由 hook 把关键状态重新注入 context，/clear、会话崩溃、compaction 都杀不死这三块石头板。

三块文件各管一段记忆，fail 的方式也不一样。plan 回答「我在做哪件事、拆成几步」，findings 回答「哪些坑已经确认过，别再撞上」，progress 回答「上一轮干到了哪个文件哪一步」。compaction 之后最先丢的就是这三类信息，而它们是续命所需的最小集合，放磁盘上属于把命门挪出考场。

省钱逻辑藏在后头：上下文丢了就得重喂背景，重喂是最贵的浪费。planning-with-files 的内部基准里，带这套文件的新会话平均 5.0 回合恢复现场，裸跑要 13.3 回合；任务通过率 96.7%，盲测 A/B 三胜零负。数字是作者自测，没有第三方复核，但方向和体感一致：差出来的 8.3 个回合，每一回合干的都是重贴背景、重新找路，消耗的恰是账单里最贵的重复输入。hook 重注入也不是免费的，每回合多几十行，但那点开销对照 8.3 个回合的重贴，差出不止一个量级。

它和 compaction 的分工值得想清楚。compaction 是丢历史的止损，历史攒多了压成一团摘要，细节永久损失；planning-with-files 是让关键信息从一开始就不住在 context 里，住的文件在磁盘上，context 里只有每回合重注入的最小快照。前者是失血后的止血带，后者是让伤口别开口子，长任务两个可以一起用。

和 CLAUDE.md 的分工也顺带说清，两者不是一回事。CLAUDE.md 存长期规范：编码风格、构建命令、领域约定，几周不改一次；三文件存任务态：这个任务拆成几步、确认过什么、干到哪了，每小时都在变。静态规范和动态记忆分开放，每回合重注入的快照才能足够小，注入本身不变成新的浪费。

这套机制我自己在运营仓里天天用，形式更土：topic-funnel.jsonl 管选题状态，calibration.jsonl 管预估校准，link-map 管发布台账。会话换了一茬又一茬，台账一直在磁盘上，任何一个新会话开场读一遍文件就能接着干。Manus 把这类机制叫「石头板」，60+ agent 可装，npm、Claude Code 插件市场、npx skills 三条路都能装。第一次用不用先读文档：开工时让 agent 把任务拆进 task_plan.md，确认过的结论随手写进 findings.md，每完成一步就更新 progress.md 的游标，hook 会在下个回合把这三样接回上下文。习惯养成之后，/clear 不再是心理负担，是随手可用的清空键。上下文频繁丢失的人，这个治本。

claude-token-optimizer：专治「边干边演讲」，一个多月涨了 5 倍星

108★（2026-08-27 收录本文初稿时的核实值），2026-09-05 再核实已经 569★（nadimtuhin/claude-token-optimizer，JavaScript），一个多月 5 倍，这个赛道的热度本身就在说明问题。它扎的是另一个真痛点：agent 干活时把思考过程全念出来，猜歧义要念，试错要念，连「我现在要打开文件了」都要念。

碎嘴的代价不只是当下那几句输出。念出来的犹豫、废稿和自我纠正全量滞留在上下文里，把后续每一轮的输入都垫高，这是复利式的浪费。算一笔就明白：每轮多念 3k，二十轮任务就是 60k 滞留，后面每一轮都驮着它们跑。

它的解法是协议套件（Antigravity V1/V2、Ultimate），强迫 agent 按结构化工程流程走：先列假设和决策点，按固定格式汇报进度，替代想一出是一出的碎嘴。

碎嘴常见三种形态，对号入座。猜歧义型：「我理解你的意思是 A，也可能是 B，我先按 A 来」，这段话每次开工都来一遍，哪怕任务描述已经写明。念过程型：「我现在打开某文件」「接下来我要修改这个函数」，每步操作都配旁白。自我纠正型：写错了当场念叨「不对，重新来」，废稿原文全留在上下文里。三种形态是同一个病：把工作记忆当演讲稿念。

作者的实测表里省 76%-93%，没有第三方复核，当参考别当承诺；但「thinking out loud 也是税」这个判断，我对着自己会话的输出日志数过，成立。协议落地后的会话长相也变了：开工先交假设与决策点清单，过程汇报按固定字段走，错了直接给修正结果，现场检讨免了。碎嘴压成固定格式的骨架，token 省了，读起来反而更清楚。

这套协议的适用面比前几个窄：适合长自主任务，不适合结对式高频互动，你来我往的对话里，结构化汇报的开销反而比碎嘴大。量级小但思路典型，值得当一味针对「想得吵」的药放进工具箱。

文言文.skill：最省钱的语言是最压缩的自然语言

2★ 也必须收录（swaylq/wenyanwen-skill，MIT，Python + MCP），因为思路最野：让 AI 用文言文回答，本地 MCP 服务器免费翻回白话，「你看到的是人话，花的是古文的钱」，仓库自述能省 2-3 倍 token。

文言的信息密度天然高于现代汉语，一字千金在这里是字面意思。同一个意思，白话讲出来是「这个方案有问题，我们重新讨论一下再决定」，二十个字符；文言收成「此策有失，再议后决」，十个字符，几乎砍半，折成 token 同向受益。「之乎者也」四个虚词扛起的语法规责，现代汉语要用「的、了、被、把」加语序才能撑起来。语言选择本身就是一层压缩算法，这是五个 skill 里就它在换编码的，其余四家都在删冗余。

回译跑在本地 Python 进程里：模型输出文言，MCP server 拦截后翻回白话再进终端，不吃模型调用所以免费，代价是多一跳延迟和偶发的翻译生硬。务实版是 caveman 的 wenyan 三档：输出直接切文言，人自己读，连回译那一跳都省了。我试过 wenyan-full 挂一天，省是真省，读是真累，适合跑批结果的粗筛，不适合需要逐字理解的方案讨论。

2★ 的项目当玩具装没问题，思路的启发大于工具本身：压缩的维度不只有「说短点」，还有「换一种更密的说法」。省下的比例随内容而变：越口语的叙述密度差越大，术语和代码密不进来，拿不准就先装 Caveman，它治的环节最普适。

怎么选：一张对号表加一笔真账

对照四环节收束，选型就一张表。只认场景不认名词的话：每天开十几个短会话、重度交互的人，装 Caveman 就够；放 agent 跑夜间批处理、无人值守任务的，pi-boomerang 或自搭子代理收摘要必选；项目大、会话频繁崩溃重连的，planning-with-files 优先级最高。

我的组合拳是 Caveman（管输出和读入）加 planning-with-files（管长任务记忆），覆盖八成日常浪费。五个工具在两个战场上的落位见下图，挑药之前先看自己中弹最多的是哪一头。

起手式别贪多，五个全装只有一个效果：skill 加载税自己先吃掉一笔，加载的每一行都从你的上下文里扣。

给一个两周路线当参考。第 1 天装 Caveman，挂 full 档正常干活，晚上记下当日 token 基线。第 3 天装 planning-with-files，专治当周最长的那次会话。第 7 天回翻会话日志，找滞留最重的环节，对照四环节表决定要不要补第三个工具。第 14 天复盘，留下省得动的，卸载没用的。跑完两周你会有一张自己的四环节占比图，第五个工具装不装，让那张图投票。工具箱要定期退坑换季：caveman 写文章时 off，planning-with-files 在小项目里是纯开销，减法同样是省法。

动手前先把量具装上。Claude Code 里 /cost 随时看当前会话的花销，Codex 后台有会话级用量明细，rtk 这类压缩工具自带 gain 统计。没有量就没有优化，感觉省了和真省了之间差着一个数量级。

真账摆在这里。我这台机器上常驻一套命令输出压缩管线 rtk，2026-09-05 查 rtk gain 的累计数：4279 条命令，输入 4.7M token，省下 4.1M，87.9%，这个累计数还会随每条命令继续涨，账是活的。拆开看大头更直观：rtk read 砍掉 2.9M（文件读取输出的压缩），rtk grep 砍掉 1.1M（搜索结果降噪），读和搜正是 agent 消耗的最大的两块。它和上面五个 skill 不在同一层：rtk 压的是工具输出，skill 管的是 agent 语言，两层叠起来才是完整的省法，agent 说得省，工具回得也省。rtk 九天实测的完整用法我另写过一篇 field notes，这里不展开。

提醒一句口径：caveman 的 65% 是输出口径，proxy 层 33.2% 是输入口径，会话账单里输入占比通常更高，别拿 65% 直接套总账单的预期。
