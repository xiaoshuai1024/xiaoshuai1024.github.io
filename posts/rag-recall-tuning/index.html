RAG 答不准,大部分人的第一反应是换 embedding 模型。换完还是不准,再调阈值,再换更大的模型——循环两轮,准确率原地踏步。

这不奇怪。文档要被检索命中,得先走完四步:切片 → 向量化 → 匹配 → 分级。切片把文档拆成语义单元,向量化把语义表达成数值,匹配把 query 和文档对起来,分级决定这些结果怎么用。四步各管一段,任何一步做错,后面的步骤都救不回来。

这篇把「怎么把四步分别做对」讲透。线上做过的讲做法,还没做的(混合检索、重排)讲原理和决策,不装作上线过。

结论先放这:召回率上不去的瓶颈,通常不在模型,在切片边界和检索结构。

一、先对现象:换了模型,准确率纹丝不动

运营文档问答,基准集准确率早期在 60% 上下。我们调了两周提到 85%,贡献最大的两件事都跟模型无关:

  1. 切片从"照搬英文 500 token"改成"中文 400 字 + overlap 100 字"。
  2. 检索从"只调 topK 和阈值"改成"四步链路分别做对"。

embedding 模型最后才换了一次,换完的收益远小于前两件事。这背后是个反直觉的事实:embedding 模型对中文的理解差异能带来约 20% 的准确率差,但切片切碎了,模型再好也拼不回被切成两半的信息。

顺着这条线,把四步逐段拆开。

二、切片:让每个 chunk 是一个完整语义单元

为什么必须切片

大模型上下文有限,不能整篇塞。但更关键的是检索的粒度问题:query 往往只有一句,文档却有几百句。整篇文档只对应一个向量,这个向量是几百个句子压缩出来的"平均脸",每个句子的特征都被稀释了,query 和它算相似度,没有哪个单句能"冒尖"。切片把文档拆成多个语义单元的向量,query 才有机会打准某一句具体的话。

token 切片和中文的坑

切片的做法是按 token 滑窗,贴着自然边界走。我们用的 Spring AI TokenTextSplitter:

new TokenTextSplitter(500, 50, 50, 100, true)
// chunkSize=500, overlap=50, keepSeparator=true(保留段落分隔符)

keepSeparator: true 让切片尽量贴着段落走,而不是纯按 token 硬切。这是初步的结构感知,它在标点和段落附近找切点,代价最小。

中文切片的第一坑:不能照搬英文的 token 数。英文一个 token 约 0.75 个单词,500 token 约 375 词,是一段完整的英文段落;中文一个汉字约 1.5–2 个 token,500 token 只有 250–330 字,一段都装不下。我们早期照搬 500 token,中文文档切得特别碎,检索经常命中半句话。后来改成按中文字符调,400 字 + overlap 100 字,才切得合理。中文 RAG 的参数要在中文语料上重调,英文教程的默认值是写给英文的。

切碎了会怎样

关键信息横跨两个 chunk 的边界。比如"上架流程第 3 步需要运营确认,确认后 24 小时内生效",如果恰好从"确认"中间切开:第一个 chunk 有"需要运营确",第二个有"认后 24 小时内生效"。两块的信息都是残缺的,命中哪个都答不准。overlap 的作用就是让这种事故不致命:跨块的信息至少在一个 chunk 里是完整的。

切片要保证的,是每个 chunk 尽量是一个完整的语义单元,也就是一个能独立回答问题的意思团块。“上架流程:创建商品、填写信息、提交审核、审核通过后生效"是一块;“审核部门是运营中心,处理时效 24 小时"是另一块。两者各自完整,拆开也不丢信息。判断标准很简单:把一个 chunk 单独拿出来,读者能不能看懂它在说什么?能,就是合格的切片。检索是在向量空间里算相似度,query 只有打进正确的语义单元,相似度才有意义,打歪到相邻单元,分数再高也是错的。

优化一:overlap 买保险

overlap 100 字,约是 chunk 的四分之一。这个比例是经验平衡点:成本是存储和 embedding 的冗余(同样的内容多存了几成),收益是跨块引用被保住。overlap 太大,等于把 chunk 撑大,检索精度下降、噪声变多;太小,又兜不住跨块引用。四分之一能覆盖大多数跨块引用,又不显著稀释信号。

优化二:结构感知和父子切片

比 token 滑窗更贴近语义的做法,是先把文档结构识别出来再切:Markdown 的 ##、HTML 的 <h2> 就是天然的语义边界,在标题处切,每个 chunk 正好是一个完整小节,标题本身也进 chunk,检索时甚至能直接命中标题。我们目前的 keepSeparator 只做了初步的结构感知,更精细的"按标题层级切"是演进方向。这条线值得做,但别一上来就做:等基础 RAG 跑稳、确认失败模式确实是"上下文不足"再上,否则容易陷在调参里。

父子切片是结构感知的进阶:小 chunk 负责检索(命中精度高),大 chunk 负责喂给模型(上下文完整)。检索命中一个小 chunk 后,回溯它的父级大 chunk(比如整节)拼进 prompt。它解决的是"检索到细节但上下文不足"的矛盾:检索粒度要细,回答上下文要全,一个 chunk 同时满足两者很难,拆成两套粒度就都满足了。

父子切片的落地,靠 metadata 把两级粒度关联起来:小 chunk 的 metadata 里存 doc_id 和 section_id,父级大 chunk 用同样一组键存。命中 child 后,按 tenant_id + doc_id + section_id 把 parent 取出来喂模型。检索粒度是 child,回答上下文是 parent,两全。

Map.of(
    "tenant_id",  tenantId,
    "doc_id",     docId,
    "section_id", sectionId,  // child 归属的小节
    "level",      "child"     // child / parent 两级
)

优化三:递归切片

另一种思路:先按段落切,段落超长再按句子切,句子还超再按子句切,直到每块达到目标大小。每块尽量是完整语义单元,而不是从中间硬切。这类实现比固定 token 滑窗更贴语义,代价是实现和调试成本。

切片的落地判断

切片优化前,先诊断失败模式:

  • “检索到了但答错” → 上下文不足,该加 overlap 或结构切片。
  • “根本没检索到” → 召回问题,切片再优化也救不了。

别在错误的层使劲。切片只能保证"分得对”,保证不了"找得到”——那是匹配那步的事。

三、向量化:embedding 是地基,别选错

切片决定了信息怎么切,向量化决定了语义怎么表达。这一层最容易踩的坑,是"选了个通用模型就上线"。

模型选型:中文专用优先

embedding 模型第一原则是语言要和语料一致。中文文档用中文预训练的模型,别拿通用多语言模型顶。多语言模型对中文的理解是"够用",不是"好";中文专用模型在中文语义上明显更强。我们早期用通用模型,运营文档检索质量一直上不去,换成中文优化过的本地模型后,同样的切片和阈值,准确率直接跳一个台阶。embedding 模型是 RAG 的地基,地基选错,后面调参再久都是白费。

本地部署还是云 API

我们用本地 BGE(bge-small-zh-v1.5),理由有三个:私有文档不出内网(数据合规)、成本为零(不按 token 计费)、模型随时可换。云 API(OpenAI text-embedding 这类)的好处是省心、效果好,但每次入库都出网、按量计费,文档量大时是持续成本。选本地的判断:知识库规模可控、对延迟和成本敏感、数据不想出网:我们就是这三个条件。

维度和领域适配

维度不是越高越好。bge-small(384 维)对运营文档这种语义相对直白的语料完全够用,还快。更大模型维度更高、表达更细,但索引更大、查询更慢。真正决定上限的是"语义单元切得对不对"和"语言对不对",维度是锦上添花。

领域词是另一个坑:如果语料里有大量行业黑话、专有缩写(“PDD"“履约"“铺货”),embedding 模型没学过这些词,近义能力就弱,换个说法可能就召不回。两条路:攒语料微调 embedding,或者搭配 BM25 做字面检索互补。先走后一条,成本低见效快,匹配那步展开讲。

换模型必须重建索引

embedding 一变,旧向量和新 query 的向量不在同一个空间,检索会全面失准。重建是换模型的另一半工作,漏了它,换模型反而把线上打挂。

四、匹配:相似度、阈值、多路召回

切片和向量化把文档准备好了,匹配负责让 query 找到它们。这一步要解决三件事:相似度怎么算、阈值怎么定、单路不够怎么办。

相似度怎么算,阈值怎么定

向量检索本质是算 query 向量和文档向量的距离。文本语义一般用 cosine 相似度(0 到 1,越接近 1 越像),它不关心向量"长度”,只关心方向,更贴合语义。

分数要有手感:0.7 以上大致是"主题相关”,0.5 附近是"沾边",0.3 以下是"无关"。阈值定多少取决于语料和问题类型:强相关场景(答案必须来自文档)卡高一点,0.7;开放问答(允许模型用自己的知识补)0.5 就够。阈值卡太死,该召回的漏了;卡太松,噪声进 prompt。它还要跟 topK 配合:阈值决定质量下限,topK 决定数量上限,先调阈值保证质量,再调 topK 保证够用。

metadata filter:先缩候选池

这是我们已经落地的做法。所有租户共用一个 ES 索引,检索时强制 tenant_id == 当前租户,再按 doc_type、tags 二级过滤。它的意义不止隔离,还在于命中率:先在"正确的池子"里找,而不是在全世界找。匹配的第一步优化是收窄候选池:从全量缩到一个租户的运营文档,相同条件下命中率天然高一截。

词表漂移:BM25 互补

单路向量检索有天然的盲区,就是词表漂移:query 说"退货",文档写的是"退款流程",字面完全不同、语义相近,向量靠 embedding 的近义能力能接住一部分。但专有名词、型号、代码、活动 ID 这类"必须字面对上"的检索,向量不擅长。查"PDD-2024 活动规则",文档里就是这个字段名,向量检索可能把语义相近的其他文档排前面,反而漏掉字面完全匹配的那个。

查询类型例子向量BM25
语义改写“怎么退款” vs 文档写"退款流程"强弱
专有名词 / 型号“PDD-2024 活动规则”弱强
混合“双十二的退款规则”中中

单路向量检索在这张表里只覆盖第一行。多路召回让向量(稠密·语义)和 BM25(稀疏·字面)两路都跑,再融合排名,把三行都覆盖,漏的自然就少。

两路的分数不能直接相加:一个是余弦相似度,一个是 BM25 的统计分数,量纲完全不同。RRF(Reciprocal Rank Fusion)按排名融合:每个文档在各路的排名折算成分数求和,把"两路都排在前面"的文档顶上去。它只关心排名先后,不关心分数大小,恰好绕开两路分数不可比的难题。ES 原生支持 BM25 + 向量 + RRF 融合,这是我们在《RAG 没那么神》里预告过的演进方向,做混合检索时不用额外引入中间件。

举例看 RRF 的偏好:文档 X 在向量路排第 2、BM25 路排第 5,得分 1/(60+2) + 1/(60+5) ≈ 0.031;文档 Y 向量路排第 1、BM25 路没进前 10,只有 1/61 ≈ 0.016。两路都靠前的 X,反超单路第一的 Y,这就是 RRF"两路都认可"的偏好。

query 改写与扩展

另一条提高命中率的路线是改 query 本身:把"退货"扩展成"退货 退款 售后"再检索,或把 query 分解成多个子查询并行检索再融合。前提是召回率诊断显示"换个说法就能查到"。这条我们还没做,优先级排在混合检索之后,先解决"两路互补"的架构性漏,再解决"说法不对"的单点漏。

五、分级:结果按置信度分档用

匹配把结果找回来了,分级决定这些结果怎么用。这一步最容易被忽略,但它直接决定"答得准不准"。

为什么分级

检索结果不是一个 0/1,是一个连续分数。把 topK 全部拼进 prompt 的问题:高分的往往就一两个,剩下的是"沾边"甚至"无关"的,全塞进去反而稀释信号、误导模型。分级就是按分数把结果分成几档,不同档用不同策略。

三档策略

一个可参考的分档:

  • 高置信(≥0.75):直接拼 prompt,正常作答。
  • 中置信(0.5–0.75):拼 prompt,但告诉模型"以下内容可能与问题不完全相关",让它保守作答,或转人工确认。
  • 低置信(<0.5):不拼 prompt,明确拒答或回退纯 LLM。知识库里没有,就答"不知道",别硬编。

三档的阈值不是固定的,它取决于你的语料相似度分布。做法:拿一批真实问题跑一遍检索,看相关结果集中在哪个分数段,再把档位切在分布上。用数据定档,别拍脑袋。

分级和缓存、拒答联动

分级不是孤立的,它和下游策略共用同一个分数。我们系统里的语义缓存用的阈值是 0.92——它其实就是一个更严的"高置信档":query 和缓存命中足够像,直接复用缓存结果,连检索都省了。检索侧的基础阈值 0.7 是"中置信下限",0.7 以下的结果默认不采用。缓存、检索、拒答,都在同一个分数轴上分级,只是档位松紧不同。

把可信度传给模型

光在检索层分级还不够,要把"这些结果可信吗"传递给模型。prompt 里明确写:“如果检索结果与问题不相关,回答’不知道’,不要编造。“这条约束看着简单,能挡住大部分瞎编:模型不是不会说"不知道”,是默认不说,你要明确告诉它。低置信档配合这条 prompt,才能把"硬编"挡在门外。

六、精排与底层算法

四步做对,召回率已经能上一个台阶。再往上,是精排和支撑它们的算法。

rerank:把最相关的顶上去

多路召回把候选池做大了,但顺序不一定对。如果只取 topK=5,排在前面的不一定最相关,因为向量检索用的双塔模型本身精度有限。双塔(bi-encoder)让 query 和 doc 各自独立编码,最后一步才算相似度,快但交互不足;交叉编码器(cross-encoder)把两者拼成一句过一个完整的 Transformer,逐词比对,准但每个候选都要单独过一遍模型。

所以两阶段是标准结构:第一阶段粗排,向量检索 topK 放到 50(便宜),把候选从全库缩到几十;第二阶段精排,cross-encoder 对 50 个候选逐一打分重排,取前 5 拼进 prompt。如果一开始就 topK=5,再好的重排也救不了"第 6 名才是对的”。这是"先宽后窄"的工程取舍。接法示意(我们评估重排时的接入结构):

List<Document> cands = vectorStore.similaritySearch(
    SearchRequest.builder().query(q).topK(50).build());   // 粗排放宽
cands.sort((a, b) -> reranker.score(q, b.getText())
                        - reranker.score(q, a.getText())); // 精排打分
List<Document> top = cands.subList(0, 5);                   // 取前 5

重排模型选型的两个原则:模型语言和语料一致(中文语料用中文预训练的 cross-encoder,和 embedding 是同一个坑);规模按 qps 预算选,别无脑上最大的。以 bge-reranker 系为代表的中文重排模型,单候选打分几十毫秒,50 个候选约一两秒,交互问答场景这就是预算上限,候选数要按延迟倒着砍。

什么时候别上重排:知识库小(几千个 chunk,粗排 topK 已经够准)、延迟敏感、粗排结果已经"第一个就是对的"。我们的系统目前还没上重排,就是因为瓶颈在召回层,先补召回,排序精度是下一层的事。

底层算法:理解取舍才不拍脑袋

这些算法不必会手写,但要理解取舍,调参和选型才不是拍脑袋。

HNSW 把向量组织成分层的图:上层稀疏、边很长,负责"跳得远";下层稠密,负责"走得细"。查询从上层往下,平均复杂度降到近似 O(log n)。代价是近似,用 efSearch 在精度和速度之间换。ES 的向量索引默认就是 HNSW。

BM25 是稀疏检索的黄金标准,三个要素:词频饱和(一个词出现 3 次和 30 次,贡献增长越来越小)、逆文档频率(越少文档出现的词权重越高,生僻词一票顶万票)、文档长度归一(长文档的词频除以长度比例)。这解释了为什么它对精确词、术语、短查询强。

RRF 融合多路排名:score = Σ 1/(k + rank_i),k 常见 60。排第一得 1/61,排第十得 1/70,梯度平缓,不会一票定生死。它不依赖各路分数可比,只依赖排名先后。

四个机制的心智模型:向量管"意思像不像",BM25 管"字面像不像",RRF 管"把两路都认可的和稀泥成一份排名",HNSW 管"让向量也搜得快"。

七、调优方法论:顺序、测法、边界

按失败模式调,别东一榔头西一棒子

召回率低,先诊断是哪一类失败:

检索到了但答错        → 上下文不足     → 加 overlap / 结构切片
没检索到但瞎编        → 阈值卡太松     → 调高 similarityThreshold + 强制拒答
召回太多、模型选错   → topK 太大      → 减 topK + 调高阈值
该查到的没进候选      → 召回漏         → 多路召回(BM25 + 向量)→ 融合 → 还不够再重排

基准集与指标

判断调优有没有效,靠固定基准集,不靠感觉。基准集要覆盖三类问题:单文档可答(答案在一个 chunk 里)、跨文档综合(要综合多个 chunk)、无答案(知识库里没有,期望模型说"不知道")。第三类最容易被漏掉,但它是测"不瞎编"的唯一手段。RAG 最怕知识库里没答案时模型硬编。我们的基准集里"无答案"类占三成,专门盯拒答能力。基准集固定后,改一个参数跑一遍,看命中率和准确率的变化,调参才从玄学变成实验。

这里要分清两个指标:命中率衡量"找没找到"(正确的 chunk 在不在 top-k 里),准确率衡量"答没答对"。调召回看命中率,调 prompt / 模型看准确率,别混。命中率低是检索层的事,准确率低可能是模型或 prompt 的事,用改 prompt 去补命中率,方向就反了。

边界与反例

  • 切片不是越细越好。 太细,一个答案散在多个 chunk,模型拼不齐;太粗,一个 chunk 混多个话题,命中率下降。400 字是文档类内容调出来的,代码、FAQ、表格各自要重调。
  • 重排补不了漏。 漏在召回层,精排只能在已召回的结果里排序。先确认漏的类型,再决定加路还是加精排。
  • 每加一层都要算延迟账。 多路召回、重排都是实打实的耗时,交互问答场景用户等不了两秒。先量端到端延迟,再决定能不能加。

心智模型总结

四步链路各司其职:切片管语义完整,向量化管语义表达,匹配管找得到,分级管用得对。用后面的手段补前面的漏,是调优里最大的浪费。顺序永远是从前往后:先保证切得对,再保证表达得对,然后保证找得到,最后决定怎么用。

这也是我们整套 RAG 系统的调优路线:切片调参做完了,下一步是多路召回,再评估重排。embedding 模型好还是坏,只是这条链路上的一块地基。
