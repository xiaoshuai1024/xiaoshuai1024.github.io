你的 AI 代码全绿也不代表能上线：407 个疑点只 4 个为真

xiaoshuai1024 included in AI 工程
About 300 words 2 minutes 
Contents

问你一个问题：AI 写的代码，编译过了、测试全绿，你敢直接上线吗？以前我敢，直到某个周二下午。前端调的接口是 orders，带 s 的；后端一重构，路由改成了单数 order。一个字母的差别，编译两边却都绿，单测各自都过，然后运营走过来，轻描淡写地说：小程序白屏了。

这个下午让我把「验收」两个字重新想了一遍，最后落成两道关：代码这道关用四道契约闸拦接缝错误，长相这道关用代码审计判 vision 的真伪。全绿和能上线之间，隔着的就是这两道关。绿灯只是起点，可复核的绿灯才是通行证，这一句是全文的总纲，后面两道关全部从它展开论述的部分。这篇把它们各自拆开，连它们自己翻过的车也一并讲——门禁也是代码，是代码就会骗人，这话后面有实锤为证。

一、错在层与层的接缝上

白屏那种 bug 最烦的地方，是这种 bug 最烦的地方在于每一层单看都对。前端按约定调 orders，后端按重构计划改 order，谁都没有做错什么，错在层和层的接缝上——编译器只保证语法契约成立，保证不了前端发的请求真的能落到后端注册的那个路由上。这就像拼音输入法永远查不出你在骂人，字全对，意思全错。排查它也格外磨人：日志里没有报错，监控里没有异常，每次都从「前端说后端改了接口」「后端说没动过约定」的对峙开始，最后靠一个字母一个字母对出来。

跨层契约一共四类，每一类都让我们吃过亏：URL 对路由、SQL 表名对建表脚本、权限 key 对种子数据、迁移版本号唯一。它们的共同点是编译器一个都不管，而且都是声明式的——路由是注解声明、表名是 SQL 声明、权限是注解声明、版本号是文件名声明。

声明式这个属性是整件事的支点。声明写在固定位置，事实源就固定、可解析，脚本能从权威位置读出「正确答案」，再去和实际引用做比对。权限 key 拼错一个字母，权限等于没配，接口对全网裸奔，这种事故只能靠声明比对拦，靠 review 靠运气都不行。四类里最不起眼的是迁移版本号：两个分支各加了一个 V12，各自环境都好好的，合并到主干，迁移框架启动失败，整个服务趴窝。这是合并冲突的另一种形态，编译器同样不管。

顺带说一个被人低估的成本：靠人验收，结论既不可复现也不可传承。同一个页面，今天的小张说可以，明天的老王说间距不对，没有客观标准，验收质量取决于当时谁在审；人审过的页面出了问题，你没法回溯「上周验收时这个间距到底量过没有」。自动化验收的深层价值，就是把「当时谁在看、什么标准算过」固化成可复跑的脚本和可留存的报告，验收从一次性人工判断变成可追溯的工程产物。

AI 在这类错误面前格外脆弱，原因不是它笨，是它的上下文天生局部。它改后端 Controller 的时候，视野里是 Controller 的代码，前端 axios 调用了什么它根本看不见；它改前端的时候，后端路由注解同样不在视野里。两个文件同时打开都未必对得上，何况 AI 一次只看一个文件。它改了路由却不同步前端，不是偷懒，是它压根不知道前端在调这个。四类契约逐一套上去全是同一个形状：改后端看不见前端，加权限看不见种子，写 SQL 看不见建表，每个 Agent 都不知道别的 Agent 加了什么迁移。

二、第一道关：四道契约闸

既然 AI 不知道，就让脚本替它知道。我在提交之前架了四道闸，全部挂在 pre-commit，四道全过才允许提交。

闸守什么拦过什么
一前端 URL 必须有后端路由接住少个 s 的路由改名
二SQL 里的表名必须在 DDL 里建过Mapper 拼错表名，运行时才炸
三权限 key 必须在种子数据里注册过key 拼错导致接口裸奔
四迁移版本号不许重复两个 V12 撞号，服务起不来

原理很朴素：prompt 是建议，AI 可能忘；脚本是法律，它忘不了。AI 不需要知道前端在调什么，脚本替它查，查不过就拦下，拦下就逼它补全。在 prompt 里反复叮嘱「改路由记得同步前端」，可靠性远不如一道闸——建议会被忘，强制不会。

四道闸各自都有几处值得交代的细节，全是跑出来的。

闸一最麻烦的是动态路由。后端注册 @GetMapping("/{id}")，前端调 /api/order/123，字符串精确匹配会判「不存在」。解法是扫到带花括号的路由就转成正则模式，前端地址命中模式即算通过。不处理这个，闸一会误报一大堆，开发者被误报烦了就会把闸关掉——被误报杀死的门禁，比比皆是。闸二有个要诚实交代的局限：它只查表名，不查字段名。字段名拼错要靠跑真实 SQL 的集成测试去抓，这是静态扫描的天花板，认清边界才不会对契约闸抱过高期待。闸三最容易被低估：权限 key 拼错是越权风险，出事就是大事；它还能顺手查命名规范，三段式的 key 半年后不用查文档就知道是哪个系统哪个动作，没规范的权限表半年后就是天书。闸四看着低级，在多 Agent 并行时反而高频：每个 Agent 都不知道别的 Agent 加了什么版本号的迁移，两个 V12 各自分支里都没事，合并到主干服务起不来，闸四在提交前就拦住。

四道闸还有个设计要点：它们是「或」的关系，任何一道红，整体就红。四类契约破哪类都是 bug，不存在「这道先放行」的妥协空间。见过把门禁设成「警告不阻断」的团队，大家习惯了警告，门禁形同虚设。硬阻断不给自己留「先提交后修复」的余地，前者在实践中约等于永远不修复。

这套闸的执行速度配得上它的位置：四个轻量扫描串起来跑完不到 8 秒，本地提交前一跑，五秒钟发现问题，改几行注解就完事。同样的错误放到 CI 里发现，要重走构建和 PR 流程，半小时起步；放到测试环境，联调半天；放到线上，事故复盘。修复代价随发现时机是指数上涨的，契约闸存在的意义就是把发现时机卡在最便宜的那个点上。

四道闸能立起来，靠的是把「声明」当事实源，而能当事实源的要满足三个条件：声明式的，写在固定位置；权威的，这一处的定义就是标准答案；机器可读的，脚本能解析不用人理解语义。Flyway 的 DDL 三条全占，所以 SQL 那道闸最稳。但有个陷阱要留神：事实源以它为准，不代表它必然正确——万一 DDL 里表名自己拼错了，脚本会报「SQL 引用了不存在的表」，根因却在 DDL。我们的解法是报错信息里同时打出两边的值，让人一眼看出是哪边错了。

这道关自己也翻过车，翻得很有教育意义。最早的路由扫描用了朴素正则，只抓方法级注解那段路径；遇到类级 @RequestMapping("/api") 加方法级 @GetMapping("/order") 的写法，真实路径是 /api/order，正则只抓到 /order——前端调 /api/order 被判「不存在」，调 /order 反而被判「存在」，判断整个是反的，而且静默。门禁以为自己在检查、实际在漏检，这种状态比没有门禁更危险，因为它发放虚假的安全感。后来改成把源码当全文解析、老老实实拼类级加方法级，才算堵住。从那以后我加了一条规矩：门禁脚本本身也要测——故意构造一个不匹配的用例，期望它红；构造一个匹配的，期望它绿。门禁脚本也是代码，是代码就有 bug，用带 bug 的脚本去拦带 bug 的代码，两层都不靠谱。

三、第二道关：407 个疑点的漏斗

代码对不对有脚本管，长得对不对是另一关。上一个项目 380 个页面，人眼走查每页停留十秒就是一个多小时，改完再走一遍，第三遍人已经废了。这一关我按场景分成两条路，两条路的工具、判断标准、能回答的问题都不一样，混在一起做，要么新功能漏了样式偏差，要么老功能没有原型无从下手。

新功能有高保真原型当标准答案，走像素级比对：Playwright 起两个浏览器上下文，一个渲染原型 HTML，一个跑真实页面，固定视口截图，pixelmatch 逐像素比，按页面类型分三档容差。支付确认页、登录页用最严的档，这些页面一个像素的偏移都可能是按钮被挡住的信号；列表页、详情页内容天然多变，放一档余量，卡太严天天误报；中间档做缺省。所有页面套同一个容差是新手最常见的错误，要么关键页漏报，要么列表页天天红。

像素比对有两个消噪音的技巧，不处理的话结果会被噪音淹没，真正该看的差异反而看不见。一是图片内容拦截：两张图里的商品图不一样会污染 diff，把所有图片请求统一拦成灰色块，只比布局。二是抗锯齿差异：同一页面在不同机器截图，字体边缘渲染不同，能凭空产生 5% 到 8% 的均匀噪点，人眼看完全一样——要么调宽容差档，要么比对前做一次轻微的高斯模糊。还有一条经验值得单独立牌：差异的形状比面积更有信息量。同样是三成差异率，集中成块、轮廓清晰的，多半是内容演进多了一个功能区；像撒胡椒面一样均匀散布的，才是间距字号系统性崩了。报告按差异连通区域分类，比只报一个总差异率有用得多。

老功能没有原型可比，走 vision 巡查加代码审计的交叉。380 张截图不全喂模型，先按文件大小做启发式筛选——异常小的可能是白屏，异常大的可能是样式崩坏——筛出 18 张代表页做深审。vision 确实能发现人眼容易漏的问题，但它会幻觉，而且幻觉得非常自信——这一段全是我的实测记录，每一条都能在代码里复核。我实录过三类：把红色购物车角标认成客服悬浮按钮，报「悬浮按钮遮挡商品价格」；把浅绿渐变背景认成纯白，批评「没有玻璃拟态」，实际渐变就在代码里，只是太浅它看不出来；凭空说某页用了紫蓝主色，全量代码一查用的都是标准 token。

18 张图，vision 一共报了 407 个疑点，平均一页二十多个，姿态是「这页全是问题」。代码审计交叉验证之后，真的只有 4 个：三个文件硬编码了一整套蓝色当模块品牌色，一个悬浮按钮用了没登记的渐变，423 比 4 的对比让泄漏位置一目了然。真阳性率不到 1%。如果照单全收，团队 97% 的精力在追幽灵。但反过来看，那 4 个真问题确实是 vision 捞出来的，不扫可能很久才暴露。所以 vision 的正确姿势是：让它当提问题的实习生，别让它当终审法官——实习生的价值在于看得多、不知疲倦，但每一句汇报都要有人复核签字才能进案卷。

这三类幻觉有个共同结构，比任何单例都值得警惕：vision 把它没理解的东西，当成了有问题的东西。看不出浅渐变，就报背景纯白；分不清角标和按钮的语义，就报悬浮按钮遮挡。它描述的并非它看到的，而是它以为自己看到的，而且说得很有底气。代码审计还澄清过一类反着的情况：全站给「需求」类内容统一用 indigo 色做分类标记，vision 看到紫色就报主色不对，但十二个文件用的是同一个 token，这是有意的分类编码。没有事实源，这种「有意的不同」和「真的错了」根本分不开。

终审靠的是确定性的真相源。所有颜色、圆角、渐变定义在 variables.css 里，机器可读；再用 Playwright 遍历真实页面每个元素的最终计算样式，转成标准格式后扫有没有绕过 token 的写死颜色。一跑下来，427 个页面里 423 个走 token，写死的就那 4 处，代码证据确凿，直接立项修。vision 报的每个疑点，要么被代码证实，要么被代码否决，不存在「没法验证但先信它」的中间态——这条规矩挡住了全部追幽灵的时间。

四、两道关合起来的验收观

把两道关放在一起，验收的完整姿势就出来了。代码关，四道契约闸管接缝，测试管行为，架构测试管分层，评审回路管语义——按「能不能机器确定性地判断」分工，确定性的给脚本，不确定性的给人和 AI 辅助。长相关，有原型走比对，没原型走交叉，vision 只出疑点清单，定案权在代码事实上。

视野再放大一圈，代码关其实是三层防线的最外层。脚本拦粗的：声明式跨层契约，秒级，零成本，拦住约七成。架构测试拦结构的：强制分层依赖方向，违反就构建失败，几十秒，再拦两成。评审回路拦语义的：行为对不对、设计合不合理，机器给建议、人拍板，最贵，拦最后一成。分层的依据是确定性：能机器确定性判断的交给机器，需要理解语义的交给人。顺序反过来，一上来全靠人工评审，七成的低级问题烧掉人的注意力，真正该人看的反而看不过来。

由此也能看清两道关共同的反模式。反模式一，全量截图直接采信 vision，报告写了几十页，97% 在追幽灵；看着很努力，场面很大，场面不等于质量。反模式二，像素 diff 当结论，60% 差异率其实是内容演进而非样式崩坏，差异的形状比面积更有信息量：集中成块的差异多半是新功能区，撒胡椒面式的差异才是真崩了。反模式三，没有真相源就让 AI 说了算，颜色散落各处，模型说主色不对，你连「对」的标准都没有。

做视觉验收绕不开一个选择题：自建还是买。商业方案我评估过一轮：按截图量收费的视觉回归 SaaS，380 页全量跑成本不低；自带「智能消除误报」的 Visual AI，消的是真误报还是真 bug，黑盒里看不清。只要想让 vision 介入整页走查，代码审计这一层都得自建——只有你自己能把判断和自家的 token 基线做交叉验证，这一层没法外包。自建的真实代价也要算进去：每周半天同步基线，新 token 进白名单、新路由进截图清单、确认无害的差异进忽略列表。只看「搭一次省多少」，会低估维护的真实成本。选型还有个务实的判断法：看哪一层的「不确定」最容易演变成线上事故，把钱砸在那里，别看哪个方案更时髦。

验收的产出物形态也有讲究：落成断言和扫描规则，别停在一份报告里。报告会丢、会过时，断言和规则每次提交都会执行，问题一冒头就拦下来。视觉验收只有落成可执行的东西，才算嵌进了研发流程；否则再漂亮的报告，也只是那次走查的纪念品。

还有一个容易被忽视的前提：新功能要走像素比对，设计交付必须包含浏览器能直接打开的原型 HTML。设计师只给一张静态设计图，开发还得手工还原成 HTML 当锚点，成本又绕回人身上。这条流程约定不立，比对这条路再好也跑不起来。

两个常见问题

测试已经写得很全了，还需要契约闸吗？ 两样东西拦的不是一类错。测试拦「行为对不对」，契约闸拦「接缝对不对」，互不替代也互不冲突。白屏那次的教训正在于此：前后端单测各自都过，谁都没打算替对方把关。四道闸只守声明式的跨层契约，行为类的正确性它不管也管不了，安心交给测试和评审——认清分工，两边才都省心。

换个更强的 vision 模型，幻觉会消失吗？ 会少，不会无。模型升级能减少「浅渐变认成白底」这类感知错误，但「把它没理解的当成有问题的」这个行为模式是机制性的。而且幻觉的可怕不在数量，在自信：它每一条读起来都像板上钉钉的结论。所以正确的投入方向不是等模型变完美，是把「只提疑问、不下结论」做成流程纪律，配一个确定性的真相源。模型年年换，事实源和交叉验证的框架可以用很多年。

收尾

回到周二下午那个白屏。它教会我的东西就一条：验收的对象从来不是 AI 的代码，是 AI 没验证过的部分。它看不见接缝，就给它脚本当眼睛；它看图会脑补，就给它事实源当法官。绿灯本身不值钱，可复现的绿灯才值钱。

记这个顺序就够了：真相源先做成机器能读的，模型只负责提疑问，人负责最后的拍板。顺序不能乱——没有真相源，疑问无从验证；没有流程纪律，疑问会冒充结论；没有人的拍板，整套体系就少了对结果负责的那个人。验收不是不信任 AI，是不信任没验证过的绿灯——AI 的代码也得过 AI 自己设的关。这一关过了，白屏才会从周二下午的惊吓，变成提交前五秒钟的一条红色输出，带着明确的两边对照，告诉你哪个字母出了问题。
