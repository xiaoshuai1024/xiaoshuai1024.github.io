你的 E2E 测的是页面还是业务：三条铁律抓静默失败

问你一个问题：你的 E2E 测试全绿，用户为什么还在投诉？我审过的项目里，十有八九的 E2E 长一个样：一个用户登录，点几个按钮，断言页面出现某段文字，通过。写的人很认真，跑得也很勤，覆盖率报表年年涨。这种测试有个更诚实的名字——摆拍。它只能证明页面没崩，证明不了业务没崩，更证明不了角色的状态在正确流转；它抓住了「按钮不见了」这类前端问题，放跑了最贵的一类 bug：界面全绿，业务已经错了。

这套摆拍式测试我以前也写，直到社交模块的一次用户投诉让我看清了它的盲区：A 给 B 点赞，B 应该收到通知，测试里只有 A，B 的通知列表从来没人查过。后来我换成一套多角色互转的写法，跑了半年多，抓出十几条点 UI 永远碰不到的 bug。这篇把这套方法拆开，三条铁律、几个真实的坑、以及怎么判断你的 E2E 有没有牙齿。

一、点赞之后，谁去看通知

先讲那个让整套方法立起来的案例。社交模块，A 给 B 点赞，B 应该收到一条通知。这个需求简单到没人在意，但单用户 E2E 永远测不出它的问题——因为测试里只有 A，A 点完赞，根本没有人去看 B 的通知列表。投递链路断没断、通知入没入库、@提醒丢没丢，全都无人知晓。测试报告上是一个漂亮的勾，现实里是一次沉默的失联。这类 bug 的性格是静默潜伏，潜伏到用户替你发现。

顺着这个案例再看一遍传统 E2E 的动作：登录、点击、断言文本。每个动作都在 A 的世界里，B 的世界从头到尾没有出现过。它代表的是一整类错误：跨角色、跨端、跨时间的业务流转出错。B 的通知没人查只是最直观的形态，同类还有静默后端失败——前端弹着「成功」，后端数据根本没落库；还有跨端数据断裂——小程序下的单，运营后台查无此单。三种形态共性一致：UI 层看着全绿，业务事实是错的。它们也共享同一种贵法：静默，用户不说你不知道；影响面大，从上线到发现已经波及一批人；排查贵，没有失败现场，只能靠时间倒推。普通的前端 bug 用户一眼看见立刻反馈，反而是这三类「表面健康」的病灶最烧钱。

这种盲区的根源值得说透：单用户测试的结构性缺陷不是「写得少」，是「视角只有一个」。业务流转的本质是状态在角色之间流动，单用户测试天然只有一个视角，流动的另一端在它的世界之外。测试报告全绿，只说明视角之内的世界正常；视角之外的那一半业务，从来没被看过一眼。

先划清这套方法的适用边界，它不是万金油。它适用于有明确角色划分、角色间有状态流转的系统：社交的互动通知、电商的买家下单卖家发货平台结算、SaaS 的租户管理员和普通成员。纯展示型网站、无状态工具类应用没有业务流转可言，单用户点 UI 就够用，硬套这套是过度设计——给一个官网首页上多角色编排，投入和产出完全不成比例。

二、铁律一：多真实角色，别自己考自己

第一条铁律：涉及 A 到 B 业务流转的测试，必须用两个独立登录态模拟两个真实用户。A 发起动作，B 感知结果，两边都走真实接口。一个用户假扮两个角色，等于自己考自己，怎么考怎么过——它永远测不出角色间状态隔离和通知投递的问题。

让两个角色低成本登场，靠 mock-login 机制：接口传入用户 ID 和昵称，返回这个用户的真实 token。用之前有个我亲手踩的坑：测试里把租户 ID 硬编码成了 1，而项目默认租户是另一个值，后端回了一句 Tenant not found，所有登录全挂。查了半天，代码没有任何问题——是测试自己压根不在那个村。从此定死一条：租户 ID 永远从项目配置取，不硬编码。mock-login 本身只该在开发与测试环境开放，生产环境不存在这个入口，这个前提也要在部署配置里显式核对，别让「方便测试」的口子开到线上。

角色登场还有一个仪式：清洗。每个测试用户配一个清洗脚本，跑测试前先清掉旧通知、旧内容，保证起始状态干净——上一次测试残留的通知会污染这一次的通知列表断言，让你看到一个「莫须有」的通过或失败。顺带固定两件事：两个用户的关联数据要一起准备，要测 B 评论 A 的帖子，A 的帖子就得先存在；两个用户要在同一租户下，跨租户互动本来就该被隔离，租户摆错了，测出来的全是假故障。数据可以复现，脏数据不可复现，两者的排查成本差一个数量级。

角色之外，数据也要顺着业务链路造。要测「B 评论 A 的帖子后 A 收到通知」，A 名下得先有一篇帖子，只造两个用户不造帖子，评论接口直接报帖子不存在，流转跑都跑不起来。顺序是先造接收方的内容，再造发起方的动作，反了就缺数据，这个顺序固化在准备脚本里，别靠人记。每个用例还该只覆盖一种通知类型：点赞、评论、关注、@提及，四种类型走不同的渲染和聚合逻辑，只测一种就宣称「通知功能没问题」，等于只检查了四分之一的邮路。发起方和接收方要刻意错位：接收方 ID 配发起方令牌，这个「错位」正是多角色测试的精髓——它验证的正是「A 的操作能正确投递给 B」。多角色还有一个隐蔽的假 bug 来源：两个用户必须在同一租户内，跨租户的互动本来就该被隔离，搞错了会出现「明明操作了却收不到通知」的假故障，能让你排查一整晚。

角色互操作还有个高价值场景：聚合。连续三条点赞通知，系统应该聚成一条「等 3 人点赞了你」，别刷出三条独立通知。聚合逻辑靠时间窗口加同类型判断，边界条件极多：窗口多长、跨窗口的怎么算、聚合后点进去落在哪条内容，每个都可能出事。我用固定套路测它：连发三条同类通知，间隔二百毫秒给聚合留时间，然后查列表断言聚合数和聚合文案。这个套路抓出过一次真实事故：聚合窗口被配成了 0，所有通知都不聚合，用户的通知列表被刷屏。那次的排查路径也值得记下：先看发起方请求的返回——注意看的是业务状态字段，HTTP 状态码 200 说明不了业务成功；确认发送成功后查接收方列表，发现三条独立通知挤在一起，再反查聚合配置，窗口归零的事实才浮出来。没有固定套路，这类时序相关的配置错误会一直被当成偶发抖动放过。

三、铁律二：断言落库，别信 UI 的表演

第二条铁律：关键断言落在数据库，不落在界面上。前端弹「成功」，只证明前端收到了 200，证明不了后端真的把数据写对了。UI 会表演，数据不会说谎，断言要落在不会表演的那一层。

什么叫静默后端失败？举一个我真实撞上的例子。评论功能上线后前端表现完全正常：用户发评论，页面立刻显示新评论。实际上后端的消费者在某次部署后挂了，评论根本没写进数据库，前端展示的是乐观更新的假象。用户一刷新，评论全没了。这种 bug 用「点 UI 看 Toast」的 E2E 永远抓不到，因为接口确实返回了成功，乐观更新不需要等后端。但如果测试在发完评论之后直接查一次库，断言这条评论真的在表里，当场就能抓住。

落到具体断言，我给通知链路定过三条：接收方查自己的通知列表，断言列表非空，这抓「根本没入库」；断言包含互动分类，这抓「点赞评论丢了」；断言包含 @提醒，这抓「特定链路断了」。排查时再逐条打印分类统计，哪类通知出了问题一目了然。

判断哪些断言该落库，分界线就一条：这个操作改不改数据。发帖、下单、支付、评论这类状态变更，关键断言必须穿透到持久化数据层——去查接收方的通知列表，断言列表非空、断言包含互动分类、断言 @提醒没丢；列表展示、搜索这类纯查询，断言 UI 就够了。「这个操作到底改没改数据」是分界线。发帖、下单、支付、评论这类状态变更，关键断言必须穿透到持久化数据层；列表展示、搜索这类纯查询，断言 UI 就够了。还有一类最隐蔽的部分失败要专门防：点赞通知正常但 @提醒丢失，说明特定链路断了。断言逐分类覆盖，每类通知都过一遍，部分失败才无处藏身。

把一条完整用例从头到尾走一遍，三条铁律如何咬合就直观了。以「评论触发通知」为例：准备阶段，清洗脚本清掉两个用户的旧通知，mock-login 拿到两套独立令牌，确认接收方名下有一篇帖子；动作阶段，发起方用自己的令牌调评论接口；验证阶段分两层，先查接口返回的业务状态确认提交成功，再用接收方的令牌查通知列表，断言列表非空、分类正确、@提及也没丢。全程两个身份、两次数据层查询，任何一环断了，失败会精确指到那一环——这就是有牙齿的 E2E 和摆拍的区别。

四、铁律三：跨端握手，别各测各的

第三条铁律管多端业务。小程序下单、运营后台管理、服务端结算，各端各写各的 E2E，「小程序下的单运营后台能不能查到」就没人保证。多端一致性的难处在于它没有天然的归属：小程序团队觉得后台能查到是后台的事，后台团队觉得查不到是小程序没下单。两头都对，问题依然在。我的做法是加一个跨端编排层，用握手标记把端与端串起来。以交易链路为例分三段：小程序端下单，产出订单号并把订单号写进桥接层；运营端先等这个握手标记出现，再拿订单号查订单可见性；服务端最后验证结算状态。每一段失败都能从那一段重跑，不必从头下单一遍。标记用业务标识，比如订单号、退款 ID，别用技术标识，两端实现再不同，业务语义是一致的。跨端断裂有专属的排查入口：运营端一直等待超时，先看小程序端有没有把握手写进桥接层——十有八九是阶段间的「写握手」逻辑漏了，业务本身没断。

造数据的顺序感和握手的时序感是一回事：业务链路里谁先谁后，测试就要按这个顺序铺 setup。先造接收方的帖子，再造发起方的评论；先等下单完成，再验后台可见。任何「假设它应该已经好了」的地方，迟早会变成偶发失败。

握手要带等待语义：运营端必须等小程序写出握手标记才开始查，不能假设下单一定先完成——两端时序竞争是跨端测试特有的坑，查不到不一定是有 bug，可能是查早了。每个阶段还要独立可重跑，第二阶段失败就从第二阶段重跑，不必从头下单，调试效率天差地别。跨端握手把「跨端一致性」从没人管的灰色地带，变成了一条有明确断言的用例。

五、跑半年之后：抓到的都是同一种病

这套方法在我自己的多租户项目里跑了半年多，抓出十几条单用户测试碰都碰不到的 bug。十几条是什么概念？同期单用户 E2E 抓到的全是页面级小问题，这十几条才是会让用户感知、会让运营半夜起来处理的那类。复盘它们，全是同一张脸：界面全绿，业务已经错了。通知没投递的、聚合数不对的、跨端查无此单的、消费者挂了前端还演着的——每一种都在测试报告全绿的背景下安静地趴着，直到真实用户撞上。

这套写法的前期成本确实比点 UI 高：要造多角色、编排流程、设计握手。但收益结构完全不同：同样写一条测试，抓业务流转的捕捉价值是抓 UI 的十倍量级。流转型 bug 更隐蔽、影响面更大、排查成本更高，这三条加在一起，让它成为测试投入里回报最高的方向。全量跑太慢的问题也有解：用文件路径到业务域的映射注册表做增量选测，提交时按改动文件只跑受影响的几条 E2E，发布时才跑全量。三十多条用例，日常提交从十几分钟降到几十秒，保障没有降。更讲究的做法是三级门禁分摊成本：提交时只跑改动命中的几条，合并请求时跑所在业务域的全量，发版时才付所有用例的成本。保障分级，频率也分级，两全。注册表的取舍原则是宁可多映射不可漏映射：多映射只是多花几十秒，漏映射是放过 bug，成本不对称。映射还要铺满所有层：交易域既要含后端订单目录，也要含前端下单页，还要含运营后台的订单管理页——任何一层的改动都可能破坏流转，漏一层，那一层就成了门禁的缺口。

半年的另一项收获是排查纪律变值钱了。这类测试失败比单用户复杂，涉及多个角色、多端、多个时间点，没有固定顺序会乱撞。怎么判断自己写的 E2E 有没有牙齿？给自己五条自查：用了至少两个独立登录态吗，整条链路只有一个令牌就是单用户测试；数据层断言占比过半了吗，健康的比例是六成以上，超过一半的断言在等页面出现某段文字，说明还停在摆拍阶段；测了反向验证吗，A 没操作时 B 不该收到，不测这条就防不住乱投递；跨端链路有显式握手吗，还是「各自测完默认它能对上」；纳入增量选测的注册表了吗，没注册的流转用例不会在相关改动时被触发，等于白写。任何一条不满足，这条用例就还在「点 UI」阶段打转，补齐再合入。

最后是排查纪律。这类测试失败时按 Console、Network、后端日志的顺序查，禁止跳步直接改代码或改断言——那不叫修，叫糊弄。通知没收到，先查发起方请求的业务状态，再核对感知方查列表用的 token 对不对，用错 token 查的是别人的列表，永远等不来自己的通知；环境类失败禁止用改测试的方式绕过，后端没起就把它起来，不是把用例 skip 掉装作通过。分不清代码 bug 还是环境问题，看一条：同样的测试在别人机器上能过、在你这里不过，大概率是环境问题；所有人都稳定复现，才轮到代码 bug 排查。偶发的先查环境——服务起了没、依赖装了没、端口占没占；稳定的直接走三步排查。禁止假绿，这条纪律跟任何测试体系都通用。

两个常见问题

我的系统没有多角色，这套还适用吗？ 看业务里有没有「A 做了什么、B 应该感知到」的流转。系统里没有这种流转，单用户点 UI 就是合适的测试深度，不必硬套；只要有——哪怕是「管理员改配置、普通用户页面生效」这种朴素形态——多角色互操作和断言落库就都有用武之地。判断标准不是系统大小，是有没有状态在角色之间流动。

断言落库是不是要把数据库层测成单元测试？ 不用，也不该。E2E 里的落库断言是「黑着查」：通过接口或直连测试库，验证关键业务事实存在且正确，几条查询就够。它和单元测试的分工是：单元测试验证代码逻辑，E2E 落库断言验证业务事实链路，包括配置、部署、消费者、定时任务这些单测看不见的环节。正是这些环节，最容易在生产部署后悄悄失效。

收尾

回到开头的反差：测试全绿，用户在投诉。两件事同时成立，只说明一个错位——测试测的东西和用户用的东西不是同一个。用户用的是业务：点赞了就该有通知，下了单就查得到，评论了刷新还在。E2E 的价值不在证明页面能点，在证明业务能转。页面是业务的皮，皮再完整，底下断了也是白搭；测试的牙齿，要长在咬得到数据的那一端。

三条铁律记住了，E2E 才算长出牙齿：多真实角色互操作，让角色流转有人管；断言落在数据上，让静默失败现原形；跨端用握手衔接，让端与端的断裂无处藏身。落地的顺序建议从断言落库开始，改造成本最低、见效最快，第一条静默失败被抓到的当天就回本；再逐步补上多角色和跨端编排。不用一步到位，每补一条铁律，就堵住一类窟窿。骨架记三句就够：角色要真的，断言要落的，端间要握手的。下次写 E2E 之前先问一句：这条用例，抓得住「后端没落库但前端假装成功」吗？抓不住，它就不配叫端到端——业务的端到端，从用户操作到数据落地，中间任何一段断了都得有人知道。
