Claude Code 与 Codex 的主循环源码对比：一个自递归 generator 和一个 Rust step loop

用 Codex 的时候我一直有个感觉：它总是「先开工」。模型的话还没说完，工具已经在跑了。而 Claude Code 给我的感觉是「先听完再干」，整轮响应结束才开始执行。我曾经把这归因于模型风格，甚至觉得它有点没礼貌，直到把两边的主循环源码摆在一起才发现——不是它没礼貌，是我们对「把话说完」的定义不同：Codex 认为 function call 一落地就可以开工，Claude Code 要收齐整轮 tool_use 再统一动工。开头这个「抢跑感」，这篇拿代码对账。

这是系列第二篇。上一篇（架构分层对比）讲了两个引擎的骨架，这篇进入调度的心脏：主循环。版本锚定不变——Claude Code v1.0.88（43 万行 beautified 后的 cli.js），Codex commit 63b268c81b（2026-08-18）。

一、Claude Code 的主循环：一个函数的递归

先看 Claude Code 这边。整个 Agent 的调度核心是 v1.0.88 里位于 L416894 的一个 async generator，混淆名叫 VE。它的结构用伪代码展开是这样：

async function* VE({ messages, systemPrompt, canUseTool, toolUseContext, ... }) {
  // 1. 入口先做两级压缩检查
  let msgs = await microcompact(messages)
  await autoCompact(msgs)

  // 2. 发起流式请求，收集 assistant 消息
  for await (let event of streamRequest(msgs, ...)) { ... }

  // 3. 提取本轮全部 tool_use
  let toolCalls = assistantMessages.flatMap(
    (m) => m.message.content.filter((c) => c.type === "tool_use"))

  // 4. 执行工具，收集 tool_result
  let results = []
  for await (let r of runTools(toolCalls, ...)) results.push(r)

  // 5. 尾递归：带着新历史进下一轮
  yield* VE({ messages: [...messages, ...assistantMessages, ...results], ... })
}

真实的混淆代码当然没这么友好，但每一步都能对上行号：入口压缩在 L416898 到 L416912（先 Kv 做 microcompact，再 hRB 做 auto-compact，命中时打点 tengu_auto_compact_succeeded）；流式请求在 L416932 到 L416960；提取工具调用在 L416995 到 L417008（filter((o) => o.type === "tool_use") 是明文）；工具执行在 L417012 到 L417018；尾递归在 L417033 到 L417055，原文就是一句 yield* VE({ messages: [...V, ...C, ...M] })。

VE 的一生很朴素：收作业、批作业，再把作业连着学生档案一起递给下一个自己。这个设计有两个点值得停下来看。

第一，它用 generator 递归代替了 while 循环。每轮迭代是一个新的 generator 实例，把上一轮的完整历史（旧消息 + assistant 块 + tool_result 块）作为参数传给自己。好处是每轮的上下文天然不可变——出了问题，那一轮的输入输出是一个完整快照；代价是深任务下调用栈一层层叠上去，靠 generator 的惰性求值撑着不炸。这是很 JS 的写法，Rust 里没有对应物。

为什么偏偏选 generator？除了不可变性，还有两个工程理由。一是可组合：yield* 委托让 subagent 循环可以原样嵌进主循环（第三篇会看到 QgB 就是这么复用 VE 的），while 循环做不到这种无缝嵌套。二是消费侧控制：generator 的消费节奏由调用方决定，UI 层可以逐个 yield 渲染进度、也可以攒着批量处理——Ink 的 React 渲染正好吃这种流式接口。一个语言特性同时解决了不可变、组合、流式三件事，这是我在整个逆向过程里最佩服的一段设计——用语言的原生特性换架构收益，是熟手才有的手感。

第二，出口条件是「没有 tool_use」。模型这轮只回了文字、没调工具，循环就走收尾分支（Stop hook、追问处理），然后 return。整个 Agent 的「停下来」不是状态机变迁，就是一次普通的函数返回。

流式解析在另一处：L388911 到 L388975 的解析器按事件类型分派——message_start 记首 token 延迟和用量，content_block_start 按 tool_use / text / thinking 初始化块，content_block_delta 里的 input_json_delta 分支增量拼接工具入参（o.input += u.delta.partial_json），message_delta 取 stop_reason。工具入参是流式攒出来的，攒完不代表马上执行——要等整轮结束统一进分发器。

这个拼接过程值得多看两眼，因为它是「模型边想边给参数」的工程映射。input_json_delta 到达时参数 JSON 还不完整——可能只有 {"file_path": "/src 这样的半截——解析器不做任何校验，纯字符串追加，等块结束才有一次完整 parse。流中断的话工具入参就是残缺 JSON，所以错误处理必须容忍这种中间态。Codex 同样有流式解析器（apply-patch crate 里还有个专门给 patch 流的 streaming_parser.rs），思路一致：增量收、边界处一次性成型。

stop_reason 的消费方式也说明两边对「模型意图」的理解差异。Claude Code 拿 stop_reason 主要判断异常（end_turn 正常、max_tokens 要处理），循环是否继续看「有没有 tool_use」；Codex 的 model_needs_follow_up 直接参与循环条件——模型说要继续就继续，工具调用只是继续的方式之一。前者以工具为中心，后者以意图为中心。

出口附近还有个容易忽略的角色：hooks。Claude Code 在无 tool_use 的收尾分支里跑 Stop hook（可以阻止会话结束、强制再来一轮），subagent 结束时跑 SubagentStop；Codex 在 turn 结束时跑 run_turn_stop_hooks（turn.rs:484）。两边的「结束」都不是终点——hook 有权把它变成逗号。第五篇讲权限的时候会再遇到这个机制，这里先记一笔：hook 的执行点嵌在主循环的出口分支里，不在工具层。

二、Codex 的主循环：三层嵌套的 step loop

Codex 这边的入口是 core/src/session/turn.rs:153 的 run_turn，由 tasks/regular.rs:39 的 RegularTask::run 驱动。它是三层结构的嵌套：

最外层是 turn 级。run_turn 先做四件准备工作：pre-turn compaction（超限先压缩）、MCP 依赖解析（按输入里 mention 了哪些 server 决定连什么）、skill / plugin 注入（build_skills_and_plugins）、然后进入 step loop。

中间是 step loop（turn.rs:281 起的 loop {}）。每一轮从 input_queue.get_pending_input 取用户在模型运行中追加的话（steering 机制），构造 sampling request 发给模型，返回后判断 needs_follow_up = model_needs_follow_up || has_pending_input || token_limit_reached——三个条件任何一个成立就再跑一轮 step。注意这个设计和 Claude Code 的根本不同：循环的驱动条件从「有没有工具调用」换成了「模型还要不要继续」，工具执行只是 step 内部的一环。

最内层是 流级。turn.rs:2160 的 try_run_sampling_request 拿到 SSE 流后事件驱动地消费，function call 一到就包成 future 推进 in_flight: FuturesOrdered——工具边到边执行，结果按提交顺序回填。

「抢跑感」的来源就在最内层。同一个「等模型输出」的动作，Claude Code 是把流当数据收集（攒齐 assistant 消息数组），Codex 是把流当指令流（每个 function call 是一条可立即执行的指令）。工程上两者都正确，但用户的等待体验完全不同：同一份 SSE 流，一个在记笔记，一个在接单——笔记记完统一开工，单子到手立马动工。

step 与 step 之间还有个不易察觉的快照机制：capture_step_context_with_required_mcp_servers 生成的 StepContext，让一次请求内的上下文和工具列表共享同一视图。为什么要快照？因为 MCP 连接和 skill 注入在 turn 内可能变化（你中途插话 mention 了新的 server），没有快照的话，同一轮 step 里工具列表前后不一致，模型的工具调用会打到不存在的目标上。Claude Code 不需要这个机制——它的工具列表在轮与轮之间才变，轮内天然稳定。又是一个「动态性强就要多操的心」的例子。

把三层连起来走一遍完整生命周期，有助于把结构变成直觉：用户输入进队列，RegularTask 取走，run_turn 做完四项准备进 step loop；第一个 step 发请求，流里来了两个 function call，in_flight 里两个工具并行跑着；此时用户插了句话，get_pending_input 在下一个 step 边界取到；模型输出结束，needs_follow_up 因为 has_pending_input 为真，再跑一个 step——这个 step 的请求里同时带着插话和上一轮的工具结果；如此往复，直到三个条件全假，turn 结束，stop hooks 跑完，控制权交还。整个过程里 CancellationToken 像一根拉绳，任何时刻拽一下，所有层一起收工。

还有一个差异藏在错误处理里。Codex 的取消是 CancellationToken 贯穿全链（child_token 一路传下去，流上的每个 await 都挂了 or_cancel），取消即 TurnAborted，干净利落。Claude Code 的中断靠 AbortController（subagent 各自持有独立实例），加上流异常的正则降级——L388505 到 L388530 有一段很务实的代码：用正则解析 API 的 400 报错里的上下文超限数字，动态下调 maxTokensOverride 再重试，打点 tengu_max_tokens_context_overflow_adjustment。一边是结构化取消，一边是字符串级自救，风格差异贯穿始终。

错误处理再展开一层，重试和降级两边也都有完整路线。Claude Code 的退避公式是 min(base * 2^(n-1), 32000) + jitter——指数退避封顶 32 秒加随机抖动，避免大量客户端同步重试打崩 API；429 限流、5xx、网络错误各有独立计数。模型级的 fallback 藏在主循环的流式请求外层：捕获到特定异常时置 fallback 标志换备选模型重跑整轮（L416932 到 L416960 的 while 结构），用户几乎无感。

Codex 的流级重试是 ResponsesStreamRetryState 状态机（上限 stream_max_retries 可配置），err.is_retryable() 判断能不能重试；ContextWindowExceeded 和 UsageLimitReached 两个特判单独处理——前者触发压缩（第四篇的主题），后者直接终止 turn 上报。模型 fallback 与主请求解耦，放在压缩模块里（compact_model_fallback.rs）。对比下来：Claude Code 的降级是「轮」级的，整轮重跑，简单但上下文一致；Codex 的降级是「流」级的，粒度细但要处理更多中间态——又是顶层架构决定微观实现的一例。

三、工具执行：收齐再分块 vs 边到边跑

两边的主循环都解决「怎么执行工具」，答案差异同样大。

Claude Code 的分发在 L417134 到 L417179 一带：先按 isConcurrencySafe() 把本轮工具调用分块——安全块进并行池（池上限就是那个写死的 dN5 = 10，L416878），不安全块串行。判断「安全」的依据很直接：内置只读工具（Read / Glob / Grep）标了安全；MCP 工具看 annotations?.readOnlyHint（L386413，server 自己声明的元数据）。

Codex 的分发链路是三个构件：ToolOrchestrator（orchestrator.rs:39）负责调度，ToolRouter（router.rs:68）负责路由到 handler，tools/parallel.rs 的并发闸门负责秩序——supports_parallel 的工具并行跑，不支持并行的工具持有 Arc<RwLock<()>> 写锁串行通过（:113-158）。

对比一下会发现一个有趣的错位：Claude Code 的并发粒度是「轮」——一轮响应里的多个工具调用可以并行，但轮与轮之间严格串行；Codex 的并发粒度是「流」——同一轮流里工具边到边跑，读写锁保证「写」类工具不撞车。对用户来说，一段需要十个只读操作的任务，Codex 的墙钟时间更短；一段「读-改-写」交替的任务，两边都会退化为串行，体感接近。

那把 dN5 = 10 调大会不会更快？v1.0.88 里它是常量，改不了。而且这个数字背后有约束：并行工具的结果回填顺序影响后续轮次的上下文顺序，池子越大，乱序回填对模型推理的扰动越大。Anthropic 把它钉死在 10，大概率是实测后的安全值，不是随手写的。

工具执行的入口还有一个前置步骤：每个工具调用先过 schema 校验再执行。L417234 的 aN5 generator 里，第一步是 inputSchema.safeParse，校验失败不抛异常——错误被包成 <tool_use_error>InputValidationError</...> 作为 tool_result 回给模型——模型下一轮自己修参数重试。这个「把错误当数据回喂」的设计是 agentic loop 的通用模式：中断循环的成本远高于让模型多试一轮。Codex 侧对应的是工具层返回 ToolExecutorFuture 的错误分支，同样以回填收场，不让循环崩溃。

理解了这套结构，复刻一个最小 Agent 主循环就不神秘了：一个循环、一个流式请求、一个工具分发、一个结果回填，四样齐了就能跑，剩下的都是加固。我自己实践过一遍，细节在工具调用的桥接实现里——写完再回头看 VE，会发现它多出来的东西（压缩、hooks、fallback、并发分块）全是工程加固，骨架就是那四样，验证过的判断。

四、steering：人在回路里的两种实现

两边都支持「模型跑着的时候继续打字」，实现位置很能说明各自的架构观。

Claude Code 的 steering 靠主循环的天然结构：每轮 yield* VE(...) 递归前，新的用户输入已经在消息队列里，下一轮迭代自然带上。没有专门的构件，机制「免费」地存在于循环结构里。

Codex 把它做成了独立构件：session/input_queue.rs 是一个显式队列，step loop 每轮开头调 get_pending_input，取到的用户输入会和模型的本轮输出一起参与 needs_follow_up 判断。换句话说，在 Codex 里「用户插话」是调度的一等输入，和「模型还想继续」同级。

使用上的差别：两边都能纠偏，但 Codex 的插话在下一个 step 边界生效（step 之间有明确检查点），Claude Code 的插话在下一轮 generator 递归生效。粒度差不多，工程表述完全不同——这也是第一篇分层差异在微观层的重演：同一个交互需求，单体架构顺手实现，平台架构必须显式建模。

插话的价值被普遍低估了，这里多说两句。没有 steering 的 agent 要等整轮跑完才能接收新信息，一轮可能几分钟——方向错了就是几分钟的浪费，长任务里累积成小时级损耗。有 steering 之后，「等一下，那个文件别动」这样的半句话就能省一整轮返工。两个产品都把它做成了默认能力，这个共识本身说明「人在回路」已经不是增强功能，是 agentic loop 的标准件。自己做 Agent 时预算紧张可以砍很多功能，这个别砍——队列加一个检查点，成本极低收益极大。

四点五、两套循环的血统

为什么两边长成这样？把循环放回各自的语言生态，答案不言自明。

VE 的每一个特征都带着 JS 生态的胎记：async generator 是 ES2018 之后 Node 异步处理的惯用武器，React 生态拿它做流式 UI 有成熟范式；Ink 用 React 组件模型渲染终端，generator 的逐 yield 输出正好接 React 的逐帧更新；不可变数组传参是函数式 JS 的日常，深递归靠事件循环的协作式调度撑住——换成任何一门有深度调用栈限制的语言，这个写法都过不了评审。甚至那个「正则解析 400 错误」的自救，也是动态语言才敢写的代码：类型系统不拦你，运行时再认。

run_turn 的每个特征同样有 Rust 生态的出处：tokio 的 FuturesOrdered 是有身份的并发原语，CancellationToken 来自 tokio-util，RwLock 是标准库并发语义的直接使用；三层嵌套对应 Rust 社区「函数短小、错误类型化」的惯例，CodexErrorDetails::TurnAborted 这种错误枚举是 thiserror 风格的标准产物；trace 宏贯穿是 tracing crate 的推广姿势。这套东西编译期就被类型系统检查过，运行时出的问题大多在「逻辑」不在「内存」。

所以「谁的主循环更好」是个伪问题。正确的问法是：各自的约束下，这是不是足够好的解——答案都是接近是。真正值得带走的是这个观察方法：看到一个 Agent 实现的循环形态，先看它的语言生态提供了什么原语，再看它拿这些原语换了什么、放弃了什么。CC 拿 generator 换了组合性和流式、放弃了结构化并发；Codex 拿 tokio 换了类型化取消和并发原语、放弃了「一个函数读完整个循环」的可讲性。你在做技术选型时面对的每组 trade-off，都是同一种交换的变体。

五、可观测：埋点名就是官方行为清单

读完结构，再说怎么验证。两边都留了观测入口，而且 Claude Code 的埋点在混淆代码里全是明文，等于官方自己写了一份运行时行为清单。

VE 一圈跑下来，埋点覆盖了所有关键节点：入口压缩命中发 tengu_auto_compact_succeeded，microcompact 发 tengu_microcompact（带 tokensSaved 字段，能算出清理收益），流错误发 tengu_streaming_error，上下文溢出调参发 tengu_max_tokens_context_overflow_adjustment，auto-compact 后的轮次计数发 tengu_post_autocompact_turn（带 turnId 和 turnCounter）。想确认自己读到的循环结构对不对，把这些事件名接进任何日志管道跑一个真实任务，事件序列就是执行轨迹的投影——结构读得对不对，轨迹当场验货。

Codex 的观测走 Rust 生态的常规路：trace_span!("run_turn") 这类 span 宏贯穿核心函数，配合 RUST_LOG=debug codex 能打出完整的调用链。事件流本身也是可观测的——protocol crate 的 EventMsg 枚举就是第一篇说过的「正式合同」，宿主端把它当日志消费即可，不需要额外埋点。

两种观测哲学对应两种产品形态：Claude Code 的埋点是给自己家 telemetry 用的，顺带便宜了逆向者；Codex 的 trace 是给运维和贡献者用的，开放是默认。对写文章的我来说前者简直是馈赠——闭源产品的埋点名，是最不会撒谎的行为描述。

顺手做个思想实验收束这篇：拿同一个任务「读 A、B 两个文件，对比后写一份 C 报告」在两个循环里各走一遍。Codex：流里第一个 function call（读 A）一到就执行，第二个（读 B）到达时也推进，两个读并行，in_flight 里按序回填，模型看到两份内容后输出报告文本，model_needs_follow_up 为假，turn 结束——全程一个 step。Claude Code：整轮流完，提取出两个读调用，isConcurrencySafe 判定安全进并行池（两个同时跑，池上限 10 远没到），结果回填，generator 递归进下一轮，模型输出报告，无 tool_use，出口。墙钟时间相差的就是「流结束前那几秒」，任务越读密集，这个差值累积越明显。一个任务讲不清体感，一百个任务就是用户口碑。

所以那不算我第一次误会 Codex 没礼貌——是我们对「把话说完」的定义不同：它听完每一个 function call，我听完一整轮。定义对上了，误会结案。

六、把差异收敛成三句话

读完两个主循环，我把执行策略的差异收敛成三句可以直接用来指导使用的话。

第一句：要并发读，选 Codex。它的流式推进加读写锁闸门，在多工具只读场景下的墙钟时间优势是结构性的，不依赖模型自觉。Claude Code 的并行池上限 10 且只在轮内生效，读密集任务会慢一截。

第二句：要确定性中断，选 Codex。CancellationToken 贯穿的结构化取消，比 AbortController 加字符串自救的容错路径更可预测——长任务里 Ctrl+C 之后会发生什么，前者有类型系统背书。这个判断有实例支撑：我跑过一次中途取消的对照，Codex 的输出停在干净的 turn 边界、事件流给出明确的 aborted 标记；Claude Code 的取消依赖 AbortController 触发的异常被各层捕获，偶尔会留下写了一半的工具调用结果。差异不大，但自动化管线里「取消后状态是否可判定」是能不能无人值守的临界线。

第三句：要看得懂的调度，读 Claude Code。一个 160 行的自递归 generator 讲完了整个 agentic loop，这是理解 Agent 原理的经典教材。我自己复刻最小 Agent 循环时抄的就是这个结构（相关实践在这篇）。Codex 的三层嵌套更工程化，也更需要耐着性子读。

三句话之外，再补一个读源码时最容易获得的误解纠正：「抢跑」不等于「更快完成」。Codex 边到边跑省的是「等待流结束」的空转，但工具总时长不变；Claude Code 收齐分块虽然起步晚，分块并行又能追回来一部分。真正拉开完成时间差距的是任务形状——读密集型 Codex 结构性占优，写交替型两边趋同。把「体感快」当「实测快」是选型最常见的坑，这篇的源码对账至少能让你知道快的是哪一段。
