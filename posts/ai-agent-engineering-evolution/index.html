大模型是裸 CPU，我花一年给它装了个操作系统

xiaoshuai1024 included in AI 开发
About 400 words 2 minutes 
Contents

  • 一、Prompt 工程：一切从一段对话开始
  • 二、Context 工程：管好它看什么，把知识喂进它脑子
  • 三、Harness 工程：把纪律焊进流程
  • 四、自治体系：让 AI 自己干，人只看边界
  • 五条认知收个尾

写了十二年代码，前六年在前端，中间补成全栈，去年开始把 AI 真正用进研发。这轮转型里我见过最多的场景，是有人拿着一个模型在聊「AI 能不能干这活」，聊完发现长任务干不动、规矩守不住、换模型也没用。

我的体感是：问题不在模型，在视角。大模型是一块裸 CPU——算力强，但没有内存管理、没有文件系统、没有进程调度。你往裸 CPU 上怼程序，指望它稳定跑一个企业级服务，跑不动才是正常的。可绝大多数人把它当成了「一台装好系统的电脑」，缺了哪块就抱怨「这个 AI 不行」，然后去换一台。

我这一年的演进，本质是在给它补操作系统。过程分成四段：先是把话说清楚（Prompt 工程），再是管好它看什么（Context 工程），然后是让规矩焊死在流程里（Harness 工程），最后是让它在边界里自己干（自治体系）。每上一层，都是被下一层的天花板逼出来的。这个「裸 CPU → 操作系统」的类比不是修辞，它精确对应了每一段工程在补哪块系统能力——这也是我写这篇的动机：把这条线完整画出来，你看完能自己判断，手头的 AI 卡在哪一层。

这篇文章把这条演进线完整讲一遍。每一段我都会说：当时怎么做、撞到什么天花板、为什么下一段必须出现。结论先放在这——AI 工程化的每一步，都是在为「稳定地、大规模地让 AI 干活」清障碍。这条线和 《别再背 AI 黑话了》里那条主线是同一条：那篇讲每个词是什么，这篇讲这些词背后，工程是怎么一层层长出来的。

先看清裸 CPU 的四个先天缺陷

动手之前，先认识对手。大模型的四个缺陷不会因为模型变大而消失，所有工程手段都是在跟它们周旋。这四个缺陷不是我从论文里读来的，是我在真实项目里一个一个撞出来的。

缺陷一：有输入就输出，没人喊停就一直干。 AI 本质是续写器：接收输入，预测最合理的下一步。需求只说了半句，它不会停下来问「你说的 A 具体指什么」，而是开写它最熟悉的那个 A；测试没过，它不会承认失败，而是改两行继续跑。这个天性我后来总结成「翻车三连」：需求含糊就往下编、方向错了错到底、改 bug 越改越乱。资深工程师和新手的差别就在这——不是老手写得快，是老手停得准，而 AI 天生不会停。项目里所有「加一个停字」的设计，都是从这个缺陷长出来的。

缺陷二：上下文窗口是稀缺资源，长任务必然掉质量。 同一个任务，3 步的时候干得干净利落，加到 15 步就开始胡说。不是模型变笨了，是窗口里塞满了前面步骤的中间产物——一次工具调用返回几万字符的 JSON，三步之后窗口就被历史占满，后面真正有用的信息被稀释。我在长链路任务里反复踩这个，最初以为是模型不行，换了几轮模型指标纹丝不动，后来把上下文里的大 JSON 挪出去，指标立刻回升。物理容量和有效容量是两回事。

缺陷三：无状态，每次对话都是新生。 昨天踩过的坑，今天换个会话继续踩。规则在上一轮说得清清楚楚，新会话里它又按自己的理解来一遍。跨会话的知识完全靠人肉搬运——把踩坑结论复制粘贴进下一段提示词，粘漏一次就重蹈覆辙。这个问题在一个人用的时候还能忍，团队用起来就是灾难：每个人都在跟 AI 重复教一遍同样的东西。

缺陷四：指令遵从率随链路衰减。 规则写在提示词里，短任务时遵从率能到九成以上，链路一长，规则就从「必须遵守」退化成「仅供参考」。你没法在每一步都提醒它一次，提醒本身也在占用上下文。更隐蔽的是，模型会「礼貌性忽略」——它不反驳你的规则，只是不执行，你以为它记住了，它其实早忘了。

这四个缺陷对应操作系统的四块缺失：没有内存管理（上下文膨胀）、没有文件系统（知识无法持久化）、没有进程调度（长任务不可控）、没有中断机制（没人喊停）。我后面的每一段工程，都是在补其中一块。

顺带说一个观察：这四个缺陷在网上被讨论的程度差别很大。上下文窗口聊得最多，无状态也常被提起；「有输入就输出」和「遵从率衰减」几乎没人当回事——但它们恰恰是后面三、四段工程的直接原因。讨论度高的缺陷有人给你方案，讨论度低的缺陷只能自己撞出来。所以我后面几段的工程，重点全压在没人讨论的那两个上。

还有人会问：为什么不一步到位直接上命令体系？因为每一段工程都有前置条件——命令要管住的是长任务，长任务的前提是上下文管得住；上下文管得住的前提是知道哪些信息值得保留、哪些可以丢；这些判断全依赖前面撞出来的认知。跳过任何一段，都是在不知道问题长什么样的时候造解决方案。

一、Prompt 工程：一切从一段对话开始

第一段演进最朴素：把该说的都写进提示词。角色、业务规则、行为约束、项目路径映射，一股脑塞进 System Prompt 和 CLAUDE.md。

刚开始效果是惊艳的。3 到 5 步的小任务，规则写清楚后几乎不会出错，写页面、改接口、补测试，速度比我自己写快一个量级。我把项目里的目录结构、部署命令、代码规范全部写进 CLAUDE.md，感觉像是在给这个 AI「上岗培训」。那段时间我的判断是：AI 编程的差距就在提示词，谁的提示词写得细，谁就赢。

撞天花板也是从这开始的，三个方向几乎同时到来。

规则靠自觉，链路一长就失效。 规则写进提示词，本质是「相信模型会读并且会遵守」。短任务它确实读，长任务它读不完——上下文一膨胀，规则和噪音一起被稀释。于是我开始在规则里加各种强调符号，像工厂墙上贴安全标语：「注意安全」永远正确，但安全如果依赖工人每次都阅读并遵守标语，这个体系就是脆弱的。真正的安全来自机械互锁，不是标语。我在提示词里叠了三个警告符号，模型的遵从率没有因此回升一个点。

知识不沉淀，每次对话重来。 CLAUDE.md 只能写「相对稳定」的东西：项目结构、部署流程。但研发里大量知识是动态的——这个接口的参数是什么、那个服务的坑在哪、这次事故的教训是什么。这些写不进 CLAUDE.md，每次遇到都要重新问、重新试、重新踩。我统计过，同一个「搜索关键词不能用空格分隔」的坑，我在不同会话里踩了不下五次，每次都花二十分钟重新教会它。

长任务不可控。 一个跨前端、BFF、后端、E2E 四个系统的功能，AI 全程自己跑，跑到第 8 步开始「自由发挥」。你没法盯着每一步，盯了就和手写没区别。我试过在提示词里写「每一步完成后都要确认」，结果它在第 3 步问我「要继续吗」，第 4 步又问——把确认当成了流程的一部分，而不是停下来的信号。

这段演进的尽头，我换过模型——从主力模型切到便宜得多的推理模型，又切到 Codex（这个切换过程记在《Codex 与 Claude Code 切换》里）——调过温度、改过提示词结构，指标没有实质变化。钱省了一半，翻车一次没少。我当时的结论是：别在提示词层面跟模型的注意力机制较劲了。规则该从「让它记住」变成「让系统执行」。这个认知把演进推向了第二段。

二、Context 工程：管好它看什么，把知识喂进它脑子

第二段演进的思路，是把「提示词」升级成「一套上下文和知识的工程体系」。三个动作：渐进式披露、技能化、知识库。这一段做的所有事，可以归成一句话：上下文是稀缺资源，知识是资产，两件事都要工程化。

动手前先处理了最脏的活——上下文本身的管理。那会儿我踩过一个典型的坑：工具返回 50KB 的 JSON，模型在长任务里要从中找一个小字段，找着找着就编。我的做法分三层：大结果外置（超过一定体量的返回不塞进上下文，存起来，只留摘要和引用，需要时按引用取回）、摘要替代（长数据用一句话总结代替原文进上下文，比如「共 23 条记录，状态均为 active」）、历史压缩（对话到一定长度后，把前段压缩成一份结构化交接文档——用户原始请求、已完成的事、试过但放弃的方案、当前卡点，四个字段固定格式，压缩后继续跑）。这三层做完，「3 步能写、15 步胡说」的问题肉眼可见地缓解，模型没换，指标变了。

渐进式披露：不再全量注入，按需加载。 我重写 CLAUDE.md 的思路，来自 Claude Code 的一个设计哲学——构建 Agent 最难的部分不在推理能力，在「动作空间」的设计。规则不再全量堆进上下文，而是拆成一份主文档 + 若干份按需加载的 reference：写博客才读写作规范，画图才读画图规范，同步公众号才读发布规范。上下文里只留索引和触发条件。

这个思路后来长成了我的整套技能库。以写作技能为例，入口是一份 500 行以内的工作流骨架，详细的风格规范、分类型规范、结构工具、SEO 规范拆在 5 个 reference 文件里，走到哪一步加载哪一份。效果很直接：上下文占用从 15K+ token 降到 3K 以内，长任务的规则遵从率反而上来了——因为规则不再和噪音抢注意力。同一个「画图禁止用 mermaid」的规则，全量注入时它看了就忘，按需加载时它正好在画图，记得牢牢的。

技能化：把重复流程固化成 Skill。 我的博客工作流全流程——选题、写作、配图、验证、发布——全部做成了技能：写作技能管正文，drawio 技能管架构图，截图技能管应用界面，发布技能管公众号同步。每次写作不再是「写一段提示词」，而是调一个成熟流程。流程是活的：技能里沉淀了全站踩过的坑，比如「drawio CLI 导出偶发失败时先拷到 /tmp 再导出」这种只有跑过才知道的经验。这些坑写进技能，就成了下次不会再踩的规则——知识从人脑搬进了流程。

MCP 把工具接进来是同一件事的延伸：Figma 设计稿通过 MCP 服务器直接喂给 AI，不用截图、不用描述、不用猜。工具能自己摸到的东西，就不要让模型「想象」。我搭过一套双服务器架构，一个管设计稿读取，一个管设计稿比对，AI 拿到的是结构化的图层数据而不是一张图片——它要改哪个组件、间距多少，一查便知，不用靠猜。

知识库：让跨会话的知识活下来。 无状态缺陷的正解是 RAG。我把自己十年的收藏夹、笔记、PDF 喂进了个人知识库，从「目录式存储」变成「联想式检索」——不用记得知识存在哪，用自然语言提问，系统把相关片段捞出来。面试前模拟、学新东西时追问、写文章时查证，一个库全干了（搭建过程写在《用 RAG 搭个能提问的私有大脑》里）。它还有个意外的好处：跨域连接。前端笔记里的 diff 算法和架构笔记里的微前端隔离本来是两座孤岛，RAG 能同时捞出来，帮我在孤岛之间搭桥——这是人脑最累的活，恰好是检索最擅长的。

这一段的效果是实打实的：单任务质量稳定了，知识跨会话存活了，重复工作明显减少。但我很快撞到第二块天花板——知识是积累起来了，纪律没有统一。

我的技能库里有十几个技能，每个技能各自规定了「应该怎么做」，但技能和技能之间没有一致的验收标准。写作技能要求「段落不超过 7 行」，代码技能要求「跑通后必须汇报证据」——各管各的，没有一个东西规定「AI 在所有任务里都必须守的底线」是什么。更麻烦的是，技能本质还是「提示词」，它的约束力取决于模型读不读。画图技能里写着「禁止用 mermaid」，模型赶时间的时候照样画 mermaid。规则要真正生效，得从「提示」变成「强制」。于是演进进入第三段。

三、Harness 工程：把纪律焊进流程

第三段演进的关键词是「流程契约」。我做了两件事：把研发每个环节的纪律固化成命令，把审查、修复、验证做成自动循环。

命令不是脚本，是流程契约。 脚本只描述「做什么」：跑一下测试，跑完就算。命令描述「做完之后怎么确认做对了」：约束行为边界、定义验收条件、违约就阻断。我在项目里沉淀了 31 条命令、3400 多行，挂在研发流程的每个环节上。写命令的模板是我自己在项目里长出来的——每条命令都包含「AI 该怎么做、必须守什么纪律、什么时候停、怎么自证」，缺一块就不发布。

对比一下就明白差别。脚本版的部署是 ./deploy.sh，中间哪步挂了 AI 甩一句「脚本报错了」就停在那。命令版的 /deploy-prod-be-ops 把「构建 → 上传 → 重启 → 冒烟验证」串成一条带验证的链，任何一步失败都明确报出是哪一环，部署完还强制跑 /prod-testing 冒烟。区别在于：脚本执行完就走人，命令执行完必须自证。512 个功能能交付，靠的就是「自证」嵌在每一步里。

需求环节挂的是 /plan-template：第一轮禁止直接输出完整方案，只产出讨论稿——范围、待确认问题、风险、不做项清单，每个待确认问题必须带推荐和理由，用户确认后才进入定稿。这条命令挡掉了大量「AI 替用户拍脑袋定稿」的浪费。它还禁止分期交付同一份方案：正文里出现「第一期/第二期」直接判违规，要分期就拆成多份独立 plan，每份各自一次做完。测试环节挂 /tdd：锁定红绿重构、缺服务先探测再启动、跑通后必须汇报证据。AI 的行为被约束在纪律内，而不是靠它自觉。

需求盘问也有专门的命令：/10-bs 并行十个视角审视同一份方案——业务闭环、技术边界、多租户、安全、性能——只把综合结论落盘，过程不污染正文。这条命令解决的是「AI 的方案看着合理，其实只过了一遍脑子」的问题，十个视角逼它把方案翻来覆去地审。

loop engineering：审查、修复、验证自动循环到收敛。 核心是「能循环的就不让人介入」。审查不过 → AI 自己改 → 重新验证 → 再审查，直到零问题才退出。把「等同事有空」这类串行等待彻底消掉，也把「人盯着每一轮」的负担消掉——人只看最终报告。我在代码评审里就是这么干的：AI 提交的代码先过自动审查，契约、覆盖率、命名、边界条件逐项查，不过就打回重写，重写完再过，循环到通过为止。人不在循环里，只在循环出口。

循环也不是无限转。每条循环都设了退出条件和最大轮数：修到第三轮还不过，就降级处理——缩小范围继续，或者打回人工。循环的纪律是收敛优先于完美：AI 在一件事上死磕三小时，不如停下来交个分析报告，让看得懂的人看一眼。夜间的修复 Agent 也一样，修不动就输出分析、不强行改，「坦诚比硬撑值钱」。

夜间巡检 daemon：把「AI 自己修 bug」跑进生产。 这套系统每天晚上 00:00 自动拉 dev 最新代码，跑 8 步全量测试——后端单测、集成测、运营单测、运营 E2E、前端 H5 E2E、小程序编译验证。挂了按类型分流：环境问题直接告警叫人，AI 修不了环境，硬上只会越改越乱；代码问题由 Agent 诊断日志、切 fix 分支改代码、用完整测试套件回归一遍，过了才提 MR——注意，只提 MR，不合并。完整设计拆在《睡一觉起来 bug 修好了》里，这里只讲它在演进线上的位置。

这个「只提 MR 不合并」是我整个信任体系里最重要的一条设计。第二天你打开飞书，要么是「全过」，要么是「已修复待 review」，要么是「修不动了快来」。没有「早上来发现昨晚合的代码炸了」这个选项。

daemon 里还有一层容易被忽略的保护：开发者的工作区不能动。脚本切 dev 之前，先把开发者未提交的改动 stash 保护起来，测完再还原。用 stash 而不是 auto-commit，是怕污染任何分支的历史——auto-commit 会在你的分支塞一个 wip 提交，stash 用完 pop 恢复，干干净净。这些边角细节，都是踩过坑才写进去的。

流程轻重也要治理。 不是所有活都该上重型流程。我同时跑两套：OpenSpec 管单点修复（单个 change 不超过 3 个文件、不跨子系统、不超过 5 个 task），Superpowers 管跨系统功能。改一行 SQL 别上重型流程，跨四个系统的新功能也别指望轻流程兜住。流程的轻重，本身也是一条纪律，选型判断我在《OpenSpec 和 Superpowers 我怎么选》里写过。这轮真实开发我跑了 5 个 OpenSpec change 加 1 个 Superpowers plan，边界很清楚：单点修复走轻的，跨系统走重的，混着用两头都堵。

第三段的成果是「3 人两个月交付 512 个功能」，命令体系的全貌在《30 条命令锁死纪律》里。但这段时间我也看到了第三块天花板：命令是单点的，Agent 之间不协调，人每天还是要看报告做判断。31 条命令各管一个环节，没有一个「总调度」知道今天该干什么、哪个 Agent 在岗、规矩守没守住。夜间 daemon 会修 bug，但它不知道修完的 bug 和昨天的知识积累有什么关系。演进的第四段回答这个问题。

四、自治体系：让 AI 自己干，人只看边界

第四段演进把散落的命令、技能、知识、巡检串成一个体系。我的说法是两条工程主线：harness 自治——人只定规则，把执行全权交给 AI；loop engineering——把审查、修复、验证做成自动循环，直到收敛才退出。这一段不是新造了一堆组件，是把前面三段攒下的东西接成一张网。

人退到三件事上：定规则、审边界、看报告。 需求怎么定、方案怎么评审、测试怎么算过、部署怎么算成功——这些是规则，人定。规则之外的执行，AI 自治。人不再出现在每一轮审查里，只在两个节点出现：规则变更时、最终报告交付时。一开始我是不习惯的——写了十二年代码，突然让我「别盯着」很难受。后来想通了：盯每一轮是执行者的活，定规则和审边界才是架构师的活，我在第三段就把执行者的角色交出去了。

信任是分级的，不是二元的。 夜间 daemon 修完代码只提 MR 不合并，就是分级信任——AI 可以修、可以验证、可以提议，但「合入主干」这一步必须有人点头。我后来把这条推广成一套完整的发布状态机：新能力先在 shadow 状态跑（结果不生效，只记录对比），再进 probation（结果生效但有人审核），连续验证通过才转 active。哪个环节出错就自动降级，停止接收新任务。信任建起来很慢，需要连续 20 次正确执行；毁掉只要一次——一个严重错误直接写进主干，用户对整个体系的信任立刻清零。

事故即规范，坑是资产。 每次踩坑不白踩：事故复盘后，教训固化成一条新规则或新命令，进入体系继续守门。覆盖率门禁、契约闸、Flyway 迁移治理，都是这么长出来的。知识从「人脑里的经验」变成「系统里的规则」，这才是跨执行积累的正解——不是记在文档里等人读，是焊进流程里强制执行。我管这个叫「事故即规范」：出了事，第一反应不是追责，是把这次的教训变成下次绕不开的约束。

配套动作是规范本身也要被治理。规则不是写一次就永远对：模型能力升级后，早期为旧模型设的防御可能变成多余约束。我定期过一遍命令的触发率，触发率掉到 5% 以下的防御，要么删，要么降级成提示。系统要能从模型进步里免费获益，而不是永远背着对抗旧模型的历史包袱。

多 Agent 协调是体系里最后一块。 单条命令解决单点任务，多个 Agent 协作解决复杂任务。夜间的修复 Agent、白天的评审 Agent、定时的巡检 Agent，各守各的岗位，通过共享的状态和规则协作。它们之间不需要互相「说服」，因为规则是同一个来源——谁违反了，谁就被门禁拦下。这比我早期设想的「Agent 之间自由对话」可靠得多：协调不靠聊天，靠同一个纪律层。

操作系统类比在这里收束。 回头看我这一年补的东西：上下文管理对应内存管理，RAG 和技能库对应文件系统，命令和流程契约对应进程调度与系统调用，夜间 daemon 对应守护进程，信任分级对应权限系统，事故即规范对应内核补丁。大模型还是那块裸 CPU，但外围已经长出了一层能稳定跑业务的操作系统。

这个映射不是事后找补。我在补每一块的时候，参照的就是操作系统的设计：内存不够就做分层压缩，知识要持久化就做文件系统式的目录与索引，任务要可控就做进程式的调度与恢复，规矩要强制就做内核式的权限检查。操作系统被验证了几十年的设计，是 Agent 工程现成的地图——这也是为什么我认为「Agent OS」不是一个营销词，是一个工程方向。

这一段的形态还在长，但它回答了最初的问题：不是让 AI 更聪明，是让它犯错成本最低、正确路径最短。 好的环境让正确的行为成为最自然的选择。

五条认知收个尾

写到这里，把这一年反复验证的几条认知摆出来。它们不孤立，互相咬合。

翻车不怪模型，怪流程里没有「停」。 AI 是续写器，有输入就输出，有错误就继续。需求含糊时它不会问，测试失败时它不会停。所以工程化的第一步不是调模型，是在流程里装「停」——盘问需求、先写测试、复现 bug，都是停。资深工程师和新手的差别从来不是写得快，是停得准，AI 也一样。我的 /plan-template、/10-bs、/tdd 这些命令，往深了看都是同一个东西：在不同环节装了一个「停」。

先减少犯错的机会，再增加做对的能力。 我能给 AI 的最大帮助，不是给它更强的推理，是消除它犯错的前提：跨步骤的数据不靠它搬运，规则不靠它自觉，验收不靠它自评。错误无从发生，比错误发生后修复便宜一个量级。这条认知决定了我的优先级排序——每次遇到问题，我先问「能不能让这个错误不发生」，再问「能不能让它发生后被拦住」，最后才考虑「能不能靠模型自己想明白」。

纪律不靠人盯，靠系统守。 人盯出来的纪律随人走，系统守住的纪律随系统走。命令、门禁、巡检、状态机——这些机械的约束比任何提示词都可靠，因为它们不依赖模型「读不读」。我在 Context 工程阶段就吃过亏：规则写进技能，模型赶时间照样违反。后来把关键规则从「提示」改成「强制」——不合并的 MR、过不了的门禁、查不到的覆盖率，物理上就过不去，这才算真正焊死。

信任是分级的，跳过人工确认就毁掉整个信任。 准确率再高，剩下那点错误一旦直接生效，用户对整个体系的信任就清零。信任建起来慢，毁掉一次够。所以边界步骤永远留给人——这不是不信任 AI，这是信任的正确姿势。AI 修 bug 可以，合并要人点头；AI 出方案可以，拍板要人确认；AI 跑测试可以，上线要人批准。分级越细，能放开的自动化越多，这不是矛盾，是同一个道理的两面。

每一阶段的天花板，都是下一阶段的起点。 提示词管不住长任务，才有了上下文工程；上下文管住了单次执行，知识却跨不出去，才有了技能库和 RAG；知识积累了纪律不统一，才有了命令体系；命令单点了，才有了自治体系。回头看，四块天花板恰好是操作系统的四块缺失，我这一年做的事，就是把它们一块一块补上。每补一块，AI 能稳定干的活就大一圈——从写一段代码，到写一个模块，到修一个 bug，到跑完一个项目。

裸 CPU 不会变，但外围可以长。AI 工程化的终点不是更聪明的工具，是让一块裸 CPU 稳定地、大规模地跑业务——这条路我从一段对话走到自治体系，走了正好一年。下一步的方向也清楚：让系统自己决定做什么，从被动的执行者变成主动的认知者。约束不是天花板，约束是设计的起点，这句话我越用越信。
