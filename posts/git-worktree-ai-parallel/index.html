让 3 个 AI 同时开工不打架：git worktree 隔离并行工作法

问你一个问题：一台电脑，怎么同时让三个 AI 干三个活？这个问题的第一步不是选哪个模型，是想清楚它们坐在哪——座位没安排妥当，再强的模型也只是更强的肇事者。座位没安排妥当，能力越强闯的祸越大；座位安排好了，并行是白送的。这篇文章讲我用 git worktree 组织 AI 并行的完整方法，从车祸现场讲起，到磁盘账和清理纪律收尾。先给结论：隔离是 AI 并行的第一块基石，且它的全部成本只是一条命令加一点磁盘。

一、先看车祸现场：共用目录为什么必炸

反面教材先上。三个 AI 会话挤在同一个目录里，改同一批文件：A 改到一半，B 读走了 A 的半成品，随手把文件盖掉；C 基于两人混合的中间态继续动手，再把两个人的成果一起踩掉。这不是协作，这是车祸现场——而且是最难定责的那种，每辆车都坚称自己有路权。

先别急着怪 AI。换成人也一样：两个同事共用一台电脑的同一个工作区，你改到一半他去保存了，结果一样是灾难，只不过人会喊一嗓子，机器不会。深层原因是文件系统没有会话隔离。AI 会话的工作单位是「当前目录里的文件」，两个会话共享同一份磁盘状态，一个会话的未完成动作对另一个会话完全可见。人肉协作时有「我在改这个文件你说一声」的默契，AI 之间没有这道社交缓冲，它看到什么就基于什么干活。半成品被当成输入，是并行出事故的标准路径。

顺着车祸往下走，还有一个更隐蔽的坑：会话的「当前认知」会过时。A 会话基于上午的文件状态给了你一套方案，B 会话中午改了文件，A 下午继续干活时，它对世界的理解和磁盘上的现实已经不一致。单会话时代这个问题不存在——唯一的会话就是现实本身；共用目录的并行让每个会话都活在自己的缓存里。顺带一提还有一层隐性损失：三个会话的历史搅在同一份 git 记录里，哪个 AI 改了什么、以哪个版本为准，事后根本理不清。事故之后想要回滚，发现要回滚的并不是一次提交，是一场混战——你分不清哪个改动属于哪个会话，只能全部推倒。并行出的事故按乘法计价：一个会话出错损失一份工作，三个会话共享目录出错，损失的是全部在途工作加当天心情。这也是为什么隔离值得在动手之前做：它是唯一一个成本在事故之前、收益在事故之后的动作。

二、解法：一条命令开几间独立工作间

解法是 Git 自带的功能：worktree。一条命令，从同一个仓库里开出多间独立工作间：

git worktree add ../blog-article -b article/ep08
git worktree add ../video-scripts -b feature/pipeline
git worktree list   # 查看所有工作间

每间工作间有自己的目录、自己的分支、自己的暂存区，互不打扰。全套命令就三个，五分钟能上手：

命令干什么
git worktree add 路径 -b 分支名开一间新工作间并建新分支
git worktree list列出所有在册工作间
git worktree remove 路径拆掉一间（干净的话直接删）
git worktree prune清掉已手动删除目录的失效记录

用完一间，remove 拆掉即可。它和再 clone 一份仓库有本质区别，重点在历史这一层：clone 是把整个仓库连同全部历史复制一遍，磁盘直接翻倍；worktree 的所有工作间共享同一套仓库历史和对象库，各自只有一份工作区文件。开五间工作间的磁盘开销，约等于五份源码加一份历史；换成 clone，就是五份完整仓库。共享的还有分支名录和标签——任何一间工作间里建的新分支，其他工作间立刻可见，跨工作间的进度随时一目了然，不需要任何额外的同步机制。

AI 视角看这个安排：每个会话拿到一间独立办公室，工牌是真发的，门禁也是真的，走廊里永远不会再撞见同事的半成品文件。会话 A 在自己的目录里改到天亮，也碰不到会话 B 的一个字节。隔离能细到这个份上，包不打架的——放心说这句，这是 Git 的机制保证，不是默契，也不需要任何一段额外的提示词去维持。

有几个机制细节值得知道，它们决定了 worktree 为什么适合 AI 并行这个场景。

第一，Git 不允许同一个分支同时被两间工作间签出，这是防呆设计——如果两间工作间能签出同一分支，隔离就名存实亡，改的还是同一份引用。所以开工作间的正确姿势是每间一个新分支，一条命令里的 -b 参数顺手就做了，分支名带上业务前缀，看名字就知道哪间在干什么。

第二，暂存区每间工作间独立一份，stash 互相看不见。这对 AI 并行恰好是好事：某间工作间临时 stash 了半成品，别的会话不受影响，也不存在「谁把谁的暂存弹错了」这种事故。

第三，提交的可见性是即时的。A 工作间里的一次提交，立刻出现在共享历史里，B 工作间马上能看到本地引用，中间不需要经过任何远端。这意味着跨工作间的协作可以纯本地进行：一间改完脚本，另一间立刻 rebase 到它的成果上继续干活，整条链路不离开你的电脑。

第四，全部工作间记录被仓库记住，git worktree list 随时列出所有活着的工作间和它们各自签出的分支。目录迷宫的解药就是这一条：所有「房间」都在册，定期查房就行。

三、我的真实用法：三仓三线

具体的并行布局长这样。我的主力项目各有主目录：博客源码仓、全栈项目仓、面试题库仓，三个仓库就是三条业务线。主目录保持不动，作为「看板」——每个仓库需要并行的活，就从主目录开出工作间。

一天里的真实排布可能是这样：下午一点，博客仓开两间，一间改视频管线的合成脚本，一间写下一篇文章的初稿；两点，全栈仓开一间调订单接口；三个 AI 会话各就各位，同一个下午三条线同时都在动。三点半，脚本那间的改动先完成，跑一遍合成验证，过了就提合并请求，拆间；四点，接口那间联调通过，同样处理；文章初稿最后收尾。到傍晚，三间工作间全部拆掉，主目录里只剩三条已合并或待评审的分支记录。

这套节奏的要点是错峰交付：三间工作间的活刻意挑周期不同的，保证任何时刻都有活可验、也有空档可喘。如果三间的周期完全一样，验收会挤在同一个时刻爆仓，并行的好处就被验收堵住。主目录里只干轻活：看进度、做 review、决定合并顺序。哪个工作间的活先干完，先提 MR，先评审先合并，合并完成后 worktree remove 拆间，工作目录和心里一起干干净净。

这套布局能成立，靠的是 worktree 的两个性质咬合：提交互不干扰，因为工作区隔离；进度互不阻塞，因为分支各走各的。三个 AI 谁也不等谁，人的注意力从「盯着一件活跑完」解放成「在几条线之间切换验收」。

我的我的三个仓库各有分工：博客源码仓承载文章和视频管线脚本，全栈项目仓承载业务开发，面试题库仓承载碎片化的知识整理。仓库是业务线，工作间是房间，先有线再开房，每间房干活时都有明确归属， nobody 走错门。三仓的活性质不同，但并行的规则一致。挑什么活进工作间，有一条经验判断：并行要给「边界清楚的重活」。改一套视频管线脚本、写一篇结构成熟的文章、调整一个主题样式，这类活有清晰的完成标准和独立的文件范围，开间并行收益最大；反过来，需要频繁互相确认的活（比如两个功能要共享同一份新接口的定义）不适合硬并行——它们天然有依赖，拆开做只会把依赖变成返工。并行的前提是活能拆干净，拆不干净的先拆设计，再拆工作间。还有一个常见误区是拿并行掩盖串行依赖：两间工作间的活共享同一份数据库迁移或同一个接口定义，那就先做完上游那间，别指望两间各猜一半最后能对上。依赖要么被隔离消灭，要么被排期消化，唯独不能被愿望消化——这条经验适用于一切并行，不止 AI。

有两个工程细节别省。第一，每间工作间的构建产物和依赖是各自的：前端项目的 node_modules 在每间工作间都要装一遍，首次开出工作间后先跑安装，别等到 AI 报出「模块找不到」才想起来。第二，Git 钩子按配置共享，提交前的检查脚本在每间工作间同样生效，隔离的是工作区，不是纪律——该过的门禁一间都少不了。

四、AI 并行了，人干嘛

三个 AI 同时开工，人的角色得跟着换。串行时代你的时间花在「等」上：等它改完、等它跑完、等它出结果，一天下来真正干活的时段被切成碎片。并行时代等待被重叠进彼此的间隙里，你的时间花在「判」上：每个工作间的产出逐个过目，哪个能合、哪个要改、哪个该推倒，拍板的人始终是你。

角色从打工人换成验收员之后，工作节奏要刻意设计，否则并行会退化成多线程救火。我的做法是给每个工作间定交付物边界：这间产出的是「一个能跑的脚本」，那间产出的是「一篇过完全部扫描的文章」，边界清楚了，验收才有落点。验收每个工作间时看什么，我有三问：改动是不是只发生在声明的工作范围内（防止 AI 越界顺手改别处）；跑过该跑的验证没有（脚本要跑通，文章要过门禁扫描）；提交信息说人话没有（将来翻历史时能看懂）。三问都过才进合并流程。

验收时还有个顺序技巧：先验改动面小的。脚本改动五分钟看完，先给它放行合掉，工作间当场拆掉；文章要通读，放在最后集中看。让短周期的工作间快进快出，磁盘和注意力都省。

另外控制并行度，这条对人是硬约束。三线是我试出来的舒适区——再多，验收的注意力就被摊薄，每个活都看得不深，出错率反而上升，返工吃掉并行省下的时间。并行的上限从来不由机器决定，机器开十间都行，瓶颈在你的 review 带宽。并行的收益曲线不是一路向上的：两到三线是峰值，再往上，人成了瓶颈，事故概率跟着涨。AI 负责并行，人负责拍板；并行省下的是等待，判断与拍板省不下，也不该省。

以前一个分支串行干三件事，切来切去，上下文来回搬运，匆匆忙忙连滚带爬；现在三个工作间各干各的，从从容容游刃有余。效率提升的真实现金来源，是把「切换成本」从人的脑子里挪进了文件系统结构里。

五、磁盘账与清理纪律

一间的完整生命周期值得单独画出来：开间、装依赖、干活、验收、合并、拆间删分支，六步走完，目录系统里不留一丝痕迹。一间的完整生命周期值得单独画出来：开间、装依赖、干活、验收、合并、拆间删分支，六步走完，目录系统里不留一丝痕迹。并行的代价要说清楚，第一笔永远是磁盘。每间工作间占一份工作区文件，依赖包各装各的，前端项目一间工作间轻松吃掉几百兆。小项目没必要开多间，一个目录串行足够；值得开间的标准只有一条：「这个活的周期足够长，长到值得为它单独付一份工作区的钱」。日抛型的两分钟小改动，开间是杀鸡用牛刀，徒增心智负担。

第二笔是清理纪律，这条不守，并行的便利会变成目录迷宫。规矩很简单：活干完、MR 合了，当场 git worktree remove 拆间；分支也一并删掉，不留「以后可能还用」的幻想。remove 有个前置条件：工作间要处于干净状态（没有未提交的改动）才能直接拆。有未提交内容时它会拒绝，这是最后一道保护——真要放弃这些改动，得显式强拆，等于亲口确认「这间的活不要了」。这个摩擦是故意的，它把「随手丢工作」从两秒钟的误操作变成一个要打force的动作。

时间一长忘了哪些工作间还活着，git worktree list 一查便知；偶尔遇到手动删了目录但仓库里还有残影的，git worktree prune 清掉失效记录。我的习惯是每周看一眼 list，超过三间的，逐间问自己「这间还有活吗」，没有就拆。我自己也翻过车：连开几间赶工，想着收工一起清，结果一周后目录里多了五个陌生文件夹，每个都要翻提交记录才能认出是什么活。并行工具的坟墓，都是用「明天再清理」堆出来的。清理还有个心理红利：每拆掉一间干净的工作间，都确认了一次「这条线已经完结」，比在一堆陌生目录里考古舒服得多。

六、两个常见问题

开这么多工作间，Git 仓库会不会变慢？ 不会。worktree 共享同一套对象库和引用，仓库数据的体积和历史的查询速度与工作间数量基本无关；变的只是工作区文件，那些本来就各归各的目录。真正会拖慢你的是依赖安装和构建产物，它们按工作间计数，这条前面已经算过。

三个 AI 用同一个模型账号，会不会互相限流？ 会话并行跑的是本地交互，模型调用的高峰取决于各会话的任务节奏，同时轰炸同一个接口确实可能碰到速率限制。实际体感还好：三条线的任务节奏天然错开（一个在读文件，一个在写内容，一个在跑构建），真正同时发起大量请求的时刻不多。真撞上了，错峰安排各线的重活就是解法，轻活穿插在空档里跑。

AI 会话之间需要共享一些上下文怎么办？ 共享的正确位置是仓库本身：公共约定写在 AGENTS.md 这类项目文档里，所有工作间天然共享；跨工作间的产出交接，走分支和合并，让 Git 记录交接历史。别用「让 AI 读另一个目录的中间文件」这种野路子共享——那等于在隔离墙上凿洞，凿着凿着就回到了车祸现场。

不用 worktree，直接 clone 几份仓库行不行？ 行，代价不同。clone 的磁盘开销大得多，历史要同步（不同步就是几个孤岛仓库），跨仓库对比和合并也麻烦。worktree 的核心优势正是「隔离工作区、共享历史」这一对组合：开间秒级即可完成，提交立刻可见于所有工作间，分支不用来回推。一两间工作间的轻度并行，clone 也能凑合；常态化的多线并行，worktree 是更干净的答案。还有一笔隐性成本：clone 出来的多份仓库，时间一长历史会漂移，你很难说清哪份是新的；worktree 的历史永远只有一份，漂移这个词在 worktree 的世界里不存在。顺带回答一个 Windows 用户关心的问题：worktree 的路径就是普通目录，放进任何盘都行，中文路径建议避开——各种工具链对中文路径的支持参差不齐，别让路径成为这套并行方案里的第一个事故现场。

六、和远端协作怎么相处

工作间的分支要不要推到远端，我的做法是分两种情况。纯本地的探索性工作（写一篇文章、调一个脚本）不推，干完合并，远端只见到结果；需要别人介入或者涉及业务系统的活，分支照常推送，同事在远端看到的和你本地完全一样——因为 worktree 的分支本质上就是普通分支，没有任何私有魔法。这也意味着同事完全可以 checkout 你的工作间分支做接力，隔离是你的选择，不是墙。

多人团队引入 worktree 还有一个协调点：约定工作间目录的命名规则。我的习惯是「仓库目录旁加业务后缀」，比如项目目录叫 app，工作间就叫 app-feature-x；固定命名让任何人扫一眼目录列表就知道每间在干什么，也方便写脚本批量清理超过一周没动静的工作间。命名是并行的路标：路标立好了，新同事进办公室不用人带。

两个常见问题

并行这件事，难点从来不在「让它们同时动起来」，在「动起来之后互不伤害」。git worktree 把隔离做成了文件系统层面的事实：目录隔离、分支隔离、暂存区隔离，历史共享、钩子共享——该隔的隔死，该连的连上，边界清楚到文件系统那一层，这才敢叫并行工作法。AI 的并行能力配上这个结构，一台电脑才真正变成了一间有多张工位的办公室。

而人的位置，在这间办公室里不是多余的那个，是唯一的验收官。开间之前想清楚每间交付什么，合完就拆不留尾巴，三线以内守住注意力——工具的纪律加上人的纪律，并行才不是「同时出事故」，是「同时出活」。最后把全文压成三行：开会间前，想清楚这间的交付物；干活时，守住三线以内的并行度；合完之后，当场拆间删分支。做到这三条，你的电脑就准备好了同时雇三个不领工资的员工——而且这一次，办公室 politics 为零。
