同一个问题贵 30 倍？DeepSeek Harness 缓存省钱的三条纪律

同一个问题问两遍，token 数一模一样，开销却可能差 30 倍。多数人把这种价差归因于模型档位或者计费策略，实际的因果链要短得多，贵的那次只是没命中缓存而已。我读 DeepSeek Harness（下称 dsh）源码时确认了更进一步的事实，命中率的高低可以被工程纪律锁死。

背后的结构相当确定：system prompt 分段注册、编号拼接，会话日志只追加不许改，上下文容器等快照变化才写入。三个安排合力保证每一轮请求的前缀逐字节稳定。模型选择只是起点，折扣稳不稳要看前缀。

一、两档价格差在哪

DeepSeek 官方 API 价格表把 v4-flash 的输入拆成两档。缓存命中的输入按 0.05 元/百万 token 计费，高峰时段 0.10；缓存未命中按 1.5 元计费，高峰时段 3.0。两档比值刚好 30 倍，命中那份在服务端复用了上次的计算结果，服务方才有底气给出这种折扣。高峰与平峰各自翻倍，比值保持 30 倍不动，这份折扣比例在任何时段都成立。

二、Agent 为什么天生吃亏

两个前提叠在一起，让 Agent 用户比纯聊天用户难受得多。其一，Agent 每一步都要重发全部历史，读文件、改代码、跑测试，每个动作的输出都追加进上下文，下一轮原样送回服务端。其二，缓存按前缀做逐字比对，从第一个字节开始，中间任何一处变动都会让它身后的一切重新计价。

于是出现一道随轮数增长的重复税：会话越长，每轮重复发送的比例越高；中途动了共享片段，前面攒的折扣一并清零。

用两档价给同一份十万 token 的历史各算一遍：未命中一次付 0.15 元，命中间隔只付 0.005 元，比值正好是价目表上的 30 倍。会话越往深处走，重复段在每轮输入里的占比越高，两种结局的累计差额随轮数线性放大。

三、dsh 的三条源码纪律

上文的吃亏逻辑倒过来读就是工程方案：既然前缀稳定值这么多倍，就把稳定做成架构属性。dsh 在源码里立了三条纪律，分别落在注册顺序、历史改动和增量写入上。

第一条，顺序不许乱。system prompt 由分段对象构成，接口名 PromptSection，每段带 order 编号，框架按编号升序拼出最终提示词。编号的分布也有讲究，harness 身份段 -100，部署人设段 0，工具指导段占 100 到 199，定义和注释都在 packages/core/system-prompt/src/index.ts。注册动作谁先谁后毫无影响，成品序列逐次一致，前缀从第一天起就是稳的。

第二条，历史不许改。会话日志只追加，写入后不存在修订入口。对旧上下文做压缩时，请求体由两部分组成，精确的旧对话前缀，加上作为末条指令的 COMPACTION_INSTRUCTION。前缀一字未动，这趟压缩请求几乎全程命中缓存，近乎免费。日志凭什么敢这么设计，我在会话当 git 那篇里拆过底座：事件流是唯一真源，改写被结构性禁止。

第三条，能不动就不动。上下文容器 PromptContext 被文档明确标为缓存安全结构，docs/subsystems/system-prompt.zh.md 第 73 行原话是 agent loop 仅在完整当前快照发生变化或被压缩移除时才记录到保留模型历史之后。快照平稳时就不去碰保留历史，前缀原样等着被下一轮整段复用。

这条门控的另一面同样成立：合法的变化也按受控姿势进场。运行时上下文的每次更新以一条新快照消息推进，旧快照经 surface 替换退场（源码深读那篇的 6.4 节拆过），替换落在保留历史之后的位置，先前的字节序列保持原样。快照平静则前缀不动，这是第三条纪律的字面含义。

四、段落注册表拿什么防手滑

第一道保险写在类型契约里。PromptSection 的 name 要求唯一，docs/subsystems/system-prompt.zh.md 的接口注释写明重复注册直接抛异常，非有限数值的 order 同样抛错。想在系统提示词里制造歧义做不成：同一段落装两次，进程当场起不来，带着含混前缀上线的路径从源头堵死。

第二道保险是作用域遮蔽规则。作用域内注册的同名段落覆盖全局段，工具 schema 与变量遵循同样的「局部优先」；每条注册都返回精确的 Cordis disposer，卸载动作即撤销登记。注册与注销还会广播 system-prompt/change 事件，提示词层面的任何变动都留有可观察的痕迹。

第三道看着像漏洞，实际也是受控门。complete 标记的段落声明「我即完整系统提示词」，组装流程照常跑完协作瀑布，让工具、上下文与变量先行解析，随后把这一段原样恢复为唯一提示词；出现两个有效 complete 段时组装直接失败。连逃生口都配了互斥锁。

PromptContext 一侧同样克制。动态上下文按 order 升序拼接，空文本不贡献任何内容；接口另备一个 suppressRuntimeContext 开关，可以在作用域内压掉全部运行时上下文贡献，无需逐个拆插件。

工具清单的装配细节同样严谨。每次组装收集到的 ToolProviderResult 除 schema 外还带一份 knownNames，即限制生效前的名称全集，用来区分「配置名拼写错误」与「已知工具在此作用域被有意隐藏」这两种情况，文档原话就是这么分的（docs/subsystems/system-prompt.zh.md）。

五、压缩的触发时刻也钉在代码里

历史改动窗口由压缩策略圈定，压缩何时获准发生则是写死的枚举。docs/subsystems/compaction.zh.md 给 CompactionTrigger 定义了两个取值：pressure 与 context-overflow。压力策略盯着最近一次持久化的路由请求判定用量；溢出策略在 provider 明确报告超窗时介入，即便用量未达阈值也会强制做一次有效缩减。

阈值数字我在源码深读那篇里逐行核对过：compaction-basic 默认 thresholdRatio 为 0.8，retainRatio 为 0.16。用量越过上下文窗口八成才动手，动手后仍按比例保留尾部原文。触发线与保留线都随包分发，什么时候动历史因此成为可审计的配置事实。

执行位置也固定：压力压缩在串行的 agent/pre-step 里运行，先于该步骤的请求推导（compaction.zh.md 服务一节）。触发后先调用可选的 toolResultPruner 处理超长工具结果，再用 ctx.tokenMeter 重新测量，测量结果直接决定范围选择，中间不给其他逻辑插手的机会。

动手次序是一组事件锁。先追加 compaction/start，随后生成摘要、写入 summary 记录与替换用的 user 消息，最后追加 end；操作中途崩溃只会留下一条没有配对的 start，日志里永远不出现谎称成功的 end。手动压缩的预期失败被枚举成 busy、cancelled、changed、summary、commit、persistence 六类错误码，失败尝试照常落盘留痕。

内容侧还有质量闸门：摘要必须严格小于被遮蔽的原文，否则报错终止；区域边界保持工具调用与结果的配对平衡，避免切出孤立的 tool_call 让下一次请求被 provider 以协议错误拒收；头部的原始任务描述永远原样保留。

除了被动等待压力，CompactionEngine 还暴露 compactNow()，作为轮次之间的维护动作主动缩减空闲会话；没有安全范围时返回 null 且不写入任何事件（compaction.zh.md）。被动阈值加主动维护，「什么时候允许动历史」的时刻表就完整了。

六、跟一轮请求走完命中全程

把前面的纪律串成流水线。轮次领取输入后的第一步是装配：按编号拼出提示词各段并收集工具 schema（architecture.zh.md 的轮次流程）。第二步 buildRequest 过 agent/request 瀑布，provider 与 model 等参数可被中间件提案修改，收尾时 markAgentLoopRequest 对整个请求执行 deepFreeze。冻结动作的意义我在源码深读第四章写过：数据离开组装函数后不可变，是后续一切复用正确性的前提。

请求发出后，流式分片进入 BlockAssembler，这个唯一的共享实现负责把 StreamChunk 折叠回内容块、usage、结束原因与回放状态（docs/subsystems/llm-streaming.zh.md）。usage 是一组互不重叠的计数：inputTokens 只统计未缓存输入，缓存读写单独记入 cacheReadTokens 与 cacheWriteTokens，计费输入等于三者之和。provider 若把命中折进单一总数，比如 DeepSeek 的 prompt_tokens，适配层负责把它再扣出来。

这组字段随后流向统计消费方，ctx.tokenMeter 持有按会话隔离的回放折叠区（capability-seams 服务表的描述），翻译层最终把 cached_tokens 与 prompt_cache_hit_tokens 两种命名归并成界面上的同一个数字。数字从服务端绕一圈回到你眼前，这条链路的每一环都站在前缀稳定的地基上。

七、什么会亲手打碎它

反面教材随手就能举，比如装插件。插件装载会向 system prompt 注入新段落，并同步调整工具清单，这两处都位于共享前缀的源头区域，从第一轮起攒下的缓存随即全线作废。切换运行模式同理，极简模式与标准模式拼出的 prompt 不同，切换瞬间等效于给会话换了个开头。

人设属于同一雷区。deployment persona 注册在 order 0，紧挨 harness 身份段，处在共享前缀的源头区域；任务中途更换人设文本，效果等同给整场会话换了开场白，此前攒下的命中一次性清零。身份与人格分离的设计（identity 归 harness、persona 由部署方在同槽注册）方便了定制，也把「动前缀的开关」交到了配置手里。

操作层的建议跟着清楚了：装插件、切模式这类动作安排在任务间隙做，避开大任务中途。

挂载链路那篇写过插件生效要经过完整的重启组装流程，这类成本放在阶段收尾做，顺带避开任务中途被打断。

任务边界之内还剩一层缓和的空间：插件与模式保持不动时，共享前缀随会话日志逐轮变长，命中输入的份额随之上涨，第二节里那笔随轮数放大的差额在同一套纪律下调了头，成了随轮数放大的节省。纪律管的只是源头那几处开关，日常轮次不需要任何额外安排。

八、官方还推了一把

上游也在往同一个方向使劲。PTC 模式原名 Code Mode，改名痕迹留在 packages/client/ui-agent-preset/src/client/locales.ts 里，字段 presetCodeName 标注着 PTC 模式。该模式让模型写一个小型 TypeScript 程序组合多步操作，把分散在多个轮次的调用并成一轮，请求数下降，攒下的前缀折扣也更耐用。

它的收益结构对缓存格外友好：分散在各轮的中间结果收进同一段程序的变量作用域，请求总数降下来，保留在每轮输入里的共享前缀份额反而更完整。缓存折扣按轮兑现，轮数本身变少了，省下的部分自然更扎实。

显示端另有一个细节。v0.1.1-rc.1 的更新包含一项精度修正，说明原文是 better precision for 99.x% cache-hit ratios，专门伺候 99.x% 区间的命中率展示。肯为百分比的第四位数字做适配，说明长期高命中已是这个团队的默认预期。

九、省钱的开关在你的请求前缀里

外部数据先摆上来。第三方横测口径下（Composio 团队测了八款 Agent 框架，36氪等媒体转载过结论），dsh 的缓存不命中率是 0.07%，换算即命中率约 99.93%。本地自查也方便：会话界面底部的 stats 区域有一行「缓存命中 {percent}%」，文案键 stats.cacheHit 定义在 packages/client/ui-conversation/src/client/locales.ts，数值出自 packages/llm/llm-deepseek/src/translate.ts 第 47 到 54 行的字段归并，cached_tokens 和 prompt_cache_hit_tokens 两种命名都被收录。

看到这里，开头的价差有了完整解释。价格表对所有人相同，分岔点在使用者手里：PromptSection 编号别乱，日志追加别改，快照平静别扰，再把插件与模式切换挪到任务边界，30 倍的价差就从抽奖结果变成固定收益。这张折扣券在供应商的谈判桌上买不到，它在第一个字节发出之前就已经定价。
