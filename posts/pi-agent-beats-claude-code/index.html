Databricks 前段时间在自家几百万行的真实代码库上，把主流模型和 Coding Agent 工具挨个跑了一遍。结果有点扎眼：性价比最高的那批组合里，一个个人维护的开源项目 Pi 出现了四次，把 Claude Code 和 Codex 挤到了旁边。成本便宜 1.2 到 2 倍，任务通过率基本不动。

这个结果跟我的体感是一致的。过去几个月我把 Pi 当日常主力用，在它上面做过二次开发，把它的扩展系统从头到尾折腾了一遍，也替团队沉淀过一套常驻扩展。这篇文章把「Pi 凭什么」拆成三层讲清楚：数据层发生了什么、上下文这笔账怎么算、扩展系统为什么是结构性的优势。

测试本身先要站得住

先说这份数据凭什么可信。市面上的公开跑分，SWE-Bench、Terminal Bench 这一套，题目是公开的，答案会慢慢泄露进各家模型的训练数据。模型在这些榜上的分数，掺了刷题的水分。

Databricks 的做法不一样：直接拿自家工程师合并过的 PR 当考题。几百万行代码、十几种语言，从每天上千次合并里挑高质量的 PR，原来 PR 里的测试用例就是评分标准。这套题有两个特点，模型没见过这些题目，评分有客观的执行结果做依据。

这种测法其实比看起来苛刻。真实 PR 的需求描述往往很短，缺上下文，模型要靠读代码库自己补齐理解——这正是日常开发的真实难度，而不是考题式的「需求写得很完整，只考实现」。测试用例当评分标准也堵住了另一条作弊路径：没有空间靠花言巧语拿分，测试跑过就是过，跑不过就是不过。

值得注意的是，这类「企业内部数据集」评测正在变多。公开榜的分数通胀让所有人都不再信任榜单，有真实代码库的公司转而用自家数据自测，再把结论公开。对选型的参考价值反而更高：它测的是「干活」，不是「做题」。看这类报告时盯两个细节——横轴是不是每任务成本（而不是 token 单价），任务是不是真实 PR（而不是造出来的需求），满足这两条，数据才值得当决策依据。

看这张图的读法：横轴是每个任务具体花多少钱，纵轴是任务通过率，点越靠左上角越好。性价比前沿线上七个点，Pi 占了四个。全场的最高分也是 Pi 接上 Opus 4.8 开到最高思考档位，通过率 90%。

这张图里还有一条很多人看漏的信息：GPT 5.5、Opus 4.8、GLM 5.2 这些旗舰模型挤在同一层，分数差在三个点以内，但价格差出数倍。开源的 GLM 5.2 质量跟 Opus 打平，单任务成本 1.28 美金对 1.94 美金。

也就是说，模型这层的差距在收窄，Agent 工具这层的差距在被放大。同一个模型、同样的思考强度，换一个 Harness，价格差 1.2 到 2 倍。这正是值得深挖的地方。

模型层：单价是错觉，总账才是真相

先把模型层讲完，因为它最容易选错。看数据时会发现一个反直觉的现象：有的模型单价只有对手的一半不到，每任务的花费反而更高。

原因在 token 效率。模型干活的风格差异很大：有的干脆利落，读一遍文件直接动手；有的谨慎，反复读、反复想、每一步都输出大段分析。谨慎的那个单价便宜，但一个任务跑下来消耗的总 token 是对手的快两倍，两边一乘，总花费反超，分数还更低。Databricks 的测试里就有这样的案例，单价便宜的模型每任务成本更高，通过率还低了六个点。

所以挑模型看两个数：每任务平均花费，和通过率。每百万 token 的单价只是报价，不是账单。这个习惯我转给国产模型之后又验证了一遍，便宜模型的正确用法是配一个省 token 的 Harness，把它的单价优势守住，而不是扔进一个重型框架里被 token 消耗吃掉——我在 /posts/codex-ccswitch-deepseek/ 里记录过具体的接法。

工具层：被低估的变量

模型层的结论是「别纠结」，工具层的结论正好相反：这是最值得花精力的变量。同一台发动机，换一个底盘，每公里油耗差出一倍——Databricks 的六组同模型对照里，五组性能差距在三个点以内，价格差 1.2 到 2 倍。

唯一的例外是 Opus 4.8 开到最高思考档位那一组，Pi 落后了七个点。测试者的猜测是噪声，也可能是上下文变长以后模型开始犯糊涂。这个细节我记下来了：极简不等于在所有场景都赢，重活上官方工具仍有优势，后面讲边界时还会回到这点。

另外一个独立开发者的评测也得出了类似的结论：Pi 做出效果差不多的结果，但更快、更便宜。两组独立数据指向同一处，这个结论就不是孤证了。

一句你好，两万 token

我最早对 Pi 产生兴趣，不是因为它跑分高，是一个数字对比：在 Claude Code 里发一句「你好」，系统提示词带下来两万 token 起步；Pi 做同样的事，不到一千五。

两万 token 都是什么？Claude Code 的系统提示词里塞了大量工程：如何规划任务的引导、几十个工具的使用说明、各种边界情况的叮嘱。这些内容每一轮对话都会作为上下文喂给模型，而且后面每一轮请求都会命中这部分前缀缓存，它决定了你这次对话的最低消费。

Databricks 给的解释是 Pi「上下文管理更有效、工具集更精简，每轮给模型的上下文少三倍左右」。我拆过 Pi 的源码，这个「有效」可以从两个地方看。

第一是起点低。Pi 的默认内核只有四个工具：运行 Bash 命令、写文件、读文件、编辑文件。没有子智能体，没有自带 MCP，系统提示词就是一段很短的说明。起步的一千五 token 里几乎没废话。

第二是过程省。这靠扩展实现，也是 Pi 最有意思的地方。有个扩展专门清洗工具的输出：模型跑 git log 查提交，原生命令会带回哈希值、作者、日期、正文、diff 一大串，这个扩展在结果返回给模型之前先做一次裁剪，只留关键字段。类似这样清洗一遍，工具输出的 token 消耗能砍掉八到九成。

这里有个关键的结构差异：Claude Code 的钩子系统允许你在工具调用前后追加信息，但改不了工具调用的结果本身。Pi 的扩展可以。数据进上下文之前先过一遍你的代码，这一刀下去，省的是每一轮、每一个工具调用的钱。

这笔账放到一个真实任务里看更直观。一次中等复杂度的改动，模型要读七八个文件、跑十几轮命令、来回三十多轮对话。每一轮都背着两万 token 的前缀，每一轮的工具输出都原样进上下文，两头叠加，这就是「单价差不多的模型，换个工具账单差一倍」的全部来历。反过来，起点低加过程省，两头都占，账单就压下来了。

我的体感和这个模型对得上：同样的活，Pi 跑完的会话文件明显更小，长任务跑到后半段也不容易因为上下文塞满而开始「忘事」。上下文不是越大越好，是越准越好——塞满历史的上下文里，跟当前任务无关的部分每多一分，模型犯糊涂的概率就多一分。

极简内核加扩展，顺序不能反

省 token 只是结果，Pi 真正的设计主张是一句话：框架应该适应人，而不是人适应框架。

这句话落在架构上，就是「极简内核 + 扩展系统」的两层结构。内核只保留一个编程智能体最少要有的东西——那个 Agent 循环、四个基本工具、会话管理。其余的一切，MCP 适配、子智能体、规划模式、浏览器控制、甚至动态工作流，全部以扩展的形式存在。要什么装什么，不想要的确实不存在于你的上下文里。

对比一下 Claude Code 这几年的演进路径，会发现一个有意思的现象。它最初有一个思考工具，给模型一块推理草稿区，这在早期模型上确实涨分；到 Sonnet 4 之后，模型自己会思考了，这个工具只剩拖慢过程的作用，被移除。早期的并行工具调用脚手架也是同样的命运，模型能力上来之后，框架里的补丁一个个变成了负担。

问题在于，走重型路线的框架，这些加法和减法你只能等官方做。动态工作流消耗大量 token，你不喜欢，也拿不到一个没有这个功能的 Claude Code。钩子系统开了口子，但改动的范围有限。

Pi 把这个矛盾从根上解了：既然框架的多数设计会随模型进化而过期，那就只保留不会过期的那部分，其余的让用户按需拼装。扩展目录里甚至有现成的「Claude Code 化」「Codex 化」扩展包，官方工具的特性可以插进来用，用完可以拔掉。

这个取舍在官方文档里写得非常直白，有一节就叫「我们没有做什么」：没有 MCP、没有子智能体、没有权限弹窗、没有规划模式、没有内置 todo、没有后台 Bash——每一项都给了「用扩展实现」的指引。把「不做」写成公开承诺，等于把边界画清楚：内核永远保持能一口气读完的体量，功能的天花板交给生态。

更激进的是扩展的编写方式：扩展可以由 Pi 自己写。它内置了扩展文档的知识，清楚当前加载了哪些扩展、接口长什么样。我在实际用的时候，直接说「帮我在输入框上方加一个显示当前分支的小组件」，它会自己去读扩展文档、写出扩展文件，reload 一下就生效。框架在运行时修改自己，这在 Claude Code 上没有对应物。

从上往下看，Pi 是五层积木

把仓库结构摊开看，「极简内核 + 扩展」不是两层，是五层积木。最底下是 AI 包，一个跨模型调用的抽象层，各家模型的接入、鉴权都在这层，可以让用户直接绑已有的订阅。往上是 Agent 包，纯的智能体循环。再往上是编程智能体包，在循环之上加了四个工具和会话管理——把它当 Claude Code 的 SDK 理解就行，但每一块都能换。然后是 TUI 包，把编程智能体装进终端界面。最上面还有个编排器包，做定时任务、多进程分派这类事，目前偏实验性。

这个分层决定了二次开发的姿势：你想做的是「用编程智能体」，就拿到一个现成 SDK；你想做的是「改智能体本身」，就下钻到 Agent 包那一层，一百多行就能读懂循环的全部。Claude Code 的 SDK 给不了第二选项。

能力全景：内核之外，Pi 到底给了你什么

「极简」两个字容易让人以为 Pi 功能寒酸，实际用下来正好相反：内核小，外围给的能力密度非常高。这部分把我用得最熟的几块摊开讲，也是 Pi 区别于「精简版 Claude Code」的地方。

四种运行模式，从终端到产品

Pi 不是只有一个终端界面，它有四种跑法。交互模式就是完整的 TUI；pi -p "问题" 是脚本化的单次执行，适合塞进 Makefile 和 CI；--mode json 把整个过程变成事件流，管道程序可以直接消费；再往上是跑在 stdin/stdout 上的 JSON RPC 协议，以及嵌入应用的 SDK。

这四种模式共享同一套会话与扩展。我在终端里调试好的扩展，换成 RPC 模式接到自己的服务里，行为完全一致。前面提到的 OpenClaw 用的就是 SDK 模式——同一个 Pi，既是你的终端工具，也是别人产品的运行时。

模型接入：十五家起步，会话中途随便换

Provider 层覆盖 Anthropic、OpenAI、Google、Azure、Bedrock、Groq、xAI、OpenRouter、Ollama、Kimi、MiniMax 等十五家以上，API key 和 OAuth 订阅都支持，还可以用 models.json 加自定义的。切换模型是会话内的即时操作，一个快捷键的事。

这对「省钱」的意义比看起来大：日常任务切到便宜的国产模型，跑到一半发现这个任务复杂了，原地切回 Opus 继续，上下文原封不动。不用开新会话、不用重新喂背景。我的习惯是把两三个常用模型加进收藏列表，一个键位循环切换。

会话是树，不是流水线

多数 Agent 工具的会话是一条线，走错了只能从头再来。Pi 的会话是树状的：所有分支存在同一个文件里，/tree 可以跳回任意一个节点继续，像 git 的提交图。旁边还有按消息类型过滤、打书签，/export 导出 HTML，/share 直接传成可分享的链接。

还有一个细节我特别喜欢：运行中转向。模型正在跑一个方向不对的任务时，不用打断，直接回车输入一条修正消息，它会在当前工具调用结束后收到这条转向指令；按 Alt+Enter 则是排进队列等这轮结束。以前我在 Claude Code 里只能眼睁睁看它跑完一段歪路再纠正，这笔时间和 token 都是白扔的。

Skills：按需加载，不动 prompt cache

Skills 是独立的能力包，每个 skill 是一套指令加配套工具，按需加载——模型判断当前任务需要哪个 skill 才把它读进来。这解决了能力扩展和 token 成本的两难：装二十个 skill 不会让系统提示词膨胀二十倍，因为它们不常驻。

官方的立场更进一步：默认不做 MCP，能用 CLI 工具加文档解决的，就不上 MCP。MCP 的运行时开销和上下文占用是真实的，这个「反着来」的选择和整个项目一脉相承。需要 MCP 的时候，扩展目录里有适配器装上就是。

上下文工程：AGENTS.md、SYSTEM.md 和可定制的压缩

上下文管理不只在「省」，还给了你显式的控制面。AGENTS.md 从用户目录、父目录、当前目录逐级加载，放全局约定还是项目约定自己定；SYSTEM.md 可以按项目替换或追加系统提示，等于给单个项目定制内核行为。

压缩（compaction）也是开放的：接近上下文上限时的自动摘要，扩展可以换成自己的策略——主题式摘要、代码感知摘要、甚至换一个便宜模型来做压缩。会话太长开始「忘事」的问题，第一次有了可编程的解法，而不是等官方的固定策略。

Packages：扩展生态的分发方式

扩展、skill、提示词模板、主题，四样东西打包成 Pi package，pi install npm:xxx 一条命令装，也支持直接从 git 仓库装。官方目录里五十多个示例扩展，子智能体、规划模式、权限门控、沙盒、SSH 执行、MCP 集成、状态栏，全是现成的。

生态规模还比不上 Claude Code 的插件市场，但分发机制是对的：npm 当注册表，git 当源，没有中心化审核的瓶颈。对企业来说还能做个私有的 package 集合，团队约定一条 pi install 命令就能铺开——比传配置文件优雅得多。

我在 Pi 上做二次开发的体感

如果说省 token 是 Pi 的性价比，扩展系统就是它的天花板。这两点我在二次开发时同时踩到了。

我的场景是在 Pi 之上搭自己的 Agent 系统，而不是把它当个终端里的编辑器用。这件事在 Claude Code 上也能凑合做——它有 SDK，可以封装。但封装和改造是两回事：SDK 给你的是「用它的方式跑」，扩展给你的是「改它跑的方式」。Pi 的扩展点覆盖工具注册、上下文注入、会话管理、命令、UI，几乎每一段行为都能换成你的实现。

举两个我实际写过的扩展的形态。一个是上下文注入：每次会话开始前，跑几条 git 命令，把当前分支、工作区状态、最近几条提交压缩成一小段摘要，追加到系统提示词后面。模型开局就知道仓库的状态，不用每次现查。

// 上下文注入扩展的骨架，实际约二十行
pi.on("beforeAgentStart", async () => {
  const summary = await buildGitSummary(cwd); // 分支/变更/最近提交
  pi.appendToSystemPrompt(`当前仓库状态：\n${summary}`);
});

另一个是工具输出清洗，就是前面说的那刀。给 Bash 这类工具的调用结果挂一个钩子，结果先过我的裁剪函数，再进上下文。两个扩展加起来几十行代码，换来的是每一轮请求都更轻。

// 工具输出清洗扩展的骨架
pi.registerToolWrapper("bash", async (result) => {
  return trimToEssentials(result); // 只留关键字段再进上下文
});

做托管形态时还有两处必须动的地方。Pi 默认把会话存成本地 JSON Lines 文件，多用户的共享后端不能这么干，我把会话存储换成了数据库，上下文压缩的时机也改由服务端控制。工具层同样要包一层：读写和 Bash 命令得落到每个用户自己的沙盒目录里执行，不能碰宿主机的文件系统。这些改动在官方 SDK 的架构里都是要「绕」的，在 Pi 里是「换」——接口本来就是开给你换的。

写扩展的体验比写插件顺，原因很简单：Pi 自己会写扩展。卡住的时候把报错丢给它，它对着自己的文档改，多数时候比我翻文档快。这个「工具能修理它自己」的体验，是我在 Claude Code 插件体系里没有过的。多 Agent 的编排思路其实也受这个影响：与其在重型框架里想办法「配置」出自治行为，不如在可改写的循环上直接「实现」它，这个方向我在 /posts/ai-agent-task-orchestration/ 里单独展开过。

这条路不是只有我一个人在走。增长最快的开源 Agent 项目 OpenClaw，底下跑的运行时就是 Pi——网关、界面、编排是自己写的，Agent 循环交给 Pi。选它的理由和我的一致：一个几万行的黑盒 SDK 改不动，一个内核加扩展的系统改得动。

Pi 不是没有代价

讲到这容易变成单方面吹，把边界也交代清楚。

第一个边界：极简内核对使用者的要求更高。重型系统提示词里那两万 token 不是全无价值——如果你的提示词写得模糊、只丢一句「帮我做个功能」，Claude Code 会用系统提示词里的工程规范替你把意图补全，产出一个相对完整的项目。Pi 收到同样模糊的输入，补全得更少，产出更贴你字面说的那个东西。提示词质量越高，Pi 的优势越大；反过来，乱写需求时重型框架反而更稳。

这个边界我在教同事用 Pi 时看得特别清楚。提示词写得细的人，切换过去毫无痛感，还嫌以前贵；习惯丢一句话等结果的人，会觉得 Pi 的产出「缺了点什么」——缺的其实是官方框架替他做的那部分规划。工具没有替你思考的义务，但重型工具确实会掩盖你提示词的短板。想通这一点，我对「哪个更好」这类问题的回答变成了「先看你的提示词质量」。

第二个边界：生态和文档的量级。Claude Code 出了问题，搜索一圈总有答案；Pi 的社区小，很多答案要自己去读源码。好在它的源码足够小，我通读一遍的代价远低于通读 Claude Code 的心理准备。这也是「极简」的隐性红利：出问题时，你能看懂它。

第三个边界：团队场景。团队里成员水平参差，给所有人一个带默认约束的重型框架，比让每个人自己拼扩展更可控。我的做法是把团队共用的扩展收进仓库，新人 clone 下来就带着一套约定好的工具和清洗规则，不要求每个人自己搭。Pi 的玩法更适合愿意动手的个人和有意愿沉淀扩展资产的小团队——前提是有人愿意当那个搭积木的人。

第四个边界：跑分之外的场景。前文提过，最高思考档位的重活上，Pi 落后了七个点。一次测试说明不了全部，但它提醒一件事：极简内核赢在常见任务，超长上下文、超复杂任务这些边角场景，重型框架的工程沉淀仍有价值。我的分工是 Pi 扛日常八成的活，剩下两成难的交给 Claude Code，这个组合跑了几个月没有再动过。

日常怎么配：我的组合

讲完原理给一份可以直接抄的配置，这是我几个月收敛下来的稳定组合。

模型上，Pi 配 GLM 或 DeepSeek 跑日常任务，成本压到 Claude Code 的零头；重活切回 Opus。Pi 的模型接入是可替换的，一份配置里放多个 Provider，按任务挑，不用像在官方工具里那样被订阅绑死。有些接入方式还能直接吃官方订阅的额度，对已经有 Claude Code 或 Codex 订阅的人来说，边际成本接近零。

扩展上我只常驻三个。上下文注入（git 状态摘要）和输出清洗前面讲过，第三个是 MCP 适配——需要连外部服务时临时开，用完关。动态工作流、子智能体这些，我装过、试过、卸了，不是不好，是我的日常任务用不上，装着只占上下文。Skills 也一样按需：写文章配一套，排查线上问题配一套，触发时才加载。扩展目录里的东西按需取，这是 Pi 用法的第一原则，装一堆用不上的扩展，它就退化成了另一个重型框架。

成本上给个体感参照：同样的任务组合（日常迭代、改 bug、小重构为主），切到 Pi 加国产模型的组合之后，我每月的 API 账单降到之前的零头，这不是省出来的，是前面那两刀——低起点、清洗过程——自动砍掉的。而且省的不只是钱，长任务的稳定性跟着变好，上下文干净了，模型中途犯糊涂、重复读同一个文件这类毛病的出现频率肉眼可见地降了。

界面上，终端里直接跑，需要给同事演示或者做可视化排查时用网页版界面。命令行和网页版底下是同一套会话和扩展，切换没有成本。社区里也有人在网页版上继续封装，做团队共享的操作台，这条路能走多远我不确定，但「同一套内核、任意换壳」本身就是 Pi 扩展系统的又一次验证。这套东西全部收在 dotfiles 仓库里，换机器一条命令拉起来——配置即代码，Agent 工具栈本身也应该被版本管理管起来，这个习惯我在 /posts/ai-dev-multi-ide-config-ssot/ 里固化过一次，现在同样适用于 Pi。

带走三句话

把这几层的推理收敛成一个能带走的框架，三句话：

模型是租来的，各家的旗舰挤在一层，选型纠结的性价比很低。账要算总账，token 效率比 token 单价更影响最终花费。Harness 是你能控制的变量——同一模型换个壳，成本差两倍，而 Pi 证明了这层变量可以完全握在自己手里。

我现在的用法是日常编码 Pi 起手，重活和模糊需求留给 Claude Code，两者的切换成本几乎为零，因为底下的模型可以是同一个。工具栈的演进我一路追下来，从命令体系到多 Agent 再到 Harness 之争，趋势一直没变过：谁把控制权交还给用户，谁赢。这个判断我在 /posts/ai-agent-engineering-evolution/ 里展开过，也在 /posts/deepseek-harness-source-internals/ 里对 DeepSeek 的「一切皆插件」做过同方向的源码验证——Pi 和它殊途同归。

极简内核加开放扩展，这不是某个工具的巧思，是这一代 Agent 基础设施该有的样子。那些没有抢到首发优势的项目靠这个思路追了上来，先发的重型框架也在一点点开放自己的内部结构，方向已经很清楚了。
