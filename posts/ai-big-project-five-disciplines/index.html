你的 AI 员工在大项目里静默翻车：5 个瞬间与 5 条管教纪律

编译能过，测试能过，页面点着也没毛病。直到月底对账，财务才发现佣金按原金额多结了一笔，积分一分没扣，经营报表里的收入比实际高出一截。你回头翻代码，罪魁祸首是三周前那次「无害的」部分退款改造：接口对、页面对、新功能的测试全对，唯独三个依赖订单状态的老模块，谁都不知道世界已经变了。

这是 Claude Code 和 Codex 用户在大项目里的标准剧情。AI 承诺的交付：功能全部完成。实际的交付：每一块都合格，拼起来是错的。它不是在摸鱼，它比谁都忙，忙着把看不懂的代码当成冗余代码删掉。这才是真·精神离职，人在工位，心已辞职，手还在删你的业务逻辑。

我把这种状态叫静默翻车：代码能运行，编译能通过，局部的测试也挑不出毛病，但系统已经和真实业务对不上号了。最气人的是追问它的那一刻：它诚恳道歉，说「对不起，是我没有考虑到位」，然后补一版代码，你再测，还是不行。道歉是无限的，考虑是不到位的。

这篇文章拆 5 个翻车瞬间，每个瞬间配一条管教纪律。方法上参考了一条高赞视频总结的五类问题，案例全部换成了我自己的工程语境：一部分直接来自我被坑过的真实项目（完整复盘见 AI 全项目反模式，这次往深一层走）。先讲机制，再对账。

一、它看得见你的代码，看不见你的业务

翻车之前先想明白一个问题：AI 在大项目里是怎么「看」你的项目的。它能读当前文件，能读上下文，能跑命令，看起来无所不知。但它看到的只是此刻的这一小块：你改哪个模块，它就读哪个模块，加上任务里贴进来的那点说明。

有人会说，AI 不是有很长的上下文吗，把规则全贴进去不就行了。大项目的规则多到什么程度：每个状态机的流转条件、每张表的归属边界、每条资金操作的先后顺序，全贴进去，速度和成本都扛不住，而且每做一个小改动都重读一遍全部历史决策，没有项目经得起这么玩。所以它实际的工作方式永远是：只看当前任务最相关的几个文件。

这就出事了。你上个月定下的退款状态校验、三年前出过事故后补上的幂等判断、口头约定好「谁都不许动」的公共过滤规则，全都不在它眼前那几个文件里。它的记忆只有一张便利贴，便利贴写不下的规则，在它眼里约等于不存在。看到「没有被引用」的判断，删；看到「多此一举」的状态检查，简化。它不是在作恶，它是在按可见的信息挑最省事的改法。问题是，业务的真相不在可见范围里。

这就是五个瞬间共同的起点：代码它都看得见，代码背后的原因它看不见。

二、瞬间一：它不知道这段代码为什么存在

退款接口，表面看就是把订单状态改成「已退款」。但真实项目里，退款要解冻占用的金额、退回积分、通知对账系统，而且只有订单处于某几个状态时才允许退款。这些判断在代码里就是几个 if，没有任何注释告诉你它们动不得。

AI 读到这段代码，看到的是几个「看起来没有被引用的状态校验」。它的判断标准很朴素：没有被用到 = 冗余 = 优化掉。于是顺手删了，删得理直气壮。你测试的时候走的是正常路径，一路绿灯；等一个异常状态的订单进来，规则裸奔，事故上岗。

上下文塞不下，第一节说过。所以规则的正确放法不在对话里，在仓库里，这就是纪律一。

纪律一：把隐性规则写进 AGENTS.md，让项目自己记住。 具体做法分两层：全局的业务铁律写进项目根目录的 AGENTS.md；每个模块单独建规则文档，存放这个模块的业务规则和设计原因，再让 AGENTS.md 指向它们。写的时候有个硬要求：不只写「这个接口怎么调用」，还要写「为什么要这样做」「哪些条件不能绕过」：

# 售后模块规则

- 订单状态为「已支付/部分退款」时才允许发起退款，
  其他状态直接拒绝。此校验是资金安全边界，禁止删除或放宽。
- 每次退款成功必须同步：解冻占用金额、扣回积分、
  通知对账系统。三者缺一属于事故，测试必须覆盖。
- 设计原因：跳过状态校验曾导致已取消订单被退款，
  见历史事故记录，改动前先读。

看到区别了吗？「禁止删除」配合设计原因，就是把便利贴换成白纸黑字。新会话一开，规则自动加载，AI 想删校验之前，至少得先读懂那笔历史事故的来龙去脉。永远不能指望 AI 记住你的项目，要让项目自己把规则记下来。

这条纪律有两个常见翻法，都翻在「怎么写」。一种是写成小说：把三年的架构演进史全塞进去，三千字的文档没人读得完，AI 也一样，太长的规则文档等于没有规则文档。另一种是写成 API 手册：只列接口参数，不写业务边界。AI 最不缺的就是读参数的能力，最缺的是知道哪条 if 背后是资金安全。

写法标准就一条，每条规则都回答「为什么不能动」，答不了为什么的规则，说明你自己也没想清楚，那条规则才是真正该删的。

顺手答一个高频问题：Claude Code 读的是 CLAUDE.md，Codex 读的是 AGENTS.md，两个工具混用怎么办？选定一个文件当正本，另一个只写一行指针「规则见 AGENTS.md」指过去，别维护两份内容。规则文档最怕的不是缺，是两份对不上：AI 信哪份都错，你自己都不知道哪份是新的。

三、瞬间二：局部全对，整体跑偏

瞬间一是删规则，瞬间二更隐蔽：一行都没删，代码逻辑本身还是对的，系统照样错。

看这个案例。原来的订单只支持整单退款，系统只需要区分「已支付」和「已退款」两个状态。现在要加部分退款，AI 在售后模块里记录每次退了多少钱，只有全部金额退完，才把订单改成「已退款」。这个逻辑对不对？完全正确。接口测试、页面测试、售后模块自己的回归测试，全绿。

问题在它没看到的地方：老系统里的佣金结算、积分扣回、经营报表，从来都是按订单状态驱动的。在它们的世界观里，「已支付」等于「一分钱没退过」。现在「已支付」的订单里混进了退掉一半金额的订单，三个老模块毫不知情，照常工作。

月底对账，三个模块的述职报告无懈可击：售后说退款准确，佣金说结算如常，报表说数据如实。合起来：公司每个月白送一笔佣金。分布式系统没有根因，只有月底对账时排队的背锅人。

纪律二：改代码之前，先让 AI 做影响分析，只分析，不动码。 把 prompt 从「帮我实现部分退款」改成两段式，第一段只做分析：

不要写任何代码。列出以下内容：
1. 本次要改的文件，以及它们调用的公共方法；
2. 依赖这些公共方法的旧模块（重点：定时任务、消息消费者、报表）；
3. 权限、租户隔离、数据范围会不会被波及；
4. 需要补跑的回归测试清单。
输出为影响分析报告，等我确认。

影响分层两层记：直接影响是当前要改的类和接口；间接影响是定时任务、消息消费者、报表这些「看不见的调用方」。把这些列出来，后面每一轮审查你都不会只盯着改动最多的那个文件，火苗会窜到哪早就心里有数。分析确认完，第二段再放开手让它写。

顺带回答一个疑问：三个老模块各自都有测试，为什么一个都没拦住？因为测试也是按模块写的。佣金模块的用例里，订单状态从来只有「已支付」「已退款」两种干净输入，「已支付但退了一半」这种混合状态根本不在用例的状态空间里。模块测试验证的是老逻辑在老输入下还对，而这次事故的输入空间本身被改动了。这就是影响分析必须人工确认的原因：它找的不是 bug，是测试用例覆盖不到的新状态组合。

有人会问：AI 扫调用链，扫得全吗？诚实回答是不一定。藏得深的间接依赖（反射调用、配置里声明的 Bean、消息队列的消费关系）它可能漏。

所以影响分析的正确姿势是 AI 与工具交叉验证：静态检索交给 grep 和 IDE 的调用层级，依赖范围交给 Maven 依赖树，消费关系交给消息中间件的控制台，AI 负责把这几路结果拼成一份完整清单。谁擅长记调用关系用谁，AI 的价值在归纳和判断「哪个影响要紧」，不在当人肉 grep。

四、瞬间三：它不知道哪里是大动脉

每个老项目都有一类代码：文件不长，看着普通，但全系统都在调它。统一权限校验、租户数据过滤、消息幂等。我把它们叫大动脉代码。它们只在项目里的一个位置，后面连着一大片功能。

AI 没有这张解剖图。一个典型场景：要给超级管理员加跨租户查询功能，AI 找到公共数据过滤规则，觉得「在这里放开限制改动最小」，直接改了。超级管理员确实能查全部数据了，同时每个普通用户接口、每个定时任务用的也是这套规则。更阴的是，其中一些调用关系藏在注解和拦截器里，页面上根本看不出来。等测试发现其他租户的数据串了，你顺着调用链能查半下午。

解剖图画不出来的时候，用三个信号识别大动脉：其一，改个方法签名，全项目 IDE 报红：爆红面积就是供血面积；其二，测试覆盖率报告里它被大量用例反复穿过，说明各路业务都押注在它身上；其三，APM 调用热点里它常年在榜。占住其中一条，就该进 AGENTS.md 的高风险区名单。

纪律三：在 AGENTS.md 里圈出高风险区，动它之前先过四问。 高风险目录和高风险方法单独列一节，明晃晃写上「改这里需要走特殊流程」。AI 的任务一旦碰到这些位置，必须先回答四个问题，答不清楚就不许执行：

# 高风险区（改动前必须回答四问）

- /security/   统一权限校验
- /tenant/     租户数据过滤
- /mq/         消息幂等

四问：1) 为什么要改这里？
      2) 现在有哪些地方在调用？
      3) 有没有只改当前模块的替代方案？
      4) 改完需要回归哪些功能？

这四问的价值不在问，在答的过程：AI 为了回答「谁在调用」，必须真的去扫一遍调用链。大动脉的分布图，就是你把一次次扫描的答案写回文档攒出来的。没有扫描就没有分布图，指望一次配齐不现实。

给你看一次合格的四问长什么样。任务：给超级管理员加跨租户查询。AI 的回答：「1) 为什么改这里：只有公共过滤规则对所有查询统一生效，改动最小；2) 调用方：用户侧全部列表接口、三个定时任务、报表导出，共 17 处；3) 替代方案：在公共规则里加管理员白名单条件，普通用户路径保持原判断不变；4) 需回归：多租户数据隔离测试、管理员越权测试、报表导出抽查。」

第一问答完你就该警觉了：「改动最小」就是大动脉的陷阱所在，四问的价值是把这份诱惑摆到桌面上，拍板的人得是你，不能是它。

顺带看第三问的答案：白名单条件加在公共规则里，作用域只对管理员查询这一条路径放开，普通用户走的判断逻辑一行没动，这就是「只改当前模块」的落点。反过来，如果当时直接放宽公共过滤规则，第 2) 问里那 17 处调用方全部被动继承新行为，回归范围从一条路径爆炸成全系统。

五、瞬间四：编译通过被当成了业务完成

这一坑我有切身之痛，之前在 编译能过不代表代码正确的事故复盘 里写过完整过程：一次看起来无害的优化之后，系统「功能正常」跑了四天，最后定位到 AI 静默删掉了一段没人记得的 270 行代码。编译全绿，测试绿灯，业务早就不对了。

编译通过只证明语法和依赖关系没问题，跟业务流程对不对是两码事。「代码写完了」和「功能交付了」之间，隔着三层测试的距离：

第一层，测新功能本身。部分退款的金额边界、退款上限、异常提示，逐条过。第二层，测直接关联的旧功能。会员列表、财务统计、权限过滤，凡是影响分析报告里点过名的，挨个跑。第三层，测核心业务流程全链路。从登录授权、创建订单、状态流转到退款到账，完整走一遍，不是抽测。

纪律四：测试结果不许只写「测试通过」四个字，留证四件套缺一不可。 输入是什么、期望结果是什么、实际返回是什么、失败时留下什么日志。这四个字段写下来，「测试通过」才从一句口号变成一份证据。之后线上出问题，你拿旧记录一对，几分钟就知道是哪次改动漏了哪层；不留证，每次排查都从零开始。它跑完还会给你发「周报」：本周完成任务 12 项，通过测试 12 项。周报不收，收证据。

一份合格的留证长这样，四个字段一条不能省：

字段反例（口号）正例（证据）
输入部分退款金额 100 元订单，退款 40 元
期望退款成功状态=部分退款，积分扣 40%，佣金按 60% 结算
实际测试通过状态=部分退款，积分扣 40%，佣金按 60% 结算
失败日志无若失败：保留 /tmp/refund-*.log

左边一列是 AI 默认交上来的东西，右边一列才是你月底敢签字的依据。两张表一对照，谁在验收、谁在念稿，一目了然。

六、瞬间五：一个会话从头错到尾

前面四个瞬间都是单点失误，第五个是系统性跑偏：同一个会话里，AI 先理解需求，再设计方案，再写代码，最后自己审查自己。听起来很高效——直到最开始的理解就是错的。

理解偏了一度，方案顺着偏，代码顺着偏，最要命的是审查环节：它自查用的还是当初那个错误前提。让写代码的自己审代码，等于让被告兼任法官，它的全部理性都在为「我没错」找证据，绩效越高你越危险。同一个错误，四道工序走了四遍，这不是质检，这是复读。

纪律五：把工作拆成三个独立会话，分析、实现、审查各一个。 分析会话负责需求分析、影响范围和测试计划；实现会话只负责照确认过的方案改代码；审查会话最特殊，重新开一个全新上下文，只给它三样东西：需求、代码差异、测试证据，让它以完全无关的第三方视角回答：功能有没有回归？有没有无关改动？权限有没有漏洞？接口参数能不能兼容？历史数据会不会受影响？

三个会话就是三个工位：分析工位想清楚，实现工位照图施工，审查工位拿着放大镜找茬。审查工位必须是个新人，不知道前面发生过什么，入职第一天就干最得罪人的活，这才是它的价值。

这套思路跟我之前总结的 explore-propose-apply 四步工作流 是同构的，区别是那篇讲单人流程，这条讲的是用独立会话把「复读机风险」物理隔离掉。

审查会话的开场 prompt 可以直接抄这个骨架：

你是独立审查员，不参与过本需求的任何实现。
只根据三份材料回答：需求描述、代码差异、测试证据。
逐项检查：功能有没有回归 / 有没有无关改动 /
权限有没有漏洞 / 接口参数能不能兼容 /
历史数据会不会受影响。
每一项结论必须指向证据的具体位置，找不到证据就写「无法确认」。

最后一句是灵魂：允许它说「无法确认」。审查会话最常见的失效方式，是它为了交差硬编一个「已检查，无问题」。把「找不到证据」和「没有问题」区分开，这份审查才值钱。

先从哪条开始：五条纪律的最小起步组合

五条纪律一起上，对大多数人是劝退价。实际落地有先后。纪律一是纯一次性投入，规则文档写一次，之后每个会话都在白嫖它，所以它永远排第一。纪律二和纪律三是流程，每次改动多做十分钟分析，换来的是审查时不用大海捞针。纪律四和纪律五是验收，成本跟着测试走，本来就该花。

预算只够一条的话，选纪律一，把「为什么不能动」写进 AGENTS.md；预算够两条，加纪律二，改码前的影响分析。纪律四的留证看着繁琐，实际是给未来的自己写排查地图，出事那天的你会感谢当初多写的那几行输入输出。剩下三条，等你的项目真的咬过你一口，自然就会去配齐：被佣金多结算咬过的人，不需要任何人说服他留证据。

还有两个常见问题值得先答。小项目需要这套吗？ 不需要。改个 landing page、写个独立小工具，上下文塞得下、调用关系一屏看得完，五个瞬间一个都不会发生，硬套流程是给自己上刑。这套纪律的适用边界就是大项目的定义，规则超出上下文、调用链超出人脑、模块数量超出你敢说「我都记得」的程度。

AI 会不会自己进化到不需要这些？ 模型的长上下文和记忆能力确实在变强，但「项目自己记住规则」和「验收留证据」保护的是你自己的判断力，跟模型强弱无关。工具再聪明，签字的人是你。

错误要拦在主分支之前

回到开头那起月底才炸的事故。复盘整条事故链：AI 不知道规则（瞬间一），改码前没做影响分析（瞬间二），动了没标记的大动脉（瞬间三），测试只看了「通过」两个字（瞬间四），最后还让它自己审自己（瞬间五）。五个瞬间里它没有一次「犯罪」，每一次都敬业、迅速、态度诚恳。问题从来不在它不够聪明，在于我们按「超级员工」的预期用了它，却按「零入职培训」的方式放了手。

五条纪律合起来就两句话：别指望它记得规矩，让仓库替它记；别指望它自查，让另一个它来查。AGENTS.md 和规则文档是把口头叮嘱变成仓库里的白纸黑字，影响分析和四问是逼它交出思考过程的成本，三层测试和留证是把你从「信任它」升级成「验证它」，三会话分离是让错误前提活不过第一道工序。

拦截点也顺着往后排：工作区里靠影响分析和四问拦一次，审查会话里靠新上下文拦一次，主分支前靠证据链拦最后一次。三层里丢两层，还有一层在；一层都不设，才叫听天由命。用得越狠，它自由发挥的空间越小，你的交付就越踏实。

数字员工转正，「能写代码」这条第一天就考过了，剩下要考的只有一道题：错了能不能被拦住。拦不住的话，它永远在试用期，你永远在对账。我是 1024 工程笔记，越基础的东西，越值得讲透。
