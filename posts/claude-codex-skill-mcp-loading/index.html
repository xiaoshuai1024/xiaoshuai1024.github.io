Claude Code 与 Codex 的 Skill 与 MCP 加载源码对比：装上不等于用上

我装过一个很不错的 Claude Code skill，用一次之后它就再也没被触发过。我以为是我描述写得不好，调整了好几轮 frontmatter 都没用。直到读了两边的加载源码，我才发现自己的预期从根上就错了：skill 不是「装上就进入工作区」的东西，它是「被发现、按需注入、特定时机触发」的三段式机制——Codex 的源码里，skill 的加载要过 selection 和 invocation 两道闸；MCP 更直接，连 server 连接都是按需的。装 20 个 MCP 不用，一个都不连；装 5 个 skill 不提，它们就只是躺在磁盘上。

这是系列最后一篇必做篇。前五篇见架构分层、主循环、subagent、上下文、权限门控。

先交代这篇的证据等级，比前几篇复杂，因为 skill 部分横跨了 CC 的两个时代：Codex 侧照旧是源码确证（commit 63b268c81b）；Claude Code 侧分两段——v1.0.88 没有 skill 系统（全文件搜索 skill 只命中一处 Arma 语法定义的关键字表，是假阳性），skill 的分析基于 2.1.229 的 claude.exe 二进制字符串勘察加官方口径；MCP 两侧都有 1.0.88 的行号级确证。每处结论我会标明来源。

一、Codex 的 skill：三道闸的按需机制

Codex 把 skill 做成了独立 crate（skills/），职责拆得很清楚：parser.rs 解析 SKILL.md 的 frontmatter（代码注释原话：Validated metadata parsed from a SKILL.md frontmatter block），loading.rs 负责发现和加载（load_roots 扫描各个 skill 根目录，LoadedSkillRoot 带快照缓存，不是每次都重扫磁盘），selection.rs 和 invocation.rs 是两道筛选闸，mentions.rs 处理 @mention 触发。

加载之后怎么进模型？不是塞进 system prompt，而是作为 context item 注入，入口在 core/src/skills.rs:83 的 maybe_emit_implicit_skill_invocation——注意函数名里的 maybe：每次是否真的注入，要看当时的上下文和触发条件。turn loop 里的 build_skills_and_plugins（第二篇讲主循环时提过的准备工作之一）负责每个 turn 重新评估。

把这个链条走一遍，「装上不等于用上」就有了源码答案。这也是全篇第一个钩子的兑现处——我那个沉睡的 skill，命运的每个关口都能在代码里指认：

  • 发现层：skill 要放在被扫描的根目录里（Codex 的 load_roots 扫描多个根，Claude Code 是用户级、项目级、插件级三个位置），frontmatter 要能通过解析。格式错了，它连候选名单都进不了。这一层的排查方法也最简单：目录对不对、文件名对不对（SKILL.md 大小写敏感）、frontmatter 能不能被 YAML 解析——三关过不了，后面的机制根本不会运行。
  • 选择层：selection.rs 在候选里挑当前相关的。你的 skill 描述和当前任务的匹配度，决定了它能不能过这关。
  • 触发层：mentions.rs 认显式的 @mention——提了名字基本必触发；maybe_emit_implicit_skill_invocation 认隐式触发——模型根据描述自己判断要不要调。显式触发是用户的保险丝：怀疑 skill 没生效，直接在输入里 @ 它的名字，绕过选择层直通触发——一次实验就能定位问题出在前两层还是模型层。

所以我那个 skill 沉睡的原因清楚了：它过了发现层，卡在选择或触发层——不是我描述写得差，是机制设计上就要求「场景精确匹配才进上下文」。这是合理的：skill 描述本身要占 token，全量注入等于给每个请求加税。

官方文档对 Claude Code 的 skill 有个「progressive disclosure」（渐进披露）的说法，我在 2.1.229 的二进制里 grep 到了 progressive、loadSkills、skill_name、available-skills、SKILL.md 这一整组字符串（二进制勘察，确证字符串存在）——机制是同构的：先只给模型一份「技能目录」（名字加一句话描述），模型点名了才加载 SKILL.md 正文，正文里的 references 再按需读。三层漏斗，每层都省 token。

回头看这段演化有个值得记下的行业细节：skill 系统的发明权在 Anthropic（2025 年下半年随 2.x 推出），OpenAI 跟进后在开源代码里实现了同构机制（Codex 的 skills crate 连 SKILL.md 这个文件名都一致）。头部产品的机制趋同速度越来越快——一个有效的抽象从出现到成为全行业标配，周期已经缩到一两个季度。对使用者的含义：别把任何一个产品的机制差异当成长期优势来规划，真正稳定的差异还是第一篇讲的那些架构层路线。自己写扩展时选「已成事实标准」的形态（SKILL.md、MCP），弃各家的私有花样，扩展的可移植性比功能的独特性值钱。自己动手写 skill 的实操细节我写过一篇手把手记录，体系层面的拆解在这篇。

二、MCP：两种连接哲学

MCP 的差异比 skill 更结构化，因为两边的连接策略是反着的。

**Claude Code v1.0.88：启动即全连。**配置发现是分层的（L349510 一带）：用户级配置之外，项目根的 .mcp.json 是团队共享通道，首次使用要过审批（settings 里有 enableAllProjectMcpServers、enabledMcpjsonServers / rejectedMcpjsonServers 三组名单，L350779 到 L350792）。连接建立后，工具注入是一条清晰的流水线（L386397 的 K2B 工厂）：

let tools = await client.request({ method: "tools/list" })
return tools.map((t) => ({
  ..., name: `mcp__${sanitize(server)}__${sanitize(t.name)}`,
  isMcp: true,
}))

mcp__服务器__工具 的三段命名（L349458 有四处变体的拼接和判断逻辑）就是系统提示里那句「All MCP-provided tools start with mcp__」的出处（L368654）。工具的能力元数据直接映射调度行为：readOnlyHint 映射并发安全（第二篇讲过），destructiveHint 映射破坏性标记（L386413 到 L420）。发送前还有一道过滤（L388701 的 HH0）：mcp_tool_use / mcp_tool_result 这类 MCP 专有块会被改写成 API 认识的格式。

**Codex：按需懒连接加预热。**连接管理在 core/src/mcp.rs:60 的 McpManager（维护 configured_servers 和 effective_servers 两份名单，配置脏了才刷新），真正连接的时机在 turn 开始时：required_mcp_servers_for_input 解析你这轮输入里 mention 了哪些 server 和 plugin，只连接需要的（session/mcp.rs 的 runtime_mcp_config_and_context），另配 session/mcp_prewarm.rs 做预热——后台提前握手，等你真用到时省等待。传输层的支持也宽：rmcp-client crate 里 stdio、streamable HTTP、独立进程传输、OAuth 全有。

两种哲学的价签都很明确。全连的好处是工具永远在线，模型随时可用；代价是启动时间随 server 数量线性涨，且所有工具描述都占上下文——MCP 装多了变慢变挤，病根在这。懒连接的好处是「装而不常用」零成本；代价是第一次触发有个连接延迟（prewarm 缓解但不消除），且模型得先「知道」要 mention 哪个 server——发现逻辑依赖输入文本，间接依赖用户的表达习惯。

这两个价签还解释了一个常见的错误归因：很多人发现 Claude Code「越用越慢」，第一反应怪模型，实际病根常在 MCP 列表——每轮请求的上下文里都驮着所有已连 server 的工具描述，十个 server 平均能让每个请求多出几千 token 的固定开销，TTFT（首 token 延迟）随之上涨。清理不用的 server 立竿见影，这是我能给 Claude Code 用户性价比最高的一条优化，没有之一——零成本、即时生效、收益直接反映在每轮请求的延迟上。Codex 用户的对称问题是「为什么第一次用某个 MCP 要等几秒」——懒连接的握手成本，预热能盖住大部分，盖不住的那部分就是按需付费的价格。

二点五、MCP 的边角：审批、elicitation 和反向服务

MCP 还有三个不显眼但影响使用的机制，补在这节。

第一个是项目级 server 的审批 UX，也是团队协作里最容易踩的坑。.mcp.json 是跟着仓库走的，第一次打开一个带 .mcp.json 的项目，工具会问你要不要启用——这个交互不是礼节，是安全边界：仓库作者能在里面声明任意命令（MCP server 就是本地起进程），不设审批等于把执行权交给了仓库。审批结果落进 settings 的 enabledMcpjsonServers / rejectedMcpjsonServers 名单，下次不再问。团队内共享 MCP 配置时，建议把「review .mcp.json 的 diff」纳入和 review package.json 同级的习惯——你引入的不是配置，是代码。

第二个是 elicitation（session/mcp.rs:499 的 request_mcp_server_elicitation）：MCP server 反向向用户要输入的通道——server 执行到一半需要你补个参数（API key、选择项），通过这个机制弹到终端问你。这让 MCP 工具从「单向调用」变成「双向交互」，做需要凭据的集成（数据库连接、登录流程）时关键。Claude Code v1.0.88 没有对应机制的明文痕迹，2.x 的 IDE 集成里 MCP 交互在增强（官方口径）。

第三个是 Codex 自身可以作为 MCP server（独立的 mcp-server/ crate）。这个方向是反的——前三条都在讲「agent 怎么用别人的能力」，这一条讲「别人怎么用 agent 的能力」：别的工具不来连接 MCP，Codex 把自己的能力暴露成 MCP 服务——意味着你可以把 Codex 当作编辑器里某个 MCP 客户端（比如另一个 Agent）的「编码执行器」来用。Agent 之间通过标准协议互相调用，这个图景是 MCP 设计初衷的完全体，也是第一篇「执行引擎」定位的又一个证据。

三、工具太多怎么办：两条不同的路

skill 和 MCP 都是给 agent 加能力的通道，加多了都会遇到同一个问题：工具列表爆炸，模型选择困难。两边的应对又是两条路。

Claude Code 的应对是 subagent（第三篇讲过）：让子代理带着精简工具集干活，主会话的工具面不膨胀。它没有对工具列表本身做治理——v1.0.88 里所有可用工具全量进请求。

Codex 的应对是给工具做暴露面分级。tools/src/tool_executor.rs 里的 ToolExposures 是个 bitflags：

const DIRECT = 0b001;    // 直接给模型
const DEFERRED = 0b010;  // 模型按需搜索发现
const CODE_MODE = 0b100; // 只在 code-mode 编排下可见

DEFERRED 是关键的那一档：工具不进初始列表，模型通过 tool_search handler（tools/src/tool_discovery.rs）按需检索——等于给工具建了索引，用的时候查。MCP 工具同样可以标 DEFERRED（mcp_tool_exposure.rs）。第一篇提过的 code-mode（模型写 JS 编排代码批量调工具）是第三档，工具在这个模式下对代码可见而不对对话可见。

这个分叉的判断价值在于它预言了方向：当工具数量从十几个涨到上百个，「全量列表塞 prompt」必然失效，要么分面（subagent），要么做索引（tool search），要么做编排（code-mode）。Codex 三个都做了，Claude Code v1.0.88 只有第一个。重度扩展用户在两边得到的体验差异，大多能追溯到这张图。

给自己的环境估个体量的方法很简单：数一下你所有 MCP server 暴露的工具总数（每个 server 的 tools/list 长度加起来），加上内置工具数。二十个以内，随便哪家全量注入都没压力；五十个上下，Claude Code 需要靠 subagent 分流（工具少的专用 agent），Codex 的 DEFERRED 开始发挥作用；上百个，只有索引加编排撑得住。这个数不用精确，量级对了策略就对——而我见到的实际情况是，大多数个人用户停在第一档，却按第三档的焦虑在折腾配置，这中间的落差就是被工具治理的讨论吓出来的过度工程。

再往前看一步：工具治理这道题才刚开头。今天的三条路（分面、索引、编排）都是静态策略——工具的暴露方式在开发期定死。可以预见的下一步是动态暴露：根据任务实时判断哪些工具该进这一轮的列表。Codex 的 tool search 已经摸到了门边（模型主动查而不是被动收），Claude Code 的 skill 触发也是同款思想在知识维度的应用。「按需可见」会从扩展机制蔓延到工具机制，这是我会持续盯的演化线。

三点五、CC 2.x 的验证过程：给闭源产品做行为勘察的方法

这篇的 Claude Code skill 部分依赖 2.x，我的验证过程值得单独交代——它是「闭源产品也能做机制验证」的一个可复制流程。

第一步是二进制字符串勘察：对 claude.exe 做 grep -a，锚点选机制关键词。结果一次命中一整组：SKILL.md（frontmatter 载体）、loadSkills（加载函数名）、available-skills（目录机制的命名空间）、skill_name（调用参数）、progressive（渐进披露）、invocation（触发机制）。这组词不是散落的——它们在语义上互相咬合（有加载、有目录、有触发、有披露层级），拼起来就是一套完整 skill 系统的骨架。字符串的成组出现比单个出现可信得多，这是反误报的关键。

第二步是和官方文档对齐：官方对 skill 的描述（目录发现、渐进披露、按需加载 references）和二进制里这组字符串一一对应。两边独立来源指向同一套机制，结论升级为「高置信」。

第三步是留边界：机制的细节（比如隐式触发的判断逻辑在 2.x 里长什么样）拿不到行号级证据，所以文中所有涉及 2.x 内部实现的表述都标注「二进制勘察 + 官方口径」，和 v1.0.88 的行号级确证明确区分。证据分级不是学究气，是对读者的诚实——读的人应该知道哪句可以拿来当依据，哪句只能当参考。

这套流程对任何闭源工具的机制分析都适用：锚点选机制关键词、看成组出现、和公开口径交叉、置信度分层表述。比起「听说 2.x 有 skill」就往下写，这一小时的勘察换来的是整节的证据底气。

四、装载策略：源码读法换来的配置建议

把这些机制翻译成使用建议，我给四条。

**Skill 要为触发而写，不是为完整而写。**三道闸里你唯一能优化的是描述：frontmatter 的 description 要写「什么场景该想起我」，别写「我是什么」。写场景的 skill 过选择层的概率远高于写功能的——这是机制推出来的，不是玄学。

具体到写法，我的模板是三段式：场景（「当代码审查发现重复模式需要重构时」）、动作（「提供分步骤的重构流程和安全检查点」）、边界（「不适用于跨文件的大型架构调整」）。三段各占一句，总长控制在三行以内——选择层拿它做匹配，写得越长匹配信号越稀。这个模板的出处是我自己的 A/B：同一个 skill，功能型描述（「代码重构工具」）一周触发零次，场景型描述三天触发四次。样本不大，方向够明确。

**MCP 按使用频率分配到两边。**天天用的核心 server 放 Claude Code（全连，永远在线）；偶尔用的一次性工具放 Codex 或者干脆用完就关（懒连接，不用不付钱）。反过来配置就是双倍浪费：高频工具吃连接延迟，低频工具吃常驻上下文。

一个判断「该不该常驻」的粗算法：过去两周用过几次？三次以上常驻，一到两次按需，零次删掉或归档。「零次也留着吧万一用到」是装载膨胀的起点——skill 目录里的每个条目都在稀释其他条目的触发概率（候选名单变长，单个被选中的先验变低），MCP 列表里的每个 server 都在吃启动和上下文。装东西的成本从来不是零，只是支付方式隐蔽——它从触发概率和请求延迟里一点点扣，不开发票，所以总觉得免费。

**mcp__ 前缀是个可利用的信号。**排查「工具为什么没被用」时，看模型输出里有没有 mention 这个前缀——有 mention 没执行是连接或权限问题，没 mention 是模型压根没想起来（选择层没过）。这个二分法能省掉一半的瞎调。

顺着这个信号再给一个进阶技巧：把 mcp__ 当调试上下文用。模型在 reasoning 里提到某个 MCP 工具的名字（哪怕没带前缀），说明工具描述被看见了、进入了它的考虑集；连提都不提，才是真正的「不可见」。所以排查分三档：没进考虑集（描述问题或根本没注入）、进了考虑集没调用（匹配度问题）、调了没成（连接或权限问题）。三档对应三组完全不同的修法，先分档再动手，是这类调试的纪律。这套分档法在我这里固化成了检查的固定顺序，平均十分钟内能定位八成的「工具没被用」类问题——剩下两成才是真 bug。

**skill 和 MCP 装载要克制。**skill 目录互相稀释触发（候选越多，单个被选中的概率越低），MCP 挤占启动和上下文。我的纪律是 skill 常驻不超过十个、MCP 常驻不超过五个，剩下的按项目临时挂。这个数字不是源码给的，是机制推的：装载成本是全局的，收益是场景的，场景不够密就别常驻。

四点五、一张扩展机制全景对照

把这篇和全系列的扩展相关证据收成一张表，两个产品的扩展版图一目了然：

扩展通道Claude Code（v1.0.88 / 2.x）Codex 2026-08
知识注入skill（2.x 引入，渐进披露）skills crate（SKILL.md + @mention）
工具接入MCP（全连，mcp__ 前缀注入）MCP（懒连接 + prewarm，可 DEFERRED）
行为定制hooks（九事件，可改写权限）hooks crate + plugin crate
子代理agent 定义文件（五级合并）角色系统 + spawn 参数覆盖
编排无（靠 subagent 组合）code-mode（模型写 JS 编排）
反向暴露无（cli.js 只导出 setup）mcp-server crate（Codex 即服务）

这张表的看点不是功能多少，是扩展通道的哲学：Claude Code 的四个通道全部围绕「让这一次会话更聪明」；Codex 的六个通道里有三个在服务「让它被别的系统使用」。又是那个从第一篇贯穿到最后的分野——个人工具和平台引擎，连扩展机制的取向都不例外。

还有一行值得单独点：「编排」是 Codex 独有的维度。code-mode 让模型写代码来编排工具调用（第六篇第一节的 ToolExposures 第三档），这在扩展谱系上是最激进的一格——用户可以教会 agent「用新的方式组织已有的能力」，而不只是「新增能力」。Claude Code 的用户想要类似效果，只能在外层套脚本，那已经是离开产品自己造编排了。

五、系列收官：六篇串成的一句话

从架构分层到 skill 与 MCP 加载，六篇看完，两个引擎的差异可以收敛回第一篇那句话：Claude Code 把一个 Agent 引擎打磨到极致紧凑，Codex 在把 Agent 引擎长成一个操作系统。主循环的 generator 递归对 step loop，subagent 的函数再入对线程调度，压缩的两级火箭对双路摘要，权限的模式加 hooks 对审批加沙箱，扩展的全量装载对按需索引——每个局部差异都是顶层路线的具体化，没有一处是偶然的。

对我自己的使用，这套源码阅读换来的最大改变是「配置有了依据」：什么时候宽模式什么时候沙箱、skill 描述往哪个方向改、MCP 装在哪边、长任务交给谁——每个决定背后都有一行代码或一组二进制字符串指着。扩展机制这篇的增量收获还有一层：装载清单本身成了被管理的对象。以前我的 skill 和 MCP 是「想到就装、装了就忘」，现在它们像依赖清单一样有定期 review——每个月一次，照着「两周使用频率」的粗算法过一遍，该删的删、该归档的归档。工具的扩展面是被精心设计过的，别让你的使用方式浪费这份设计。工具会用是熟练，知道它为什么这样用是专业，这六篇是我从前者往后者走的记录。如果读者只打算从全系列带走一个习惯，我推荐这个：装任何扩展之前，先去它的文档里找「什么时候不会生效」那一节——找不到这节的产品文档不值得信，找到了就认真读。装载的克制和触发的理解，是扩展机制给使用者的两道考题，源码只提供答案的形状，作答永远在使用侧。

证据边界最后重申：Codex 侧全部基于 commit 63b268c81b 的源码；Claude Code 侧 v1.0.88 行号级确证加 2.1.229 二进制字符串勘察加官方口径，文中逐处标注。两个项目都在快速迭代，读到的机制会过时，但两条工程路线的差异——单体紧凑对平台化索引——在可见的时间里还会继续塑造这两个产品。第 7 篇（事件协议与会话持久化）视素材情况可能补上，系列主线到此完整。
