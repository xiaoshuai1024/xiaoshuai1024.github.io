Flask 作者谈 Pi 爆火：限制 Agent 的不是 AI，是系统架构

Pi 火了之后，中文圈的解读大多停在第一层：只给模型一个 bash，上下文干净，省钱，所以赢了 Claude Code。2026-09-01，Flask 作者 Armin Ronacher 上了一期近两小时的播客访谈，把话题引向了别处。他是当事方，他所在的 Earendil 刚收购了 Pi 和它的作者 Mario Zechner。但整场访谈讲得最多的，是模型之外的事：Agent 真正卡住的地方，是三个做了几十年的老工程问题。其中一堵墙里有这么个故事，一家公司的 Agent 干了几周活，用户才发现自己的 Postgres 从来没跑起来过。

这场访谈我印象最深的一个判断：强模型这一层，换壳已经不是杠杆了。伯克利 HarnessTax 做过 21 组实测，同一个模型换不同的壳，任务成功率只动 1 个百分点上下，换到终端操作基准差异放大到 ±5%，账单则差出 2 到 5 倍，完整数据我在《你的 Claude 不一定需要 Claude Code》里分析过。注意这组基准没测的东西：不查库、不配界面、跑在现成的测试容器里。Agent 卡住的恰好是这些，3 堵墙，数据操作、界面与问责、运行环境，一堵都不需要等 AI 突破。

极简是表象，能自己长才是赢面

Pi 全部家当是 read、write、edit、bash 四件工具，系统提示词短到一屏读完。赢的原因，Armin 的解释很直接：模型非常擅长使用计算机，bash 加管道让上下文保持自由和高效，专用工具塞多了反而稀释。他举的证据就在对家门里：Codex 找文件靠的也是 bash 跑 ripgrep，不是什么专用检索工具。

工具箱塞满的代价有实测数据：Claude Code 的 37 个工具说明书合计 154KB，每轮请求都要重发一遍，缓存命中时实付能压低不少，但前缀一变，重复部分照原价走。但 Armin 不把 Pi 的胜利归给「少」。访谈里他反复强调的是可扩展：别的 Agent 厂商在往壳里塞工具，Pi 把扩展留给用户和模型自己写，模型可以现场给自己写一个扩展装上。他把这类软件叫自扩展软件，认为 Pi 踩中的是这个平衡点。Earendil 收购 Pi，目标明说就是拉人，Mario 曾被 Gmail 缔造者 Paul Buchheit 称作「没人知道的最好的程序员」。

Pi 的机制层，极简内核怎么搭、扩展怎么写，我之前在《Pi Agent 凭什么打赢 Claude Code》里分析过，这篇不重复。往下过那三堵墙。

墙一：Agent 被锁在聊天记录里

访谈里最反直觉的一句判断：Agent 不需要记忆，需要数据操作能力。

这句话我第一遍没同意，想了想还真是。记忆是弹性的、被处理过的，进了压缩摘要就走样；Agent 干活要用的场景数据，账目、库存、用户行为，躺在数据库里，保持原始形态。一个能查库的 Agent，不需要「想起」发生过什么，它直接查。

Armin 点出的结构性限制是：Agent 被锁在聊天记录里。你交给它的数据确实持久化了，存在会话记录里，但只在那次会话里有效。想给 Agent 配一个自定义界面，每次都要把材料重新粘贴一遍。程序化取用更难，别的程序想读这段上下文，得先解析聊天记录。

我的对照来自自己的仓库。我用 Agent 跑自媒体管线半年，最早撞上的就是这堵墙，Agent 换一次会话就失忆，视频发没发、定时卡挂没挂，全靠人脑记。后来的做法就是给它数据操作：发布结果写进 link-map.json，任务预约写进 task-queue.jsonl，管线状态写进 state.json，Agent 每次开屏跑一条 make next 读台账，不靠回忆，靠查询。台账化之后体感很具体：Agent 从「聊过的事记得」变成「该知道的事知道」。

所以下次想给 Agent 加记忆层，先过一道判断：这份数据需不需要被程序查询、被核对、被别的人用。需要，就给它一个数据库，或者干脆一个 JSON 文件加一条查询命令。只有对话语料本身才配留在聊天记录里。

墙二：给 Agent 做界面，是前端工程师的老活

墙一管 Agent 怎么读到数据，这一堵管两件更老的事：数据写进去之后别出事，出了事查得到人。

给 Agent 做自定义 UI，Armin 说这就是状态管理加组件库，前端工程师熟悉得不能再熟悉的活。让 Agent 操作数据库又不把数据搞坏，事务、约束、权限，经典工程一样不少。他的原话是，限制 Agent 的是经典系统架构问题，不是 AI 突破问题。这些障碍现在才显形，因为模型刚够到「会用工具」这条线，够到之后撞上的第一批东西，全是系统没给它留的接口。

墙的后面还站着审计。访谈里有句冷话：银行不会永远 vibe coding。关键系统要能问责，人和 Agent 必须看同一个界面，谁都能检查谁干了什么。他预测 Markdown、JSON、Unix 管道会成为这一层的底座，理由朴素：人和 Agent 这两个物种都读得懂。

我的仓库是个现成样本。AGENTS.md 就是人机共用界面，8 支视频换来的死规矩写在里面，我先读，Agent 也读，出了问题回头翻同一条记录对账（这套规矩的来历见《看完我的 AGENTS.md》）。发布动作一律登记进台账，我核对和 Agent 核对走同一条命令。两条记录路径必然漂移，一条对账链只能有一个源头，共用格式的红利就在这：审计是免费的。

动手排查自己项目的时候，这张三行判别表对照着用：

症状归模型层的信号归系统层的信号
Agent 理解错需求给了完整上下文还是错给结构化数据后明显好转
干完的活没法验收换模型自评照样不可信加机器可判的门禁就稳了
会干但不敢让它干输出质量随机波动缺权限边界和审计记录

右边那一列，没有一项归模型厂商管。

墙三：假环境骗得了 Agent，几周才发现

第三堵墙是运行环境。Armin 讲了一个 debug 案例：一家大公司的 Agent 在云端环境干活，用户跑了几周，才发现自己的 Postgres 从来没真正跑起来过，Agent 一直在一个 mock 出来的环境里自洽地干活。这个案例的教训说得直白些：Agent 说它连上了，你要有一条它骗不了你的路径去核实。

我的发布管线全在本地 Mac 上跑，但防住假环境的不是机器在自己手里，是两条纪律：发布前 probe 逐平台体检，发布后 audit 对平台侧实查，上传器日志说「发布成功」从来不算数，这规矩是事故换来的。Armin 的版本更松弛：摩擦更少、成功率更高的路径，是自己控制的机器加 SSH。

他顺带给了一个选型风向：Linux 会复兴，因为训练数据最多；Rust、NixOS、Kafka 这些出了名难伺候的技术会更流行，因为它们的复杂度对 Agent 不构成同等负担。技术选型的标尺从来是「团队学不学得动」，现在多了一格：「Agent 用不用得顺」。

企业算不出 AI 的回报

播客后半段聊企业 ROI，Armin 的判断相当冷：除了 commit 数量，看不到任何衡量 AI 回报的可靠指标。成本立刻显现，收益慢慢显现，中间的差值让公司变得更贵。做 side project 的人用 AI 的成功率，比在公司里全面铺开的高。

这个判断我在《阿里 AI 写了 85% 的代码，交付却没变快》里见过同构的证据：生码率从 5% 提到 85%，业务侧的排期感受没变化，因为写代码只占需求全程的两成。个人和公司的差距也好解释，不是墙的有无，是修墙的速度：我给自己仓库加台账当天就上线了，同样一次改动在公司里要走评审、排期、安全评估，模型等多久，墙就立多久。

三堵墙，没有一堵要等 AI

回到开头那张图：换壳撬不动的那部分差距，立在系统层。

这三堵墙值钱的地方在它们的年纪。数据操作是数据库工程，界面与问责是前端加审计的老手艺，运行环境是运维的分内事。谁在做 Agent 系统，预算的下一笔与其押在等一个更强的模型上，不如先花在给现有模型留操作面上：一个能查的接口，一份人和 Agent 共读的格式，一台自己控制的机器。模型的天花板归厂商，这三堵墙归你。

Pi 用四件工具证明了模型的下限早就够高，Armin 用整场访谈把剩下的差距指回了工程。墙是旧的，解法也是旧的，新的只是这回轮到 Agent 来撞它。
