MCP拖慢会话，skill按需付费：渐进式披露怎么帮Claude Code省上下文

装了十几个 skill，模型却一次都不主动用？MCP 越装越多，会话越开越慢，token 消耗怎么压都压不下来？先别急着卸载插件，这两个毛病多半同源。

我在 Claude Code 里装了 30 个 skill。每次启动新会话，这 30 个 skill 的正文一行都不会进入模型的上下文，真正进来的只有 30 行介绍，每个 skill 一行，内容是名字加描述。第一反应是安装出了问题，直到把加载源码翻完，我才确认这不是缺陷，是官方文档里写明的设计，名字叫渐进式披露（progressive disclosure）。

skill 为什么沉睡、MCP 为什么拖慢会话、写 skill 时描述到底该写给谁看，这篇统一回答。文中引用的源码结论来自之前对 Claude Code 与 Codex 加载机制的源码对比，那篇有行号级证据，这篇负责把原理讲成人人能用的大白话。

先看这张总览图，全文都围绕它展开：

一、三层加载：每层只在需要时出场

一个 skill 就是磁盘上的一个目录：必备一份 SKILL.md，头部是 YAML 元数据，关键字段 name 和 description，正文写操作指引；可以再放 references/ 存详细资料、scripts/ 放脚本。关键在于这三部分进入模型视野的时机完全不同。

元数据（名字加描述）会话启动时就进入上下文，全程常驻；SKILL.md 正文只在模型判断当前任务需要时才被读取。

references/ 和 scripts/ 更靠后，连正文都只提一句，模型按指引在真正用到时才去读。「渐进式」和「披露」两个词都用得准确：信息都在磁盘上，分批出示，什么时候出示、出示给谁，机制说了算。

三层的 token 量级差得很远。元数据层每个 skill 几十 token，30 个 skill 合计千把 token，这是一次会话的固定开销；正文层单份一两千 token，但只为真正触发的技能付费，一次会话通常只触发两三个；附件层不预先加载，读到哪个算哪个。

对比一下全量注入：30 份正文全部塞进上下文，按单份 1500 到 2500 token 估算，常驻开销冲到 6 万 token，渐进式把它压到千把，只剩百分之二上下。Claude Code 2.1.229 的二进制里能找到 progressive、loadSkills、available-skills 这组字符串，与官方口径互相印证。

内容该写进哪一层，跟着加载时机走：让模型决定「要不要调我」的信息放进描述，只有描述常驻，场景词放这里才参与匹配；每次触发必走的流程主干放进正文；参考表、命令清单、长代码模板这类分支性细节拆进附件，正文留一句指引。放错层的信号也很直接：正文大部分内容只在少数情况下用得上，那就是该拆附件的形状。

二、注意力比 token 更贵：全量注入的两个代价

第一个原因是钱和延迟。常驻内容意味着每一轮请求重复付费，固定开销每多一千 token，乘上几十轮对话就是肉眼可见的差额。延迟同理，MCP 是最典型的对照：10 个 server 的工具描述全量注册后，每个请求额外驮几千 token，首 token 延迟明显上涨，清理不用的 server 立竿见影，这个结论我在源码对比里实测过。

第二个原因是注意力稀释，这一层很少有文章讲。模型的注意力不是无限细分的资源，塞进上下文的内容越多，摊在每一段上的注意力越薄。30 份正文全部常驻，等于让模型背着装满资料的背包走路，真正相关的那份反而可能被淹在另外 29 份里。渐进式披露同时是一种注意力管理：平时只给一份目录，被点名的正文才入场，入场时周围是干净的，没有 29 个同伴抢戏。开头那两个提问的病根在这里：skill 沉睡是匹配问题（下一节讲），会话变慢是常驻开销问题。

给超线的会话减负只要三步：清点 MCP server，一个月没调用的直接移除；给 skill 描述瘦身，只留场景句；把超千 token 的正文拆进 references/。渐进式披露并非唯一正确解，skill 只有三五个且正文短时，全量注入反而省掉触发的不确定性；数量上几十个、单份上千 token，它的优势才会拉开。

三、触发机制：描述是写给模型看的检索键

模型对 skill 的调用决策依据全在元数据层，具体说，全在那句 description 里。启动后模型手里只有一份技能目录，每轮对话拿当前任务跟目录里的描述做匹配。Codex 的源码把这一步拆成两道闸：selection 闸挑出与任务相关的候选，invocation 闸决定本次是否真的注入，函数名 maybe_emit_implicit_skill_invocation 里那个 maybe 说明每次都在重新评估，没有一次是必然触发。

推论很直接：description 不是功能介绍，是检索键，读者是模型不是人。我栽过跟头：一个格式转换的 skill，描述写「支持多种文档格式互相转换，快速高效」，从此再没被触发过；改成「当用户要求在 Markdown、PDF、Word 之间转换文档时使用」，触发恢复正常。前者是说明书语言，后者给了模型可以匹配上的场景信号。

描述的失败模式集中在三种：写成用法手册，全是步骤没有场景；写得太泛，「辅助日常开发」跟什么都能沾边也就什么都不匹配；多个 skill 描述互相重叠，模型挑中谁看运气，那要靠合并或划清边界来解。实操口径三条：场景词前置；用用户会真说出口的词；控制在一两句，描述是常驻开销，30 个 skill 堆起来并不小。

显式触发是留给用户的保险丝：怀疑没生效，直接 @ 它的名字，这条路径绕过匹配直通触发。@ 了能用，问题在描述匹配；@ 了也没反应，才去查安装和格式。

四、排坑五查：skill 沉睡的定位清单

skill 沉睡的原因按加载顺序归类只有五处，从磁盘到模型逐层排查，10 分钟内基本能定位。建议收藏，出问题按层走。

一查发现层：skill 是否在会被扫描的目录里（用户级、项目级、插件级三个位置），文件名必须是 SKILL.md，大小写敏感。

二查解析层：frontmatter 能否被 YAML 解析，name 和 description 字段在不在。新会话问一句现在有哪些技能可用，报不出名字就是前两关的问题；老版本 Claude Code 没有这套机制，先确认版本。

三查匹配层：描述里有没有当前场景的触发词，用词贴不贴近你实际下达任务的措辞。改写后开新会话重试，这是收益最高的一处修改。

四查直通层：@ 名字做一次显式触发。能用说明问题在匹配环节，不能说明问题在更底层，避免在错误方向上反复调描述。

五查分工层：这个需求该不该做成 skill。有些「不触发」的根源是选型错了，动作调用类需求技能自然接不住，见下一节。

我有个发布检查类的 skill 装完两周没触发，走完前四查发现是描述只写了「检查文章质量」，改成「文章定稿准备发布时使用，逐项核对配图、链接与格式」，触发恢复，全程没动一行代码。这张清单和自己动手写 skill的六步流程配合用，写完自检一遍能提前排掉大半问题。

五、skill 与 MCP 的分工：动作注册和知识调取

MCP 是工具注册：server 一连上，每个工具的完整描述（含参数结构）全量进入上下文全程常驻，模型每轮都看得见、直接调用，适合外部世界的接口，查数据库、发消息、读文件系统这类动作明确参数固定的事。skill 是知识调取：常驻的只有一句描述，正文讲「做这类事情的流程和注意事项」，触发时才入场，适合程序性知识，多步骤、细节量大、特定场景才需要。

需求特征合适的形态
每轮都可能调用的外部动作（查库、发消息、读文件）MCP 工具
需要参数化调用的外部系统接口MCP 工具
特定场景才需要的多步骤流程知识skill
团队规范、写作与检查方法论skill
三五行就能说清的小技巧直接写进项目说明，两者都不用

开销上一算就清楚：5 个工具的 MCP server，常驻开销几千 token 起且不随使用变化；一个 skill 常驻只有几十 token 的描述，正文按触发付费。把低频知识做成工具是让它全天候占座，把高频动作做成技能是每次调用绕一道匹配，两种错法方向相反、浪费相同。反模式就两个：skill 当网盘用，正文几千行，渐进式被自己废掉；MCP 装一个留一个，每个请求都在为不用的工具付费。

收在思想处：上下文稀缺时代的通用设计

这篇的结论可以压成一个判断：渐进式披露用「先报名字、按需展开」把上下文从全量摊开改成按需调取，省下的既是 token，也是模型有限的注意力。往深里看，RAG 只把查询命中的片段召回上下文，agent 记忆把历史压成摘要按需取用，和 skill 的三层加载同族：上下文是模型时代最贵的资源，任何常驻内容都要证明自己值得那个位置。
