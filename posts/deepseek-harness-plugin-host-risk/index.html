装个插件就能干掉宿主？DeepSeek Harness 的信任边界现状

对 dsh 插件市场做安全扫描的人，扫出一个尴尬结果：排在 critical 榜首的插件，本职工作是安全评估。dsh-cyber-sec，自己身上挂着 11 个 critical 发现。

这篇不复述惊吓，只拆两件事：装进来的插件实际拿到多大的执行面，以及这条边界现在由谁守。答案可以先放在这里：契约有、隔离无，剩下的环节靠人。

一、官方自己的示例，也只敢用受限模式跑 bash

判断一个框架的野心和它的克制程度，看官方示例就够了。dsh 面向开发者的示例代码里，执行类工具自始至终只有一个 bash，而且开工前要先想清楚把哪些能力放进受限模式。沙箱那篇拆过这套默认组合的设计动机：发播方自己都不敢默认裸奔，说明执行面的危险性在项目内部是有共识的。

这里先把 bash 工具的处境立起来当参照物：它每执行一步，身边都跟着一个按次携带的策略对象，权限细到每一次调用。记住这个刻度，下一节你会看到插件这条路拿到的待遇，跟它完全不在一个量级。

二、插件的执行面究竟有多大

外部公开分析已经把结论说破：SSD Nodes 中文页对 dsh 插件机制的梳理口径里，插件以 agent 权限运行第三方代码，且没有进程隔离。这两半句分别是能力和权限维度的事实，拼在一起才算完整：插件能做 agent 能做的一切，并且和宿主共用同一个操作系统身份。

把「agent 权限」翻译成日常动作，awesome 目录在自己的声明里给过对照：dsh 插件可以读写你的文件、跑命令、连网络。文件、进程、网络，这三样正好是操作系统权限的主干；那句「没有进程隔离」落到桌面上，指的就是它们全部敞开。

ctx.dynamicCordisRunner   # Dynamic Cordis package host runner
cordis-host-runner        # 宿主侧：承载包的动态装载
cordis-client-runner      # 客户端侧：连接运行中的容器

源码证据同样是明牌。插件树由 ctx.dynamicCordisRunner 这条接缝承载包的动态装载，仓库的 docs/capability-seams.zh.md 里明确列出了 cordis-host-runner 与 cordis-client-runner 两端 runner 包。动态装一条包进来不需要越过任何特权检查点，同机同权执行属于设计内行为，原理见接缝架构那篇。

同机同权四个字在桌面环境的含义，也值得停一下细想：你的下载目录、剪贴板、浏览器会话、云盘客户端的凭据缓存，全在这一权的射程之内。第一节里 bash 每走一步都有策略对象跟着，而这条路径上第三方代码拿到的，是一张没有策略对象的完整通行证。

而且这条装载路径是 API 化的，不是运维动作。扩展子系统的文档里，define() 接口接收会话归属、插件元数据与源码本身，由宿主铸造插件和包的身份；run() 按不可变的包版本激活一次运行。整条流程能在模型自己的会话里发起，第三方代码进你的机器，从「管理员敲了一条命令」降格为「一次方法调用」。

设计者当然权衡过：把动态性给足，灵活性的上限才高。但工程上的等价换算是，每个插件的作者都拿到了和你本人几乎相同的机器权限。

三、契约上能声明什么，批准之后又覆盖了什么

权限给到这个程度，契约层总该留下可核对的凭据。通读扩展子系统的接口文档，声明和检查的能力确实设计过，只是各自的覆盖范围值得逐条看清。

先看审批的门。client 半区的包在未授权状态下要等用户点头才拿得到运行许可，这条路是真实存在的。但审批条款里有一句写得非常坦率：plugin 级的授权自动覆盖同一插件后续的版本。也就是说你批准的对象是一个身份，内容却可以流动——上游仓库发一个新版本，新包默认继承你当初批出去的那份信任，不需要你再确认一次。

再看收敛侧的工具族。inspect 接口被刻意设计成 source-free：inventory 返回每个插件的元数据行，snapshot 展示活跃运行和宿主 fiber，注释里反复注明不给源码；真要看代码得走显式的 inspectPackage，还要持有一个精确的运行身份才能调。停用一侧分了两档，stop 只停当前运行、保留全部历史版本，undefine 连同活动运行和所有不可变包一起移除。每一次激活和撤回还有专门的动态包事件广播出来做审计线索。

用户面板一侧的接口也有个容易被忽略的细节：从设置里移除一个插件时，这次状态变化会被编排进模型下一轮可见的上下文。连「卸载了什么」都会成为模型知道的事实，管理动作本身进入了信息流。

这套组合说明官方对动态性的风险并非无感，该有的声明字段和核对工具都在。只是审批守的是激活请求那一个时点，通过之后的执行面，就是上一节描绘的那个样子；守门的精度和不设防的广度之间的差值，正是后面几节数字的来源。

四、1309 个插件扫出来什么

GitHub Discussion #1770 里有人替整个市场做了轮体检：1309 个插件，60% 没有严重的静态发现，15 个被标记为 critical。单看这两个比例，结论似乎是好消息，六成插件静态干净，出问题的只是少数。

讽刺藏在 critical 清单内部：得分最高的正是开头那个 dsh-cyber-sec，自己做安全评估的产品，自己背着 11 个 critical。生态整体健康与单个插件高风险，在这份报告里同时成立，前者的存在不能替后者作保。

数字还可以再往下读一层。15 个 critical 里 11 个出自同一个插件，高危呈明显的聚堆分布。聚堆对个人的含义很直接：市场层面的干净比例推不到任何一台具体的机器上，真正构成风险的只有你亲手装进来的那几个，这个判断不随大盘变好而自动松动。

更麻烦的在于区分成本：普通用户没法凭名字、star 数或简介挑出那 15 分之几，静态扫描的结论也对动态行为无能为力。这正是第四节数字之后，第五节还要继续往下数洞的原因。

五、已经写进公开记录的四个洞

已披露材料的清单相当具体：配置解析路径上的 !!js 标签会触发任意求值；read-only 沙箱档位名义上只读，实际上进程仍可全盘读取；动态插件的 vm 沙箱存在 exec 逃逸；这几点连同一条完整的链式利用路径，腾讯新闻等多个渠道都做过实录整理。

沙箱篇末尾提到的 v0.1.1-rc.1 修复，bwrap 的 /proc/<pid>/root 逃逸，属于本体侧收紧的例证。本体和生态要分开看：前者每一次逃逸都会在被发现后焊死，后者连发现机制都还在讨论怎么建。

四个洞没有一个出自想象，全部有编号、有复现、有修复或披露记录。它们共同指向的问题只有一个：执行面太大，而隔板太少。

六、read-only 档的名字承诺得多，做到的少

四个洞里第二个值得单独立一节，因为它顶着最有安全感的名字。先摆设计本意：沙箱篇里写过，read-only 档的定义是只许读加少量临时区写入，策略按次携带，每次调用各自签订，三种档位里它是约束意图最重的一档。名字取到这个份上，用户的预期自然照着字面走。

披露出来的事实则是反方向的：名义上只读，实际进程仍可全盘读取。两条已知陈述放到一起，落差就具体了：这一档真正管住的只有写入面，读取面没有被拦住。名字许诺的是「这台机器我不动」，实际交付的是「我不留下改动」，中间差着一整个读取半径。

落到使用场景，这个落差不抽象。SSH 私钥、环境变量文件里的 key、浏览器的登录态存储，全都躺在一台机器的常规可读范围内。选 read-only 的人是想让进程远离这些区域，而这个档位的读取视野从头到尾就是整块盘。档位的字面含义和实现覆盖面对不上时，照着名字理解权限的人最先被这份落差伤到。

再对照第一节立起来的刻度看，这道落差更有分量。本体侧沙箱的哲学是拦不住就不跑，宁可任务失败也不撤防线；read-only 这个洞正好出在名字先行的乐观上：档位按意图命名，实现只兑现了一半。fail-closed 的反面教材藏在语义与实现的缝隙里，没有出现在任何一行失败分支的代码中。

七、护栏在建，你手里还能有一套装机审查流程

制度化尝试已经出现：GitHub #2269 号提案建议给插件市场与安装流程引入 STANDARD.md 安全规则，要求上架插件提交标准化的安全声明。提案仍停留在讨论阶段，方向有了，距离成体系还远。

提案生效之前，操作位在你自己手里。标准化声明还没影子的阶段，普通用户能拿到的审查材料只剩两样：插件自己的 README 和源码本体。我把 top10 实测那篇用过的选型纪律并进来，把两样材料排成一个固定顺序，压成一份装机前走得完的流程：

  1. 选型先过四刀：star 个位数的不碰，爆发期里 star 就是社区的预筛；最近一次 push 不在今天附近的不要，跟进 rc 的速度就是生存意愿；README 首屏没写适配哪个 rc 的跳过；说不清自己解决什么痛点的直接排除，整活作品再多 star 也不是生产力；
  2. 决定装之前读源码，重点看初始化和网络请求逻辑，十行以内的小插件两分钟就能看完 apply 里干了什么；大仓库读不动源码就退一步看 star 增长曲线和 issue 区有没有人回应，活跃社区预先消化过一部分坑；
  3. 敏感任务的 profile 少装杂件，宁可手动复制几段内容也别攒一堆低频插件；试试心里没底的新东西之前，先把 profile 目录拷一份当快照；
  4. 升级跟上 rc 修补节奏，逃逸类修复密集出现在近期版本里，装完记得核一遍生效清单。

第二条的具体验证手法，插件挂载那篇的「验证：说不算就不算」一节可以直接当操作手册用：dump-config 和设置页两条路，都能核对你这台机器上实际生效的插件清单。

这套流程单次成本不到十五分钟，换来的东西却很具体：在官方护栏上岗之前，你对装进来的每一个插件至少亲眼看过一遍它要什么权限、往哪里发起连接。审查做不到替你担保任何一个插件，它做到的是把「我装了这些」从一句模糊的印象，变成一份写得出行、记得起来源的清单。

八、边界的现状，以及买到灵活性时付了什么

现状可以压成几个短句：契约有，隔离无，护栏在投票中。「一切皆插件」是 dsh 架构最锋利的卖点，改装自由度直接拉满；价格则写在本文第二到五节里，执行面、扫描报告和漏洞清单，都是这张价签的背面。

最终付钱的是用户。隔离与评级制度进场之前，供应链审查这份工作被交回到每一个装机的人手里，愿意花十分钟读一遍源码、核一遍清单的人，目前就是这条信任边界本身。护栏总会有的，但在它上岗之前，别把这段空窗当成安全期。
