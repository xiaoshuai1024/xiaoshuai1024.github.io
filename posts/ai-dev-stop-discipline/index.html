让 AI 写代码的人，大概率见过这三种翻车：

需求只说了一半，AI 就敢往下编，编出来的代码「看着像回事、一跑就露馅」。

方向错了，它一路错到底。你让它做 A，它从第一步就走偏，之后每一步都在给错误的方案补细节，全程不喊停。

改 bug 也是。你让它改，它就改。改完复测，旧 bug 没了，新 bug 冒出来，来回三轮，代码已经看不出原样。

遇到这种问题，多数人的第一反应是换模型、调提示词、改温度。我的做法不一样：先搞清楚翻车的根源在哪，再找对应的工具。这篇文章讲的就是我在这个过程中挖到的一个项目，它把「资深工程师为什么不会翻车」这件事，拆成了 25 个可执行的 skill。

一、翻车不怪模型，怪流程里没有「停」

先看 AI 的工作方式。它是「续写器」：接收输入，预测最合理的下一步。这个机制决定了两个天性：有输入就输出，有错误就继续。

需求含糊，它不会停下来问「你说的 A 具体指什么」，而是开写它最熟悉的那个 A。测试没过，它不会停下来承认失败，而是分析一下「可能哪里不对」，改两行继续跑。

这些行为放在人身上很好理解：没人喊停，就一直干。AI 比人更顺从，人累了会停，AI 不会。

所以问题不在模型聪明不聪明，在流程里有没有「停」这个环节。资深工程师和新手的差别就在这里：新手拿到需求就写，写错了再改；老手会先盘问需求、先写测试、先把 bug 复现出来。不是老手写得快，是老手停得准。

这个认知不新鲜，但把「停得准」变成 AI 绕不过的流程，最近有个项目做到了极致。

二、mattpocock/skills：一个 21 万 Star 的开源技能库

这个项目是 mattpocock/skills，作者 Matt Pocock，TypeScript 社区的知名教育者（Total TypeScript 作者）。他把自己日常写代码用的整套 Agent 技能库开源了，MIT 协议，GitHub 上 21 万 Star。

仓库简介一句话：Skills for Real Engineers，给真实工程师用的技能，不是 vibe coding（瞎写）用的。

先看整体结构。25 个 skill 按两大轴组织：一类是 Engineering（工程向），一类是 Productivity（通用向）；按触发方式又分两种，用户主动敲的（/grill-me）和模型自动触发的（/tdd）。

安装简单到不像一个 21 万 Star 的项目：

# Claude Code（官方插件市场，自动更新）
claude plugins install mattpocock-skills

# Codex 和其他 Agent（可编辑版本，装进项目）
npx skills@latest add mattpocock/skills

装完跑一次 /setup-matt-pocock-skills，选好 issue tracker（GitHub / Linear / 本地文件）、标签规则、文档存放位置，就绪。

项目里还有一句很有态度的话：GSD、BMAD、Spec-Kit 这些框架想通过「接管流程」帮你，但代价是拿走你的控制权，流程里的 bug 还难排查。这个项目的设计原则正好相反：skill 要小、要容易改、要可组合，任何模型都能用。

三、每个 skill，都是资深工程师的一个隐性判断

拆开看之前，先讲这个项目最核心的设计思想：它把资深工程师的隐性判断，固化成可执行的流程。

「隐性判断」是什么？就是老手干活时自己都没意识到的那些决定。举个例子，你让一个老手「加个积分功能」，他不会马上写代码。他心里会过一遍：积分从哪来、退款扣不扣、抵扣比例多少、明细在哪展示。这些不是他记性好，是长期踩坑形成的肌肉记忆。

AI 没有这种肌肉记忆，但你可以把肌肉记忆写成流程。这个项目就是这么干的：每一个 skill，对应一个资深工程师的隐性判断。

举几组例子：

  • /grill-me、/grill-with-docs：反复盘问需求、把模糊术语钉成 glossary、把难逆权衡写进 ADR。对应老手开工前盘问 PM 的动作。
  • /wayfinder、/to-spec、/to-tickets：巨型项目先变决策地图，再压成规格，最后按端到端最小切片排序。对应老手「先想清楚再做」的规划能力。
  • /tdd、/diagnosing-bugs：先建会变红的反馈环，再让实现或根因修复把它变绿。对应「先写会失败的测试」的肌肉记忆。
  • /code-review：同时追问「写得合格吗」和「是不是当初要的」，不让两种判断互相遮蔽。对应老手 review 时的双重视角。
  • /improve-codebase-architecture、/codebase-design：先盘出值得治理的架构账，再为选中模块设计更深的 interface。对应「这里该藏起来」的直觉。

这个「隐性判断 → 流程」的映射，是整个项目的方法论核心。理解了这个，再看它组织流程的方式。

四、SDLC 决策路由：从想法到上线，六关怎么过

25 个 skill 不是堆在一起的工具列表，它们按软件开发生命周期（SDLC）组织成一条决策路由。官方 README 里给了一条主线：idea → ship。

第一关：需求、设计、规划起点

从模糊想法到可执行蓝图，项目拆了三步：

需求澄清用 /grill-with-docs（有仓库时，把共识写进 CONTEXT.md）或 /grill-me（无仓库时，纯访谈）。核心机制在底层的 /grilling skill 里：把计划画成设计树，每轮只问「前提已满足」的那批问题（frontier），带着推荐答案问，等回答再展开下一轮。直到树的每个分支都访问过、没有静默假设，才算共识达成。

这个机制里有两个细节很关键。一是每个问题都要带推荐答案。AI 不能只问「积分从哪来？」，要问「积分从哪来？我的推荐是下单按 1:1 送，你同意吗」。带推荐答案的问题，回答成本低，对方更容易给确定答复，而不是又抛回来一句「你觉得呢」。二是找事实是 AI 的活，不是用户的活。frontier 里需要查环境（文件系统、工具）的事实，AI 派子 agent 去找，不拿「你帮我看下 X 文件」来烦用户。决策归用户，事实归 AI，分工明确。

这一关最常见的坑：拿到模糊想法直接开写，需求没收敛就编码。返工的大头都死在这。

架构设计用 /codebase-design（模块形状、接口、seam、depth）和 /improve-codebase-architecture（扫描深化机会）。它管的是「接口别设计成宽而浅，什么都暴露，无法测试演进」。

巨型模糊项目用 /wayfinder：想法大到装不进一个会话时，先在 issue tracker 上建一张「决策票地图」，一张一张解决，直到通往目的地的路变清晰。坑是「一上来就拆任务，结果方向都没定，任务白拆」。

共享语言：CONTEXT.md 的价值

盘问收敛会写下一个 CONTEXT.md，这是整个项目里被作者称为「最酷的技巧」的东西。它解决的问题是：AI 初进项目，用词和项目实际术语对不上。

作者给了一个很有说服力的对比。同样是描述一个问题：

  • 改之前：「课程里一个 lesson 在 section 里被标记为 real（即在文件系统里有了位置）时，会有问题」
  • 改之后：「materialization cascade 有问题」

前者二十多个字，后者五个词。差别在于共享语言：CONTEXT.md 里定义了项目术语（materialization cascade 就是「课程内容实体化时的级联」），AI 读到后，变量命名、函数命名、文件组织全用这套语言，对话里再也不用反复解释。

好处不止省 token。术语统一后，代码库对 AI 来说更好导航，AI 思考时也更省，不用每次把二十个字的描述在心里翻译一遍。这个机制藏在 /grill-with-docs 里：盘问的同时建共享语言、把难逆决策记进 ADR，一石三鸟。

第二关：规格、测试先行

共识必须在脑子里待不住，要落盘。

/to-spec 把当前对话综合成规格，直接发到 issue tracker（不做访谈，只做总结）。/to-tickets 把规格拆成纵向 tracer-bullet 切片，每张票声明自己的阻塞边。纵向切片的意思是：先做一个端到端能跑通的最小切片（比如一个页面全链路），而不是横切片（先做完所有 DB、再做完所有 API）。横切片没法增量验证。

「阻塞边」是拆票时的核心概念：每张票明确声明它依赖哪些前置条件，依赖没就绪的票不会先开工。这和任务拆分的直觉相反——多数人习惯把「相似的工作」归到一起（所有数据库改动一批），但那样的话，第一批做完没有任何可验证的产出。按纵向切片 + 阻塞边拆票，每完成一张票，系统就多一条能跑的链路，进度是可见的。

然后是 /tdd：红 → 绿 → 重构，一次一个切片。这个 skill 写得非常细，后面单独讲。

第三关：实现、审查、根因定位

/implement 负责执行：每个 ticket 开独立会话，内部跑 /tdd，收尾跑 /code-review，每票之间 /clear 清上下文。坑是「一个会话又规划又实现又 review，上下文炸了，质量滑坡」。

/code-review 是双轴 review：Standards（代码是否符合仓库规范 + Fowler 坏味道基线）和 Spec（是否忠实实现了来源 issue 的本意），两条轴并行跑，互相不污染。坑是「review 只看风格，不看是否实现了 spec 的本意」。

/diagnosing-bugs 管调试：先建稳定复现的红灯，再最小化 → 假设 → 修复 → 回归测试。坑是「凭直觉瞎猜改，没复现就动手，改 A 坏 B」。

第四关：冲突、重构、领域建模

这三块管的是「代码库三年后还能不能维护」。

/resolving-merge-conflicts：逐 hunk 追溯双方意图，绝不 --abort。坑是「逐行 --ours/--theirs 二选一，丢失双方意图，埋雷」。

/improve-codebase-architecture：扫描代码库，列出「该治理的账」，挑一个进主干。注意它的定位：扫描不是救援。真正老旧的代码库它会找出真实候选，但不会替你解开泥球。

/domain-modeling：挑战术语、消歧、把难逆决策记进 ADR。「account」一个词干三件事，就是沟通灾难的开始。

第五关：试探、交接、传承

/prototype：一次性代码回答一个设计问题（UI 状态机用几个差异化的 HTML 变体，状态/逻辑问题用单文件），试探完折叠进真代码。坑是「在纸上争 UI 长什么样，争不动」。

/handoff：把当前会话压成可移植的 markdown，交给新会话或同事。坑是「上下文要爆了，又不想丢前面所有思考」。

/wizard：生成交互式 bash 向导，带人配密钥、跑控制台。这些是只有人能做的步骤。

/writing-for-agents、/wait-what、/teach：写给 Agent 读的文档、没听懂时的重新解释、跨多会话教学。

主干：一条线串起来

六关不是平的，官方给了一条主流水线：

idea → /grill-with-docs 盘问收敛（写下 CONTEXT.md）
     → /to-spec + /to-tickets 落盘规格（到这可以 /clear）
     → 循环：/implement + /tdd + /code-review，每票独立会话
     → ship

三个入口匝道汇入主干：/triage（外部需求堆积）、/diagnosing-bugs（东西坏了）、/wayfinder（巨大模糊项目）。不确定用哪个时，/ask-matt 替你选刀。

五、/tdd：一个值得单独拆的 skill

25 个 skill 里，/tdd 是打磨最狠的一个，值得单独看，因为它把「先写会失败的测试」这句口号写成了可执行的规则。

它的核心定义：测试只写在预先约定的 seam（接缝）上。写任何测试之前，先写下要测的 seam 并和用户确认，测试不写在未确认的 seam 上。这解决了「测试写在哪」的含糊。

三个反模式写得尤其清楚：

  • 实现耦合：mock 内部协作对象、测私有方法、走旁路验证（查数据库而不是用接口）。特征：重构时行为没变但测试碎了。
  • 同义反复：断言用代码同款方式重算期望值（expect(add(a, b)).toBe(a + b)），永远不可能和代码不一致。期望值必须来自独立来源：已知正确的字面量、手算例子、spec。
  • 横切片：先写完所有测试再写所有实现。批量测试验证的是「想象的行为」而不是用户可见行为，测的是形状不是行为。正确做法是纵向切片：一个测试 → 一个实现 → 重复，每个测试都是回应上一轮经验的 tracer bullet。

还有一条规则：重构不属于 TDD 循环，它属于 review 阶段。红绿循环里只做「让测试变绿的最小改动」。

这些规则不是 AI 生成的，是 Matt Pocock 二十年工程经验的浓缩。/tdd 之所以比「让 AI 写测试」的提示词管用，就是因为这些细节。

一条真实需求走完全程

光看流程抽象，感受不到这套东西的密度。拿「给用户加积分功能」走一遍：

第一步，你对 AI 说「想加个积分功能」，跑 /grill-with-docs。AI 按设计树开问，每问带推荐答案：「积分从哪来？推荐下单按实付金额 1:1 送」「退款时扣回吗？推荐退款成功才扣」「抵扣比例？推荐 100 积分抵 1 元，单笔上限 50%」。五轮问答，需求从一句话变成一份带决策依据的规格。同时 CONTEXT.md 更新了「积分」「抵扣」「发放时机」的术语定义。

第二步，/to-spec 把对话综合成 spec 发到 issue tracker，/to-tickets 拆成纵向切片：「积分发放 + 展示积分明细 + 抵扣下单金额」，三张票按端到端可验证排序。第一张票：「用户下单成功 → 积分入账 → 个人中心能看到」，一条链路走通。

第三步，/implement 开独立会话，内部 /tdd 红绿循环写第一张票，/code-review 双轴审查（符合仓库规范吗 + 实现的是 spec 本意吗），过审后 commit、/clear，开下一张票的会话。

第四步，全部票完成，ship。回看整个过程，每个环节都有 skill 兜着，没有一步是「凭感觉」的。

这条流程里最关键的一点，是每张票一个独立会话。一个会话又盘需求又写 spec 又实现又 review，上下文很快就会炸，质量必然滑坡。分票 + 每票 clear，是这套流水线能持续运转的关键。

七、过度工程红线：什么时候 skill 反而是累赘

这套速查表最资深的一页，是「什么时候别用 skill」。这是很多工具教程不会告诉你的部分。

  • 单文件小改、几行 bug 修复：杀鸡用牛刀，直接裸改。
  • 目标明确无歧义（如「login.ts:50 加日志」）：直接做。
  • 一次性脚本、探索实验：/prototype 都嫌重。
  • 没冲突时别预防性跑 /resolving-merge-conflicts。

判断标准一句话：动作复杂度 < skill 流程开销，直接做。

举个例子。改个按钮文案，走 /grill-with-docs + /to-tickets + /tdd 全套，光流程沟通就是改动本身的十倍工作量，没人受得了，最后大家会直接绕过 skill——流程一旦被绕过一次，就成了摆设。这套 skill 的聪明之处在于把「哪些不用走流程」也写成了规则，等于给自己留了活路。

这个红线很重要。任何流程化工具都有这个两面性：它把纪律变成可执行，也把「本来一句话的事」变成一场仪式。用对了省时间，用错了浪费时间还招人烦。这套 skill 自己把红线写进文档，说明作者清楚这个边界。

为什么需要这套 skill

把红线放一边，回到最初的问题：不用这套东西，会怎样？

对照项目 README 里列的四个常见失败模式，全是不用纪律的必然结果：

  • Agent 没做你要的事：你以为它懂了，它其实没懂，做出来完全不是那么回事。/grill-me、/grill-with-docs 治这个。
  • Agent 太啰嗦：术语各说各的，一句话能说清的事它用二十个词。共享语言治这个。
  • 代码跑不起来：没有反馈环，Agent 闭眼飞。/tdd、/diagnosing-bugs 治这个。
  • 代码库变成泥球：Agent 加速了熵增，代码复杂度以史无前例的速度膨胀。/improve-codebase-architecture、/codebase-design 治这个。

四个失败模式，每一条都是「没告诉 AI 该停」的变体：没确认就写、没测试就交付、没复现就修、没设计就堆。

八、我的判断：这套东西好在哪、缺什么

用了一段时间之后，说我的判断。

好在哪，三点。第一，它把「资深工程师的隐性判断」这个抽象概念，落成了 25 个可复现的流程，这是很多 AI 编程方法论想做没做到的。第二，设计原则正确：skill 小、可改、可组合、不锁模型，这意味着它不会像 GSD 那种框架一样把你关进笼子。第三，细节到位，/tdd 里那些反模式、/grilling 的设计树追问，是真正写过大量代码的人才能总结出来的。

缺什么，也三点。第一，它默认你有一个规范的工程环境：issue tracker、git 流程、测试基础设施。项目环境混乱的团队，装上这套 skill 也跑不起来，得先把工程基建补上。第二，学习成本不低：25 个 skill 的决策路由，头两周基本靠 /ask-matt 和速查表活着。第三，它治的是「流程」，治不了「人」。需求盘问再彻底，如果回答的人自己都没想清楚，收敛出来的也是错的。

它和「接管流程」的框架有什么不同，这个值得单独说。GSD、BMAD、Spec-Kit 这类方案的路子是：框架替你拥有整个开发流程，你按它的节奏走。代价是流程里的 bug 很难排查，框架越重，出错时越难定位是「我的问题」还是「框架的问题」。

mattpocock/skills 的路线反过来：每个 skill 都很小，只管一个动作，可以单独改、单独删、自由组合。/tdd 不喜欢，改它的 SKILL.md；/wizard 用不上，删掉，不影响其他 skill。这种「小而可组合」的设计，让这套东西能长在项目上，而不是项目长在它里面。README 里原话是「hack around with them. Make them your own」，改它、让它变成你的。

上手建议

如果你也想试，我的建议是别一次全装。安装是整包装的，但使用可以从三个 skill 开始：

  • /grill-with-docs：下一个需求就用，感受「设计树追问」和 CONTEXT.md 的威力。这是最容易见效的一个。
  • /tdd：配合现有测试基建，从一个小功能开始红绿循环。它写得很细，照着做就行。
  • /ask-matt：记不住 25 个 skill 时，让它帮你选刀，顺便熟悉路由。

三个跑熟，再往流水线深处加。一次性 25 个 skill 全上，会跟刚买了全套厨具一样，看着齐全，实际只用一个锅。

和我在项目里攒下的 skills 体系（百万行项目那篇）对比：那套是项目专属的、和我的 28 个命令绑定的；这套是通用的、拿来即用的。两者不冲突，它补上了我体系里「需求盘问」和「架构设计」这两块的深度，我补上它没有的项目定制。

九、它回答了什么

回到开头的问题：AI 翻车，翻在哪？

翻在没人告诉它什么时候该停。mattpocock/skills 做的事，就是把「该停就停」从一句感慨变成 25 个流程：需求没收敛就编码？/grill-with-docs 拦住。测试没先行就实现？/tdd 拦住。没复现就动手修？/diagnosing-bugs 拦住。上下文快炸了？/handoff 和 /clear 接住。

模型负责快，流程负责停。这个项目证明了一件事：把工程师几十年的自律写成 Agent 绕不过的流程，AI 写代码的质量就能追平资深工程师。不是模型变聪明了，是流程变严了。

这也是它值 21 万 Star 的原因。工具谁都会列，把「隐性判断」拆成「可执行流程」的本事，才是这个项目真正开源的东西。对正在用 AI 写代码的人来说，这套东西值得花一个晚上读完，第二天就装上试试，效果自己会说话。
