三天前我上手实测了 dsh，装完跑了一圈任务，看完插件生态。但实测只能回答「它好用吗」，回答不了「它为什么这样做」。这三天我把 deepseek-ai/deepseek-harness 的源码从头到尾读了一遍——80MB 的 TypeScript monorepo，133 个插件包，外加一套 vendored 的 Cordis 内核。这篇文章是完整的源码笔记，从启动流程一路讲到上下文压缩和定时调度，所有结论都带 file:line 引用，你可以拿着仓库对照看。

我的总体读后感先放这：dsh 是我读过的 Agent harness 里工程约束执行得最彻底的一个。它不是功能最多的，但每一个「容易写歪的地方」——重试、压缩、沙箱、并发、持久化——都用了同一种手法：把决策变成事件，把状态变成投影，把危险变成默认拒绝。这篇文章就是要把这个手法在六七个子系统里怎么落地的拆开看。

版本说明：分析基于我手上的 clone（根 package.json 版本 0.1.0-rc.5，实测文章用的 rc.6），行号以这份代码为准，开发者预览期重构频繁，行号可能漂移。

一、先看地形：仓库结构和那套 vendored 内核

clone 下来第一眼要看的其实是根目录的 vendor/，packages/ 反而可以后看。里面有五个目录：cordis、loader、include、hmr、timer——全部是直接拷进仓库的源码，不走 npm 依赖。

Cordis 是一个「依赖注入 + 插件生命周期」框架（koishi 生态那套思路）：核心概念是 Context（上下文）、Fiber（插件的运行时载体，一个状态机）、Service（命名服务）。插件就是一个对象：

{ name, inject, Config, apply(ctx) }

inject 声明依赖的服务名，apply 在激活时拿到 Context 挂自己的服务。Loader 负责按声明拓扑加载，服务没就绪时依赖方 fiber 停在 pending 状态，Service.check 就绪后放行。

为什么 vendor 而不是装 npm 包？我的看法：harness 对内核的稳定性要求是「每一行都要为我负责」。插件内核是整个系统的地基，升级一个第三方包带来的行为漂移，在 133 个插件的系统里排查成本极高。拷进来，锁死，自己改。这个选择本身就说明了 dsh 团队对「内核」的界定有多严格。

packages/ 下的分组也值得记一下，后面全要用到：

  • packages/boot/* —— 启动、profile、cmdline、app-boot
  • packages/core/* —— agent-loop、session、tools、system-prompt
  • packages/llm/* —— LlmRuntime、deepseek 适配器、重试
  • packages/context/* —— compaction、spill、todo、plan-mode、goal
  • packages/schedule/*、packages/jobs/* —— 定时调度和后台作业
  • packages/subagent/、packages/sandbox/、packages/skill/ —— 子代理、沙箱、技能
  • apps/cli、apps/web —— 启动器和浏览器前端
  • packages/host/* —— webserver、apiproxy

1.1 最大的特点：插件是组织单元

读完一遍再回头总结，dsh 最大的特点可以一句话说清：插件在别的工具里是扩展机制，在 dsh 里是组织代码的基本单元。

Claude Code、Codex 也有插件/扩展，但它们的内核是产品自带的，插件挂在预留的扩展点上——扩展点是「打洞」打出来的，洞的位置由厂商决定。dsh 把这个关系倒了过来：仓库里没有内核应用，只有插件和加载插件的 loader。模型接入（llm-deepseek）、会话（session）、工具执行（tools）、甚至 Web UI（web-app）全部以同等身份住在树上，官方默认栈只是「预组装好的一棵默认树」。想换模型 provider、想换沙箱实现、想把 Web UI 换成 TUI，动作是同一个：加一行补丁，插入一个插件。

这个倒置带来三个连锁后果。其一，可替换面接近 100%——实测文章里 275 个生态插件能在发布两天内长出来，技术上就是因为没有任何一块是焊死的。其二，官方和第三方走同一条路——官方 provider 和社区 provider 都经过同一套注册、校验、审计流程，不存在只有内部能用的暗门 API。其三，代价是复杂度前移——理解 dsh 必须先理解插件树怎么组装、怎么激活，这也是为什么下一节要把注册流程逐步拆开讲。

二、启动：五层补丁叠出一棵插件树

启动链从 apps/cli/src/bin.ts 开始。它用 Commander 的 passThrough 模式，只认三个自己的 flag：--profile、--patch、--dump-config。从第一个不认识的分词开始，后面全部原样传给 profile 里的应用。这就是实测文章里说的「参数分界」的出处。

profile 的组装在 apps/cli/src/profile-boot.ts 的 composeProfile（142-171 行）。一个 profile 就是 $DSH_HOME/profiles/<name>/ 目录，package.json 里 dsh.profile.bundles 字段给出基础 bundle 的顺序列表。然后五层补丁从低到高叠上去：

  1. bundle 层（按 dsh.profile.bundles 声明顺序）
  2. profile 目录里的 cordis.patch.yml
  3. $DSH_HOME/cordis.patch.yml（home 层，用户全局自定义）
  4. --patch 传入的命令行补丁（可多个，按出现顺序）
  5. 遥测开关补丁（由 DSH_TELEMETRY_MODE 环境变量生成）

每一层是一个 cordis.patch.yml，条目长这样：

- id: use-official-provider
  insert: packages/llm/llm-deepseek
  name: deepseek-official
  config: { apiKey: "!!js env.DEEPSEEK_API_KEY" }

字段就五个：id（同 id 的补丁在高层整块替换低层）、insert（插件源路径）、name、config、disabled、inject。合并逻辑在 vendor/include/src/index.ts 的 applyEntryPatches（58-128 行）：按 id 做「整键替换」，不做深合并。想改一个 provider 的 apiKey，就写一个同 id 补丁把 config 整个换掉。!!js 开头的 YAML 表达式保留原文，激活时才插值——所以环境变量改了不用重新组装树。

写配置用 tmp + rename，遇到 EACCES/EBUSY 重试十次（Windows 文件锁的兼容处理）。层级结构画出来：

真正把树跑起来的是 packages/boot/app-boot/src/index.ts 的 boot()（757-802 行），这个函数的执行顺序值得逐行看：

// 简化后的顺序
await loadLayeredEnv()      // 分层 .env，屏蔽 DSH_/XDG_/DYLD_/BASH_FUNC_
provideCmdline(args)        // cmdlineArgs 冻结快照，注册为服务
installFailLoud()           // unhandledRejection → exit(1)
await mountRootInclude()    // 挂载根 Include
await auditFiberStates()    // 所有 fiber 必须 ACTIVE，否则启动失败

两个点。第一，环境变量分层加载时显式屏蔽 DSH_、XDG_、DYLD_、BASH_FUNC_ 前缀——前者防 .env 文件覆盖启动器已经消费的配置，DYLD_ 和 BASH_FUNC_ 是 macOS 动态库注入和 shell 函数导出的攻击面，一个启动函数把这个都想到了。第二，auditFiberStates：启动结束时遍历所有 fiber，状态不是 ACTIVE（状态值 2）就整体启动失败。没有「带病运行」这个选项。配合 installFailLoud 把未处理的 Promise rejection 直接变成进程退出，dsh 的启动哲学是要么全好，要么别起。

cmdline 的处理也有味道（packages/boot/cmdline/src/index.ts:68-72）：参数在启动早期被冻结成不可变快照，注册为 Cordis 服务。后面所有插件读到的 cmdline 是同一个 frozen 对象——启动中期用户改了 process.argv 之类的怪事在这里被结构性排除。

2.1 插件注册流程：从一行补丁到 ACTIVE fiber

前面的启动链讲的是「树怎么叠出来」，这一节往里走一层：树上的一行插件，从补丁文本到可用服务，完整经过哪些站。这是理解 dsh 乃至给它写插件的主干道。

第 1 站：路径解析与模块加载。合并后的树里每个条目有一个 insert 路径，Loader 按路径 resolve 模块。resolve 失败会触发 BFS 模块自愈——沿着 node_modules 逐层检查并重建 symlink（pnpm 的符号链接布局被手动删过、断过，都能自动修复），修复后重试。这一步对应实测文章里 dsh plugin 命令的另一半工作：它除了转发 pnpm 参数装包，还会做 bundles reconcile——比对 profile 的 bundle 清单和实际装上的包，缺的补装、多的登记。

第 2 站：插件对象校验。模块导出的必须是 { name, inject, Config, apply } 形状：name 唯一标识；inject 是依赖的服务名列表；Config 是一个 schema 定义（声明这个插件接受哪些配置项）；apply 是激活函数。Loader 校验形状，然后拿补丁行里的 config（记得吗，!!js 表达式在这里才插值）对着 Config 做 schema 校验——配置项拼错、类型不对，在这里报错，带插件名和字段名。

第 3 站：fiber 创建与状态机。每个插件条目对应一个 fiber，状态机大致是 pending → loading → ACTIVE（外加失败态）。fiber 创建后进 pending，等待两个放行条件：自身模块加载完成、inject 列表里的服务全部就绪。

第 4 站：依赖解析（Service.check）。Cordis 的服务是按名查找的：任何插件通过 ctx 访问 inject 声明过的服务，访问到一个未就绪的服务会挂起等待，Service.check 在服务提供方 fiber ACTIVE 后放行所有等待者。所以加载顺序无关紧要——树可以按任意顺序激活，依赖关系自己排队。这也解释了前述 fiber 审计为什么可行：审计只看终态，拓扑排序交给状态机自己完成。

第 5 站：apply(ctx) 执行。放行后 Loader 调用 apply(ctx)，插件在这里注册自己的服务（ctx.plugin() / 各类 register API）、订阅事件、挂钩子。注册 API 全部走前面讲的「全有或全无」纪律：命名冲突（如 DUPLICATE_ADAPTER）抛错且整批回滚，tools 的 register 拒绝保留名。apply 同步阶段结束时，服务对外可见。

第 6 站：终态审计。全部 fiber 到达 ACTIVE，auditFiberStates 通过，启动完成。任何 fiber 卡在中间态或失败态，整个进程拒绝启动——你永远不会面对一个「web 界面开了但沙箱没起来」的半瘫系统。

第 7 站：运行期变更。配置文件变化触发 vendor/hmr 的局部重建：受影响的 fiber 被销毁重建，未受影响的保持运行；preset 挂载时还会审计 inactiveRows（树里有但没激活的行）和 leakedServices（注册了服务但 fiber 未激活的泄漏）。装一个新插件，多数情况不用重启整个服务。

整条链路串起来看，注册流程本身也是那个统一手法的应用：每一步都有明确的失败方式，失败要么回滚要么拒启，没有静默降级。给 dsh 写插件时踩到的任何报错，几乎都能定位到上面某一站——这也是我建议插件作者把这一节当 debug 地图的原因。

三、Agent 主循环：一切输入都是事件

核心循环在 packages/core/agent-loop/src/agent.ts，类名 ReactLoopAgent（名字致敬 ReAct）。它有一个三态 phase：idle / maintenance / running（39 行和 93 行附近定义），外加三个输入方法：

  • followup —— 追加下一轮对话，唤醒
  • steer —— 插入下一步指令，唤醒
  • inject —— 注入上下文，不唤醒

三个方法最终都走 kick()，内部是 while (await this.turn()) 这样一个朴素到令人怀疑的循环。但 turn() 里的每一步都是事件。

三个输入的语义差异值得展开。followup 是「用户/调度器说了新话」——追加到下一轮（next-turn），唤醒；steer 是「运行中的指令修正」——插入到下一步（next-step），唤醒，用于用户在模型干活时插话改方向；inject 是「环境状态变了」——注入到下一步但不唤醒，如果 agent 正 idle，这份注入就静静躺在日志里等下一次唤醒一起生效。唤醒本身由 wakeDriver 用 wakeRequested 闩锁实现——多次 kick 在一个 turn 边界合并成一次，不会因为并发输入把循环踢乱。

turn()（246-330 行）先 session.append('turn/start')，然后进内层循环：preStep 决策 → session.append('step/start') → step() → stepEnd。命中 max-tokens 时是 sticky 的（连续续写），agent/turn-stopping 钩子作为最后防线。step()（332-401 行）是单次模型调用：

const request = await this.buildRequest();     // 407-495 行
const stream = await this.llmRuntime.stream(request);
for await (const chunk of stream) {
  session.append('assistant/chunk', chunk);    // 每个 chunk 落盘
}
// BlockAssembler 聚合分段 → finish kind:
// error / aborted / max-tokens / completed

注意 for await 循环体内做的事：每一个流式 chunk 都追加进会话事件日志，带 sourceEventSeqs 溯源字段。模型说到一半进程崩了，重启后日志里有半个回答——重放时能精确知道断在哪。请求出错走 agent/request-error 瀑布，可重试的进重试（后面讲），没有 toolCalls 就 completed 结束 turn，有就走 executeToolCalls。四种 finish kind 的后续处理各不相同：error 进 agent/request-error 瀑布（可重试的走重试，不可重试的终止 turn）；aborted 是用户取消，干净收尾不重试；max-tokens 是 sticky 的——下一轮 step 自动带上「继续」的语义接着写；completed 才是真正的功成身退。流的结束方式本身就被类型化了，每种结束方式有明确的后续路径，没有「不知道为什么就停了」的状态。

buildRequest（407-495 行）是「瀑布 + 折叠」模式的典型：request/header 先折叠出基础请求，再过 agent/request 瀑布——provider、model、effort、maxTokens 都允许被中间件提案修改——最后过 request/context（上下文窗口预算），markAgentLoopRequest 把整个请求 deepFreeze。请求数据在离开 buildRequest 之后不可变，这是后面一切缓存和复用的前提。

时序画出来：

我读这段的最大感受是「事件密度」。一个 turn 里落盘的事件有 turn/start、step/start、assistant/chunk×N、工具事件、turn/end。事件日志在这里承担了数据结构的角色——模型看到的对话、UI 渲染的历史、崩溃恢复的现场，全部从同一个日志投影出来。这个决定的影响贯穿后面所有子系统。

四、LLM 层：适配器注册表与错误分类

packages/llm/llm/src/index.ts（947 行）是 LlmRuntime。两个设计点：

适配器注册是全有或全无。注册同名 adapter 抛 DUPLICATE_ADAPTER，且整个注册批次回滚。听起来严格，但配合插件系统就好理解了：如果两个插件都注册了 deepseek-official，行为取决于加载顺序——这是最难排查的一类 bug，dsh 直接让它在启动时爆炸。

PreparedLlmCall 冻结快照。每次调用前把 adapter、连接配置、key 全部冻结成 PreparedLlmCall，流式过程中连接配置变了（比如热更新换了 key），本次调用不受影响。流式传输中途换钥匙这种事被结构性禁止。

DeepSeek 官方适配器在 packages/llm/llm-deepseek/src/adapter.ts，它是个纯传输层：不缓存、不重试、不做业务决策，只负责 fetch + SSE 解析 + 错误映射。几个值得抄的细节：

  • 每次调用取连接快照，key 从同一个快照里来——不会出现 key 换了一半的窗口期
  • idleWatchdog 300 秒无数据判 TIMEOUT，不留悬挂流
  • 请求头带 x-deepseek-harness-user-id / -session-id / -compact，服务端能识别 harness 流量
  • HTTP 错误码映射：401/403→AUTH，429→RATE_LIMIT，400→CONTEXT_WINDOW_EXCEEDED 或 INVALID_REQUEST，≥500→SERVER，retry-after 头原样透传

重试不写在 adapter 里，在独立的 llm-retry 插件：监听 agent/request-error 事件，指数退避加抖动，公式是 min(initial * 2^min(retry-1, 1024), max)。关键细节：重试决策先落盘再等待。「我决定 30 秒后重试」这个事实写进事件日志后才进入可取消的等待——进程如果在等待中崩溃，恢复时知道还有一次未执行的重试。

resolveModel 里的默认值也透着官方身份：contextWindow 默认 1,000,000，maxTokens 256,000，effort 档位 off/high/max。这些数值和 DeepSeek 模型的实际能力对齐，第三方模型接进来要自己声明。

五、工具运行时：四阶段管线与 fail-closed 并发

packages/core/tools/src/index.ts 有 1946 行，是单文件里密度最高的一个。ToolDefinition 的形状：

{
  execute,                          // 执行体
  output: { schema, render },       // 输出 schema + UI 渲染器
  timeoutMs,
  isConcurrencySafe                 // 必须显式声明才允许并行
}

注册时保留名 run_code 被拒绝。guard() 函数是单调收紧的：权限钩子只能收紧、不能放宽——一个安全插件 deny 掉的操作，另一个插件不能把它 allow 回来。

工具执行是四个阶段，每阶段之间都有事件落盘：

  1. createExecution —— 参数快照 snapshotJsonValue 冻结；Code Mode 折叠判定（collapses() = 非嵌套 && mode===‘code’ && name!==‘run_code’，命中时除 run_code 外全部折叠，提示「only run_code is callable directly」）
  2. prepareExecution —— tools/pre-execute 钩子返回 allow / deny / ask；ask 走 serviceAsk 弹审批 UI；全程 3 次 caller 取消检查
  3. dispatch —— tools/execute 前后钩子包裹真正执行；fuseToolSignals 保证 started body 永不放弃——已经启动的执行不会因为取消信号丢失结果
  4. finalize / finish —— tools/post-execute 钩子可 accept / replace / block；结果 deepFreeze 后发 tools/result 事件

结果对象经 createSuccessResult 用 JSON-Schema 校验输出——工具自己声称的输出格式是强制的，不合格直接算失败而不是静默透传给模型。

并发分组在 tool-calls.ts：按 executionMode 分组，parallel 组吸收后续可并行项，exclusive 是栅栏（整批排队）。执行用 bounded rolling pool（maxParallelToolCalls 上限），提交按模型原序：commitReady 只推进连续就绪的槽位——第 3 个工具先完成但第 2 个还没完成时，3 不提交，等 2。模型看到的工具结果顺序永远和自己发出调用的顺序一致。abort 时未执行的调用补合成错误结果，保证重放时对话结构完整。

这里还有个容易忽略的容错：模型输出的 toolCall 参数是 JSON 字符串，解析失败时 JSON.parse 外面套的是 catch { return raw }——解析不出结构就把原文当字符串传进去，而不是整个调用报错。模型手滑输出了非法 JSON（截断、多余逗号都常见），工具还能拿到原始输入自己判断。配合重放完整性（合成错误结果）和顺序提交，这一层把「模型输出不可靠」当成常态来设计，而不是当成异常。

最狠的一条：executionMode fail-closed。工具没显式声明 isConcurrencySafe: true，一律按 exclusive 处理。并行的收益和并行的风险做权衡时，dsh 把默认值给到了安全那侧。

沙箱在 packages/sandbox-local，头两行的注释就说明了架构：Linux 用 bubblewrap，探测到不支持降级 Landlock（native 的 @deepseek-ai/node-addon-landlock-run），macOS 用 Seatbelt 的 sandbox-exec，Windows 用 ACL 受限令牌。每一档在启动时真的跑一次 true 来功能验证——不看内核版本猜支持，实际执行确认。失败就 fail-closed 降档，永不裸跑 argv。SandboxMode 三档：read-only / workspace-write / danger-full-access。

六、上下文管理：事件日志、surface 投影、三层削减

这是整个 dsh 里我最欣赏的部分，也是最值得慢慢讲的部分。

6.1 会话即日志

packages/core/session/src/index.ts（1157 行）：会话是只追加的事件日志，seq 从 0 单调递增，事件不可变。模型看到的对话历史要经过一道转换：deriveMessages() 从 session.surface.nodes——surface 投影——导出。

surface 的更新原语是 surfaceOp：

{ op: 'replace', start, end }

把 seq 区间 [start, end) 的事件替换成新内容，替换记录进 folded.replacements[]，原事件进 shadowedSeqs。被替换的事件没有删除，还在日志里，只是不再出现在模型视界。UI 想显示「完整原始历史」？读日志。模型只需要当前有效上下文？读投影。一套数据，两种视界。

fork() 派生子会话时带 parentSession / seedLength / delegationDepth，有 OPEN_TURN 守卫（turn 进行中不许 fork）。

6.2 压缩：80% 阈值触发的结构化摘要

压缩引擎 CompactionEngine 有两个触发条件：压力触发（used/contextWindow ≥ thresholdRatio 0.8）和溢出触发（provider 报 CONTEXT_WINDOW_EXCEEDED）。默认配置在 compaction-basic 的 config.ts（27-28 行定义、74-76 行取默认值）：thresholdRatio=0.8，retainRatio=0.16。

压缩的执行（region.ts + summarizer.ts）有几个教科书级的细节：

尾部保留。被压缩区域的最尾部按 token 数保留原文（retainRatio 决定），且做工具调用配对平衡——不会把一个 tool_call 和它的 result 压到摘要的两侧。配对平衡比听起来重要：多模态协议里孤立的 tool_call 消息（没有对应 result）在不少 provider 侧直接 400，压缩如果无脑按 token 切，切出来的会话下一次请求就废了。region 的选择从头尾两侧向中间推进，摘要只覆盖中段，头部的 system prompt 和原始任务描述永远原样保留——「用户最初要什么」这件事不允许被摘要二手化。

摘要请求吃 KV 缓存。摘要的输入是「精确的对话前缀 + COMPACTION_INSTRUCTION 作为最后一条 user 消息」。因为前缀和主对话完全一致，provider 侧的 KV-cache 前缀直接命中——压缩这一次额外调用几乎是增量的。在长会话里这个设计省的钱是实打实的。

摘要必须更小。summarizer 校验摘要严格小于被遮蔽的内容，否则压缩没有意义，报错。COMPACTION_INSTRUCTION（summarizer.ts:31-66 行）要求摘要按固定 section 输出——## Primary Request and Intent / ## Key Technical Concepts / ## Files and Code / ## Errors and Fixes / ## Pending Jobs / ## Current Work / ## Next Step / ## Critical Context，外面包 <compacted-summary> 标记加 CHECKPOINT_PREAMBLE。如果你用过 Claude Code 的 microcompact，会发现这个结构眼熟——dsh 用的是同一族 checkpoint 格式，但把触发、保留、校验全部显式工程化了。

提交顺序即锁。compaction/start 事件先落盘（持久锁），摘要完成依次提交 compaction/summary → user/message（带 surfaceOp replace）→ compaction/end。崩溃在任何一点，恢复时都能从日志判断压缩是否完整、该重做还是该续上。

6.3 裁剪和外溢：压缩之外的两层

tool-result-pruner：工具结果超长时做确定性的 Unicode 码点级 head/tail 截断，中间插 PRUNE_MARKER。确定性意味着同样的输入永远产出同样的截断——对缓存和测试都友好。裁剪事件（compaction/prune）紧贴 replacement 记录，形成「影子价格」协议：日志读者能准确知道每个 replacement 省了多少。

spill：超过 maxInlineBytes 的文本结果整体落磁盘成为 artifact，上下文里只留 head/tail 预览加通知。模型需要时用工具把文件读回来。一个精妙的反循环豁免：read 工具的结果跳过 spill 的 post-execute——不然「读大文件 → 结果外溢 → 模型看不到全文 → 再读」就是死循环。spill-local 的落盘用 mkdtemp 0700 目录 + 0600 独占创建（‘wx’ 标志）。

6.4 一个容易漏看的语义：runtime context 覆盖

运行时上下文（技能目录、todo 状态、goal）作为持久的 user 消息存在，前言写着（system-prompt 侧 index.ts:239 行）：

Current runtime context. This snapshot supersedes earlier runtime-context snapshots.

每次更新发一条新的快照消息，旧的被表面替换掉。配合 skills 目录的 digest 幂等（目录内容 SHA-256 相同就不发新消息）和目录更新消息里那句「replaces every earlier available-skills list」，这套机制把「环境状态」也纳入了事件日志 + 投影的统一模型——没有旁路状态。

七、提示词系统：一个有序 section 注册表

packages/core/system-prompt/src/index.ts（545 行）里找不到「一个大 prompt 字符串」——它实现的是一张有序的 section 注册表。每个插件注册自己的 section 带优先级，渲染时按序拼接：

  • -100：harness identity
  • -99：源路径说明
  • 0：deployment persona
  • 100-199：各工具的说明
  • 105：tool:bash
  • 110：sandbox:policy
  • 115：approval:policy
  • 116.5：subagent 委托说明
  • 之后：tools:sdk、<unlisted-tools>（未列出的工具统一收纳）

identity 那一行原文（361 行，我逐字核对过）：

You are an AI agent powered by DeepSeek Harness.

就这一句，加上 persona 插槽。身份和人格是分离的——identity 是 harness 的，persona 是 deployment 配的，persona 插件通过导入 PERSONA_SECTION / PERSONA_ORDER 常量在同槽遮蔽，不是硬编码字符串替换。

渲染用严格的 {{var}} 插值，缺失变量直接 throw——提示词里的模板变量拼错，启动/渲染时就炸，而不是渲染出一个 {{modelNam}} 送给模型。空 section 自动丢弃；complete: true 的 section 可以替换整个提示词（给完全自定义的 deployment 留的口子）。

子代理的委托提示在 packages/subagent 的 child-agent.ts:135-139，同样值得逐字读：权限范围在启动时固定、被拒操作不要重试、在回复里说明受限状态。三句话把子代理最容易失控的行为（反复撞权限墙）约束住了。applyChildComposition（163-175 行）以 order 120 注入 subagent:delegation 上下文。

八、记忆：没有 memory 包，这是故意的

我 grep 了整棵树找 memory——没有独立的记忆子系统。dsh 的「记忆」是三个机制的组合：

  1. agent-instructions：AGENTS.md / CLAUDE.md 作为基线上下文；FILE_TOUCH_TOOL_NAMES 集合内的 read/write/edit 工具触碰文件后，diff 作为 user 消息推进对话——模型对自己改过什么有增量感知
  2. session-reference：跨会话引用快照，带 untrusted-content 前言（防注入），cwd 亲和度排序
  3. session-query：对事件日志做 sqlite 索引查询，结果按 current / shadowed / log-only 分类——「还在视界里的」「被压缩遮蔽的」「纯日志的」三种时效性明明白白

我的解读：dsh 团队认为「记忆」不应该是独立存储，而是事件日志的一种查询。所有发生过的事都在日志里（包括被压缩的——shadowedSeqs 还能查到），记忆 = 按需检索 + 受控注入。这和 RAG 派的记忆路线是两个世界，更像「事件溯源系统里的读模型」。

九、持久化：为崩溃准备的每一毫米

packages/context/session-persistence/coordinator.ts（1361 行）的 PersistenceCoordinator：write-behind 200ms 批量落盘，严格 seq 校验（乱序事件拒绝），interruptedTurnClosers 合成（崩溃时未闭合的 turn 在恢复时补上闭合事件），HMR 前缀收养（热更新后新代码能接管旧日志）。

后端是 JSONL：<root>/<cwd>/<sessionId>/session.jsonl（可 .zstd 压缩，打包块比裸 JSONL 小约 60%）。崩溃安全三件套：

  • 写入用 tmp + fsync + link()——注意不是 rename。link 是原子创建，rename 在某些文件系统上有替换语义的边角案例
  • 撕裂尾修复：崩溃时写到一半的行，恢复时检测并截断
  • zstd 帧恢复：压缩流截断，按完整帧边界抢救

附件（attachment）走内容寻址：SHA-256 定名，提交前 verify、读取时字节校验、目录 fsync。配上 spill 的 0700/0600 权限策略，磁盘上的每一份数据都有完整性保障。

十、调度与作业：事件溯源的定时器

packages/schedule/schedule/src/runtime.ts 的 ScheduleRuntime 是调度核心，它的做法一眼少见：定时器不存状态，是事件日志的投影。foldScheduleEvents 回放日志重建当前该有哪些定时器；超过 MAX_TIMER_DELAY_MS 的长延迟分段续期。driveOnce 的顺序：折叠定时器事件 → 决策 → agent.runMaintenance → agent.followup（source kind 标记为 plugin）→ flush barrier。agent 进入 idle 时再驱动下一轮。

后台作业是 LocalJobRegistry（jobs-local）：每个 owner 最多 10 个并发作业，owner 隔离用 assertAccess，settle 结果先到先得。模型侧的接口是 tool-jobs 三个工具：job_output / job_list / job_kill，waitTimeoutMs 30 秒，maxConsecutiveWakes: 3——连续三次唤醒都没等到结果就不再等，这是防自激的设计（作业系统唤醒 agent、agent 又查作业、查询本身又触发唤醒的死循环，在这里被数值上限掐死）。

SubagentRuntime（packages/subagent/src/index.ts:171-497）：命名 provider 注册表（DUPLICATE_PROVIDER 同样全有或全无），能力检查，maxDepth 断言防无限套娃，outputSchema 必须是 object。生命周期 startContinuable / followup / reportFrom，drainContinuableDescendants 按子先于父的顺序排空。

并发模型整体上保守得清醒：单进程事件循环。bash/pwsh 走子进程，worker 线程只给 workflow-worker-thread 和 code-runtime 两个明确需要 CPU 隔离的场景，没有通用线程池。Node 的事件循环对 IO 密集的 Agent 负载够用，线程留给真正需要的地方——这个克制在遍地 worker pool 的年代反而少见。

十一、Web 面与安全边界

host 侧 packages/host/webserver 是个 Service(‘webServer’)，最长前缀路由 + SPA 兜底。apiproxy 是传输无关的 RPC 网关（ctx.apiProxy），toFetchHandler 适配 HTTP，AbstractApiClient 给客户端。

值得单独说的是几道安全栅栏：

  • web-startup 拒绝 --host 0.0.0.0（startup.ts:69-71 行）——想暴露到公网？直接拒绝启动。默认钉死 127.0.0.1:3080
  • 客户端 connection 模块对 /api 前缀做 isTrustedApiRequest 校验——DNS rebinding 防御：域名解析到 127.0.0.1 的外部页面拿不到信任身份
  • PRIVILEGED_METHODS 钉死在 loopback
  • WebSocket 做事件下行，前端的状态是服务端事件流的镜像

构建层的 DSH_BUILD_FACE=host|client（tsdown.config.ts:7）让同一批源码按面打包——插件代码在浏览器端和 node 端是同源的两个构建产物。前端启动时 client/modules 注入 window.__DSH_BOOT__ 模块图（带 ?rev= 哈希做缓存失效）。

十二、扩展机制：skills 的六层 rank 与 hooks 协议

12.1 SKILL.md 的发现与发布

skill 系统（packages/skill）兼容 Claude 的 SKILL.md 格式：frontmatter 里 name + description，可选 whenToUse、disable-model-invocation、user-invocable。发现的 rank 层级（skill-filesystem 246-258 行，我逐层核对过）：

rank目录
100项目 .dsh/skills
200项目 .agents/skills
300自定义根（配置注入）
400~/.dsh/skills
500~/.agents/skills
600harness 内置

同名 skill 高 rank 遮蔽低 rank——项目里放一个同名 SKILL.md 就能盖掉用户目录和内置的。仓库自己的 .agents/skills/ 下就有十来个 dsh-* 开头的 skill，既是 dogfooding 也是格式范本。运行时 rank 是 250，落在项目 .agents 和自定义根之间。

变更监听用 chokidar 的 depth:1 watch，项目缓存是 LRU 128——开再多大项目也不会把技能索引撑爆内存。

发布给模型的机制很省：技能目录作为持久 user 消息放在 <system-reminder><available_skills> 里，消息的 digest 是条目 JSON 的 SHA-256——注意是条目数据的哈希，不是渲染后文本的哈希，所以「身份」和「渲染」解耦，渲染格式改了不会误触发更新。目录没变（digest 相同）就不发新消息；发了新消息，前言写明「replaces every earlier available-skills list」，配合 runtime context 的 supersedes 语义，旧目录被表面替换掉。/name 这种用户手势的 regex 只在 source.kind==='user' 的事件上扫描——模型生成的文本里就算出现 /xxx 也不会被当成命令。

12.2 hooks：成对落盘的调用协议

hooks 协议（hook-protocol）是「调用 + 结果」成对事件：持久的 hook/invoked 加 hook/result。每个 hook 点是一个瀑布，插件可以拦截、改写、否决。

官方带了两个兼容桥：hooks-claude-code 桥接 Claude Code 的六个钩子点（SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / Stop / SubagentStop），hooks-codex 桥接 Codex 的五个点（regex 匹配）。也就是说你在 Claude Code 里写的那套 PreToolUse 审计脚本，搬到 dsh 基本直接能跑——迁移成本被刻意压低。

前文反复出现的 tools/pre-execute / tools/execute / tools/post-execute / agent/request / agent/request-error / agent/turn-stopping，全部都是这个协议上的瀑布点。整个 harness 的可编程面就是这些命名瀑布，没有第二个旁路机制。

12.3 typert：从 TS 源码生成工具 schema

顺带一提 packages/typert：分析器（analyzer.ts，单文件 3113 行）能从 TypeScript 源码推导出类型化的工具 schema——写一个类型安全的 execute 函数，工具的 JSON-Schema 自动生成，不用手写。loader 会自动注册 ./typert 的导出。这是 dsh 工具生态能快速长出来的基础设施之一，细节够单独一篇，这里只记位置。

十三、配置与热更新：last-good、文件锁、前缀收养

配置文件（settings-file）的处理是三个小而硬的机制叠加：

  • chokidar 监听，解析失败时回退 last-good 内容——配置文件写坏半个 YAML，运行中的服务不崩，继续用上一份好的
  • withFileLock 的读-改-写——多个插件同时改 settings.yaml 不会互相覆盖
  • 原子写 + 0600 权限——和前面 attachment/spill 同一套纪律

热更新（vendor/hmr）是 Cordis 自带能力的延伸：配置 watch 触发插件树局部重建。最有意思的是持久化层的 HMR 前缀收养（session-persistence）：热更新后新版本的代码能「收养」旧代码写到一半的日志前缀，会话跨代码版本连续。配合 preset（agent-presets/mount.ts）——PresetTree 继承 Include，挂载时审计 inactiveRows 和 leakedServices（注册了服务但 fiber 没激活的泄漏）——「改配置不重启、重启不丢会话」在这套代码里由结构保证，没有给运维运气留角色。

workspace 管理（workspace 包）用 WorkspaceRegistry 维护 canonical-cwd 索引，一次性 bootstrap 从 sessionPersistence.list() 重建——重启后工作区列表从会话存储里长回来，又是一次「状态即投影」。

十四、把六个子系统放在一起看

读到这里可以回答开篇的问题了：dsh 的统一手法是什么？

事件溯源作为脊柱。会话是事件日志，定时器是日志投影，上下文是日志的 surface 投影，记忆是日志的查询，崩溃恢复是日志的重放。一个数据结构承担了五个子系统的基础——这就是为什么 133 个插件能不散架：插件之间不直接共享可变状态，共享的是同一个 append-only 日志和它上面的投影规则。

冻结作为契约。cmdline 冻结、PreparedLlmCall 冻结、请求 deepFreeze、参数快照冻结、结果 deepFreeze。数据跨阶段传递时不可变，缓存的正确性、重放的确定性、并发的安全性全部由此而来。

fail-closed 作为默认。并发安全要显式声明、沙箱每档实测验证、fiber 状态全 ACTIVE 才启动、模板变量缺失直接 throw、启动器拒绝公网监听。每一条都是「出问题时选择不工作，而不是选择可能不安全地工作」。

事件溯源、能力模型、copy-on-write 都是老东西，dsh 没有发明新原则。它做的是把它们在一个 Agent harness 里不折不扣地贯彻到每个角落，没有「这里特殊，通融一下」的例外。工程上最难的从来是 80MB 代码里不留下一个破例的口子。至少在我读过的这些路径里，我没找到。

要不要按这套思路写自己的 harness？我的答案是读它、抄它的手法，但别急着 fork 它。它是为 DeepSeek 模型的特性（百万上下文、特定 effort 档位）调过的，开发者预览期 API 还在动。真正值得带走的是三件东西：surface 投影式的上下文管理（比你想象的便宜且好用）、工具管线的四阶段拆分（审批和观测都有位置插）、事件溯源的调度（天然免掉了定时器状态同步的一堆脏活）。这三件套在任何一个 Agent 项目里都能落地，和用什么模型无关。

源码我还在继续读，typert（从 TS 源码生成类型化工具 schema 的分析器，单文件 3113 行）和 hooks 协议的细节值得再开一篇。这份源码是 2026 年 Agent 工程化的一个高质量样本——不管 dsh 最终生态做不做得起来，它把「一个生产级 harness 内部长什么样」这个问题回答得非常完整。
