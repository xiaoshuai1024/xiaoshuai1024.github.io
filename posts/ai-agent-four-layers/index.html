Agent 拆开就四层，账单能差 30 倍：架构拆解与我的配置

同一个模型，关在聊天框里是台收音机：你放一句，它回一句，你不按播放键它就永远沉默。装进 Agent 里是条流水线：原料丢进去，成品吐出来，中间自己干，不用你守着。这两年所有人都在聊 Agent，聊的其实是这条流水线怎么搭。

但流水线有流水线的代价。很多 Agent 不是死在不能用，是死在月底账单：你以为开了台机器，结果机器空转也在烧电。每次调用都是一次全新握手，握手就计费；任务越复杂，提示词越写越长，token 烧得越猛。我在 AI 编程账单拆解 里晒过自己一条 952 万 token 的真实会话：同一个问题，配置不同，开销能差 30 倍。差距不在模型，在架构。

这篇文章把 Agent 拆成四层讲：大脑（怎么拆任务）、能源（怎么调模型、怎么省钱）、手脚（怎么连外部工具）、手册（怎么把流程固化成稳定能力）。四层各管一摊：大脑决定能力上限，能源决定运行成本，手脚决定能力边界，手册决定稳定下限。框架参考了一条高赞架构课的讲法，配置和账单部分换成我自己的实战数据。四层都拆完，你看任何 AI 产品都能一眼看穿它在哪层偷了工。

四层配置速查：先拿走，再读原理

层管什么可直接照做的配置
大脑任务拆解质量动手前先复述目标的开场验收（第一节）
能源账单与稳定模型路由分档表 + 缓存座次原则（第二节）
手脚能力边界MCP 三步接线与三条安全纪律（第三节）
手册稳定下限Skill 模块骨架与入库判据（第四节）

每层配置都在对应章节里，出问题先拿文末的四层排查速查表对症状查层，再回头读对应层的原理。

第一层：大脑，从你问一句它答一句到自己干到完

先把「Agent 为什么显得能干」这个神奇感拆掉。聊天框模式是响应式：输入什么，吐出什么，全程被动。Agent 模式换了个活法：给一个大目标，它自己拆步骤，自己调工具，干完一步看一眼结果，不行就调整再来，直到办成。

拿一个通用例子看它内部怎么转。目标「调研竞品，写份报告」，它会自己拆成三步：先当探索者去抓资料，再当分析师清洗信息、剔除对不上的部分，最后才当写作者成稿。每一步都在「按自己对任务的理解」做取舍：理解对，步步精准；理解偏，它会以最高效率把错误执行到底。这个执行循环是 Agent 全部能力的来源，也是全部风险的来源，后面第三层第四层都在给它修护栏。

这个循环有个正式名字：ReAct，思考、行动、观察三拍一轮。思考是模型对自己说「下一步该干嘛」，行动是调用工具，观察是读工具返回的结果，三拍完了带着新信息进下一轮。名字不重要，重要的是这个结构解释了 Agent 和聊天机器人的全部行为差异：聊天模型收到输入直接给输出，一锤子买卖；Agent 在思考与观察之间来回穿行，每一轮都带着上一轮的战果修正路线。你后面调试 Agent 时的全部日志分析，看的就是这三拍的轮转记录。

大脑层装没装好，有个简单验收：把任务丢给它，看它动手前说不说人话。合格的大脑会复述目标、列出打算分几步、每步用什么工具，然后等你点头或直接开跑；不合格的大脑拿到任务直接闷头写，写完你再发现方向整个歪了。复述这一步省下的返工，比任何模型升级都划算，这也是为什么说规划质量一半在模板：模板就是逼它开口讲人话的那道工序。

支撑这个循环的是三个部件。大模型是 CPU，负责想；规划是主频，决定任务拆得细不细；记忆是内存，存着上下文和干活的中间状态；工具调用是外设接口，让它读得到文件、跑得动命令、查得了数据库。只配 CPU 不配外设，主频再高也只能跑分，这是很多人搭 Agent 的第一个坑：模型买到顶配，工具一个没接，全靠模型用嘴干活。

三个部件落到工程上是三份配置。规划落在提示词里的任务拆解模板：先复述目标、再列步骤、每步标注打算用什么工具，模板写没写、写得细不细，直接决定规划质量。记忆分两条路，短期记忆靠上下文窗口，装当前任务的来龙去脉；长期记忆要外置，写文件、写数据库，会话结束也不丢。工具调用落在函数签名：每个工具的名字、参数、返回值定义得越规整，模型选工具的准确率越高，含糊的签名是调错工具的第一来源。

CPU 有个出厂设置必须知道：它的内存条每次通电自动清零。这次会话里你们聊得再透，下一次调用，它连你上周定的规矩都不记得。别怪它高冷，API 的无状态设计就是这样，下一层展开。

第二层：能源，API 是通用货币，汇率还分档

大脑要思考，思考要耗电，电就是 API。理解这一层，先认一条：API 是 AI 世界的通用货币，而且汇率分档。同一个请求，走大模型是商务舱，走小模型是地铁：都能到，票价差一个数量级。

计费机制先看清楚。Agent 发请求，带上 API key 当身份证明，网关验证合法性，模型算完吐结果，一次握手完成、一次账单记上。这个流程是无状态的：模型不记得上一次说了什么，每次调用都从零开始。你感觉在跟一个连续的助手对话，账单看得清楚：那是 N 次独立握手拼出来的连续。

账单的算式也简单：输入 token 乘输入单价，加输出 token 乘输出单价，输出单价通常是输入的数倍。对普通对话模型，中间步骤留在上下文里滚动，按输入价计费，最后吐给你的结论才吃输出价，「多想」确实比「多说」便宜。

但推理型模型要单独留心。思维链 token 多数厂商按输出价计费，「想得越久越贵」在新模型上是常态，别拿旧经验套新账单。反过来还有一条隐性成本：把大段文档塞进输入，每轮对话都重新计费一次，你以为是连续对话，实际每句话都带着全部行李重新过一遍安检。

省钱的核心操作是模型路由：按任务复杂度动态分流。简单分类、格式转换、路由分发这类活，7B、8B 级别的小模型速度快、成本低，完全够用；写复杂代码、做多步推理才值得上大模型。全走大模型等于出门就坐商务舱，钱花在刀背上。国产模型这两年在这个分档里的性价比很能打，我自己高频任务常年跑在 DeepSeek 上，账单比全用海外模型友好得多。

路由的分档可以列成一张决策表：文档摘要、意图识别、格式转换，走小模型；代码生成、多步推理、长链分析，走大模型；中间地带的任务先小后大，小模型输出拿不准再升级重跑。第一次跑通的任务按大模型档验证效果，稳定之后逐级降档试水，降到效果掉线为止，那个临界点就是这类任务该坐的舱位。

路由之外还有容灾三件套，缺一个稳定性就塌一角：超时自动重试、主模型故障自动切备用、上下文超限自动截断或总结。网络波动、API 超时、token 超限是日常，不是事故。

三件各自的触发场景分清楚。超时管外部服务无响应，重试要带间隔递增，连着重试等于给故障服务补刀；备用切换管主模型大面积报错或限流，切换动作要自动，否则半夜任务全挂；截断管上下文逼近上限，正确姿势是先把早期对话总结成摘要再丢原文，直接掐头会丢掉开头的任务目标，那是最不能丢的部分。

这三件套不用手写，开源中间件都封装好了：我之前写过 cc-switch 切换 DeepSeek 的完整配置，换模型像换加油站，油枪不动，改个端口，油品还便宜了。真正决定月账单的另有其事：缓存命中率。我的那条 952 万 token 账单里，输入输出比 144 比 1，缓存命中率的差距让整体开销差出 30 倍，机制和数据都在账单那篇里。

缓存值得单独说透，因为它是输入侧最大的省钱杠杆。原理不复杂：两次请求如果开头的内容完全一致，第二次的开头部分可以走缓存价，价格比原价低一个档。Agent 恰好是最容易吃缓存的形态：系统提示词、工具定义、规则文档，每次请求都原样带着，前缀天然稳定。

144 比 1 这个比例的杠杆含义在这。每输出 1 个 token，要陪进去 144 个输入 token，输入侧省下的每一分钱都被放大 144 倍计价。而缓存按前缀严格匹配，从第一个 token 起逐字比对，前缀里任何一处变动，变动点之后全部按原价重算。

这直接决定了请求内容的组织原则：稳定在前，易变在后。系统提示词和工具定义钉死版本放最前，规则文档跟着，最容易变的对话历史放最后，能命中缓存的前缀就最长。所以能源层的省钱纪律，是先排好请求内容的座次，再谈换模型降单价。座次一乱，缓存全部失效，单价降了总价反涨。

结论就一条：怎么问，比问谁更能省钱。

第三层：手脚，从蛛网专线到统一插座

大脑会想、能源管够，还差一样：够得着外部世界。要联网查资料、读数据库、碰本地文件，都得靠工具。工具怎么接，接法走过一段弯路。

老办法是点对点。每接一个工具，就写一套专门的对接代码，告诉 Agent 怎么跟这个数据库说话、怎么跟那个网站交流。三个工具还行，十个工具就是灾难，对接代码比业务代码还多，工具一升级全部重写，Agent 拿到的信息格式还七零八落。机房里全是专线，缠成蛛网，断一根查半天。而且这套蛛网没法复用，你在这个项目里接好的数据库通道，换个项目全部重来，工程投入是一次性的，浪费也是一次性的。

MCP（Model Context Protocol）就是为拆这张蛛网来的：统一插座标准，一次开发，随处插。Agent 不需要知道数据库怎么运作、网页代码多复杂，它只对着 MCP 这个统一接口说话。

具体干活的流程就三步。第一步握手：Agent 问 MCP 服务器「你有什么本事」，对方递上一份技能清单，联网搜索、读文件、查数据库，能力一目了然。第二步格式转换：网页抓下来是 HTML 方言，模型只听得懂结构化的普通话，MCP 在中间当翻译。第三步指令代理：Agent 下个简单命令，MCP 跑去执行，把结果带回来交差。

三步走完，Agent 始终不碰工具的内部细节，专注自己的核心逻辑。时序上再注意一点：握手一个会话只做一次，清单挂在会话里备用；格式转换和指令代理才是每个任务的日常循环，你的性能开销几乎都发生在这两步。

三步里有三个工程细节值得抠。技能清单要精简，清单越长，模型选工具越容易犹豫，宁可按任务场景挂载子集，也别把二十个工具全堆进一次会话。格式转换的目标是结构化：转出来的不是「一大段文字」，是带字段的结果对象，字段越清楚，模型消化成本越低。指令代理要管超时和幂等，外部服务卡住要有超时退出，重复执行不能重复扣款，这两条是工具层事故的重灾区。

还有一个容易被忽略的面：安全。MCP 服务器干的事，是把你本地或内网的权限开一个口子给 Agent，装一个来路不明的服务器，等于把家门钥匙塞给陌生软件。只装可信源的、按最小权限配置、敏感操作加白名单确认，这三条纪律比性能调优重要得多。

现在开源社区现成的 MCP 服务器一大把：查天气的、读本地文件的、连各类 API 的都有。你的动作只剩一个：把插头往 Agent 上一插，能力立刻拓宽一圈。拓宽的节奏也有讲究，一次只插一个新工具，跑稳一两个真实任务再插下一个，出问题时你才知道是哪个插头带来的。工具调用这层在大模型侧的机制（模型怎么决定调哪个工具、参数怎么生成），我在 工具调用桥接实践 里拆过，模型层的决策逻辑和协议层的连接逻辑是两码事，别混。

第四层：手册，把口头传授印成说明书

前三层装好，Agent 能跑了，但你会发现一个新问题：每次让它干活，你都得从头教一遍。任务背景、操作步骤、注意事项，全塞在提示词里，一次几百上千 token。任务一复杂，提示词越长，token 消耗曲线往上飞，准确率曲线反而往下掉——塞得太满，模型自己都绕晕，输出开始胡说。

这就是第四层要解决的：Skill 模块化封装。把高频、复杂的业务逻辑固化成一个个标准模块，每个模块写清楚输入格式、执行步骤、输出规范。下次遇到同类任务，直接调模块，跳过口头传授。一句对比说清它的价值：长提示词是每次口头传授，Skill 是把传授印成说明书，第一万次干活和第一次一样标准，你也不用站在旁边盯。

一份合格的 Skill 要做好三件事，缺一件就在某个场景掉链子。第一件，输入规范：参数必须长什么样提前定义死，少一个直接拒收，从源头挡住大部分错误。第二件，过程约束：把业务流程的每一步、每步输出什么格式都画好线，模型没有自由发挥的空间。

第三件，异常处理，也是最容易漏的一件。数据库连不上、接口超时，不能卡死在那，得有自动重试或跳过的机制。前两件是生产线，这一件是保险丝：短路自动跳闸，不用整台机器陪着重启。Skill 的具体写法、怎么让模型稳定复用，我在 手写一个 Claude Code skill 里给过完整模板。

三件事落到文件里，一个 Skill 模块大致长这样：

# 技能：订单日报生成

- 输入规范：date（必填，YYYY-MM-DD）、scope（shop|all）
  缺字段直接返回「参数不全」，禁止猜测默认值
- 过程：1) 查订单表按状态分组统计
       2) 对比昨日数据算环比
       3) 按固定模板输出，禁止自行发挥格式
- 异常处理：查询失败重试 2 次；仍失败输出
  「数据源暂不可用」，跳过当日日报并记录日志

这个骨架的要点在边界清晰：能做什么、不能做什么、坏了怎么办，三段写死。Skill 和普通 system prompt 的差别就在这里：prompt 是建议，模型可以临场发挥；Skill 把边界写成硬约束，字段级写死，第一千次执行和第一次执行同一标准。

手册层有两个常见误区。一个是把 Skill 当笔记写：记了一堆背景知识，没写输入规范和异常处理，模型读完还是不知道边界在哪，这叫读了说明书不会开机。另一个是过早固化：任务才跑过一次就写 Skill，固化的是运气不是流程，等第三次跑出不同结果再回头改，成本翻倍。判断标准还是那条，重复第三次的高频任务才值得入库。

还有一条运营纪律：执行结果的回流。任务跑得好，把这次有效的参数和步骤固化进 Skill 的下一个版本；跑砸了，把失败案例也记进去，标注「此路不通」。手册不是写完就归档的文档，是随流水线迭代的产品，版本越滚越厚，Agent 才越用越顺手。

组装：四层一条线，先问要不要

四层合起来看整条流水线：手册层存着技能模块，大脑层接任务、拆步骤、查手册决定用哪个技能，能源层按任务难度选择烧哪个档位的模型，手脚层通过 MCP 够到外部世界执行。执行结果回流：效果好，把这个用法记进手册；效果差，修对应那层的配置。用得越久，手册越厚，流水线越顺。

搭之前先过一道边界判断：这个活需要 Agent 吗？判断标准看两条：任务是否多步骤、是否要用外部工具。写一段正则、总结一篇文章，聊天框一问一答就够，硬上 Agent 是给自行车装 V12。跨系统取数、多轮加工、定时跑批，这才是流水线的主场。很多人 Agent 用得又贵又累，问题出在给了流水线一份收音机的活。

确认要搭，也别四层一步到位。最小可用组合是两层：大脑加能源，先让它在聊天框外把多步任务跑通，模型路由配好，账单心里有数。这两层跑不通，说明问题出在任务本身不适合自动化，后面两层接了也白接，先回到边界判断那一步。

跑顺一周再加手脚，接两三个最常用的 MCP 工具，技能清单保持精简。手册层最后上，而且只固化高频任务，第一次做的任务现场教，重复第三次的任务才值得写进 Skill。顺序反了，先写一摞 Skill 再接任务源，八成写的是想象中的流程，真任务来了推倒重来。

还有一条经验按层排查：Agent 表现不对，先定位是哪层的病。把常见症状整理成速查表：

症状先查哪层第一步动作
答非所问、任务跑偏大脑看任务拆解模板写没写，目标复述清不清
又慢又贵能源看模型路由分档和缓存前缀稳不稳
够不到数据、工具报错手脚看 MCP 配置和技能清单挂载
同一任务时好时坏手册看流程固化没固化，还是每次现场发挥

四层分清楚，调试从玄学变成查表。

机器不神秘，工序才值钱

回到开头那 30 倍的账单差距。看完四层你会发现，模型只占其中一层，剩下三层全是你自己的工程决策：路由怎么配、缓存怎么吃、工具怎么接、流程怎么固化。同一个大脑，装在不同的机身里，一台是精密流水线，一台是烧钱的碎钞机，差的就是这三层的功课。

预算的分配观也跟着清楚了。四层里直接花现金的只有能源层：模型订阅和 API 账单，看得见摸得着。手脚层的 MCP 服务器开源免费，花的是选型和安全审查的精力。大脑层花的是写好任务模板的心思。手册层花的是把重复劳动文档化的耐心。钱只占四分之一，剩下四分之三付的是工程功夫，这就是为什么同一个模型，有人用出十倍差价，有人用出十倍稳定度。

Agent 不神秘，它就是四层零件：大脑决定会不会想，能源决定烧不烧得起，手脚决定够不够得着，手册决定稳不稳。哪层出问题修哪层，修不好大脑的，多半是手册没写。工序比天赋值钱，这条流水线上最贵的从来不是模型，是把四层装明白的那个人。我是 1024 工程笔记，越基础的东西，越值得讲透。
