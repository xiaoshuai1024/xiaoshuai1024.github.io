拆完 56 条接缝才看懂：DeepSeek Harness 为什么敢无特权内核

读框架源码最容易产生的疑问是：哪些东西是这个项目不许别人碰的核心？

DeepSeek Harness（dsh）对这个问题的回答记录在 docs/architecture.zh.md 第 11 行，我第一次读到时反复确认了三遍是不是翻译错了——产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop（智能体循环）本身，因此每一部分都可以从配置替换。

循环是 Agent 的心脏。大多数框架的心脏写在最深的调用栈里，动它的方式只有 fork 项目改代码。dsh 把心脏也做成了配件。

一、官方的第二句话更狠

同一份文档第 13 行还有一句：「不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。」

这句话包含两个工程承诺。第一个是对外的：扩展不碰存量代码，你的插件和官方插件挂在同一棵树的旁边，地位对等。第二个更容易被忽略，对内的：你注册的一切（服务、事件监听、类型声明）都是副作用，插件的 fiber 卸载时会被系统自动撤销，树恢复到没有你这个插件时的样子。

「可逆」是把「敢替换」变成现实的机制前提。挂上去出错，卸下来干净；上一秒还在运行的配置组合，下一秒可以少一个部件继续跑。Cordis 容器那篇讲的层一生命周期与作用域分离，支撑的就是这件事。

二、插件长什么样，第一句就写完了

Cordis 入门（docs/cordis-primer.zh.md）对插件的定义浓缩成一句：插件是实现 Service 的对象。它可以是一个带可选 inject 与 apply(ctx) 字段的函数，也可以是一个 Service 子类，生命周期由 Cordis 挂载到当前上下文。仓库里一百多个插件全部装在这个形状里，不存在第二种特权形态。

挂载动作产出一个 fiber。插件在自己的作用域里完成的服务注册、事件监听与类型贡献，全部登记为可撤销的副作用，fiber 卸载时逐一回收，容器回到装载之前的样子。源码初见那篇介绍过 Cordis 底座的论文出处，「注册即效果」的主张落在这句类型定义上执行。

协作方式也有统一契约。waterfall 类事件要求监听器调用 next() 把控制权交给下家，serial 类事件干脆不给 next()；想在管道里动手脚的扩展必须学会接力（docs/architecture.zh.md 轮次流程一节的说明）。拦截有位置，拦截之后要放行，规则写在框架层而不靠口头约定。

注册形态的具体样本在内核里随处可见。cmdline 参数在启动早期被冻结成不可变快照再注册为服务，之后每个插件读到的都是同一份；模型请求组装的收尾会执行 deepFreeze，之后数据不再可变（源码深读第二、四章拆过这两处）。副作用登记的是动作本身，动过的数据则以冻结快照的方式流转。

三、能力的单位：接缝

具体能力以什么形状存在？架构文档给了术语：capability seam（能力接缝）。一条接缝等于一个接口加一个默认实现。接口挂在共享上下文上（ctx.xxx），默认实现是一个独立包，谁都可以提供自己的实现然后让配置指向它。

一条接缝内部有三种角色。架构文档的命名是 Service Definition（声明接口）、Service Provider（实现接口）与 Consumer（使用能力，通常做成面向模型的工具）；一个包可以兼任多角，但单一角色本身不构成接缝，添加一项能力意味着把三者一并设计清楚（docs/architecture.zh.md 能力 seam 一节）。

拿最核心的循环举例。ctx.agentLoop 是接缝，packages/core/agent-loop 是实现这个接口的默认驱动器，文档的服务清单表格里就是这么两行。想换？写一个同接口的实现，配置指过去。

tools 这条接缝顺便示范了契约能细到什么程度。同一个服务行的承诺写着：让每一次工具调用依次经过策略前处理、单调守卫、环绕分派、策略后处理与最终结果观测（docs/capability-seams.zh.md 服务表）。关卡的顺序属于契约本身，无论哪个后端当选都得遵守。

这个结构的价值在约束和自由之间取的位置很妙。接口存在意味着替代品必须讲普通话：工具执行的输入输出、LLM 调用的请求响应、会话事件的字段，全都按契约来。契约之外的自由度则完全放开：你可以把上下文压缩换成自己的策略，把沙箱后端换成公司内部方案，把模型适配指向私有网关。

替换是日常操作，货架是现成的。ctx.llm 名下注册着 llm-deepseek、llm-pi-ai、llm-replay 三个适配器；ctx.shell 挂着 bash-local、bash-sandbox、pwsh-local；ctx.fs 有 fs-local、fs-sandbox、fs-e2b 三家；ctx.subagents 带六个提供方，从进程内 spawn 到把一个轮次整个委派给 Codex 或 Claude Code；连会话标题都有两个可选的 LLM 实现，持久化与存储也各备 jsonl 与 sqlite 双后端供组合时挑选（docs/capability-seams.zh.md）。

架构文档点过这种替换的杠杆效应：文件系统与进程提供方共享同一个执行世界，把两者指向远程沙箱，Bash、PTY 与 LSP 就被一并搬过去，无需按提供方逐个 fork。换掉一条接缝的实现，等于搬动一整片执行面。

服务图里还藏着唯一一条虚线边：fs 指向 fs-observation-policy 的 event gate。它标出了另一条改变行为的通道：不经任何实现替换，仅凭监听能力事件给接缝挂上门禁策略（docs/capability-seams.zh.md 服务图）。

平权还有更细的注脚，全部来自同一张服务表。approval 接缝的回答方是监听器，ACP 为自己的 agent 提供桥接，没有回答方时按 unavailable 关闭失败；userQuestions 靠 UI 前端注册的应答提供方，把工具调用悬停在与具体前端无关的 ask() 上；settings 由插件注册命名空间 schema 再解析分层值；credentials 的配置只携带引用，真实值留在本地后端，凭据轮换后的下一次请求立即生效。回答人可以换，交互层可以换，机密存放位置照样可以换。

四、再数一遍：56 条的真实分布

接缝到底有多少？我把 docs/capability-seams.zh.md 里带服务声明的引用逐个数了一遍，ctx.* 形态的服务有 56 个。数法也交代一下：只统计服务表里的 ctx 键行，页面由生成脚本从 Cordis 声明同步产出，完整性守卫盯在脚本层，人工抄漏会被查出。

56 个里角色标为 seam（可替换接缝）的有 26 个，标为 core 的有 29 个，标为 bundle 的只有 agentLoop 一个。可替换面盖过了单例面，多数能力的默认实现都按「过客」设计；循环被单独做成 bundle 组合包，文档备注写明它是唯一的具体循环插件。

按职能重排一遍，分布看得更清：

  • 循环与生成（6）：agents、agentLoop、agentDefaultModel、llm、systemPrompt、tools
  • 会话与状态（13）：sessions、sessionPersistence、sessionQuery、sessionReferenceResolver、sessionTitle、sessionTelemetry、sessionProjections、sessionProjectionCache、storage、storageDomain、messageFeedback、workspaceRegistry、goals
  • 上下文预算（4）：compaction、tokenMeter、toolResultPruner、spillStore
  • 进程执行面（10）：shell、shellEnv、subprocess、terminals、sandbox、e2b、fs、codeRuntime、workflowEngine、jobs
  • 安全与治理（6）：sandboxPolicy、approval、permissionPresets、invariants、typert、typertGateway
  • 扩展接入与宿主通道（17）：skills、commands、settings、credentials、web、lsp、attachments、subagents、agentPresets、userQuestions、planMode、directoryPicker、apiProxy、webServer、clientModules、dynamicCordisRunner、cordisInspect

两组数字值得对照着读。上下文预算只有 4 条接缝，却承担了压缩、计量、剪枝与外溢全部削减工作，是密度最高的一组；扩展接入与宿主通道一组占去 17 席，说明产品的增长方式是不断往新通道上插插件，而非往老服务里堆逻辑。

数字本身不是重点，分布才是。安全相关的审批、权限预设也是接缝，意思是守门的方式可以换，但门本身永远在。整个系统没有一个「改这里要连坐全局」的中心点，一个模块的行为变化被接口切在了局部。

三个标签的分工有文档原话撑着：服务可以是核心主干服务、可替换的能力 seam，也可以是组合包或组合点。照这个口径重读分布，标 seam 的 26 席给替代实现留着座位，标 core 的 29 席由官方主干把守，agentLoop 独占 bundle 名额，同它那份唯一具体循环插件的备注正好对上。

五、一轮之内，接缝在哪些时刻开火

抽象地说替换容易，把镜头推进到一轮内部更有体感。架构文档的轮次流程给出了完整顺序：驱动器从 inbox 认领输入，先装配提示词各段与工具 schema，随即穿过一串命名节点。agent/pre-step 站在最前面，监听器可以改写或直接拒绝本步的消息；首次认领被拒时会照常关闭一个不含步骤的持久轮次，日志里留下这次尝试的痕迹。

步骤主体依次是 step/start、消息以 user/message 落盘、历史从日志当场派生、agent/request 放行请求、llm/stream 流回响应分片。工具被调用后引出三道瀑布式的执行关口（tools/pre-execute、execute、post-execute），以 tool/result 事件收尾；waterfall 家族的监听器都必须调用 next()，链条上谁也拿不走控制权。

收束同样有规矩：只要工具还欠着下一次请求、或者 inbox 又进了新消息，就领取下一步继续；无账可收时先过 serial 型的 agent/turn-stopping 监听，它没有 next()，被授权的插件可以直接叫停这一轮，最后写下 turn/end。把这张时序表与 56 条接缝并列着看，每一处可能被打断的时刻都能对上一个事件域的名字，替换与拦截在这套时序里各有明确位置。

六、放大一号：目录地形与装配顺序

架构文档另有一张目录级静图。核心包表格列了七行：core/session 管仅追加日志与内存存储，core/system-prompt 管提示词与工具 schema 的组装，core/tools 管带把关的执行流水线，core/agent 管 Agent 接口与活跃注册表，core/agent-loop 是该接口的默认驱动器，core/scope 提供按 agent 划分作用域的原语（库形态，无 ctx 键），llm/llm 承载消息流式词汇与适配器接缝（docs/architecture.zh.md 核心包表）。

动态侧是四层的装配顺序：dsh-base 打底，内容覆盖模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测；其上按 profile 声明的顺序叠加组合包，随后依次吃进 profile 的补丁、home 级补丁与 –patch overlay。patch 按 id 定位条目，要么替换整个 config 要么插入新条目；你机器上 dsh --profile web --dump-config 打印出的任何一行都能这样改掉。

profile 在磁盘上是可直接安装的插件工程。我实测 web profile 的目录里有组合出的最终配置、用户补丁层、package.json 与 workspace 声明四份文件，跑一遍配置转储共 490 行，每一行来自哪一层都标得清清楚楚（源码初见的实测记录）。装第三方插件就是往这个目录加依赖，树的形状随时可查。

归属还有一张速查表。加模型提供方去 ctx.llm 注册；加面向模型的能力去 ctx.tools 注册并让 schema 进提示词组装；fork 活跃会话调用 ctx.sessions.fork(source, boundary?, childSessionId?)；把注册限定到单个 agent 用它的 agent.ctx。新行为的座位事先都排好了位次，扩展实操手册（extension-cookbook）再把这张表展开成新增包、新增工具、新增 LLM 适配器与新增 Chat 节点四篇分步指南。

六、这个系列的终点站

到此为止，DSH 源码深读系列拆过的机制可以做一次归位：

系列各期拆过在架构里的位置
缓存命中纪律（ep2）compaction / systemPrompt 接缝的前缀稳定性
会话当 git 用（ep3）sessions 接缝的日志派生设计
插件挂载链路（ep4）bundles → 插件树的标准装配
沙箱 fail-closed（ep5）sandbox 接缝的四平台实现

回头看，「一切皆插件」这句宣传语的真实含义现在清楚了：每条能力都被接缝切成「契约」和「实现」两半——官方自己提供的也只是默认实现那一半，和你写的第三方插件在契约面前完全平权。

所以第一句的答案可以落定了。为什么敢无特权内核？因为特权这种东西被结构性地取消了：没有任何一块逻辑藏在接缝后面不可替换，自然也就不需要 privileged 这个概念。架构的安全性不靠信任,靠可替换性本身。

系列后续的候选选题已经排好：官方 postmortem 目录里的四篇事故复盘，每一篇都是现成的深度素材。
