133 个插件为什么没写成一坨：dsh 插件系统五层拆解

上篇源码深读写完，我又肝了两天两夜，把 deepseek-ai/deepseek-harness 插件系统的源码和机制从头到尾过了一遍——从 vendored 的 Cordis 内核，到 133 个插件包的注册、装配、技能发现、hooks 权限、typert 类型协议，所有结论都带 file:line 引用，你可以拿着仓库对照看。这篇是 DeepSeek Harness 插件系统的源码解析，也是上篇结尾承诺的兑现：typert 和 hooks 的细节值得再开一篇，拆完发现范围可以更大——插件系统不是 dsh 的一个子系统，它 IS dsh。结论先说：插件不是一个文件，是一套五层设计。「一切皆插件」不是宣传语，是它的组织方式本身——133 个插件没写成一坨，是因为每一层只回答一个问题，层与层之间不互相越权。这篇要讲的不是「插件怎么装」，是「插件为什么能成为这个系统的核心」。

一、插件不是文件，是五层

先看一个反直觉的事实：deepseek-harness 的仓库根目录，AGENTS.md 第一行就写着 plugin-based agent harness on vendored Cordis，everything is a plugin——这一行不是背景介绍，是仓库的组织宪法。54 个包、133 个插件包、每个包都是一个 Cordis 插件，包括它自己。但「插件」这个概念在 dsh 里不是一个文件、不是一个 npm 包，而是五层叠加：

  1. 生命周期层（Cordis 内核）：插件怎么被实例化、怎么活、怎么死
  2. 装配层（profile/bundle）：插件怎么被选进一个运行实例
  3. 发现层（skill registry）：插件的子能力怎么被模型找到、怎么排优先级
  4. 约束层（hooks 协议）：外部进程怎么参与插件的权限决策
  5. 类型层（typert）：插件的服务怎么被别的进程类型安全地调用

这五层不是并列的五个功能，是五个不同的问题域。写插件的人只需要懂第一层（生命周期），装插件的人需要懂第二层（装配），而 skill、hooks、typert 是插件暴露给外部世界的三个面：模型看到的技能、外部进程参与的决策、跨进程调用的协议。读完这篇你会在任何一个点上都说得清「这个机制在哪一层、为什么放在这一层」。

我读源码时数过一遍 packages 目录，133 个插件里真正的「功能插件」不到一半，剩下的是工具注册表、会话、提示词这类基础设施——它们也是插件，也在 cordis.yml 里挂入口，也走同样的生命周期。这个事实本身就是个信号：dsh 把「插件」当成了唯一的组织单元，任何新能力进来都得先回答「你的 apply 是什么」。规范不是写在文档里，是写进架构里的。把这句话再往前推一步就是本篇的立场：插件系统不是 dsh 的一个子系统，它 IS dsh——内核、工具、技能、界面，全部是插件的实例化。

二、直觉：插件是一句话契约

在往下钻之前，先记住插件的最小样子。dsh 官方教程对插件的定义是：导出 apply 函数的 TS 模块（docs/user/develop/basic/index.md）。加一行 cordis.yml entry，插件就装上去了。一个最简插件：

export const name = 'my-plugin'
export const inject = ['tools']

export function apply(ctx, config) {
  // 在这里挂服务、注册工具、监听事件
}

这就是全部。name 是插件的身份证，inject 声明它依赖哪些服务，apply 在激活时拿到 Context 做初始化，Config（可选）声明可配置项。插件自己是声明，框架负责执行——这是读 dsh 插件系统需要一直记住的简化模型。

这个契约为什么能撑起 133 个插件？因为它的约束是「少」而不是「严」。插件不需要继承基类、不需要实现接口、不需要注册到任何中心。它只需要在 apply 里跟 Context 要东西、挂东西。剩下的一切——依赖什么时候就绪、生命周期怎么管理、失败怎么回滚——都是框架的事。接下来五层逐层看，每一层都是这条契约的一个具体实现。

把 54 个包过一遍会发现，「插件」内部其实有三种分工（packages/README.md 的分组表是官方索引）：

  • 能力包：fs、shell、llm、skill、todo、plan、hooks——每个都是直接给模型/用户提供能力的业务插件
  • 基础设施包：core（工具注册表、agent 循环）、api、sdk、util——它们也是插件（导出 apply），但服务的是其它插件而不是终端用户
  • 分发聚合层：bundle/base、bundle/web-app——自己不实现功能，只把插件行以 patch 形式打进 profile，是「插件树的分发单元」

这个分工很重要：dsh 没有「核心 vs 外围」的代码边界，只有「功能 vs 平台」的语义边界。core 包写错了和第三方插件写错了，走的是同一条生命周期管线、同样的校验和同样的失败处理——没有特权路径。这对一个 80MB 的仓库是罕见的选择：大多数框架会给核心代码留后门，dsh 没有。

三、层一：生命周期——插件怎么活

插件装进系统后，第一个问题是：它怎么被实例化？答案在 vendored 的 Cordis 内核里。

vendor/loader/src/index.ts:65 的 Loader 类挂在 ctx.loader 服务上，它维护一棵 EntryTree——每个配置入口对应一个 Entry（vendor/loader/src/config/entry.ts:52）。一个 Entry 的生命周期是固定的五步：import 模块 → unwrap 导出 → 注入依赖 → apply → 失败 rollback。关键在第 3 步：inject 声明的依赖服务没就绪时，插件的 fiber 停在 pending 状态，Service.check 就绪后放行——依赖不是「要求先装好」，是「状态机等待」。

每个插件实例在 Cordis 里是一个 Fiber（状态机）：pending → active → disposed。加载器启动时 assertEntriesActivated()（packages/boot/app-boot/src/index.ts:692）会审计每个 entry 的 fiber 是否真的激活——配置写了但没激活的插件直接报错，不留「装了但没生效」的灰色地带。

三个细节值得注意。第一，apply 是同步注册一切的位置——注册服务、挂工具、监听事件都在这里完成，之后插件就没有「运行时」了，它退化成一组挂在 Context 上的服务和监听器。第二，插件的卸载是 dispose 语义：注册时返回的 disposer 函数按顺序逆序执行，Cordis 保证 teardown 顺序和 setup 顺序相反。第三，fiber 激活失败不会拖垮别人——失败 rollback 只回滚自己的副作用，其它插件照常。

为什么这个生命周期能稳定？vendor 是关键。Cordis 不是 npm 依赖，是拷进 vendor/cordis 的源码——上篇讲过这个选择的理由（升级一个第三方包带来的行为漂移，在 133 个插件的系统里排查成本极高），这里从插件视角补一个细节：插件契约（name/inject/Config/apply）本身就是 vendored 代码的一部分。框架层改契约 = 改自己的代码，不用等上游发版、不用做破坏性迁移。dsh 团队对「内核的每一行都要为我负责」的执行，在插件契约上比在内核本身上更彻底——契约是插件生态的地基，地基锁死，生态才敢长。

还有一处体现「契约极简」的细节：插件对象不需要是类，{ name, inject, Config, apply } 就是一个合法的插件。inject 里声明依赖的服务名，apply 时 Context 里已经有全部就绪的服务。这种「鸭子类型」的插件契约在 2026 年的 TS 生态里显得朴素，但它的好处是：插件可以是一个文件、一个函数、甚至一段动态生成的代码——extensions 包里的运行时插件就是这么干的，agent 在运行时可以 define 一个插件挂进自己的插件树（packages/extensions/cordis-host-runner/src/index.ts:140）。契约的朴素让「插件」这个概念的适用范围最大化。

这一层的设计意图：插件的生命周期是框架的唯一责任，插件自己只做声明。没有插件的 main 函数、没有启动顺序的讲究、没有手动清理——全部由 fiber 状态机接管。

一切皆插件在这层有个最极端的例子：加载器本身也是插件。boot() 用 ctx.plugin(Loader) 把加载器装进自己的 Context（packages/boot/app-boot/src/index.ts:771）——加载插件树的那个东西，自己也是一棵待加载的插件。这个自举不是炫技：它意味着连「加载」这件事都能被其它插件替换和扩展，框架没有把任何机制锁死在代码里。这也是「没有特权路径」最彻底的证明——执行一切皆插件的代码，自己也得先过插件这关。

四、层二：装配——插件怎么装

生命周期管「一个插件怎么活」，装配层管「哪些插件组成一个运行实例」。这层有三个概念：cordis.yml、profile、bundle。

cordis.yml 是插件树的配置。boot() 启动时（packages/boot/app-boot/src/index.ts:757）把 cordis.yml 挂为根 include 入口（:486），文件里每一行 - id/name 就是一个插件入口。上篇讲过五层补丁叠插件树，这里不再重复，只说装配层的两件事：profile 和 bundle。

profile 是层列表，bundle 是层的内容。dsh.profile.bundles 声明「我这个 profile 由哪些 bundle 按序叠加」（packages/boot/app-boot/src/profile.ts:48），dsh.bundle.patch 声明「我这个包是一个 bundle，我的补丁层在 ./cordis.patch.yml」（:42）。内置 profile 的初始层来自模板：web 版 = dsh-base + dsh-web-app，headless 类似（:114）。一个运行中的 dsh 就是按序叠出的插件树——官方文档的原话是 a running dsh is a plugin tree composed at boot from ordered layers（docs/architecture.md:17）。

dsh plugin 命令刻意不做包管理。apps/cli/src/plugin.ts:120 的 runPlugin() 把参数原样转发给 pnpm（在 profile 目录里执行），装完跑 reconcilePlugins()（:59）按安装结果回写 dsh.profile.bundles 层列表；:36 的 exportsPatch() 判断装进来的包是否声明了 dsh.bundle，声明了就把它当补丁层。插件市场则退化成 npm + GitHub topic——README 里写的是给插件仓库打 dsh-plugin topic 便于被发现（README.md:40）。

这一层的信息量很大，但核心只有一句话：装配是声明式层序叠加，不是命令式脚本。你要什么插件、按什么顺序，写进配置；系统按层序组合出插件树，谁先谁后由层序决定，不由加载时序碰运气。

cordis.yml 长什么样，直接看官方 example（examples/headless-agent/cordis.yml）最直观——每行一个插件入口，带配置：

- id: settings
  name: '@deepseek-ai/dsh-settings-file'

- id: credentials
  name: '@deepseek-ai/dsh-credentials-local'

- id: llm-deepseek
  name: '@deepseek-ai/dsh-llm-deepseek'
  config:
    thinking: enabled
    reasoningEffort: max
    models:
      - id: deepseek-v4-pro
        contextWindow: 128000

- id: bash
  name: '@deepseek-ai/dsh-bash-local'
  config:
    timeoutMs: 60000

bundle 的 patch 文件也是这个格式，但语义不同：cordis.patch.yml 是一批 insert，按行 id 寻址（packages/bundle/base/cordis.patch.yml 开头的注释写得很清楚：later bundle patches and the user’s profile address these rows by id, with the last write winning per row）。两个注意点：patch 替换整行 config 而不是合并——所以一个插件跨 mode 的配置差异必须拆到各自的 mode bundle 里，不能靠 patch 覆盖字段；行顺序不承载加载语义（激活是服务可用性驱动的），分组只是为了人读。

dsh plugin add 的实际流程（官方教程 docs/user/develop/basic/publish.md）：在 profile 目录里执行 pnpm add → reconcilePlugins 把新包写进 dsh.profile.bundles 层列表 → 重启生效。你装的是声明了 dsh.bundle 的包时，它自带 patch 层，自动参与层序；否则它只是个普通依赖，需要你自己在 cordis.yml 或 patch 里挂入口。装插件和激活插件是两回事，这个区分初用者最容易忽略。

想成为能被 dsh plugin add 正确识别的插件，package.json 有几条硬规范（AGENTS.md:100 和 bundle/base/package.json 的实例）：peerDependencies 必须含 @deepseek-ai/cordis（显式声明你依赖的内核版本）；exports 需要暴露 ./src/*（让 cordis.yml 能用文件路径直接挂入口）；bundle 还要暴露 ./cordis.patch.yml；files 白名单只发 lib 产物。这些规范的共同点：插件包对自身的可装配性负责——发布时就把「能被发现、能被挂载、能被补丁」所需的信息带齐，装配层不用猜。

五、层三：发现——插件的能力怎么被找到

插件装上之后，模型怎么知道一个插件提供了什么技能？dsh 的答案是 skill registry——一个把「技能从哪来」完全插拔化的注册表。这个注册表有两个概念：provider 和 rank。

provider 是技能的来源。ctx.skills.registerProvider()（packages/skill/skill/src/index.ts:391）注册一个来源——本地文件系统、远程 registry、运行时注入都行。provider 只需要实现两个方法：list() 返回候选清单，get() 按需加载完整技能体。发现和加载是分离的：ctx.skills.list() 只出摘要（index.ts:471），ctx.skills.get() 才读正文（:501）——技能体是懒加载的，模型没用到的技能不会读盘。

rank 是层内优先级。这是全文最关键的一个设计：compareIndexedCandidates（index.ts:807）按 rank → providerOrder → localOrder 排序，但rank 只在同一层内决定同名技能的胜负（index.ts:75 的注释写得很直白：Lower ranks win duplicate skill names before provider registration order is considered）。跨层的情况完全不一样——层是 shadowing 语义：合并时 global 层打底，scope chain 逐层覆盖，最近的层同名直接赢（index.ts:553）。

本地文件系统 provider 定义了六层 rank（packages/skill/skill-filesystem/src/index.ts:36）：

ranksource目录
100project-dsh项目根 .dsh/skills
200project-agents项目根 .agents/skills
250runtime运行时注入（注册表内建）
300custom配置的自定义目录
400user-dsh~/.dsh/skills
500user-agents~/.agents/skills
600bundled环境内置（BUNDLED_SKILL_RANK）

这套排名的语义我读下来的理解是：项目里的技能压用户级，用户级压内置。.dsh/skills 里的技能是跟着代码仓库走的，优先级最高；~/.agents/skills 是个人沉淀，中等；内置技能是最后的公共底座。同名冲突时低 rank 静默让位，注册表打 warn 日志（index.ts:576）——不报错，因为同名覆盖是预期的分层行为。

被选中的技能最终通过 renderSkillContent（index.ts:171）渲染成统一的 <skill_content> 块喂给模型：<skill_resources> 说明资源在哪、<skill_instructions> 放正文。模型看到的技能格式是唯一的，不管它来自哪个 provider——发现是插拔的，呈现是统一的。

scope 是发现层的隐藏维度。注册表的分层不只有 global 一层：agent preset 挂载的插件注册进自己 preset 的 scope 层（index.ts:349 的注释），读取时 global 打底、scope chain 逐层叠加、最近的层同名直接赢。同一个技能名，不同 agent 看到的可以是不同实现——一个 preset 覆盖全局技能、别的 preset 不受影响。这是 Cordis scope 机制在发现层的延伸，也是「133 个插件不互相踩」的空间隔离手段。

invocation 策略控制谁能调。每个技能带 modelInvocable / userInvocable（index.ts:48）：模型可调、人（命令面）可调。技能目录对模型和对人可以是两个不同的列表，一个技能可以被设计成「只能人用」或「只能模型用」。

性能细节：缓存 + watch。目录扫描不是每次 list 都做——collectCache 按 cwd + scope chain + revision 缓存（index.ts:528），注册表变化时 revision 递增整体失效（:622）。文件系统 provider 用 chokidar 监听技能目录，文件变化 200ms 稳定后触发失效（skill-filesystem/src/index.ts:41）——写一半的 SKILL.md 不会触发半成品进目录。发现层的目标是「模型看到的目录永远新鲜且完整」，缓存和 watch 都是为这个目标服务的。

防御是双向的。provider 返回的候选要过 validateCandidate（index.ts:708）：名字必须匹配 kebab-case 语法（/^[a-z0-9]+(?:-[a-z0-9]+)*$/）、description 非空、rank 必须是有限数字、candidate 声明的 provider 必须等于注册它的 provider。任何一项不过，这个候选被拒绝而不是被容忍。注册表不信任任何 provider 的自觉——第三方插件如果返回坏候选，拦在目录之外，不会污染模型看到的技能列表。

技能体的解析在 provider 侧：skill-filesystem 的 parseSkillFile 读 SKILL.md 的 YAML frontmatter（name/description/whenToUse/invocation/metadata），正文剥离元数据后成为 content（skill-filesystem/src/index.ts:206 的 get()）。文件系统 provider 同时支持目录包（目录里多个文件 + 相对资源）和单文件两种形态，resourceBase 标记技能的资源根（目录路径），模型读 <skill_resources> 就知道相对路径往哪解析。技能是 markdown 还是目录包，对注册表透明——provider 的职责边界把「来源的多样性」挡在协议之外。

六、层四：约束——外部进程怎么参与决策

插件的能力不止工具和技能，还有权限。dsh 的权限模型里，外部进程（比如你本地的安全脚本）可以在关键时刻拦一刀。这是 hooks 协议——一个把 Claude Code 和 Codex 两套 hooks 方言收成一套中立协议的实现，全在 packages/hooks/hook-protocol/（8 个文件，加起来不到 700 行）。

一次 hook 拦截的完整链路：

  1. 接线：桥接层（hooks-claude-code / hooks-codex）把 hooks.json 解析成「事件 → matcher 组」，监听对应事件点（如 tools/post-execute，hooks-claude-code/src/index.ts:247）
  2. 匹配：事件发生时用 matchesMatcher（matcher.ts:57）选出命中的 hook。双方言差异在这里统一：纯 [A-Za-z0-9_|] 的模式按 Claude 字面量（| 分隔的精确备选）解释，其余按 Codex 的无锚 regex 解释；缺失、空、* 都是全匹配
  3. 执行：runHook（runner.ts:67）把 JSON payload 写进 hook 进程的 stdin，走 ctx.shell 执行——凭证擦除、进程组取消、超时全套机制复用。默认超时 10 分钟（DEFAULT_HOOK_TIMEOUT_MS = 600_000，runner.ts:20）
  4. 解码：parseHookOutput（codec.ts:59）把进程结果翻译成中立语义。三个关键规则：exit 2 = 拦截（stderr 是给模型的理由）；exit 0 且 stdout 以 { 开头 = 结构化 JSON；其余输出当普通文本。结构化 JSON 里 hookSpecificOutput.permissionDecision（allow/deny/ask）覆盖顶层 legacy decision（approve/block），而 hookEventName 防串事件——声明是别的事件的拦截块，事件相关字段直接丢弃（codec.ts:122）
  5. 合并：mergeHookOutputs（merge.ts:62）把同一事件点所有 hook 的结果折成最严格决策：deny > ask > allow；continue:false 是粘性的停；理由只保留获胜档位的；additionalContext 按 hook 顺序累积

这个协议最值得读的是它怎么处理不确定性。hook 进程可能没装、可能超时、可能输出非法 JSON——协议给每个异常都定了「不拦截」的默认：spawn 失败当非拦截错误（runner.ts:96）、非法 JSON 当纯文本（codec.ts:79）、非法 regex 运行时返回不匹配（matcher.ts:64）。默认放行，只有明确表达才拦截——但一旦明确表达（exit 2 或结构化 decision），它就是最高优先级。

merge 的语义用一个场景说清：同一个 PreToolUse 事件挂了两个 hook，一个返回 {"decision":"allow"}，一个返回 {"continue":false,"stopReason":"需要人工确认"} 且 exit 2。折叠结果是 deny——exit 2 的 block 和 deny 同档（merge.ts:37），continue:false 的 stop 粘住，stopReason 保留，第一个 hook 的 allow 被覆盖。反过来，如果第一个 hook 返回 deny、第二个返回 ask，结果是 deny 且理由来自 deny 的那个（merge.ts:91：理由只保留获胜档位的）——不会出现「一个说不一个说行，最后系统自己猜」的中间态，决策永远是确定的。

每次 hook 调用都会写一对事件：hook/invoked + hook/result（types.ts:19），用 handlerId 关联，只做日志记录。这对事件是上篇讲过的「事件溯源」纪律在 hooks 里的落地——hook 拦了什么、放行什么、耗时多少，全部有日志为证，审计不用猜。

hooks 的配置形态双方言几乎一致，一个真实的 hooks.json（Claude Code 方言）：

{
  "PreToolUse": [
    {
      "matcher": "bash|execute",
      "hooks": [
        {
          "type": "command",
          "command": "python /opt/guard/check_command.py",
          "timeout": 30
        }
      ]
    }
  ]
}

Claude 方言的 matcher 是字面量备选（bash|execute 精确匹配两个工具名），Codex 方言同一个 matcher 会被当无锚正则——bash|execute 在正则里含义完全不同。协议用 MatcherMode 区分（types.ts:79），桥接层各自解析，但运行时的匹配、解码、合并全走同一套代码。配置里非 command 类型（CC 的 prompt/agent/http）被解析但跳过，桥接层对每个跳过的类型打警告（hooks-claude-code/src/config.ts 的 skipped 集合）——协议只认 command，其他类型留给未来。

Claude 方言一共 7 个事件点：SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop、SubagentStart、SubagentStop（config.ts:16）。UserPromptSubmit 和 Stop 的 matcher 会被丢弃（config.ts:112 的注释：这两个事件没有可匹配的主体）。事件点不是无限扩展的，协议收敛到引擎真正有的拦截位置——多一个事件点就是多一份双方言都要实现的承诺。

hook 进程的 stdin 拿到的是完整上下文，不是一行参数。以 PreToolUse 为例，payload 里包含 tool_name、tool_input（完整参数对象）、tool_use_id，以及 agent 身份、会话信息（hooks-claude-code/src/index.ts:342 的 postToolPayload 是同构的例子，PostToolUse 额外带 tool_response 的文本块）。拦截脚本不需要自己拼参数——协议把事件的完整快照交给它，它只需要根据快照做决策、把决策写进 stdout JSON。决策和执行的分离在 payload 层面就已经完成：hook 只读快照、只写决策，永远不会拿到执行权。

七、层五：类型——插件怎么被跨进程调用

前四层都在一个进程内。但 dsh 有桌面端和浏览器面，插件注册的服务需要被别的进程类型安全地调用——这是 typert 的地盘，也是上篇结尾承诺展开的两个机制之一。

typert 的思路一句话：类型即协议。你在插件里写一个 TypeScript Service 类，标注 @typert service JSDoc（如 packages/api/gateway/src/index.ts:88），构建时 analyzer.ts（单文件 3113 行）分析 AST——类成员、签名、JSDoc、类型——生成一个跨进程调用的完整 manifest：有哪些服务、哪些方法、参数怎么编码、结果怎么解码，全部从源码推导，不需要手写任何 wire schema。

生成物通过包的 ./typert 导出暴露（packages/interaction/commands/package.json 里 exports["./typert"] 指向 lib/typert.host.js）。typert-loader（packages/typert/loader/src/index.ts:284）在插件 fiber 挂载时自动导入这个 manifest 注册进 ctx.typert，卸载时撤回——注册跟着插件生命周期走，不用手动管理。

loader 对 manifest 的校验严格到近乎苛刻：validateTypertManifest（loader/src/index.ts:83）逐字段检查——manifest 的 package 必须等于导出它的包名、face 必须是 host、schema 必须是 zod v4 实例、服务成员的类型声明必须完整。任何一项不合格，加载直接失败并点名（loader/src/index.ts:432 把全部失败聚合抛出一个 AggregateError）。这是典型的 dsh 风格：构建期能发现的问题绝不留到运行时。类型层出错意味着跨进程调用可能静默损坏数据，所以它在装载时就 fail loud。

manifest 里的核心是 invocations——每个可跨进程调用的方法完整描述「怎么调」：receiver 是 direct（同进程直调）还是 context（经 Context 查找服务）、参数从哪来（json 直接编码或 lookup 从上下文查）、每个参数和结果用什么 codec 编解码（loader/src/index.ts:190 的 requireInvocation）。生成器产出 host 面和 remote-client 面（package.json 里 ./typert 和 ./remote 两个导出），host 面注册进 registry，remote 面给调用方进程用——一个服务一份类型定义，两端各自生成，签名漂移在构建期就被发现，而不是运行时对不上字段才报错。

typert 和上篇提过的工具 schema 是两条线：工具 schema 是 defineTool 的参数声明编译成 JSON Schema（手写声明、运行时校验），typert 是服务级协议（源码推导、构建期生成、装载期校验）。一个管模型调工具，一个管进程调服务——dsh 把这两条边界分得很清，模型接口和进程接口各自有自己的类型纪律。

typert 的注册不只有自动一条路。ctx.typert.register() 的入口始终开放（loader/src/index.ts:21 的注释：hand-written wire schemas, tests, non-loader compositions 走手动注册）——不用 ./typert 产物也能贡献类型化服务，只是失去了「跟着 fiber 生命周期自动注册/撤回」的便利。自动路径和手动路径的区分，和装配层「bundle 自动参与层序 vs 普通依赖手动挂入口」是同一个设计模式：框架识别得了的形态给自动化，识别不了的留手动入口，但两条路走的是同一个注册表、同一套校验。

analyzer 怎么工作值得多说两句，因为「类型即协议」是句口号，落地全靠它。analyzer.ts 分析的是 TypeScript AST 的这几样东西：Service 类声明（@typert service 注解标记）、成员方法签名（参数类型、返回类型）、JSDoc（描述、@param 注释）、类型引用（interface/type 别名在仓库内的解析）。生成模型里每个 service 有 key、exportName、members、types 四件套（loader/src/index.ts:113 的校验对应这个结构），每个 invocation 有 receiver/parameters/result/codec（loader/src/index.ts:190）。换句话说，analyzer 做的是「把 TS 的类型系统翻译成进程边界的协议描述」——TS 编译器本来就要做类型检查，typert 让检查结果不止停留在编译期，而是变成一份可以跨进程执行的契约。

八、源码佐证：一个插件从声明到注册

五层讲完，用真实的插件把全链路串一遍。dsh 仓库里最适合当教材的是 tool-todo（packages/todo/tool-todo/src/index.ts，整个插件 227 行），它同时展示了一个工具插件的最小契约和 dsh 的「把决策变成事件」手法。

契约三件套（index.ts:22）：name = 'tool-todo'、inject = ['tools']、Config 用 schemastery 声明配置 schema（:41，allowParallelInProgress 必须显式配置，不设默认值——配置缺失直接拒绝启动，不给隐式行为留空间）。

apply 里的两件事（:128）：

export function apply(ctx, config) {
  ctx.inject(['sessionProjections'], (projectionCtx) => {
    projectionCtx.sessionProjections.register<'todos', TodoItem[] | null>({ ... })
  })
  ctx.tools.register(defineTool({ ... }))
}

第一件事是可选的子能力：如果会话投影服务被装配（headless 组合没有这个服务就跳过），注册一个 todos 投影——todo 列表的当前状态从 todo/write 事件推导。第二件事是注册工具。注意 ctx.tools.register 的 defineTool（packages/core/tools/src/schema.ts:545）——五要素：

  • parameters：模型可见的参数 JSON Schema（additionalProperties: false，多传的字段直接 schema 层拒绝）
  • output.schema + render：canonical 输出 schema + 纯函数渲染
  • execute：参数校验后执行，返回值再按 output schema 校验
  • presentCall / presentResult：UI 呈现（展示是重放语义，参数对不上旧 schema 就静默降级通用卡片，不能抛——schema.ts:594 的注释专门讲了这件事）
  • timeoutMs：可选协作超时

把决策变成事件体现在 execute 里（index.ts:206）：工具不直接改任何状态，而是 exec.agent.session.append('todo/write', { todos })——把一次写入追加进会话事件日志，todo 列表的当前值由 todos 投影从事件流推导。这就是上篇总结的手法在插件层的最小闭环：插件是状态的生产者，状态是投影的产物。

完整注册链：cordis.yml 一行 entry → boot() 挂根 include → Loader 的 Entry 五步加载 → fiber 激活 → apply 执行 → ctx.tools.register 把定义注册进工具注册表 → 模型的工具列表里多一个 todo_write。从配置到模型可见，一条没有断点的链。

顺着这条链再往前看一步，tool-todo 还示范了插件怎么写才能融入整个 harness 而不只是「自己能用」。它的 inject = ['tools'] 只声明了最小依赖；sessionProjections 是可选的（ctx.inject 的第二个参数只在服务存在时执行）——插件对装配的容错是声明式的：缺了投影服务，工具照常注册，只是没有 UI 侧的实时状态。这种「核心必需、扩展可选」的声明方式，让同一个插件在 headless 和桌面两种装配里都能跑，且行为差异是显式的。

九、边界与坑

五层设计不是没有代价。读源码时我记下了这些边界，写插件和配插件的人各会踩到一部分：

装配层的层序冲突。两个 bundle 装了同名插件，胜者由 bundle 层序决定（dsh.profile.bundles 的列表顺序），不是由安装时间决定。排查「我装了 A 插件但生效的是 B」时，先看层序再看版本——这个方向反了会很浪费时间。

发现层的静默让位。同名技能低 rank 让位只打 warn（skill/src/index.ts:576），不报错。后果是：你在 ~/.agents/skills 里放了一个和项目 .dsh/skills 同名的技能，它永远不生效，只有日志里一行 warning。同名是分层特性，但排查时容易忽略这行日志。

约束层的超时与跳过。hook 默认超时 10 分钟，跑一个长时间阻塞的 hook 会把整个 turn 拖住；CC 配置里的 prompt/agent/http 类型 hook 会被解析但跳过（只跑 command 类型，hooks-claude-code/src/config.ts 的 skipped 集合）——配置了但不生效的类型不会报错，只有警告。另外 updatedInput（hook 重写工具入参）被解析但明确不执行——协议留了口子，实现没接，看到文档提它别以为能用。

类型层的严格校验。typert manifest 不合格直接 fail loud 并点名包名。构建期生成、装载期校验，意味着插件作者改服务签名后忘了重新构建，装插件时直接报错——这设计是故意的（跨进程类型漂移的后果比构建报错严重得多），但头几次遇到会觉得它「小题大做」。

注册顺序的隐藏权重。同一层内 rank 相同时，providerOrder（注册顺序）和 localOrder（候选顺序）决胜（skill/src/index.ts:807）。注册顺序是单调递增的全局计数（:369）——先注册的 provider 在同 rank 下赢。这不是 bug，是同层内的稳定性保证，但如果你动态注册了两个同 rank provider，胜负取决于谁先 apply。

十、五层的可观测性：每层都有日志留痕

五层除了各管一件事，还有一个共同点值得单说：每一层都把自己的决策写进了事件流。装配层的启动审计（哪个 fiber 没激活，boot 时直接报告）；发现层的同名让位警告和技能变更通知（skills/change 事件，skill/src/index.ts:297）；约束层的 hook/invoked + hook/result 事件对；类型层的注册/撤回跟着 fiber 生命周期走。插件系统不是黑盒——出问题时的排查路径是现成的：看事件流，每一层都留下了痕迹。

这和上篇总结的「事件溯源作为脊柱」一脉相承。插件系统的五层不是五个独立的黑箱，它们共享同一条日志纪律：状态改变要可重放、决策要有记录、异常要有归因。133 个插件长期不散架，一半靠分层，一半靠每层都把自己摊开给人看。

十一、带走的模型

五层各有各的答案，但骨架是同一个：插件是声明，框架是执行——这也是「一切皆插件」的完整含义：它不是一个技术选型，是 dsh 对「系统如何组织」给出的回答。插件只写「我要什么（inject）、我提供什么（服务/工具/技能）、我接受什么（Config）」，生命周期、装配、发现、约束、类型安全全部由框架的各层接管。133 个插件没散，不是因为每个插件写得多规矩，是因为框架把「怎么活、怎么装、怎么被找到、怎么被约束、怎么被调用」这五个问题的答案收敛在了五个明确的位置。

另一个贯穿的纪律是 fail-closed 与 fail-loud 的组合。插件配置缺字段 → 拒绝启动；manifest 不合格 → 装载期报错；hook 进程异常 → 默认放行但记录在案；同名技能冲突 → 静默让位加警告。该拦的在入口拦，该记录的在日志里留痕，该放行的绝不让一个异常进程卡住主流程。这套「入口从严、运行从宽、处处留痕」的组合，比任何单一策略都更能解释为什么这个系统能长期保持可诊断。

把五层连起来看，还有一个更根本的设计取向：dsh 把插件的「身份」和「形态」拆开了。身份是 name（kebab-case 字符串），形态可以是一个 npm 包、一个本地目录、一段运行时生成的代码、一个 ./typert 导出。身份统一、形态自由，是插件生态能同时容纳官方包、第三方包、用户本地技能、agent 自改运行时而不互相干扰的原因——每一层认的都是身份，不认形态。

上篇的结尾我说源码还在继续读。读完插件系统这五层，我的判断没变：dsh 值得抄的是手法不是代码。而它最值得抄的第一手法，就是把「一切皆插件」当真——从内核到界面，从加载器到技能，没有一条特权路径。生命周期、装配、发现、约束、类型，这五个问题任何 Agent 项目都会遇到，而 dsh 给出的答案——声明式装配、provider 化发现、外部进程参与决策、类型即协议——都是可以脱离 DeepSeek 语境单独落地的设计。对想自己写 harness 的人来说，这篇和上篇合起来就是一张从内核到插件的完整地图。

插件装上之后怎么用起来，我在插件 top10 实测里筛过一遍，从零写自己的 skill讲的是同一套发现机制的 Claude Code 版。源码读到这个深度，下一步我打算照着五层的手法自己搭一个最小 harness 的插件骨架——到时候再写一篇实操对比。
