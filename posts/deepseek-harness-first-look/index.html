打开 GitHub，DeepSeek Harness（dsh）的仓库挂在趋势榜第一。创建时间 2026-08-13 11:56:32 UTC，发布时 star 已经 1.5 万，到我实测时已涨到 2.9 万——发布 12 小时不到，逼近 3 万。模型厂商下场做 Agent 工具链，这本来就是大事，但真正让我放下手头活去装的，是仓库描述里那句话：Everything is a Plugin，一切皆插件。

装完跑了一圈，我的结论先放在这：dsh 没有把 Claude Code 或 Codex 重新实现一遍，它做的是把 Agent harness 从「封闭产品」拆成「插件平台」——模型、工具、会话、沙箱、UI 全部是插件，任何一块都能替换。这是 Agent 工具链形态上的一个变化，不是又一个 CLI 工具。但它现在是 developer preview，Node 版本有硬门槛，插件生态刚爆发还没沉淀，我的判断是：值得装来看，别急着全切。

这篇文章把「我看到了什么、怎么装、为什么这么设计、实测体感、插件生态、有哪些坑」完整讲一遍。内容基于 2026-08-13 发布到 2026-08-14 的真实操作，版本号以我实测时的 0.1.0-rc.6 为准。

反常的地方：没有 CLI，是一个 Web 服务

用惯了 Claude Code、Codex 这类终端工具，第一反应是去找 dsh 命令。装完才发现方向反了——dsh 的入口是一个常驻的 node 后台服务，真正的操作界面是浏览器。

安装只有一行：

npx @deepseek-ai/dsh web

第一次运行会自动拉取 @deepseek-ai/dsh 包，初始化 web 和 headless 两个 profile，然后起服务。启动成功的输出只有一行：dsh web: http://127.0.0.1:3080。浏览器打开这个地址，就是完整的操作界面。

想从源码跑也简单，仓库给了完整流程：

git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web

整个流程里没有全局命令、没有配置文件的折腾。数据落在 $DSH_HOME（默认 ~/.dsh），第一次启动自动生成 profiles、sessions、settings.yaml 这些目录。下面这张图是完整流程：

dsh 命令本身不是应用，是一个 launcher——它只解析自己的参数，剩下的全部交给 profile 里的应用。dsh --help 的完整能力只有三块：

dsh --profile <name> [args...]   # 启动指定 profile
dsh --patch <path>               # 追加补丁层（可重复）
dsh --dump-config                # 打印组合出的插件树，不启动
dsh --dump-default-config        # 不带用户补丁的默认树
dsh web                          # --profile web 的别名
dsh plugin --profile <name> <pnpm args>  # 转发给 pnpm 管理插件

参数分界很有意思：launcher 认自己的 flags，遇到的第一个不认识的分词，后面全是应用的参数。所以 dsh --profile web --port 8080 里 --port 是 web 应用的，dsh --profile headless "run the tests" 里引号里的是 headless 的任务。

这个设计让「换 profile 就是换一套界面」成了可能——同一棵树，web 套浏览器 UI，headless 套一次性 runner，以后想接 TUI 只需要装个插件。

打开浏览器，dsh 先弹一个「Internal Testing Notice」，直说 0.1 还在测试期、核心插件和基础 API 会在未来几个月快速演进。接着要求配置 DeepSeek API key——官方 provider 叫 deepseek-official，也可以点「Configure later」跳过。跳过之后进主界面，选一个 workspace 目录，就能发消息了。

https://github.com/deepseek-ai/deepseek-harness 的 README 和官方文档 Web UI 指南 都有完整说明。我先不展开界面细节，因为界面本身不是重点——重点是它背后那套插件架构。

「一切皆插件」拆开看：没有特权的内核

dsh 的架构核心是 Cordis，一个插件化框架，设计源自一篇讲「时空可组合性」的论文。一句话概括它的做法：运行中的 dsh 是一棵启动时组合出来的插件树，没有一块代码是「特权核心」。模型适配器是插件，工具注册表是插件，会话日志是插件，连 agent 主循环本身都是插件。

这意味着两件事。第一，任何一块都能从配置里替换——不用改源码，不用等官方发版。第二，插件注册的效果在卸载时会自动撤销，不会留残留。想扩展 dsh，不是往内核里加代码，而是在插件树旁边再挂一个插件。

组合的方式是三层结构：bundle → profile → patch。

  • bundle 是插件配置的分发格式。官方内置三个：dsh-base（模型适配、工具、会话、沙箱、权限、存储、遥测，每个 profile 的第一层）、dsh-web-app（浏览器应用）、dsh-headless（无服务器的一次性 runner）。
  • profile 是命名组合，存在 $DSH_HOME/profiles/<name> 下。web 和 headless 是出厂自带的两个模板。profile 目录里一个 package.json 声明要叠哪些 bundle，一个 cordis.patch.yml 是用户自己的补丁层。
  • patch 是覆盖机制。按插件 id 替换整段配置，或者插入新的配置行。补丁按顺序叠加：profile 的 patch → 全局 $DSH_HOME/cordis.patch.yml → 命令行 --patch 覆盖。

这套设计的好处是 dsh 命令本身可以非常薄。dsh web 只是 --profile web 的别名，--profile headless "任务" 是跑一次就退出的无界面模式，dsh plugin 把参数转发给 pnpm 去管理 profile 里的插件。想验证你的机器实际启动了什么样的插件树，一行命令：

dsh --profile web --dump-config

我跑出来的配置树 490 行，每层来源标得清清楚楚——哪行来自 dsh-base，哪行被 dsh-web-app 打过补丁。默认配置里能看到不少细节，比如 agent-default-model 默认指向 deepseek-v4-flash，会话持久化走 JSONL，存在 $DSH_HOME/sessions 下。

profile 目录的实际内容也印证了这套分层。~/.dsh/profiles/web/ 下有四个文件：cordis.yml（组合出的最终配置）、cordis.patch.yml（用户补丁层）、package.json（声明 bundles 和额外插件依赖）、pnpm-workspace.yaml。也就是说，一个 profile 就是一个可独立 pnpm install 的插件工程——装第三方插件就是往这个目录里加依赖。

事件的三种用途：扩展点比配置更底层

patch 能改配置，但插件之间怎么协作？答案在事件系统。dsh 的架构文档把事件分成三类，用途完全不同：

  • 会话事件（session/*）是持久事实，追加进日志并广播，重载后还在——会话怎么开始的、每一步模型输出了什么，都走这里。
  • Agent 事件（agent/*）携带活的 Agent 对象，用来观察或拦截进行中的工作——收到指令、开始步骤、请求模型、校验、继续，每个环节都有事件。
  • 能力事件（fs/*、tools/*、telemetry/*）把策略和适配器挂到固定接缝上，不用碰主循环。

配图和插件的语义在这里统一了：扩展 dsh 的两种姿势，要么 patch 改配置，要么监听/发事件改行为。而每一步（step）的定义也很工程化——一次模型请求加它调用的工具算一步，一个回合（turn）是零到多步，从第一个输入被认领开始，到没有欠账为止。

为什么选 Cordis：先有论文，后有框架

dsh 的插件系统不是自研的，基于 Cordis（cordiverse/cordis），设计出处是一篇论文《A Programming Paradigm for Spatiotemporal Composability》。选一个学术界出身的插件框架当底座，而不是自研一套，这个决定本身值得说两句。

Cordis 的核心主张是「注册即效果」：插件向共享上下文贡献服务、类型化事件、可撤销的效果，卸载时全部回滚。这解决了 Agent harness 里最麻烦的问题——运行时动态增删能力而不留脏状态。对话中间装个插件、用完卸载，会话还能继续跑。自研要达到这个效果，要么做一堆约束声明，要么靠约定，而 Cordis 已经把机制做完了。

实测：133 个插件挂载，界面像一个 IDE

跳过 API key 之后，主界面长这样：左侧是会话列表和 workspace 管理，中间是对话区，右侧（或者顶部，取决于布局）是预览区。选好 workspace 前，发送按钮是禁用的——这是一个「先选项目再干活」的设计。

设置页有四个 tab：General、Models、Plugins、Agent presets。

  • General：Agent 预设（Standard mode）、默认权限模式（Workspace Write）、语言、外观主题、回车行为（队列还是打断）。
  • Models：官方 DeepSeek 卡片，填 API key 即用；「Add provider」里是 Anthropic、OpenAI 这类目录内 provider；「Add a custom provider」给自建网关、内网模型服务用，支持任意 OpenAI-compatible 协议。模型支持 Bedrock、Vertex、Azure、Codex 的原生鉴权，不只是一张 API key。
  • Plugins：两个 tab。「Plugin configuration」里能改 Shell（限制 agent 跑的命令）、Agent loop（调度工具调用的方式）、Web search（DeepSeek 搜索 provider）这些插件的配置；「Plugin list」是完整清单。
  • Agent presets：预设组合，新会话默认继承，运行中的会话保留启动时的预设。

Models 页是模型接入的门面，值得单独看：

「Add a custom provider」的表单字段是 Provider ID、显示名、Base URL、API 协议、凭据、至少一个模型。其中 Provider ID 是永久的——请求、已存会话、模型默认值、凭据引用都拿它当键，想改名只能新建一个再删旧的。

目录内的 provider 还有「Fetch available models」按钮，直接调 OpenAI-compatible 的 GET /models 拉模型清单，不用手敲。手敲的模型默认按纯文本处理，要支持图片得在 $DSH_HOME/settings.yaml 里给模型加 input: [text, image]——这个粒度细到按模型配多模态，也是插件化思维的表现。

Plugin list 打开那一刻是最直观的「一切皆插件」：133 个插件，从 llm、agent、session、tools 到 typert-registry、session-persistence-jsonl、session-query-sqlite、session-telemetry-otel，全部以「Mounted, Enabled」状态挂在树上。

连会话查询（SQLite）、遥测导出（OpenTelemetry）都是插件——这就是把 Agent harness 里你能想到的每一块能力都插件化的样子。

凭据处理也做得比较仔细：API key 是只写的，保存后界面只显示脱敏描述符，真实密钥落在 $DSH_HOME/.credentials.yaml，settings 里只存引用。

会话数据是我比较在意的一块，因为它直接决定工作成果能不能带走。实测 ~/.dsh 的落盘结构：

~/.dsh/
├── profiles/
│   ├── web/          # cordis.yml + cordis.patch.yml + package.json
│   └── headless/     # 同上，无 UI 的一次性 runner
├── sessions/         # JSONL 会话日志
├── storages/         # 存储数据
└── settings.yaml

会话是 append-only 的 JSONL 事件流——每次模型请求、每步工具调用都是日志里的一个事件。这个格式的实用价值在于：JSONL 是纯文本，可以 grep、可以写脚本分析、可以进版本管理。对比一下，Claude Code 的会话是私有格式，导出还要靠工具。

dsh 把「会话可导出」做成了核心设计（官方还内置 session-persistence-jsonl 插件），对想拿真实数据做分析的人很友好——我写 《AI 研发效率账本》 时就在数据采集上花过功夫，这种设计能省不少事。

https://github.com/deepseek-ai/deepseek-harness/tree/main/docs/user/guide/index.md 的 Web UI 指南确认了流程：模型配置即时生效不用重启，选 workspace 后 agent 可以读改文件、跑命令、委派子任务，操作前按权限策略请求批准。

权限和运行轨迹：两个工程化细节

权限模式默认是「Workspace Write」——agent 能读能写 workspace 内的文件，跑命令、改外部路径这类操作按策略请求批准。这个默认值选得克制：能干活，但不会乱动 workspace 之外的东西。设置里还能切换更严的模式，对应不同信任等级的任务。

运行轨迹是 dsh 面向「观察 agent 在干什么」的设计：每次模型请求、每步工具调用都会进入会话事件流，Web UI 能实时看。对比终端工具只能在滚动输出里追日志，Web 界面把轮次、时长、token 速度、缓存命中率这些指标做成常驻状态栏，agent 干活的过程是可视化而不是黑盒。这对调试复杂任务（agent 为什么绕路、哪步卡住）比终端舒服——长任务跑到十几轮的时候，有个仪表盘和翻终端日志是两种体验。

真实任务实测：headless 模式完整跑通

测试环境是 headless 模式加 DEEPSEEK_API_KEY 环境变量——dsh 支持两种存 key 的方式，环境变量适合脚本场景，Web 页面写入适合交互场景。没配 key 时的报错值得看，它把凭据体系讲透了：

dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route
"deepseek-official"; store DEEPSEEK_API_KEY through the credentials
service (the web Models page writes it), or export DEEPSEEK_API_KEY
in the launching environment

provider 路由（deepseek-official）和凭据分离，存 key 有两条路，这也解释了为什么 headless 和 web 能共用一套配置：凭据是全局的，跑法只是 profile 不同。

配好 key 之后跑第一个任务：

dsh --profile headless "列出当前目录的文件，并简要说明 README.md 的内容"

返回结果完整：列出了目录里的 README.md，读完后准确总结了内容。这验证了模型接入、工具注册、会话编排整条链路是通的。

第二个任务上强度——多 agent 协作：主 agent 开发一个表单网页，同时派子代理去写测试。这也是验证「Subagents 以插件形式集成」的说法是不是真的：

dsh --profile headless "开发一个表单网页：在 form-demo 目录下创建
index.html（姓名/邮箱/留言三个字段，带必填和邮箱格式校验，样式美观），
然后派一个子代理编写 Node 测试验证表单校验逻辑，最后运行测试并汇报
结果。子代理负责测试部分，你负责网页部分。"

主 agent 的计划和干活的顺序清晰可查：先 todo_write 列计划，bash 确认环境，写 validation.js（浏览器/Node 通用的校验逻辑），再写 index.html，然后调 subagent 工具把测试任务委派出去，job_output 等待子代理结果。网页部分完成后返回的中间状态是这样的：

✅ 网页部分完成：form-demo/index.html（姓名/邮箱/留言三字段 + 必填校验
   + 邮箱格式校验 + 渐变卡片式美观样式，含错误提示、成功反馈、焦点态
   与响应式）
✅ form-demo/validation.js：浏览器/Node 通用的校验逻辑，自检通过
⏳ 子代理正在编写并运行 Node 测试，待其完成后我将亲自复跑测试并汇报结果

这里有一个真实的发现：headless 是「跑完即退」的一次性会话，子代理的 240 秒等待窗口内测试没写完，会话就结束了。第二次会话补写测试并运行，结果 10/10 全部通过。这个细节说明两件事——子代理委派是真实机制（后面会话数据会看到），但长任务委派在 headless 一次性会话里可能跑不完，得给足超时或用 web 会话。

会话数据长什么样：zstd 压缩的 JSONL 事件流

任务跑完，~/.dsh/sessions/ 里多了会话文件。有个细节：落盘文件名是 session.jsonl.zstd——JSONL 事件流做了 zstd 压缩。这正好解释了 Node 版本那个坑：createZstdDecompress 是压缩会话的插件在用的 API。

解压主会话看事件流，结构跟架构文档说的一模一样，472 个事件：

session                    # 会话头：id、cwd、delegationDepth
user/message               # 用户输入
step/start × 13            # 十三个步骤
reasoning-chunks           # 模型思考过程流式输出
tool/call + tool/result    # 工具调用与结果（todo_write/bash/write/subagent…）
assistant/chunk            # 回复流式输出
assistant/message          # 最终回复
session/title              # 自动生成会话标题

两个发现值得一提。一是 session/title 自动生成标题，web 会话列表里那个「Ungrouped」下能起名字，是这个事件在起作用。

二是多 agent 委派在会话数据里的样子——主会话调 subagent 工具后，落盘了一个独立的子代理会话：自己的 session id、自己的事件流，会话头 delegationDepth: 1，还有 subagent/descriptor 事件描述子代理的模式（continuable）。

sandbox/mode 和 approval/policy 两个事件都标注 source: 'delegation'——子代理不是主会话里的一段记录，是一个继承了沙箱和权限策略的独立 Agent，跑完把结果通过 job_output 送回主会话。多 Agent 委派是底层设计而非插件补丁，这句话在数据层面坐实了。

微信上那篇《DeepSeek Harness震撼发布，一切皆插件》提到的点，我逐条验证过：npx 安装、node 后台服务 + Web 前端、Cordis 插件系统、MCP/Skills/Subagents/Loop 以插件形式集成、会话数据 JSONL 导出——全部属实。

它说「速度飞快，运行轨迹公开给用户看，底部状态栏显示运行轮次、LLM 与工具调用时长、token 输出速度、缓存命中比例」，状态栏在 UI 里是存在的，会话事件流里每一步也确实可追踪。它自己都说了「容我这两天深度测试再写一篇」，我这边把该测的测完了，下面展开。

和 Claude Code、Codex 摆在一起比

用了一整年 Claude Code，dsh 给我的第一感觉是「同一个家族的不同物种」。直接对比一下：

维度Claude Code / Codexdsh
形态终端 CLI，cd 进目录即用node 后台服务 + 浏览器 UI
扩展内置功能 + MCP/Skills 外挂一切皆插件，模型/工具/会话/UI 全可替换
模型接入官方模型为主，切换要配置多 provider 目录 + 任意 OpenAI-compatible

这张表的落点是定位差异：Claude Code 是「把一件事做到极致的产品」，dsh 是「让你自己组装 Agent 的平台」。前者的承诺是开箱即用，后者的承诺是万物可换。我日常依赖 Claude Code 的闭环流程——《改一行代码别上重型流程》 里那套 SKILL 体系，就是建立在「harness 稳定、接口不变」的前提上。dsh 现在给不了这个前提，但它指出了另一条路：当 harness 本身可替换时，工程自律可以焊得更深。

headless 模式是现在就能直接用的场景：dsh --profile headless "任务" 跑完即退，输出最终答案，配合 DEEPSEEK_API_KEY 环境变量，适合塞进 CI、脚本、定时任务——不用开浏览器，不占常驻端口。

写个 cron 夜间跑 Agent 巡检（《夜间巡检 daemon》 那种活），dsh 是一个比 Claude Code 更轻的选项——它没有交互终端的状态负担，天生就是服务形态。我实测的表单开发任务就是这种用法：一条命令，任务跑完，产物落盘，会话留档。

插件生态：发布 12 小时，275 个仓库

「一切皆插件」的承诺兑现到什么程度，看生态比看架构文档更直接。2026-08-13 晚（发布 12 小时内）的数据：GitHub dsh-plugin 话题下有 15 个直接命中的仓库。

社区维护的 awesome-dsh-plugins 目录（带每日兼容性追踪）收录了约 275 个仓库——单插件 195、基础设施 35、插件集 17、技能 12、远程渠道 7、研究 5。发布 12 小时就有这个密度，速度远超预期。

Hacker News 在 2026-08-13 当天把这个项目顶到 #1，讨论焦点除了架构就是「Every Run is Traceable」——append-only 会话日志让每次运行的 system prompt、推理、工具调用、子代理调度都能回放。这个特性在实测里是真实的：我解压的会话事件流完整记录了每个步骤。

我实测了插件安装：一条命令，12 秒挂载

插件安装走 dsh plugin 命令，它把参数转发给 profile 目录里的 pnpm。实测装一个 JSON 查询工具：

dsh plugin --profile web add "github:dsh-external/dsh-tool-json#main"

12 秒装完。装完看 ~/.dsh/profiles/web/package.json，变化一目了然——依赖表里加了 @deepseek-ai/dsh-tool-json，dsh.profile.bundles 列表里追加了同一个名字。这个设计把「插件」和「bundle」统一了：一个第三方仓库就是一个 bundle，装进 profile 即成为插件树的一层。

重启 dsh web 后 --dump-config 里出现了新的一节：

# == @deepseek-ai/dsh-tool-json
- id: tool-json
  name: '@deepseek-ai/dsh-tool-json'

从安装到挂载的闭环完整可用。有个小提醒：装的时候报了 peer 依赖缺失（cordis、dsh-tools 的 rc 版本），这是 dsh 快速迭代期的正常现象，装完能跑就行。

三个坑：Node 版本、预览期、生态爆发期

坑一：Node 版本有硬门槛，v22.13 直接起不来

这是我最先踩的。本机 Node v22.13.0，npx @deepseek-ai/dsh web 启动直接崩：

Error: dsh: plugin tree failed to load: failed to apply loader entry
include (cordis:include): failed to import loader entry
session-persistence-jsonl (@deepseek-ai/dsh-session-persistence-jsonl):
The requested module 'node:zlib' does not provide an export named
'createZstdDecompress'

createZstdDecompress 是 Node 22.14 才加入 node:zlib 的 API，会话 JSONL 持久化插件用了 zstd 压缩。npx 安装时其实已经给了提示——@earendil-works/pi-ai 要求 node >=22.19.0，当时没当回事。切到 Node 24.14.0 后一切正常。

结论很明确：跑 dsh 需要 Node 22.14+，建议直接上 24 LTS。如果你用 nvm 管理版本，nvm install 24 切过去就行。这个坑在新手期几乎是必踩的，因为报错信息跟 Node 版本毫无关系，只在插件加载那一步炸开。

坑二：官方明说了会有破坏性变更

README 第一屏就是开发者预览声明：「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」。npm 上这个包 2026-08-10 才发第一个 rc，到 2026-08-13 已经发了 6 个版本——0.0.1-rc.1 到 0.1.0-rc.6，3 天迭代 6 轮。这意味着现在学的配置写法，下个 rc 可能就变了。

给插件开发者的信号更直接：--dump-default-config 和 --dump-config 的输出格式、patch 的写法、事件的命名，都在快速变动。写插件可以，别指望长期稳定。

坑三：生态爆发期，质量参差、兼容性不稳

275 个仓库看着热闹，但里面混着不少「一天写的玩具」——dsh-ads 是给 Web UI 加 2005 年风格广告的整活，dsh-stock-market 的卖点是「写代码的时候账户不能同时亏钱」。装插件前要看清两点：仓库有没有维护动作，作者有没有说明适配的 dsh 版本。

awesome-dsh-plugins 自己都声明：收录不等于兼容，静态检查不等于运行可用，运行可用不等于安全审计。插件可以读写你的文件、跑命令、连网络，装第三方插件前过一遍源码是基本动作。我实测装插件时遇到的 peer 依赖缺失就是征兆——rc 阶段的包依赖变动很快，插件装完过几天就可能缺依赖。

还有一个务实的坑：中文资料依然稀缺，文档全英文，排错靠 GitHub Discussions。微信上那篇 555 字的预告文是早期中文圈信息量最大的一篇。

现在多了 dsh-handbook（新手教程白皮书）和 dsh-plugin-guide（插件开发指南）这类社区文档，比 2026-08-13 发布当天好多了。

我的建议是装的时候把 Web UI 指南 和 架构文档 两个页面开着，报错直接对着文档查，比搜引擎快。

另外提醒一个形态差异：dsh 的 workspace 选择走系统目录选择器，CLI 老兵如果期待「cd 进目录就能用」，会不习惯。它更像一个常驻的本地服务，配合浏览器使用。

心智模型：Agent 工具链的三段演进

把 dsh 放进时间线看，Agent 工具链的形态演进其实很清晰：

第一阶段是单体 CLI。 Claude Code、Codex 把模型接入、工具、会话、权限全部内置，功能靠版本迭代堆。能力很强，但用户想改任何一块都要等官方发版，私有化定制几乎不可能。

第二阶段是协议外挂。 MCP 把工具接入标准化，Skills 把提示工程包成可复用资产。能力可以外接了，但 harness 本身还是封闭单体——模型选择、会话管理、agent 循环这些核心，用户依然碰不到。

第三阶段就是插件化平台。 dsh 把「核心」这个词删掉了。模型、工具、技能、会话、沙箱、存储、循环、调度、UI，全是插件，全可替换。harness 从「产品」变成了「平台」，内核只做一件事——让所有能力都能被替换。

这套演进的驱动力是现实的：我的 Agent 工作流里，把工具、技能、模型换来换去是常态，而每次换都要跟 harness 的封闭结构较劲。上一篇文章里我把这一年的工程实践总结成「给大模型装操作系统」——harness 层管的就是进程调度和系统调用。dsh 把这个比喻再推进一步：它把「操作系统」本身做成可插拔的，内核小到几乎没有。

回到模型这一侧，dsh 默认模型是 deepseek-v4-flash，官方适配自己的模型是顺理成章的事。我在 《DeepSeek 便宜到骨折还拿了世界第二》 里聊过 V4 Flash 的编程能力——模型是第一梯队，现在配套的 harness 也开源了，DeepSeek 在走「模型 + 工具链」整条链路。

模型厂商为什么做 Agent 工具链

过去一年 Agent 工具链是 Anthropic、OpenAI、Google 这些大厂的战场，DeepSeek 的强项一直在模型本身。这次下场做 harness，我有三层理解。

第一层是产品适配。模型厂商做工具链，能把模型的能力边界吃透——V4 Flash 擅长什么、什么场景要换更大模型、思考预算怎么调，这些只有自己的 harness 能调到最优。第三方工具链对各家模型是一视同仁的，厂商自己做的能偏袒自家模型。

第二层是数据回馈。Agent harness 是模型真实使用的入口，运行轨迹、工具调用成功率、用户怎么改 prompt，这些数据对模型迭代是金矿。开源 harness 意味着全世界的开发者帮你产生真实使用数据，这在数据是核心资产的行业里，是战略级的投入。

第三层是生态占位。Agent 工具链的格局还没定，插件生态的入口效应一旦形成，后来者很难翻盘。dsh 的插件机制、dsh-plugin 话题、Discord 社区，都是提前占住「Agent 插件平台」这个生态位。MIT 协议 + 论文级架构文档，摆明了是奔着事实标准去的。

这三层叠加，结论是我在文章开头那句判断的注脚：dsh 不是 DeepSeek 的玩具项目，是「模型 + 工具链」战略的一块拼图。对开发者来说，多一个真金白银投入的 Agent 平台是好事——竞争会让每个工具都更好用。

我的判断：现在该做什么

dsh 2026-08-13 发布当天就逼近 3 万 star，说明市场对「插件化 Agent 平台」这个方向有真实需求，不只是 DeepSeek 在推。它的架构把 Agent harness 的扩展成本从「等官方」降到了「自己挂插件」，这个方向我认。

但三个现实问题摆在这：Node 版本门槛会劝退一部分人，开发者预览期的破坏性变更意味着学习成果可能作废，插件生态刚爆发、质量参差意味着选型要自己把关。这三条加在一起，我的做法是：装好它、跑通它、看懂它的插件树，插件挑着装，但不把生产工作流迁过去。

什么时候值得重新评估？2026-08-13 发布当天我给自己定了三个信号：一是 dsh-plugin 生态出现能直接用的第三方插件，二是官方宣布插件 API 稳定、不再破坏性变更，三是 headless 在 CI 场景跑出真实案例。发布首日实测让我先划掉一个——插件生态这个信号已经亮了，275 个仓库摆在那，TUI、记忆、浏览器操控这些痛点都有人接。剩下两个信号（API 稳定、CI 案例）出现了，就值得再花半天认真试一遍。

值得持续关注的点是它的插件机制会不会成为事实标准——如果 dsh-plugin 生态长起来，Agent 工具链的选型逻辑会从「选哪个 CLI」变成「选哪个平台」。到那时候，这篇实测就是见证起点的一篇。我对 dsh 的架构文档 的评价是：一个开源项目把架构文档写到这个粒度，至少说明团队是把这事当长期工程做的，不是蹭热点。
