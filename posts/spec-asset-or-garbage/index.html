18 份归档 spec 的两种寿命：AI 编程时代怎么决定文档去留

上周末清理文档目录，我数了一下仓库归档区：18 份 spec，最早的一份是几个月前的一次管线重构，最新的还带着上周的日期。清理过程颇为狼狈：有两份相邻变更的 proposal 内容八成重合，分不清哪份是最终版；有一份过程稿记录的方案早就被推翻，却在地窖里躺了三个月，任何人看了都会被它误导；还有几份只有半页，写到验收就断了，连当时为什么停笔都想不起来。我几乎从不回看这些文档，但每次开新变更，我依然规规矩矩先写 proposal 再动手。

写的时候视若珍宝，写完束之高阁。这两件事同时成立，说明我对 spec 的写作标准和留存标准根本不是一套。是我在形式主义，还是归档区里躺着的真的是资产？把这个问题想透花了我一点时间，结论值得写下来：spec 有两种寿命，一种活在写的过程，一种活在后续的读者手里。两种都合法，混着用才是灾难。

一、spec 到底解决什么问题

先退回到最朴素的场景。没有 spec 的开发长什么样：脑子里有个方向，开口说个大概，AI 动手，做到一半发现理解偏了，纠正，再偏，再纠正。小改动两轮收敛，大改动能来回一下午，最后交付物和最初嘴上说的那个东西已经是两回事。

三个老问题反复出现。上下文是半成品的：你脑子里那幅完整图景，对方只拿到口头的一角。口径是漂移的：第一轮说的「简单做一下」和第三轮理解出的边界，中间隔了无数次即兴补充。验收靠回忆：做完了对不对，全凭双方各自记得当初说了什么，而记忆是不可靠的。

spec 是给这三个问题的同一个答案：把「想清楚」外化成一份双方都能引用的文本。需求方写下来的过程会逼自己补上跳掉的步骤；AI 拿到完整输入；验收时逐条对照，不靠回忆。

有人会问，这些坑 AI 之前也存在，为什么没见人人手一份 spec？因为口头校正曾经很便宜：会议室、白板、工位上喊一嗓子，五秒钟修正一次理解，写文档的时间成本远高于收益。AI 时代供需反转了，校正变贵了：每一轮对话都有延迟和 token 成本，模型还不会主动追问，你不说它就猜。当修正一次理解的价格高于写下一次理解的价格，spec 就从仪式变成了刚需。

AI 编程把这件事的权重放大了。以前的「对方」是同事，还有频繁的口头校正兜着；现在的对方是模型，每次会话都是新人，没有记忆继承，输入质量直接决定输出质量。模型落笔的能力越强，需求的模糊就越成为瓶颈，这也是近两年 spec 驱动开发忽然人人都在谈的原因：不是理念变新了，是执行端变强了，供应端的模糊成了新的短板。

顺便划清一个容易混淆的界线：spec 和笔记不是一回事。笔记是思考的草稿，允许混乱、允许未收敛；spec 是承诺的载体，每一个句子都会被当成「已经确认的事实」去执行。把自己的思考笔记直接丢给模型当需求，是新手最常见的错误之一。模型不会替你区分哪些是结论、哪些是还没想完的中间态。

二、立场光谱：三种做法各有各的理

观察身边的团队和公开的工程实践，对 spec 的态度大致站成三派，谁也说服不了谁。

一派可以叫删光派：spec 是脚手架，楼盖起来就该拆。他们的仓库里代码之外几乎不留过程文档，写完即弃，理由是文档和代码天然会分叉，留一份过期的文档比留空白更危险。

另一派是轻量派：spec 要有，但重流程必死。他们用最简的文件命名约定跑状态机，文件名前缀就是阶段，改一个字也要走的流程和跨系统的需求走同一套，方法是把仪式感压到零。

第三派是地基派：spec 是共识资产，是整套工程方法的第一块基石。他们的经验是纪律必须先达成共识，没有一份彼此认可的设计文档，后面的自动化工具会被搭歪，返工的成本远超写文档的时间。

三派看起来水火不容，我在自己的仓库里把三种都试过之后发现，他们吵的从来不是同一个问题。删光派谈的是「写完之后文档还有什么价值」，地基派谈的是「动手之前如何强迫共识」，轻量派谈的是「中间过程如何不压垮执行」。各自都对，混着谈才吵。

换个视角看更清楚：三派各自守着文档生命周期的不同阶段。地基派守写前，共识不达成不动手；轻量派守写中，过程不添堵；删光派守写后，垃圾不清走。一份 spec 从诞生到死亡要经过全部三段，三派把每一段的极端化主张各拿了一个。所以我后来不再问「该信哪一派」，改问「这份文档现在处于哪一段」。三派还有一个共同的盲区值得点破：它们都把「文档」当主语，谈的是文档该不该存在，读者只是被动接受方。而真正决定文档命运的是读者，谁在读、什么时候读、读它解决什么问题。把读者放回主语，很多争论会自动消解。

三、核心模型：spec 的两种寿命

把三派的分歧拆到最小单位，我得到一个模型：spec 有两种寿命。

第一种是过程稿。它的使命发生在写的过程中：逼你把模糊的想法变成清晰的句子，把跳掉的步骤补上，把自以为想清楚的地方暴露出来。写完的那一刻，它的使命已经完成了。它关于「将要发生的事」，而一旦事情发生，它记录的方案细节随时可能被现实修正。这种 spec 的自然结局是被替换、被删除，删了项目照跑，因为它承载的价值，也就是想清楚这个过程，已经兑现进代码和你的脑子里。

第二种是设计说明。它关于「已经存在的事」：这块代码为什么这样设计，当初考虑过哪些方案，哪些坑已经踩过。它的读者是下一个要改这块代码的人，也可能是未来完全失忆的你自己，或者是每次会话都从零开始的 AI。它的自然结局是跟着代码走，代码在它在，代码改它跟着改。

两种 spec 长得几乎一样，都是 Markdown 文件，都有小节和验收项，躺在同一个目录里。寿命完全不同：前者是耗材，用完即弃；后者是资产，跟代码同生共死。

灾难发生在把两者混用的时刻。把过程稿当资产留下来，仓库里堆满和现实分叉的过期方案，误导每一个信它的读者；把设计说明当耗材随手扔，下一个改代码的人从零考古，AI 每次都把已经踩过的坑重新踩一次。判断一份文档的去留，第一个问题不是「写得好不好」，是「它是哪一种寿命」。

两种寿命之间还存在一条单行道：过程稿可以在项目结束时「转正」为设计说明。做法是把时态从将来时改成过去时，把「计划怎么做」改写成「实际怎么做的、中途改了哪些决定、为什么」，删掉那些被现实推翻的部分。转正的判据就一条：内容描述的是事实而非意图。没经过这一步转正的草稿，永远按耗材对待；转正过的，按资产养。我仓库里那 18 份归档，清理时按这条线一划，哪些留哪些删几乎不需要犹豫。

四、AI 带来了第三个读者

传统语境里 spec 的读者是人：协作者、评审、接手的新人。AI 编程加了一个字面意义上的读者：模型。这个读者有三个特点，直接改变了 spec 的写法。

它没有记忆继承，每次会话都是陌生人，你三个月前口头上补充过的边界，它永远不知道。它不理解言外之意，「简单处理一下」这种人类黑话会被字面执行。它的窗口有限，一份塞满无关信息的 spec 会挤占真正需要的上下文。

所以给 AI 读的 spec 需要明确的骨架，我的模板是六节：

背景与问题，两三句讲清为什么做这件事，让模型知道上下文从哪来。目标，做成什么样算完成，写成可判定的陈述。非目标与边界，同样重要：明确不做什么，防止模型自作主张扩大战果，这是实战里最贵的错误。验收标准，每一条都要能变成一次运行、一个命令、一个退出码，写不成的说明你自己还没想清楚。禁止事项，这个项目的红线，比如不许动某个目录、不许引入新依赖。开放问题，还没想清楚的地方明说，让模型把它当变量，不许自行填空。

六节骨架是上限，不是起点。小需求三节就够：目标、边界、验收，写清这三样模型就能干活，硬凑六节反而稀释重点。模板服务你，不是你服务模板，判断标准永远是「这一节帮模型避开了哪类猜错」，答不上来的节直接删。配套的是状态机。我的做法是文件名即状态：草稿期带 draft 前缀，方案敲定改成 ready，做完挪进归档目录。状态写在文件名里，不写进文档内容，好处有三个：机器一眼可查，ls 就能列出所有待办和已完成；不依赖任何人的记忆，离开三个月回来状态依然一目了然；防止跳步，没有 ready 前缀的文档不许开工，规则简单到没有解释空间。

目录约定同样从简：进行区一个目录，归档区一个目录，归档文件名带日期。AI 拿到一份 ready 文档，就有了完整且经过确认的需求上下文，不需要人在对话里反复喂。

五、一次真实变更的走查

光讲模型没用，拿我自己仓库里正在进行的一个变更走一遍。它是个调研型任务：搞清楚公众号的推荐和考核机制，回答「缩短篇幅能不能换来阅读量」这个问题，结论再反哺写作规范。

为什么调研也要写 spec？因为这个问题足够容易跑偏。「怎么提高阅读量」是个开放问题，没有一份先行的 proposal 圈定范围，调研会变成无限刷帖，看到什么证据都觉得有理。所以先写三块：要回答的具体问题是什么（推荐机制、考核指标、篇幅与阅读量的关系，一张三个子问题的清单）、证据从哪来（运营圈的公开实测、平台官方口径，来源在开工前列好）、结论落成什么形态（写作规范里的三条修订，写明改哪个文件的哪一节）。

最有价值的是最后那个容易被忽略的小节：失败条件。什么情况说明调研该停？如果公开来源查不到可交叉验证的考核口径，就承认拿不到一手证据，结论降级为「运营圈共识汇编」并标注可信度，别再继续烧时间。给失败留一个明确的出口，是对抗「沉没成本式调研」的唯一有效手段；这类约束靠对话里的自觉几乎守不住，落在文档里才立得住。顺带说清调研型 spec 和实现型 spec 的差别：实现型的验收是测试、构建、退出码，全部可以自动化判定；调研型的验收是「结论落进了哪个文件的哪一节」，落了就是落了，没落就是没落。形式不同，标准相同：验收必须可判定，判定不了的条目没有资格待在验收区。

这份 spec 现在还躺在未归档目录里，它属于过程稿的寿命：调研结论一旦落进写作规范，这份文档的历史使命就结束了。但它大概率不会被删，因为归档之后它还有两种再开的时机：半年后有人质疑「为什么规范里写完读率优先」，答案在归档里；下次做同类调研，这份 proposal 的结构和证据清单能直接复用；以及交接给未来的自己，彼时的我对这件事的记忆是零。三种再开时机没有一种需要提前规划，它们是归档这个动作自带的期权：留存一份文档的成本是几 KB 磁盘，换来的是三种可能性，这是我见过性价比最高的保险。

这个案例也说明两种寿命不对应两种文件，同一份 spec 可以先用第一种寿命，再用第二种。判断的关键从来不是删还是留，是清不清楚它此刻在服务谁。

六、反模式集：四种病与病理

反模式比正面案例更有教育意义，四种常见病，每一种我都在自己或别人身上见过。

第一种，文档表演。为了流程写 spec，写了没人读，归档没人查，模板越做越精致，内容越写越空洞。病理是把写 spec 当成了交付物，它只是过程产物。判别方法很简单：问一句「这份 spec 上次被谁读过」，答案是没有，就是表演。我自己就产出过这种表演品：早期学流程的时候，为两个小改动硬套了完整模板，背景、里程碑、风险评估一节不落，写完连自己都没再打开过。那两份文档唯一的产出，是让我明白了模板可以服务文档，也可以杀死文档。

第二种，过期地图。设计说明不跟着代码更新，三个月后就从资产变成负债。地图过期的危险在于它不表现为缺失，表现为自信的错误指引：读者（包括 AI）拿到一份言之凿凿的旧文档，只会沿着错路走得更快。空白只是慢，误导才致命。让设计说明跟上代码，靠的不是定期重写，是把文档维护嵌进改代码的流程：每处理完一次事故、每定下一条新规矩，顺手把它写进对应的文档，几行的事。我维护得最勤的一份技能文档就是这样长起来的，几十个事故条目全是事后几分钟补的，从来没有专门抽时间「整理文档」，它却是全仓库被引用最多的一份。

第三种，拿 spec 当评分表。把验收标准写成模糊的语义描述，然后指望对着它逐条给产出打分，尤其是让另一个模型来打分。语义判分的误差往往大于信号本身，同一份产物换个裁判能差出几个等级。验收判据必须可执行：一条命令、一个脚本、一个退出码，写不成这样就从 spec 里拿掉，那种条目本来就不该出现在验收区。

第四种，巨型 spec。一个文档想装下一个季度的所有规划，主题越堆越多，最后每个主题都只写了半句。判据是主题数量：几个独立主题装不进一篇，就拆成系列，每份 spec 只服务一个清晰的问题。拆分的 pain 远小于混装的痛。

四种病各配一个判别动作，成本都很低。防表演：归档前问「这份文档上次被谁读过」。防过期地图：每次改代码顺手问「这次改动让哪些文档失真了」，和跑测试放在同一个习惯里。防评分表：写验收标准时当场跑一遍判据命令，跑不成的当场改写。防巨型：数主题，超过一个独立主题就当场拆文件。习惯成自然之后，这些动作加起来每次不到一分钟，却能把四种病挡在进仓之前。

七、删与留：三条标准与一条边界

回到开头那 18 份归档。我现在清理它们只看三个问题：流程还在引用它吗，AI 还在读它吗，删了会不会有人来问「当初为什么这么做」。三个都是否，删；任何一个是有，留，并顺手检查它是否还和现实一致。实操上我在归档区维护一份索引，一行一份记录三个字段：变更名、寿命类型、再开价值。清理时按索引过一遍，十分钟清完一季；没有索引的归档区不是知识库，是坟场，每次进去都得重新考古。

边界也要说清。探索期的小改动，不值得写 spec，一段对话加两行注释足够，仪式感会杀死灵感；成熟期的大改动，没有 spec 直接动手，返工成本会指数级超过写文档的时间。判断量级的能力，比掌握任何模板都重要。一个可操作的粗判：这次改动如果失败，重来一次的成本低于半小时，属于小；失败要牵连别的系统、要回滚数据、要向别人解释，属于大。小的不写，大的不省，中间地带凭手感，手感来自每次变更后回看当初的判断准不准。

还有一条经验性的边界：spec 的收益在写的过程里就兑现了大半。哪怕写完就扔，写的过程中被迫补齐的思考也不会浪费。所以不要因为「反正要删」就不写，也不要因为「写了就舍不得删」而留一堆过期稿。写，认真地写；写完，冷静地分类。

回到开头的问题。18 份归档 spec 不是资产也不是垃圾，它们只是各自站在自己的寿命里：有的还在服务下一次变更和未来的我，有的只剩审计价值，有的早就该清走了。那次清理的最后，我把留下的每一份都做了转正补记，把扔掉的每一份都问了一遍当初为什么没转正——答案清一色是「方案没落地就变了」，这正是过程稿该有的死法，没什么可惜。文档的去留从来不看它写得好不好，看它还有没有读者。下一份 spec 落笔之前，先想清楚它服务的是哪一种寿命；写完之后，再问一次它该走转正还是直接退役。两个问题问完，开头那对矛盾——写作时珍重、留存时冷清——就和解了：珍重的是写的过程，冷清的是没有读者的残稿，两者本来就不冲突。
