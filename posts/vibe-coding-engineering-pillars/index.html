Claude Code 裸聊会翻车：单轮 11 倍消耗与五根工程柱子

2026-08-20 那天我翻了一张 Codex 会话账单，越翻越不对劲。54 次调用，累计输入 952 万 token，输出只有 6.6 万，输入输出比 144:1。单轮消耗从 20,611 一路涨到 226,262，一个会话之内翻了 11 倍，干的活却没变。

再往前，还有一笔更疼的。270 行并发守卫代码被一次「搜索优化」提交静默删掉，编译照样绿，没人发现。潜伏四天，大促订单超卖，又花了四天排查才把根因挖出来，详见 那次幽灵删除的完整复盘。

这两笔消耗指向同一个病根。很多人第一反应是模型不够聪明，或者提示词写得不够好，方向全偏了。模型没问题，出问题的是我把一件工程活当成了聊天：需求靠口述，规则靠临时想起，验收靠肉眼，成本靠事后惊讶。

Karpathy 把这种状态叫做 vibe coding，全凭感觉跟 AI 对话，代码哗哗地出。这个词用来形容爽感很准，用来指导干活就危险了。爽感来自「聊」，质量来自「工程」，两件事的差距就是上面那张账单和那次超卖。

这两年带着小团队用 Claude Code 交付了近百万行的多租户 SaaS，我把踩过的坑收拢成五根工程柱子：项目记忆、skill 资产、spec 契约、测试门禁、边界与成本。五根柱子的组合逻辑也简单：前两根管 AI 知不知道，第三根管干的是什么活，第四根管干得对不对，第五根管能不能干得久。每根柱子拦住哪类事故、怎么装、装晚了会缺什么，下面逐根拆开。

一、先看裸聊翻车的四种姿势

裸聊的事故看着花样繁多，归拢之后就四种。每一种我都交过学费，先摆出来，后面五根柱子逐一对应。

**姿势一：AI 不懂你家的规矩。**每个仓库都有一堆写不进代码的隐性规则。我仓库里有三个老模块按订单状态驱动，直接改状态字段会绕过佣金结算，这条规则不存在任何代码注释里。AI 每次会话都是新人，没人告诉它，它就敢直接改。部分退款改造那次，佣金多结、积分没扣、报表虚高，月底对账才炸。

**姿势二：聊天记录当需求文档。**口述的需求散落在几十条消息里，AI 记住的永远是最后一版。我说过一句「给这个接口加个缓存」，它回敬了我一整套缓存体系：多级缓存、过期策略、预热脚本，账单翻倍，而我要的只是三行代码。聊得越多，意图被稀释得越狠，最后一轮的 AI 是拿着转述了二十遍的需求在干活。

**姿势三：「看起来对」就合入。**AI 说「搞定了」的时候，它的目标函数是让验收变绿，管绿灯是真是假。我见过 178 个测试全绿、真实环境一连就崩的交付；也见过快照测试把 bug 输出固化成标准答案，从此每次都「通过」。编译能过、页面能开、测试能绿，三样加起来证明不了行为正确。

**姿势四：一把梭，没边界也没成本概念。**一个会话从早聊到晚，上下文雪球越滚越大，账单曲线就是第一节那张 11 倍的曲线。三个会话共用一个目录并行开发，互相覆盖对方的改动，git status 里全是看不懂的冲突。夜里挂个自动重试，醒来发现它把同一个错误重试了两百遍。

四种姿势对应一个共同结构：缺了某个工程件，AI 就用最自然的方式把这个洞撞开。

它们还容易被误诊成提示词问题。姿势一怪 AI 记性差，姿势二怪它不听话，姿势三怪它吹牛，姿势四怪它烧钱，于是解法永远在换模型、换提示词模板之间打转。病根其实在工程侧：聊天这个交互形态天生没有记忆、没有契约、没有验收，而这三样正是软件工程积累了五十年的存货。下一节从最便宜的那根柱子装起。

症状缺的柱子典型代价
AI 不懂规矩项目记忆隐性规则被绕过，静默改错
聊天记录当文档spec 契约意图稀释，账单翻倍
看起来对就合入测试门禁假绿灯，线上事故
一把梭无边界边界与成本会话雪球、并行互踩

二、第一根柱子：项目记忆，AGENTS.md 是员工手册

每次新会话，AI 都是一个没有记忆的实习生。AGENTS.md 就是它的员工手册，随每次请求自动进入上下文。把仓库的隐性规则、事故教训、环境坑写进去，它上岗第一分钟就知道红线在哪。

手册该写什么，我的判据只有一条：写「从代码里看不出来」的东西。订单状态驱动的老模块、租户隔离的强制条件、Windows 下 symlink 的权限坑、WSL 迁到 D 盘的历史，这些写进去都值。目录结构、框架用法这类模型自己能探索的东西，一行都别写。

手册越厚，每轮越贵。AGENTS.md 是每轮请求都重发的前缀，我那本三千字的手册在一个 54 轮的会话里重发了约 16 万 token。所以手册是骨头，只管「这个仓库永远为真」的少量硬规则，片段大致长这样：

# AGENTS.md（节选）
- 订单、结算、佣金三个老模块按订单状态驱动，改前先做影响分析
- 删除超过 50 行的 diff 必须单独说明，评审时重点标注
- 所有 SQL 必须带 tenant_id，迁移脚本禁用 MySQL 8+ 语法
- 「无法确认」是合法结论：确认不了就停下来问，别猜

最后一条是我最喜欢的。手册不止告诉它能干什么，还要给它合法的停机权利，允许说「我确认不了」，比逼它硬编一个答案便宜得多。大项目里的隐性规则管理和三会话分离，我写过专文，见大项目里 AI 静默翻车的五条纪律。

工程化的第二步是让手册不漂移。Claude Code 读 CLAUDE.md，Codex 读 AGENTS.md，一份内容写两份很快就会一处改了一处忘。我的做法是单一事实源加一行指针，双正本互指，多个 IDE 共享同一份记忆，这套接线方式见一处配置同步五个 IDE。

还有一条回写纪律：每次事故必须有产出物。修完只写复盘文档，三个月后没人看；把「别再犯」固化成手册里的一条规则或者一个 hook，才算修完。事故怎么变成规则，见事故固化成规则才拦得住。员工手册是活的，事故回写是它主要的更新来源。

手册也有三种常见的写废方式。写成了目录导览，全是模型自己扫一眼仓库就能知道的信息，白烧每轮的 token；写成了愿望清单，「代码要优雅」「注意性能」这类没有判断标准的句子，AI 读不读都一样；写成了一次性的，项目演进了半年手册一个字没动，过期的规则比没有规则更坏，AI 会拿半年前的红线拦今天的正确做法。所以手册要配复查节奏，我的习惯是每次事故复盘顺手问一句：这条教训要不要进手册。

三、第二根柱子：skill 资产，重复第三遍就入库

手册管住「这个仓库永远为真」，管不住「这类活怎么干」。每次发文章都要过一遍去 AI 味词表，每次发视频都要查四平台声明，这些流程每次口述一遍，AI 每次执行都有出入。第三遍的时候就该停下来了，把它写成 skill。

skill 和手册的分工用身体打比方就够了：AGENTS.md 是骨头，skill 是肌肉。骨头负责撑住结构性的硬规则，肌肉负责一类活的完整动作。一个 skill 通常三件事都管：输入规范（这类活要给什么材料）、过程约束（按什么顺序干、哪些不许碰）、异常处理（干不下去怎么办）。

这条柱子最容易被低估的地方是路由。skill 的 description 不是简介，是路由依据，要写场景词加时机词，AI 靠它在几百个 skill 里决定这次加载谁。

写不好 description 的 skill 等于没写，要么永不被触发，要么乱触发。我自己从零写第一个 skill 的完整过程，包括怎么迭代词表和扫描脚本，见收藏 80 个 skill 不如写 1 个。

数量按仓库的历史风险点定，不按热度榜单定，多租户仓库就在租户隔离上加肌肉，迁移频繁的仓库就在 schema 治理上加肌肉。什么时候不该写成 skill 也要有判据：只会在某个特定任务里用一次的流程，写在任务的 prompt 里就够；依赖外部服务状态的活，先看有没有更稳的通道，skill 管流程不管通道。

还有一个供应链细节：skill 来源要锁。我的自研 skill 全部走 git submodule 挂进仓库，skills-lock.json 记来源和哈希，上游变更先验哈希再生效，防止上游仓库哪天没了或者被人推了恶意提交。我的主力仓库长期维持在一百个上下，托住了近百万行的交付，经验写在百万行代码没这 100 个 skill 会翻车。命令是 skill 的近亲，把流程契约化，31 条命令锁死了 3 人两月交付 512 个功能点的纪律，那是另一篇命令体系的主线。

跳过这根柱子的代价很具体：同一类错误反复发生，每一次都像第一次。skill 资产的意义在于让纠正只发生一次，之后由机器保证执行。

四、第三根柱子：spec 契约，聊天记录当不了需求文档

前两根柱子解决「AI 知不知道」，这根解决「AI 干的是什么活」。聊天话术天然是模糊的，「加个缓存」「优化一下」「参考那个页面」，每个词都留了解释空间。AI 会选一个解释继续干，选错的成本由你的账单支付。

我的定规是 plan-first：动手之前先出计划，人确认了再写代码。这一步看起来慢，实际是全文最省钱的一步，因为它把「发现理解错了」从第 40 轮提前到第 1 轮。有一次我提了个加缓存的需求，计划阶段的追问直接把它问没了：读多写少才值得缓存，这个接口写多读少。口头聊天阶段我永远不会发现这一点。

正经的做法是把意图升格成 spec，四个件配齐：proposal 讲为什么做，spec 讲做成什么样，design 讲怎么做，tasks 拆成可验收的任务单。spec 里的 WHEN/THEN 场景一举两用，实现之前是指令，实现之后是试卷。开头那次佣金事故如果先有 spec，下面这两行 WHEN 就问不出去：

# spec 片段：部分退款场景（WHEN/THEN）
WHEN 部分退款金额大于已支付金额
THEN 拒绝请求，返回 REFUND_EXCEEDS_PAID
THEN 不触发佣金重算，不写退款流水

我用 OpenSpec 把这条流水线固化下来，从 explore 到 archive 六步，整套用法见OpenSpec 的 skill 流水线。成本也实测过：中等改动从探索到归档走完大约小半天，换来的是返工轮次明显下降，外加一份能跟代码对账的记录。单文件小修别套这条流水线，流程开销超过动作本身就不划算。

流水线里人只出现在一个点：计划确认。这一票必须人投，投完之后的执行交给 AI 自治。中间产物还要管寿命，过程稿用完就删，跟代码走的设计说明才配归档，我清点过 18 份归档 spec，两种寿命混放的仓库里，被推翻的旧方案误导过我三个月，见18 份归档 spec 的两种寿命。

装这根柱子的判断线也简单：改动跨文件、有外部副作用、需要决策留痕，三者中一条就立项写 spec；单文件小修直接聊，别把流程做成负担。

五、第四根柱子：测试门禁，「搞定了」必须有证据

现在回收开头那 270 行的事故。删代码的提交编译是绿的，因为编译器只校验语法契约，不校验行为存在。AI 没有心虚的概念，它只对验收信号负责，验收信号是绿的，它就交差。想让它交出真的对，唯一的办法是把「对」做成机器可校验的东西，我把这叫做 Proof-of-Work，说完不算，跑出来算。

那次复盘用 5 Whys 往下挖，挖到底的结论与手滑无关：门禁纪律没有跟上生产方式的升级。人写代码的年代靠评审盯 diff，AI 写代码的年代 diff 产出速度翻了十倍，肉眼评审第一个失守。

门禁分三层。最里面一层是测试纪律，UT/IT/E2E 各管各的，配套几条硬规矩：禁 skip、禁占位断言、expect(true) 直接打回、失败立即停不重跑。

有个 JOIN 漏了 tenant_id 的多租户越权，就是被 IT 层的反向断言逮住的，断言写的是「结果里不允许出现别的租户的行」。三层测试怎么配，见三层测试纪律。

往外一层是契约闸。URL 改了路由没改、SQL 和 DDL 不一致、权限 key 和种子数据对不上，这类跨层 bug 编译和单测都看不见，我用四道 pre-commit 脚本做事实源比对，总共不到 8 秒，拦住了七成的跨层问题。剩下三成由架构测试和评审回路分掉。四道闸的实现和误判翻车，见四道脚本闸。

同一类问题在不同阶段被逮住，代价差着量级。提交前被契约闸拦下，改一分钟；合进主干被 E2E 拦下，回滚加定位半天；漏到线上，就是开头那次四天排查加超卖赔偿。门禁每往前挪一个阶段，修复成本往下掉一个台阶，这 8 秒买的就是这个差价。

# 契约闸的一条：路由与调用方必须一致（伪码）
routes    = extract_routes("src/main/java/**/controller")
clients   = extract_api_calls("frontend/src/api/**")
assert set(clients) <= set(routes), \
    f"调用方引用了不存在的路由: {set(clients) - set(routes)}"

最外一层是验收形态本身。UI 改动要过截图对比，「我看过一眼」不算验收；平台发布要复查现存状态，上传器日志不可信。「我搞定了」后面必须跟着可复查的证据，这些验收手段的松紧决定 AI 交付质量的下限，见视觉验收。

一个提醒：测试也可能是假的。快照测试把当前输出封存成标准答案，bug 从此永远「正确」，这类假绿灯比没测试更贵。门禁本身也要被人审查，这是第六节权限分离的伏笔。

六、第五根柱子：边界与成本，权限、并行和 token 都是资源

现在回收账单那个钩子。952 万 token 那个会话的问题不在干得多，在从来不新开会话，上下文一路滚到收不了场。上下文每轮全量重发，缓存命中率本来有 92% 到 98%，我中途改了一次 AGENTS.md，前缀变化，命中率跌到 46%，实付差了 5.5 倍。

从那以后我立了三条纪律：一段一验收，验收完新开会话；稳定内容放前、易变内容放后；会话中途不动 AGENTS.md。新会话也不是从零开始，把上一段确认过的结论压缩成几句话带过去，比拖着一整段历史便宜得多。

账单背后是更一般的原则：上下文、权限、并行度都是资源，裸聊的人把它们当成无限的。权限上，审查会话只给只读，修复会话才给写权限，两件事永远不用同一个会话干，自审自修等于没审。

大任务再进一步是三会话分离：分析会话只许读代码和提问，产出影响分析；实现会话拿着分析结论动手；审查会话最后只读 diff 挑毛病，并且被明确告知「允许说无法确认」。三个会话互相不知道彼此的思路死角，串起来比一个全能会话稳得多。

并行上，几个 AI 同时开工必须各自隔离目录，git worktree 一条命令搞定目录、分支、暂存区三重隔离，并行度上限就压在三条线以内，见让 3 个 AI 同时开工不打架。

自动化也要有闸。我的夜间巡检 daemon 每天零点跑全量测试，失败自动修、修完跑完整回归再提 MR，但三条红线焊死：环境类失败不修、flaky 不修、根因未定不修，并且绝不无限重试。信任但要验证，验证的闸要焊在自动化自己身上，见夜间自动修测试的 daemon。

成本侧还有一层是模型路由。简单重构不值得上最强模型，探索性任务别用最便宜的。

把 Agent 拆成大脑、能源、手脚、手册四层之后，路由和容灾都有明确的着力点，账单差距能到 30 倍，见Agent 四层拆解。交给 AI 多少自主权也有档位，从旁路观察到全自动，我的判断线写在Codex 五级用法，核心一条：验证手段有多硬，放手就可以有多松。

七、从零装起：顺序、比例和放手判断

五根柱子不用一次装齐，装错顺序反而累。我的推荐顺序按「拦住的损失除以安装成本」排，三周走完第一批。

第一周装两样：AGENTS.md 骨架加最小测试门禁。手册第一天就能写，把脑子里口述过三遍以上的规则倒进去；门禁先只拦最疼的一类，比如禁 skip 和禁占位断言。这两样成本最低，拦的是静默改错和假绿灯，全是不可逆的损失。

第二到三周装 skill 和 spec。按风险点补肌肉，把口述重复的流程入库；spec 从 plan-first 两步开始用，先不追求四件套齐全，等吃过一次「计划问掉需求」的甜头，你再回不去。第四周起管边界与成本：会话拆分、缓存纪律、权限分离、worktree 并行，这时候你的交付量已经上来了，没有这些闸，账单和事故会替你叫停。

投入比例我给一个实测数：那 4 个人 2 个月近百万行的项目里，大约 30% 的时间花在搭这套体系上，完整账在产能账本。这个比例不是损耗，AI 放大的是执行力，放大不了判断力，判断力就住在这些工程件里。

安装路上还有三个常见的跑偏。一个是先追 skill 数量，一晚上装八十个别人的 skill，真正被触发的没几个，路由表先乱掉；一个是跳过门禁直接上自治，让没有验收闸的 AI 夜里自由发挥，早上收到的只有一份事故报告；还有一个是门禁装完就不管，我的契约闸脚本就被人整块删过，后来跟架构测试绑在一起互相接应，删掉任何一个，另一个会报警。闸要配哨兵，装完不管等于没装。

放手到什么程度，可以用一张表判断。核心原则只有一条：验证手段有多硬，放手就可以有多松。

放手档位适用场景人的位置
旁路观察新仓库、新模型、新类型任务全程盯着每一轮
计划确认后执行跨文件的功能开发投计划那一票，验收结果
门禁自治有门禁覆盖的例行改动抽查门禁漏网样本
夜间自治daemon 全量回归加自动修第二天早上看报告

成熟度可以粗分三段：聊天段，AI 是高级补全，人盯每一行；契约段，spec 和门禁接管质量，人管计划确认和验收；自治段，夜间 daemon 和多 agent 评审接管例行工作，人只处理升级上来的决策。

判断自己处在哪一段有三个自测问题：隐性规则离开你的口述还能不能生效；AI 说搞定了之后，有没有一条命令能复核；上个事故的教训，现在写在仓库的哪个文件里。三问全过是契约段，前两问过才算摸到契约段的门，第三问过才有资格谈自治。大多数个人项目和中小团队，把契约段做扎实就够吃很久了，自治段的闸没焊牢之前，别羡慕别人夜里睡觉 AI 干活。

先立柱子，再谈手感

回头看这两笔学费，952 万 token 买的和 270 行代码赔的，指向同一个判断：vibe coding 的质量上限，跟模型关系不大，跟你把多少工程纪律翻译成机器可执行的资产成正比。手册、肌肉、契约、门禁、闸，五根柱子没有一根是新技术，全是从软件工程里搬来的老手艺，只是这次要搬给一个没有长期记忆、不会心虚、执行力被放大了十倍的新同事。

模型每次升级都在放大你的工程水位。纪律齐的人拿到的是复利，裸聊的人拿到的是同一张账单的更高倍数。所以下次 AI 再翻车，先别急着换模型、调提示词，打开仓库看看，那五根柱子立起来了几根。
