我观察到一个现象：两个水平差不多的开发者同时开始用 Claude Code，三个月后效率能差出三倍。

工具一样，模型一样，差距在哪？不是提示词写得花不花哨——提示词的边际收益在第一个月就到顶了。真正拉开差距的，是对 Claude Code 作为工程工具的完整理解。

很多人用 Claude Code 的方式，本质上还是 Chat 那套：在一个会话里不断提问，上下文越滚越胀，然后会话崩了、模型开始胡扯，就关掉重开。这不是用工具，这是在把 IDE 当 ChatGPT 用。

而真正用得好的人，理解这套工具的完整能力面：

  • 命令是给 AI 套纪律边界，不是「问它一个问题」
  • Skill 是把经验固化成可复用的命令，不是写一次性提示词
  • Subagent 是一个人指挥一群 AI，不是一次只做一件事
  • 打断与恢复是效率杠杆，不是失败

这篇文章把这套技能树拆开讲。每条都不是「技巧」，是工作方式的切换——从被动响应到主动编排，这才是高手和新手的真正差距。

一、Claude Code 使用金字塔

我对 Claude Code 的使用深度分了三个层级。大多数人停在第一层，高手在第二层和第三层之间切换。

第一层，对话级。把 Claude Code 当高级 ChatGPT 用——打开就聊，问问题、写代码、修 bug，一个会话从头跑到尾，跑崩了就重开。这一层能解决日常 60% 的问题，但你永远在给 AI 当助理——每次重复上下文、每次重新描述项目结构、每次等着它慢慢推理。

第二层，命令级。开始用 /command、Skill、Task 这些结构化接口。这一层的核心变化是：你不写提示词了，你调用预定义的流程。命令像 API 一样有输入输出契约，Skill 像函数一样封装了可复用的逻辑。这一层效率提升不是线性的，是乘法——写一次命令，反复用几百次。

第三层，编排级。同时启动多个 Subagent，各自做独立任务，你在中间做决策和收敛。用到 Workflow 做多阶段自动化：审查、修复、验证全部并行，最后一轮收敛才叫你。这一层你从「AI 的操作员」变成了「AI 的指挥官」。

这个金字塔得先讲明白，因为后面每一节都是在讲「怎么从当前层爬到上一层」。

二、内置命令与工具：先弄清楚有什么

Claude Code 的「命令」其实分三类：斜杠命令（/xxx 在会话里输入）、工具（内置函数，AI 在后台调用）、CLI 子命令（终端里输入 claude xxx）。三者的区别决定了你用什么方式控制 AI，这点得先搞清再往下讲。

斜杠命令（Slash Commands）

在会话里直接输入 /xxx 调用。这是你作为用户主动控制 AI 的主要方式。

Skill 和内置命令的调用方式一样都是 /name，但来源不同——内置命令是 CLI 自带的，Skill 是项目 .claude/skills/ 目录里的文件。Skill 可以被版本管理、团队共享。

工具（Tools）

这些不是 / 命令，是 AI 在后台调用的函数——你不需要手动输入，但理解它们的存在很重要：

  • Task 管理：TaskCreate、TaskStop、TaskGet、TaskList、TaskOutput。用于创建和管理后台运行的子任务。
  • Agent 工具：你可以让 Claude “launch a subagent to explore the API documentation”——这会创建一个独立会话在后台跑，不阻塞你当前的会话。
  • Workflow 工具：编排多个 Agent 执行多阶段任务，支持串行和并行模式。

CLI 子命令

在终端里输入 claude xxx 调用，不进入交互式会话：

命令作用
claude agents查看和管理所有后台 Agent
claude doctor运行环境诊断
claude ultrareview云上多 Agent 代码审查
claude update检查并安装更新
claude -p "prompt"非交互式模式，直接输出结果
claude --resume恢复之前的会话

哪一个场景用什么？

判断很简单：

  • 想在当前会话里做某事 → 斜杠命令（/clear、/review、/compact）
  • 想查你的使用数据或调设置 → 斜杠命令（/help、/config）
  • 想同时做多件独立的事 → Agent 工具（launch a subagent）
  • 想编排多 Agent 自动走多步流程 → Workflow 工具
  • 想从终端快速一问 → CLI 子命令（claude -p "..."）

特别说一下 /compact

/compact 和 /clear 是上下文管理的两个互补工具，区别很关键：

  • /clear（别名 /reset、/new）：删掉对话历史一刀切，适合「话题完了，重开」。工作区状态（文件修改、终端进程）不受影响。
  • /compact [说明]：把对话压缩成摘要，释放上下文窗口（官方数据：节省 60-70% token）。保留历史精华——模型记住关键决策但不保留每条对话原文。还可以传可选说明定向压缩，如 /compact focus on database migration decisions。

什么时候用：模型开始忘记几分钟前说过的事、重复你的话、或者编造不存在的信息——说明上下文撑满了。先 /compact，不行再 /clear。

Skill 的详细介绍见下一节。Agent 和 Workflow 在第四、六节展开。

三、Skill：把经验固化成可复用的命令

Skill 是 Claude Code 的「函数定义」——你把一段频繁执行的工作流写成 Skill 文件，然后通过 /skill-name 调用。

Skill vs 普通提示词

普通提示词Skill
复用性每次重写或复制粘贴一个文件反复调用
一致性每次措辞不同，AI 理解有偏差固定指令，输出稳定
分享靠口口相传文件提交进仓库，团队共享
维护需要改时得找到历史会话改一个文件全局生效

我做了一个很朴素的选择：任何需要跟 Claude Code 说两次以上的话，都值得写成 Skill。这个阈值很低，一个月下来就能攒不少。

Skill 的形态

一个 Skill 就是一个 Markdown 文件，放在 .claude/skills/<name>/SKILL.md。

比如我写 crawl skill 时，文件结构是：

.claude/skills/
├── crawl/SKILL.md        # /crawl 爬虫最佳实践
├── drawio/SKILL.md       # /drawio 画图工作流
└── ...

调用时直接 /crawl，Skill 里的完整指令注入到当前会话。

Skill 的设计原则

写 Skill 不是「把一段提示词拷进文件」就行，有几个设计点：

命中条件前置。Skill 文件开头写清楚「何时用本 skill」，防止选错工具。我的 drawio skill 开头第一句是「架构图/部署图/时序图用这里，概念图/心智模型请改用 Excalidraw」——不写这一句，AI 可能会拿 drawio 画概念图。

可执行性优先。Skill 里的步骤必须可以被 AI 按顺序执行，不要留「看情况」「视需求」这种模糊分支。每一步是一个确定的动作。

版本化。Skill 文件进 git，改了什么有记录。跟代码一样，Skill 也会犯错——改了之后发现不如以前，能 git revert。

Skill 的复利效应

Skill 最值钱的地方不是省打字，是让经验可传承。团队加一个人，不需要口口相传「我们这里怎么怎么做」，给他看一眼 Skill 目录就行。换了一个项目，原来攒的 Skill 思路能复用，把具体内容按新项目改一下就好。最容易被忽略的是：Skill 能做到跨会话的连续性——每次 /crawl 调用，不管会话开了多久、上下文多乱，注入的指令都是一致的。这个「一致性」在高频操作中省掉的纠错时间远超想象。

四、Subagent：一个人指挥一群 AI

Subagent 是 Claude Code 里升维最多的功能——但也是门槛最高的。

什么时候该用 Subagent

Subagent 解决的核心问题是串行阻塞。当你面前有三件独立的事：查 API Schema、翻历史日志、读另一个服务的接口定义——串行做，一件事等下一件事。并行做，三件事同时完成。

Subagent 的正确场景就是「可独立拆分的任务」。判断标准很简单：这件事能不能在不知道另一件事结果的前提下做完？ 能，就开 Subagent。

怎么用 Subagent

在 Claude Code 里启用的方式很简单：

Launch a subagent to explore the crawler directory and report which selectors are broken

启动后 Subagent 在后台独立运行，你的当前会话不阻塞，可以继续做别的事。等它完成时通知你结果。

常见的两种用法

并行探索。不改代码，只做调查。比如写新功能前让一个 Subagent 读 API 文档，另一个扫代码库看现有实现，第三个去查数据库 Schema。三个结果拿回来你合并决策。这是信息采集的并行化。

分派执行。一个改前端，一个改后端，一个写测试。各自独立跑，最后你审查合并。这里有个关键：Subagent 执行前必须把上下文锁死——定好接口契约、数据格式、验收条件。不然两个 Agent 各自做各自的，合起来对不上。锁死接口契约比锁死实现方案重要——只要接口对齐，实现方案各有各的风格问题不大。

Subagent 的代价

Subagent 不是免费的。启动一个新 Agent 有上下文加载成本，而且 Subagent 没有主会话的完整上下文——它只拿到你给它的指令。所以给 Subagent 的提示词必须自包含：需要什么信息、输出什么格式、验收标准是什么。

高手会在主会话里写好 Subagent 的完整指令再发出去，而不是丢一句「去看一下那个文件」。

五、任务打断与恢复：高手不怕打断

这是最反直觉的一条：打断是好事，不是失败。

为什么需要打断

AI 推理的质量跟方向有关。方向对了，跑得越久产出越好；方向偏了，跑得越久浪费越多。

大多数人不敢打断的原因是一种心理障碍：觉得打断就是「浪费了已经跑了的那些时间」。沉没成本谬误在跟 AI 协作时特别明显——你都看到它跑偏了，还在等它「跑完这段再说」。这不是耐心，是舍不得已经花掉的 token。

高手会在一发现偏了就打断，说明原因，让 AI 重新来。这么做的理由是：AI 从错误方向回头的成本远低于从零开始。你打断后给它一句话的纠正，它能复用已生成的正确部分，只重做偏掉的那块。

怎么打断

按 Esc 键。Claude Code 会停掉当前生成，回到等待输入状态。

打断后要做三件事：

  1. 说明为什么打断。「方向偏了，我在要求 X，你却在做 Y。重新看一下需求，只做 X 相关的」。
  2. 看看 AI 已经做了什么。有时候 AI 其实做了不少正确的事，看一眼终端输出或文件改动，确认哪些能保留。
  3. 提供修正方向后重发指令。不要只说「不对，重做」，要说明怎么才对。
（按 Esc 打断）
（看 AI 已经做了什么，确认哪些保留）
重新来。前三步的文件结构是对的，保留。
从第四步开始，改成本地缓存方案，不要用分布式缓存。

恢复的两种模式

热恢复：同一会话内，上下文还在，打断后立即修正继续。适用于方向微调。

冷恢复：会话混乱到没法修了，/clear 清上下文，或者关掉重开，带着关键结论进入新会话。适用于上下文已经膨胀到让模型开始胡扯的情况。

什么时候该打断

我给自己定了三条打断原则，任何一条触发就停：

  • AI 开始编造不存在的 API、方法、文件——说明上下文已失真，继续只是加速偏离
  • 输出质量明显下降——推理变浅、开始重复套话、回避复杂问题的具体分析
  • 方向跟需求不一致超过 30 秒——不要等它「跑完这轮」

这三条的核心是同一个判断：AI 推理跟开车一样，偏了 5 度开 10 分钟就偏出一公里。30 秒的偏离，继续 5 分钟就是完全不同的东西。 打断越早，沉没成本越低。

六、Workflow 编排：多 Agent 的乐谱

如果说 Subagent 是做单个任务，Workflow 就是编排一群 Subagent 按乐谱演奏。

什么时候用 Workflow

Workflow 的场景是「多步骤、多 Agent、有依赖关系」的任务。举几个例子：

  • 代码审查：10 个 Agent 各自审 5 个文件，审完后再派 5 个 Agent 修复问题，最后汇总报告
  • 跨平台发布：一个 Agent 写文章、一个做图、一个检查排版，全部准备好再统一发布
  • 迁移审计：先扫全仓代码找迁移点，再分片执行替换，最后验证

Pipeline vs Parallel

这是我用 Workflow 时最常做的选择。

Pipeline（流水线）：一件事做完再做下一件。适用于步骤之间有依赖——不想在接口契约没定好的时候就开始改前端代码。

Parallel（并行）：多件事同时做。适用于相互独立——查 API 文档、读代码库、看数据库 Schema，三个 Subagent 可以同时跑。

在实际中，我经常混用：第一阶段 Parallel 探路，第二阶段 Pipeline 按依赖执行，最后再 Parallel 验证。

第一阶段(并行): 查 API 文档 + 扫代码库 + 看 Schema
第二阶段(串行): 定方案 → 改后端 → 改前端
第三阶段(并行): 编译检查 + 测试 + 安全审查

Workflow 的墙钟优势

Workflow 最大的价值不是功能多，是墙钟时间短。串行做三件事，时间 = A + B + C。并行做，时间 ≈ max(A, B, C)。差距在复杂任务上能差出 3-5 倍。

代价是编排复杂度。Workflow 的脚本需要人写，逻辑需要人调试。所以我的选择原则是：一件事超过 3 个步骤且有天然可并行的子任务，才值得上 Workflow。少于这个复杂度，手动做更快。

这也是从命令级到编排级最难跨的一步——编排能力不来自工具，来自「把复杂任务拆解成可并行子任务」的思维习惯。

七、新手最常见的几个误区

误区一：把 Claude Code 当 ChatGPT 用

最普遍的用法。一个会话打开就一直聊，不问方向、不打断、不拆任务。结果就是会话越来越长，模型越来越胡扯，最后关掉重开。

根因是没理解 Claude Code 是工程工具不是聊天工具。ChatGPT 一个会话聊到天荒地老没问题，但 Claude Code 的上下文是企业级代码库的复杂度，跟闲聊的记忆需求不是一个量级。代码上下文不能断——断了 AI 就记不住项目结构。

正确的做法：有明确任务就开新会话，任务完就 /clear 或结束，不要一个会话挂几天。

误区二：重复写同样的提示词

每次写「帮我检查一下这个文件有没有线程安全问题」——写了 20 次，第 21 次还在写。写成 Skill 或者在 CLAUDE.md 里加一条规则，一劳永逸。

根因是没建立「复用」的思维模式。写提示词是零次性的，建 Skill 是一次性投入长期复用。前者的成本每次都能感觉到但不致命，后者的收益要积累多次才能量化——这种「先投后收」的模式恰恰是很多人跨不过去的门槛。

误区三：不用 /clear

上下文窗口是有限的。一个会话里聊了 50 轮后，AI 对项目结构的记忆开始模糊。不 /clear 就继续，很快进入「编造不存在文件」的阶段。

根因是没意识到上下文衰减。模型对越久远的上下文注意力越低，不是「记得但不想用」——是物理上就衰减了。遇到模型行为异常，第一反应应该是「是不是该 /clear 了」，而不是怀疑模型能力。

误区四：不会也不愿意打断

看着 AI 偏了还在等。「让它跑完吧，说不定后面能绕回来」——绕不回来。

根因是两个心理障碍的叠加：沉没成本谬误（已经花了 token 跑这段了）和中断反感（打断正在进行的事情天然不舒服）。克服这两个障碍是有意识地练习出来的——我花了大概两周才形成本能反应。

误区五：所有事自己干

不开 Subagent、不做 Workflow，所有事在当前会话里串行完成。不是不能做，是浪费了时间杠杆。

根因是缺乏「拆分并行」的习惯训练。技术工作天然是串行思考的——人一次只能想一件事。但 Subagent 改变了这个假设：你现在可以同时想多件事了，只是需要练习这种「拆—派—收」的工作节奏。这个节奏从陌生到自然，大概需要一周。

八、核心判断

回到开头那个问题：同样用 Claude Code，差距从哪来？

不是模型知识，不是提示词技巧。是对工具能力面的认知深度。

命令、Skill、Subagent、Workflow——这些功能全都写在文档里。所有人都能看到，但不是所有人都能意识到它们意味着什么。看到 /clear 只是「清屏」，和意识到 /clear 是「上下文管理的主动策略」，对效率的影响差了两个数量级。

我至今也在不断发现这个工具的新用法。每多理解一个功能的真实用途，效率就往上跳一档。让我最有感触的是：工具的能力值是一个固定数字，你对它的利用率才是变量。高手不是用了更好的工具——只是把自己手里的工具用到了更深。

换个说法：你不需要一个更强的 AI，你需要一个你更会用的 AI。这个差距，是你和昨天的自己的差距。
