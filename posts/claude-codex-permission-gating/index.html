Claude Code 与 Codex 的权限门控源码对比：hooks 改写决策和沙箱硬隔离

xiaoshuai1024 included in AI 开发
About 500 words 3 minutes 
Contents

  • 二、Codex：审批枚举加三平台沙箱
  • 三、软约束和硬隔离的真实边界
  • 四、使用层的直接建议

有一天我翻 Claude Code 的混淆代码翻到一段名单，愣了一下：["mkdir","touch","rm","rmdir","mv","cp"]——在 acceptEdits 模式下，这六个命令是免审直通的（L378700 到 L378740，decisionReason 标注 type: "mode", mode: "acceptEdits"）。我一直以为这个模式只是「少点几次确认」，边界比我想的宽：它放行的不只是编辑，还有一组文件系统命令，其中 rm 和 mv 都在。这个发现让我把两边的权限门控源码完整读了一遍，这篇就是结论。

系列第五篇。前四篇见架构分层、主循环、subagent、上下文管理。版本锚定不变。权限和前四篇的性质不太一样：主循环、压缩、subagent 出问题损失的是效率和 token，权限出问题损失的是数据和信任——它是这个系列里唯一「错了难以回滚」的议题，所以这篇的每个使用建议我都写得比前面几篇更保守。

一、Claude Code：模式加 hooks 的双轨

Claude Code 的权限决策有两条轨：模式轨决定默认行为，hooks 轨允许运行时改写。

模式轨是四个字符串常量（L378725 等处确证）：default（逐次询问）、acceptEdits（编辑类放行）、bypassPermissions（全放行，dangerouslySkipPermissions 开关就是往这切，L364292）、plan（只读规划）。模式之外还有规则语法：allowedTools 列表支持带参数的规则（L416466 的快照示例 Read(~/**)、Edit(~/.claude/settings.json)），粒度到「工具加路径模式」。

这套规则语法的表达力是 Claude Code 权限体系里最精细的部分。一条规则三要素：工具名、参数模式、来源（allow / ask）。Read(~/**) 放行家目录下所有读取，Edit(docs/**) 放行文档目录的编辑，Bash(npm run *) 覆盖一类命令。实践里我建议「窄开正门」：把信任的高频操作逐条开白（读、文档编辑、固定的几个构建命令），而不是用宽模式开侧门——正门越具体，异常越显眼。规则配好后 default 模式能覆盖九成日常，弹出来的询问本身就是异常信号，而不是噪音。

整体看，这套体系的取向是把权限决策变成可声明的配置：四模式是预设档位，allowedTools 是档位上的精调，hooks 是配置之外的编程出口——三层从粗到细，分别覆盖「大多数人」「讲究的人」「有组织策略的人」。个人用户停在前两层就够，团队要走到第三层。

四个模式里最没存在感的 plan 值得替它说句话。只读规划模式下 agent 不能改任何东西，产出的是计划而不是代码——听起来是残血模式，实际上是高风险任务的前置关卡：先让 agent 在 plan 模式下出完整方案，人审方案（审「它打算干什么」比审「它干了什么」便宜一个数量级），认可后切回执行模式。我的夜间批处理任务全部走这个流程，方案错杀在纸面，执行阶段的审批量也小了——方案已经把要做的事说清，异常操作反而更醒目。Codex 有对应的 plan.rs handler，机制是现成的，用不用在习惯。

开头那六个命令的白名单就是模式轨的实现细节。设计逻辑说得通：acceptEdits 的语义是「我信任它改文件」，而 rm/mv/cp 在 agent 的日常工作流里和编辑文件是一回事——模型改完代码清理临时文件、挪个构建产物，如果每次都要人点确认，这个模式就失去意义了。但风险同样真实：一次错误的 rm -rf 在这个模式下没有人拦。

hooks 轨是运行时改写层。事件枚举在 L350463 到 L350471，九种事件一字排开：PreToolUse、PostToolUse、Notification、SessionStart、SessionEnd、Stop、SubagentStop、PreCompact、UserPromptSubmit。其中 PreToolUse 是权限体系的参与方：工具执行前（L417234 的 aN5 generator 里，先过 inputSchema.safeParse 校验，再进 hook 包装器），hook 可以返回 permissionDecision: "allow" | "deny" | "ask"，直接改写本来的权限决策——改写发生时，决策原因会标注 decisionReason: { type: "hook", hookName: "PreToolUse:Bash" }（L417327 到 L417335 原文）。多个 hook 可以注册在同一事件上，并行执行。

这套设计的定位是软约束加可编程：默认策略保守，用户用 hooks 把自己的策略编进去——公司可以把「涉密目录禁写」做成一个 PreToolUse hook 挂给全员，比教育模型靠谱得多。代价是约束的强度上限就是 hook 脚本的可靠性：hook 写崩了会话跟着崩（单进程），hook 没覆盖的路径完全靠模式默认值。

hook 的配置格式和执行协议也有值得抠的细节。配置侧是「事件 + matcher + 命令」的结构：matcher 按工具名过滤（新版格式 {"matcher": {"tools": ["BashTool"]}}，L350925 有迁移提示），一个事件可以挂多条。执行侧的输出协议（L390988 的 schema）里，PreToolUse 的返回除了 permissionDecision 三值，还有结构化的 reason 字段——这意味着 hook 的决策是可解释的：为什么拦这条命令，可以写进决策记录。多条 hook 并行执行（L407786 明文），全部跑完取合并结果。

写一个权限 hook 的最小实现，其实就是读 stdin 的 JSON（工具名 + 参数）、做判断、往 stdout 写三值决策。二十行脚本就能把「生产数据库路径禁写」这类组织策略固化。但要记住它的两个边界：hook 只在工具执行时点触发（第二篇讲过它嵌在主循环的工具管线里），拦不了「模型读了敏感内容往回复里写」；hook 脚本本身是任意代码，挂 hook 等于给它的作者开了后门——团队里引入别人的 hook 配置前，像 review 依赖一样 review 它。

还有个容易漏看的细节：Task 工具免权限。L411591 的 checkPermissions 直接返回 {behavior: "allow"}——派 subagent 不需要任何审批。结合第三篇的「subagent 复用主循环」，这意味着权限的守门员只在工具层，不在「派活」层：拦得住工具调用，拦不住「派一个带着工具的 agent」。理解了这一点，就理解了为什么 allowedTools 的配置会被子 agent 继承——门只有一扇，钥匙管的是门不是人。

二、Codex：审批枚举加三平台沙箱

Codex 的权限体系是三层硬结构。

第一层审批枚举：protocol/src/protocol.rs:915 的 AskForApproval 枚举定义审批强度，ReviewDecision 定义决策结果。审批流在 core/src/tools/approvals.rs，入口四兄弟：request_approval（:484，总入口）、request_reviewer_approval（评审者审）、request_guardian_approval（:580，guardian 代理审）、request_user_approval（:656，人来审）。审批不是布尔值，是分级的：谁审、按什么策略审、审不过怎么办，都是类型系统的字段。

「审批是枚举不是布尔」这个设计决定值得所有做 Agent 的人记住。布尔审批（问/不问）只能表达强度，表达不了立场：这条请求该由谁审、审的人拿到什么信息、拒绝之后走什么路径。枚举把这些都变成了类型——AskForApproval 的变体对应不同强度的审批场景（从不问到必须人到「只在整个会话开始时问一次」），ReviewDecision 的变体对应不同的裁决出口（通过、拒绝、带修改的通过）。当审批流要接进 IDE、接进 CI、接进云端时，每个宿主对这些问题都有自己的答案——布尔给不了，枚举给得了。第一篇说 Codex 是「协议化的平台」，审批枚举就是协议化在安全域的具体形态。

四个入口的分工也是一套小型的组织架构图：request_approval 是前台（判断该走哪条线），request_reviewer_approval 是评审席（代码改动类的专业审查），request_guardian_approval 是安检门（策略符合性），request_user_approval 是终审（人）。一个工具调用从进来到放行，走的路径取决于它是什么、改了什么、策略怎么说——审批的路径本身就是风险分级。

第二层 guardian：core/src/guardian/ 是个内置的审批代理——有独立的 policy.md（策略以文档形式维护，有意思的选择）、review.rs 和 approval_request.rs。它站在人和工具之间，代替人做第一道过滤，人只处理 guardian 拿不准的请求。这是 Claude Code 没有的层级：那边 hooks 是「用户的代理」，这边 guardian 是「产品的代理」，立场不同。

guardian 用 Markdown 维护策略这个选择值得单独品味。策略文件不是配置代码而是自然语言文档，意味着策略的修改门槛极低——产品运营可以调，安全团队可以直接 review 文字。代价是精确性：自然语言策略的边界天然模糊，执行时要靠 review.rs 里的程序化规则把文字落成判断。这个「文档定方向、代码定边界」的双层结构，和人类的「安全规范 + 实施细则」同构。Claude Code 的 hooks 走了另一条极端：策略完全是代码，精确但门槛高。策略的可读性和精确性是一对真实矛盾，两边各站了一头。

「代理审批」还有个心理学层面的作用：它改变了「询问」的默认含义。没有 guardian 时，每次询问都是一次打断——用户被训练成条件反射式点允许（审批疲劳的根源）。有 guardian 时，到达人面前的请求已经过了机器预筛，频率低、质量高，用户有理由认真对待每一个。审批系统的敌人从来不是严格，是高频——guardian 的价值一半在安全，一半在保护用户的注意力。这一点对 Claude Code 用户的启示是：与其追求「每次都问」，不如追求「问得少而准」——白名单收掉九成常规操作后，剩下的询问才是值得动脑的。我自己的数据是配好白名单后日均询问从四十多次降到七次以内，而我对每次询问的认真程度完全不是从前可比。

第三层沙箱：独立 crate sandboxing/，按平台三套实现——Linux 用 landlock（landlock.rs）、macOS 用 seatbelt（seatbelt.rs，配套 .sbpl 策略文件，基础策略和网络策略分开）、Windows 有自己的实现（windows.rs），统一由 manager.rs 的 SandboxManager 管理。另有 linux-sandbox/（bwrap 启动器）和独立的 execpolicy/ crate 做命令策略评估（PolicyParser 解析命令、判断要不要拦截）。命令级策略在 core/src/exec_policy/ 与 shell 运行时（tools/runtimes/shell.rs 的 approval_action、sandbox_permissions、escalate_on_failure）联动：先在沙箱里跑，失败且策略允许才升级权限重试。

沙箱这层展开说两句原理，因为「沙箱」这个词被用得太滥。landlock 是 Linux 内核的 unprivileged 强制访问控制——不需要 root，进程自己声明「我只访问这几个目录」，内核负责执行，越界的系统调用直接被拒。seatbelt 是 macOS 同样定位的机制（.sbpl 是它的策略语言，Codex 把「文件系统基础策略」和「网络策略」拆成两个文件，粒度可见一斑）。关键是这两者都是内核态强制：模型生成的命令再怎么花哨，系统调用过不了策略就是过不了，没有「绕过」这个选项——这和「提示模型别干坏事」是两个宇宙的防御。Windows 实现独立成文件也说明平台差异真实存在，成熟度要按平台分别评估。

execpolicy 的存在补上了「命令级」的判断：沙箱管的是系统调用面，execpolicy 管的是命令语义——同一条 bash -c，里面是 ls 还是 curl 外网 策略完全不同。PolicyParser 把命令拆开评估，决定放行、拦截还是要求审批。系统调用层 + 命令语义层的双层过滤，是「硬隔离」能号称硬的原因：光有沙箱拦不住语义级危险（比如在允许的目录里干坏事），光有命令解析拦不住绕过解析的执行。两层各管一段，合起来才接近「无死角」——这个分层在安全工程里有成熟先例（防火墙管包、IDS 管语义），Codex 等于把经典防御纵深搬进了 agent 的工具执行路径。

对比一下这个「先沙箱后升级」的思路和 Claude Code 的「先问人再执行」：前者把默认路径做成安全的（沙箱里跑挂了再说），把人的注意力留给真正需要的场景；后者把默认路径做成询问的（每个危险动作过一遍人）。一个是环境级防御，一个是行为级审批——前者防「做错事」，后者防「做你不知道的事」。

三、软约束和硬隔离的真实边界

把两边的机制并排，边界就清楚了。

维度Claude Code v1.0.88Codex 2026-08
决策粒度工具 + 路径模式（Read(~/**)）工具 + 命令策略（execpolicy 解析）
默认策略四种模式，逐级放宽审批枚举分级，逐级收紧
运行时改写PreToolUse hook 三值决策guardian 代理自动审批
执行隔离无（同进程直接执行）landlock / seatbelt / Windows 沙箱
失败路径400 自救重试（字符串级）沙箱内失败 → 策略允许才升级重试
权限守门范围工具层（Task 免审）工具层 + 环境层双守
决策留痕decisionReason（模式/hook 来源）ReviewDecision 枚举 + 审批流记录

最后一行「决策留痕」是容易忽略但重要的一行：Claude Code 的每个决策带 decisionReason（是模式放的还是 hook 放的），Codex 的审批走类型化流程、每个环节有记录。出事后回答「当时为什么放行」，两边都能答，但 Codex 的答案结构化程度高一档——审计系统接起来是查询，不是文本解析。

我对这套差异的定性：Claude Code 的安全模型信任配置，Codex 的安全模型信任环境。

acceptEdits 加 hooks 这条路，安全性取决于你配得对不对——白名单模式、hook 覆盖度、路径规则的严谨性，配错一处就是缺口。它的优势是灵活：hooks 是任意可编程的，公司策略、个人习惯、临时管控都能塞进去，且即时生效。

沙箱这条路，安全性取决于内核机制的强度——landlock 和 seatbelt 是操作系统级的强制访问控制，模型再怎么幻觉也越不过沙箱的文件系统边界。它的代价是环境依赖：Windows 的沙箱实现成熟度、容器里的嵌套限制、性能开销，都是要付的账。

拿一个具体的越界请求走两边流程，差异会非常直观——这也是我推荐读者自己做的一次思想实验，读完这节拿自己的配置对号入座。假设模型幻觉了，决定删除 ~/important/ 下的文件。Claude Code 这边：Bash 工具带着 rm -rf ~/important/x 进执行管线，先 schema 校验（参数合法），再查模式——acceptEdits 下 rm 在白名单（HP6），放行；如果配了 PreToolUse hook 且 matcher 匹配 Bash，hook 有最后机会 deny。没配 hook，文件没了——防线全靠你之前配了什么。Codex 这边：同样的命令先过 execpolicy 解析（rm 加家目录路径，命中敏感路径策略），guardian 评估（家目录不在工作区白名单），审批升级到人；就算策略意外放行，命令还要在沙箱里跑——沙箱的文件系统策略只开放了工作区，~/important 根本不可见，系统调用层面直接失败。同一条命令，一条路上有五道闸，另一条路上有几道取决于你的配置。这就是「信任环境」和「信任配置」在事故面前的差距：前者的闸门是出厂自带的，后者的闸门是你亲手装了几道就是几道。

还有个隐蔽的差异值得单独说：事故的形状不同。Claude Code 的事故是「审批疲劳后的顺手放行」——你点了三百次允许，第三百零一次是错的；Codex 的事故是「策略配置错误导致的静默放行」——execpolicy 的规则写松了，guardian 不再问人。两种事故都不好防，但防法不同：前者靠模式收敛（少用宽模式），后者靠策略 review（把 execpolicy 当代码管理）。

四、使用层的直接建议

建议一：用 acceptEdits 之前，先看一眼你的 git 状态。这个模式下 rm 直通，未提交的工作区没有第二道防线。我的习惯是进宽模式前先 commit 或者 stash，让 git 当那道「事后可恢复」的保险——权限体系拦不住的，版本控制能救回来。这套组合我固定用了很久：宽模式提速、git 兜住不可挽回的操作，两道防线一软一硬。

这个组合还有一个进阶形态：把工作区做成「可抛弃」的。agent 在分支上干活，主分支只接受合并——这样即使 rm 误删了什么，损失上限是一个分支的工作量，而且大概率能在 reflog 里捞回来。权限问题的一半其实是「爆炸半径」问题，把半径控制住，宽模式的风险就从「灾难」降级成「返工」。Codex 用户天然有沙箱控制半径，Claude Code 用户就用 git——工具不同，思路相同。

建议二：团队场景优先 hooks，个人场景优先模式。hooks 的价值在策略复用：一份 PreToolUse 脚本全组共享，比每个人自己配 allowedTools 靠谱。单人使用没必要写 hook，模式加白名单够用。

建议三：跑不可信任务时，沙箱是唯一认真的选项。给开源项目做贡献、跑来路不明的 MCP 工具、让 agent 执行安装脚本——这些场景下「问人」会被点穿，「沙箱」是物理边界。Codex 在这类场景的默认安全水位高一截，这是架构给的，不是提示词给的。

这个建议的反面也成立，值得明说：可信任务别套不可信的待遇。日常开发里对自家代码库的常规操作，全走审批只会训练你条件反射式放行——审批疲劳不是风险的反应，是风险的来源。我的分级是三档：自家代码库常规操作走宽模式（配 git 保险）、涉及网络和安装的任务走默认审批、外部来源的任务走沙箱。档位切换的成本要低（一条命令的事），否则人会偷懒常驻最宽档。

建议四：别把 bypassPermissions 当效率工具。它在 v1.0.88 里的实现就是往模式列表里 push 一个字符串（L364292），没有任何额外防护。开了它，hooks 的 allow/deny 还在，但模式轨的一切默认询问都没了。效率的提升是真实的，防线的拆除也是真实的。

再补一个实战视角：权限体系要定期演练，不演练等于没有。我的做法是每季度做一次「红队半小时」：故意诱导 agent 做越界操作（让它删一个标记为保护的重要目录、让它往配置文件写东西），观察两边各自的拦截表现，记录漏网情况，回头补规则或补策略。这套演练的灵感来自数据备份领域的「恢复演练」——没验证过的防线和没有防线，在事故面前是同一件事。几次演练下来我对两边的体感：Claude Code 的规则语法拦路径类越界很稳，命令拼接类的绕过（比如通过脚本间接操作）要看 hook 覆盖；Codex 的沙箱在文件系统越界上几乎无懈可击，但策略升级（escalate）链路偶尔会给「看起来合理」的请求放行。两边都有缝隙，缝隙的形状不同——这也是「不演练等于没有」的原因：文档不会告诉你缝隙在哪，只有演练会。

最后收个口径：这篇讲的所有「谁更安全」都是机制层对比，不是产品评价。Claude Code 的软约束配 hooks，在「懂配置的个人开发者」手里能达到很高的水位；Codex 的硬隔离在「不配置的默认状态」下就有及格线以上的水位。前者上限高、下限低，后者下限高、上限靠策略运营。评估自己的场景时先问一句：你的用户（包括未来的你）会认真配置吗？会，选前者；不会，选后者。

再看一眼演化方向，能看出两边在互相靠近：Claude Code 2.x 的官方文档里出现了沙箱化执行的内容（二进制化后有了进程隔离的物质基础），Codex 也在补 hooks 这类可编程出口（独立的 hooks crate 已经在 workspace 里）。软约束在变硬，硬隔离在变软——终局大概率是「可编程策略 + 环境隔离」的混合形态，今天两边的差异是这个收敛过程的两个中间态。对选型的含义：别把当前差异当成永久差异，按「你今天需要什么」选，而不是按「谁的理念会赢」选。
