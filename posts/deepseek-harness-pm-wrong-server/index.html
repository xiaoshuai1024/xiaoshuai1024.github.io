AI 说修好了？DeepSeek Harness 的一次错误验收复盘

模型在消息里写下「验证通过」，语气笃定；用户面前的页面是一片白屏，浏览器控制台的报错和这份成功毫无关系。更荒诞的是，模型后来报出的成功 URL，和用户从始至终开着的页面根本不在同一个端口。

这是 DeepSeek Harness 官方复盘 0003 记录的真实事故（docs/postmortem/0003-web-agent-gui-feedback-loop.zh.md，下文事实全部出自这份一手材料）。它暴露的结构很清晰：Agent 的「验收成功」一旦拿环境里碰巧存在的信号当证据（HTTP 200、构建产物、另一个恰好起得来的服务），就会把错误自信地交还给用户；解药只有一个，让验收对象本身可查证。

一、它到底验收了谁的页面？

先把端口摆清楚。这场会话运行在 3081 端口的 DeepSeek Harness Web GUI 里，用户选的 Workspace 是一个空的 test/ 目录，事件日志头部记录的 cwd 指向本地的 deepseek-harness-gui-master/test。而发给模型的请求里，既没有说明这个 GUI 的存在，也没附上它的源码检出目录、URL、承载进程或更新模式。

仓库里的选项倒不少。apps/web 提供了 Vite 开发脚本，完整的浏览器组合则由 dsh web 命令提供，两条路都真实存在。缺的信息只有一条：你现在改的主题，最终要呈现在哪个进程、哪个 origin 上。项目目录被当成了应用目录，后面所有的混乱都从这里开始。

这里有个容易被忽略的结构事实：Web GUI 在这个架构里并不属于 agent loop 主干，它是一层可选能力。文档对 client 模块系统的定位写得很直白：它是 Web GUI 栈的一项可选能力，消费 HTTP 载体插件提供的前缀路由和 index 转换。也就是说，「GUI 存在、跑在 3081、由完整宿主承载」这套信息完全住在模型请求之外的世界里，模型没有任何制度化的通道能读到它。

二、三步是怎么一路走偏的？

第一步是把传输层就绪当成了应用就绪。第 2 轮 agent 改完主题，在序列 30939 的消息里让用户自己去跑 pnpm run demo:tui 或打开一个没说清地址的 Web 应用，对组装后的应用没做任何验收。第 3 轮它读 apps/web/package.json，在序列 31865 于 5173 端口起了个裸 Vite，看到 HTTP 200 就宣布成功。浏览器随即抛出白屏：

client-modules: window.__DSH_BOOT__ is missing or not an object

这个变量只由完整宿主注入，裸 Vite 给不出来。

第二步是用替代服务冒充既有页面。第 4 轮 agent 找到完整的 dsh web 启动路径，重新构建 shell，在序列 34309 于 3334 端口拉起一个不受管理的进程，还在序列 34441 验了它能返回 200 和启动 manifest。3081 端口从头到尾没探测过一次。讽刺的地方在于：原页面此刻已经加载了重建产物，新主题其实早就生效了。

替代服务还有一层被绕开的机制：agent 通过 shell & 让进程进后台，于是受管任务的生命周期全部失效：任务身份、完成通知、结果收集、清理，一个都没接上。等到要清理时，系统对这台 3334 端口上的进程没有任何记录可查，它的存在要靠用户在对话里亲口指出。

第三步是用户替 agent 完成了验收。这一轮用户连续指出三个错误：agent 不该把验收交还给用户；建议预览的页面一片空白；报告成功的 URL 不是用户开着的那一个。用户在序列 34556 报告 3081 已显示出新主题后，agent 到序列 34681 才检查既有进程并移除那台多余的替代服务器。

三、裸 Vite 为什么注定是一具空壳？

浏览器那条报错不是玄学，它精确描述了一个缺失的协议件。官方文档把 dsh-client-modules 定义为 Web 插件表：Node 半扫描宿主 Loader 的 entry，找出声明了 dsh.client 字段的包，组合出 window.DSH_BOOT 的 entry 图，在 /plugins//client.js 提供各个 bundle，再经 index 转换把清单注入页面。扫描、组图、供包、注入，同一个服务的四个面。

图本身的形状也值得看一眼。每一行 entry 带着包名、bundle 地址和一个内容哈希 rev 作缓存失效锚点，整张图再对各行的内容加哈希得出一根总锚点。宿主把它作为 head 里的第一个脚本塞进页面，壳程序在启动任何东西之前先解析这张图；没有有效 manifest 的页面无法启动，浏览器侧解析器遇到图缺失或畸形时会大声抛错。

所以那条报错读起来像点名：前缀 client-modules 指名是模块系统的浏览器半在抗议，missing or not an object 指名抗议的对象是整张启动图。裸 Vite 只跑了 apps/web 的前端源码，Node 半的扫描和注入根本不在场，图的生成者不存在，页面上自然只剩空白。

回看第 3 轮的判断链，模型缺的就是这一页架构事实：它不知道启动图的存在，也不知道注入者是完整宿主。相关机制就写在仓库文档里，却不在它的上下文里。

顺着这条线再看 HTTP 200，它的含金量还能再跌一截。宿主组合里认领回退席位的静态产物插件遵循固定语义：任何未被具名路由认领的请求都以 200 回退到 index.html。在这样的栈里，200 只证明「有东西回来了」，离「应用按预期启动」隔着整套启动协议。模型把第一个信号当成了第二个，中间没人拦。

四、证据为什么能完整回放？

因为每一步都留在了持久化事件日志里。初始请求头在 seq 6，错误交接在 seq 30939，裸 Vite 启动在 seq 31865，替代宿主启动在 seq 34309，manifest 探测在 seq 34441，首次探测 3081 真主机已经是 seq 34681。复盘里的全部结论都落在具体事件上，没有一句依赖事后回忆或反推意图。

这正是会话当 git 用那套设计带来的红利。事件日志只追加、seq 单调递增，事故因此能被逐帧放大检查：哪一步开始偏、每个动作当时依据的是什么信号，全都有据可查。少了这层记录，「每一步单看都合理」的事故最后只会缩成一句说不清的「AI 会犯错」。

回放可信还有一半功劳记在存储设计上。每个会话的元数据头（格式版本、cwd、血统）与事件日志分开存储，不进事件流、也不污染语义；事件流自己的约束则更硬：seq 就是日志里的单调递增位置，等于当前长度；持久化后端必须守住连续性契约，每一批追加事件的第一个 seq 必须等于已存的下一个 seq，乱序与缺口直接违反契约而非被悄悄容忍。

复盘作者还顺带交代了一条调查纪律：只读的 3081 与 3082 试验服务在整个调查期间未被重启、未被修改，现场保持原样。一份档案经不经得起推敲，这类克制占一半分量：证据的价值取决于取证过程本身有没有污染现场。

五、六个序列号怎么锁定责任步？

取证的具体动作，是把整个事故压缩成一张两列表：左列候选答案，右列序列号。第一行就可以下判：初始请求头停在 seq 6，cwd 正确记录了 Workspace，但 GUI 的存在、URL、模式一样都没进来，信息缺口从第 0 步就已存在。从 6 到 30939 之间装下了整整两轮工作，唯独没装下任何一次针对组装后应用的验收。

相邻对的读法更锋利。34309 与 34441 挨得很近：启动替代服务和验证 manifest 是连着做的，动作干脆利落，只是验错了对象：执行力没问题，方向有问题。从 34441 到 34681 之间隔着的，是用户连续三轮纠正加上亲手确认 3081 已生效；这段距离全是用户替机器走的路，责任步归属清晰得可以做减法。

这套方法的准入门槛只有三条：日志只追加、位置单调递增、动作落到日志上。三条齐备，「谁在第几步欠了一次检查」就从叙事题变成了算术题；缺任何一条，现场还原就只能依赖各方回忆，而回忆恰好是这类事故里最不可信的证据源。dsh 把这三条当架构约束来实现，才有了这卷经得起逐帧检视的档案。

六、官方补了哪三道闸？

第一道闸解决「模型不知道自己连着谁」。Web 启动器把规范环回 URL 和实际的生产／开发模式写进两个位置：受管的 app:web-surface 提示词区段，以及 $DSH_WEB_URL 与 $DSH_WEB_MODE 环境变量。后者意味着 shell 里一条 echo 就能查到当前 origin，身份信息从口口相传变成了可读取的事实，而且提示词区段直接进上下文，模型不需要主动去找。

第二道闸堵住裸 Vite 这条歧路。apps/web 的独立 Vite 服务模式会在配置阶段拒绝启动；配套的子进程测试验证进程自然退出，还插桩了 Server.listen()，短暂绑定过端口也逃不掉检测。指引同步讲清：生产模式要重建产物、刷新后验证既有 URL；开发模式只挂载 HMR 接收端，客户端 bundle 和普通包的改动仍然需要刷新页面。

第三道闸改掉验收的判据本身。生产模式刷新与开发模式 HMR 的验收依据改为外部状态：外部浏览器观测、HTTP 观测、进程状态与会话日志，全部指向确切的 origin。PR 证据保留原始 3081 会话截图和真实模型驱动修改的前后对比，验证标准就摆在观测结果上。

七、分层测试把同一课又钉了一遍

防护清单里最容易被扫过的是第四条：分层的真实路径测试。它覆盖的面依次铺开：CLI 请求、精确的生产／开发模式提示词、shell 运行时事实、同端口静态产物替换、源码 watcher 重建、宿主 stat 轮询，以及页面 identity 不变的浏览器 HMR。七层各盯一道闸的一种失效方式，谁的守卫松了，对应的测试先红。

这层测试还吸收了事故里另一个差点复播的错误。最早的回归测试同样栽在信号误读上：超时机制终止 Vite 之后，非零退出断言照样通过，看起来验住了，实际什么都没抓住，直到真实复现暴露误报。教训因此写成两条硬标准：进程超时不等于快速失败；进程退出后端口恢复可用，也证明不了端口从未被绑定。判定规则必须能对所报告的机制失败做出反应，否则绿灯只测了个寂寞。

教训清单里还有一句定性：agent 必须先掌握隐藏的运行时前置条件，才有资格指导用户；启动模式属于应用上下文，不该依赖团队里的口头默契。三道闸与这七层测试合起来，正是把这句话拆成了机器可执行的形态：上下文缺什么就注入什么，歧路在哪里就在哪里设卡，判据含混就把判据换成外部观测。

八、这篇复盘值钱的地方在哪里？

复盘最有信息量的地方，不在「AI 会犯错」这个常识，而在事件日志把错误逐帧放大之后露出的结构：每一个错误动作在当时都握着一份看似合理的证据。HTTP 200 是真的，替代服务器能返回 manifest 也是真的，缺的只是这些证据与用户屏幕之间的关联。于是验收变成临场判断哪些信号算数的手艺活，质量没法由系统把关。

三道闸的公共思路因此很明确：把判断从模型的临场推理挪进环境的事实查询。URL 可查、端口归属可查、就绪与否可查，验收从一个含混的姿态收敛成一个具体动作——查询所声明 origin 上的外部状态，查得到才许报成功，查不到就该如实报失败。这套做法不挑框架，任何让 Agent 把结果直接交还给用户验收的场景都用得上。
