装完 OpenSpec 的 skill 不会用,等于往仓库扔白纸

装上 OpenSpec 的 skill 只是开始,真正的问题是怎么用对它们。

我见过太多人装完 OpenSpec 的 skill 就放着——知道有 /opsx:propose 建变更,剩下五个 skill 全在吃灰,或者用错时机。skill 装得全不等于会用,就像买了全套工具,不等于每把都摸过。

我在「前端 → 全栈 → AI 开发」这条线上一路走过来,OpenSpec 的 skill 是我唯一真正放进日常流程的规格驱动工具。这篇文章就把这六个 skill 按真实使用顺序逐个讲透:每个解决什么问题、产出什么、什么时候用、怎么和前后衔接。

结论是:这六个 skill 不是六个独立工具,是一条流水线。 想法进来,经过 explore → propose → update → apply → sync → archive 六道工序,变成主规格里沉淀下来的能力。每一步的产物,都是下一步的输入。

下面我用一条真实的改动走完整条流水线:给一个查询功能加缓存。它不涉及任何具体业务,就是个最常见的编程场景——查询太慢,想加一层缓存。这条改动小到看得懂,又完整到每一步 skill 都有对应动作。

先认识四个产出物

讲 skill 之前,得先认识它们操作的对象。OpenSpec 把一次改动固化成一个 change,里面是四个文件,放进仓库的 openspec/changes/<名字>/ 目录。四件套是流水线反复操作的工件:

  • proposal.md——为什么改、改什么、影响什么,相当于立项报告
  • specs/<能力>/spec.md——系统必须做什么,是增量规格,只声明本次改的行为
  • design.md——怎么做、权衡了什么,是决策留痕
  • tasks.md——按什么顺序做,是执行计划

四件事混在一份文档里,就是一份没人能维护的巨型需求书;拆开,每一件都能单独演进、单独 review、单独归档。四个产出物是你和 AI 之间的合同,后面的 skill 全部围着它们转。

第一个:explore——想清楚再动手

流水线的入口不是建变更,是 explore。它是个思考模式,不写代码、不建 change,只做一件事:把模糊的想法摊开,变成可以写进 proposal 的共识。

什么时候值得先 explore?判断标准是三条:改动牵扯多个模块、你还没想清楚边界、或者「要不要做」本身没定。这三条占一条,直接 propose 大概率产出空洞的四件套——spec 的场景编不圆,是因为需求本身没成形。

explore 的边界很明确:它只探索,不实现。 如果聊着聊着冒出一个明确的实现方向,正确做法是退出 explore,去走 propose 流程,把探索出来的结论固化成变更。探索的产物不是文件,是写 proposal 的原料。

explore 具体怎么用?我的套路是让它读代码、画结构、列问题,把模糊的表述变成能拍板的事实。它不写代码,但可以读代码——把相关模块翻一遍,把「查询太慢」落到「到底是哪一层慢、调用链什么样」,问题就从一句话变成一张图。

我用 explore 最多的地方,是把「要不要做」这个决定本身聊透。还是用加缓存举例,需求一句话:「查询太慢,加个缓存。」先摊开几个问题:

  • 缓存的粒度是查询结果还是整页?这决定 change 的边界
  • 数据多久变一次?这决定缓存失效策略是 TTL 还是主动失效
  • 缓存穿透、雪崩要不要处理?这决定实现复杂度
  • 查询分布在几个实例?这决定进程内缓存会不会不一致

这四个问题的答案,直接决定 change 长什么样。想清楚,四件套就好写;不想,spec 里每个场景都得靠猜。

explore 还有个隐藏价值:它经常帮我「问掉」一个 change。想清楚之后发现收益不值成本,直接放弃立项——这比建了 change 做一半再废弃省太多。探不明,别立项,这是流水线里最容易被跳过、又最省钱的一步。

第二个:propose——一次生成四件套

propose 是立项,也是唯一能一次生成全部四件套的 skill。它的工作流背后是几个 openspec 命令,理解它们,你就理解了 propose 在干什么。

第一步,openspec new change "<名字>" 建变更目录。名字用 kebab-case——加缓存,就叫 add-query-cache。

第二步,openspec status --change <名字> --json 拿到依赖顺序。第三步,openspec instructions <产物名> --change <名字> --json 逐个取模板和规则,照模板填充。最后 openspec status 确认全部就绪。

propose 最有价值的一点,是它强迫你按依赖顺序走。 四个产出物不是平级的:proposal 先写,spec 依赖它,design 依赖 spec,tasks 最后。你不能先写 design 再补 proposal——工具会告诉你当前哪个产出物的依赖还没满足。这个约束治好了我「想到哪写到哪」的老毛病:先立边界,再写契约,再谈权衡,最后排顺序。

这里值得说透一件事:skill 本身不写文件,它是一层封装,真正干活的是背后那几条 openspec 命令。status 返回当前状态和依赖,instructions 返回某个产出物的模板、规则、指令,skill 把它们读进来、按模板填充、写进指定路径。

所以你要排查问题,直接手跑 openspec status --change <名字> --json 和 openspec instructions proposal --change <名字> --json,就能看到 skill 看到的全部信息——这不是黑盒,每一步都透明可查。skill 替你做的,是把「读 JSON、判断依赖、套模板」这些重复动作收敛成一步,而不是给你一个猜不透的魔法。

四件套里我最花心思的是 spec,因为它最反直觉。它不写实现,写行为,用固定的 WHEN/THEN 格式:

### Requirement: 缓存查询结果
The system SHALL cache query results by key.

#### Scenario: 命中缓存 → 返回缓存值
- **WHEN** 查询键在缓存中存在
- **THEN** 系统返回缓存值,不执行底层查询

#### Scenario: 缓存未命中 → 执行查询并写入缓存
- **WHEN** 查询键在缓存中不存在
- **THEN** 系统执行底层查询,并把结果写入缓存

一个 WHEN/THEN 场景就是一个最小验收用例:AI 实现完,你照着场景逐条测,能过就是改对了。同一个规格,既是指令又是试卷。

写 spec 最容易犯的错,是把实现细节塞进来——比如「调用 Redis 的 GET 命令」。那是实现,不是行为。行为是「缓存命中的时候返回缓存值,不碰底层查询」。写实现细节有两个坏处:AI 会照着字面抄,你换存储它不会跟;验收时你核对的是实现姿势,不是真实效果。规格只写 WHAT,把 HOW 留给 design 和代码。

四件套其余三件,各有一个要点值得说。

proposal 的关键是写清 Non-Goals。加缓存这件事,Why 是「查询太慢」,What Changes 是「加一层查询缓存」,但真正挡住 scope creep 的是 Non-Goals——明确「不做整页缓存」「不处理跨节点一致性问题」。写清不做什么,和写清做什么一样重要,它防止 AI 自作主张把改动扩大。

design 的关键是写「为什么」,不是写「是什么」。缓存方案用进程内还是 Redis?我选 Redis,理由是「查询分布在多个实例,进程内缓存会不一致」——这个理由本身比结论值钱。design 里每个决策都该是「我选了 A,因为 B 和 C 不可行,依据是 D」的结构。这些权衡不落盘,下次接手的人会重新踩一遍。

tasks 的关键是把「摸清真相」放最前面。加缓存第一步不是写代码,是确认查询入口在哪、有哪些调用方、数据变更怎么通知缓存失效——先把事实探明,再排实现任务。AI 编程里最贵的是「没搞清事实就动手」,tasks 把「先探明真相」变成明文要求。

第三个:update——改主意了怎么办

需求会变,计划也是。实现到一半发现设计有问题,或者需求变了——这时候不需要推倒重来,用 update 修订既有计划。

update 做的事,是把四件套拉回来保持自洽。你改 design 里的一个决策,spec 的场景可能对不上,proposal 的边界可能失效。update 会检查它们之间的一致性,把该跟着改的都改掉,而不是让你改完 design 就以为完事。

比如我给缓存方案做 update:原本定了 Redis,后来发现这个查询频率低、不值得引入中间件,改成进程内缓存。这个改动不止是 design 换一行——spec 里「缓存失效」场景的处理方式要跟着变,proposal 的 Impact 也要去掉 Redis 依赖。update 会把这几处联动都指出来。

这里有一条重要的分界线:update 是修订,不是重写。 如果改动已经偏离原需求太多,plan 已经烂到缝补不如重来,update 会建议你新开一个 change,而不是硬在一个旧变更上打补丁。判断标准是「改动是否改变了变更的意图本身」——加一个缓存场景、换个存储方案,是修订;从「加缓存」变成「重构查询层」,是重写。

update 的另一个用途是当「回顾检查」用。四件套写完、实现之前,我会主动跑一次 update 式的自检:proposal 的边界和 spec 的场景对不对得上,design 的决策有没有真的在 spec 里落地。这一轮自检能挡掉不少「写完了才发现 spec 和 proposal 打架」的返工。

我在 apply 过程中发现规格和实现对不上,标准动作就是回到 update 改计划,而不是直接改代码绕过规格。规格是合同,合同错了改合同,不能偷偷改施工图。

第四个:apply——照规格施工

四件套齐了,apply 开始实现。它先 openspec instructions apply --change <名字> --json,拿到上下文文件(四件套的路径)和任务清单,然后逐条实现 tasks.md 里的任务,每完成一个勾一个。

apply 有两个纪律值得记住。

第一,每完成一个任务立刻勾选。 - [ ] 变成 - [x],进度即时可查,中断了也能精确续上。这不是仪式感——tasks 是给 apply 自己读的,勾选状态就是它的记忆。我中断过一个任务,第二天回来直接看 tasks,哪步做完了、哪步卡着,一目了然。

第二,遇到不确定就暂停,别猜。 任务描述不清晰、实现暴露出设计问题、或者有阻塞,apply 都会停下来问你。它不会为了「看起来在推进」而硬猜,因为猜错的成本远高于停下来问一句的成本。加缓存时我就在 tasks 里遇到过一个模糊项「处理缓存穿透」——穿透的定义、要处理到什么程度,都得先对齐再动手。

apply 的暂停不是失败,是它设计的一部分。skill 里明确定义了三种暂停场景:任务本身不清晰、实现时发现规格有硬伤、或者撞上外部阻塞。暂停时它会给你当前进度和选项,而不是闷头继续。这个「停下来问」的姿态,比「闭眼往前冲」更能守住质量底线——宁可慢一步,不把错做下去。

第五个:sync——把增量规格并进主规格

实现完了,四件套里的增量规格要沉淀进系统。这就轮到 sync——把 changes/<名字>/specs/ 下的增量规格,智能合并进 openspec/specs/<能力>/spec.md 主规格。

增量规格用段首标记声明本次改了什么:

  • ## ADDED Requirements——新增的行为
  • ## MODIFIED Requirements——给已有行为加场景
  • ## REMOVED Requirements——废弃的行为
  • ## RENAMED Requirements——重命名的行为

sync 的合并是智能合并,不是整文件覆盖:ADDED 的加进去,MODIFIED 的改掉对应场景,REMOVED 的删掉,主规格里没提到的场景原样保留。将来要给缓存加「只读模式」,就在对应 requirement 下加一个新场景,其余几条原样不动——增量合并只改你声明过的,没提的绝不误伤。

「智能」具体体现在一个地方:MODIFIED 不是整段替换,是只补增量里的场景。比如主规格里「缓存查询结果」这条 requirement 原本挂了三个场景,增量里只声明了「加一个命中缓存的场景」,合并时只把这个场景塞进去,另外两个原样留着。这和程序化合并「按块覆盖」的本质区别——它不是把主规格当白板重写,是在既有契约上精准打补丁。

这里有个细节值得注意:主规格和增量规格是两种格式。增量规格带着 ## ADDED 这类段首标记,合并进主规格后,标记被剥掉,所有 requirement 归拢到统一的 ## Requirements 段下——主规格永远是一份干净的、可直接阅读的能力清单,不会残留「这次加」「上次改」的痕迹。

主规格的格式固定成三块:# <能力> Specification 标题、## Purpose 用途、## Requirements 全部行为。任何一次 sync 或 archive 都遵循这个形状。这带来的一个隐性好处是:主规格格式统一,意味着它天然可被程序读取——不管是人 review,还是 AI 后续拿它当上下文,看到的都是同一份结构稳定的契约,不会因为每轮变更的写法不同而解析困难。

这个机制的价值在能力随变更持续沉淀。每完成一个变更,主规格就长厚一点。下次要改同一个能力,先读主规格——它不是过时的文档,是跟着每次变更同步进化的「能力宪法」。这套设计和 Git 是同构的:git 管代码的变更历史,主规格管行为的变更历史。规格和代码同生命周期,这比任何独立的设计文档平台都可靠。

第六个:archive——归档并确认沉淀

archive 是流水线的最后一站,它做两件事:同步增量规格到主规格,然后把整个 change 移进 archive/ 目录,按 YYYY-MM-DD-<名字> 命名归档。

归档前 archive 会检查两件事:四件套是否齐全、tasks 是否全部勾选。有不齐的,它会警告并让你确认,而不是静默跳过——因为归档意味着这份合同的历史使命结束,带着未完成的任务归档,等于把烂账埋起来。

这个「警告而非阻止」的设计值得留意。archive 默认不拦你——它把状态摊开,把后果说清楚,决定权交给你。带两个未完成任务归档,可能是「那些任务本来就不该做,但懒得删」,也可能是「漏了」。两种情况的处理不一样,所以它不替你选,只保证你选的时候是知情地选。

我归档完习惯先 git diff 看一眼主规格——如果合并出来不是我想要的样子,还能回滚;而变更历史留在 archive 里,哪条行为是哪个 change 加的,随时能查。归档不是终点,是这条能力的又一次沉淀。

配套命令:status、validate、list

六个 skill 之外,还有三个命令值得日常使用,它们不封装在 skill 里,是手工查状态的工具。

  • openspec list——列出当前所有变更,按最近修改排序
  • openspec status --change <名字> --json——看单个变更的产物依赖和完成情况
  • openspec validate——校验变更的格式,spec 有没有写错段首标记、场景引用对不对

这三个命令解决了 skill 流程之外的场景:比如 list 帮你回答「我手上到底有几个没归档的变更」,status 帮你确认「这个变更现在卡在哪个产物」,validate 在归档前补扫一遍格式。skill 是流程,命令是检查——流程负责走,命令负责确认走得对不对。

把它们和 skill 的分工记住,你就不会在「要不要手动跑命令」上纠结:日常走流程用 skill,涉及状态确认、格式校验、批量盘点时,直接命令更快。两条路通往同一个事实,因为 skill 本身就是这些命令的封装。

什么时候别用这套

六个 skill 的流水线有成本:propose 要写四件套,update 要维护自洽,archive 要合并归档。用得不对,流程就成了负担。

我的判断标准很简单,改动满足下面任一条,才值得走完整流水线:

  • 跨多个文件,或者牵扯到现有能力的行为变化
  • 有外部可见副作用
  • 需要决策留痕,或者验收标准不清晰

反过来,单文件小修、纯改排版、一句话能说清的,直接改就行。我曾经想给每个小修复都建一个变更,很快就发现重了——四件套写的时间比改代码还长,那是本末倒置。

这套流水线的真实成本在哪?propose 写四件套是一次性投入,update 维护自洽是持续投入,archive 合并归档是收尾投入——三笔加起来,一个中等复杂度的改动要花小半天。这个成本对「改一个 bug」「调一个样式」是浪费,对「跨模块加能力」「动核心行为」则是便宜的保险。算清这笔账,你就不会两极化——既不无脑套流程,也不全盘拒绝。

还有个边界值得想:这套流水线对「不存在的需求」也没用。如果你自己都没想清楚为什么要改,proposal 写出来就是空洞的,spec 的场景怎么编都编不圆。它放大的是你已有的判断力,替代不了。

至于适配团队,我的体会是这套流程单人效率最高——四件套的写、归档的合并,都是一个人的连贯动作。多人协作时需要约定「谁负责 update」「合并冲突归谁」,否则流水线会多出协调成本。但哪怕单人,也要守它的纪律,否则就只是多了三份没人读的文档。

三个反模式,踩过就回不去:

  • 把 spec 写成实现细节。场景里写「调哪个接口、用什么数据结构」,AI 照抄不思考,你换技术栈它不会跟。规格写行为,不写姿势。
  • 跳过 explore 直接 propose。需求还是模糊的就立项,四件套全靠猜,后面每一步都在为这个仓促买单。探不明,别立项。
  • 改完代码不 sync。实现完了,增量规格还躺在 change 里,主规格停在半年前。规格和代码脱节,流水线就白走了。

这套流水线跑顺后,我得到了什么

把这六个 skill 放进日常,最大的变化不是「写得更快」,是每一步都有据可查。

propose 逼我在动手前把边界和契约说清;update 让计划跟得上变化;apply 让我不再靠「感觉它改对了」验收,而是照着 spec 的场景逐条核对;sync 让能力持续沉淀,下次改同一个地方先读主规格而不是翻聊天记录;archive 让每笔变更都有档案。

规格驱动的本质,是给 AI 编程的不确定性装上验收。对话式编程把质量押在 AI 的临场发挥上,规格驱动把质量押在事先说清的契约上。人负责把合同写清楚,AI 负责照着施工,双方各司其职。

一个我反复遇到的细节最能说明这套流水线的价值:AI 实现完后,我拿着 spec 的场景逐条问「这条过没过」——命中缓存、未命中写缓存、失效重查,每一条都能指回四件套里的某个 WHEN/THEN。我不是在「感觉它改对了」,是照着自己签的合同逐条核对。

这不是给 AI 上锁。相反,它让 AI 可以更大胆地干活——因为每一步都有据可查,错了能定位,对了能沉淀。

我给自己留了三条复述这套流水线的心智模型,每次要用它之前先过一遍:

  • 规格是合同,不是文档。文档给人读,合同给 AI 和人共同验收,谁都能拿它当验收基准。
  • 先写做什么,再写怎么做。顺序反了,AI 的高效就变成高速做错事的效率。
  • 增量规格让能力持续沉淀。每次变更长进主规格,仓库就是会自我生长的「能力宪法」。

这三条,加上六个 skill 各自「探不明别立项、改合同别改施工图、没沉淀别归档」的教训,就是这篇文章想让你带走的。
