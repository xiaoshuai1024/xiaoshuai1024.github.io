让 agent 干活的都见过这类场面：让它改个配置，它顺手动了测试文件；让它加个功能，它把三个模块的重构一起做了；让它查个问题，它给出两套自相矛盾的结论。

遇到这种问题，多数人的第一反应是换更强的模型、写更细的提示词。我的做法不一样：先搞清楚翻车的根源在哪。根源不在模型——模型聪明得很。根源在环境：agent 干活的每一步，没有人在旁边立规矩。

这篇文章讲的就是我在这个过程中挖到的一个项目。它把「给 agent 搭环境」这件事，做成了一座能安装的仓库。

一、翻车不怪模型，怪环境里没有「停」

资深工程师干活为什么不翻车？他周围的工程环境在替他踩刹车——规范文档告诉他边界在哪，代码审查在他出错时拦住他，测试在他改坏时叫醒他。刹车踩得准的人，干得不一定快，但翻不了车。agent 缺的正是这套环境。给 agent 搭这套环境，就是 harness 这个词的全部含义。

2026 年上半年，skill 仓库扎堆冲上 10 万星：官方 anthropics/skills 16.7 万，mattpocock/skills 21 万，ECC 24 万——三个 20 万级仓库一年之内全冒出来。这在前端框架身上见过，在配置仓库身上是头一回。星数把「怎么用 AI 干活」推成了现象级话题，也让 skill 仓库从个人经验分享变成了一场生态竞赛。ECC 是这场竞赛里跑得最快的那个。

二、ECC：一个 24 万星的 agent 工程操作系统

这个项目是 affaan-m/ECC，全称 everything-claude-code，作者 Affaan Mustafa，在 Anthropic 黑客松上用 Claude Code 8 小时做出产品夺冠的开发者——冠军奖是 1.5 万美元的 API 额度，他拿它继续打磨这套工作流。打磨了 10 个月之后开源，MIT 协议，GitHub 上 24 万 Star，8 个月超过 Linux 内核。

仓库简介一句话：the agent harness performance optimization system——agent 运行环境的性能优化系统，给 agent 搭运行环境，让它每一步都有人管。

这 10 个月的分量在于：仓库里的东西不是拼凑的教程合集，是一个人天天高强度用 agent 干活、持续修正出来的配置。用出来的东西和写出来的东西，成色不一样。

先看整体结构。整仓库由五块组成：

  • skills：284 个，覆盖 12 种语言的约定和通用工作流，是仓库的主体
  • agents：68 个，每个是一份定制角色文件，比如 planner、code-reviewer、build-error-resolver
  • instincts：从会话里自动提取可复用模式，按置信度存储，攒够了聚类成新 skill
  • memory：Memory Vault，跨会话、跨工具的记忆与交接
  • security：AgentShield，102 条静态规则加 1282 个测试，专扫 AI 写的代码和配置

这五块不是绑在 Claude Code 上，而是通过一套 DRY Adapter 挂在十几个 harness 上——Claude Code、Codex、Cursor、OpenCode、Gemini、Zed、Copilot，甚至 Qwen、Hermes、Kimi。仓库根目录一排 .claude、.codex、.cursor 文件夹，同一套 skill 定义翻译成各家的配置格式。

安装简单到不像一个 24 万 Star 的项目。官方路径一条命令：/plugin marketplace add https://github.com/affaan-m/ECC 再 /plugin install ecc@ecc。装完跑 /ecc:configure-ecc 做一次交互式配置，选好你的技术栈和要装的组件，就绪。轻量用户走 --profile minimal，只要规则和角色，不要运行时 hooks。最轻的一档是问它的内置顾问：

node scripts/ecc.js consult "security reviews" --target claude

一句话说出你要什么，顾问从 284 个 skill 里挑出匹配的那几个。一个仓库内置了「帮你在自己身上挑零件」的工具，这个设计本身就说明作者清楚全套装有多重。

装完之后跑一次 /ecc:configure-ecc，它会带着你把关键项过一遍：技术栈选哪些、规则装哪些、hook 开哪些。装是整包装的，用是裁剪过的，这套「装完再配」的流程是 ECC 和一堆「clone 下来自己看着办」的 skill 仓库拉开差距的地方。

三、ECC 能做什么

拆开看之前，先说它能干什么。README 里有一张「Without a system vs With ECC」的对照表，我翻译过来，比任何介绍都直观：

没有系统时有 ECC 之后
计划消失在聊天记录里计划先落成可编辑的文档，再动手实现
「记得写测试」是一句会被忘掉的嘱咐TDD 变成红绿重构的门禁流程，每一步带着证据
同一份上下文既写代码又审查自己全新上下文的 reviewer 专门找盲区和回归
记忆等于存一整个聊天记录会话被蒸馏成摘要、instinct 和可复用 skill
质量检查靠人提醒hooks 在模型上下文之外强制执行
agent 配置默认可信AgentShield 把 harness 本身当攻击面扫

六行对照，每行都是一个能力。把六行归拢一下，ECC 能做的就四个词：计划（先把事想清楚）、证据（每步有东西可查）、隔离（写和审分开）、扫描（安全不靠自觉）。对照表前两行讲的是同一件事：把「脑子里想的」先变成「纸上写的」。没有系统时，计划和「记得写测试」都活在你和 agent 的对话里，随聊天记录一起消失；有了 ECC，/ecc:plan 先把计划落成可编辑的文档，确认之后才动手，测试门禁挡在实现之前。记忆那一行也是同理：存一整个聊天记录等于没存，蒸馏成摘要和 skill 才有复用价值。

挑两个最有代表性的展开。

一个是 TDD 证据链。/ecc:plan 把需求先变成可确认的计划，然后激活 tdd-workflow：先记录 RED 失败的证据，再实现到 GREEN，然后从全新上下文做审查，修复发现的问题并补回归测试，最后验证构建、lint、类型和测试全绿。产出的不只是代码，是一条证据链：计划、失败的测试、通过的测试、审查发现、最终验证。这解决了「agent 说做完了」最不可信的问题——每一步都有东西可查。

多 agent 分工是第二个能力。同一个需求，planner 出计划、tdd-guide 带着写测试、code-reviewer 用全新上下文审查——三个角色三个上下文，互相不串味。规划的人不写实现，写实现的人不审自己，工程上的职责分离被原样套到了 agent 身上。

安全扫描是第三个。不用装全套，npx 直接跑：

npx -y ecc-agentshield scan --path .

扫的是硬编码密钥、权限过宽的配置、hook 注入这类人工审查容易漏的点。配套的还有 /context-budget 查上下文压力——窗口还剩多少额度、哪些东西占了最多，一目了然。这些能力有个共同点：都在模型上下文之外起作用，不靠 agent 自觉。

另一个是跨工具记忆。Memory Vault 用一个本地 markdown 格式，让 Claude、Codex、Hermes 这些工具共享同一份项目记忆和交接文档：

ecc memory init --scope project
ecc memory handoff --from hermes --target codex --title "继续认证迁移"
ecc memory search "authentication migration"

一个工具干到一半的活，另一个工具接着干，上下文不丢。多工具横跳的人，光这一条就值回安装成本。

把能力合起来走一遍更直观：让 agent 给订单服务加一个查询接口。你刚说完需求，/ecc:plan 先把计划落成文档，你确认后 tdd-workflow 激活——先写失败测试，再实现到通过。写完 code-reviewer 从全新上下文审一遍，AgentShield 再扫一遍安全。全部通过，SessionStop 把这次的决策写回记忆。每一步都有一个机制在岗，没有一步靠 agent 自觉，翻车的空间被压到最小。

四、README 的含金量

我拆过不少 skill 仓库，这个 README 是信息密度最高的一个。十一万字节，四处值得逐页读。

第一处是安装页。三条路径写得清清楚楚——插件方式、install.sh 按 profile、consult 顾问——还特意标了「每个 harness 只选一条路」，叠加安装会出重复 hooks。更少见的是官方安全警告：只从官方渠道安装，第三方镜像可能含恶意软件。把坑明说，这是对用户负责。

第二处是 Start Using 速查表。它把「你在做什么」直接映射到入口：开发功能走 /ecc:plan 加 tdd-workflow，修 bug 先写失败测试，审查新代码走 /code-review，修构建走 /build-fix，清理代码走 /refactor-clean，检查上下文压力走 /context-budget，长会话收尾走 /save-session 存档、/resume-session 恢复。新手不用读文档，照着这张表就能用起来。这张表也暴露了作者的意图：skill 是主要工作流，命令只是入口和兼容垫片。

第三处是「Which agent should I use」表。每个入口背后是哪个 agent 在干活，写得一清二楚——/ecc:plan 背后是 planner，/code-review 背后是 code-reviewer，/security-scan 背后是 security-reviewer。这不是装饰，是让你知道钱花在哪、活派给了谁。

第四处是 Key Concepts 一节。它用一张表讲清五个概念的分工：skills 按需加载、agents 独立上下文干活、rules 常驻、hooks 在模型之外执行、instincts 带置信度召回。能把这套分工讲清楚，说明作者想明白了自己造的是什么。

第五处是 What’s Inside 的带注释目录。这不是普通的文件清单——每个目录、每个 skill、每个 agent 后面都跟着一句用途注解，agents 目录逐个标了 planner 管什么、harness-optimizer 管什么。对着这份目录逛一遍，等于把整个仓库的骨架读完了。

Memory Vault 一节里还有一句含金量很高的话：memory 是未经审查的上下文，不是可执行策略。意思是 AI 存下来的记忆，只能当参考资料，不能当规矩执行；重要的结论要先经人审查，再提升成项目文档。把「记忆的信任边界」这种细节写进 README 的仓库，一只手数得过来。

更新日志也值得扫一眼。v2.0 版本号后面写的是「The Agent Harness Operating System」——我这个标题的出处。商业信息同样写得不藏着：MIT 免费开源，ECC Pro 私有仓订阅 19 刀一个席位，赞助商名单公开。钱从哪来写得明明白白，这比「为爱发电」可靠。

五、284 个 skill 里，值得认识的几类

284 个 skill 按语言铺开，但结构很有规律。一个语言是一套四件套：patterns（约定）、security（安全）、tdd（测试驱动）、verification（验证）。Spring Boot 一套，Django 一套，Laravel 一套，Quarkus 一套，格式完全一致。

四件套的分工也很清楚：patterns 是该语言的写法约定，比如 JPA 怎么映射、事务怎么开；security 是该语言的安全清单，常见的注入和越权点列在明面上；tdd 是把测试先行套进这门语言的测试框架里；verification 是改完之后的验证环。换语言时零学习成本——你会用 Spring Boot 那套，就会用 Django 那套，因为骨架一模一样。你只需要认识自己那套。

跨语言的通用件里，有几类成色不错：

  • 设计审查类：api-design（REST 约定）、database-migrations（迁移模式）、jpa-patterns、postgres-patterns、deployment-patterns（CI/CD、回滚）、docker-patterns。单领域约定，拿来改改就能用。
  • 质量门禁类：tdd-workflow（红绿门禁）、eval-harness（验证循环）、security-review、security-scan（AgentShield 集成）、e2e-testing（Playwright 模式）。这类是纪律，值得重点看——它们解决的不是「怎么写」，是「怎么信」。
  • 内容与调研类：article-writing（去掉通用 AI 味的写作）、content-engine（多平台内容）、market-research（带来源的研究）。它不只是编程仓库，写作和投研的工作流也在里面，甚至还有 investor-materials 这种融资材料件。写博客的人看到 article-writing 会心一笑——「去掉通用 AI 味」这句话，它写在了 skill 描述里。
  • 特色件：cost-aware-llm-pipeline（按任务路由便宜模型、跟踪预算）、regex-vs-llm-structured-text（正则还是 LLM 的决策框架）、videodb（音视频处理）。这类体现作者的工程品味，别处见不到。

agents 那边同样有料：planner 管计划、architect 管架构决策、tdd-guide 管测试、code-reviewer 管审查、security-reviewer 管漏洞、build-error-resolver 管构建报错，再加一排语言专属 reviewer——java-reviewer 专审 Java 和 Spring Boot 代码，database-reviewer 专审数据库查询，连 HarmonyOS 应用都有专属的 app-resolver。68 个角色的分类标准一句话：它在这个项目里对什么负责。

还有两个元技能值得一提。configure-ecc 是装完之后的交互式配置向导，security-scan 是把 AgentShield 接进日常的开关。元技能的存在说明作者把「装」和「用」也当成了工作流在管——装完只是开始，配好才算是自己的。

六、我建议从这几个开始装

装东西前先套我的标准：每个 skill 都得答得上「它替我拦住了哪一步会翻车的操作」，答不上来就不装。按这个标准，从 ECC 里挑出这几个：

  1. memory hooks。SessionStart 读入项目状态、SessionStop 写回进度，机制简单、收益确定，和任何体系都兼容，最值得直接拿走的一块。
  2. code-reviewer。带防御基线的新鲜上下文审查——不得泄露密钥、不得输出可执行代码、外部数据当不可信输入，几条铁律直接拷进你自己的 review skill，白赚一套 prompt 层防线。
  3. security-review 加 security-scan。安全清单加 AgentShield 集成，把「写代码注意安全」变成每次必跑的检查，高危项（密钥、越权、hook 注入）列在明面上。
  4. api-design。单领域约定的范本，拷进项目改触发词、补上你团队的错误码表就能用，十分钟的事。
  5. tdd-workflow。红绿门禁流程，配合你项目现有的测试基建，治「agent 说做完了」的毛病。
  6. 你技术栈的那套四件套。栈是 Spring Boot，就装 springboot-patterns、springboot-security、springboot-tdd、springboot-verification，其余语言的别碰——跨语言件是纯上下文税。
  7. cost-aware-llm-pipeline（可选）。任务多到开始关心 token 账单时再上，它按任务路由便宜模型、跟踪预算。

七个起步，加一个原则：minimal profile 起步，consult 顾问挑货，装完跑一个小任务看看哪块真的被触发了、哪块只是躺在目录里占 token。三个月没触发过的，无论出处多响亮，都摘掉。

这七个不是随便挑的，按拦截点分：memory 拦「忘了」，code-reviewer 拦「写歪了」，security 拦「埋雷了」，api-design 拦「发明轮子」，tdd 拦「没验证」，四件套拦「不合栈」，cost 拦「烧钱」。七个拦截点，覆盖 agent 翻车的七个主要姿势。拦得住，才快得起来。

七、三个 20 万级仓库，三种哲学

把 ECC 放进坐标系里看更清楚：

仓库星数哲学解决的问题
anthropics/skills16.7 万少而权威skill 长什么样，定义格式
mattpocock/skills21 万小而准skill 怎么组织，一条 SDLC 主线
affaan-m/ECC24 万大而全全都给你，一个全家桶

官方给新手定标准，mattpocock 给单人开发者立流程，ECC 给「什么都想要」的人一个起点——以及给懂行的人一座零件库。注意一个细节：ECC 的 skill 文件里带着 metadata: origin: ECC 标记，格式上完全兼容官方标准。它没有另立山头，而是在官方格式之上做工程化，这是生态成熟的表现——格式归官方管，工程各凭本事。三个仓库的维护者也是三种节奏：官方背后是 Anthropic 的标准委员会，节奏稳；mattpocock 一个人管 25 个 skill，每个都打磨到位；ECC 也是一个人，每周往十几个 harness 发货，靠 1282 个测试和社区 Issues 当质量网。三个仓库的正确打开顺序：先用官方仓库把 SKILL.md 格式学标准，再用 mattpocock 的 25 个 skill 学「怎么把判断排成流程」，最后把 ECC 当零件库拆着用。顺序反了会吃亏。

八、ECC 的代价

一个 24 万星的仓库，它的缺点和它的规模一样大。

上下文税排在第一位。180 个 skill 光 frontmatter 元数据就占 1.8 万到 3.6 万 token——一个 SKILL.md 的 frontmatter 三五行、100 到 200 token，284 个就是 3 到 5 万，扣掉按 profile 裁剪的，落在 2 到 4 万之间。模型每轮对话都要把这批「目录」读一遍才知道自己有哪些技能可用，200k 的窗口被压到 70k 也不奇怪。所以仓库里塞满了灭活开关，需要这么多「关掉我」的开关，本身就说明默认状态太重。这个问题的解法只有裁剪，没有捷径。

概率触发是第二个。藏在 continuous-learning 的 SKILL.md 里最诚实的一句话：v1 版本承认技能触发是概率性的，大约 50% 到 80% 的时间才会被加载，v2 改用 hooks 是因为 hooks 100% 可靠。

原因在机制上：skill 的加载靠模型自行判断触发描述匹不匹配，判断权在模型手里，就有漏判。hooks 是生命周期事件到点必触发，没有判断环节。这也解释了我的体系里纪律性 skill 为什么全挂在 hook、CLAUDE.md 硬约束、命令前缀这些确定性机制上——约束一旦依赖模型自觉，就有了失灵率。对追求交付一致性的团队来说，「约束有 20% 到 50% 的概率不生效」是灾难。

安装陷阱是第三个。插件和 install.sh 两条路径叠加会产生重复 hooks，rules 文件还得手动复制，官方贴着「只从官方渠道安装」的警告，README 里也写着完整的引导式安装要等 2.2 版本。星数泡沫是第四个——8 个月 24 万星的曲线远超配置类项目常态，Discussions 冷清、Issues 热闹。我的态度是这件事不重要，星数虚不虚不影响仓库里有真东西，但被星数推上神坛的仓库会让新人产生「装了就和作者一样强」的错觉，这才是实际危害。

四个代价同一条根：默认配置太贪。作者自己在 README 里给的解法也是「挑适合自己的、删掉用不上的、再加自己的」——这已经承认了正确用法是拆着用。

九、我的判断：这套东西好在哪、缺什么

好在三点。第一，它把「agent 工程环境」从玄学变成了仓库——安全、记忆、学习、跨工具这些方向，它全部趟了一遍，我拆完最大的收获不是装了它，是把它的目录结构当成了参考地图。四件套的组织方式、agents 的职责分类、README 的分层写法，抄的就是这些思路，不是文件本身。第二，工程化程度高，102 条安全规则配 1282 个测试，单维护者敢每周往十几个 harness 发货，靠的就是这套测试和社区反馈当质量网。一个配置仓库舍得在测试上花这个力气，是因为安全规则误报一次，信任就塌一次。第三，README 的诚实度——把安装坑、触发概率、安全警告全写进去，这份自知之明在开源项目里不多见。

缺什么也三点。第一，默认状态太重，上下文税和灭活开关的数量成正比。第二，instincts 的自动攒 skill 还不到能用的时候——skill 的准确率比数量重要，攒出一堆半成品不如一个月手工打磨一个。第三，概率触发的机制缺陷它自己清楚，但除 hooks 之外没有根治，skill 加载的最后一跳始终靠模型自觉，这个洞就一直在。

所以我的用法是零件单取：memory hooks 和 code-reviewer 的防御基线直接抄，安全规则当检查表用，api-design 拷进项目改触发词就能用，全家桶不碰。这和它 24 万星之间最拧巴的地方也在这里：它把「一切现成」当作卖点，而 skill 体系最值钱的部分恰恰不可能现成。

十、它回答了什么

回到开头的问题：agent 干活不老实，翻在哪？

翻在环境。模型负责聪明，环境负责刹车，ECC 做的事就是把「给 agent 搭环境」从一门手艺变成一座仓库——安全怎么管、记忆怎么存、角色怎么拆、跨工具怎么适配，它都给出了可安装的答案。这个项目证明了一件事：把工程师的护栏做成 agent 绕不过的环境，AI 写代码的质量就能追平资深工程师。不是模型变聪明了，是环境变严了。

先把这座仓库翻一遍，你会知道 AI 编程的地基长什么样。我在《别再背 AI 黑话了》里写过一条主线：大模型、Agent、Skill、MCP、Harness，一层比一层更能自己干活。ECC 落在最上面那层——它把 harness 这层的全部家当打包好了，剩下的问题是你要从里面挑什么。

再往后一步，agent 工程环境正在变成 AI 编程的标配层，就像测试基建一样，每个认真用 AI 干活的团队迟早都要有自己的一份。区别只在于，你是从零攒，还是从 ECC 这样的仓库里挑零件攒。路不一样，终点一样——装出来的体系是别人的，长出来的体系才是自己的。
