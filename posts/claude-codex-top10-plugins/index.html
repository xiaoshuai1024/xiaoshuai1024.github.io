Claude 和 Codex 必装的 10 大插件:双持大半年,两边都给我装上了

今年我的工作流稳定成了一个固定搭配：白天主力 Claude Code，跑长任务和交叉验证用 Codex。两个 agent 换着用之后遇到一个现实问题——给 Claude Code 精心挑的插件和 skills，切到 Codex 就没了，反过来一样。

好在插件里最有价值的 skill 这层东西天生就是跨端的：一个仓库里放一个 SKILL.md 加几个参考文件，Claude Code 读它，Codex 也读它。2026 年这个生态已经变了样：OpenAI 给 Codex 上齐了 skills 和插件系统，Vercel、Trail of Bits 这些工程团队把内部经验直接开源成 skill 格式，Anthropic 官方仓库涨到 17 万 star。skill 正在变成 agent 界的 npm 包——写一次，全平台装。

这篇是 Claude Code 必装插件的姊妹篇，口径换成双端：Claude 和 Codex 必装的 10 大插件，按 GitHub Star 排行，挑两边都能装、都值得装的。和上篇有五个重合（Superpowers、ECC、karpathy、graphify、Context7）——不是偷懒，是双持之后我对它们的评估又深了一层，安装命令也补了 Codex 侧的写法。Star 数截至 2026 年 8 月，用 GitHub API 现查的，每天在涨，只作量级参考。

先分清三个词

讲插件之前，把三个容易混的词掰开，后面选型才不晕：

skill 是一份说明书。一个文件夹，核心是一篇 SKILL.md——告诉 agent 某类任务怎么做，可以带参考文档和脚本。它不改 agent 本身，就是往它的「工作记忆」里塞经验。因为只是文件，谁都能读，所以 Claude 和 Codex 通用。

插件是安装和分发的单位。Claude Code 的 plugin 可以打包 skills、hooks、MCP 配置一起装；Codex 后来也上了插件系统，套路一样。插件是容器，skill 是内容物。

MCP 是接外部工具的管道。数据库、浏览器、第三方服务，agent 通过 MCP server 碰到外面的世界。skill 教它「怎么用」，MCP 给它「用的东西」。

一句话串起来：插件把 skill 和 MCP 打包送到 agent 身上。这十个按 Star 从高到低讲，每个的安装命令都从对应仓库 README 抓的真实写法，Claude 和 Codex 两端的装法都给。

先看排行

装之前先讲清楚一件事：这些插件怎么同时进两个 agent。

三条路。Claude Code 走 /plugin marketplace add；Codex 在 CLI 里输 /plugins 从目录装，或者用它内置的 $skill-installer；最省心的是中间那条——npx skills add，装的时候让你选目标 agent，Claude 和 Codex 各装一份。

1. Superpowers · 约 26 万 stars

仓库：github.com/obra/superpowers

它是什么：一套 agentic skills 框架加软件开发方法论，整个生态里 star 最高的男人。brainstorm、设计、TDD、代码审查、调试、执行计划，每个环节都有对应 skill。跨 11 个 agent 平台，Claude Code 和 Codex 都在支持列表里。

为什么两边都装：它把「高手怎么用 AI 编程」沉淀成了可复用技能，你不用每次从零写提示词。双持之后我多了一层体会——它的 executing-plans（每步验证门）和 finishing-a-development-branch（收尾前跑全量验证再问你怎么处理分支）在 Codex 上跑得比 Claude Code 还顺，因为 Codex 的沙箱模式跑验证不问你要权限。方法论这种东西装两边才值：不管今天主力是谁，纪律不断。

安装（Claude Code）：

/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

Codex 端用通用安装器挑单个 skill：

npx skills add https://github.com/obra/superpowers --skill finishing-a-development-branch

实际用起来的样子：最有感的是 executing-plans 的验证门——计划拆成步骤后，每完成一步必须跑一次验证贴输出，不过门不许进下一步。我拿它跑过一次数据库迁移改造，八步计划走到第五步时测试挂了，agent 当场回头修，而不是闷头跑完再告诉我全崩了。上篇评论里有读者问「Superpowers 会不会太重」，双持之后的答案是不重、但不能贪：两端各装一套、只开一个主 profile，纪律是共享的，开销是各自独立的。

2. ECC · 约 23.7 万 stars

仓库：github.com/affaan-m/ECC

它是什么：全称 The agent harness performance optimization system。打包了 skills、instincts（直觉规则）、memory（记忆）、security（安全）、research-first development（研究优先开发）五个维度，给 Claude Code、Codex、OpenCode、Cursor 用。

为什么两边都装：它管的是 agent「怎么跑任务」本身——记忆怎么留、安全怎么守、动手前先调研。觉得自己的 agent 跑着跑着就飘了，先看这个。双持场景下它的 memory 模块价值翻倍：任务从 Claude 换到 Codex，留下的记忆文件两边都认，交接不用从头交代背景。minimal 和 full 两种 profile，建议先 minimal，跑一周再加到 full。

安装（两端同一条命令，换 target）：

npx ecc-install --profile minimal --target claude
npx ecc-install --profile minimal --target codex

实际用起来的样子：minimal 跑一周后我加到了 full，差别主要在 research-first 那条规则——动手改代码前，agent 会先把相关模块的现状摸一遍再下笔，改动的「外科手术感」明显变强。memory 模块则是双持的隐形收益：它把项目约定、踩过的坑写成文件，Claude 和 Codex 都读这份，我在 Claude 里纠正过一次「这个项目不用 ORM」，切到 Codex 它也知道。这比在两个 AGENTS.md 里各维护一份省心太多。

3. mattpocock/skills · 约 21.9 万 stars

仓库：github.com/mattpocock/skills

它是什么：TypeScript 圈知名教育家 Matt Pocock 放出来的自家 .agents 目录，slogan 是 Skills for Real Engineers。数量不多，但每个都是真实工作里天天用的，最有名的是 grill-me 和 handoff。

为什么两边都装：grill-me 解决「我描述完需求，agent 点头就开干」这个大坑——它反过来面试你，一个问题一个问题问到双方理解一致，每个问题还附推荐答案。handoff 是双持用户的刚需：把当前上下文压缩成一份 markdown，从 Claude 换到 Codex 接着干，状态不丢。我的固定节奏是 Claude 里开任务先让 grill-me 上，上下文烧得差不多或要转 Codex 交叉验证时跑一次 handoff，等于给双持工作流配了开工仪式和交接仪式。

安装（通用安装器，选 agent）：

npx skills add https://github.com/mattpocock/skills --skill grill-me
npx skills add mattpocock/skills skill=handoff -y -g

4. karpathy-skills · 约 19.8 万 stars

仓库：github.com/multica-ai/andrej-karpathy-skills

它是什么：源自 Andrej Karpathy 对 LLM 编程陷阱的观察，四条行为规则：写码前先想、简单优先、外科手术式改动、目标驱动执行。清单里最轻的一个，就一个文件。

为什么两边都装：Karpathy 对「LLM 写代码常踩哪些坑」的观察非常准，把这些反模式直接写进 agent 的行为规则，等于给两个 agent 都装了避坑直觉。零成本、收益直接。双持之后我把它当「出厂设置」：新机器、新环境，Claude 和 Codex 各装一份这个，再谈别的。Codex 端还可以直接合并进 AGENTS.md，连插件都不用。

安装（Claude Code 插件方式）：

/plugin marketplace add forrestchang/andrej-karpathy-skills
/plugin install andrej-karpathy-skills@karpathy-skills

Codex 端用通用安装器，或把内容并进项目 AGENTS.md：

npx skills add multica-ai/andrej-karpathy-skills

实际用起来的样子：四条规则里治得最狠的是「外科手术式改动」。没装它之前，我让 agent 改一个接口返回值，它顺手把旁边三个「看着不顺眼」的方法也重构了，diff 大到没法审。装了之后同样一句话，diff 只碰该碰的那几行。这套规则给两个 agent 都上了缰绳，成本几乎为零——就一个文件，这是我把它长期留在必装清单的原因。

5. anthropics/skills · 约 17 万 stars

仓库：github.com/anthropics/skills

它是什么：Anthropic 官方的 Agent Skills 仓库，skill 这个格式的定义者。官方技能样例加模板，最有含金量的是 mcp-builder——四阶段流程带你造一个生产级 MCP server，连评估环节都排好了。

为什么两边都装：官方仓库的价值不在「拿来就用」，在「照着写」。想知道一个合格的 SKILL.md 该怎么拆步骤、references 怎么组织、scripts 什么时候该带，看这里的源码比看任何教程都准。我第一次认真读它，是想搞明白自己写的 skill 为什么触发不稳定——翻源码才发现问题出在 description 的写法上：官方每个 skill 的描述都在回答「什么任务该用我」，而我写的是「我能干什么」。这招对两端通用，因为 Codex 读 skill 的逻辑和 Claude 一致。注意部分技能是 source-available 许可，参考写法没问题，商用前看一眼 LICENSE。

安装（Claude Code 走插件市场；Codex 用通用安装器）：

/plugin marketplace add anthropics/skills
npx skills add https://github.com/anthropics/skills --skill mcp-builder

6. graphify · 约 10 万 stars

仓库：github.com/Graphify-Labs/graphify

它是什么：把任意代码库（文档、SQL schema、配置、PDF）转成可查询的知识图谱。一个 /graphify skill，本地确定性 AST 解析，每条边都可解释，不依赖向量库。支持 Claude Code、Cursor、Codex、Gemini CLI。注意 PyPI 包名是 graphifyy（双 y），CLI 命令才是 graphify。

为什么两边都装：大型 codebase 是 AI 编程的最大障碍——上下文塞不下，agent 看不全就乱改。graphify 把代码库结构化成图谱，agent 查关系、追调用、定位改动点都有了准头。双持场景它还有个隐藏用法：图谱建一次，两个 agent 查同一份。Claude Code 改完让 Codex 来复核时，Codex 不用重新理解一遍项目结构，直接查图谱——这比把代码重新喂一遍省太多上下文。项目越大越值钱，且本地解析、确定性、不调云。

安装：

pip install graphifyy

然后两端都能用 /graphify 建图谱查关系。

实际用起来的样子：我最大的仓库大约二十万行，裸问 agent「支付回调链路经过哪些服务」，它凭印象答，漏两个环节。建完图谱再问，它按边查，从入口到落库一条不漏。双持的用法是这样：图谱文件放项目里，Claude Code 改代码前查一遍，改完让 Codex 复核时再查一遍——两个 agent 共享同一张地图，谁都不用重新认路。建图谱那一下要跑几分钟，之后查询都是秒级。

7. ComposioHQ/awesome-claude-skills · 约 7.3 万 stars

仓库：github.com/ComposioHQ/awesome-claude-skills

它是什么：Composio 维护的 awesome 清单，把社区 skills 按类别整理成索引，每条带仓库链接和一句话说明。

为什么值得收着：它是「选货」的入口而不是「货」本身。装新 skill 前先来这里翻一圈，能避免重复造轮子——你要的能力大概率有人已经写好还维护着。我的经验是动手写 skill 之前，在索引里花五分钟搜一下，命中率大概一半。上个月我要给公众号同步流程加自动压图，先来这搜 image compress，翻到两个现成 skill，一个直接能用。awesome 类清单的通病是收录质量参差，所以只当目录用，进具体仓库前自己看 star 趋势和最近提交。

用法：不需要安装，翻目录，看中哪个仓库再用 npx skills add 装对应的。

实际用起来的样子：上个月我要给公众号同步流程加一个自动压图的能力，第一反应不是自己写，先来这份清单搜 image compress，翻到两个现成 skill，读了一遍源码，一个直接能用，一个思路对但实现糙——改改就省了半个晚上。我的经验是：动手写 skill 之前，在索引里花五分钟搜一下，命中率大概一半。另外把这份清单按你的方向筛选一遍（比如只看 engineering 类），比从头翻效率高得多。

8. Context7 · 约 6 万 stars

仓库：github.com/upstash/context7

它是什么：实时文档 MCP。agent 写代码用的库版本可能已经变了，Context7 把最新版文档直接注入上下文，杜绝「按两年前的 API 写代码」。

为什么两边都装：这个坑在 Codex 上更疼——它的训练数据截止更早，遇到新框架新版本更容易凭记忆瞎写。挂上 Context7 之后，两个 agent 查的都是当下最新的文档，答案对得上。双持还有个连带好处：Claude Code 里验证过「Context7 说这个 API 这样用」，切到 Codex 复核时同一个 MCP 给同样的答案，两个 agent 不会各执一词。文档老变的技术栈，这个是刚需。

安装（Claude Code）：

claude mcp add context7 -- npx -y @upstash/context7-mcp

Codex 端在 ~/.codex/config.toml 注册同一个 server，或：

codex mcp add context7 -- npx -y @upstash/context7-mcp

实际用起来的样子：翻车现场是这样的：agent 按记忆里的旧 API 写了一段数据库连接代码，类型对不上，编译报错，它又按记忆改，越改越歪。挂上 Context7 后同一段任务，它先查当前版本文档再写，一次过。我的触发词习惯是「用 context7 查一下这个库的最新用法」，两个 agent 都认。前后端框架迭代快的项目，这个插件省下的调试时间比它占的上下文值钱得多。

9. K-Dense-AI/scientific-agent-skills · 约 3.4 万 stars

仓库：github.com/K-Dense-AI/scientific-agent-skills

它是什么：面向科研场景的技能库，161 个经过验证的 skills，覆盖生物、化学、医学、药物发现，还接了一百多个科研数据库。README 说全球 17 万科研人在用。

为什么值得装：如果你写代码是为了跑数据分析、做研究，这仓库比任何通用合集都值钱——它的 skills 是按科研工作流验证过的，不是拍脑袋生成的。哪怕不搞科研，它也是「垂直行业 skill 库该长什么样」的最佳样本：按域分组、每个 skill 带验证说明。我拿它帮家里做生物信息分析的亲戚干活，产出的图表和统计检验有据可查，和让裸 agent「帮我分析数据」是两种可靠度。做 AI 应用的工程师拿它当参考架构看，也不亏。

安装（通用安装器，兼容 Cursor / Claude Code / Codex）：

npx skills add K-Dense-AI/scientific-agent-skills

实际用起来的样子：帮亲戚处理一批测序数据时，我把前处理流程交给 agent，配这里的分析 skills，产出的图表和统计检验每个都标注了方法来源，复查有据可依。对比试验我做过一次：同样的任务让裸 agent 跑，它给的检验方法选型是错的，p 值解释也含糊。垂直 skill 库的价值就在这——它把领域内的正确做法固化了，不依赖模型的自由发挥。

10. openai/skills · 约 2.5 万 stars

仓库：github.com/openai/skills

它是什么：OpenAI 官方的 Codex 技能目录，分 .system、.curated、.experimental 三层。curated 层的 yeet（暂存、提交、推送、开 PR 一气呵成）、gh-fix-ci（诊断失败的 CI 并起草修复）、gh-address-comments（处理 PR 审查意见）是日常提效最狠的三个。

为什么两边都装：star 是这份榜单里最低的，出身是最正的——OpenAI 官方出品，就是给 Codex 用的。双持场景下它还藏了一个宝贝：migrate-to-codex，把 Claude Code 的 skills、hooks、MCP 配置转成 Codex 格式，我从 Claude 全量迁 Codex 时十几个 skill 加 MCP 配置就是它转的格式，手动做这事一下午都不够。注意这是 Codex 官方目录，Claude 端想用里面的 skill，用通用安装器同样装得进去，skill 文件本身不挑 agent。一天里重复最多的「改完—提交—推—开 PR」，yeet 一条命令搞定，提交信息还按仓库既有风格写。

安装（Codex 内）：

$skill-installer yeet
$skill-installer gh-fix-ci
$skill-installer migrate-to-codex

Claude 端：npx skills add openai/skills --skill yeet。

实际用起来的样子：一天里重复最多的动作就是「改完—提交—推—开 PR」，yeet 把这四步变成一条命令，提交信息还按仓库既有风格写。gh-fix-ci 在 CI 挂掉的时候最省心：它先读失败日志定位原因，起草修复方案，等确认了才动手——不会上来就乱改一通把别的测试搞挂。gh-address-comments 处理 PR 审查意见也贴心：把评论列出来让你勾选处理哪几条，不会全盘照收也不会漏。这一层 skill 小而具体，但天天用，是「使用频率除以学习成本」最高的一个仓库。

双持怎么分工

装完之后还有个绕不开的问题：同一个任务，什么时候丢给 Claude Code，什么时候丢给 Codex？我的分法不是「哪个更聪明」，是按两边的生态强项切：

改代码、写新功能给 Claude Code。 我在 Claude Code 上沉淀的 skills 和 hooks 最多，插件生态也最厚（上次那篇 12 个插件讲过）。它的上下文管理和子 agent 调度处理复杂改动更稳。

交叉验证、跑独立任务给 Codex。 同一份改动让 Codex 带着代码审查 skill 再看一遍，因为两个模型的知识盲区不同，互相挑错比自审有效。跑实验性任务、生成对比方案这类不需要共享上下文的活，也丢给它并行跑。

中间靠 handoff 和 graphify 图谱衔接。 会话交接用 handoff 生成的文档，项目结构靠 graphify 的图谱共享，两边 agent 读同一份东西。ECC 的 memory 文件也参与进来，项目级的约定两边共读。这就是双持的诀窍——状态放文件里，不放任何一个 agent 的记忆里，谁随时接手都能续上。

顺着这个分法你会发现，十个插件里大半的价值不在「某个 agent 变强了」，而在「两个 agent 变成了一个团队」。

装来的 skill 要动手改

开源 skill 很少有拿来就能完全对上自己工作流的，我的做法是装完先改三处：

改 description。skill 会不会被自动触发，八成取决于 SKILL.md 开头那段描述。很多仓库的描述是英文泛写，我的任务描述是中文场景，直接照抄就经常不触发。把描述改成「你在什么情况下该用我」的中文说法，触发率立竿见影。这是读 anthropics/skills 源码学到的最值钱的一招。

删不相关分支。一个 skill 覆盖的场景越多，正文越长，占的上下文越多。做后端项目的，把 skill 里移动端、桌面的分支删掉，只留自己会用到的路径，skill 更短，agent 执行也更专注。改之前留一份原始版本，方便升级时对照。

换成自己的验收标准。多数 skill 自带的完成判据是「跑通」，我的标准是「跑通加测试过加贴出输出」。把验证要求写严一档，agent 自报完成的水分就少一截。这是从 pua 那类纪律 skill 借来的思路，揉进日常 skill 里，比单独装一个管纪律的更顺手。

改完记得同步两边：npx skills 装的 skill 在两个 agent 目录里各有一份，改了 Claude 端的别忘了 Codex 端。我的习惯是改动只做一次，然后复制过去，不让两边各自演化。

怎么选，别照单全收

十个看下来，和上次那篇一样的提醒：全装是最差的选法。插件装多了互相打架、占上下文、agent 不知道听谁的。我的分层用法就四层：

方法论层只选一套。 Superpowers、ECC、karpathy-skills 都带行为约束，别同时全开，选一套吃透。可以 karpathy-skills 当起手式（一个文件零成本），再选一个主方法论（Superpowers 或 ECC）。纪律这东西一套就够，两套就打架。

能力层按缺口补。 项目太大 agent 看不全 → graphify；文档老变 → Context7；工作流交接 → mattpocock 的 grill-me 加 handoff；git 环节重复劳动多 → openai/skills 三件套。不是 star 高就装，是缺这个能力才装。

垂直层按行当加。 做科研加 K-Dense，都不是你的行当就跳过。垂直库的性价比取决于你掉进那个场景的频率——一年碰两次科研分析，就别装 161 个 skill 进去，要用的时候单独捞那一个。判断方法很土：回想上个月干过的活，哪个场景重复了五次以上，就给哪个场景配垂直 skill，其余的等用到再说，别为「可能用到」预支上下文。

索引层只翻不装。 awesome 清单是字典，遇到新需求先查字典，查完按需装单个，字典本身永远不进 agent。道理和书架一样：字典放书架上随手查，你要是把字典每一页都背下来，脑子就没地方干正事了。

另外一条安全纪律：带 scripts/ 目录的 skill，装之前打开看一眼脚本内容——skill 是会被 agent 执行的，这和装 npm 包要看 postinstall 是一个道理。社区 skill 没有审核机制，star 高只代表受欢迎，不代表安全。我的习惯是 scripts 里的东西自己读一遍才让装，读不懂的就不装；SKILL.md 和 references/ 这种纯文档部分风险小得多，放心用。

一个判断

双持 Claude Code 和 Codex 这大半年，我越来越确定一件事：agent 之间的差距在被 skill 这层抹平，真正拉开差距的是你给它们喂了什么技能。 同一个 Codex，裸装时像个聪明的新人，装完 Superpowers 的验证门加 openai/skills 的 git 三件套之后，干活的完成度和一个熟练 junior 没区别。这大半年我真正的工作流变化不是「换了个更强的模型」，而是「往两个 agent 身上持续装技能」——模型月月在换，skill 沉淀是自己的。

如果只装三个，我会装 Superpowers（保证做的事和做事的纪律）、Context7（保证用的知识是对的）、mattpocock 的 grill-me 加 handoff（管开工和双端交接）。这三个覆盖了一个任务从开工、执行到换手接续的完整路径，两边 agent 各装一份，切换成本降到最低。

剩下按缺口补。选的时候记住一条：每个插件都要答得上来「它替我省了哪一步」——答不上来的，star 再高也不装。
