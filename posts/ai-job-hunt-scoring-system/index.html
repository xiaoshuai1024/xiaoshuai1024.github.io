我的求职系统里有一张表，其中一行写着：AI 应用开发工程师，月薪 20-40K，AI 工程化方向 72 分起投。

意思是，这个岗位投不投，取决于测评分数够不够 72。差几分，这份简历就先压着，把短板补上再投。分数来自 72 项技能的逐项测评，每项 0 到 5 分，做完题才算数，自我感觉在这套流程里不算证据。

这张表背后是一套跑了半年的系统：四条 Claude Code 自定义命令，接成一圈。扫岗位、测能力、补短板、练面试，各管一段，上一条的输出就是下一条的输入。这个月我把整个项目整理开源了，GitHub 上 169 个文件，MIT 协议，clone 下来改三处就能换成你自己的求职系统。

这篇文章把系统拆开讲清楚：每条命令怎么工作，72 分这条线怎么标定，它凭什么能治「学了就忘」，以及你拿去之后要改哪三处。先从古法求职的问题说起。

古法求职的三个死结

古法求职我用了 12 年，总结下来就三个死结：没有标准、没有反馈、没有复盘。每一个都不是靠努力能补的，它们缺的是结构，态度补不上结构。三个死结叠在一起还有个隐性代价：求职周期被拉长。岗位会过期，手感和状态会衰减，拖上三个月，市场上适合你的坑位换了一轮，你还在原地修感觉。

第一个死结是没有标准。「我准备好了吗」这个问题全凭感觉。觉得自己 Vue 用得挺熟，觉得微服务「差不多懂了」，觉得算法「应该够了」。面试官不认感觉，他只认你能不能把问题讲透，而感觉和讲透之间的差距，你事先量不出来。

第二个死结是学了东西没人检验。看文档、刷教程、收藏文章，整个过程没有一道题来验证你到底会不会。收藏夹越来越厚，本事原地踏步。我在上一篇文章里拆过这个现象，问题出在学习流程里没有回路，学了没检验，时间花了等于白花。

第三个，没有复盘。面完一场就扔。面试官问了什么、哪题卡住、哪句话答得虚，全靠脑子记。记不住就丢了，于是同一类问题可以在三场面试里卡你三次，你甚至不知道它们是同一类。

下面这套系统，就是针对这三个死结逐个下手的。它的起点很朴素：一次技术选型会上被一句 RAG 追问问到哑口，当天晚上我写出了第一版能力评分表。

第一步：把招聘市场变成数据源

系统的采集端是 /find-jobs。它扫八个招聘平台，BOSS直聘、猎聘、拉勾、51Job、智联这些，把岗位收进一张表。表的每行长这样（内容做了虚构处理）：

公司岗位薪资核心技能背调
某智能硬件公司AI 应用工程师20-30KRAG、LangChain、Spring AI300 人规模，自研产品，非外包

一行岗位，五列信息。背调那一列是我坚持要有的：公司规模、劳务纠纷记录、外包比例，这三样决定你要不要把一场面试的机会花在这家公司上。岗位描述写得再漂亮，仲裁记录拉出长长一串的公司也要三思，这类信息手动查得翻裁判文书网，命令直接帮你汇总。这些内容散落在八个平台和几十页搜索结果里，手工整理要一个下午，命令跑完不到一分钟。

八个平台各有性格。BOSS直聘响应最快，岗位更新最勤；猎聘集中在中高端岗位；51Job 和智联覆盖更多传统企业；高校人才网和公司官网渠道则是冷门机会的藏身处，官网经常挂着没同步到平台的岗位。同一岗位多平台都挂的，系统按公司加岗位名去重，只留一行，各平台链接并进去。

岗位库还配了一个 MCP 服务端。开启之后，Claude Code 里的任何会话都能直接查这张表，按城市、薪资、技能标签过滤，统计任意时间段的新增岗位数。「青岛地区 25K 以上的 AI 岗位，过去两周新增了几个，技能要求有什么变化」这类问题，它自己发工具调用去查库，不用你翻表格。采集和使用接在一起，这张表就从存档变成了随时可问的数据源。

/scan-jobs 负责让数据保鲜。它可以按天扫新岗位、GitHub trending 和掘金热榜，发现 JD 里冒出来的新技术要求，自动对照我的能力评分表：市场在要求、我表上还没有的技能，直接加进技术学习清单。MCP 就是一个实例，去年它的岗位 JD 出现频率一路上涨，扫描抓到这个变化，学习清单跟着把它排到了前面。

求职是信息问题。把信息采集做成每天自动跑的流程之后，你对「市场要什么」的判断从印象变成了记录。刷到「XX 上岸分享」就焦虑的毛病也顺带好了一半，你的对照物是岗位表和评分表，不再是别人的战报。

第二步：分数线从 JD 里来

/skill-test 是整套系统的刻度尺。它把归并出来的技能要求整理成 72 项，按五个方向归档：前端开发 20 项，后端开发 18 项，AI 工程化 22 项，全栈架构 10 项，Python 2 项。每一项的分数怎么读，都事先定义清楚。

0 分，没接触过。1 分，知道概念，说不清原理。2 分，跟着教程做过，换个场景就卡。3 分，能独立完成常规任务。4 分，理解实现机制，处理过边界情况。5 分，讲得透设计取舍，踩过真实的坑，能带别人入门。档位定义清晰的好处是判分有依据，AI 判完分你能对着标准复核。

打分靠做题。对它说「测一下 MCP 协议」，它按分级出题，答完它判分，分数写回评分表。题型结构是定死的：五到八道题里，基础理解两三道，场景应用两三道，深度思考一到两道，最后一档通常是设计题。难度爬坡的好处是能定位问题，基础题错是概念没通，设计题错是经验没到，两种错的补法完全不同。自评会高估，做题不会，3 分和 4 分的差距具体在哪道题上丢的，记录里清清楚楚。

有了分，还差一条线。72 分这条线是从目标岗位的 JD 反推的：把 20-40K 档 AI 应用岗位的高频技能要求铺开，算出这些岗位普遍要求的技能覆盖度，换算成百分制就是分数线。前端线 72 分对应 15-25K 的高级前端岗，全栈架构线 45 分对应 30K+ 的架构师岗，线不一样，因为岗位的要求密度不一样。它是经验标定，随扫描数据持续校准，但它给了我一个过去从来没有的东西：一个可以量化的「够了」。

这张评分表还是活文档。市场冒出新技能，扫描把它加进表里；某些老技能在 JD 里出现频率持续走低，权重跟着下调。技能表跟着市场长，写死不动、半年不更新的清单，撑不过一个招聘季。

把三条线换算成比例看更有意思：前端线 72 分是满分 100 的 72%，AI 工程化线 72 分是满分 110 的 65%，全栈架构线 45 分却是满分 50 的 90%。架构师岗对均衡度的要求最苛刻，十个技能项里任何一项拉胯，这条线都过不去，架构师的短板效应比工程师岗狠得多。

分数线同样会动。每个月把新扫到的 JD 重新归并一遍，要求密度变了，线就跟着浮。半年前 AI 应用岗对部署和推理优化的要求还没这么密，现在这类技能已经进了必选项。线是市场的影子，市场变了线不动，投递策略就失真了。

打分的用处在这一刻兑现。同一个问题，过去的答案是「我觉得我差不多了」，现在的答案是「我 71 分，差 1 分，差在 MCP 的 resource 和 prompt 两类能力细节上」。差距被定位到具体技能项，下一步学什么就不用猜了。

这里要交代一个诚实的边界：AI 判分有误差，尤其 4 分和 5 分之间的界线，它偶尔把握不准。我的用法是把 AI 的分数当初评，5 分这种高分项，自己再复述一遍机制，讲不利索就降档。系统里没有机制能对付自欺欺人，这道防线得自己守。

第三步：让学过的东西留得住

/study 针对的是最要命的那个死结：学了就忘。它的流程是，从评分表里挑最弱项选题，输出一份学习材料，包含概述、核心概念拆解、实战代码、常见陷阱和面试考点，然后当场出 5 到 8 道题检测，检测过了再进 3 到 5 轮模拟面试，错的地方自动归进错题本。

举个真实的例子。评分表显示我的 MCP 协议只有 2 分，对它说「学 MCP」，十几秒后材料出来了：核心概念按 host、client、server 三层拆开讲，实战部分是一个最小可运行的 server 例子，陷阱部分专门讲 resource 和 tool 的适用边界，末尾附五个高频面试考点。学完当场做题，五道错了一道 resource 订阅机制的，错题进本，三天后重测。

这套流程治「学了就忘」的机理不复杂：记忆靠提取练习，不靠反复重读。看十遍文档，不如合上文档做一道题。以前不做题的理由是出题成本太高，一份好题目的编写时间比学习时间还长，AI 把这个成本压到了十几秒，回路就转得起来了。上一篇里那个两周前学的 RAG 被同事一句追问问哑的故事，症结就是这两周里一次提取练习都没有。

材料里我读得最仔细的是「技术对比」和「常见陷阱」两节。前者把相似概念摆在一起切边界，比如 tool 和 resource 各自该在什么场景用；后者直接告诉你错误姿势长什么样。这两样正好是面试最爱考的，教程反而最少讲。

错题本是这套流程里我最有感情的文件。每道错题记着当时怎么答错的、正确理解是什么、隔了几天要重测。隔三差五跑一次 /study review，它把错题本里的旧题翻出来重考。生词本是错题本的小兄弟，记的是概念卡壳的瞬间。/study log 能看学习历史和统计：这周学了几个主题、测验通过率多少、哪个主题重测了几次。数据攒起来，你能看见自己的学习曲线，焦虑大多来自看不见进度，曲线一画出来就踏实了。

我把它排进了周节奏。工作日晚上一个 /study 主题，四十分钟；周末一次 /skill-test，把本周学的东西实测成分数；面试季每天加一轮模拟面试。学习从「有空再说」变成日程表上的固定格子，这个变化本身就把大多数人甩开了。

第四步：面试是可以排练的

/interview-prep 解决复盘缺失的问题。给它一份目标岗位的 JD，它先定位考察方向，再结合评分表生成备战材料：自我介绍怎么开头、哪些高频题大概率出现、项目经历按什么线讲。材料备完直接进模拟面试，AI 按面试官的路数追问，一轮一轮点出你答得虚的地方，面完给五维评分和话术修改建议。

模拟面试长什么样，讲一段实录的对话结构。它先问：「你的岗位数据从八个平台来，怎么保证不漏掉新岗位？」我答了扫描频率。它跟着追问：平台反爬策略变了导致数据断更一周，你怎么发现？这类问题考的是你对自家系统的掌控力，知识点倒在其次。三轮之后复盘指出，我的回答里「应该」「大概」出现了四次，面试官视角这就是没把握的信号，下次回答要换成具体的数字和机制。

/company-check 是配套的背调命令：目标公司的业务盘子、规模、舆情记录、外包比例，面之前过一遍。这些信息决定你怎么讲项目。对三五百人的自研产品公司，讲架构演进的长期规划是对路的；对外包占比高的团队，讲交付效率和范围控制更对题。讲错方向的准备，等于白准备。

这条命令里有一条写死的约束，我觉得比功能本身更重要：所有话术只基于简历里的真实经历，任何数字必须能在简历里找到对应出处，找不到就标「待验证」。AI 排练面试最危险的坑是帮你编故事，有这条约束，话术只能从真实经历里生成。排练帮你把真本事讲清楚；假经历就算排练得再顺，也经不起两层追问。

我最近一次求职走完了全套流程。面完每一场，复盘自动归档，暴露的薄弱项回流评分表，驱动下一轮 /study 的选题。面试一场一场往下排，第一场暴露的表达问题，第三场就改掉了；第三场暴露的知识盲区，一周内进了学习清单，到后期面试官的追问类型，大半是模拟面试里演过的。这场求职的终点是一份技术总监岗的 offer。offer 到手的时候，评分表上当初几个 1 分、2 分的技能项，都已经练到了 4 分以上。

开源之后：clone 过来改哪三处

项目在 GitHub 上，仓库叫 learn_for_interview，169 个文件，MIT 协议。四条核心命令之外，还有岗位爬虫和 MCP 服务端、在线简历自动填写工具、成套的技术面试教材（MySQL 索引与事务、JVM 参数配置、监控预警体系、秒杀系统设计）和分岗位的面试题集。教材和题集是通用内容，clone 下来直接能读。

要用它，改三处就够。第一，cv/ 目录放上你自己的简历，markdown 格式，配套样式和 PDF 导出脚本都在。第二，infos/ 目录建你的个人档案，基本信息、目标岗位、能力自评，命令会读这里的上下文。第三，配置里把目标城市和岗位方向改成你的，/find-jobs 的扫描范围跟着变。其余数据文件，岗位表、评分表、学习日志、错题本，命令会自己生成，.gitignore 已经把这类个人数据挡在版本库外。

仓库里还有个顺手的工具值得一说。投递要填在线简历表，一家一个格式，手填一次半小时。resume-filler 把你的简历信息读成结构化的 JSON，配合浏览器自动化往平台表单里填，格式差异它来适配。模板里有个细节我挺得意：薪资期望字段是故意留空的，简历上不写、初面不报底线，这是谈判纪律，工具的职责是帮人守住它。自带的数据模板是虚构示例，换上你自己的就行。

爬虫的边界也提前说明白：只采集公开发布的岗位信息，控制请求频率，不碰需要登录才能看的数据，仅供个人求职用。实现上它走浏览器自动化，起一个带调试端口的浏览器实例，每个平台一个采集器，请求之间强制限速。牺牲了速度，换来的是行为像真人浏览，对平台的负担小，对自己也安全。这套东西只该用来让自己的信息采集快一点，给别人添麻烦的用法一概不碰。

四种用错的方式

方法讲完，讲坑。第一种用错的方式，是把爬来的岗位数据当定论，不做人工复核就改学习计划。爬虫会漏，平台页面会改版，数据要人眼过一遍再用，这一步省不得。

第二种，把分数线当铁律。分数差半分就绝对不投，或者分数够了就闭眼投，都曲解了这条线的用途。分数线的用途是排优先级，投不投的最后一步还得人自己定，面试邀请本身也是信息，别浪费。

第三种，在模拟面试里让 AI 给你编经历。编出来的故事第一次讲很顺，追问两层就露馅，这条约束在命令里写死了，绕开它等于给自己埋雷。

第四种，把自己的真实简历和档案塞进仓库就往公开推。个人数据先脱敏，我的做法是让所有个人信息目录都待在 gitignore 里，公开仓只留方法和示例模板，你照着结构填自己的内容。

这套系统不适合谁

方法有边界，说完适用就得说不适用。应届生用它收益有限，简历经历还薄，评分表上也没有历史数据可对照，先攒实习和项目更实在。目标模糊的人别急着跑它，系统需要你先定一个岗位方向才能扫 JD 定分数线，方向本身它给不了。岗位极少的城市也要掂量，样本太少时分数线没有统计意义，把目标城市放宽或者把远程岗位纳入扫描，是更合理的调法。

再补一个用法。如果你是带团队的，这套方法反过来用就是团队能力盘点：评分表换成团队版本，每个人的强弱项摆在一起，招聘要补什么、培养先投谁，优先级从数据里出来。它起名 learn for interview，但量化加反馈的方法本身，跟「面试」两个字没有强绑定。

写在最后

回头看开头那张表。72 分不是我自己拍的一个吉利数字，它是三十份 JD 归并出来的市场要求，乘上逐项做题测出来的真实差距。这套流程走顺之后，求职里那些过去让人睡不着觉的问题，都变成了有数字可看的问题：市场要什么，有岗位表；我会什么，有评分表；差多少，有分数线；怎么补，有学习回路；能不能讲清楚，有模拟面试。

我不是说有了系统就万事大吉。AI 会出难题也会判错分，爬来的岗位信息需要人眼复核，分数线要随市场变动校准，这些活它替不了你。它消除的是盲区，努力本身省不掉，该准备的知识一项不会少。它改变的是你分配努力的方式：从到处撒网，改成对着分数差距精准使力。

但方向是明确的：找工作最大的不确定性，来自你对自身差距和市场要求都只有模糊感觉。把两头都变成数据，中间每一步学什么、练什么、投不投，就都有了可以踩实的依据。

开源地址在我的 GitHub 主页，仓库名 learn_for_interview。clone 下来，改三处，跑起来，祝你也早日把「我准备好了吗」变成一道有分数的题。
