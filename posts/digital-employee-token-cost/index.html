你的 AI 员工工资按字算：952 万 token 账单与 30 倍折扣的管法

我雇了一群不领工资的员工：写稿的、配音的、剪片的、写代码的，全都不拿月薪。代价是他们的工资按字算，每读一个字、每写一个字，都在计费。这个发薪方式决定了整篇文章要讲的事：你的数字员工，账单形状和人类员工完全不同。

先给最反直觉的那个数字。我做一条视频，从稿子到成片，本地管线跑完，一个月成本不到一杯奶茶；而同一个月里，一条 Codex 会话记录显示，单个会话吃掉 952 万 token。最便宜的和最贵的，在同一张工资单上。

这篇把管饭方法拆成四块：先盘家底，看哪些成本可以压到电费级；再认大胃王，看清 952 万 token 的账单形状；然后拆那张 30 倍的价签，讲清折扣从哪来；最后是三条家规和月底对账的习惯。每一步的数字都能自己复现，文末给了入口。

一、先盘家底：哪些员工可以只付电费

数字员工分两类，发薪方式天差地别。一类跑在你自己家里：配音、转写、渲染，吃你的电，不找你收费；另一类跑在云上，按 token 计费，字字要钱。管饭的第一步，是把能搬回家的搬回家。

我自己的产线长这样：配音用 IndexTTS-2，一张 8GB 显卡本地合成，音色是我自己的克隆；转写用 whisper，同样本地跑；渲染在本地机器直接出片。这三样没有月费、没有订阅、没有按量计费，成本只有电费。

岗位方案计费方式月成本量级
配音IndexTTS-2 本地克隆电费一杯奶茶的分项
转写whisper 本地电费同上
渲染本地出片电费同上
写作 / 编码Codex + DeepSeek 通道按 token大头，见后文

这张表的含义不在省了多少，在结构：本地岗位的边际成本接近零，我可以放开了让它干活，不用担心哪一步多花一分钱。云端岗位相反，每一步都在走表。把「不计费的岗位」最大化，是数字员工成本管理里杠杆最大的一步，做完这一步，剩下的战场只剩 token。

搬家有代价，得说实话。本地意味着自己管环境：8GB 显存是 IndexTTS-2 的及格线，而且要以 fp16 方式加载、关掉 CUDA kernel 编译，否则一张 8GB 卡会卡在 JIT 编译上十几分钟没有产出。这些摩擦是真实存在的，但它们是一次性的、可积累经验的；token 账单是按量的、随使用线性上涨的。一个买设备，一个交房租，我选买设备。

哪些活适合搬回家，我的验收标准就一条：这一步的输出，你能不能低成本地亲自验收。配音听一遍就知道行不行，转写对着时间轴扫一眼，渲染成片直接看。输出可检验的岗位，本地模型的水平够用，出了问题你当场就能发现。反过来，开放性生成的活（文章初稿、代码方案）不适合搬：验收成本高、迭代轮数多，云端模型的推理质量仍是主要生产力，硬搬是省小钱误大事。

还要留一条退路。克隆链路依赖的环境偶尔会出状况，我配了备链：edge-tts 出播音腔底稿，Seed-VC 换声。备链的音质不如主链，但它保证了「设备出问题的那几天，产线不停摆」。管成本的前提是产线活着，退路的费用是保险费，不是浪费。

另一个真实事故记在这防你重蹈：WSL 环境整体放在 D 盘之后，有阵子 C 盘被写满，整个 WSL 直接报错起不来，本地产线全停。从那以后我的巡检清单里多了一行磁盘余量。本地产线的每一分便宜，都建立在环境健康的前提上。

二、大胃王的本相：952 万 token 的账单形状

云端岗位里吃得最凶的是编程 Agent。我翻过自己的 Codex 会话流水，有一条会话让我坐直了：2026-08-20 16:45:36（UTC+8）开始，54 次模型调用，总输入 9,529,727 token，总输出 6.6 万。输入是输出的 144 倍。

这个比值值得盯着看久一点。它说明编程 Agent 的成本大头不在「模型写了多少代码」，在「模型每轮重新读了多少遍你俩的对话」。模型是无状态的，它对你的全部记忆，就是这一次请求里装的东西；所以每一轮，客户端都得把系统提示、项目文档、全部对话历史、工具输出原样重发一遍。

重发的速度是复利式的。那条会话的每轮输入序列是这样的：首轮 20,611，第三轮 33,133，第十轮附近 15 万，最后一次调用 226,262。第一轮的两万，到最后一轮涨了 11 倍，中间没有任何一次浪费，就是同一个任务正常往下推。把 54 根柱子加起来，就是 952 万。

这里有个多数人会算错的口径。CLI 跑完打印的 tokens used，我拿两组数据验证过，它约等于「非缓存输入加输出」，不是总消耗。那条 952 万的会话看起来吓人，实际计费量远小于这个数，因为重发的大头被缓存折扣接住了。接住多少、怎么接住的，就是下一节的内容。

账单上还有两笔「看不见的固定支出」，值得单独点名。第一笔是项目文档的每轮计费。AGENTS.md 被拼进每一轮请求的指令区，一轮不落。我做过受控实验：两个空目录放同一份代码，唯一差别是一份 3.5KB 的胖文档和一份三行的瘦文档，首轮输入差 931 token。这不是一次性成本，跑 50 轮就是 4.6 万 token 的重复输入。我的主力仓库文档 6KB，对裸目录的首轮基线差是 4,200 token/轮，这是它的真实单价。

第二笔是思考 token。那批会话全局开着 high 档，思考部分占输出的 45% 到 64%，按输出价计费。这一笔不一定是浪费（难题上高档位是合理支出），但它应该是你知情选择的产品，别让默认值悄悄替你下单。

至于上下文压缩，多数人对它有错觉。快满的时候 Codex 会自动把历史摘要成一段，压缩救的是上下文窗口，不是钱：压缩那一下本身就是一次按当时全量上下文计费的大请求。所以我的用法分两码事：任务边界到了直接开新会话归零；确实需要长会话推进的，才把压缩当窗口管理工具用。

完整的逐轮拆解、八条会话的全景表、胖瘦文档的受控 A/B，我在上一篇文章里拆到了每一轮，这里不重复占版面，只留结论：上下文是复利负债，账单的形状由「你允许什么东西每一轮重新进一次上下文」决定。

三、30 倍的价签：折扣从哪来

同一个问题问两遍，token 数一模一样，开销能差 30 倍。价差不在模型档位，不在计费策略，因果链短得很：贵的那次没命中缓存。DeepSeek 官方价格表把 v4-flash 的输入拆成两档，缓存命中 0.05 元/百万 token，未命中 1.5 元，比值正好 30 倍，高峰时段各自翻倍、比值不动。

用一个具体场景感受这两档价。一份十万 token 的会话历史，下一轮要重发：没命中，付 0.15 元；命中，付 0.005 元。单轮看都是零钱，但会话越往深处走，重复段在每轮输入里占比越高，两种结局的累计差额随轮数线性放大。54 轮的会话，就是 54 次二选一。

缓存的工作方式是前缀匹配：服务端记住你上次请求开头的那一长串，这次请求的开头和上次逐字节一致，命中成立；第一个不一致的字节之后，全部按原价。这带来三个推论。一，会话内命中率高是天然的，历史只追加不修改，前缀自然稳。二，站在前缀最顶端的是系统提示和项目文档，改动一个字，身后全部作废。三，首轮永远没有缓存，文档越胖，首轮原价部分越大。

我在受控实验里量过这层的威力：同一份代码、同一个任务，胖文档目录缓存命中率 46%，计费 21,984；瘦文档目录命中率 98%，计费 3,989。同样的活，计费差 5.5 倍。把这件事和我那条 98% 命中率的 952 万会话放在一起看，结论相同：重发量决定账单的基数，命中率决定你在基数上打几折。

想自己把 token 换算成钱，公式一行就够：实付等于命中价乘以缓存命中量，加原价乘以未命中输入，加输出价乘以输出。三个单价去通道定价页拿，流水从会话文件里读。套我那条 952 万的会话：命中 98%，九成多的重发走了折扣价，这就是重发量吓人、账单却没有爆炸的原因。但别因此觉得重发无所谓，命中率是脆弱的，换个任务、改个配置，同样的重发量就按原价砸下来。

订阅制用户先别急着划走。你交的是月费，重发消耗的换成限额和速率窗口：长会话照样把你顶到限流，下午干到一半被迫等窗口重置，损失的货币换成了时间。流水里的 rate_limits 字段在官方通道下会给出窗口用量，拿它当仪表盘，判断「该不该开新会话」比凭体感准。

四、三条家规：把折扣从抽奖变工资

既然前缀稳定值 30 倍，就该把稳定做成默认值，别每次碰运气。这一节把纪律摆出来。有意思的是，我自己的会话纪律和 DeepSeek 官方 Harness 的源码设计，最后收敛到了同样的三条，下面逐条对照着讲。

家规自己的用法dsh 源码里的对应
日志只追加，不改写会话流水只进不出，改写需求用新会话表达会话日志只追加，压缩请求也是精确旧前缀加末条指令
上下文能不动就不动项目文档稳定期上锁，要改集中批量改PromptContext 快照门控，快照平静不碰保留历史
前缀源头不乱动装插件、换配置排在任务边界分段按 order 编号装配，注册顺序无关，成品序列天然一致

第一条家规解决「改写」。会话历史只追加，听着像限制，其实是保命：前缀匹配是逐字节的，你回头改了第 3 轮里的某句对话，第 4 轮到第 54 轮的全部缓存一起清零，下一轮按原价重来。dsh 在这一点上做得更绝，写入后不存在修订入口，连压缩都是拿精确的旧前缀加一条末尾指令完成，整趟压缩请求几乎全程命中。架构层面把「手滑」堵死，比意志力可靠。

第二条家规解决「频繁触碰」。上下文容器里的东西，快照没变就不去碰它。落到日常操作：AGENTS.md 进稳定期后当合同对待，不随手改；全局配置的纪律是季度级稳定，因为它是所有会话的公共前缀，改一次，所有会话的缓存链一起断。我的 AGENTS.md 实测单价是 4,200 token/轮（6KB 文档对裸目录的基线差），一个字都不该白付。

第三条家规解决「源头污染」。系统提示的顶端区域、人设、插件注入的工具说明，全站在共享前缀的源头。装个插件、切个模式、换个任务人设，效果等同给整场会话换了开场白，此前攒下的命中一次性清零。这些动作可以做，关键在排期：放到任务边界做，代价从「作废 50 轮折扣」降到「作废 1 轮」。

三条纪律合起来是什么效果？第三方横测口径下，Composio 团队测了八款 Agent 框架，dsh 的缓存不命中率是 0.07%，换算命中率约 99.93%。这个数字说明折扣是工程属性：前缀稳，折扣就在；前缀乱，30 倍的价签原样砸回来。

顺手提一个反面教训，跟纪律同样值钱。我曾经迷信省 token 攻略，把推理档位从 high 调到 low，结果思考 token 反而更多。后来翻流水才发现，那个参数在我的兼容通道上根本没透传给模型。配置文件里写了，不等于模型收到了；任何省钱的动作，先用数据验证生效，再谈坚持。验证方法很简单，两分钟：对照流水里的档位值和实际思考占比，下发了没执行，数据不会说谎。

最后放一张反模式对照表，左边是最常见的手滑，右边是各自的代价和正确姿势。这张表的每一行我都在自己或别人身上见过，值得打印出来贴在工位：

手滑操作实际代价正确姿势
任务中途装插件前缀源头区域变更，已攒缓存一次性清零排期到任务边界，代价从 50 轮折扣变 1 轮
频繁改全局配置它是所有会话的公共前缀，改一次全线断链全局层季度级稳定，拿不准的先放项目层试跑

迷信档位开关参数可能被兼容层静默吞掉，开关是装饰改动当周跑一次对照，流水里核对档位与思考占比

五、月底对账：让账单自己开口

纪律定完，剩下的是让成本可见。我的习惯是每月月底拉一次各通道的开销记录，盘三件事：钱花在哪、折扣还在不在、哪些岗位该搬回本地。这套动作二十分钟，换来的东西叫「不出意外」——成本失控很少源于大额支出，多数是没人看的小额乘以没人数的天数。

对账的入口比多数人想的浅。Codex 侧，~/.codex/sessions 下的逐行 JSON 就是计费流水，四个字段对应全部四个变量：input_tokens 是重发的全部输入，cached_input_tokens 是走了折扣的部分，output_tokens 和 reasoning_output_tokens 是输出和思考。DeepSeek 侧，dsh 会话界面底部的 stats 区域直接显示缓存命中率，不用自己算。

对账能抓到的典型问题，我各给一个真实样本。一是忘关的会话：有一条会话忘了收尾，在后台挂了一整夜，第二天翻记录才发现它是当月增量最大的单笔——数字员工不睡觉，你不喊停它就一直走表。二是悄悄失效的折扣：换通道之后没验证透传，档位开关拨了等于没拨，这个坑在第二节那篇文章里写过，对账表里加一行「参数验证过吗」就能拦住。

三是岗位的再盘点。本地管线的能力边界每个月都在变，上个月还要花钱上云的活，这个月本地跑得动了。月底盘一遍「哪些新任务可以搬回家」，是把那张奶茶账单继续压低的方式。成本管理属于每月二十分钟的例行公事，架构决策只决定起点。

这三件事合成一张对账单，你可以直接抄：各通道总输入与命中率、新增会话的纪律合规（该切的是不是切了）、参数改动的验证记录、可本地化岗位清单。贴在你看得到的地方，比任何记账软件都管用，因为它的每一行都对应一个你亲手做过的决定。

时间预算交代一下，免得这套习惯听起来沉重。二十分钟的分配大概是：五分钟拉流水跑脚本，十分钟逐项核对上面四行，最后五分钟决定下个月的搬家清单和排期。频率不用更高，成本数据是月粒度就够准的东西，天天看除了焦虑什么都不会产出；也不用更低，拖到季度，忘关会话那类增量的追责窗口就过了。

参数验证的 SOP 也一并给出，两步：同一个只读提示词跑两遍，一遍带参数覆盖一遍不带；然后翻各自的会话流水，对照下发的档位值和实际思考占比。两边对得上，参数才是活的；对不上，先解决通道问题再谈优化，否则你优化的是想象中的账单。

两个常见问题

纪律这么多，会不会把工作流搞得很累？ 恰好相反，这三条家规的设计目标是让日常操作零负担。日志只追加和快照门控是「什么都不做」就自动成立的；需要你动手的只有两处，装插件和换配置挪到任务边界，本来就该在那儿做的事，只是排期意识。dsh 把纪律写进源码架构就是这个思路：好的成本纪律不靠自觉，靠让正确的方式成为省力的方式。

我不用 Codex 也不用 DeepSeek，这些结论还成立吗？ 分两层看。每轮全量重发是对话式模型 HTTP 接口的无状态属性决定的，跟客户端、跟通道都无关，这层结论一定成立；缓存折扣的倍数、命中行为、参数透传是通道行为，换了要重新验证。好在验证工具是通用的，各家都会在响应里给 usage 字段，缓存命中量的字段名可能不同，含义一致。方法比结论耐用：先量出自己的两档价和命中率，再决定信谁的攻略。哪天换了通道，把本文的受控 A/B 原样跑一遍，数字会给你同样的答案。

收尾

回到开头那张工资单。本地的一群员工只吃电费，云上的大胃王一顿饭 952 万 token，同一份工作换个人干，开销差 30 倍。这些数字摆在一起，指向同一个结论：数字员工的成本，几乎不由工具决定，由使用者的前缀纪律和盘点习惯决定。

我的判断标准最后就剩两条。每次要让数字员工干活之前，先问这活能不能搬回本地，能搬的都搬，电费是唯一不按字算的钱；搬不回的，问这一轮请求的前缀稳不稳，稳，折扣就是工资的一部分，乱，30 倍价签原价奉陪。

数字员工不闹情绪、不请假、不谈涨薪，它只有一张按字计费的工资单。饭量管住，它是最便宜的同事；饭量放开，它就是账单上最贵的祖宗。而管饭的勺子，从第一个字节发出之前，就握在你手里。
