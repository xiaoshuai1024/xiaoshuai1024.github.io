178 个测试全绿，真实编辑器一连就崩

一个 ACP 服务器接上真实编辑器 Zed，第一个请求 session/new 就当场返回 Internal error，而此刻 CI 里 178 个单元测试全绿、行覆盖率 100%。DeepSeek Harness 的官方复盘文档记录过这次事故，它值得每个写测试的人花十分钟看一遍。行覆盖打满的项目，照样会在用户走的路上翻车。

一、Zed 连上来的一瞬间发生了什么？

报错稳定得像刻进去的。ACP bridge 启动一切正常，Zed 发来第一个 session/new，服务器直接返回：

Internal error: cannot get property "agents" without inject
Internal error: cannot get property "sessionPersistence" without inject

前一条出现在建新会话时，后一条出现在恢复旧会话的 session/load 里。属性名不同，句式相同：读取某个属性时发现从头到尾没人注入过它。

影响面也由入口位置决定：建新会话与恢复会话恰好是编辑器接入后最先调用的两个 RPC，任何想把 agent 挂进 Zed 的人都会当场撞墙。复盘顺带记下一句止损结论：崩溃前没有任何内容被持久化，数据零丢失；代价集中在功能完全不可用，加上先后两轮定位各自烧掉的调试时间。

时机上还有个反直觉的细节：异常抛在插件加载阶段，而不在任何请求处理器内部。session/new 只是恰好成了触发器，真正引爆的是加载过程本身。这解释了失败为何稳定到毫无波动：编辑器接入的入口链路每一次都会装载同一批插件，雷埋在必经之路上，谁路过谁触发。

二、178 个绿和一个报错

反差摆在一起才有杀伤力。同一份代码，单元测试 178 个全绿、行覆盖率 100%；换真实编辑器进来，第一次握手就断在两组属性上。完成度指标和存活能力之间那段距离，就藏在插件系统的挂载方式里。

测试给插件安排的是一条温室路径：手工把插件对象装进容器，依赖项提前备好，inject 天然就在。Zed 走的才是用户的路：Loader 读入口模块、辨认导出形态、动态装配服务，一步都不能少。

两条通路在源码地图上几乎不相交。走不到的那条路上埋着什么，全绿的测试给不出任何线索。

178 这个数字也值得拆开看成色。复盘记载的测试清单相当体面：codec、内存传输、生成的协议消息、失败路径、HMR 各有专属单测；另有一条需要 key 的真实 API e2e 和一条无需 key 的 stdout 纯净性 e2e。规模与形态都在水准线上，唯独形态这个维度出了问题：清单里的每一项都没打算伪装成真实 Loader。

分岔点还有个隐蔽属性：它藏在框架语义层，业务代码层看不见。bridge 自己的逻辑、协议处理、会话管理全都经过了充分测试；唯独「一个模块如何变成容器里的插件」这段胶水，两边各有一套实现，测试只覆盖了其中与生产无关的那套。审查 diff 的人看到的是一段段被绿灯覆盖过的逻辑，感知不到脚下悬空的部分。

三、「shadow 边界」理论是怎么倒掉的？

第一嫌疑人是 shadow 边界。这套机制在源码里真实存在，报错的长相也和它的失效模式对得上，理论乍一看稳了。验证一做，馅就露了出来。

动作有两步：给 vendor 目录里的 reflect.ts 加桩，盯着 fiber 遍历的每一步；再起一个真实子进程，让完整链路从头跑一遍。异常落点很快浮出——apply() 第 179 行，时机在插件加载阶段，当时遍历到的还是 ROOT fiber，头上根本没有 shadow。session/new 的现场和理论要求的条件对不上，理论出局。这段排查比结论更值钱：嫌疑再合理，也要拿插桩和真实进程验一遍才算数。

复盘为这次弯路留了一句分量很重的注脚：优雅的 shadow 解释确实是真实的，但它对应第二个 bug；第一个 bug 只是一行导出错误。此前数小时的推理再自洽，也敌不过一个 fiber 遍历里的 console.error，后者几分钟就把异常落点打印到了眼前。取证动作的最小颗粒度越细，纠偏越快，理论的保质期就越短。

四、两个 bug 和它们共享的病根

第一个 bug 小得离谱：插件文件里多了一行 export default apply。多出来的默认导出让 Loader 认到的导出形态失真，连带把应该注入的整套 inject 拒之门外。删掉这一行，session/new 立刻通了。

丢的过程值得逐帧看。Loader 收到导入的模块先做一次形态归一化：只要 exports.default 存在就优先取它，再看 __esModule 标记决定要不要继续解包。命名空间插件把 name、inject、Config、apply 并排挂在模块命名空间上，invariants、llm-deepseek、tool-bash、tui 无一例外都长这样；多出的那一行使归一化产物从完整命名空间缩成一枚裸函数，三个并列导出全部随命名空间一起蒸发。Loader 接着拿空 inject 搭起插件 fiber，apply 第一行去读 ctx.agents，沿 ROOT 到 Include 到 Loader 再折返的路线找遍每层 store 都落空，撞到根节点后掷出那句报错。

修复过程中第二个 bug 浮出水面：可选服务的查找要经过一层可追踪代理，这层代理在 shadow 边界处把请求拦了下来。它和导出判断是完全不同的机制，需要单独隔离修复，前面那份理论的尸体旁边还站着另一个真凶。

第二个机制说来更有味道。AgentLoop 的静态注入清单故意不含 sessionPersistence：一旦声明依赖它，非持久化的演示场景就会在恢复时苦等一个永远不会到来的存储后端，整个挂死。真实安排是让一个兄弟插件各自持有该服务，AgentLoop 以机会主义姿势读取，读到就用，读不到不碍事。麻烦出在读取路径上：经由可追踪代理进入方法调用时，this 被重绑进一个 shadow 对象，其 ctx 回指 AgentLoop 自己的构造上下文，属性解析从这条 fiber 起步且只朝祖先方向爬升；sessionPersistence 住在兄弟分支上，注定不在祖先链里，爬到根只能抛错。

修复 #2 把读取改写为 ctx.get(‘sessionPersistence’)。这个方法基于全局 isolate 键控 store 做查找，与 fiber 拓扑无关，兄弟分支也能命中，同时保留活跃状态检查；服务未活跃时读到 undefined，不会把一个已经拆除的后端递到调用方手里。同一次修改还在代码旁留了注释，把 shadow 遍历这个陷阱钉在下一个读者眼前。

两个 bug 的共性一眼可见：测试挂载插件走的路径，把真实加载和服务解析整段跳了过去。Loader 的导出判定逻辑零覆盖，可追踪代理的行为也从没人在真实链路里观察过，178 个绿色自然抓不到它们。

五、四个缺口放跑了两个 bug

复盘把「为什么没有测试抓住它们」拆成了具体的窟窿，一共四个。其一，内存 harness 手工构建插件对象挂载，inject 由测试亲手递进去；unwrapExports 这个函数只有 Loader 会调用，手工挂载绕开它的方式让它在这个仓库里等于从未被测过，第一个 bug 结构性不可见。

其二，同一个 harness 把一切平铺挂在一个根上下文上，AgentLoop 的恢复要么跑在顶层、要么经由的 shadow 原点解析回 root，两条路都避开了祖先遍历的死胡同，第二个 bug 同样结构性不可见。其三，唯一无需 key 的 e2e 发送 initialize 然后检查 stdout 纯净性，而 initialize 根本不会触达插件工厂，于是连它在内的所有常规通道都对两个 bug 网开一面。

其四最有戏剧性：真正驱动 session/new 与 session/load 的那个 e2e 需要 API key 才能运行，CI 环境无 key，直接跳过；开发者本地看到的绿色来自一份陈旧的已构建 lib/，里面的旧代码恰好满足模块解析要求。也就是说，本地那枚绿钩子里装的是一个早已过期的事实。后来新增的守卫专门修的就是这一格：spawn 子进程时固定 TSX_TSCONFIG_PATH，把 tsx 的解析锚在仓库 tsconfig 上，与运行目录解耦，保证被测的确定是源码本身。

官方文档随后把这层教训编成了通用规则，写进 testing 文档：手动构建插件的测试验证不了插件的加载方式，至少要有一条测试端到端驱动真实 Loader 与导出路径；核心操作不调用模型时就无需 API key，这样的测试属于 CI，不该锁在 key 门禁后面。

六、行覆盖打满为什么什么都证明不了

先把指标的定义收紧。行覆盖率回答的问题极其克制：这行代码有没有被执行过，执行过一次即计满分。它不记录执行顺序，不关心并发与重试的时序，更不过问执行者是谁、参数像不像生产流量。178 全绿加上 100% 覆盖，合起来描述的只是一个封闭房间里发生过的故事。

对照这次事故，覆盖盲区能精确分成三种。路径缺口：unwrapExports 从未被一份「从 cordis.yml 导入的模块」驱动过，用户走的那条分支没有人踏足；拓扑缺口：shadow 与 fiber 祖先关系属于结构性事实，换个挂载方式结论就翻转，平铺测试把兄弟分支整条抹掉了；时序缺口：首次握手这种时刻只在集成边界出现，单元环境里根本无法自然发生。行覆盖指标对这三层全部沉默，因为它设计时就只测量另一个维度。

官方复盘的收束句值得原样抄下：覆盖率证明代码行被执行过，它不能说明功能是否按交付方式正常工作。前半句是它的全部能力，后半句是这次事故的全部代价。testing 文档还在旁边补了一条操作性警告：测试若经由包导出把导入解析到构建后的 lib，陈旧产物会让进程加载出第二份模块单例，行为对不上任何一方的源码；源码路径与产物路径必须写进约定、显式选择。

七、护栏修在了结构上

官方最终把修复收进 PR feat/acp-2-bridge。改动之外更有分量的是新增的结构护栏：一条无需 API key 的真实 Loader 测试，专门覆盖走上线路径的插件装载；再加包级规则，管住插件的导出形态与可选服务访问。前者让同类问题在下一位作者的终端本地就被拦下，后者把约定变成了静态检查能抓的东西。

护栏自身也按规矩验过货：把 export default apply 还原回去，新的无 key e2e 立刻变红。仓库文档为此补了一条通用原则，守卫只有在回归真的能让它失败时才有效——红过一次的守卫才算存在。testing 文档同时把默认导出陷阱写成了可复制的断言模板：显式断言 default 不在模块导出中，加上 unwrapExports 往返校验，任何插件包都能照抄一道。

本文的现象、数字（178 绿 / 100% 覆盖 / apply():179）与修复出处，均来自官方复盘文档 docs/postmortem/0001-acp-default-export-drops-inject.zh.md 与 PR feat/acp-2-bridge 的记载，没有外推的部分。

八、给「全绿」降一次权

覆盖率回答的问题是「这段代码被执行过吗」。它永远回答不了另一半：执行的路径是不是用户走的那条。经验规则可以这样定：在关键集成点上补一条带真实依赖的 e2e，性价比高于再堆一百个单测。Loader、进程启动、握手首包这类位置一旦失守，整个功能等于不存在，配得上最接近现实的探针。

测试套件的作用是把已知风险圈起来，真实的接入方式才定义产品活着的样子。下次看到一片绿色先别急着放心，问自己一句：有没有任何一个测试，用上了用户即将使用的那种打开方式。答不上来的时候，五百个绿也顶不住 Zed 的第一次握手。
