快照测试把 bug 认成标准答案：DeepSeek Harness 事故复盘

全绿的测试套件也会替故障背书：DeepSeek Harness 有一次合入，单元测试、覆盖率、快照、文档、构建、hygiene 检查全数通过，实际情况是文件系统工具栈从未注册，七个场景调用的都是注册表里不存在的工具。此后的每一次 CI 绿灯，都在给这个 bug 作证。

事故记在官方复盘 0002（docs/postmortem/0002-js-expression-disabled-filesystem-tools.zh.md，本文细节全部出自这份一手材料）。最危险的回归就藏在绿灯里：测试没抓到 bug 还有救，bug 的输出一旦被刷新成新基准，往后每一条全绿的流水线都在为故障站台。

一、七个场景同时调用不存在的工具

先交代这组组合的出身。默认的 ACP（Agent Client Protocol）组合有意只启用 bash，因为它的沙箱约束不了进程内的文件系统提供方；可文件系统快照场景又需要 read、write、edit 三个工具，于是这些插件被放进默认的 cordis.yml，附带一个 disabled 表达式，意图是只在全权限启动和快照模式下放开它们。

实际运行结果是任何一个模式都没放开。表现相当齐整：七个文件系统场景加一个混合工作区编辑场景，全部调用了注册表中不存在的工具。结构化会话日志里带着这样的错误：

ToolNotFoundError, code = UNKNOWN_TOOL

而 stdout 上渲染出来的，只是一张通用的失败工具卡片，失败原因被完全抹平。

两类记录的落差值得单独停留一会。日志保留的是事实层：工具解析不到，代码 UNKNOWN_TOOL，指向注册表层面的缺席；stdout 渲染出的是表情层：一张谁都长得一样的失败卡片。事故后期能够定案，靠的全是前者；如果整个系统只剩后者，这桩事连被发现的资格都没有。

二、全绿流水线放行了什么？

时间线短得可疑。PR #261 做了三件事：整合 ACP 组合、刷新文件系统快照、引入条件式文件系统配置项。合入门禁逐一亮灯：单元测试、覆盖率、快照、文档、构建、hygiene，六类检查全部通过。按这套门槛自己的口径，这次合入找不出毛病。

拦下它的力量来自人工评审，此前所有自动门禁一路放行。翻看刷新后的文件系统预期输出时，两种异样浮出来：通用的失败卡片，配上结构化的 UNKNOWN_TOOL 结果。随后的一次真实 Loader 启动给出确认级证据：每个 disabled 字段拿到的仍是表达式对象，每个文件系统 fiber 都从未被创建过。

六类检查各管一段辖区：函数行为、覆盖数字、输出形状、文档、构建产物、仓库规范。合起来看像一张严密的网，但「这些场景依赖的工具究竟进了注册表没有」这个疑问，不在任何一类的提问范围里。事后重读这份清单，缺掉的那一格比填满的格子更有信息量。

这层分工很值得多看一眼。CI 只回答「回归能否按原样回放」，「行为是否正确」被默认留给了人眼，等价的自动判定在当时并不存在。人这道防线挡住了故障随合入扩散，但它太贵、也太不稳定；此后仓库补下的每一条守卫都指向同一个方向：把这层判断从人的眼睛里搬进检查器。

三、一个 truthy 对象的杀伤半径有多大？

源头是一个想当然的假设。作者想用 disabled: !!js 这类 JS 表达式按启动模式开关 fs 插件，默认认为 !!js 标签在整个 Loader 配置项上都生效；实际实现里只有 entry.options.config 字段经过 Entry._resolveConfig() 做 JS 表达式求值，disabled 属于配置项元数据，Entry.disabled 读到的永远是未加工的原始值。对这套 Cordis 插件装载机制不熟的读者，可以先看插件系统那篇的铺垫。

于是链条变成这样：Include 把每个 !!js 标量解析成一个表达式对象，Loader 又不对元数据求值，disabled 字段拿到的就是一个 truthy 的表达式对象，布尔判定恒为真，fs 栈因此在所有模式下保持禁用。更麻烦的是 YAML 标签在语法上完全合法，加载过程不给任何诊断信息，写错位置的配置就这么静默通过了。这重边界还带着不对称：Loader 对 config 的插值是递归做的，嵌套再深的表达式最终都会被求值；悬在同一配置项旁的元数据字段却从头到尾原样读取。近在咫尺的两块字段，适用两套互不通气的规则。

求值边界还埋着一层不对称。config 走插值、元数据走原样读取，两者紧挨着住在同一个配置项里，字面写法却分不出区别；!!js 标签在哪个字段生效，答案不在 YAML 里，只在 Entry 的实现代码里。想让边界可见，要么实现层把越界的表达式拒掉，要么文档把生效范围钉死，二者在这份代码库里当初一样都不存在。

四、Loader 边界上的两起事故

单独读 0002，教训容易被压扁成「表达式放错了位置」的个案。把它和同目录的另一卷复盘并排，结构才完整显形。178 个测试全绿那篇记录的是同一片区域里的另一起：一行多余的 export default，让 Loader 的 unwrapExports 归一化导出形态时优先取了 .default，模块命名空间连同声明的 inject 整体被丢掉。两起事故的触发字符不同，案发坐标相同：都在装载器对插件做形态加工的那一小段代码里。

单点拆开更能体会这种盲区的精度。以导出那一案为例：Loader 收到模块先做形态归一化，只要 exports.default 存在就优先取它。命名空间插件把 name、inject、Config、apply 并排挂在模块对象上，一旦多出一行 export default，归一化产物就从完整命名空间缩水成一枚裸函数，inject 随之无处安放。每一行语法都合法，合并后的结局却是插件跑在一个零注入的 fiber 里。

这片区域的特殊之处在于源码阅读保护不了任何人。disabled: !!js 是完全合法的 YAML 语法，export default 是完全合法的 TS 语法，逐行审查都挑不出毛病；实质差别只住在装载器的实现选择里，diff 视图和编辑器一概不显示。两个仓库各自补的守卫也因此长得像孪生：一侧把默认导出禁令写成包级规则，另一侧把元数据表达式写成静态拒绝。一致的姿态是把这类判断从人脑搬进机器，因为人在这里已经系统性失明两次。

五、快照循环怎么把 bug 固化成标准答案

快照框架把任何确定性的 transcript 都当有效行为。七个场景稳定产出同样的失败卡片和 UNKNOWN_TOOL 日志，确定性无可挑剔，刷新 fixture 时这批失败输出就被整体接受为新预期。此后每次跑套件，断言验证的都是回归能否按原样回放，与行为是否正确已经无关。

校验层也没能独立拦住它。Header pin 验证了组合后的工具 schema，但文件系统场景共享来自默认组合的 pin，没有任何断言证明过所需工具已注册；刷新赶在语义断言拒绝缺失工具之前，就把预期的 stdout 和会话日志一起改写了。问题最终靠人工评审翻看刷新结果才暴露，随后的一次真实 Loader 启动给出确认：每个 disabled 值仍是表达式对象，每个文件系统 fiber 都没创建过。

顺序在这里是决定性的变量。假如存在一条独立于 fixture 的语义断言，刷新无论怎么跑都会先撞上它；现实是刷新先行，断言缺位，产出物理所当然地变成了输入。流水线上谁先执行，本身就是一种设计决策，只是当时的决策没人做过。

事后补上的两道闸门把这个顺序变量也一并收走了。静态解析把元数据表达式拦在提交之前，快照检查拒绝结构化的 UNKNOWN_TOOL 结果进入新运行或已提交的 fixture；刷新即便仍排在前头，产出也无处置放。

六、比 bug 更冷的一道思考题

实际运行的受限默认模式并没有获得意外的文件系统访问权限，这个结局带着运气成分：故障方向恰好是多禁了。复盘明确警告，草率地修好插值、让条件生效，受限模式反而可能拿到 fs 访问。复盘原文把这层边界写成了一段足够引用的判定：权限预设在运行时更新的只有 bash 沙箱和审批状态，挂载不了、卸载不掉、也约束不了进程内的文件系统栈，组合期的声明没法安全跟着运行时的预设走（沙箱这层设计我在fail-closed 那篇里展开过）。

顺着这段警告推一步会更冷：修复一个「所有模式都禁用」的 bug，最符合直觉的动作就是把条件改对，而那个动作在这个权限模型下会制造安全事件。一个修法本身成了新的风险点，说明出错的不只是一个字段，字段背后的所有权分配早就不成立：运行时预设管不了进程内栈，声明期却允许把它们写在一起。

七、守卫怎么逐个钉在失守点上？

官方的最终方案分两层，先改声明方式，再上自动闸门，逐条对应失守位置。文件系统场景改从显式的 fs.cordis.yml 启动：固定的全权限 overlay，配对应的回放配置和独立的 request-header 类，能力声明不再绕经 disabled 开关。需要文件系统的场景自己亮明身份、自带授权形状：固定的全权限 overlay 负责放权，配套的回放配置让场景在离线重放中照样成立，独立的 request-header 类给这一族请求立起单独的档头。绕经 disabled 开关的老路就此作废。

文档层的动作是把假设钉进必读材料。AGENTS.md 与 Cordis 入门的「Loader 配置」一节同步标注 !!js 仅在插件 config 内有效、各字段如何求值有据可查，条件式组合应改用 overlay。事故起点原本是一句只存在于作者脑子里的臆测，如今被写进了每一个新贡献者迟早会读到的地方；入库文档的作用不是装饰，是在下一次有人临场猜测之前先把答案递过去。

剩下两道都是自动闸门。verify-cordis-config 静态解析仓库里的 Cordis YAML，凡 Loader 配置项元数据中出现表达式节点一律拒绝，include patch 与插入的配置项同样覆盖在内；dsh-acp-snapshot 则在全新运行和已提交的 fixture 中拒绝结构化的 UNKNOWN_TOOL 结果。前一道把非法形态挡在提交前，后一道把「失败输出成为预期」的那条通道整个焊死，两头各锁一次。

八、给你的快照套件做一次 X 光

复盘给出的教训说得很直白：语法上被接受的值不一定在该位置被求值，要记录并验证具体哪些字段会被插值；快照刷新是 fixture 的生产过程，谈不上正确性审查，语义上不可能的结果（例如已注册工具缺失）需要独立于预期输出的断言；权限控制只应描述自己实际管辖的能力。

我更愿意把它翻译成一个可执行的动作：挑个空闲时段，故意破坏一处行为，再跑一次快照。断言变红，说明你的测试还有行为判断力；假如它顺滑地把新的坏结果也存了下来，你仓库里就埋着同款雷。快照的价值在于捕获意外变化，它给不了语义正确性，两种职责混在一起时，绿灯越多越要多留一个心眼。看完这卷复盘再去回望 Loader 边界上的另一起同类案，你对绿灯这个符号会多一层分辨力：它能证明历史照旧轨迹重放，证明不了脚下的路通往真实用户。
