AI 编程省 token 技能：rtk 实测 9 天与完整用法

AI 编程的账单里，最不被看见的一项是命令输出。模型每跑一条 ls、git log、grep，返回的原始文本会整体进上下文：一次全量目录列表几万字节，一轮排查下来几十条命令，token 就这么漏掉了。

rtk（Rust Token Killer，开源仓库 rtk-ai/rtk）是堵这个漏洞的工具：一个 Rust 写的 CLI 代理，官方口径是压缩 60% 到 90%。装上之前我对这类数字是存疑的，压得越狠语义丢得越多，这是这类工具的物理规律。全局跑了 9 天之后，我机器上的留存数据是：2301 条命令，输入 360 万 token，吐回 27.6 万，省下 330 万，压缩率 92.3%，比官方口径的上限还高。

但这个数字不值得直接羡慕。它成立的条件、它的收益构成、它的风险面，才是这篇要拆的东西。我的结论先给：输出压缩不是一个装上就完事的工具，是一项要练的技能——练什么、怎么练、什么时候不该用，文末附完整使用方式。

一、先搞清它站在哪：上下文的第一道闸

普通工作流里，AI 助手执行 Bash 命令，返回值原样进上下文窗口。装上 rtk 之后，命令会先被改写，输出在进入上下文之前过一道过滤器。位置画出来就一条线：命令产生原始输出，过滤器裁剪压缩，模型看到的是瘦身版。

有人会问：让模型自己总结输出不行吗？位置不对。输出一旦进了上下文，占用的窗口就已经花了，模型再怎么总结都是花完之后的补救。过滤器的位置价值在于「进上下文之前」，省下的是窗口本身，顺带把模型的注意力从找行里解放出来。这也是它和「提示 AI 挑重点读」的区别：一个省资源，一个花资源。

它压缩的手段归起来五类。裁剪：ls -la 的权限位、属主、日期列直接砍掉，只留文件名和大小。分组：搜索结果按文件归拢，重复前缀合并。截断：超长输出保留头尾，中间留一行「[N more lines]」标记。去重与浓缩：日志去重、diff 只留变更行。摘要：对特定场景直接给两行技术结论。

五类手段不是均质的。裁剪和分组是结构性收益，砍掉的列模型本来就不需要，接近零损失；截断和摘要有损，是风险集中区。同一份输出可能同时吃到多类手段，git log 就是截断加去重的组合。判断一条输出会被怎么处理，看它的命令家族落在哪一类，这也是分清探索类和核对类的依据。

过滤器按命令家族建，rtk --help 里能数出一百多个子命令：文件类的 ls、tree、read、find，搜索类的 grep、rg，版本控制的 git、gh、glab、diff，测试类的 test、jest、vitest，运维类的 docker、kubectl、psql、aws，还有 err（只显示错误和警告）、json（只看键）、smart（两行技术摘要）这类专门的收敛命令。子命令虽多，选择逻辑只有一条：看输出的最终用途。要看全貌的（ls、tree）重裁剪，要看命中的（grep、rg）重分组，要看过程的（git log、diff）重截断与浓缩，要结论的（smart、summary）直接摘要。记住用途逻辑，一百多个子命令不用背。

这套设计决定了它的收益模式：命令家族覆盖得越广，你的会话里被压的面越大。同时它留了一条硬后路，rtk proxy <命令> 直通原文，一个前缀的事。这个后路后面会反复出现，它是这项技能能放心练的前提。

二、9 天留存数据：钱省在哪一天、哪类命令

rtk gain 是它的统计入口，按天、周、月、命令四个维度留存。先交代口径：这是全局维度，覆盖本机所有工作区的助手会话；tracking 由 rtk 自带，历史默认留九十天，我拉的是 2026-08-20 到 2026-08-28 的完整留存期。总量构成如下：

命令类型次数节省 token占比
rtk read（读文件）523220 万67%
rtk grep（搜代码）547110 万33%
其余一百多个子命令合计1231不到 2 万<1%

第一眼结论很刺眼：省下的 330 万几乎全部来自读文件和搜代码，其他命令加起来是零头。原因不复杂，这两类命令的输出天然最肥，一次 read 就是整个文件的原始文本，而且它们是 AI 排查问题的最高频动作。523 次读、547 次搜，平均每次会话都在几十次的量级。再算单次均值，差距更直白：read 单次约四千二百 token，grep 单次约两千，高频之外还肥上加肥，大头落在它们身上毫无悬念。

命令粒度上还有个值得单独说的细节。rtk gain 的命令排行里，靠前的都是高频小户，read 和 grep 各五百多次，单次收益不大，靠次数堆出体量。但榜单里混着一个独行侠：rtk diff 只出现过一次，单次就省了 3.3K token，压缩率 99.8%。一个几千行的 diff，过滤后只剩变更行，这是过滤器最漂亮的场面。反过来看，git commit 出现 13 次只省了 2.5K，命令输出本来就瘦，压不出花。单次收益看输出的基线冗余，总收益再乘频次，这个公式后面还会用到。

按天拆，能看到另一种规律。2026-08-20 单日 193 条命令省了 150 万 token，压缩率 97.8%，那天我在通读一个完全陌生的代码库，全天都是 read 和 grep。2026-08-21 只省了 1.1 万，那天在写稿，一天没怎么翻仓库。2026-08-27 又是一百二十万量级。

8 月 27 日那天值得单独回看。438 条命令省了一百二十万 token，那天的日志主题是视频号定时发布链路修复和九支视频的四平台排期核验，大量页面状态扫描类输出，全是肥的。没有这层过滤，那个下午的会话至少多经历几轮压缩，核验做到后半段时，前几轮的平台状态恐怕已经被压缩吃掉了。

同一个工具，日收益差一百多倍，差异变量只有一个：当天会话的探索强度。这是这项技能的第一课，装之前先看清自己的会话画像，读和搜占大头的人吃肉，执行型会话喝汤。

三、四组对照实验：收益等于冗余乘频次

宏观数字之外，我跑了四组同命令的前后对照，rtk proxy 走原文，过滤器版本走压缩，字节数直接可查。方法先交代：同一条命令、同一目录、同一时点跑两遍，字节数用 wc -c 计。字节数不严格等于 token 数，中文和代码的换算比例不同，但同一份内容压缩前后的字节比例与 token 比例同向，看趋势够用；要精确值的读者可以在自己的 gain 里匹配同款命令看单次均值。

第一组，目录列表。ls -la 一个 60 多个文件的目录，原文 9951 字节，压缩后 5106 字节。砍掉的是权限位、属主、硬链接数、日期列，留下文件名和大小。对「找文件」这个任务，信息一点没少，属于结构性收益。

第二组，提交历史。git log --oneline -12，原文 3354 字节，压缩后 2084 字节，砍掉三分之一。每条提交消息保留前九十个字符左右，超长部分截断。我的提交消息习惯把关键细节写在前缀里，前九十字符基本够判断改动主题，但要看完整描述的场景确实存在，此时该走 proxy 展开看，硬读截断版会带着残缺事实往下走。

第三组，搜索命中。搜一个出现在多篇文章里的关键词，原文 2315 字节，压缩后 2274 字节，收益约等于零。搜索命中的行本来就短，去掉的只有路径前缀的重复字符。这组实验把「压缩率 92.3%」拉回地面：宏观数字是 read 类肥输出撑起来的，瘦输出压不动。

第四组，小目录树。tree -L 1 一个小目录，原文 92 字节，压缩后 78 字节。没意义的十四个字节，连横线都省不出花来。

四组放一起，收益公式就出来了：节省量 = 输出基线冗余 × 命令频次。目录列表和整文件阅读两项双高，所以 read 是大头；搜索频次同样高但输出瘦，收益薄；低频命令再肥也贡献有限。这个公式也回答了「装不装」的一半问题，先看你自己的高频命令长什么样。

四、三类风险与一条误会：有损是有账的

压出来的每一字节都不是免费的。风险三类，另有一条常见误会，都摆出来。

第一类，截断的误伤。截断本身是可见的，读到中间被裁的文件会留「[235 more lines]」标记，头尾都在，模型知道自己看到的是节选。真正要防的是分组截断：搜索结果按文件归拢后，单行超长部分被切掉，你要的那个关键词位置可能正好在切口后面。后果不致命，代价是多跑一次原文查询，一次往返。

第二类，语义的偏移。git log 那组实验里，提交消息超过九十字符就断。如果判断依据恰好藏在消息尾部，读压缩版会得出和原文不同的结论。这类偏移没有报警，它不报错，只是让你带着残缺的事实往下走，比截断更阴。

第三类，代理层自身的故障面。多一层代理等于多一层可能出 bug 的软件，这是所有中间层工具的通债。我的 0.45.0 用了九天没复现过输出错误，但我不会把它当零风险：涉及发布、金额、删除的命令，我一律走 proxy，这些场景里「极小概率的输出异常」是不可接受的代价。

误会那条是脱敏。有人指望过滤顺带把内网地址、私有路径挡在上下文外面，它没有这个设计目标，过滤逻辑只认格式冗余，不认敏感字段。私有信息要在源头处理，输出之前就该清干净，过滤器只负责省，不负责保密。

对应的绕行规则三条，也是这项技能的核心纪律。核对类输出必走原文：发布门禁、日志审计、lint 报告、任何要逐字对账的场景，一个 rtk proxy 前缀的事。探索类输出放心交给过滤器：读码、搜码、看目录，线索断了再回原文。每周看一次 rtk gain 的构成表：read 和 grep 占比掉到一半以下，说明会话变瘦了，hook 可以摘了。

三条纪律背后是同一条判断式：这条输出我需不需要为它的每一个字符负责。需要，proxy；不需要，过滤器。把这条判断式讲给协作者，比讲工具用法更有用，工具会换，判断式不会。

五、钱和窗口，分开衡量

很多人第一反应是拿钱衡量这个工具。两本账分开算，结论不一样。

钱这本，按订阅口径折算。同样的 330 万 token，按 Claude Max 20x 档（月配额约 1.2 亿）算是 2.8%，零头；按 Pro 档（月配额约 600 万）算是 55.3%，半个月配额。按 API 计价粗算，330 万输入 token 在主流模型三美元每百万的档位上约合十美元，九天的量。你站在哪个档位，决定了这本账是零钱还是工资。

窗口这本更值钱。330 万 token 如果不经压缩直接涌进上下文，意味着几十次完整的窗口轮换：200K 的窗口被目录列表和源码原文塞满，触发压缩，压缩完的会话丢失细节，模型重新搜索、重新读取，再塞满，再压缩。每一轮都是真金白银的重复劳动和一次记忆清零。压缩之后，同一个窗口装下的有效信息密度高了几倍，压缩的触发次数成倍下降，会话的长程记忆完整得多。这道换算你自己也能做：把 gain 里的节省总量除以你的窗口大小，得到的就是替模型省下的完整窗口轮换次数。我的 330 万除以 200K，约等于十六轮；每轮轮换背后是一次上下文压缩加一段记忆丢失，换算完，窗口的收益就从抽象变具体了。

所以钱是小头。这项技能的产出，是让你的模型在同样的窗口里保持更长时间的清醒。长排查、大仓库、多轮迭代的场景里，这份清醒比省下的订阅额度值钱得多。

还有两笔延伸的小账。一是缓存：主流模型对重复前缀有 prompt cache，压缩后每轮输出有变化，前缀一致性会不会受影响？我的留存数据里看不出明显反噬，但这个交互我没做专门实验，先记成开放问题，谁在乎谁去测。二是多 agent：我的工作流强制能并行就开子 agent，每个子 agent 都有独立的上下文窗口，输出压缩的收益按 agent 数量成倍放大。单 agent 用户省一份，并行管线用户省 N 份，这大概是它在我的工作流里表现格外好的原因之一。

六、边界：这些场景我劝你别装

技能的价值等于收益减维护成本，有几类场景这项技能是负的。

输出本来就瘦的会话：日常工作如果是改配置、跑固定脚本、调现成接口，高频命令全在瘦输出区，装它收益趋近于零，白多一层代理。审计要求原文留存的管线：任何需要逐字对账、合规留存的场景，有损压缩是原则问题，不是效率问题。执行型短会话：几分钟一次问答的用法，窗口压力本来就不存在。

团队统一镜像强推是另一档否定。工程层治理输出，指的不是行政规定，是命令本身带参数：git log --oneline 天然比全量 diff 瘦，测试框架的静默模式天然比完整日志瘦。参数写进脚本，一次治理全员受益，不引入新依赖。末端压缩是给「没有工程层」的场景准备的补丁，个人仓库没有工程层，所以它是正路；有工程层的团队再装它，是在补丁上打补丁。

还有一类半否定：API 按量计费的大户。钱上它仍然成立，但这类用户的痛点通常是速度和稳定性而非 token 单价，多一层代理换省钱的买卖要自己算一遍延迟与故障的期望成本。rtk 的额外延迟在十毫秒量级，多数情况可以忽略，账还是要自己过一遍。

摘 hook 的时机也有判据，不用凭感觉。连续两周 rtk gain 的日节省低于一万 token，或者构成表里 read 和 grep 加起来掉到一半以下，说明会话形态已经变了，这一层可以撤。工具跟着会话走，会话变了还守着旧配置，就成了负担。

七、把它当技能练：三条纪律、进阶玩法与练习路径

工具是装完即止的，技能是练出来的。这项技能的练习量不大，三条纪律加一组进阶玩法。

纪律前面都出现过，收拢一下。其一，分清两类输出：探索类交给过滤器，核对类走 rtk proxy，判断标准是「这条输出我要不要逐字负责」。其二，定期复盘构成：gain 的命令分布表是会话画像的自画像，read 和 grep 掉到一半以下就该考虑摘 hook。其三，盯住故障面：升级版本后抽几条常用命令对比原文，确认过滤器没有把关键信息压丢。抽检我自己只盯三条，git log 的截断长度、read 的头尾保留、diff 的变更行完整性，因为它们是我高频命令里仅有的三个有损家族，结构性裁剪那几个从来没让我操过心。

进阶玩法是几个专门的收敛命令。rtk err <命令> 只留错误和警告，跑构建跑测试时干净得多；rtk test 同理只看失败用例；rtk json --keys-only 对大 JSON 先看结构再取值；rtk diff 只看变更行；rtk smart <文件> 给两行技术摘要，快速判断一个文件值不值得细读。这些命令的共同逻辑是把「模型自己过滤」变成「进上下文之前就过滤」，模型省下的注意力用在判断上。

练习路径可以按周排。第一周只观察：装上什么都不做，每天扫一眼 gain，先建立对自己会话画像的直觉。第二周练纪律：刻意区分探索和核对，每次想看原文先问自己这条输出要不要逐字负责，把 proxy 用成肌肉记忆。第三周调配置：把不关心的目录加进忽略列表，把高频的瘦命令从过滤器里排除，让过滤器围着你的画像转。

最后一步是把构成表讲出去。写给团队 wiki 也好，写进复盘也好，解释收益来源的过程会逼你确认每个数字的成因，我这份九天数据的留存过程就是这么来的。输出压缩这件事，最贵的不是 token，是不知道自己的 token 花在哪，讲一遍就治好了。

八、使用方式：从安装到生效

最后是实操章节，从零到生效四步，照做即可。

第一步，安装。到 GitHub 仓库 rtk-ai/rtk 按你的平台取安装方式，产物是单个二进制文件，扔进 PATH 即可。Windows 上我放在用户目录的 .local/bin 下，配置文件在 AppData/Roaming/rtk/config.toml，默认配置就能用，想调忽略目录、显示宽度再改它。

第二步，注册 hook。执行 rtk init -g，它会把改写逻辑挂到 AI 编程助手的命令执行层。挂好之后助手跑的每条 Bash 命令都会先过 rtk。

第三步，验证生效。随便让助手跑一条 ls -la，输出明显变瘦即成功；再跑 rtk gain，能看到计数在涨。这一步别跳过，hook 没挂上时 rtk 会一直打告警，看到告警先查挂载。

生效之后建议做一次个性化调整，只动一处：把构建产物和依赖目录加进配置的 ignore_dirs，比如 target、node_modules、dist 这类你从不让模型细读的目录，默认列表里已有一部分，按项目补全。显示宽度、忽略文件那些选项等用出体感再动，一次只改一个变量，改完跑两条常用命令对比，确认没有误伤。

三个安装期的坑提前说。一是 PATH 不生效，Windows 装完务必重开终端再验证，老会话里的 PATH 是旧的。二是 config.toml 提示不存在是正常的，默认配置内置，文件只在你真的要改时才需要创建，我的至今没建过。三是告警常驻：我的环境里那条「No hook installed」告警一直挂着，但 gain 的数字一直在涨，说明压缩实际生效，告警来自它的 init 状态检查，和实际挂载通道对不上。看到告警别慌，用 gain 的数字判断，别信提示文案。

第四步，日常使用。高频命令按下面这张速查表来：

rtk gain              # 节省统计（-d 按天 / -m 按月 / -q 配额折算）
rtk gain -q -t pro    # 按订阅档位折算省下的配额占比
rtk read <文件>        # 读文件，智能过滤
rtk grep <词> <路径>   # 压缩版搜索
rtk git log -20       # 压缩版提交历史
rtk diff              # 只看变更行
rtk err <命令>         # 只显示错误和警告
rtk json --keys-only  # 大 JSON 先看键
rtk proxy <原命令>     # 原文直通，核对类场景专用
rtk init -g           # 重新注册或修复 hook

一条使用心法收住：把它当成「给上下文第一道闸配的技能」。闸开多大、什么时候全开（proxy）、什么时候关（瘦会话摘 hook），判断权在你，rtk gain 每周替你出一次考卷。

九、收尾

九天三百三十万 token，我留下了它。这项技能的终点不在压缩率多高，在于你对自己的会话有了一张清晰的画像：什么在吃窗口，什么值得进上下文，什么该挡在外面。

画像有了，装不装 rtk 只是选型细节。先装上跑一周自己的数据，构成表会替你把答案写好。
