月底对账,AI替你核完要多久?0.003秒,10笔差异

订单、账单、流水三方金额笔笔对得平,AI 却说这份对账结果有问题。最后证明 AI 是对的:一处差异值 2000 块,藏在合同条款里,不在任何一张表的数字里。

这是我这周做的一个实测:把财务每月的供应商对账,整个交给 AI 数字员工干,从派活到交付全程留证。程序化 agent 跑完 203 单核对用时 0.003 秒;把同一张工单丢给 Claude Code,它 5.3 分钟交付,中间还自己写了个对账脚本。两边对同一份验收基准,10 笔差异全部命中,零误报。

先把结果放在这,后面每一节都会兑现:

周日早上的消息轰炸

事情从一个虚构但眼熟的场面开始。财务部王姐,周日早上 9:02,消息和四份文件一起砸过来:8 月三家供应商的账单今天必须核完,老板下午 4 点要看差异汇报。

接下来的几个小时,要求持续加码:供应商换了对账系统、账单格式跟以前不一样,要你「迁就一下」;银行流水导过一版旧的,重新导了一份,文件名带着 (1);「7 月的也重新核一遍」「不对,还是全核吧,保险」;然后是催命三连:「进度怎么样了」「?」「小周?」。

这是演示用的虚构记录,但干过对账的人应该都不陌生。这类活有三个特征,凑齐了就是数字员工的第一落点:

重复:月月做,逢月必有,流程不变只有数据变。复杂:三方数据交叉(ERP 订单、供应商账单、银行流水),还要叠加合同条款推理,不是单表去重那种一眼活。可验证:对没对,拿差异清单对着原始数据一查就知道,不存在「说得对不对全凭感觉」。

反过来说,三条缺任何一条的活都不适合现在交给 AI:一次性的活不值得建管线,简单的活 Excel 公式更快,不可验证的活你没法信任它的输出。选场景这件事,比写代码重要。

派活的关键产物是工单,不是提示词

王姐最后受不了了,13:42 把这单活转给了数字员工。派活的东西不是一段咒语式的提示词,是一张工单:

王姐的原话是这么写的:「小助手,月底了,8 月的三家供应商要对了,老规矩。东西都在 data/ 目录里:erp_orders.csv 是咱们 ERP 里导出来的 8 月采购订单,supplier_invoice.csv 是三家供应商开过来的账单,bank_flow.csv 是公司账户 8 月的付款流水,contract_terms.csv 是三家的合同条款,对的时候要照着合同来。」

这张工单是纯大白话,但里面有三个不可缺少的结构。第一是业务口径:本月账期已到,应该全部开票、全部付款完毕,有不一致就是差异;ERP 里「已取消」的单子原则上不该出现在账单里;金额 1 元以内当尾差忽略。第二是数据位置:四份文件各是什么、在哪。第三是交付物定义:一份能直接给老板看的报告,有几笔问题、涉及多少钱、什么原因、怎么处理。

网上流传的「万能提示词」解决不了这三件事。口径决定 AI 怎么判定「差异」,交付物定义决定它输出什么形态,数据位置决定它从哪取数。你给同事派活也是这么派的:告诉他标准、给他文件、说清楚要什么成品。对 AI 派活没有魔法,就是好好写工单。

我把这张工单的模板放在这,照抄改口径就能用:

任务:<什么活,什么期间>
数据:<哪几张表,各自是什么,在哪>
口径 1:<怎样算正常,怎样算差异>
口径 2:<特殊情况的处理原则,如取消单/尾差/账期>
口径 3:<需要结合的规则文件,如合同条款>
交付:<报告形态,给谁看,包含什么>

程序化数字员工:0.003 秒

第一遍,我用一个程序化 agent 跑:读工单、加载四张表、三维核对、自查、出报告,全程固化成一条管线。核对策略是它读完工单后自己定的,分三个维度:

维度一,账单对订单:先做双向存在性(ERP 有单账单缺的是漏开票,账单有单 ERP 查无的是无订单开票),再对在册单据的数量、单价、金额三个字段。维度二,流水对订单:从流水备注里提订单号,查重复付款、应付实付差额、状态与资金流的矛盾。维度三,合同条款:逐份读条款,把「当月累计货款满 10 万减免 2000」这类文字规则换算成计算,重算应付。

验收方法是我埋的答案。数据是模拟生成的,我在生成时故意埋了 10 处差异:已取消订单仍开票、单价多收 0.5 元、总额少算 188 元、两笔漏开票、一笔无订单开票、一笔重复付款、一笔线下付款没回写 ERP、一笔只付一半、还有合同返利漏扣。埋点清单单独存档,agent 跑完对着清单验收,10 笔全中,没有一笔误报。

交付前它多做了个动作:把三方总额重新加总核对。订单总额扣除已知差异的影响后,与账单、流水各自的总颟能完全对得上,这证明差异清单是完整的,不存在一笔没被发现的漏网差异。总额勾稽是老会计的验账手法,数字员工把它变成了交付前的固定动作,清单敢承重,靠的是两头都对得上。

第一版不是这样的。最初那版对返利漏扣的判定,依赖「账单总额恰好等于订单总额」这个前提,结果被同一供应商内部的另一笔金额差异干扰,直接漏报了那 2000 元。修复后的判定改成两步:先看累计货款是否过门槛,再逐行核对账单侧有没有折让、返利、负向调整记录。这个翻车恰好验证了验收方法的价值:没有埋点清单,这次漏报根本不会被发现,报告照样交,数字照样好看。数字员工和人一样,要过试用期,考核方式就是拿已知答案考它。

总耗时 0.003 秒。人工做同样的活,三方各 200 行加合同条款,半天是常态。要说明的是,这个数字的意义不在快,而在稳定:第二个月换一批数据,它还是这个速度、这个准确率,不会因为周五下午想下班而漏看一行。

把同一张工单丢给 Claude Code

程序化 agent 再快,总有人会说:那是程序员写死的脚本,不是 AI 干活。所以第二遍,我把同一张工单原样丢给了 Claude Code,不给代码、不给规则,只给它 TASK.md 和四张表。

它的完整行为记录在会话日志里,值得逐段看。第一步,通读 TASK.md 和四张表,然后它自己说:口径清楚了,肉眼已经扫出几处嫌疑,但 600 多行手工核对不可靠,于是决定写脚本。第二步,写了一个 200 多行的对账脚本,一次跑通。第三步,抽样复核脚本的输出和原始 CSV 能对上,确认差异清单没有遗漏。第四步,把报告写出来交付。全程 5.3 分钟。

结果同样是 10 笔全中。它跑完脚本后的自检原话是:ERP 自身 203 笔金额全部自洽,筛出 13 条原始告警,人工复核合并为 10 笔业务差异,三方总额能完全勾稽。注意 13 合并成 10 这个动作:同一笔差异会在多个维度各报一次,比如无订单开票的单据同时在存在性和金额两个维度告警,它做了去重合并,把 13 条收敛成财务要的「一笔一事项」。这个动作没有任何人教它,是它自己判断出了财务要什么。

更值得说的是它的两个额外动作。

它先验证了「ERP 自身 203 笔金额全部自洽」,数量乘单价等于金额,排除了源头数据本身的错,再谈三方差异。它还发现了两件工单口径之外的事:15 笔订单超出合同账期、21 笔付款日期晚于对账日。这两类在我的口径设定里都不算差异,但它主动报出来给了人去判断。

展开说值得。15 笔超账期:按口径这是付款纪律问题,不是数据错误,但供应商催款和资金计划都挂在上面,拖到下月就会变成对账差异。21 笔付款晚于对账日:严格说钱是付了,只是时间戳越界,大概率是银行入账时点问题,但若有人挪用资金滚动付款,先看到的正是这类信号。人工对账根本不会去看这两类,因为没有一条差异规则覆盖它们。

agent 的价值在这里多出一层:它不只回答你问的问题,还顺手把你没问但可疑的摆出来。要不要处理是你的决定,但至少你看见了。

这就是「数字员工」和「自动化脚本」的区别所在。脚本只会执行你想到的规则,agent 会先判断这活该怎么干、干完自己复核、顺手报告你没问到但可疑的事。而整个过程不需要一个程序员在场:一个懂业务的财务,在终端里把工单文件给它,就完成了接入。

两笔高光差异:钱在哪儿漏的

10 笔差异里,有两笔值得单独讲,因为它们解释了为什么这类活人工做不可靠。

第一笔,单价多收。订单 PO-2608-0008,ERP 单价 81.86 元,供应商账单开的是 82.36 元,每件多 0.5 元,35 件合计多收 17.50 元。单价差藏在两个 200 行的表里,金额列粗看毫无异常,人眼逐格扫描的漏检率接近百分之百。0.5 元不多,但同一供应商每月这么开一次,一年就是两百多块。你不知道的还有多少家供应商在这么开。

第二笔,合同返利漏扣,就是开头那处藏在「金额全平」后面的差异。华南五金当月累计货款 249,211.54 元,合同写明「当月累计货款满 10 万元,当月账单总额直接减免 2000 元」。订单、账单、流水三方每一笔都对得上,任何金额比对都是平的。差异只存在于一个地方:合同条款该兑现而没兑现。agent 的做法是把条款文字换算成计算:累计过门槛,账单侧逐行核过,没有任何折让、返利、负向调整记录,所以这 2000 元是实打实没扣的。

第三笔顺带一提,重复付款。订单 PO-2608-0102 在银行流水里出现两笔一模一样的付款,合计多付 1517.40 元。这笔的隐蔽之处在汇总口径:如果财务按日汇总付款,两笔同额付款会互相抵消成「这笔金额翻倍了」,只有逐笔记账才能发现是付重了。银企直连的重试、审批系统的重复提交,都是它的常见成因,钱已经出去了,发现越晚追回越难。

把前两笔放一起看,能得出一个对选工具很有用的判断:纯数字比对,Excel 和 python 脚本都能做,又快又稳;但「带着合同条款重算应付」这件事,需要把自然语言规则接进核对流程,这正是 agent 的价值位。你可以基于这个判断给自己的团队分工:数字比对交给脚本,规则推理交给 agent,人守最后的签字确认。

为什么 Excel 干不了这个活

懂 Excel 的人会问:这活 VLOOKUP 加数据透视表不也能干?数字层的比对确实能。前五类差异(存在性、单价、金额、漏开票、无订单)用两套 VLOOKUP 加条件格式也能抓个大概,很多财务也是这么干的。

但往下走三层就断了。第一层,跨表状态矛盾:ERP 的「待付款」和银行流水的存在性分别在两张表里,透视表没有「状态乘存在性」这种交叉维度,已付未登记这类差异它看不见。第二层,自由文本解析:银行流水的备注是「货款 PO-2608-0103」这种文本,得先提取订单号再聚合付款,Excel 的匹配键是单元格,不是正则。第三层,条款推理:「满 10 万减 2000」这条规则活在合同的一段中文里,整张工作簿没有能承载它的位置。

所以传统方案的边界很清楚:数字对数字可以,规则、状态、自由文本不行。而数字员工的核对策略,恰好是从读合同、读备注、读状态字段开始的。这不是工具好坏问题,是范式差异:电子表格把数据当格子,agent 把数据当业务。

对账 checklist:差异的十种形态

这次实测攒下来一份对账差异形态清单,拿去对着你自己的月末核对用,每一条都对应本次实测里的一笔真实命中:

  1. 已取消订单仍开票:取消信息没同步给供应商,属于不应支付的款项
  2. 单价不符:账单单价与订单约定不一致,多收方向直接是损失
  3. 金额不符:数量单价一致但总额对不上,两边平不了
  4. 漏开票:ERP 有单、账单缺失,应付台账低估
  5. 无订单开票:账单引用的订单号在 ERP 查无,疑似错录或凭空开票
  6. 重复付款:同一订单两笔相同付款,按日汇总会互相抵消成「金额翻倍」
  7. 已付款未登记:线下付款没回写系统,应付余额虚增
  8. 部分付款:实付不足应付,状态却标了「已付款」
  9. 合同返利漏扣:金额全平,差异只在条款里,纯数字核对永远查不出
  10. 账期外观察:超账期未付、付款晚于对账日,不一定是错,但值得人看一眼

前八条是数字层的,第九条是规则层的,第十条是 agent 主动报出来的。人肉对账通常只覆盖前五条,因为六到九条要么跨表要么跨文档,核对成本太高。

这份清单还有个用法:给你的核对工具做能力定位。前五条,Excel 和脚本都行;第六到八条要跨表关联加自由文本解析,得上脚本;第九条要读合同,只有 agent 干得了。你可以拿它当采购清单用,团队里每种工具该买什么单,一对照就知道。

把数字员工接入你的月度活

如果你想在自己的团队跑一遍同样的流程,四步就够。

第一步,选场景,用前面说的三条标准筛:重复、复杂、可验证。对账、报表合并、工单分类、简历初筛,都在射程内。

第二步,写工单,用上面的模板,把口径写全——口径写不全,AI 的判定就没有依据,这是整个流程里最值得花时间的一步。第三步,选执行者。有开发资源的团队可以固化成程序化管线,享受毫秒级和零漂移;没有开发资源的,直接把工单丢给 Claude Code 这类通用 agent,首次接入成本约等于零。两条路线这次实测都跑通了,差异只在速度和额外发现的多寡。

第四步,定验收。埋一批已知答案的差异,让 agent 对着跑,命中率就是它的上岗证。这一步别省,数字员工和人一样,先试用期再转正。

成本这块顺带说一句,通用 agent 跑完这一单的 token 开销按订阅额度计,折算成本低于一杯咖啡。

程序化管线的运行成本约等于零。给数字员工算人力成本的思路,我在数字员工的 token 成本账里算过整月口径,结论是这类重复活每接管一项,边际成本递减。

AI 出证据,人守红线

最后把边界说清楚,这部分和前面的效率数字同样重要。

报告里每一笔差异的建议动作,注意看动词:联系供应商、退回多付款、补记状态、要求换开账单,全部是人的动作。数字员工的产出是证据和清单,不是决定。付款确认必须人签字,因为它对应资金流出;供应商沟通必须人去做,因为那是对外关系;异常的最终定性必须人拍板,因为 AI 报的「口径外观察」可能只是业务惯例。好在判断的依据它已经替你备齐:单号、金额、时间、条款出处样样在列,人要做的只是决定怎么处置。比传统模式下既要找证据又要做判断,省掉的正是最耗时间的那一半。这个分工我在怎么用 AI 把一整单业务从头拧到尾里拆解过,核心分工:AI 负责把人从重复核对里捞出来,人负责在证据齐全的基础上做判断。

企业接入还有一条硬约束要提前想清楚:数据去哪。程序化 agent 零依赖、本地跑,四张表不出内网,财务数据敏感的公司可以放心接。通用 agent 是云端模型,订单和流水要发出去,涉密行业和上市公司财报期前,这条通道要先过法务。

折中路线也有:数据留在本地脚本里算,只把差异清单和合同条款发给模型做归因,原始明细一个字段都不出域。这次实测的 LLM 归因模块就是这么设计的,没有配 key 时自动降级为内置归因,核对结果不受影响。

接入方案没有标准答案,数据分级是第一步。

还有一条诚实声明。本文的数据是模拟生成的:虚构的公司、虚构的供应商、用固定随机种子造出来的 203 单流水,埋了已知的差异当考题。但系统形态、工单写法、agent 的执行过程、核对逻辑、报告交付,全部是真实运行的产物,Claude Code 的会话日志原文都在,没有一段是事后编的。用模拟数据测真管线,这是给 AI 做验收最省事的方法:你手上永远有标准答案。

顺带说复用成本。第二个月再跑,程序化 agent 只需要换四张表文件,工单一字不改,管线原样执行;Claude Code 这边同样,把新数据放进目录,把同一张工单再发一次。第一次接入花的是设计工单和验收的心思,之后每个月的成本趋近于零。这也是「重复」这条筛选标准的价值:重复的活,接入成本摊到每个月都在降价。

这轮实测跑完,我对「数字员工」这个词的判断收敛成一句:它不是替你上班的人,是把「核对类工作」从人的月历上划掉的那支笔。划掉之后,王姐们剩下的时间是去处理那些真正需要判断的事,比如为什么同一个供应商,连续两个月都在单价上多收 0.5 元。这个问题的答案,AI 给不了,但发现这个问题,从这周起是它的事了。

这是「数字员工上岗实录」的第一篇。下一篇,我打算让它接一个更刁钻的活:多方数据源口径不一致的月报合并,那才是真正考「工单怎么写」的场景。
