做过 SaaS 多租户 Web 的人，第一反应都是「一个商户号收钱就行，后台记一下是哪个租户的，月底对账分钱」。在浏览器里这套没问题，但在微信小程序上直接死——商户号绑定 AppId，一个小程序只能挂一个商户号。你一个平台商户号，对应的是自己小程序的 AppId，收不了租户小程序的款。

这篇就讲这个硬约束逼出来的两种解法：直连商户（每个租户独立签约微信支付，用户付的钱直接到租户的商户号）和服务商模式（平台注册为微信支付服务商，统一收银 + sub_mch_id 标记每笔资金的归属）。

先把结论丢出来：

  • 服务商模式：平台统一收银，sub_mch_id 区分资金归属，一份接入走遍所有租户。租户越多收益越大，这是首选。
  • 直连商户：每个租户自己签商户号，资金不经平台手，合规最干净。租户少、合规严的场景下反而更省心。

和上篇（代开 vs 按租户打包）不同，直连商户在特定场景下优于服务商模式。支付架构的选择不是"哪个更先进"，而是"哪个更适合你的租户画像"。下文会展开为什么。

难点：微信支付的商户号绑定 AppId 约束

做 SaaS 多租户 Web 的同学，第一反应是：「一个商户号走天下，后台记 tenant_id 不就行了？」在 PC/H5 支付里，这套确实跑得通——一个商户号可以登记多个公众号/H5/App 的支付能力，同一个商户号收所有渠道的钱。但在小程序侧，这个绑定关系是反过来的：

一个小程序的 AppId，只能绑一个微信支付商户号。

微信支付的商户号产品登记逻辑是这样的：一个商户号可以在开放平台登记多个 AppId（公众号、小程序、H5、App 各一个），但反过来看——一个小程序只能登记一个商户号作为自己的支付能力。这意味着：

  • 你开发了一个 SaaS 平台，自己也注册了商户号（平台商户号）
  • 这个平台商户号只能绑到你自己的小程序上
  • 你绑不了租户的小程序——因为租户的小程序是一个独立的微信实体，它要绑的商户号必须是这个租户自己签约的商户号（直连模式），或者通过服务商模式用你的平台商户号代收

换句话说，“一个商户号收所有租户的钱"在小程序上直接走不通——你收不了租户小程序的钱。这个约束和上篇的 AppId 构建期烧死是同一个性质：微信平台的底层绑定关系，绕不开。

我们走过的弯路：一个商户号想解决所有问题

我们最初的设计也和大部分人一样：「一个平台商户号收钱，反正后端的订单表里有 tenant_id，月底对账按租户分钱。」甚至画了一个很漂亮的资金流图——用户付到平台，平台按比例分给各租户，觉得完美。

两周后才发现哪里都走不通。

第一道墙是微信结算的粒度。微信支付 T+1 打款，不是按订单维度打的，是按商户号维度汇总的。用户付了你 100 块，微信 T+1 把 100 块打到你商户号绑定的银行账户——你不可能让微信把其中的 30 块直接打到租户A的账户，20 块打到租户B的账户。微信不提供"按订单分账到不同银行账户"这个能力。分账 API 只能把资金分到sub_mch_id（子商户号）或 openid（个人零钱），不能分到任意银行账户。

第二道墙是退款路由。用户在租户A的小程序买了东西要退款，钱应该从租户A的商户号余额退。但如果所有钱都进了你的平台商户号，退款时你就要判断"这笔钱是哪个租户的”——听起来简单，但线上情况复杂得多：租户A余额不足了怎么办？平台先垫？垫了租户A不认账怎么办？

第三道墙是合规。平台一次性经手所有租户的资金流，在央行支付体系里这叫「二清」（二次清分）风险。微信支付的服务商资质本身就要求平台不能碰资金，所有资金必须通过微信结算体系直接到租户账户。

走通这些墙之后，我们发现只有两条路可以选。没有第三条。

模式一：直连商户（每个租户独立签约）

每个租户自己向微信支付申请一个商户号（像任何一个独立商家一样走签约流程），平台只负责在技术层面帮租户完成入驻和配置。用户在租户A的小程序付钱，钱直接到租户A的商户号，微信 T+1 结算到租户A的银行账户。平台不碰资金，只传递订单信息。

入驻流程自动化

微信支付开放了商户入驻 API（/applyment/），平台可以替租户提交入驻资料：

// 入驻流程编排 - 关键步骤
// 1. 收集租户资料（营业执照、法人信息、对公账户）
ApplymentInfo info = new ApplymentInfo()
    .businessLicense(tenant.getLicenseUrl())       // 营业执照图片
    .idCard(tenant.getLegalPersonIdCard())           // 法人身份证
    .bankAccount(tenant.getSettlementBankAccount())  // 结算银行账户
    .merchantShortName(tenant.getBrandName())         // 商户简称-展示在用户支付页
    .contactInfo(tenant.getContactInfo());            // 运营联系方式

// 2. 调微信入驻 API
ApplymentResult result = wechatPayApi.submitApplyment(info);
// 返回申请单号，微信异步审核

// 3. 轮询审核状态（审核周期通常 1-5 个工作日）
while (notFinal(result.getApplymentId())) {
    Thread.sleep(30_000); // 30 秒轮询一次
    result = wechatPayApi.queryApplyment(result.getApplymentId());
}
// 审核通过后拿到商户号
String subMchId = result.getSubMchId();

踩坑：入驻审核失败时微信只返回模糊原因（“资料不符”、“信息不匹配”），不告诉你具体哪个字段不对。我们做了详细的状态机，把常见失败原因归类成可操作提示：营业执照照片不清晰、法人姓名和身份证号不匹配、对公账户开户行名称填错。运营看到分类提示就能直接告诉租户改哪里，不用猜。

直连模式的适配层还有一个容易忽略的点：每个商户号有自己的 API 证书（.p12/.pem）和 API v3 密钥。N 个租户就有 N 套凭证，存储和管理不能靠"放配置文件就行"。我们沿用了上篇的三层读取视图思路：C 端匿名只返回布尔能力位、运营端脱敏、内部服务明文用于调微信 API。每个租户的凭证在数据库里 AES 加密，使用才解密，用完立即释放。

直连模式的回调路由

每个商户号的回调 URL 只能配一个（在微信支付商户平台配置），N 个租户 N 个商户号，理论上回调 URL 跟着不同商户号走——但你不可能部署 N 套回调服务。

做法是在回调 URL 里编码租户标识：

https://api.xxx.com/payment/notify/{tenantId}

微信支付回调时带上这个 URL，后端从 URL 路径里拿到 tenantId，选择对应租户的证书和密钥来验签和处理。

注意：URL 路径里的 tenantId 只用于"选证书"，不用于"判断这笔订单是谁的"。订单归属的判断必须从订单号反解——后文会详细展开为什么。

直连模式的隐藏约束：基本账户与运营账户资金隔离——平台垫资的根源

直连模式还有一个比证书管理和入驻更隐蔽的约束：微信支付的账户体系实行"收支两条线"——基本账户和运营账户资金完全隔离，不可互转。

这是微信支付在 2022 年底升级的合规规则，目的是符合央行《银行卡收单业务管理办法》。简单说：

  • 基本账户（就是通常说的"可提现余额"）：只进不出（收款）和提现到对公银行卡。不能用于发放佣金、红包、营销补贴。
  • 运营账户（营销专用）：只出不进（发红包、佣金、商家转账到零钱），但不能接收交易资金，只能通过对公银行卡手动充值。

基本账户和运营账户之间没有直接划转通道。想把基本账户的营收款用于运营支出，唯一路径是：基本账户→提现至对公银行卡→从银行卡手动充值到运营账户。

这在有分账体系的业务里是个致命约束。以达人佣金为例：

  1. 用户在租户A的小店下单 100 元，钱进了租户A的基本账户
  2. 达人带货赚了 40 元佣金，需要从运营账户出款（发到达人微信零钱）
  3. 但租户A基本账户的 100 元不能直接转入运营账户，也不能直接发给达人
  4. 租户A需要先把钱提现到自己的对公银行卡，再充值回运营账户

到这里问题来了：在直连模式下，平台不能强制租户完成"提现→充值"这个操作。租户可能资金周转不开、提现还没到账、或者干脆不配合。但达人已经干了活要结算——最后只能平台用自己的钱先垫付给达人，再从租户的后续结算中扣回。

这就是直连模式下平台垫资的根源。不是平台想垫资，是微信支付的账户隔离规则逼着你垫。

更隐蔽的还有直连模式的分账比例上限。微信支付直连商户的分账默认上限是 30%（可在商户平台申请调整，但调整审核严格）。如果达人佣金 + 平台抽佣超过订单金额的 30%，连分账 API 都用不了——平台只能完全走"垫资→回收"这条线下结算的路，连自动化的资金通路都没有。

// 直连模式分账请求 - 注意分账金额上限
Map<String, Object> params = Map.of(
    "transaction_id", wechatPayTransactionId,
    "out_order_no", splitOrderNo,
    "receivers", List.of(
        Map.of(
            "type", "PERSONAL_OPENID",      // 达人接收 - 分到个人零钱
            "account", talent.getOpenId(),
            "amount", commissionAmount,     // 注意: 不能超过订单金额 × 分账比例上限
            "description", "达人佣金"
        )
    ),
    "unfreeze_unsplit", true  // 分账完成后剩余资金解冻给租户
);
// 如果 commissionAmount > orderAmount × 30%, 这请求会直接报错

这个问题的解决方案有两个：

  • 换服务商模式：服务商模式下平台是分账发起方，通过 sub_mch_id 路由资金，不受直连商户的账户隔离限制。达人佣金直接从平台的分账链路走，资金从子商户的冻结池到达人零钱，不经过子商户的基本账户和运营账户流转——这是服务商模式比分账场景更合适的核心原因。
  • 如果坚持直连模式：平台和租户之间需要签署代付协议，平台先垫资给达人，再从租户的货款结算中扣除垫资部分。这要求平台有完善的"垫资→回收"账务系统，包括垫资额度管理、账期控制、坏账准备。这套系统本身就是一个不小的开发投入。

直连模式的适用场景

直连模式不是"落后"的模式，它在这些场景下反而是对的：

  • 租户少（< 20）且每家都是实体企业：各自签约各自结算，平台最省心
  • 租户要求自己能查微信支付账单：直连模式下租户有自己的商户号后台，能看到每一笔交易
  • 合规审计严格（金融、教育、医疗）：平台不经手资金流，审计直接看微信的结算流水就行
  • 租户需要自己处理退款和售后：租户在自己的商户号后台就能操作，不用经过平台
  • 没有达人/分销等分账场景：纯收银场景下，直连模式的账户隔离问题不触发

我们最开始 10 个租户都是直连模式，简单可控，平台不碰资金。直到租户数超过 30，入驻管理成本高了，才开始上服务商模式。但真正促使我们全面切换到服务商模式的，不是入驻成本，而是分账场景下的垫资问题——达人佣金规模上来之后，平台垫资额从几万涨到几十万，财务受不了。

模式二：服务商模式（platform + sub_mch_id 统一收银）

平台先申请微信支付服务商资质，然后让租户授权平台代管他的支付。租户不需要自己签约——平台在服务商体系下为租户创建一个子商户（sub_mch_id），所有租户共用平台的商户号收钱，但每笔交易通过 sub_mch_id 标记资金归属。

子商户也有入驻流程，但比直连模式简单：不需要租户自己去微信支付签约，平台代提交资料，微信审核通过后生成一个 sub_mch_id 即可。

统一下单：核心在 sub_mch_id

// 服务商模式下单 - 关键参数
Map<String, Object> params = Map.of(
    "sp_appid", platform.getAppId(),          // 服务商（平台）的 AppId
    "sp_mchid", platform.getMchId(),          // 服务商商户号
    "sub_appid", tenant.getAppId(),           // 租户小程序的 AppId
    "sub_mchid", tenant.getSubMchId(),        // 子商户号 - 资金归属关键
    "description", tenant.getBrandName() + "-订单",
    "out_trade_no", buildOrderNo(tenant),     // 订单号必须编码租户标识
    "notify_url", "https://api.xxx.com/payment/callback",
    "amount", Map.of(
        "total", order.getAmount(),
        "currency", "CNY"
    )
);

sub_mch_id 是服务商模式的灵魂。它在统一下单时传入，微信支付收到后：

  1. 验证这个 sub_mch_id 确实是你（服务商）名下的子商户
  2. 用户付钱后，这笔资金在微信内部就标记为"归属子商户A"
  3. T+1 结算时，微信把归属子商户A的钱打到子商户A的银行账户——不是打到你的银行账户

资金流的结论：即使服务商模式下，平台还是碰不到钱——微信把资金直接结算到子商户的银行账户。服务商做的只是"订单级别的资金标记"，不是"收款后再分钱"。

很多人对服务商模式的恐惧都来自"钱先进平台账户，平台再分给租户"这个误解——这不叫服务商模式，这叫二清。正规的服务商模式，资金根本不会在平台账户停留。

回调处理：订单号是唯一可信的租户标识

服务商模式下，所有租户共用一个回调 URL（因为都是调你的平台商户号）。那回调到了之后，怎么知道这单是哪个租户的？

方案：在订单号里编码租户标识。我们用的格式是 ord_{tenantId}_{yyMMdd}_{8位seq}。

回调处理的完整逻辑：

@PostMapping("/payment/callback")
public ResponseEntity<String> handleCallback(@RequestBody String xmlBody) {
    // 1. 解析微信回调 XML，拿到 out_trade_no
    String outTradeNo = parseOutTradeNo(xmlBody);
    
    // 2. 从订单号反解租户 - 只信任订单号本身
    String tenantId = resolveTenantFromOrderNo(outTradeNo);
    // 格式: ord_<tenantId>_<yyMMdd>_<8位seq>
    // 例: ord_t001_260715_00001314
    
    // 3. 加载该租户的商户凭证
    TenantWechatConfig config = tenantConfigService.getWechatConfig(tenantId);
    if (config == null) {
        // 找不到租户 = 非法回调或订单号错误
        return failureXml("INVALID_TENANT");
    }
    
    // 4. 用平台的 API v3 密钥 + 该租户的 sub_mch_id 验签
    boolean verified = verifySignWithTenantKey(xmlBody, config);
    if (!verified) {
        return failureXml("SIGN_VERIFY_FAILED");
    }
    
    // 5. 更新订单状态（幂等处理）
    orderService.markPaid(outTradeNo, parseAmount(xmlBody));
    
    return successXml();
}

一次真实的坑：回调只信订单号，不信任何外部参数

这个坑我印象极深。

有一版重构时，我觉得"每次都从订单号反解租户太麻烦"，想偷懒。改成了在统一下单时把 tenantId 放在 attach 字段（微信允许传的附加数据），回调里直接读 attach 拿租户。听起来更优雅对不对？少了一步反解逻辑，直接读微信传来的字段就是租户。

上线后第三天出事了。凌晨对账发现一笔 2000 块的订单入库到了错误租户。排查了一小时，根因是：

  1. 下单时某个请求的 attach 字段传错了，带了 A 租户的 ID，但订单实际属于 B 租户
  2. 回调时系统读到 attach 里的 A 租户 ID，更新了 A 租户的订单状态
  3. 对账时发现 B 租户少了一笔 2000 块的入账，A 租户多了一笔

attach 字段是下单时后端自己传的，出错只能在代码层面——某个请求的租户上下文没传对，导致 attach 和实际订单归属不一致。这种 bug 在测试环境根本测不出，因为测试环境永远只有一个租户在跑。

修不修复？我们改了两种做法：

  1. 强制从订单号反解租户：out_trade_no 的租户前缀是下单时由专门的方法生成的，和 tenantId 同源，不存在上下文传递错的问题
  2. 回调里拿订单号反解的租户，和 attach 字段/sub_mch_id 做交叉校验：两者不一致立刻告警 + 拒绝处理，人工排查

核心教训很直接：回调处理里，只相信订单号自带的租户标识。不信任任何 URL 参数、Header、attach 字段、甚至 sub_mch_id 本身——这些都可能因为代码 bug 或上下文污染而传错。订单号的租户前缀是在创建订单的那一刻由统一方法注入的，它和订单本身绑定，不会被上下文污染。

模式二的退款：一个更隐蔽的坑

退款是服务商模式下最容易出资金事故的环节，而且出错后很难追回。

微信服务商模式的退款 API 要求传入 sub_mch_id——指定从哪个子商户的账户退款。如果代码里取的是当前处理上下文的租户，而不是订单原归属租户，退款就会从错误的商户出钱。

最常见的 bugs 场景：

  • 运营在管理后台发起退款，后台的"当前租户"是运营最后查看的那个租户，不是订单所属的租户
  • 退款接口从 HTTP 请求的 Header 里取 X-Tenant-Id，但这个 Header 可能被上游转发错了
  • 定时任务退款时，任务上下文没有重置租户，用了上一个批次处理的租户

我们的修复方案和回调路由一致：退款时只从订单号反查原始租户，不接受任何上下文参数。

public RefundResult refund(String outTradeNo, int amount) {
    // 只相信订单号 - 反查租户
    Order order = orderService.getByOutTradeNo(outTradeNo);
    if (order == null) {
        throw new BusinessException("订单不存在: " + outTradeNo);
    }
    
    TenantWechatConfig config = tenantConfigService.getWechatConfig(order.getTenantId());
    
    // 退款请求
    Map<String, Object> params = Map.of(
        "sub_mchid", config.getSubMchId(),                      // 用订单的原始租户
        "out_trade_no", outTradeNo,
        "out_refund_no", buildRefundNo(order.getTenantId()),
        "amount", Map.of("refund", amount, "total", order.getAmount(), "currency", "CNY")
    );
    
    return wechatPayApi.refund(params, config.getApiV3Key());
}

这个 order.getTenantId() 就是上面回调处理更新订单时，从 out_trade_no 反解出来的那个租户 ID。整条链路闭环：下单时编码 → 回调时反解 → 退款时反查。任何一个环节都不依赖"当前上下文"。

核心决策表

你的情况推荐模式理由
租户 < 20 且每家都是实体企业直连商户各自结算，平台不碰资金，合规最省心
租户 > 30 且持续增长服务商模式入驻成本 O(1)，不用帮每家手动签商户号
租户需要自己查微信支付后台直连商户服务商模式下租户没有独立商户号后台
合规审计极严（金融/教育/医疗）直连商户平台不经手资金流，微信直接结算到租户
租户频繁入驻/变动服务商模式子商户入驻比直连商户签约快得多
已经有独立小程序的租户两者都行代开模式下每个租户有独立 AppId，直连商户天然匹配
小商户为主，不会自己管支付服务商模式租户不需要接触微信支付后台，平台全包
退款/售后需要平台统一处理服务商模式平台可以在回调层统一处理退款路由
已有平台没有服务商资质直连商户服务商资质审核 2-4 周，前置投入必须先确认

一个常见的误判：很多人一上来就选服务商模式，觉得"一套接口走天下"听起来很酷。但服务商模式的管理成本不低——你需要维护 N 个 sub_mch_id 和对应的 API 证书、做三层对账、处理退款路由、应对子商户的审核问题。租户少于 20 的话，这些管理成本可能超过直连商户的入驻成本。

证书轮转：双槽切换

支付系统里证书管理是容易出事但通常没人提前准备的事。

每个租户的 API v3 密钥和商户证书都有有效期。微信支付会在到期前发通知提醒，但线上环境里"忘了换证书"的结果就是支付链路直接断开，用户付不了钱，退款走不通——而且你大概率是在凌晨对账失败告警响了才发现。

我们的做法是"双槽切换"：每个租户维护两个证书槽位——当前在用和备用。

轮转流程:
  ① 生成新证书（或从微信下载最新证书）
  ② 存入备用槽位（不覆盖当前槽）
  ③ 用备用证书调一次微信查询接口（验证新旧证书同属一个商户号）
  ④ 验证通过后，把当前槽位指针切换到备用槽
  ⑤ 旧证书保留 72 小时后清除（给回滚留窗口）

关键在第三步——验证。不是"存进去了就行"，是"存进去后真的能调通微信接口"。

public void rotateCertificate(String tenantId) {
    TenantCert current = certRepo.getCurrent(tenantId);
    TenantCert standby = certRepo.getStandby(tenantId);
    
    // 1. 验证备用证书可用
    boolean verified = wechatPayApi.verifyCertificate(tenantId, standby);
    if (!verified) {
        // 备用证书有问题，告警 + 中止轮转
        alertService.send("证书轮转失败: 备用证书验证未通过, tenant=" + tenantId);
        return;
    }
    
    // 2. 切换指针（原子操作）
    certRepo.switchToStandby(tenantId);
    
    // 3. 设定时任务 72h 后清除旧证书
    certCleanupScheduler.schedule(tenantId, current.getKeyId(), 72, TimeUnit.HOURS);
}

这个设计和上篇的凭证三层读取视图是一个思路：证书切换的关键不是技术实现的复杂度，是"切过去之后发现有问题回不来"的风险。双槽切换保证任何时候至少有一个可用证书在线上服务，不会出现"切换中途全挂了"的状态。

三层对账

支付系统上线第一天就要对账，不是可有可无的运维任务。

服务商模式下对账相对复杂：微信不仅提供平台商户号的账单，还提供每个子商户的账单。加起来可能几十个 CSV 文件，需要做三层比对：

第一层：微信商户账单 vs 平台订单表

  • 微信有哪些交易，平台没有记录？→ 可能是回调丢失，需补单
  • 平台有哪些订单，微信账单里没有？→ 可能是订单未支付，需核查
  • 金额不一致？→ 最严重，需要立刻告警

第二层：平台订单表 vs 分账记录

  • 已支付的订单，分账记录完整吗？
  • 分账金额和订单金额的比例对不对？

第三层：汇总校验

  • 平台商户号的结算总额 + 各子商户的结算总额 = 各租户的应收总额
  • 这个等式如果不成立，说明有资金错配

踩坑：一开始我们用"单日对账"——今天的账单对今天的订单。但微信结算有时会延迟 2-4 个小时，凌晨跑对账脚本时今天的账单还没出完，每天都告警。后来改成 24 小时滚动窗口：对账范围是"过去 24 小时的交易"，不是"今天 0-24 点的交易"，才算消停。

对账的实现可以很简单：每天凌晨下载微信账单 CSV，逐行比对数据库里的订单和分账记录，差异写入 reconciliation_diff 表，按类型决定自动修复还是人工介入。一开始不需要复杂的对账引擎，一个脚本跑 CSV 比对就够用。

几条判断

最后把这套架构的判断点收敛一下：

  • 微信支付的商户号绑定 AppId 是所有多租户支付架构的前提，绕不开。所有方案都是在解决"如何在 AppId 和商户号的绑定约束下，让每个租户有自己的收款能力"。
  • 服务商模式不是"二清"，资金不经过平台账户停留，而是通过 sub_mch_id 在微信侧直接结算到子商户。这是正规的服务商模式。如果有人说"钱先到我平台账户我再分给租户"，那是违规的二清，不是服务商模式。
  • 回调处理只信任订单号字面的租户标识，不信任任何外部参数。out_trade_no 的租户前缀是在订单创建时由统一方法注入的，和订单本身绑定，不会被上下文污染。这是一个用事故换来的教训。
  • 退款的资金路由必须从订单号反查，不从上下文取。下单、回调、退款，这条链路里的租户标识必须是同源的。
  • 证书轮转走双槽切换不是技术选型，是风险控制——支付链路断了就是资损，双槽保证任何时候有退路。
  • 三层对账不是可选项，是第一天上线的必需品。支付系统不出事则以，出事就是资金损失。对账是发现资金错配的最后一道防线。
  • 直连商户的基本账户和运营账户资金隔离，是分账场景下的隐藏成本。有达人佣金、分销分润的业务，直连模式下平台几乎必然要垫资，因为租户基本账户的钱不能直接用于佣金发放。这项隐形成本在决策时容易被忽视，等到达人规模上来才暴露。如果你有分账场景，服务商模式在账户体系上天生适配——资金在冻结层通过分账 API 直达各参与方，不经过基本账户和运营账户的流转。
  • 直连和服务商不是非此即彼的选择。大租户走直连（各自结算各自对账）、中小租户走服务商（平台统一管理），混用模式是最常见的线上状态。运营后台给每个租户标注支付模式，所有按订单号的操作（回调/退款/对账）自动路由到对应逻辑。但要注意：混用模式下，有分账场景的租户优先走服务商，纯收银场景的租户可以走直连。

决策清单：你应该选哪种模式

如果你也在做 SaaS 多租户的支付设计，这里给一份可拷贝的决策表，不需要看完上面所有论述，对号入座就行：

你的情况推荐模式一句话理由
租户 < 20，每家都自己有财务直连商户让腾讯帮你做结算，最省心
租户 > 30，小商户为主服务商模式入驻成本抵不过管理成本时就该切
有达人/分销等分账场景服务商模式直连模式下基本账户和运营账户资金隔离，平台会被迫垫资
纯收银场景（无分账）两者都行账户隔离问题不触发，选熟悉的模式即可
合规要求平台不碰资金直连商户资金直接到租户，审计只看微信流水
租户自己管不好支付服务商模式统一管理，减少租户的运维压力
已经用代开部署小程序服务商模式更方便平台统一 AppId + 统一商户号，天然匹配
已经按租户打包部署直连商户更方便每个租户有独立 AppId，直连商户天然匹配

从直连迁移到服务商的路线：先用直连把业务跑通，等租户数涨到管理成本心痛了，再申请服务商资质。迁移时存量大租户不动、新租户走服务商，双轨运行。回调层事先做成"根据订单号前缀路由到不同处理逻辑"的架构，迁移时就改配置不改代码。

这里要特别说明一下双轨运行阶段的管理方式。两种模式下订单号前缀的编码规则不一样：直连模式的订单号用 dir_{tenantId} 开头，服务商模式的用 srv_{tenantId} 开头。后端回调接口在解析订单号时，前缀决定了用哪种方式选证书、哪个商户号处理退款、哪套对账逻辑。这种"前缀路由"的设计模式意味着后端代码里没有 if (直连) 和 if (服务商) 的散装判断，统一收敛在订单号解析层。后续再加第三种支付模式，只需要新增一个前缀解码器，不需要改回调/退款/对账的中间逻辑。

关于微信审核：服务商资质是隐藏的前置条件

直连模式和服务商模式都需要前置准备，直连是"每个租户自己签"，服务商是"平台先有资质再帮租户创建子商户"。服务商资质申请常被低估，这里单独说几点实际踩过的坑：

  • 审核周期 2-4 周，如果遇到资料退回重填，可能拖到 6 周。这个周期要算进项目排期里，不要等到上线前两周才申请。
  • 经营范围和服务商类型要匹配：电商类 SaaS 选"电商工具服务商"，不能选"线下零售服务商"，选错了会被驳回重审。
  • 平台主体和商户号的法人必须一致：如果平台的商户号是 A 公司资质申请的服务商，那服务商资质也必须用 A 公司的营业执照——不能先用 A 公司注册平台再用 B 公司的资质申请服务商。
  • 服务商资质下来后，每个子商户入驻仍然要单独审核：子商户入驻审核周期 1-3 个工作日，不是"有了资质就一键生成"。所以新租户上线要预留入驻审核的时间。

服务商资质这件事最容易被忽略的是时间成本——它不是技术问题，但技术架构选了服务商模式后，业务上线时间就被这个资质卡死了。我们当时服务商资质申请花了 3 周，期间直连模式已经跑通了 10 个租户。所以务实的选择是：先直连跑着，服务商资质慢慢申请，下来了再加新租户走服务商。
