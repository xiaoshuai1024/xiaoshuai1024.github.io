Claude Code 与 Codex 的架构分层源码对比：两个 Agent 引擎的拆解

我每天在用的 Claude Code，上个月被我拆开看了一眼，结果发现一个没人告诉我的事实：npm 包里的 cli.js 早就没了。2026-08-18 我升级到 2.1.229 后解开安装目录，里面只剩一个 307MB 的 claude.exe——你天天在用的这个「Node 脚本」，现在是一块编译好的原生二进制，JS 源码被整个焊死在可执行文件里。

这个发现还只是开胃菜。往下读我陆续撞见一串反常识的东西：Claude Code 的 subagent 根本不开新进程，只是同一个函数的递归调用；它并行执行工具的上限是写死的 10，就藏在 L416878 一个不起眼的变量里；而 Codex 那边，agent 的父子关系居然有专门的数据库存着，重启都能把整棵 agent 树恢复回来。这些事用一年也感受不到，翻开源码十分钟就能确认。

于是我决定把两边的源码完整读一遍，这个系列就是这个决定的产物。不是出于收藏癖——是我发现自己对这两个工具的所有判断都来自体感，而体感经常是错的。我一直以为两者的差距主要在模型，读完才知道，调度层面的工程路线差异比模型差异大得多。

先交代本文范围：讲架构分层和发布物形态，是系列的地基。Claude Code 侧的分析锚定 v1.0.88（2025 年中，npm 包里还是纯 cli.js，展开后约 43 万行），2.x 的演进用官方发布物和本机行为验证补充；Codex 侧锚定 2026-08-18 的最新代码（commit 63b268c81b）。所有行号和文件路径都来自这两个版本，后续版本可能对不上。

一、先说清楚：闭源的东西怎么读

Claude Code 闭源，但它的发布物是可分析的。v1.0.88 的 cli.js 是一个 esbuild 风格的单文件 bundle：混淆了函数名和变量名，但字符串常量不混淆。工具名 "Task"、hook 事件名 "PreToolUse"、压缩标记 "[Old tool result content cleared]"，这些都是明文。

我的做法是先用 prettier 把 9MB 压缩文件展开成 43 万行可读格式，然后拿字符串当锚点 grep 行号，顺着调用关系往外扩。这个方法不新鲜，社区里 Dingjz 的 v1.0.33 逆向分析和知乎的 Agent 调度分析都是这么做的，我拿他们的结论和我的 grep 结果交叉验证过，关键位置一致。

混淆代码里还藏着一类高价值字符串：遥测打点事件名。Claude Code 内部到处在发 tengu_ 前缀的埋点——tengu_auto_compact_succeeded、tengu_microcompact、tengu_streaming_error、tengu_max_tokens_context_overflow_adjustment。这些事件名等于官方自己写的运行时行为清单：哪里有压缩、哪里有降级、哪里有重试，埋点名全招了。读不到源码逻辑时，埋点是最可靠的行为索引。

据此，这个系列对 Claude Code 侧的证据分三级：确证（混淆码里字符串直接可见，给行号）、推断（混淆结构推断，标注推断依据）、官方口径（2.x 行为，引官方文档或本机验证）。Codex 侧统一是确证。文中出现的每个机制论断，我都会标明属于哪级——读者可以按级别决定信多少。

Codex 就没有这个问题。openai/codex 是开源 Rust 工程，codex-rs/ 是一个 130 多个 crate 的 workspace，crate 名就是目录名，读源码的体验和读任何中型 Rust 项目一样。

有个事实需要说在前面：网上大部分 Codex 源码分析文章基于 2025 年的版本，那会儿的核心还是 codex.rs 一个大文件加 run_agent_turn 函数。2026-08 的代码里这两个名字都找不到了——已经拆成 core/src/session/turn.rs 的 run_turn 加一整套 task 调度。引用旧文时要小心，这个项目迭代速度极快。

顺带交代 2.x 发布物考古的具体做法，这条路读者可以自己复现。npm view @anthropic-ai/claude-code@1.0.88 显示 unpackedSize 约 77MB（含 vendored 的 IDE 插件），@2.1.100 缩到约 49MB；再到本机的 2.1.229，包结构变成 bin/claude.exe 加平台二进制子包（@anthropic-ai/claude-code-win32-x64），JS 入口彻底消失。把三个时间点的包结构摆在一起，发布物形态的迁移路径就清楚了：从「Node 脚本」到「平台二进制子包」，中间没有任何过渡形态留在 npm 上。

另外提醒一个读混淆代码的常见坑：假阳性。比如 grep "Bash" 会在 L103422 命中一个 name: "Bash"，看着像工具定义，实际是 highlight.js 的 bash 语法定义（打包进来的语法高亮表）。判断标准很简单——真工具定义周围一定有 description、inputSchema、checkPermissions 这些字段，语法表周围是 tokenize 规则。没有这套交叉检查，行号引用就是自欺欺人。

二、发布物：一个在不断藏起来，一个一直摊开

两个项目对「别人能不能读懂我」的态度，直接反映在发布物形态上。

Claude Code 的路线是逐步收紧。1.x 时代发 cli.js，一个 Node 进程就能跑，任何人解包就能看到完整逻辑（虽然要过混淆这一关）。到了 2.x，npm 包里的 JS 消失了，换成各平台的原生二进制——本机 Windows 版是 307MB 的 PE 可执行文件。对普通使用者这是好事：不依赖 Node 环境、启动更快、想扒源码的人大幅减少。对想读源码的人，这意味着静态分析的入口从「解包 npm tarball」变成了「分析二进制里嵌入的 bundle」。

Codex 的路线是一直摊开。GitHub 上就是完整工程，cargo 直接编译。更有意思的是它的结构还在往「更像操作系统」的方向长：2025 年是 core + exec + tui 三五个主要 crate，现在 workspace 里有 sandboxing（landlock / seatbelt / Windows 三套沙箱实现）、agent-graph-store（agent 父子树的持久化存储）、skills（SKILL.md 解析）、guardian（内置审批代理）、rollout（会话落盘加 SQLite 索引）。

这里面最值得单独点名的是 code-mode 系列 crate。它的思路激进：给模型一个能直接写 JavaScript 编排代码的运行时会话，模型不再逐个调工具，而是写一段代码把几十个工具调用编排起来跑。配套的 code-mode-host / code-mode-protocol / code-mode-runtime 拆得很细，甚至支持 gRPC 和独立进程两种宿主形态。工具暴露面也因此多了一档——ToolExposures 里除了 DIRECT（直接给模型）、DEFERRED（模型按需搜索发现），还有 CODE_MODE（只在这种编排模式下可见）。

这是一个架构信号：当工具数量从十几个涨到上百个，「把工具列表塞进 system prompt」的模型失效了，Codex 的应对是给工具做索引（DEFERRED + tool search）和做编排（code-mode）两条腿走路。Claude Code 同期的工具数量没到这个量级，它的应对是 subagent——让子代理自带精简工具集。两个方向没有对错，但决定了「工具很多的重度用户」在两边会得到完全不同的体验。

还有一组 crate 说明 Codex 的野心不在终端：cloud-tasks / cloud-tasks-client（云端任务）、chatgpt（ChatGPT 账号体系打通）、app-server-daemon（常驻守护进程）。终端 TUI 只是它的一个宿主形态，这个产品从架构上就是奔着「随处可部署的执行引擎」设计的。

这两条路线没有高下，但有个实际后果：Claude Code 的架构演进只能靠版本考古和黑盒验证推断，Codex 的每一次架构决策都有 commit 记录可查。写这个系列时，我的证据密度在 Codex 侧天然就高一些。

三、分层模型：单进程的「一杆子捅到底」 vs 多进程的协议化

把两边的分层画在一张图上，差异一目了然。

Claude Code 是单进程架构。终端 UI（Ink，本质是 React 渲染到终端）、主循环、工具层、上下文管理、API client，全部住在同一个 Node 进程里。UI 层和调度层之间没有协议，就是函数调用。它的调度核心是一个函数——v1.0.88 里位于 L416894 的主循环 generator，后面讲主循环的那篇会拆开讲，这里只需要知道：整个 Agent 的行为，浓缩在一个自递归的 async generator 里。

Codex 是多进程协议化架构。你敲下 codex 命令后，实际是 tui 进程通过 JSON-RPC 跟 app-server 进程通信，app-server 再往下走 ThreadManager 创建 Session，Session 里的 task 调度器把输入交给 RegularTask，最终驱动 run_turn。UI 和调度核心之间隔着一条显式的协议边界。

把 Codex 这 130 多个 crate 按职责归一下类，会发现它的分层比「多进程」三个字更讲究：

职责层crate干什么
入口cli / tui / exec交互 TUI、非交互执行、multitool 分发
宿主app-server + 一众 transport crateJSON-RPC / WebSocket，IDE 和云端的接入口
调度core（session / thread_manager / tasks / agent）会话、线程、turn 执行、agent 注册与控制
工具tools / apply-patch / execpolicyToolExecutor trait、补丁解析、命令策略
安全sandboxing / guardianlandlock / seatbelt / Windows 沙箱、审批代理
持久化rollout / agent-graph-store / thread-storeJSONL 落盘、SQLite 索引、agent 树
扩展skills / rmcp-client / plugin / hooksSKILL.md、MCP 连接、插件、hook 事件

注意这张表里没有任何一个 crate 叫「brain」或「orchestrator of everything」。Codex 把调度拆成了三层（线程管理、turn 执行、工具编排），每层职责单一。这个粒度在 Rust 项目里不算过度设计——每个 crate 独立编译、独立测试，改沙箱不会碰到主循环。

注意 tui/src/legacy_core/ 这个目录名——它本身就是证据：TUI 曾经直接内嵌 core，后来被剥离，改走 app-server 的 JSON-RPC。剥离的收益是 app-server 成了统一宿主：IDE 插件、云端会话、TUI，消费的是同一套协议。这套分层让它可以不碰终端代码就把整个 Agent 搬进 VS Code 扩展或云环境。

我读到这里时的感受：Claude Code 像一个精心打磨的单体应用，Codex 在往平台方向长。单体的优势是链路短——一个函数调用就能从 UI 触达主循环，没有序列化开销，也没有跨进程状态同步问题。平台的优势是复用面——代价是每加一层抽象，调试时要多跨一次进程边界。

四、启动链路：两步 vs 跨三个进程

从「敲命令」到「第一条消息进入主循环」，两边的路径长度差异很大。

Claude Code 的链路压缩得很短。cli.js 尾部是 commander 风格的命令注册（doctor、update、install，约 L432550 起），parseAsync 之后进总启动函数，读 settings（z0()，L355734，合并 .mcp.json、allowedTools、hooks 配置），拉起 Ink REPL，用户第一条消息直接进主循环。全程一个进程。

Codex 的链路是：cli/src/main.rs 的 main 解析 MultitoolCli，无子命令进入交互模式，拉起 tui；tui 通过 AppServerSession 发 JSON-RPC 请求（newThread / sendUserTurn）；app-server 侧 core/src/thread_manager.rs:1617 的 spawn_new_thread 创建 Session；用户输入进 session/input_queue.rs，由 tasks/mod.rs 的调度器取出，交给 tasks/regular.rs:39 的 RegularTask::run，最终进 session/turn.rs:153 的 run_turn。

这条长链路里有个容易被路过但很关键的构件：input_queue。用户在模型跑着的时候继续打字，输入不会丢，会排队等 turn loop 下一轮取走（step loop 里每轮调 get_pending_input）。这个设计叫 steering——跑偏了随时插话纠偏，不用等整轮结束。Claude Code 同样支持运行中追加输入，实现方式是主循环每轮迭代重新读消息队列。交互细节相似，但 Codex 把队列做成了独立构件，等于承认「人在回路中」是调度的一等公民，不是 UI 层的补丁。

两条链路还各有一条非交互支线：Claude Code 的 claude -p（print 模式，一条命令跑完退出，CI 里常用）复用同一套主循环；Codex 有独立的 exec crate（exec/src/main.rs），event_processor 把事件流按 human 或 jsonl 格式输出。给 CI 做 Agent 步骤时这是主要接入口——两边都支持，但 Codex 的 jsonl 事件输出更规整，方便程序消费。

这个差异在「会话持久化」上的投影很有意思。Claude Code 的会话历史在内存里的 messages 数组，落盘是 JSONL；Codex 有独立的 rollout crate，JSONL 之外还建了 SQLite 索引（rollout/src/state_db.rs），支持倒序扫描（reverse_jsonl_scanner.rs）。为什么 Codex 需要索引？开头第二个钩子在这里兑现：subagent 的父子关系存在 agent-graph-store 这个独立存储里，重启后能把整棵树找回来。单进程内存模型天然用不上这些。

一个对写代码的人很实际的推论：中断恢复的语义两边不一样。Claude Code 的会话恢复是「把历史消息重放进一个新进程」，subagent 的中间态没了就是没了；Codex 因为有 rollout 加 agent 图存储，恢复的是「结构和断点」，thread 之间的 spawn 关系、每个 agent 跑到哪个 turn 都有记录。跑长任务（比如夜间批量重构）时这个差异会直接决定你敢不敢 Ctrl+C。

还有一个容易被忽略的分层差异：事件流。Codex 的 protocol crate 里定义了 Op / EventMsg 枚举，是 core 和所有宿主之间的正式合同——TUI 收到的是结构化事件，不是渲染指令。Claude Code 的 Ink UI 和主循环之间没有这层合同，UI 状态和调度状态揉在同一个 React 树里。这就是为什么第三方想给 Claude Code 做个 GUI 壳很难，而 Codex 的 app-server 生来就是给别人做壳用的。

五、藏在混淆代码里的模块地图

「Codex 有 130 个 crate」这个数字容易给人错误印象：Claude Code 那个 43 万行的单文件是不是就没结构？不是。它有清晰的分区，只是边界不写在目录里，要靠字符串锚点聚类出来。

几个关键坐标：L1 到约 L345000 是三方库打包区（AWS SDK、highlight.js 语法表都在这，注意 L103422 有个 name: "Bash" 是语法定义不是工具定义，别认错）；L345000 到 370000 是配置与 MCP 客户端；L377000 到 395000 是工具定义加 API 流处理；L416000 到 418000 这两千行是整个产品的灵魂——主循环、工具分发、subagent 启动器全在这里；L419000 之后是 Ink UI 和 CLI 入口。

每个分区里都有能直接认领的锚点。配置区有 z0()（settings 总读入口，L355734）和 .mcp.json 的发现逻辑（L349510）；工具区有工具名常量表（"Task" 在 L368573、"Read" 在 L345990、"Write" 在 L368635）和 hook 事件枚举（L350463 起九种事件一字排开）；灵魂区有主循环 VE（L416894）、工具分发管线（L417134 起）和 subagent 启动器（L417610）。这些行号在系列后续每篇都会反复出现，等于我们有了混淆代码里的门牌号。

分区的边界感还有个佐证：bundle 的导出声明在文件最后一行，只有三个 setup 相关函数。也就是说这 43 万行里 99.99% 的代码都在为终端会话服务，没有为「被当作库复用」留任何正式接口。对照 Codex 把 core 做成可被 app-server 消费的库，两种产品形态的意图差异写在最后一行导出里。

这个分布本身就是设计宣言：一个 Agent 引擎的功能核心，其实就两万行上下。剩下四十万行是 UI、配置、三方依赖、多环境兼容。对比 Codex 把同样职责拆进十几个 crate，你会发现**「Agent 引擎本体」在两边都是小头，大头都在工程化配套上**。这也是我自己写 Agent 任务编排时反复验证过的判断：调度逻辑不难写，难的是让它安全、可恢复、可观测。

这个分区地图还有个实用价值：它是系列的导航。后面每篇讲到一个机制，我都可以直接给出它在地图上的坐标——讲权限时你该去看 L345000–370000 的配置区和 L417234 的工具执行管线；讲上下文压缩时该去 L394000 一带找阈值常量。混淆不是黑盒，只是没有目录的黑盒。

六、先给一张核心对象对照表

总览篇的最后，我把后续五篇要拆的核心对象先摆出来。这张表现在看是索引，看完系列回头再看，就是两个引擎的完整对照。

机制Claude Code v1.0.88Codex 2026-08
主循环VE，自递归 async generator（L416894）run_turn，step loop 加 FuturesOrdered（session/turn.rs:153）
subagentTask 工具，复用同一个主循环，不开新进程（L417610）multi_agents_v2 工具族，独立 thread 加 AgentExecutionLimiter 信号量
并发上限工具级并行池，硬编码 10（L416878）agent 级可配置 max_concurrent_threads_per_session
上下文压缩microcompact 清旧工具输出 + auto-compact 摘要compact.rs 独立摘要请求 + 服务端压缩双路
权限四种模式 + hooks 事件改写决策AskForApproval 枚举 + guardian 审批代理 + 三平台沙箱
扩展加载settings 合并 + .mcp.json 发现skills / rmcp-client / plugin 三个独立 crate

每一行都够写一篇五千字，这也是这个系列的由来。表里最值得先盯一眼的是第一行和第二行的组合：Claude Code 的 subagent 是「同一个循环的递归」，Codex 的 subagent 是「另一个线程的调度」——这一个差异往下辐射出并发模型、通信方式、恢复能力的全部不同。

读法上给个建议：这张表别当结论背，当问题清单用。每一行都是一个「为什么两边长成了不一样」的疑问，带着疑问进对应那篇，比顺着目录读收获大。架构对比的意义从来不是记住谁用了什么，是理解每种取舍背后的问题形状——下次你自己做技术选型，套的是问题形状，不是别人的答案。

七、两条路线的取舍，落到使用上是什么

架构分析如果落不到使用层，就是自嗨。这两条路线的差异，我在日常使用里能对上号的至少有三点。

第一，扩展机制的位置不同。Claude Code 的扩展（hooks、MCP、output styles）都挂在一个进程内，加载即生效，出了问题整个进程一起感知——一个 hook 写崩了，会话跟着崩。Codex 的扩展边界在进程和 crate 边界上，MCP 走独立的 rmcp-client，沙箱是独立 crate，审批走 guardian，隔离性天然强一档。

第二，确定性来源不同。Claude Code 靠模型自律加 hooks 约束，快速但松；Codex 在语言层就上了强约束——Rust 的类型系统加独立沙箱 crate（Linux 用 landlock、macOS 用 seatbelt），危险操作在编译期和运行期都被拦。这解释了我为什么把高风险的批量改动更多地交给 Codex 跑（配合多 Agent 评审的实践），而探索性的快速迭代用 Claude Code。

第三，演进速度和可解释性在做交换。Claude Code 一年从 1.0 到 2.1 两百多个版本，发布物都换了形态，但没有 commit 历史可考，我只能说「它变了」；Codex 的每次重构——比如 TUI 和 core 的解耦——都有目录名和代码为证。选型时如果你在意「这个工具十年后还能不能被理解」，开源这条路线的确定性是实打实的。

第四，启动和加载策略的手感差异。Claude Code 启动时把配置里声明的 MCP server 全部连上，工具列表一次性注入；Codex 走按需路线——turn 开始时先解析你输入里 mention 了哪些 server 和 skill，只连接需要的（required_mcp_servers_for_input），再加一层 prewarm。这解释一个很多人遇到过的现象：MCP 装多了 Claude Code 启动变慢、上下文变挤，而 Codex 对「装而不常用」宽容得多。这个机制系列第六篇展开。

第五，「抢跑感」的来源。用 Codex 时常常感觉它更早开工执行工具，这不是错觉：它的流处理是 function call 一到就推进 FuturesOrdered 并发执行；Claude Code 是一轮响应收完、提取全部 tool_use 后再统一分块执行。两种策略各有道理（统一分块能按安全性分组），但体感差异是真的，背后就是分层图里那两行蓝底框的差别。第二篇拆主循环时拿代码对账。

这些使用层的对应关系，就是我坚持读源码的原因。体感告诉你「更快」「更稳」，源码告诉你快在哪一行、稳在哪一层。前者只能用来聊天，后者能用来做决策——什么时候切工具、什么时候改配置、什么时候自己写编排。

投入产出也说一下，给想跟进的读者一个预期。这次勘察我实际花的功夫：Codex 侧 clone 加定向阅读约一个晚上（开源代码有目录，按图索骥）；Claude Code 侧 prettier 展开加锚点 grep 约两个晚上（混淆代码没有目录，但字符串锚点之后效率不低）。换句话说，「读一个 CLI Agent 的源码」是普通工程师一两个周末能完成的事，不是什么大工程。门槛不在技术，在于肯不肯把「用工具」的时间分一点给「懂工具」。

收在这

把两边的分层摊开看，Claude Code 和 Codex 的差异可以收敛成一句话：前者把一个 Agent 引擎打磨到极致紧凑，后者在把 Agent 引擎长成一个操作系统。单文件、单进程、单循环，换来的是链路短、启动快、行为直接；多进程、多 crate、协议化，换来的是可复用、可恢复、可被别的宿主消费。

这两种路线都能做出好产品，但它们适合的人不一样。如果你主要在终端里单人使用，Claude Code 的紧凑是优势；如果你要把它嵌进 IDE、跑在云端、管一群 subagent 的生命周期，Codex 的分层才是能撑住的地基。这个判断会贯穿整个系列——后面五篇会分别拆主循环、subagent 调度、上下文管理、工具与权限、skill 与 MCP 加载，每篇都带着这两条路线的对照去看。

最后交代一下证据边界：Claude Code 侧的行号基于 v1.0.88 逆向，2.x 的结论标注了来源（发布物检查、官方文档、本机行为）；Codex 侧基于 2026-08-18 的 commit 63b268c81b。两个项目迭代都很快，读者复现时请以自己拿到的版本为准——这也是读源码系列文章的基本礼仪：版本先锚定，结论才有意义。

相关的实操背景我放在另外两篇：自己动手写 skill 的踩坑记录在这里，Claude Code 的 skills 体系拆解在这里。下一篇拆主循环：一个自递归 generator 和一个 Rust step loop，怎么把同一件事做出了两种手感。
