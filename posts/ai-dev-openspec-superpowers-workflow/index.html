OpenSpec 和 Superpowers 别二选一,它们管的是两件事

OpenSpec 装上了，Superpowers 也装上了，项目照样乱。

打开项目目录，openspec/changes/ 和 docs/superpowers/plans/ 两个目录都在，真要让 AI 动手，它还是直接改、改完不归档，下次那批约定又得从头再来。你手上两套工具，等于两套都只装了没跑。

还有一种更隐蔽的误区：以为两套都装上了，就是「规格化开发」了。结果只是多出一堆没人读的文档，AI 的产出还是无规格、无计划的状态。

问题不在工具，在于没搞清这两套东西管的是两件不同的事。这两套是唯一同时放进我日常流程的规格化工作流，反复迭代的视频管线、公众号发布、站内搜索都是它们管出来的。核心分工是：OpenSpec 管「一次变更的规格」，Superpowers 管「一个项目的计划」。 粒度不同、产物不同、驱动方式不同，配起来才完整。

为什么一个规格工具不够

先看 OpenSpec 解决什么。它把一次变更固化成 change，放进仓库的 openspec/changes/<名字>/，里面是四件套：proposal.md（为什么改、改什么、影响什么）、specs/<能力>/spec.md（系统必须做什么，增量规格）、design.md（怎么做、权衡了什么）、tasks.md（按什么顺序做）。六个 skill 组成流水线：explore 想清楚 → propose 生成四件套 → apply 照 tasks 施工 → sync 预览合并效果 → update 回炉修订 → archive 归档并合并进主规格。

这套东西管到的最小单位是一次变更。它把「加个缓存」「加个封面自动上传」这种改动定义得清清楚楚，AI 照着 spec 施工，改完归档，能力攒进主规格。我在 /posts/ai-dev-openspec-spec-driven/ 里用一条加缓存的改动把六个 skill 走了个遍，这里不重复。

但一整个项目目标不是 change 的粒度。「把公众号自动发布做出来」这个目标，涉及账号对接、定时发送、封面上传、失败重试、群发通知，拆开是几十个变更。OpenSpec 能把每一个变更定义明白，却管不了这几十个怎么排、阶段怎么分、跨变更的依赖是什么、整个目标收敛没有。那不是变更规格层的事。

再看 Superpowers 管什么。仓库里 docs/superpowers/plans/ 下每个 plan 长这样：Goal（定目标）、Architecture、Tech Stack、Spec 引用、文件结构表、checkbox 任务清单。由 superpowers:subagent-driven-development 按计划逐条执行，勾完一个推进一个。它管到的最小单位是一个项目的落地：目标怎么拆、任务怎么排、进度怎么跟踪。

但 plan 不承担变更规格。plan 里写「做站内搜索」，不会细到每个接口的验收场景。这些细节天然该落在变更规格层，而不是塞进项目计划。

两套粒度不同，一个管项目计划（大），一个管变更规格（小）。只用任一个，就有一层没人管：只上 OpenSpec，项目级的目标没人拆解跟踪；只上 Superpowers，变更级的行为没人定义验收。这不是二选一，是缺一半。

分工：粒度、产物、驱动方式

两条流水线的差异不止粒度，产物形态和驱动方式也完全不同。把它们并排看，界限才清楚。

OpenSpec 变更规格层

  • 粒度：一次变更
  • 产物：openspec/changes/<名字>/ 四件套
  • 驱动：六个 skill 流水线（explore → propose → apply → sync → update → archive）
  • 规格是增量的，只声明本次变更的行为
  • 归档后合并进主规格，能力长期积累

Superpowers 项目计划层

  • 粒度：一个项目 / 一个落地目标
  • 产物：docs/superpowers/plans/<日期>-<名字>.md + 对应的 design spec
  • 驱动：superpowers:subagent-driven-development 按 checkbox 任务逐条执行
  • 计划是全局的，一次覆盖整个目标
  • 任务用 checkbox 跟踪，勾完 = 目标落地

增量规格和全局计划，这两条差异值得展开。

OpenSpec 的「增量」设计是有意为之。一次 change 只声明本次变更的行为，不重写整个系统，归档时才合并进主规格。好处是规格不会腐化。主规格始终是最新能力的合集，而 openspec/changes/ 本身就是一部变更史，像 git log 一样能回看每一次为什么这么改。我在仓库里见过太多「装完 OpenSpec 不 archive」的项目，主规格停在几个月前，change 叠了一堆没合并，等于规格史断更了。

Superpowers 的「全局」设计对应计划层特有的价值：任务依赖和进度可见。一个 plan 把整个目标铺开，任务清单用 checkbox 勾选，subagent 逐条执行、勾完一条推进一条。断点也清楚：这周干到第几条、还剩几条，打开 plan 一目了然。这是变更规格层给不了的项目视图。

两套在我仓库里的真实分布能佐证这个分工：openspec/changes/ 下有 8 个活跃 change（公众号自动发布、抖音选题 skill、Remotion 3D 视频、视频多平台发布、去 AI 味护栏……），另有 3 个已归档（视频横向 skill、文章篇幅改革、封面统一）；docs/superpowers/plans/ 下有 4 个完整 plan（公众号同步、低代码平台页面、图文生成管线、站内搜索），每个都配了 design spec。

一个关键认识：这两套在我这里不是严格的先后关系，是分工关系。新项目落地，用 Superpowers 铺全局计划；持续迭代里每一次变更，用 OpenSpec 规格化。像视频管线这种反复改的东西，OpenSpec 的归档价值最明显：一次次的临时决定通过 archive 攒进主规格，下次 AI 启动时不会把这些约定忘掉。

衔接：plan 是地图，change 是施工令

两套怎么接起来，用一条真实链路讲（内容脱敏）。

目标进来：「做一个从博客文章到图文的半自动生成管线」。这是项目级的事，Superpowers 先铺 plan：Goal 定目标，Architecture 定 Python 模块怎么分，Tech Stack 定 Jinja2 + Playwright + Pillow，文件结构表列清每个脚本的责任，最后是 checkbox 任务清单。subagent 按这张地图推进，一步勾一步。

推进中遇到「渲染层要支持一种新模板」这种具体变更，这是变更级的事，走 OpenSpec：propose 生成四件套，spec 声明新模板的行为和验收，apply 照 tasks 施工，测完 archive 合并进主规格。

两层的衔接点就在这里：plan 是地图，change 是施工令。 plan 拆出来的大块任务，细化成具体的变更规格；apply 施工的是每个 change，服务的是 plan 画出的整张地图。plan 回答「这个项目做到什么程度算完」，change 回答「这一次改动怎么做才符合约定」。

收尾看两张表：plan 的 checkbox 全部勾完，代表项目落地；change 全部归档，代表能力进了主规格。地图画完、施工令全部执行完，这件事才算真正做完。

但要守住诚实边界：不是每个项目都严格走完两条。 小的一次性任务，plan 和 change 都不用走，explore 聊透直接干。两套不是流程仪式，判断标准只有一条——这个任务大到需要全局计划，还是小到只需要一次变更规格。

决策表：什么情况走哪个

场景走哪套为什么
新项目，目标明确要落地Superpowers plan需要全局拆解、任务跟踪、进度可见
既有功能迭代，一次变更OpenSpec change需要定义行为、验收、留档，攒进主规格
大项目里出现架构级变更两层都走plan 更新目标视图，change 规格化这次变更
一次性探索 / 试错都不走还没到立项的粒度，explore 聊透再定

判断规则只有一条：看要不要长期积累。 变更的行为要攒进主规格，走 OpenSpec；项目要按计划执行并跟踪，走 Superpowers。两层同时需要的信号也很明确：plan 拆出来的大任务，细化成了具体的变更规格，这时候两层一起走，不冲突。

反模式：两套最常见的错法

分工讲清了，最常见的错法就那些。列出来，对照自查。

把 change 当项目计划用。 一个 change 里塞一整个项目，四件套写成巨型需求书。OpenSpec 的增量规格是它存在的意义——一次 change 只声明一次变更的行为；塞满一个项目，就退回没人维护的单文件时代，规格史也断更了。

把 plan 当变更规格用。 plan 里写每个接口的验收场景，plan 膨胀到没人读。计划层管「做到什么程度」，变更层管「这次行为怎么验收」，职责一混，plan 变成没人愿意维护的巨型文档，subagent 执行起来也找不到主线。

apply 完不 archive。 施工完不归档，spec 不合并进主规格，能力没攒下来，下次 AI 启动那批约定又得从头再来。归档不是仪式，是把约定攒下来；它也是最容易被跳过、又最伤长期效果的一步。

同一个任务两套都建。 同一个任务建了 plan 又建 change，重复记账，两份文档互相不同步，改一处忘一处。粒度错了就换，别两边都记。判断标准还是那句「要不要长期积累」。

只装不用。 装了一堆 skill，项目还是「直接让 AI 写」。工具在吃灰，AI 的产出还是无规格、无计划的裸奔。装上但没跑进流程，等于没装。这也是很多项目「装了两套还乱」的直接原因。

自查清单：开工前过一遍

把上面的分工收敛成一张能直接拷进团队协作规范的清单。每次 AI 开工前，按这几条过一遍：

  • 任务有明确落地目标，要拆多步、跟踪进度 → 建 docs/superpowers/plans/<日期>-<名字>.md
  • 这次是一次变更，行为需要定义和验收 → 建 openspec/changes/<名字>/ 四件套
  • 变更多到需要排期、互相有依赖 → 说明它其实是项目，先建 plan，再拆 change
  • 一次性试错 / 探索 → 两个都不建，explore 聊透再动手

配套两条硬约束：不要在一个 change 里塞一整个项目；不要在 plan 里写每个接口的验收场景。

这三问值得每次开工前问自己：要不要长期积累？ 要，走变更规格层；要跟踪到落地，走计划层；都要，两层一起。判断清楚再让 AI 动手，省下的返工远多于写文档的时间。

我的收尾判断

回到开头那个判断：两套东西不是在抢同一个位置，它们管的粒度天生不同。OpenSpec 管一次变更怎么被定义、被照做、被记进主规格，Superpowers 管一个项目怎么被计划、被拆解、被跟踪。把两套配成双流水线，项目级的事交给计划层，变更级的事交给规格层，AI 的产出才真正从「会写代码」变成「有章法地交付」。装完 OpenSpec，再补上 Superpowers，这另一半才是很多人缺的那一块。
