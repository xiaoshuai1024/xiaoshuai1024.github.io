Claude Code 的 skill 能自己进化？25 万星 ECC 源码拆出答案

能。Claude Code 的 skill 确实可以自己进化——不用你写一行 SKILL.md，它从你的日常会话里观察、提炼、攒成本能，再定期把本能聚成新 skill。跑通这件事的项目叫 ECC，GitHub 上 25.7 万星，agent harness 赛道目前最大的开源项目。

这套进化机制的核心代码在 instinct-cli.py 里，第 1158 行藏着一句怨念很深的注释：trigger 句子平均只有 7 个词，用 Jaccard 相似度算聚类，明显相关的两条最高也只能到 0.33，「nothing ever groups」——什么都聚不起来。为了这句注释，作者把整个聚类算法换成了 overlap coefficient。

这是 ECC 的 Instincts 子系统。翻完它的源码，我最大的感受是它的诚实：每一层都在直面同一个物理事实——大语言模型没有记忆，你感觉到的「记性」，全部是外挂工程拼出来的。

这篇文章把这个外挂拆开看。先讲清楚为什么记忆必须外挂，再顺着数据流拆四层：观察、本能、注入、进化。ECC 给每一层交出的工程答案，比大多数「AI 记忆」创业产品的宣传页都有信息量。

一、先纠正一个错觉：模型的「记忆」是三种不同的东西

很多人聊 AI 记忆时把它们混成一团。认知科学把人类记忆分成三类，这个框架搬过来正好用：

认知科学分类日常对应AI 编程代理里的对应物
工作记忆脑子里「正在想」的内容上下文窗口（context window）
情景记忆「上周三发生过什么」会话日志、transcript 文件
程序记忆骑自行车这种「肌肉记忆」系统提示词、skills、规则文件

关键在第一行。LLM 是无状态的：每次推理，模型只看得到当前上下文窗口里的 token，上一次会话发生的一切对它来说不存在。你在 Claude Code 里教过它一百次「这个项目提交信息用 conventional commits」，新开一个会话，它照样给你写 update stuff。不是它不听话，是那个信息物理上不在它的输入里。

所以「让 AI 有记性」这个需求，翻译成工程语言就是：怎么把情景记忆（历史会话）提炼成程序记忆（可注入的行为规则），然后在恰当的时机塞回工作记忆（上下文窗口）。

ECC 的做法是四步：hooks 观察你的每次操作 → 后台代理从观察里提炼「本能」（instinct）→ 每次开新会话时把最相关的本能注入上下文 → 定期把攒多的本能聚合成 skills、commands、agents。整个 Instincts 子系统就跑在这条数据流上。

下文按这四步逐层拆。每层我都会贴源码里的真实实现，包括那些 README 不会告诉你的翻车记录。

二、观察层：v1 为什么被推倒重来

观察是整个系统的地基：观察不到的东西，后面全部免谈。ECC 在这一层交过一次学费，v1 到 v2 的重写理由值得单独讲。

v1 的观察挂在 Claude Code 的 Stop hook 上——会话结束时，让主模型回看整个 transcript，总结出经验。听起来合理，实际跑起来有两个致命问题：

第一，Stop hook 会因为各种原因不触发（会话异常退出、用户直接关终端），观察是有损耗的。地基漏一半，后面的记忆系统等于建在沙子上。

第二，让主上下文的模型做分析，等于用最贵的 token 干最杂的活。会话本身就是模型在干活，再让它分心做「元认知」，成本和干扰都不可接受。

v2 的答案换了个思路：观察和分析彻底分离。

观察交给 PreToolUse / PostToolUse hooks。这两个 hook 在每次工具调用前后必然触发，源码里的说法是「100% reliable」。hook 本身不做任何分析，只把原始事件追加写进 observations.jsonl：

{"timestamp":"2025-01-22T10:30:00Z","event":"tool_start","session":"abc123","tool":"Edit","input":"...","project_id":"a1b2c3d4e5f6"}
{"timestamp":"2025-01-22T10:30:01Z","event":"tool_complete","session":"abc123","tool":"Edit","output":"...","project_id":"a1b2c3d4e5f6"}
{"timestamp":"2025-01-22T10:30:05Z","event":"tool_start","session":"abc123","tool":"Bash","input":"npm test","project_id":"a1b2c3d4e5f6"}

分析交给一个后台观察者代理（observer agent），配置里明晃晃写着 model: haiku——用最便宜的模型干提炼的活。它不参与你的会话，只在观察攒够 20 条（可配置）、或每 5 分钟定时、或收到 SIGUSR1 信号时醒来，读一把 jsonl 文件。

观察者代理的任务书（agents/observer.md）里写死了四类要识别的模式，这四类就是「经验」的全部来源：

  1. 用户纠正：你打断了模型的输出说「不对，用 X 不要用 Y」。这是质量最高的信号，人类反馈直接纠偏
  2. 错误解决配对：一个工具输出报错，接下来几次调用把它修好了。同一类错误被相似方式解决多次，就值得记下来
  3. 重复工作流：同样的工具序列反复出现。总是先 Grep 再 Edit，总是改完跑同一个测试命令
  4. 工具偏好：某些场景下你总是选特定工具。比如读文件一律用 Read，查代码一律先 Grep

这四类模式的共同点：都是行为层面的信号，不碰语义内容。观察者不关心你在写什么业务代码，只关心「人和模型互动时反复出现的模式」。这个克制是整套系统能跑得动的关键——分析面收窄，廉价模型才扛得住。

v2.1 又在这层补了一刀：项目隔离。观察事件里带上了 project_id，这个 ID 不是随便生成的：优先取 git remote get-url origin 的哈希。这意味着同一个 GitHub 仓库在你的台式机和笔记本上会得到同一个 project ID，两边攒的本能可以合并。而 React 项目里攒的「组件用 hooks 写法」，也再不会污染到 Python 脚本仓库里去。v2 时代所有本能混在一个全局目录里跨项目串味的问题，是 v2.1 明确写在变更说明里的修复动机。

三、本能层：一条 YAML 就是一个带证据链的置信度断言

观察者代理的产出物叫 instinct（本能），存成一个个 YAML 文件。先看一条真实样本——这是 ECC 官方仓库自带的本能库里的第一条：

---
id: everything-claude-code-conventional-commits
trigger: "when making a commit in everything-claude-code"
confidence: 0.9
domain: git
source: repo-curation
---
## Action
Use conventional commit prefixes such as `feat:`, `fix:`, `docs:`, `test:`, `chore:`, and `refactor:`.
## Evidence
- Mainline history consistently uses conventional commit subjects.
- Release and changelog automation expect readable commit categorization.

解剖这条 YAML，能看出 instinct 模型的全部设计决策：

Atomic（原子性）。一条本能只有一个 trigger、一个 action。「写提交信息时用 conventional commits」，不掺别的。后面聚类进化时你会发现这个约束的用意：原子颗粒才能自由组合，一条大而全的「经验总结」什么也组合不出来。

trigger + action 分离。trigger 是激活条件（「什么时候」），action 是行为（「做什么」）。这个结构和行为主义的 S-R（刺激-反应）公式同构，也和 Claude Code 的 skill 触发机制同构——后面进化成 skill 时几乎无缝。

confidence 0.3~0.9。这是整条本能的灵魂。它不是模型输出的概率（大模型的 token 概率在这里毫无用处），而是一个外部维护的信念分数：观察到 5 次证据，0.5；观察到 8 次且用户每次都这么纠正，0.9；只在一次会话里出现过，0.3。这个分数由观察者代理根据证据累积更新——相当于把贝叶斯信念更新做成了工程上的计数加成。为什么模型自己给不了这个分数？因为无状态：模型对「过去被验证过几次」一无所知，这个信息只能从外部账本查。

Evidence（证据链）。每条本能必须写清楚它是从哪些观察得出的。「Observed 8 times in session abc123」——可溯源，可审计。你作为系统的主人，可以打开文件质疑任何一条本能：这个 0.9 我不认，删掉。证据链是把「记忆的信任问题」交还给人的机制。

domain 标签。git、code-style、testing、debugging、workflow——粗粒度领域分类，注入和聚类时都用到。

这里有个容易被忽略的细节：instinct 文件的正文的 Markdown 标题结构是固定的 ## Action + ## Evidence。YAML front matter 给机器读，正文给人读、也给注入时当原文用。一份文件两个受众，这是整个 ECC 文档组织的惯例——Memory Vault 的设计文档里同样写着「Markdown 是正本，SQLite 和 embedding 只是索引，绝不能变成仅剩的副本」。

本能层还有一套保鲜机制防止垃圾堆积：pending 状态的观察有 TTL（过期天数），status 命令会提前预警快过期的待定项；跨项目提升（promote）有 0.8 的置信度硬门槛——一个项目里的局部经验，要在第二个项目里也被验证过，才配变成全局本能。源码里的常量名就叫 PROMOTE_CONFIDENCE_THRESHOLD = 0.8。

四、注入层：开新会话时，6 条本能怎么选

本能攒起来只是库存，真正决定体验的是注入：每次 SessionStart，把哪些本能塞进上下文？

直觉做法是全塞进去——反正都是经验。ECC 没这么干，session-start.js 开头的三个常量先划死了预算：

const DEFAULT_MAX_INJECTED_INSTINCTS = 6;            // 最多注入 6 条
const MAX_INJECTED_LEARNED_SKILLS = 6;
const DEFAULT_SESSION_START_CONTEXT_MAX_CHARS = 8000; // 本能区总预算 8000 字符

6 条、8000 字符。为什么这么抠？因为上下文窗口是工作记忆，工作记忆的每一个 token 都在和其他内容抢位置——你的任务描述、代码文件、工具输出全都要往里挤。本能注入太多，挤占的是正事的空间；而注意力机制对中段内容本就不友好（丢失中间现象，lost in the middle），塞一堆低相关记忆进去，效果是负的。注入的工程目标因此非常明确：用最小预算，把「此刻最可能用到」的记忆放进开场。

那「最可能用到」怎么排序？第一反应是按 confidence 排——0.9 的排前面。但 ECC 在 v2.1 加了一个精妙的修正，scripts/lib/instinct-relevance.js 的注释把设计意图说得明明白白：

这些加成刻意做成不可配置。设计目标是：让项目内的 0.7 本能（0.7 + 0.25 = 0.95）能压过不相干的全局 0.9；让技术栈匹配的 0.75 本能（0.75 + 0.2 = 0.95）也能压过不相干的 0.9。

翻译一下排序公式：最终分 = 置信度 + 场景相关性加成。当前项目特有的本能 +0.25，技术栈匹配的本能（检测到 terraform 文件、dbt 配置之类）+0.2。两个加成都设计成「恰好能把低 0.15~0.2 的相关本能顶过不相关的高分本能」。

这个设计的深意在于承认了置信度的局限：confidence 衡量的是「这条经验被验证得多充分」，但注入要的是「这条经验现在用不用得上」——这是两个正交的维度。一个全局的 git 提交规范本能（0.9，在别的项目攒的）和一个当前项目的 React hooks 惯例（0.7），后者对眼前这个会话的价值明显更大。场景加成就是在「信念强度」和「场景相关」之间做了一次工程折中，而且折中的力度被刻意钉死、不给用户调成旋钮的余地——注释原话：「issue 要的是相关性排序，不是更多可调旋钮」。

检测技术栈的方式也值得一看：非递归读项目根目录的文件清单，看到 .tf 文件算 terraform，看到 dbt_project.yml 算 dbt。注释特意强调 kept cheap for a blocking SessionStart hook——SessionStart 是阻塞式 hook，每毫秒都直接拖慢会话启动，所以宁可检测得糙一点。这是「启动延迟」约束下的诚实取舍。

注入完成后，你会在新会话开场看到类似这样的块：每条本能一行，置信度渲染成百分比，末尾带一条提示「这些本能来自历史会话观察，可用 /instinct-status 管理」。不装神弄鬼，明明白白告诉用户上下文里被塞了什么，记忆系统的可解释性做在了明面上。

五、进化层：本能攒多了，怎么变成技能

单条本能解决的是「记住」，进化层解决的是「成长」。本能库攒到几十条之后，/evolve 命令上场：把相关本能聚成簇，生成更高阶的结构。

进化产物有三种，对应三种行为形态，进化规则文档（commands/evolve.md）给出了明确判据：

产物适用形态触发判据（源码常量）
Command用户主动调用的动作描述「用户要求做 X 时」的本能序列
Skill自动触发的行为trigger 相似、2 条以上的本能簇
Agent需要独立上下文的多步流程簇内 ≥3 条本能且平均置信度 ≥0.75

一个直观的例子：你在项目里攒了三条本能——「加表时先写 migration」「加表时更新 schema 文件」「加表时重新生成类型定义」。/evolve 发现它们的 trigger 都围绕「加表」，聚成一簇，生成一个 new-table command。下次你说「加一张用户表」，一条命令把三步全带上。三段各自独立的行为记忆，拼成了一个完整的工作流——这就是「本能进化成技能」的实义。

聚类实现是整个子系统里最有「人味」的部分，也就是开头提到的那段翻车实录。第一版用 Jaccard 相似度聚 trigger，结果什么都聚不起来。源码注释还原了排查过程：

Jaccard 在这里是错误的度量：trigger 关键词集平均约 7 个词，明显相关的两条算出来最高也就 0.33，永远达不到分组线。

于是换成 overlap coefficient（交集除以较小集合）。同样两个 7 词的集合共享 4 个词，Jaccard 算 4/(7+7-4)=0.4，overlap 算 4/7=0.57，对短集合友好得多。分簇阈值定 0.5，另加一道保险：共享关键词少于 2 个不许进同簇（TRIGGER_MIN_SHARED_KEYWORDS = 2），防止一个偶然撞词把不相干的本能拽到一起。

聚类策略用的是贪心：每条本能找分数最高的现成簇去比，够线就并入，并且把簇的关键词核心更新为交集，「让簇保持在一个主题上」。

值得停下来想一下：2026 年了，聚类的默认答案难道不该是 embedding 向量聚类？ECC 偏不用。翻 Memory Vault 的设计文档能找到这个选择的哲学根源：本地优先、无网络依赖、无 embedding 服务依赖、不用模型也能跑。关键词重叠聚类可解释——每个簇的标签就是共享关键词本身，你能看懂为什么这几条被聚到一起；向量聚类给不了这个透明度。代价是召回上限低，语义相关但用词不同的本能会漏聚。这是「可解释性换智能程度」的典型交易，ECC 在记忆这个高危场景里每次都选了可解释的一边。

进化层还有个容易错过的细节：生成的产物文件名 slug 要截断到固定长度（skill 30 字符、command/agent 20 字符），且必须截在单词边界上。注释里记着教训：硬切产生过 investigating-comple 这种文件名，「读起来像错别字」。一个 25 万星的项目在给文件名截断写防御性代码，工程质量的成色就体现在这种地方。

六、拆完之后，能抄走什么

把四层连起来看，ECC 的记忆系统其实回答了三个通用问题，这三个答案不依赖 ECC 本身，你自己搭任何记忆系统都用得上。

记忆怎么采集：挂在确定性事件上，别挂在模型自觉上。 v1 靠会话结束时模型自查，漏采且贵；v2 靠 hooks 事件流，零漏采且便宜，分析甩给后台廉价模型。数据源必须是 100% 可靠的管道，模型只做管道之后的提炼——这个分层是整个系统能立住的地基。

记忆怎么信：置信度外部化，证据链强制。 模型对自己的历史一无所知，所以「这条经验被验证过几次」必须记在外部账本上；每条记忆强制挂证据（哪次会话、观察到什么），让人能否决任何一条。「记忆是上下文，不是指令」——Memory Vault 设计文档里这句话值得抄进每个记忆系统的设计目标：自动采集的东西永远默认 unreviewed，晋升为可执行规则必须过人的审查或硬门槛（promote 的 0.8）。

记忆怎么用：预算制注入，相关性压过置信度。 工作记忆按 token 计价，注入天然是资源分配问题。6 条上限、8000 字符预算、场景加成钉死不给调，每一刀都在防「记忆膨胀吃掉正事」。排序公式「置信度 + 场景相关性」承认了一个常被忽略的事实：被验证得最充分的记忆，不一定是此刻最用得上的记忆。

至于为什么这套东西值得现在看：Claude Code 的 skills 生态正在把「程序记忆」标准化（我在/posts/claude-code-write-your-own-skill/里拆过怎么写一个自己的 skill），而 skills 的内容从哪来，目前大多数人的答案是手写。ECC 给出了另一条路：从你和代理的真实协作记录里自动攒出来。它现在还很糙：聚类只会数关键词，观察者只认四类模式，进化产物还要人审。但方向是对的：记忆系统的瓶颈从来不在模型的记忆能力（模型根本没有这个东西），而在信息架构——什么该记、记了信不信、用时给多少。

ECC 把这三个问题各给了一个工程上站得住的答案，剩下的打磨空间，就是接下来整个「AI 记忆」赛道的活儿。
