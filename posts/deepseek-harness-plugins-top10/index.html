三天前我上手实测 dsh 的时候，dsh-plugin 话题下是 275 个仓库；写这篇文章的今天，这个数字过了 1400。中间我又把源码从头读了一遍。生态爆发的另一面是泥沙俱下：有给 Web UI 加 2005 年风格广告的整活插件，有「写代码的时候账户不能同时亏钱」的炒股面板，一天写完就没人维护的占了相当比例。

这篇的选稿标准比上一版严了一档：只收高 star 且当天有维护动作的。理由很实际：生态爆发期 star 就是社区的预筛，几百人替你踩过坑的插件，排错时 issue 区里就有答案；而 star 个位数的仓库，哪怕方向再对，装了就是把排错责任全揽到自己身上。10 个插件全部过了 GitHub API 验证，star 数取 2026-08-18 的实测值，当天全部有提交。

按「看 / 点 / 想」三类能力排开。读完之后，你能在 20 分钟内把它们装好，并且知道同类两个插件选哪个、装不上怎么办。

先看全景：

1400 个仓库怎么砍到 10 个

先交代筛法，你可以拿同样的标准自己去筛，不必认我的清单。

第一刀砍 star 不够的。门槛不设固定值，但个位数 star 的直接跳过。不是否认方向，是这个阶段你耗不起排错时间。我上一版清单里有个零 star 的代码地图插件，方向很对，但没人验证过，这次按新标准请出去了。

第二刀砍没有维护动作的。生态爆发期的典型寿命是「发布当天一个 commit，之后永远沉默」。我看仓库先看最近一次提交时间，再看 issue 区有没有人报错、作者有没有回。这次 10 个的最后一次 push 全部在 2026-08-17 或 2026-08-18，跟进 rc 的速度就是生存意愿。

第三刀砍不声明适配版本的。dsh 三天发了 6 个 rc，插件作者如果连「我适配的是 rc 几」都没写，说明他自己也没认真跟。这个信号在 README 第一屏就能看到，两秒钟排除一个。

第四刀砍痛点不明的。这个插件解决什么问题，十秒讲不清的不要。广告插件、炒股面板这类整活作品，star 再高也不是生产力的菜。

四刀下去，1400 个仓库剩下的才有看的价值。10 个里 star 排在末位的也有 158，而且方向稀缺：跨会话记忆这个能力找不出第二个高 star 选项。

你需要先准备好的东西

这篇是系列第三篇，前两篇的结论直接沿用，这里只列清单：

  • Node 22.14+，建议直接上 24 LTS。这是硬门槛：会话持久化插件用了 zstd 压缩，createZstdDecompress 是 Node 22.14 才进的 node:zlib。v22.13 启动会直接崩，而且报错信息完全看不出跟 Node 版本有关。nvm 用户 nvm install 24 切过去
  • dsh 0.1.0-rc.6，我这篇实测的版本。开发者预览期三天发了 6 个 rc，你读到这篇文章时版本多半更新了，命令不变，但插件兼容性要看仓库说明
  • profile 已跑通：npx @deepseek-ai/dsh web 能打开 Web UI、配置过 DeepSeek API key、选过 workspace。没跑通的先回第一篇的安装章节
  • 一个前提认知：插件装进的是 profile，不是全局。web 和 headless 是两棵独立的插件树，给 web 装的插件，headless 跑批用不到，要装两遍

版本门槛过不了的话，后面所有步骤都会以各种奇怪的方式失败，先把 Node 搞对。

装插件的机制：一条命令背后发生了什么

10 个插件的安装命令长得一模一样（例外是 anchored-standard，最后讲），先花两分钟搞懂机制，后面就是体力活。

dsh 的插件安装走 dsh plugin 命令，它把参数原样转发给 profile 目录里的 pnpm。以我实测装一个 JSON 查询工具为例：

dsh plugin --profile web add "github:dsh-external/dsh-tool-json#main"

12 秒装完。这条命令背后做了两件事：往 ~/.dsh/profiles/web/package.json 的依赖表里加了 @deepseek-ai/dsh-tool-json，同时往 dsh.profile.bundles 列表里追了同一个名字。也就是说，一个第三方仓库就是一个 bundle，装进 profile 就成了插件树的一层。

装完必须重启 dsh web，插件树是启动时组装的，不重启不生效。重启后两种验证方式任选：

dsh --dump-config

输出里出现新的一节：

# == @deepseek-ai/dsh-tool-json
- id: tool-json
  name: '@deepseek-ai/dsh-tool-json'

或者在浏览器设置页打开 Plugins → Plugin list，找新插件是不是 Mounted, Enabled 状态。这个 133 个插件挂载的列表长这样：

看类：给模型一双眼睛

DeepSeek 当前的模型默认纯文本。报错截图、设计稿、UI 还原对比，这些全发不了。这类插件补的是最高频的缺口，所以放最前面讲。

modlens：贴图问答，图里有什么给证据

2841 star，视觉类断档领先，README 的口径是「第一个 dsh 视觉插件」，而且野心不止 dsh 一家，它把自己定位成所有终端聊天工具的视觉桥：

dsh plugin --profile web add "github:liustack/modlens#main"

它的取向是「贴图问答」：你把图贴进会话，它读图里的文字和版面，回答时给结构化的 JSON 证据，句子干巴巴的那种它不产。前端排错场景很实用：甩一张控制台报错截图，它把报错文本、所在行号、周边版面结构都摘出来，模型直接拿着定位。

dsh-vision-toolkit：多图问答和 UI 还原

视觉类第二个选择，638 star，同一个作者还维护着回滚类插件，产出稳定：

dsh plugin --profile web add "github:Anionex/dsh-vision-toolkit#main"

它比 modlens 多两块能力：多张图一起问（「这两版设计稿差在哪」这类问题），以及截图到前端 UI 还原：给它一张成品截图，它比对现状给出还原改法。

最省心的是它的免费档：内置免费视觉服务，装完就能用，不需要配任何 API key，限额每台机器每天 300 张图，个人开发者日常排错完全够用。贴图即用也做得干净：在 Web 里贴一张图，纯文本路由自动切到它的 Vision Toolkit 变体，不用手动改路径换模型；缩略图、会话历史、工作区路径都保持原样，Web 里能预览的图，headless 跑批拿到的还是同一份结构化结果。

两个怎么选：要「读图给证据」的富交互选 modlens，要「免费用 + 多图对比 + UI 还原」选 vision-toolkit。前端工程师我倾向后者，UI 还原是它独有的。两个都装也不冲突，工具注册表各占各的位。

点类：让界面和回答都好用

这类解决的是「官方 Web UI 是个毛坯」的问题，五个插件各管一块，互不打架。

dsh-web-ui：看板和 Git 图谱的全家桶

4187 star，第三方增强版全家桶，这个细分的人气王：

dsh plugin --profile web add "github:zhu1090093659/dsh-web-ui#main"

任务看板支持 cron 定时跑任务，Git 图谱把提交历史画成一张网，外加文件树和多款皮肤，甚至能在界面上养宠物。整活归整活，正事它也干。定时任务跑自动化巡检这类场景，看板比命令行直观得多。注意它和官方自带的 Web UI 是两个东西。

dsh-TUI：补上终端

dsh 发布时最大的争议就是没有 CLI，只有一个浏览器界面。ssh 到服务器上就没有浏览器可用，dsh-TUI 是补位之作：Claude Code 风格的全屏 TUI，1837 star：

dsh plugin --profile web add "github:ccch1mneyyy/dsh-cc-tui#main"

鲸鱼顶栏、实时状态、流式思考、双击 Esc 回滚、上下文进度与 TPS 显示，键盘操作跟你在 Claude Code 里的习惯一致。仓库后来从 dsh-cc-tui 改名 dsh-TUI，旧地址会自动重定向，安装命令不受影响。

DSH-better-sidebar：侧边栏装下终端、Git 和子代理

1993 star，omdsh-dev 出品（跟 genui 同一个组织，这个组织这两天连出了两个头部插件）：

dsh plugin --profile web add "github:omdsh-dev/DSH-better-sidebar#main"

它把 Web UI 的侧边栏做成服务化的开放框架：文件管理、编辑预览、内嵌浏览器、真实终端、Git、子代理页面全收进侧边栏，还支持第三方插件注册新页面，README 那句「一套开箱即用的完整工作台」不算吹。装完之后你基本不用离开主界面：模型改了文件，侧边栏里直接看 diff；要跑个命令验证，拉出内嵌终端；想盯子代理在干什么，切到子代理页。窗口管理成本从「三四个窗口来回切」降到「一个窗口里点标签」。

它跟 web-ui 互补，各管一摊：web-ui 管看板和图谱这类「视图」，sidebar 管「操作」。两个都来自活跃作者，装一起没冲突。

dsh-market：把插件市场装进 dsh

863 star，装机顺序上应该排第一个的插件：

dsh plugin --profile web add "github:dsh-market/dsh-market#main"

它把插件市场直接嵌进 dsh：浏览、搜索、一键安装，不用再回终端敲命令。本文后面九个插件，装完它之后都可以从市场里点装。手敲命令的价值在于可复现（脚本里写死仓库地址），日常探索交给市场。

一个版本细节提前说：market 要求 dsh web 0.1.0-rc.6 或更新。宿主版本过旧时它会安静地自我禁用、只在浏览器控制台里留一行提示，省得对着不存在的基础设施硬渲染。所以如果你装完在 Settings 里找不到 Plugin Market 入口，九成是 dsh 本体太旧，先升级再排查。桌面打包版尤其要留意：它自带的 dsh 可能比你 npm 装的旧。这种自我禁用的设计，比一上来就崩的插件体面得多。

dsh-genui：回答里长出能点的组件

192 star，star 不高但方向新，而且是点类里动手改「回答本身」的那一个：

dsh plugin --profile web add "github:omdsh-dev/dsh-genui#main"

模型在回答里声明一个 UI 组件，插件负责渲染，你直接在对话流里跟组件交互。我实际用下来最顺的场景是方案评审：以前让模型给三个技术选型，输出是一长串「方案 A 优点缺点、方案 B 优点缺点」，看到一半就串行；现在三个方案各是一张卡片，标题写一句结论，点开才是论据。组件不是模型瞎画的：插件内置一套受控的组件清单，模型只能从清单里挑，渲染不会跑飞。

为什么「受控清单」这个设计值得单独讲：另一条路是让模型直接生成 HTML 再渲染，自由度高但不可控，模型写错一个标签整个面板就白屏，还有往界面里塞奇怪内容的风险。genui 把自由度收窄到十几种验证过的组件，换来的是稳定性，这跟前端团队不让孩子直接 innerHTML 是同一个取舍。评估一个 GenUI 类插件靠不靠谱，先看它的组件清单是不是闭集，这是这类插件的生命线。

想类：路由、预设和记忆

这类插件不改变界面，改变的是模型「怎么想、想多久、记得什么」。API 账单敏感的，这节优先看。

dsh-routing-suite：按任务自动切思考模式

5437 star，整个 dsh 插件生态的 star 榜第一：

dsh plugin --profile web add "github:yjh051108/dsh-routing-suite#main"

它的思路是研究模型的思考风格：简单任务别让推理模型长篇大论，难任务别让快模型硬上，按任务特征自动选对模式，目标是把任务完成率顶上去。README 里的场景划分值得看一眼：改个文案、补个测试用例这类一眼能想到答案的，走轻量模式省 token；跨模块重构、排一个时隐时现的并发 bug，自动升级到深度思考；中间地带的常规开发任务走标准档。也就是说它管的不只是省钱，还有反面：该想清楚的任务别吝啬推理。

安装时留意它的形态：这是个 injector + 路由标准的套件，装完先用 --dump-config 确认注入器真的挂上了。如果启动后有「注入失败」的日志，多半又是 rc 版本对不上，处理思路同坑一。

dsh-anchored-standard：会话预设标准

3445 star，想类里最「工程」的一个。它不是传统插件，是一套实验性的 agent preset（预设标准）：

它解决的问题：会话一上来就全量工具伺候，模型容易在工具堆里发散。anchored-standard 把会话锚定在 Minimal 条件上：真实的最小工具集、不自动注入上下文；等会话跑稳了，再解锁小型常驻目录，重型 Standard 工具按需放行。翻译成人话：新会话先轻装上阵，证明自己稳定后再逐步加码。四个模式可选（Zero-Anchored / Whoami / Eternal Minimal / Combo），社区评测里有对照结果。

安装不走 dsh plugin add：推荐路径是把仓库交给你的 coding agent，让它按仓库里的安装契约（prefab/AGENT_INSTALL.md）执行，agent 报 INSTALL READY 后在 dsh 里选 Prefab Anchored Standard 预设开新会话；或手动把 preset 目录拷进用户预设目录。这也是「一切皆插件」生态的另一种形态，预设本身也是可分享、可版本化的资产。

dsh-memory-evolve：跨会话的长期记忆

158 star，清单里排在末位，但跨会话记忆这个方向上找不出第二个高 star 选项，且当天有提交：

dsh plugin --profile web add "github:csyangwen/dsh-memory-evolve#main"

官方 Discussions 里呼声最高的需求。dsh 默认每个会话失忆：今天告诉它你的项目规范、技术栈偏好，明天开新会话全部归零。memory 把这些存下来跨会话复用，evolve 版还加了记忆自我审查和技能自我进化。README 的概括很准：让 DSH 里的 AI 越用越懂你，换会话不丢上下文。

体感上这个插件的收益是复利型的：第一周感觉不到差别，第二周开始你会注意到它记住了你的命名习惯、常用目录、踩过的坑；一个月后新开会话的冷启动成本明显变低。跟人带新同事一个道理，交接文档写得再全，也不如他跟你干过两周活。前提是你信任它存的内容，建议先在非敏感项目跑两周。

装完之后的三个组合拳

单个插件解决单个问题，组合起来才有乘法。三个我实际在用的搭配：

账单组合：routing-suite + anchored-standard。 路由管「这个任务用多深的思考」，预设管「这个会话开多少工具」，一个管运行时一个管开局，两层省下来的是同一笔钱。月底看 API 账单，这两层各占一半功劳。上手顺序建议反着来：先装 anchored-standard 把会话的开销压住，跑一周摸清自己的任务分布，再上 routing-suite 做细粒度的模式切换。一上来两个全开，出了效果反而说不清是谁的功劳。

一屏工作台：better-sidebar + web-ui。 sidebar 把文件、终端、Git、子代理收进侧边栏管「操作」，web-ui 用看板和图谱管「总览」。开一个浏览器窗口干完一天的事，Alt+Tab 的次数肉眼可见地降下来。

演示三件套：genui + web-ui + market。 录视频、给团队演示 agent 的时候一起开：模型回答长出能点的面板（genui），任务在看板上一格一格走（web-ui），现场从市场点装一个新插件展示生态（market）。讲十句「agent 能干什么」，不如让这三块屏自己说话。

装不上怎么办：四个高频坑

坑一：peer 依赖缺失警告。 装插件时报 missing peer cordis@rc.x 或 dsh-tools@rc.x。原因：dsh 还在快速迭代，rc 阶段的包依赖版本变动很快，插件作者适配的版本和你本地的对不上。判断技巧：只有 WARN 字样、装完后 --dump-config 里能看到新插件的，属于良性，忽略；装完直接抛 ERR_PNPM、bundles 列表里也没写进去的，是硬失败，别反复重试，先看本地 dsh 版本和插件 README 声明的适配版本差了几个 rc。预览期版本对不上是常态，等一两天作者追上，比你自己改依赖版本靠谱。

坑二：装完没生效。 九成是没重启。插件树是启动时组装的，dsh plugin add 只是改了 profile 目录里的 package.json 和 bundles 声明。重启 dsh web，再用 --dump-config 或设置页 Plugin list 验证挂载状态。另一成是装错了 profile，web 和 headless 是两棵树。

坑三：启动直接崩在插件加载。 报错带 node:zlib does not provide an export named createZstdDecompress。这是 Node 版本问题不是插件问题：22.14 以下必炸，切 Node 24 LTS 解决。这个坑阴在报错信息完全不提版本，新手几乎必踩。

坑四：插件之间冲突，启动变慢。 两个插件都往 Web UI 注入面板、或都接管同一个工具注册表时，轻则界面异常，重则启动失败。处理思路是减法：dsh plugin --profile web remove 一个一个退，定位到冲突源后二选一。另外每装一个插件，启动时的插件树组装就多一分工作量，装到二十个以上启动明显变慢，定期清掉不用的。

还有一个提醒不算坑但更重要：装第三方插件前过一遍源码。dsh 插件可以读写你的文件、跑命令、连网络，awesome-dsh-plugins 目录自己都声明「收录不等于兼容，运行可用不等于安全审计」。十行以内的小插件花两分钟看一遍 apply 里干了什么，大插件看它的 star 增长和 issue 活跃度。预览期的生态，谨慎不亏。

全部命令放一起

按本文顺序，全部命令集中一份，方便直接抄（anchored-standard 走 agent 安装契约，见上文）。先点类：

# 点类：先装市场，后面点装
dsh plugin --profile web add "github:dsh-market/dsh-market#main"
dsh plugin --profile web add "github:zhu1090093659/dsh-web-ui#main"
dsh plugin --profile web add "github:ccch1mneyyy/dsh-cc-tui#main"
dsh plugin --profile web add "github:omdsh-dev/DSH-better-sidebar#main"
dsh plugin --profile web add "github:omdsh-dev/dsh-genui#main"

看类和想类接着来：

# 看类：视觉
dsh plugin --profile web add "github:liustack/modlens#main"
dsh plugin --profile web add "github:Anionex/dsh-vision-toolkit#main"

# 想类：路由、预设、记忆
dsh plugin --profile web add "github:yjh051108/dsh-routing-suite#main"
dsh plugin --profile web add "github:csyangwen/dsh-memory-evolve#main"

# 验证
dsh --dump-config | grep -A2 "dsh-"

插件发现渠道记两个就够：awesome-dsh-plugins 目录（带每日兼容性追踪，1415 个候选里实测 883 个可用）和 dshfind.com（按 star 和周增长排序）。

盯榜单的方法也交代一下，这套我每天花五分钟：dshfind 按「周增长」排，别看总量榜——总量榜头部是先发优势，周增长榜才是此刻社区的注意力在哪。看到新面孔先点进仓库看两样东西：最近一次提交时间和 README 首屏的适配版本声明，两项都过关再花两分钟过一遍源码。这套动作做熟了，你比大多数「收藏了等于装了」的人早一周用上好插件，也早一周避开坏插件。

卸载、回滚与双 profile

装是加法，会用减法才算完整掌控这套体系。

卸载和安装完全对称：dsh plugin --profile web remove @deepseek-ai/dsh-web-ui，注意 remove 接的是包名不是仓库地址，包名在 package.json 依赖表里能看到。卸完同样要重启才真正从插件树里摘掉。

整棵 profile 玩坏了也不怕。profile 就是 ~/.dsh/profiles/web/ 这一个目录，出问题直接删掉重建，或者整个目录拷一份当快照：试一堆不放心的新插件之前先拷一份，炸了原地还原，比逐个卸载快得多。

headless 跑批要复用这套能力的话，把命令里的 --profile web 换成 --profile headless 再跑一遍。两棵树不共享插件，但配置里的 API key 是共用的，不用配两次。我的做法是 web 装全 10 个，headless 只装 memory 和 routing-suite，跑批场景要记忆和省钱，看板和交互面板装了也没人看。

下一步

这 10 个插件解决的是「用」的问题。往下一层是「造」。dsh 的插件开发门槛出乎意料地低：一个插件就是四个具名导出的对象，name、inject、Config、apply，不需要懂 Cordis 全貌就能写出一个能被 agent 调用的工具。系列下一篇就写这个，从 20 行的最小插件开始。

三类框架好用，是因为它把「装插件」从跟风变成了查缺：视觉缺了补看类，界面毛坯补点类，账单和记忆补想类。插件选型的能力，跟你当年选 Webpack 还是选 Vite 是同一种能力——在爆发期的生态里快速识别哪些值得投入。

这套「识别哪些值得投入」的判断法，我在 Claude Code 插件上用一个月真实任务完整跑过一遍，留 6 删 6 的过程写在插件实测淘汰清单里，判据可以平移到 dsh 生态。
