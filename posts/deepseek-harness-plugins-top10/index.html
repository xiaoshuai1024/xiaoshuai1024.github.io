三天前我上手实测 dsh 的时候，dsh-plugin 话题下是 275 个仓库；写这篇文章的今天，这个数字过了 1400。中间我又把源码从头读了一遍。生态爆发的另一面是泥沙俱下：这里面有给 Web UI 加 2005 年风格广告的整活插件，有「写代码的时候账户不能同时亏钱」的炒股面板，一天写完就没人维护的占了相当比例。

这篇文章的目标很具体：读完之后，你能在 20 分钟内把 10 个真正值得装的插件装好，并且知道先装哪个、后装哪个、装不上怎么办。筛选标准不是 star 数，是「解决什么痛点」——没有明确痛点的，再火也不进清单。

先看全景，10 个插件按三档排：

1400 个仓库怎么砍到 10 个

先交代筛法，你可以拿同样的标准自己去筛，不必认我的清单。

第一刀砍没有维护动作的。生态爆发期的典型寿命是「发布当天一个 commit，之后永远沉默」。我看仓库先看最近一次提交时间，再看 issue 区有没有人报错、作者有没有回。三天内没有任何动静的仓库，装了就是把排错责任揽到自己身上。

第二刀砍不声明适配版本的。dsh 三天发了 6 个 rc，插件作者如果连「我适配的是 rc 几」都没写，说明他自己也没认真跟。这个信号在 README 第一屏就能看到，两秒钟排除一个。

第三刀砍痛点不明的。回到那个标准：这个插件解决什么问题，一句话说不清的不要。「一切皆插件」的架构降低了写插件的门槛，也就降低了写玩具的门槛——dsh-ads 给 Web UI 加 2005 年风格广告，dsh-stock-market 的卖点是「写代码的时候账户不能同时亏钱」，这类整活作品 star 再高也不是生产力的菜。

三刀下去，1400 个仓库剩下的百来个才有看的价值。下面的 10 个，是从这百来个里按「解决真实痛点 + 维护活跃」再排出来的。

你需要先准备好的东西

这篇是系列第三篇，前两篇的结论直接沿用，这里只列清单：

  • Node 22.14+，建议直接上 24 LTS。这是硬门槛：会话持久化插件用了 zstd 压缩，createZstdDecompress 是 Node 22.14 才进的 node:zlib。v22.13 启动会直接崩，而且报错信息完全看不出跟 Node 版本有关。nvm 用户 nvm install 24 切过去
  • dsh 0.1.0-rc.6，我这篇实测的版本。开发者预览期三天发了 6 个 rc，你读到这篇文章时版本多半更新了，命令不变，但插件兼容性要看仓库说明
  • profile 已跑通：npx @deepseek-ai/dsh web 能打开 Web UI、配置过 DeepSeek API key、选过 workspace。没跑通的先回第一篇的安装章节
  • 一个前提认知：插件装进的是 profile，不是全局。web 和 headless 是两棵独立的插件树，给 web 装的插件，headless 跑批用不到，要装两遍

版本门槛过不了的话，后面所有步骤都会以各种奇怪的方式失败，先把 Node 搞对。

装插件的机制：一条命令背后发生了什么

10 个插件的安装命令长得一模一样，先花两分钟搞懂机制，后面就是体力活。

dsh 的插件安装走 dsh plugin 命令，它把参数原样转发给 profile 目录里的 pnpm。以我实测装一个 JSON 查询工具为例：

dsh plugin --profile web add "github:dsh-external/dsh-tool-json#main"

12 秒装完。这条命令背后做了两件事：往 ~/.dsh/profiles/web/package.json 的依赖表里加了 @deepseek-ai/dsh-tool-json，同时往 dsh.profile.bundles 列表里追加了同一个名字。也就是说，一个第三方仓库就是一个 bundle，装进 profile 就成了插件树的一层。

装完必须重启 dsh web——插件树是启动时组装的，不重启不生效。重启后两种验证方式任选：

dsh --dump-config

输出里出现新的一节：

# == @deepseek-ai/dsh-tool-json
- id: tool-json
  name: '@deepseek-ai/dsh-tool-json'

或者在浏览器设置页打开 Plugins → Plugin list，找新插件是不是 Mounted, Enabled 状态。这个 133 个插件挂载的列表长这样：

装第三个插件时会遇到的 peer 依赖警告，放到文末报错排查一起讲。

第一档：不装难受，先解决 dsh 的明显缺口

这一档解决的是「官方没做、但你天天要用」的问题。按优先级从上往下装。

插件 1：dsh-cc-tui，给 dsh 补上终端

dsh 发布时最大的争议就是没有 CLI，只有一个浏览器界面。它是常驻本地服务的形态，日常用没问题，但 ssh 到服务器上就没有浏览器可用了。dsh-cc-tui 是补位之作，Claude Code 风格的全屏 TUI，发布当天冲到 125 star，截稿时已经涨到 1.4k，是这批插件里热度最高的。仓库后来改名成了 dsh-TUI，旧地址会自动跳转，安装命令不受影响：

dsh plugin --profile web add "github:ccch1mneyyy/dsh-cc-tui#main"

预期结果：重启后 dsh 命令多了 TUI 入口，全屏终端界面，键盘操作，体验对齐你在 Claude Code 里的习惯。服务器场景和浏览器没开的场景，全靠它。

插件 2：dsh-turn-rewind，AI 改错了就回滚

agent 跑飞了、把文件改错了，以前的办法是 git checkout 手动恢复。turn-rewind 把「撤回上一轮修改」做成一个操作，按轮次回滚。它管的不是 git 提交，是 agent 的 turn——模型每一轮动了哪些文件，撤哪轮清清楚楚。

dsh plugin --profile web add "github:Anionex/dsh-turn-rewind#main"

预期结果：会话里出现 rewind 操作入口，agent 改错文件后不用再进 git 手动对账。

插件 3：dsh-memory，跨会话的长期记忆

官方 Discussions 里呼声最高的一个。dsh 默认每个会话失忆：今天告诉它你的项目规范、你的技术栈偏好，明天开新会话全部归零。dsh-memory 把这些存下来跨会话复用。注意一个变化：最初收录时的 dsh-external/dsh-memory 仓库已经迁移，作者把基础记忆和自我进化合并成了 dsh-memory-evolve 一个包，116 star，安装以它为准：

dsh plugin --profile web add "github:csyangwen/dsh-memory-evolve#main"

预期结果：新会话里 agent 能引用之前会话沉淀的信息，不用重复交代背景。evolve 版在基础记忆之上加了记忆自我审查和技能自我进化，功能多但装卸依然干净，卸载即净。长期记忆类插件的前提是你信任它存的内容，建议先在非敏感项目跑两周。

体感上这个插件的收益是复利型的：第一周感觉不到差别，第二周开始你会注意到它记住了你的命名习惯、常用目录、踩过的坑；一个月后新开会话的冷启动成本明显变低。跟人带新同事一个道理——交接文档写得再全，也不如他跟你干过两周活。

这一档装完，dsh 才算一个顺手的日常工具。下一档是让它比原来更强。

第二档：装完变强，给模型补上没有的能力

插件 4：dsh-vision，让 DeepSeek 看图

DeepSeek 当前的模型默认纯文本。报错截图、设计稿、UI 还原对比，这些全发不了。dsh-vision 补上看图能力，仓库现在挂在作者个人账号 william-jin-cmu 下，旧地址同样自动跳转：

dsh plugin --profile web add "github:william-jin-cmu/dsh-vision#main"

预期结果：会话里能直接贴图，模型描述图片内容。前端 Debug 场景——甩一张控制台报错截图让它直接定位——是最高频用法。多模态路由的配置在 $DSH_HOME/settings.yaml 里给对应模型加 input: [text, image]，粒度细到按模型开关。

一个使用细节：给手敲添加的模型配多模态时，默认按纯文本处理，必须手动改 settings.yaml 才认图。从 provider 目录里用「Fetch available models」拉进来的模型没这个问题。这个细节第一篇实测时踩过，这里直接替你踩平。

插件 5：dsh-role-router，双模型路由

一件事两类模型各干一半：规划任务交给推理模型想清楚，执行交给快模型跑。token 成本降下来，质量不掉。这跟我之前写的 Claude Code 计划模式是一个思路，区别是 dsh 把「哪个环节用哪个模型」也做成了可替换的插件：

dsh plugin --profile web add "github:SnowAmberX/dsh-role-router#main"

预期结果：复杂任务先出规划再执行，两阶段明显分开。API 账单敏感的先装这个，它省的是真金白银。

插件 6：dsh-openwolf，给模型一张代码地图

模型读大仓库靠 grep 瞎摸，token 花得多还不一定找对。openwolf 自称「code-map 第二大脑」，给整个仓库建 symbol 索引——调用层级、继承树，模型先查地图再动代码：

dsh plugin --profile web add "github:hawk2048/dsh-openwolf#main"

预期结果：模型定位函数引用、追调用链的准确率明显上升，长会话的 token 消耗下降。仓库越大收益越明显，小项目可以缓装。

值得知道它为什么省 token：裸用 dsh 时模型了解你的仓库靠读文件，一次跨模块的调用链追踪要把七八个文件读进上下文，几十 k 的 token 就没了。symbol 索引把「哪个函数在哪、被谁调用」压成结构化数据，模型查一次索引顶过去读一堆文件。这是索引换上下文的思路，跟 IDE 的 workspace index 是一回事，只是消费方从你变成了模型。

插件 7：dsh-session-search，跨工具搜会话

你跟 AI 聊过的东西散落在各家工具里，找一条历史结论要挨个翻。session-search 把 dsh、Claude Code、Codex、OpenCode 的会话拢到一处全文搜索：

dsh plugin --profile web add "github:Tieboyh/dsh-session-search#main"

预期结果：一个搜索框出四家工具的历史对话。「上个月让 Claude 改的那个正则在哪」这类问题，一搜就有。这个插件的取向很有代表性——官方没做的事，生态在做。

第三档：炫给别人看，演示和迁移场景

这一档不影响日常开发，但演示、录屏、写文章的时候效果直接。另外有个隐藏价值：给团队或读者演示 agent 工作原理时，可视化面板比黑盒终端的说服力高一个档位——你讲「agent 会自己开浏览器查资料」，不如当场让它开给你看。

插件 8：dsh-web-ui，看板和 Git 图谱

任务看板支持 cron 定时跑任务，Git 图谱把提交历史画成一张网，外加文件树和 7 款皮肤。注意它和官方自带的 Web UI 是两个东西，这是第三方增强版全家桶：

dsh plugin --profile web add "github:zhu1090093659/dsh-web-ui#main"

预期结果：主界面多出看板和图谱视图。定时任务跑自动化巡检这类场景，看板比命令行直观得多。

插件 9：reef，模型操控浏览器

WebUI 里内嵌一个真实浏览器，模型实时开页面、滚动、点击、填表单，全程你盯着。reef 是这套场景的全家桶实现，浏览器自动化之外还带 MCP Server 和自动评审。查资料、对照设计稿改样式这类任务，比让它靠 fetch 猜页面结构强一个量级：

dsh plugin --profile web add "github:huey1in/reef#main"

预期结果：会话里模型发起浏览操作，右侧面板实时展示页面。同类的还有 dsh-kimi-browser，二选一即可。

插件 10：claude-bridge，把 Claude Code 的积累整个搬过来

压轴给从 Claude Code 迁移过来的人。你最值钱的资产不是工具本身，是积累的 CLAUDE.md、Skills、历史记忆。claude-bridge 把这些整套搬进 dsh，迁移成本直接清零：

dsh plugin --profile web add "github:YYTbit/dsh-plugin-claude-bridge#main"

预期结果：dsh 会话能直接使用你 Claude Code 里的项目规范和 Skill，不用从头教。

我没急着全切到 dsh，目前是 Claude Code 主力、dsh 并行试用——这个 bridge 插件就是并行期的桥梁，两边共用同一套规范资产。

装完之后的两个组合拳

单个插件解决单个问题，组合起来才有乘法。两个我实际在用的搭配：

大仓库重构：openwolf + role-router。 先让 openwolf 建好索引，再走 role-router 的规划阶段——推理模型拿着代码地图拆任务、排依赖，执行阶段快模型照单跑。重构最贵的不是执行，是想清楚动哪里、什么顺序动，这个组合正好把「想」和「做」分开计价。

规范资产化：claude-bridge + memory。 CLAUDE.md 里的项目规范先搬进来，memory 负责在新会话里持续生效，之后你在 dsh 里积累的新偏好又会被 memory 沉淀下来。跑一个月，你就有了一份两边通用、越用越准的项目记忆。这两个插件管的是同一件事的两端：一个管存量迁移，一个管增量积累。

装不上怎么办：三个高频坑

坑一：peer 依赖缺失警告。 装插件时报 missing peer cordis@rc.x 或 dsh-tools@rc.x。原因：dsh 自己还在快速迭代，rc 阶段的包依赖版本变动很快，插件作者适配的版本和你本地的对不上。处理：装完能跑就先不管；跑不起来就到插件仓库看 issue，一般作者会在几天内跟进新 rc。

补充一个判断技巧：警告分两种。只有 WARN 字样、装完后 --dump-config 里能看到新插件的，属于良性，忽略即可；装完直接抛 ERR_PNPM、bundles 列表里也没写进去的，是硬失败，别反复重试，先看本地 dsh 版本和插件 README 声明的适配版本差了几个 rc。预览期版本对不上是常态，等一两天作者追上，比你自己改依赖版本靠谱。

坑二：装完没生效。 九成是没重启。插件树是启动时组装的，dsh plugin add 只是改了 profile 目录里的 package.json 和 bundles 声明。重启 dsh web，再用 --dump-config 或设置页 Plugin list 验证挂载状态。另一成是装错了 profile——web 和 headless 是两棵树。

坑三：启动直接崩在插件加载。 报错带 node:zlib does not provide an export named createZstdDecompress。这是 Node 版本问题不是插件问题，前面前提一节讲过：22.14 以下必炸，切 Node 24 LTS 解决。这个坑阴在报错信息完全不提版本，新手几乎必踩。

坑四：插件之间冲突，启动变慢。 生态爆发期的隐藏问题：两个插件都往 Web UI 注入面板、或都接管同一个工具注册表时，轻则界面异常，重则启动失败。处理思路是减法——dsh plugin --profile web remove 一个一个退，定位到冲突源后二选一。另外每装一个插件，启动时的插件树组装就多一分工作量，装到二十个以上启动明显变慢，定期清掉不用的，别把插件树养成依赖沼泽。

还有一个提醒不算坑但更重要：装第三方插件前过一遍源码。dsh 插件可以读写你的文件、跑命令、连网络，awesome-dsh-plugins 目录自己都声明「收录不等于兼容，运行可用不等于安全审计」。十行以内的小插件花两分钟看一遍 apply 里干了什么，大插件看它的 star 增长和 issue 活跃度。预览期的生态，谨慎不亏。

全部命令放一起

按本文顺序，全部命令集中一份，方便直接抄：

# 第一档：补缺口
dsh plugin --profile web add "github:ccch1mneyyy/dsh-cc-tui#main"
dsh plugin --profile web add "github:csyangwen/dsh-memory-evolve#main"
dsh plugin --profile web add "github:Anionex/dsh-turn-rewind#main"

# 第二档：补能力
dsh plugin --profile web add "github:william-jin-cmu/dsh-vision#main"
dsh plugin --profile web add "github:SnowAmberX/dsh-role-router#main"
dsh plugin --profile web add "github:hawk2048/dsh-openwolf#main"
dsh plugin --profile web add "github:Tieboyh/dsh-session-search#main"

# 第三档：演示与迁移
dsh plugin --profile web add "github:zhu1090093659/dsh-web-ui#main"
dsh plugin --profile web add "github:huey1in/reef#main"
dsh plugin --profile web add "github:YYTbit/dsh-plugin-claude-bridge#main"

# 验证
dsh --dump-config | grep -A2 "dsh-"

插件发现渠道记两个就够：awesome-dsh-plugins 目录（带每日兼容性追踪）和 dshfind.com（按 star 和周增长排序）。装完这 10 个，你的 dsh 在终端、记忆、视觉、规划、搜索五个维度都不再是裸机状态。

卸载、回滚与双 profile

装插件是加法，会用减法才算完整掌控这套体系。

卸载和安装完全对称：dsh plugin --profile web remove @deepseek-ai/dsh-memory，注意 remove 接的是包名不是仓库地址，包名在 package.json 依赖表里能看到。卸完同样要重启才真正从插件树里摘掉。

整棵 profile 玩坏了也不怕。profile 就是 ~/.dsh/profiles/web/ 这一个目录，出问题直接删掉重建，或者整个目录拷一份当快照——试一堆不放心的新插件之前先拷一份，炸了原地还原，比逐个卸载快得多。

headless 跑批要复用这套能力的话，把上面命令里的 --profile web 换成 --profile headless 再跑一遍。两棵树不共享插件，但配置里的 API key 是共用的，不用配两次。我的做法是 web 装全 10 个，headless 只装 memory 和 openwolf——跑批场景要记忆和代码地图，看板和浏览器面板装了也没人看。

下一步

这 10 个插件解决的是「用」的问题。往下一层是「造」：dsh 的插件开发门槛出乎意料地低——一个插件就是四个具名导出的对象，name、inject、Config、apply，不需要懂 Cordis 全貌就能写出一个能被 agent 调用的工具。系列下一篇就写这个，从 20 行的最小插件开始。

在「前端 → 全栈 → AI 开发」的成长线上，这一篇的位置是把新工具用顺手——插件选型的能力，本质上跟你当年选 Webpack 还是选 Vite 是同一种能力：在爆发期的生态里快速识别哪些值得投入。前两篇在这里：发布当天的上手实测，80MB 源码的完整深读。
