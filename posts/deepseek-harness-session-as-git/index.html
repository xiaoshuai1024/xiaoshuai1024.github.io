Agent 改炸了怎么救？DeepSeek Harness 把会话当 git 用

xiaoshuai1024 included in AI 开发

让 Agent 跑一个真实任务，最怕的不是它慢，是它自信。第十七轮修改把你那段能跑的代码改成了不能跑的版本，你盯着屏幕想按 Ctrl+Z，发现这个键只对你的编辑器有效，Agent 在磁盘上做的每一笔改动都不会退回去。

我在读 DeepSeek Harness（dsh）源码的时候意识到，它的作者们把这个场景当成了一等公民来设计。解决方案写在架构文档第一页：产品的每一部分都是插件，包括会话日志本身。而会话日志的设计，用过 git 的人一眼就能认出来。

直接给结论：dsh 把整个会话做成一条只追加的事件日志，模型每轮看到的消息历史都是这条日志当场投影出来的。于是「回到过去」不需要备份，只需要换个投影方式或者从任意一轮重新分叉。

一、会话是一条日志，不是聊天记录

打开 docs/subsystems/session.zh.md 第 5 行，原话是：Session 是一份由类型化 SessionEvent 组成的仅追加日志，是智能体完整交互历史的单一真源。LLM 消息历史从日志派生而来，从不单独存储；回放即从同一组事件重新派生。

这句话有三层信息，值得一句句抠。

第一层，「仅追加」。事件只能往尾部加，编号 seq 单调递增，接口上不存在修改和删除旧事件的路径。你在界面上打的每个字、模型的每次回复、每一次工具调用及其返回值，落盘时全部是事件。这份设计我在源码深读那篇里从 packages/core/session/src/index.ts 一路验证过：seq 校验做在持久化层，乱序事件直接拒绝写入。

第二层，「单一真源」。没有第二份数据。模型看到的对话、界面渲染的历史、调试时翻的记录，源头都是同一条日志。

第三层，「派生」。这是整套机制最反直觉的地方：你以为模型在「聊天的上下文里续聊」，实际上每一轮请求的消息数组都是当下从日志重新算出来的。会话不是一个容器，是一台能随时重演的机器。

二、两套视界：模型看投影，你看日志

既然日志不可改，那上下文压缩怎么办？把旧对话压成摘要，不就等于改了历史吗？

dsh 的解法是在日志上面架一层投影。deriveMessages() 不直接遍历日志，而是遍历 session.surface.nodes 这个投影结构。投影的更新原语只有一个：

{ op: 'replace', start, end }

含义是：把 seq 区间 [start, end) 的事件替换成新内容。执行之后发生三件事：新内容写进折叠结果 folded.replacements[]，被替换的原事件记入 shadowedSeqs，日志本体一个字节都不动。

于是出现了一个很干净的分工。模型请求时走投影，看到的是「当前视界」：摘要替代了旧对话，窗口不爆。你想审计完整历史时读日志本体，被替换的原文全都在，界面上照样能翻。一套数据，两种视界，中间靠 replace 操作切换。文档把这层叫 surface 回放，配合上一节说的派生机制，压缩这件事从「危险地改历史」变成了「安全地换视界」。

三、fork：从任意一轮重新分叉

杀手锏在 fork()。签名带三个关键字段：parentSession 指向母会话，seedLength 标记种子长度，delegationDepth 记录委派层级。它的语义是：从母会话的第 k 个事件处截断，前面全部事件作为种子送进新会话，后面的一概不带。

这就是 git 里 branch 的动作。项目在第十七轮被改炸了？回到第十五轮 fork 一个新会话，三条路线各跑各的。老的留在原地可以对照 diff，新的随便试错，两边互不污染。

有一个细节能看出这套 API 的工程成熟度：OPEN_TURN 守卫。turn 进行到一半时不允许 fork，因为此时会话尾部是一个没有闭合的状态，从这里截出的种子是个半成品， fork 出来的子会话起点就是脏的。守卫强制你等当前轮次闭合再操作，宁可慢一步，不发半棵树。种子边界的处理还有配套语义：新会话自己的第一次实时写入之前，会追加一个只日志事件，标记边界位置 firstLiveSeq（session.zh.md 的 SessionHeader 一节）。恢复、fork、回放三种来源的种子在这里统一收口。

四、一次 fork 在数据层的六个时刻

第一与第二个时刻发生在校验层。调用方给出源会话与可选 boundary，截取截至该 seq（含）的前缀，缺省取当前最后一个事件；接口随即检查所选前缀的结尾，若停在未闭合的轮次里就整个拒绝操作，拒绝永远先于静默截断（docs/subsystems/session.zh.md 的活跃会话 fork API 一节）。层次关系也交代一句：ctx.sessions.create(id, { seed }) 是底层的回放与 fork 原语，fork() 是包装在其上的策略 API，后者补齐了校验与元数据继承。

第三个时刻是深拷贝。通过校验的种子事件被深克隆进新的内存会话；第四个时刻落在元数据：parentSession 记下血统，seedLength 固定继承长度，cwd 从母会话照抄。显式 boundary 的表达力比直觉宽，既可以从更早的 turn/end 处分叉，也可以越过一个尚未闭合的轮次、停在更晚的独立纯日志事件上，源会话不必为此停下来。

第五个时刻是立界碑。子会话第一次实时写入之前，构造函数追加一个仅日志的 session/end-seed 事件，其位置就是 firstLiveSeq 的持久投影；界碑之前的 seq 全部来自种子，属于一个已经结束的生命周期。它存在的理由相当锋利：种子历史与实时工作在字节层面完全相同，一条没有配对的 compaction/start 无法自证是崩溃残留还是压缩正在进行，而 end-seed 之前的开放标记可以被直接判为已死。

第六个时刻回到权限归属。end-seed 的合法写入方只有 Session 构造函数一处；核心只写不读，括号词汇的解释权仍在各插件手里，所以崩溃修复只会补轮次、步骤与工具三类边界，从不会代笔 compaction/* 的闭合。并发 fork 同一段历史时，文档也直说还需要日志之外的存活信号配合，一个日志文件解决不了全部问题。

五、断电与升级：比你想的皮实

改炸可以 fork，但进程本身崩了呢？

持久化层 packages/context/session-persistence/coordinator.ts 里的 PersistenceCoordinator（1361 行）给了三层保险。写盘是 write-behind 模式，200ms 攒一批再落，性能和安全的平衡点压得很低；每批写入带严格 seq 校验，缺号乱号拒绝入库。崩溃恢复时最巧的是 interruptedTurnClosers：异常退出会把轮次的闭合事件吞掉，恢复逻辑扫到没闭合的 turn 就自动补一条闭合事件进去——日志永远是自洽的。这条合成事件的 reason 叫 interrupted，文档特意注明轮次结束原因里仅此一个来自循环之外，来历在类型层面就可辨认（docs/subsystems/persistence.zh.md）。

第三层保险针对代码升级。热更新之后新旧两个版本的代码操作同一个日志文件，靠的是「前缀收养」：新代码接管旧代码写到一半的前缀，接着追加。会话跨越代码版本保持连续，重启 dsh 不等于丢会话。

落盘格式是两个可互换后端的对照题。JSONL 后端把每个会话存成一份仅追加的逻辑日志，默认写成带 checksum 的连续 Zstandard 帧，也能配置为原始行；SQLite 后端基于 node:sqlite，每个 SessionEvent 一行，行字段覆盖 seq、类型、时间、数据、来源引用与 surface 元数据，与事件一一对应，不存在需要保持同步的第二套 schema（docs/subsystems/persistence.zh.md）。应用在组合时挑一个，上层代码感知不到差别。

写失败同样有章法。后台写入被拒绝时，对应事件保留、自动重试暂停，新事件开启新窗口；显式 flush 会立即重试，并通过 agent/error 与 logger 报告失败，失败永远不会被记录成已闭合轮次之后的会话事件（persistence.zh.md flush 一节）。批处理窗口由第一个待处理事件开启固定截止时间，后来者加入而不推迟窗口，延迟上界因此可推算。

格式演进另有专门一道闸。后端用 SessionFormatUnsupportedError 与「损坏」划清界限：header 版本比当前构建更新时，提示去升级 harness；更旧则声明本构建没有升级路径。词汇表之外的未知事件类型同样拒收，除非信封自带 ignorable 标记，理由写在文档里：静默跳过一个不认识的必需事件，可能改变日志其余部分的解读方式。

这三层合起来回答了开头那个 Ctrl+Z 的焦虑——数据层面的事故已经被结构性防住了，剩下的只有磁盘损坏这种物理级的意外。

六、一条总线带出一串读模型

总线视角值得单独立起来。架构文档把事件分成三个域：会话事件是追加进日志的持久事实，重新加载之后依然成立；agent/* 事件携带活的 Agent 对象，用来观察或拦截进行中的工作；能力事件（fs/、tools/、telemetry/*）无需导入循环就能给接缝挂策略。源码初见那篇给过概括：扩展点比配置更底层，patch 动参数，事件动行为。

session/event 的广播是整套设计的汇合点。事件矩阵里监听它的包多达 23 个：持久化插件复制落盘，投影单元折叠界面状态，遥测侧去标识后外发，tokenMeter 维护测量折叠区，标题生成器挑时机起名字（docs/event-producer-consumer.zh.md）。一份日志同时供给持久化、投影、回放、fork 与恢复，架构文档把这层契约压成短句：模型可见即已记录。

日志旁边站着三个专职读模型。session-query 用 sqlite 索引查询事件流，结果按 current、shadowed、log-only 三档标注时效，「还在视界里的」「被压缩遮蔽的」「纯日志的」分得清清楚楚；session-reference 把表层里有界的对话快照投成持久的不可信消息上下文，前言声明内容不可信以隔离注入；session-telemetry 捕获会话记录、去标识后交给外部后端，输出直接离开进程（capability-seams 服务表）。记忆在 dsh 里由此有了确定形态：对日志的受控检索加受控注入。

这三个读模型自己也站在接缝上。查询、引用与遥测各占一条独立的服务行，消费同一份事件流却互不牵扯，换掉其中任何一个实现，另外两条链路都不必跟着改动。「一切皆插件」的外延在这里一直伸到了读侧。

七、和 git 摆在一起看

你熟悉的 gitdsh 的对应物
commit 历史，append-only只追加 SessionEvent 日志
checkout 旧提交投影 replace 出的历史视界
branchfork() 加 seedLength
protected branch 规则OPEN_TURN 守卫
reflog 找回丢的操作shadowedSeqs 影子区

类比的尽头还是要回到差异：git 保护的是代码文本，dsh 保护的是「模型当时看到了什么」。后者就是出事时你最想知道的东西：复盘 Agent 的行为，靠的不是记忆里的对话截图，是那条谁也没动过的原始日志。掘金社区在拆解 dsh 时也提到同一点：出了岔子想复盘，重放出来的上下文必须和当时模型实际看到的完全一致，这正是事件日志存在的理由。

差异不止于保护对象，实现深度也不同。git 的 reflog 记录的是引用移动，dsh 的 shadowedSeqs 直接保存被遮蔽内容的坐标；stash 要手动创建，投影 replace 自动发生且留有完整的审计轨迹；protected branch 依赖人工配置，OPEN_TURN 守卫则长在数据结构内部。对照表里的每一行，实现层都有一句对应的话撑着。

我的最终看法是：把会话当 git 存，不是炫技式的设计趣味，是被「AI 改炸项目」这个高频事故倒逼出来的工程底线。传统应用丢了状态就丢了，而 Agent 的错误是有惯性的，它会基于自己上一轮的错误输出继续推理。能回到任意一轮重来，才谈得上放心地把大任务交给它。
