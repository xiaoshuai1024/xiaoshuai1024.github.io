你敢让 AI 通宵修代码吗：夜间 daemon 的三条边界与 8 步回归

问你一个问题：你睡觉的这几个小时，你的代码在干嘛？我的在打工，而且干得比白天还规矩。每天凌晨，一个夜间巡检 daemon 自己拉最新代码、跑 8 步全量测试，挂了就让 Claude Agent 读日志、找根因、切分支、修代码，修完回归验证，通过才提 MR——然后去飞书叫醒我。

这套东西跑了半年，第二天早上我只剩三种开场：全过，接着睡；已修复，花 20 分钟看 MR；修不动了，才真正动手。没有第四种「昨晚合的代码炸了」。但今天这篇不讲怎么搭，搭建过程在之前那篇拆过了，这篇讲更要紧的事：凭什么敢让它通宵无人值守。答案是三条边界，每一条都是拿真实教训换的。

什么叫夜间巡检？一个专上夜班、全年无休的守护进程，工资是电费。不领工资的员工随叫随到，可没人管它怎么干活，所以边界比能力重要，这是全文的主张。不领工资的员工最大的好处是随叫随到，最大的风险是没人管它怎么干活。所以边界比能力重要，这是全文的主张。

一、边界一：你的工作区它碰不得

第一个要防的，是 daemon 伤到开发者本人。巡检要切分支、拉代码，而你下班时可能正卡在某个 feature 分支上，改到一半的东西摊在工作区。多少夜间脚本在这一步变成了事故：早上来一看，分支被切走了，改动没了。

这类事故其实在圈子里有个固定剧本：夜间任务切走分支、开发者的未提交改动被冲掉、第二天找回损失的时间比写脚本的时间还长。所以我的做法分三层。第一层，动手之前先记现场：把每个仓库当前的分支名写进状态文件，这一步是后面一切还原的依据。第二层，切 dev 之前，把你没提交的改动用 stash 包起来。这里有个值得展开的选择：放着自动 commit 不用，为什么选 stash？commit 会往你的分支塞一个 wip 提交，就算后面能撤，reflog 里也留了痕，提交树被搞乱；stash 是 Git 原生暂存，用完 pop 回来，干干净净。源码注释里写得直白：避免污染任何分支的历史。翻译成人话：它帮你收拾屋子，但绝不碰你抽屉里的私人物品。

第三层，跑完必还原。不管测试过没过、修没修，最后一定把每个仓库切回最初记录的分支，fix 分支清理掉，后端进程停掉，锁释放。脚本被正常终止时 trap 也会补执行；退出、中断、终止信号三类事件都挂了清理逻辑，正常用到的路径全覆盖。第二天你打开电脑，工作区和你昨晚离开时一模一样，分支还是你下班时那个分支，一行都没少。

这层边界里还藏着一个可爱的工程细节：抢锁。daemon 要防两个实例同时跑，我没用 flock（跨平台麻烦），用的是 mkdir 当锁——同一个目录下 mkdir 要么成功要么失败，天生原子。更妙的是僵尸锁自愈：每次抢锁先检查上一个持有者的进程还活着没，进程死了锁没清，就自动清掉重抢。连报错文案都给人留了退路，告诉你手动删除哪个目录。自动化系统的每一层，都得假设上一层的操作者是个会手滑的人类，包括深夜里那个可能迷迷糊糊爬起来敲命令的你自己。

stash 这条路还有个不起眼的前置动作：执行前先确认状态目录在 .gitignore 里。漏了这步会出什么事故？日志目录会被 stash 一起打包带走，接下来脚本想写状态文件，写不进去，整条链路跟着哑火。这种坑不踩不知道，踩过才会写进代码。边界设计的难度从来不在主路径，在主路径旁边这些不起眼的小沟坎。

顺带一个反例警示：这套 trap 机制拦得住 Ctrl-C、拦得住 kill，唯独拦不住 kill -9。那是操作系统级的强制终止，任何脚本逻辑都来不及执行。所以停 daemon 用 stop 命令或者普通 kill，永远别上来就 kill -9；真被强杀了，去状态目录里看当时记录的分支名，手动切回去。自动化再周全，也要给操作系统留面子。

二、边界二：修好了也不许合并

第二条边界管的是 Agent 的手。修复流程长这样：读日志、定位根因、从 dev 切出 fix 分支、改代码。到这里不算完，最关键的一步在后面——把 fix 分支拉回来，跑完整 8 步测试回归，全绿才由脚本提 MR。注意主语：提 MR 的是脚本，从来就不是 Agent。

为什么合并不给 Agent？两个原因，一个比一个疼。第一个是流程原因：建 MR 是流程动作，改代码是技术动作，两件事的判断标准不同。Agent 自己建 MR，等于自己修自己验收，它完全可以跳过验证直接把代码推上主线。把「建 MR」这个动作从它手里拿走，验收就必须经过外部脚本这道关，想跳都跳不了。

第二个原因更疼，是拿真实事故换的。早先版本图省事，Agent 修完只重跑失败的那一步：后端单测挂了，修完只重跑后端单测，过了就提 MR。有一次它修后端单测时改了一个公用工具类的方法签名，后端确实过了，但运营端 E2E 依赖这个签名，MR 合进 dev，第二天运营 E2E 全红。根因想明白了很朴素：Agent 的视野是局部的，它只看了失败步骤的日志，它的改动影响面却是全局的。它不会主动检查副作用，但完整 8 步回归会替它检查。AI 修的代码，也得过 AI 自己设的关。

这也是 8 步全量测试存在的真正意义。8 步里有后端单测、集成、运营单测、运营 E2E、前端单测、H5 E2E、小程序编译，能并行的并行（后端和前端单测一起跑），任何一步挂，后面不跑，时间省下来留给修复。具体长这样：

步骤内容命令
1-2后端单测、集成测mvn test / mvn verify
3-4前端单测、运营单测（并行）pnpm test
5拉起后端给 E2E 用mvn spring-boot:run
6-7运营 E2E、前端 H5 E2Epnpm run test:e2e
8小程序编译验证pnpm run build:mp-weixin

防回归靠的不是聪明，是笨功夫：把视野从「一个点」强行拉到「整个系统」。每步挂 30 分钟超时，超时的跨平台适配还颇有年代感：有 timeout 命令用 timeout，macOS 上换 gtimeout，实在没有就拿 perl 的 alarm 顶上。跨平台 shell 脚本的一多半代码量，都花在这种「有没有那个命令」的适配上。

给 Agent 的修复指令里同样埋着边界，四条硬约束写死在 prompt 里：只修能明确归因的代码问题；定不下根因的输出说明，不许强行改；不许动测试断言（除非断言本身写错了）；不许自己建 MR。最后一条前面讲过了，第三条值得多说一句：测试挂了有两种可能，代码错了，或者断言写错了。允许 Agent 随手改断言，等于允许它把题目改成自己会做的样子，那测试就从量具变成了橡皮图章。

工具权限也按边界分配。修复时给 Read、Write、Edit、Bash 这些动手的权限；另有会话级的 review 环节只给只读权限，它想改代码都改不了。能动手的和能说话的分开，权限表本身就是一份边界声明。

一个真实的运行快照，说明这套机制失败时也体面。某天上午手动触发跑了一次，后端单测挂了：fail-fast 生效，依赖后端的集成测直接没跑，省了时间；并行跑的前端单测不受影响，继续跑完；当时开发者卡在哪个分支，被忠实记进状态文件。失败的现场被完整保留，哪一步挂了、退出码多少、当时在哪个分支，第二天一看便知，不用回忆也不用复现。

边界设计讲完「应该怎样」，看一次真实失败里它如何兑现。那天上午手动触发了一次，跑完的状态目录里留着完整痕迹：运行编号、结果文件里写着 status 为 fail、失败步骤是后端单测、退出码 1；并行的前端单测也挂了，因为两个是同时跑的，各自留了退出码；最有信息量的是那个 git 状态文件——当时开发者正卡在某个 feature 分支上，这个事实被原样记了下来。

这个失败现场恰好把三条边界全演示了一遍：fail-fast 生效，依赖后端的集成测压根没启动，时间省下了；并行的前端单测不受牵连，跑完才停；工作区状态被忠实记录，还原环节会把它切回原来的分支。失败的系统比成功的系统更能暴露设计质量——这次失败里没有发生任何越界，这就是边界存在的证明。

三、边界三：不确定就开口要人

前两条边界管「能做什么」，第三条管「怎么说话」——这是对自动修复系统最要命的一条。三种结局，脚本分得很清：修好且回归通过，提 MR 等你 review；修完回归没过，删掉分支，通知你修复未通过验证；找不到根因，输出分析报告，一行代码不动。

最后一种是我特意留的。对一个自动修复系统来说，最吓人的汇报从来就是那句轻飘飘的「已修复」——修了哪里、改了什么、影响多大，一概不知，合上去才知道。所以飞书通知是三种固定文案：全过，接着睡；已修复，点开 MR 看；修不动了，起快来。Agent 不确定的时候绝不嘴硬，宁可早上挨骂，也不夜里硬撑。

「不修清单」同样重要，它划的是 Agent 的能力边界，比「能修什么」更能决定系统会不会帮倒忙。环境问题不修：数据库连不上、后端起不来，Agent 一概不动，直接告警叫人——它改的是代码，基础设施没它的权限，硬上只会越改越乱，甚至为了让测试通过去调大超时、注释断言，那等于掩盖问题。E2E 偶发抖动不修：它分不清「代码挂了」和「测试本身 flaky」，硬修会把测试改成永远通过的样子。根因定不下来的不修：它自己都说「可能是 A 也可能是 B」，那就交报告，强改一个不确定的根因，改错的概率比改对高。

三种结局落到飞书上，是三种固定文案，一眼知道该干什么。全过的最省事，一行通过状态加运行编号，看完继续睡。已修复的那条带着失败步骤、修复分支和 MR 链接，你的动作从「看日志排查」变成「点开 review」。修不动的那条长这样：Agent 分析后未找到可修复的代码问题，失败步骤某某，需人工排查——明确告诉你它试过了、败在哪，把现场交出来。文案是死的，分寸是活的：通知怎么写，决定了早上的人怎么醒。

这条边界还有个隐藏条款，也是最反直觉的一条：修不好，就只修一次。AI 修复失败后最容易掉进去的坑是「再让它试一次」，然后无限循环——每轮重试都在烧 token，改出来的代码越来越偏。我的规矩是修一次，验证不过就删分支叫人。「重试」这个动作必须从 Agent 手里拿走，变成人的决策。AI 的优势是快，不是锲而不舍；凌晨让它无限重试，是在用它最弱的判断力去赌它最强的速度，方向反了。

四、边界的边角料：让 daemon 活得久的设计

三条大边界之外，还有一堆小设计，单个看不起眼，合起来决定这套系统能不能 7×24 真的活着。

错峰是用代价换的。最初定凌晨零点跑，听着合理，结果和数据库备份、日志轮转这些定时任务挤在一起抢资源——全量测试要起后端、连数据库，两边都慢，更险的是测试把库搞脏，备份就把脏数据备了份。后来挪到两点，跑完四点，九点上班时报告已经在飞书里。定时任务的「什么时候跑」和「跑什么」一样重要，撞车比不跑还糟。

守护进程自己也需要守护。巡检进程可能被 OOM、被误杀、随机器重启没了，而你可能把「早上没收到告警」误读成「昨晚全过」。所以巡检每十分钟往心跳文件写一次时间戳，另一个更简单的监控任务盯着这个文件，超半小时没更新就告警。用更简单的系统监督更复杂的系统，这是「谁来监督监督者」的工程化回答。

实现上它也不依赖系统 crontab，是自管理的：后台进程循环运行，每轮算下一次触发时间，然后每五分钟醒一次检查信号。为什么不直接睡到明天？因为停止命令的实现就是删掉 PID 文件，循环五分钟一查，删了就退；一觉睡十小时，停个 daemon 都要等到第二天。分段 sleep 加信号检查，比依赖系统调度器可控得多。定时配置本身也落了盘：几点跑、修不修，写进状态目录下的配置文件，机器重启之后 daemon 按上次的配置继续上岗，不用人重新交代。

还有两个部署期的坑，写下来省你一个下午。一是 daemon 环境的 PATH 极简，nvm 没加载，claude 命令找不到，要显式加载 nvm 并指定 Node 版本。二是服务器没有桌面 Chrome，Playwright 找不到浏览器，这个坑只在服务器上冒头，本地开发完全遇不到，得用环境变量告诉它走内置 Chromium。自动化脚本的兼容代码，一大半都花在「有没有那个命令」的适配上。

修完提 MR 这一步也有个值得留档的坑。最初的方案是调一个现成的建 MR 脚本，结果它是为另一套流程设计的：优先走云服务接口，参数只认命名格式，夜间脚本传的是位置参数，主路径直接对不上。真正接住局面的反而是 Git 的原生能力：push 时附带 merge_request.create 的 push option，一条命令完成建 MR，不依赖任何外部服务。教训很实在——自动化的最后一步往往最依赖外部系统，也最容易断；链路的末端要留一个不依赖任何人的原生后备，才算真的能通宵。

四点五、两个常见问题

夜里让 Agent 修 bug，token 不得烧爆？ 这笔开销比直觉健康。烧 token 的前提是「测试挂了且代码问题」，而多数夜晚测试是全过的，Agent 一晚上零调用；真挂了，一次修复的读日志加改动通常在几十万 token 量级，走缓存折扣后是几毛到几块钱的事。对比项是人的时间：同样一次夜间故障，早上救火要一个上午。用几块钱把一个上午买回来，这是全套系统里回报率最高的一笔支出。何况夜间跑还有个白天没有的好处：它和你的工作时段完全错开，速率窗口整晚空闲，跑再多次都不占你白天的额度。真正要防的是无限重试，这在前面的边界三里已经拆掉了。

为什么不直接用现成的自动修复产品？ 现成方案的问题是边界由别人定。哪类问题敢修、修完验多少步、失败怎么分流、工作区怎么保护，这些决策每家产品各有各的答案，而它们是最不能外包的那一类——出了事，为边界买单的是你的代码库，不是产品经理。自己搭的全部意义，是把「不修清单」和「不合并」这几条写进自己能审计的脚本里。当然这话有边界：如果某个现成方案允许你逐条配置这些边界，用它并不可耻，配置边界的工作量远小于从零写脚本。

五、和 CI 的分工，以及那笔时间账

经常有人问：这不就是 CI 加了个自动修复？对，但差别正是边界。普通 CI 跑完测试给你红灯，报完看你表演；这套是红灯亮了 Agent 自己上场，修完还验一遍。分工因此很清楚：CI 守白天的增量提交，daemon 守夜里的存量状态，会话级的定时 review 守单次工作会话。三者互不替代。

维度普通 CI会话级定时 review这套夜间 daemon
跑在哪CI 服务器claude 会话内业务服务器
触发push / PR会话内定时7×24 定时
失败后报红灯，人工接手出报告加告警自动修复，全量回归，提 MR
会话关闭不影响就地停止不影响
早上要做的从看日志开始看报告20 分钟 review 或继续睡

三个方案各守一段，谁也别想替代谁。会话级方案窗口一关就停，守不住夜里；CI 环境隔离，安全但没有修复动作。daemon 填的空白很明确：7×24 在跑，失败之后有动作。多出来的这个「动作」，就是全部边界设计要圈住的东西。

最后把时间摆出来算一算，这是这套系统全部设计的目的所在。没有它，早上发现 dev 挂了，看日志、定位、修、提 MR，一上午在救火，原计划全推迟。有了它，早上要么全过（直接干正事），要么有 MR 等 review（20 分钟合掉），要么才需要动手。三种情况里只有最后一种吃掉大块时间，前两种几乎不影响当天的节奏。再算细一点：review 20 分钟里真正动脑的只有「这个修复对不对」一个问题，其余的定位、复现、验证、提交流程，全被夜里那三条边界消化掉了。把救火的时间还给开发，边界划得再细都值回票价。

收尾

回到开头那个问题：凭什么敢让它通宵？凭的不是它多能修，是它被管得多死。工作区碰不得，合并权拿不走，不确定就开口要人——三条边界画完，它的全部自主性都被关在「修代码」这一项工作里，其余每一步都留了人的位置。它的全部自主性，就是修代码这独一门活计。

自动化系统的成熟度，看的从来不是它 autonomous 到什么程度，是它的边界清晰到什么程度。修一百次都对，不如修错一次能自己举手。信任，但验证；放手，但画圈。这八个字写起来只要一秒，落到代码里却是 stash 与 commit 之间、修一次与修一百次之间、说「已修复」与开口要人之间的全部设计。这八个字，就是整套系统唯一的设计原则。
