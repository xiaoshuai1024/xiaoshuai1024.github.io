收藏 80 个 skill 不如写 1 个：Claude Code 从零到能跑

skill 清单我见过太多份了。mattpocock 的、superpowers 的、各种「10 个必装 Claude Code skill」的合集，我自己也装过 80 多个（这件事我写在百万行代码后的 Skills 实战里）。装完的实际情况是，触发频率前 10 的 skill 占了九成调用量，剩下的常年躺在那儿吃灰。

后来我想明白了。清单里别人的 skill，解决的是别人的问题。我自己的问题，比如「AI 写出来的稿子一股 AI 味」，任何清单里都没有答案，因为只有我知道我受不了哪些词、我的改稿流程长什么样。这种事只能自己写。

这篇就带你从零写一个自己的 skill。不推清单，不讲概念，每一步都有真实代码，全部来自我这半年天天在用的 de-ai-smell（一个专治 AI 味的 skill）。你跟着做完，手里会有一个属于自己的、能被 Claude Code 自动触发的东西。

而且这件事的复利比看起来大。清单里的 skill 是别人的经验，你收藏来只能用到别人踩过的坑为止。自己写 skill 的过程，本质是把你自己踩过的坑变成模型的能力，写一个少犯一类错。de-ai-smell 我前后投入不到一天，换回来的是全站五十多篇文章的改稿时间砍半，怎么算都划算。

一、读完你能做出什么

一个最小的 skill 长这样：

.claude/skills/
└── my-skill/
    └── SKILL.md

一个文件夹，一个 Markdown 文件，加起来不到十行，它就能工作了。Claude Code 启动时扫描这个目录，读到你的文件，之后在合适的时机自己决定用不用它。不需要注册，也不用改任何配置，一行代码都不用写。

图 1 是整个机制的示意，你可以先有个地图。

二、前提

  • 装好了 Claude Code，能在终端里跑起来。版本别太旧，太老的版本不认 skills
  • 会写 Markdown。skill 的全部语法就是 Markdown 加 YAML 头，没有第二门语言
  • 手头有一件你重复教过 AI 的事。这是道绕不开的门槛，动手部分的第一步会给判断标准
  • 想深入的话，我之前写过一篇 Claude Code Skills 体系拆解，讲的是整套生态。这篇不管那些，只管「你亲手写出一个」

顺带说一句适用范围。skill 这个格式不是 Claude Code 私有的，它走的是 Agent Skills 开放规范，同一份 SKILL.md 放进 Cursor、Codex、Gemini CLI 都能被识别。你在本文写的东西不绑定任何一家工具，换客户端不用重写，这也是我愿意往里投入的原因之一。

三、整体思路

写一个 skill 分六步。

第一步找到值得写的那件事，这一步决定成败，写错了选题后面全白费。第二步建目录写文件，纯体力活。第三步写 description，这几行是整个 skill 里最贵的几行，因为它决定模型什么时候想起你。第四步写正文规则，把「你每次都要重复说的话」翻译成模型能执行的约束。第五步挂一个能跑的扫描脚本，让规则可机检。第六步验证触发，确认模型真的会想起你。

我的建议是第一遍先写个最小的，能触发就行，然后再迭代。de-ai-smell 现在有一千多行，还有扫描脚本和五个 reference 文件，但它最早的版本不到五十行，就是一个词表加几条规则。先跑起来，再长肉。

写之前还要分清楚，你这个需求到底该做成什么。Claude Code 里有三个容易混淆的位置。CLAUDE.md 是每次对话都在场的全局约束，适合放底线和习惯，比如「数据库用 MySQL」「构建用 mvn package」。自定义命令（slash command）是你主动敲 /xxx 才触发的固定动作，适合「每次都一模一样」的操作流程。skill 是模型自己判断该不该用的知识包，适合「该想起来的经验」。

拿我的用法对照。.claude/skills 里挂着去 AI 味的、画架构图的、发公众号的十几个 skill，我不敲任何命令，写到哪一步它们自己出现。而「跑全站扫描」这种我每次都明确要的动作，做成了 Makefile 目标加自定义命令。放错位置的后果很直接，经验做成命令，你忘了敲就等于没有；固定流程做成 skill，模型可能在你想直接干活的时候插进来多嘴。

四、动手

步骤 1：找到值得写成 skill 的那件事

判断标准只有一条，你在不同的对话里，把同一段要求粘贴给 AI 超过三次。

这条标准有几个变体信号，你对一下。一种是「换会话就失忆」，你明明教过它，新开一个对话它又犯同样的毛病。一种是「口头禅式纠正」，你发现自己在反复打同一行字，比如「别用破折号」「代码只放关键几行」。还有一种是「跟别人吐槽过」，你跟同事抱怨过 AI 总在某个地方翻车，抱怨本身就是在复述规则。任何一个信号出现两次以上，就值得固化。

我拿自己的真实经历说。我用 Claude Code 写博客，AI 出的稿子总有股味儿，「赋能」「闭环」「底层逻辑」满天飞，破折号一页能出现二十几个。一开始我口头骂，让它改。第二篇稿子，同样的味儿又来了，我把要禁的词贴给它。第三篇，我又贴了一遍。

贴到第三遍的那个瞬间我就知道了，这件事该做成 skill。口头骂和贴小抄都是一次性的，只管当前对话，换个会话它全忘。写进 SKILL.md 才是永久的，每次新对话它自己带着这套规则来。

时间成本也值得拆开看。贴一次小抄三十秒，看着不多，但它是持续支出，每篇稿子都要贴，而且贴晚了它已经把带味的初稿写完了，返工成本另算。写成 skill 是一次性投入，半小时把规则整理清楚，之后所有对话免费自带。任何每周都会发生两次以上的纠正动作，都值得做这笔置换。

反过来说，只发生过一次的事别写。比如某次排查一个冷门报错，解决了就解决了，做成 skill 只会让模型在该专注的时候分心。skill 是给重复问题准备的，宁缺毋滥，我宁可备忘录里攒着候选，也不往 .claude/skills 里塞低频货。

步骤 2：建目录，写头三行

在项目根目录建 .claude/skills/de-ai-smell/SKILL.md，文件开头是 YAML frontmatter：

---
name: de-ai-smell
description: 去 AI 味——L1 禁词（兜底/铁证/说白了/先说/根子/扎眼）+ L2 慎用词、行为规范（少冒号、别随便加粗、限破折号）、扫描脚本（make check-ai-smell）。写文章/口播/图文前先过一遍。
---

就这两行配置，name 和 description。name 是文件夹同名，description 负责讲清这个 skill 干什么、什么时候该用。到此为止一个 skill 已经成立了，下面正文随便写点什么它都能被触发。

给你一个完整的最小骨架，直接复制走改名字就能用：

---
name: my-first-skill
description: （什么时候 + 干什么，写具体场景词和时机词）
---
# 我的第一个 skill

## 什么时候用
（用户会怎么说、什么任务出现时加载这份规则）

## 规则
1. （把你要重复说的话一条条写在这里）
2. （能量化的写死数字，别写「尽量」）

## 怎么验证
（怎么确认模型真的执行了）

这个骨架的思路是把「何时触发」和「怎么执行」分成两块写。frontmatter 里那句话是给路由看的，正文才是给执行看的。第一版最容易犯的错是把两者混着写，规则堆了一堆但 description 含糊，规则再好也轮不到出场。

预期输出：在 Claude Code 里问一句「帮我改这段稿子，去掉 AI 味」，如果它开始按你 SKILL.md 里写的规则干活，就是成功了。

步骤 3：把触发时机写进 description

这是整个 skill 里最值得花心思的地方，我单独拉出来讲。

description 不是给人看的文档，它是写给模型的路由依据。Claude Code 同时挂着几十个 skill，模型在每次对话开始时读所有 description，判断当前任务该不该加载你这一份。写得含糊，它就永远想不起来你。

对比一下两种写法。「写作助手，提升文章质量」，这种描述跟一百个别的 skill 撞脸，模型没理由选中它。我实际写的是「写文章/口播/图文前先过一遍」，注意这里有个具体的动作信号「写……前」。模型看到用户说「帮我写篇稿子」，这个描述立刻匹配上。

拆开看，一句能打的 description 有三个部件。场景词，写文章、口播、图文，用户任务里会出现原话的那种。时机词，「写……前」「改稿后」，告诉模型在流程的哪个点介入。能力词，L1 禁词、扫描脚本，让模型知道加载之后能干什么。三个里面场景词最不能省，省了它，剩下写得再漂亮也没人认领。

还有一个反面教材是我真实踩过的。早期我的 description 写的是「让文字更自然」，结果它在我重构 Java 代码的时候冒出来，建议我把注释改得「更口语」。问题不在模型，在我的描述里全是效果词，没有一个场景词，它只能靠猜。改成具体场景之后，乱触发一次都没再出现。

诀窍就一条，把「什么时候该用」直接写进描述里，越具体越好。什么场景、什么动作、什么时机，能写多具体就写多具体。图 2 是这两种写法在触发环节的差别。

步骤 4：正文写规则，一定要分级

正文就是你平时贴给 AI 的那段话，但直接照贴效果不好，要重新组织。我踩出来的经验是两条。

第一，规则分级。把「碰都不能碰的」和「看情况商量的」分开。de-ai-smell 的词表分两级，摘一段真实的正文给你看：

**L1 禁词（出现即改，无例外）**

| 词 | 替代 |
|----|------|
| 兜底 | 回退 / 降级 / 把它拦下来 |
| 铁证 | 实测 / 日志为证 |
| 说白了 | 删掉，直接说结论 |

**L2 慎用词（命中提示，人工判断后再留）**

| 词 | 可留 vs 要改 |
|----|------|
| 本质 | 名词「问题的本质」留；副词「本质上」改「原理」 |
| 真相 | 名词「事件真相」留；戏剧化的「真相是」删 |

为什么必须分级，看两个真实句子就懂了。「兜底方案」里的兜底，技术上讲的是降级路径，但它已经是 AI 文本的重灾区词，读者看见就皱眉，所以归 L1，出现就换。「问题的本质是什么」里的本质是正经名词，禁掉它稿子没法说话，所以归 L2，让我人工看一眼再决定。要是不分级把所有词一刀切，稿子会被改得不会说话，这个 skill 也就废了。

第二，别只列词，把行为也写进去。光删词治不了 AI 味，我清理过全站五十多篇文章，最重的味道在句式里。给你看一组改前改后的真实对比，词没一个违禁的，味道全在结构上：

改前：把规则装进文件，把词表分成两级，把脚本接到 Makefile，我们就拥有了可复用的能力。

改后：规则装进文件，词表分两级，脚本接上 Makefile。这套东西就能复用了。

前一句三连排比加「拥有了」式收尾，是典型的机器节奏；后一句长短错开，像人话。所以 de-ai-smell 的正文里一半篇幅是行为规范，破折号每篇最多两处、加粗每节最多两处、「不是 A 而是 B」句型直接禁、每段结尾不许总结升华。词是表象，句式才是它的签名。

写成文件的规则跟口头说还有一个区别，文件里的规则模型执行得严格得多。口头说「少用点破折号」，它改三个留五个；写在 SKILL.md 里标明上限，它真的会数着写。我猜原因是文件里的规则带着明确数字和「无例外」的措辞，模型对写死的约束执行得比对模糊建议认真得多。你写自己的 skill 时可以直接利用这一点，能量化的规则就写死数字，别写「尽量少」。

步骤 5：挂一个能跑的脚本

规则写到几百行之后，靠模型自己逐条对照会漏。这时候给 skill 配一个脚本，让它能动手扫描。

de-ai-smell 配的是 scripts/check_ai_smell.py，词表跟 SKILL.md 里那份保持同源，接到 Makefile 上：

check-ai-smell:
	python scripts/check_ai_smell.py

check-ai-smell-one:
	python scripts/check_ai_smell.py $(path)

然后在 SKILL.md 正文里告诉模型这个命令的存在和用法。实际效果是，模型改完稿子会主动跑一遍扫描，把命中的行号列出来，我只要人工确认这些命中是不是误报。扫描输出长这样：

content/xxx.md
  L23  [L1] 兜底        → 回退 / 降级 / 把它拦下来
  L41  [L2] 本质        → 副词用法，建议改「原理」
  L67  [风格] 破折号 4 处 → 上限 2 处，逐处换成逗号或拆句

我有一篇稿子破折号二十六处，肉眼检查时我自信地觉得没几个，脚本一跑，红了一屏。

有一点必须强调，脚本只定位，不自动改。扫描一定有误报，front matter 里的 tags、反讽语境里的「赋能」，这些不能删。自动改写会改坏事实，这比留着 AI 味严重得多。去 AI 味的第一原则是保真，删套话可以，造事实不行，原文没说的，输出不许说。这条原则本身也写在 SKILL.md 里，模型执行扫描时同样受它约束。

步骤 6：验证它真的会被触发

写完别急着收工，开个新对话测三遍。这一步最容易省掉，也最不该省，我就有过 description 改完自我感觉良好，实际两周一次都没触发过的经历，还是翻对话记录才发现的。

第一遍说一个 description 里写了的场景，比如「写篇口播稿」，看它会不会主动加载 skill。第二遍说一个相邻但不想触发的场景，比如「帮我重构这段代码」，看它会不会乱触发。第三遍在触发后抽查行为，随便指一段问它违反了哪条规则。

三遍都过了才算成。第一遍不触发，回步骤 3 改 description；乱触发，说明描述写得太宽，加限定词。图 3 是 de-ai-smell 现在的完整工作流，从写前加载到写后扫描，你可以对照看看一个成熟 skill 长什么样。

为什么乱触发也要当回事。一个不相关的 skill 被加载，不只是浪费上下文，它会真的改变模型行为。我那次被「让文字更自然」捣乱的重构任务里，模型改了三个 Java 文件的方法注释，全是无意义的改动，还得我一个个看回去。

宁可漏触发，你手动说一句「用 xxx skill」就能补救，乱触发的清理成本高得多。

五、一个 skill 是怎么长到一千行的

既然说先写五十行的最小版本，那后续怎么长大，我把 de-ai-smell 的三次迭代摆出来，你会看到每一步都是被真实问题逼出来的。

第一版只有词表。四十来个词，分两栏，禁词加替代。用了两周发现不对，词删干净了稿子还是机器味，问题出在句式上，于是第二版加进了行为规范，破折号上限、加粗上限、禁排比、禁收尾升华。这一版的正文从五十行涨到三百行，效果跳了一档。

第二版用了两个月，新问题出现。规则多了，模型偶尔漏执行，三百行里挑着遵守。我不想删规则，就把词表和详细案例拆到 references 子文件，SKILL.md 只留骨架，再写了扫描脚本接到 Makefile，让机器替模型数数。这是第三版，也是现在的形态，SKILL.md 一千多行加五个子文件加一个脚本。

拆子文件这件事多说两句，因为它解决的是上下文经济学。skill 每次触发都是全文进上下文，一千行常驻等于每次对话先交一笔固定税。拆出去之后，SKILL.md 里只留一句「完整词表见 references/ai-smell-word-list.md，命中场景再读」，模型平时只带骨架干活，真要核对具体某个词才去读那份文件。代价是多一次文件读取，换来的是九成对话的上下文干净。我实际拆出去的五份分别是完整词表、保护片段清单、句式套路详解、正向风格目标和防幻觉一致性检查，全是「用得着但不用常驻」的内容。

回头看，三次迭代对应三次真实的失灵，词不对、句式不对、执行不严。你现在直接拿走这个结构可以少走半年弯路，词表管词、规范管句式、脚本管执行，三层各管一段。但顺序别变，先解决你当下最痛的那一层，痛了再加下一层。一上来就搭三层，大概率每层都没调准。

六、常见坑

坑一：SKILL.md 越写越大。 规则攒到上千行，模型每次触发都全文加载，上下文被吃掉一大块，还容易顾此失彼。我的实际感受是超过四百行之后，边角规则开始被无视，模型优先执行开头和结尾的条目，中间的靠运气。解法是拆 references 子文件，SKILL.md 只留骨架和最常用的规则，详细词表、案例放子文件，正文里注明「需要时再读」。de-ai-smell 的五个 reference 文件就是这么长出来的。

坑二：规则之间打架。 我早期同时写了「段落不超过七行」和「每步都要有运行结果」，结果模型为了塞运行结果硬把段落撑长。规则多了以后通读一遍找冲突，打架的合并成一条，说清优先级。

坑三：一次想把 skill 写完美。 第一个版本控制在五十行以内，先求能触发、能执行。规则是从真实的失败里长出来的，你还没用它，就不知道该补什么。我那份词表里一半的词，是后来扫描真稿子时一个个抓出来的，最初的四十个词里大概有十个，实际写稿根本碰不上，纯属想当然。用两周再回看，删掉没触发的规则，补上真实翻车的规则，这一轮修剪比闭门写三天都有用。

坑四：跟 CLAUDE.md 抢活。 CLAUDE.md 管全局底线，每个对话都加载；skill 管特定任务的做法，按需触发。把「碰都不能碰的约束」放进 CLAUDE.md，把「这类活儿怎么干」放进 skill。放反了要么上下文爆炸，要么该在场的时候不在场。我的分法是拿 DELETE 语句做例子，「删数据前必须带 where 并过租户检查」写 CLAUDE.md，「排查数据问题的完整步骤」写 skill。前者出事就是事故，永远要在场；后者只在特定任务里用得上。

坑五：description 写成营销文案。 「最强改稿神器，让你的文章脱胎换骨」，这种描述对模型路由毫无用处，它不找最强的，它找最匹配的。描述里放的应该是场景词和时机词，用户会怎么说、什么动作发生时该用你，把这些原话写进去。判断方法很土但有效，把你的 description 拿给同事看，问他「什么活儿你会想到它」，答不上来就重写。

七、完整产物

de-ai-smell 的完整代码在我开源的 skills 仓库里，地址 github.com/xiaoshuai1024/skills，里面的 skills/de-ai-smell/ 目录就是本文的例子本体，SKILL.md、五个 reference、扫描脚本全套都在，可以直接照着改结构。仓库里还有写博客、画架构图、发公众号这些配套 skill，一条 npx skills add xiaoshuai1024/skills 就能装。

八、下一步

写出第一个之后，你大概率会开始留意自己还在重复教 AI 什么，那个清单会自己长出来。我现在的习惯是，每次忍不住在对话里纠正 AI 一句，就顺手记到备忘录里，攒够三条同类就开一个新 skill 或者并进旧的。

还有一个练习建议。今天就用半小时把你最烦的那件事写成 skill，别等想清楚全部规则再动手，写个二十行就挂上去用。你会在第三次触发的时候知道哪里要改，这个手感看多少篇文章都替代不了，我的 de-ai-smell 就是这么三轮改到一千行的。

回到我最想说的那个判断。收藏 80 个别人的 skill，解决的是别人的问题。你每个礼拜都在重复教 AI 的那件事，才是你的第一个 skill，而且只有你能写好它。门槛低到只是一个 Markdown 文件，缺的从来不是技术，是你意识到这件事值得固化下来。
