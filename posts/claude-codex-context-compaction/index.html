Claude Code 与 Codex 的上下文管理源码对比：先清工具输出还是先做摘要

有一次长会话压缩之后，我让 Claude Code 继续改一个之前读过的文件，它把文件重新读了一遍。当时我以为是它忘了，读完源码才明白：压缩的时候对话原文一个字没动，被清掉的是旧的工具输出——那个文件的完整内容是作为 Read 的 tool_result 存在的，microcompact 把它替换成了 [Old tool result content cleared]。所以它记得需求（对话还在），丢了文件细节（工具输出没了），只能重读。这不是 bug，是精确设计的取舍。

这是系列第四篇。前四篇见架构分层、主循环、subagent 调度。版本锚定不变：Claude Code v1.0.88，Codex commit 63b268c81b。

上下文是这个系列里离每个用户最近的议题——不管你用什么姿势用 Agent，压缩都在你背后发生。这篇的目标是把那件「背景里的事」拉到前台：触发线在哪、清什么留什么、压缩后你的会话变成了什么样、哪些损耗可以靠使用习惯找回来。开头的「记得需求丢了细节」，读完你会知道它精确发生在哪一行、为什么被设计成这样、以及怎么和它相处。

一、Claude Code 的两级压缩

Claude Code 的上下文管理是两级火箭，都在主循环入口处检查（L416898 到 L416912：先 Kv 做 microcompact，再 hRB 做 auto-compact）。

第一级 microcompact：便宜、激进、只动工具输出。实现逻辑是把旧的 tool_result 内容替换成占位符，原文在 v1.0.88 里是明文的 [Old tool result content cleared]（L394465 一带）。配套的埋点 tengu_microcompact 携带的字段能说明它清理了什么：toolsCompacted（清了几个工具的结果）、totalUncompactedTokens、tokensSaved、triggerType（manual 还是 auto）。

为什么先动工具输出？看一眼长会话的构成就有答案：一轮「读三个文件改一处」的交互里，对话文本可能只有两百 token，三个文件的完整内容加上 diff 输出能到几万。长会话的体积大头永远是工具输出，清它性价比最高。而且工具输出有「时效性」——早期读的文件大概率已经改过了，留着旧内容反而误导模型。

第二级 auto-compact：贵、彻底、做全文摘要。microcompact 救不回来时触发，走一次独立的摘要请求，prompt 原文在 L392454 / L392550（「Your task is to create a detailed summary of the conversation so far…」两个变体），摘要完成后用续接 prompt 重新开场（L392681：「This session is being continued from a previous conversation that ran out of context…」）。摘要请求有独立的流式配置（promptCategory: "compact"），失败时打点 tengu_compact_failed，reason 是 no_summary——摘要没生成出来就继续用旧上下文硬撑。

阈值体系是我见过最较真的部分（L394307 到 L394332，全部确证）：

var hJ5 = 13000,  // auto-compact 距窗口上限的余量
    gJ5 = 20000,  // warning 余量
    uJ5 = 20000;  // error 余量

function contextStatus(used) {
  let limit = availableWindow();          // fRB()：模型窗口 - 预留输出
  let autoCompactAt = limit - 13000;      // 到这条线触发压缩
  let warnAt = limit - 20000;             // UI 警告线
  let errorAt = limit - 20000;            // UI 报错线
  ...
}

注意没有硬编码 160000——窗口按模型动态查表（fRB() = 模型上下文窗口减预留输出 token）。auto-compact 的开关是 settings 里的 autoCompactEnabled（/config 命令可切，切换时打点 tengu_auto_compact_setting_changed），关掉之后 UI 会显示「Context low (X% remaining) · Run /compact to compact & continue」（L423308）——手动 /compact 走的是同一套摘要逻辑。

这套阈值代码里还藏着三个值得咀嚼的细节。

第一个：为什么触发线比警告线还宽？auto-compact 在距上限 13000 token 时就动手，warning 却要到距上限 20000 才亮——顺序反了？不是。auto-compact 是「提前量」，它需要留出一轮工具调用的空间（一个中型 tool_result 就能吃掉几千 token），13000 是「这一轮安全做完、下一轮开始前压缩」的缓冲；warning/error 的 20000 是「给用户看的红黄牌」，触发时其实已经比 auto-compact 线更深了——也就是 auto-compact 被关掉或失败了的场景。两条线服务两个受众：一条给机器，一条给人。

第二个：百分比在 UI 上的口径。L423308 那行「Context left until auto-compact: X%」的分母不是模型窗口，是 auto-compact 触发线——所以你看到的 20% 不是「窗口还剩五分之一」，是「离压缩还有五分之一的路」。口径影响心理：按窗口算的百分比总是更乐观，按触发线算的百分比诚实得多。

第三个：压缩后的轮次计数。tengu_post_autocompact_turn 带着压缩后的 turnCounter——这个埋点的存在说明 Anthropic 在度量「压缩后任务还要跑多久」，即摘要质量对任务连续性的影响。做长任务时如果发现每次压缩后模型都要「重新对齐」一两轮，这不是错觉，是摘要损耗的可见形态，这个埋点就是官方也在盯这个问题的证据。

摘要 prompt 本身（L392454 / L392550 两个变体）是个值得抄的模板。它要求摘要覆盖：主要目标和任务状态、关键的技术决策和理由、代码变更清单、未完成的下一步——注意这个清单的取向：保「决策与状态」，舍「过程与细节」。两个变体的差异在结构化程度上（一个分节要求，一个自然语言要求），大概率是 A/B 后的共存。续接 prompt 那句「This session is being continued from a previous conversation that ran out of context」则是给新会话定调：你带着前情摘要上场，不是从头开始。自己搭 Agent 遇到要压缩的场景，这两个 prompt 都是可直接改抄的起点。

二、Codex 的压缩：独立 crate 加双路实现

Codex 把压缩做成了 core/src/compact.rs 一个专门模块，入口三个：run_compact_task（:143，手动 /compact）、run_inline_auto_compact_task（:111，turn 内自动）、run_manual_compact_task（带 token 预算评估的变体，在 compact_token_budget.rs）。

摘要的生成方式和 Claude Code 同构：发一次 CodexResponsesRequestKind::Compaction 类型的独立请求，让模型自己对历史做总结，产出替换原历史。触发判断在 core/src/session/context_window.rs 的 context_window_token_status，turn loop 每轮检查 token_limit_reached 标志位——这就是第二篇讲过的 needs_follow_up 三条件里的第三个。

「压缩是一种请求类型」这个设计比看起来重要。CodexResponsesRequestKind 里 Compaction 和普通采样是并列的变体——意味着压缩请求有自己的预算、重试、模型选择策略（compact_model_fallback.rs：主模型压缩失败换备选），不占用主请求的任何配额语义。Claude Code 的压缩请求也有独立配置（promptCategory: "compact" 加 maxOutputTokensOverride），思路相同。把压缩当一等请求而不是主循环里的一个 hack，是两个产品不约而同的选择——自己写 Agent 时别把压缩塞进主 prompt 流程里，单独发请求，单独管预算。

Codex 还有两个和上下文窗口相关的工具值得点名：get_context_remaining（handler 在 tools/handlers/ 下）让模型自己查询剩余空间——模型能感知「我还剩多少弹药」，在长任务里主动规划（比如先输出结论再展开）；new_context_window 允许主动开新窗口而不是等被动压缩。这两个工具把上下文管理从「系统的隐形行为」变成「模型的可操作对象」，是编排自主性的一部分。Claude Code 的模型感知不到这些，只能被系统推着走。

差异在两个 Codex 独有的设计。

第一是双路压缩：本地压缩之外还有 compact_remote*.rs 系列实现服务端压缩——把压缩这个活交给服务端做，客户端只收结果。配套的 compact_model_fallback.rs 处理「主模型压缩失败换备选模型」的降级。为什么需要服务端压缩？还是平台定位：云端会话的历史在服务端，客户端发起本地压缩反而要把全量历史拉下来，不划算。

第二是历史结构本身为压缩设计：core/src/context_manager/history.rs:52 的 ContextManager 持有 items: Arc<Vec<ResponseItemEnvelope>>，oldest 在前，copy-on-write——每次 compaction 或 rollback 都 bump history_version 生成新快照，旧版本还在内存里，撤销压缩、对比 diff 都有据可查。Claude Code 的 messages 数组没有版本概念，压缩即覆盖。

工具输出侧 Codex 也有对应机制：codex-utils-output-truncation crate 的 truncate_function_output_items_with_policy，按策略截断超长工具输出——不过它是写入前截断，不是 Claude Code 那种事后清理。一个防患于未然，一个事后补救，时间点不同。

「写入前截断」的策略细节值得单独看：截断不是一刀切，保头保尾是常见形态——工具输出的开头（往往是结论或错误信息）和结尾（往往是摘要状态行）信息密度最高，中间的重复性内容（长列表、日志刷屏）最适合折叠。这就是为什么你偶尔会在 Codex 的工具结果里看到「output truncated」加头尾拼接的形态。Claude Code 的 BashOutput 工具族也做了类似的事（后台命令输出分页查看），思路殊途同归：在产出侧限流，比在消费侧清理体面。

还有一个 Codex 独有的时间点：pre-turn compaction（run_pre_sampling_compact，第二篇提过的 turn 级准备工作第一项）。它在发模型请求之前做压缩判断——为什么要提前而不是等 API 报错？因为请求失败的代价高（第二篇讲过 400 后的 maxTokens 自救是被动的、有损的），主动预判并在请求前压缩，把溢出消灭在发出之前。Claude Code 的两级检查也在主循环入口（发请求前），时间点上两家一致——「请求前检查」是共识，「请求后自救」是无奈，两边的实现里都有前者，也都有后者作为防线，纵深防御在这个细节上也成立。

三、落盘：内存数组 vs JSONL 加索引

上下文的另一半问题是持久化。Claude Code 会话落盘是 JSONL（每条消息一行），恢复时重放；上下文本身在内存里就是主循环递归传参的那个数组，没有别的结构。

Codex 的 rollout crate 是重装备：recorder.rs 负责写 JSONL，reverse_jsonl_scanner.rs 支持倒序扫描（找最近的会话不用从头读），session_index.rs 加 state_db.rs 建 SQLite 索引。为什么需要数据库级设施？第三篇说过的 agent 树恢复是原因之一，另一个原因是 codex resume 的场景——多会话列表、按时间检索、断点续跑，这些都是查询操作，JSONL 顺序扫描撑不住。

message-history 和 thread-store 两个 crate 进一步拆分了「消息」和「线程」的存储边界。对照 Claude Code 的单文件 JSONL，又一次是同构需求、异构实现：功能等价，工程复杂度按产品定位配给。

拿一个具体场景掂量这个差距的价值：你维护着二十个项目的长期 agent 会话，偶尔要回查「三周前那个会话里 agent 引用过哪个配置值」。Claude Code 的形态下这是 grep 会话目录的体力活（找到会话 → 顺序读到那个位置）；Codex 的形态下这是索引查询（会话列表按项目过滤 → 状态库定位消息）。一次两次无所谓，高频回查的团队会感受到数据库和文件的本质差距。上下文的持久化形态，长期看决定了「历史」是资产还是归档——归档只能翻，资产能查。

三点五、一次压缩的全程走读

把机制串成时间线，看一次 auto-compact 从触发到恢复的完整旅程（Claude Code 侧，Codex 同构）：

你的会话跑了四十轮，工具输出累积，token 计量逼近触发线。第四十一轮开始，主循环入口先过 microcompact：扫描历史里「足够旧」的 tool_result（近期的保留），替换成占位符——省下来的空间如果让总量回到了安全区，压缩到此为止，这轮你毫无感知；如果不够，auto-compact 接手：冻结当前任务状态，发一次独立的摘要请求（模型读完整历史，按「目标、决策、变更、待办」的结构输出摘要），摘要回来后，旧历史整体下岗，新会话以续接 prompt 开场——「你从上个对话延续而来，摘要在上」。

下一轮，模型基于摘要继续任务。它记得你要什么、记得改了哪些文件（摘要里都有），但要引用三小时前读过的某个函数细节时，发现对应工具输出已经是占位符——于是重读文件。这次重读产生的 tool_result 是「新」的，microcompact 的年龄计时从头开始。压缩不是一次事件，是一个循环：内容被清、被重读、再老化、再被清。理解了这个循环，就理解了长会话的 token 消耗曲线为什么是锯齿状而不是平台状——每个锯齿的上升沿里，都藏着一部分「重读税」。锯齿的深度由摘要质量决定（浅锯齿说明摘要保真），锯齿的间距由使用习惯决定（晚读文件、断点压缩都能拉长间距）——曲线的两个参数，一个归产品，一个归你。

降低重读税的手段到此也清晰了：让重读的颗粒度变细（读函数而不是读整文件）、让重读有据可查（路径写进任务描述）、让断点对齐压缩点（前面说过的「在断点压缩」）。三个手段都不在压缩机制里，在使用习惯里——机制定了大局，习惯决定边际。

四、把两边并排放：三种哲学

维度Claude Code v1.0.88Codex 2026-08
第一响应microcompact：清旧工具输出工具输出写入前截断
终极手段auto-compact：独立摘要请求本地摘要 + 服务端压缩双路
阈值距窗口 13000 token 触发，warning 20000turn loop 检查 token_limit_reached
历史内存数组，压缩即覆盖copy-on-write，版本化快照
落盘JSONL 重放JSONL + SQLite 索引 + 倒序扫描

看完这张表，我的判断是三个设计哲学的差异。

Claude Code 的哲学是分层省钱：能不清就不清，能少清就少清，两级压缩按成本递增排序，microcompact 这个「只清工具输出」的中间档是它独有的发明。用户得到的体验是压缩感很轻——对话记忆连续，只有翻旧账时才发现细节没了。

Codex 的哲学是结构化可靠：压缩是带类型的请求（Compaction kind），历史是带版本的快照，落盘是带索引的库。压缩不是「救命手段」是「常规操作」，所以敢做成服务端协作的双路。用户得到的体验是长任务稳，但每次压缩的感知成本更高（全文摘要的连续性损耗两边都有）。

第三种哲学藏在两边共同的沉默里：都不做向量检索式的「记忆」。压缩都是摘要式的，不是「把旧内容存进向量库按需取回」。RAG 记忆在两个头部产品里都没进主路径，说明摘要加清理在当前 token 经济学下还是最优解。自己做 Agent 设计时别急着上向量记忆，先把这两级的取舍抄明白。

哲学之下还有一层实操哲学：压缩时机的主动权归属。Claude Code 里你可以用 /compact 主动触发（在任务的自然断点——比如一个模块刚改完、测试全绿——手动压缩，摘要质量远高于在任务中途被自动触发）；Codex 里除了 /compact 还有 new_context_window 这个「换新账本」的选项，适合阶段性收束。在断点压缩这个习惯能显著降低摘要损耗：断点处的历史本身就有小结结构，模型摘要时能蹭到现成的章节感。反之在工具调用密集的中途被压缩，摘要要在一堆 tool_result 里捞线索，质量天差地别——两个产品的自动触发都不挑时机（只看 token 线），挑时机的只能是你。

五、使用层的四个直接推论

推论一：长会话里重要文件要「晚读」不要「早读」。既然 microcompact 清的是旧工具输出，早读的文件内容一定先丢。把关键文件的 Read 放在临近使用的轮次，能显著减少重读。这个习惯我现在已经固化，效果就是压缩次数肉眼可见地少了。

推论一还有个加强版：用「重读」代替「记住」作为长任务的默认预期。既然压缩机制决定了细节必然流失，任务设计上就该假设「任何超过压缩周期的信息都要有重新获取的路径」——文件路径写清楚、命令可重跑、约定落在文件里而不是对话里。这不是向机制投降，是和机制合作。我的长任务提示词里现在都带一句「需要引用早期内容时重新读取，不要凭记忆」，一句话省掉无数次幻觉式引用。

推论二：关掉 auto-compact 要慎重。开关在 settings 里随手可切，但关掉后上下文溢出会走另一条路——API 400 加动态下调 maxTokens（第二篇讲过的正则自救），输出质量先受影响。除非你在精细控制上下文，否则让两级压缩自己工作。

推论三：Codex 的会话是资源，Claude Code 的会话是文件。前者的索引化存储意味着 resume、多会话管理、长任务编排都是一等能力；后者就是 JSONL 重放。把重要长任务放 Codex 跑、把轻量探索放 Claude Code 跑，和第三篇 subagent 的结论指向同一个分工。

推论四是给做风控的人的：上下文管理是审计面。Codex 的 rollout 加索引意味着「agent 当时看到了什么」是可回放的——事故复盘时能精确重放决策时刻的上下文状态；Claude Code 的 JSONL 也能重放，但压缩发生的时刻没有版本快照（压缩即覆盖），压缩前后的上下文差异要靠推断。合规要求高的场景，这个差异应该进选型清单。

这个审计视角值得多说一句，因为它是两个产品差距最被低估的维度。Agent 出了错（改坏了文件、引用了过期信息），归因的前提是还原「它当时知道什么」：上下文里有什么、压缩在哪个点发生过、哪些细节已经变成占位符。Codex 的版本化历史把这三个问题都变成了查询；Claude Code 只能回答第一个。没有审计面的自动化不敢上生产——这比任何功能清单都更决定 Agent 的企业可用性，而它的地基就是这篇讲的这些看着不起眼的存储机制。反过来说，个人开发者不为审计付费是理性的：单人场景里「错了重跑」的成本，远低于维护版本化历史的成本，Claude Code 的轻装在这类场景就是正确答案。

五点五、自己搭 Agent 时的抄作业清单

如果读者自己要做 Agent 的上下文管理，这篇的源码可以直接换算成一张实现清单，按优先级排。清单的样子本身就是这篇的结论：从便宜往贵排、从局部往全局排，每一步都有源码出处，没有一条是我发明的：

先做工具输出截断（Codex 的写入前截断路线）——成本最低收益最大，长输出的截断策略（保头保尾、中间折叠）一个函数就能写完。再做旧工具输出清理（Claude Code 的 microcompact 路线）——「清工具输出不动对话」这一条就值得整个抄走，它同时解决了体积和过期两个问题。然后才是全文摘要压缩（两边同构的独立请求路线）——记得把压缩当一等请求：独立预算、独立重试、失败降级。最后如果你做多 agent，才需要考虑 Codex 那套 copy-on-write 历史和断点持久化——单体场景用不上，别预支复杂度。

这个顺序的依据是投入产出比，也隐含着一个反直觉：上下文管理的核心不是「压缩算法」，是「什么内容该在什么时刻离开上下文」。两个产品几十个文件的压缩相关代码，真正的智能全在「选择性遗忘」的规则上——哪些该清（旧工具输出）、哪些该保（对话决策）、哪些该摘要（过程性内容）。算法层面就是普通的模型请求，没有魔法。

清单之外补一个测试建议：压缩逻辑一定要有专门的对拍用例。我的做法是准备一个「压缩敏感任务」——跨越压缩点引用早期信息的多步任务，每次改上下文管理代码就跑一遍，对比压缩前后的完成质量。没有这种固定探针，压缩逻辑的回归只能在真实长任务里翻车后发现，那已经是事故了。Claude Code 那个 tengu_post_autocompact_turn 埋点启发的思路：压缩质量必须被度量，不能被假设——哪怕你的度量就是「探针任务十次里成功九次」这么粗糙。
