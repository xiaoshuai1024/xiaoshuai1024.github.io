Claude Code 与 Codex 的 Subagent 调度源码对比：同一个循环的递归和另一个线程的调度

我用 Claude Code 跑多 agent 任务时一直有个错觉：subagent 开得越多越危险，怕进程爆炸，所以并行数从不敢超过五个。读完源码才发现，我连「招人」这件事都理解错了——我一直以为派 subagent 是招临时工，实际上 Claude Code 是自己戴上假发、换张工牌，又去面试了一轮：没有新员工，只有同一个主循环的第二次入场。实际的并发上限不在「进程」不在「agent」，而在工具级并行池里写死的 10——一个藏在混淆代码第 416878 行的数字。而 Codex 走的是完全另一条路：每个 subagent 是一个独立 thread，有信号量限流、有消息总线、重启后还能把整棵 agent 树从磁盘上恢复出来。

这是系列第三篇，也是承上启下的一篇。前两篇见架构分层对比和主循环对比，版本锚定不变：Claude Code v1.0.88，Codex commit 63b268c81b。

一、Claude Code 的 subagent：一个函数的两种用法

Task 工具的描述文本在 v1.0.88 的 L409611 起，是动态生成的——把当前可用的 agent 类型列进去，还带两句关键指令：「Launch multiple agents concurrently whenever possible」（尽可能并行启动多个 agent）和「Each agent invocation is stateless」（每次调用无状态）。工具名常量 "Task" 在 L368573，工具对象在 L411575 到 L411600。

真正有意思的是 subagent 怎么跑起来的。L417610 的 QgB 是 subagent 启动器，它做的事浓缩到一行：构造一个精简的 toolUseContext，然后 yield* VE(...) 直接复用主循环。这个精简上下文的配置是明文可读的：

options: {
  ..., maxThinkingTokens: 0,     // subagent 不开思考预算
  mcpClients: [],                 // 不带任何 MCP 连接
  isNonInteractiveSession: true,  // 非交互标记
},
agentId: rN5(),                   // crypto.randomUUID，独立身份

外加一个独立的 AbortController——主会话和 subagent 的取消互不牵连，杀掉一个不会带崩其他。

也就是说，Claude Code 里「派 subagent」和「跑一轮工具调用」在进程模型上是同一个动作：都是同一个 generator 函数的执行。区别只在上下文配置——subagent 砍掉了 MCP、砍掉了思考预算、换了个身份 ID。轻到可以随手派，也轻到没有隔离：subagent 和主会话共享同一个 Node 进程的内存空间和事件循环——一个 subagent 里的异常如果处理不当，波及的是整个会话。

agent 从哪来？L393415 的 kM 是加载管线，从配置目录读 markdown 文件（frontmatter 含 name / description / when-to-use / tools / color / model），然后按五级优先级合并：内置定义 < 插件 < 用户设置 < 项目设置 < 策略设置，同名去重。内置只有一个 general-purpose（L392937，tools: ["*"]，默认 sonnet），加上两个功能性的 setup agent。subagent 的模型还可以用环境变量 CLAUDE_CODE_SUBAGENT_MODEL 全局覆盖（L339931）。

Task 工具的 prompt 本身值得精读（L409611 起，混淆码里整段明文）。它给模型的行为指令能概括成四条：尽可能在同一条消息里发多个 Task 调用来并行（直接对应第二篇的「安全块进并行池」）；给每个 subagent 完整的上下文（它们看不到父会话）；subagent 是无状态的——一次调用一个任务，不指望它记住上次任何东西；结果里只保留有用部分（让 subagent 自己在总结时过滤）。

「无状态」这条是 Claude Code subagent 模型的定价标签，值得展开。因为无状态，派发成本极低（构造个精简上下文就行）、并发安全性好（互不依赖）、失败重试干净（重派一次即可）；也因为无状态，延续性任务要靠父会话手动串联——每个 Task 调用都是冷启动，之前的探索不自动继承。Codex 的 fork_mode: FullHistory 补的就是这块：子 agent 可以带着父的完整历史出生，代价是每个 fork 的初始上下文成本。便宜无状态的复制，和昂贵有记忆的分身，这是两种 subagent 哲学的第一个分叉点，后面的通信、恢复、重试成本差异都从这一点衍生。

frontmatter 里那个 tools 字段的语义也有讲究：["*"] 表示全量工具，也可以列子集（比如只给 Read 和 Grep 的「调研型」agent）。工具收窄不只是安全考虑，更是注意力管理——工具列表本身就是对模型行为的强提示，一个只有 Read/Grep 的 agent 几乎不可能跑去改文件，因为它看不见 Edit。自定义 agent 时把这个字段当「岗位说明书」来写，比在 system prompt 里写「请不要修改文件」可靠一个数量级。

二、Codex 的 subagent：一个 thread 就是一个调度单元

Codex 这边不玩变装，直接给每个 subagent 上户口——独立 thread、独立 Session、注册表登记，正式员工入职的全套流程。它的多 agent 是显式建模的，而且有两代实现并存：tools/handlers/multi_agents/ 是 v1，multi_agents_v2/ 是现役。v2 是一组工具族，不是单个工具：

  • spawn_agent（spawn.rs）：创建子 agent，支持 fork_mode（FullHistory 模式下继承父的完整历史）、角色指定、模型和推理参数覆盖
  • send_message / interrupt_agent：向运行中的子 agent 发消息或打断
  • wait：等子 agent 出结果
  • list_agents / followup_task：枚举和追问

派发链路在 core/src/agent/control/spawn.rs:207 的 spawn_agent：继承父的执行环境和命令策略，创建新 thread，登记进 core/src/agent/registry.rs 的注册表。每个 thread 有自己的 Session、自己的 run_turn——「派 subagent」在 Codex 里是真实的调度单元创建，走的是和主会话完全相同的线程管理链路（ThreadManager）。

并发控制是信号量式的：core/src/agent/control/execution.rs:14 的 AgentExecutionLimiter，initialize(max_threads) 设上限，每个 agent 启动前 ensure_execution_capacity_for_turn_start 检查容量，跑完由 AgentExecutionGuard 的 Drop 析构释放。上限本身是配置项：

// config/src/config_toml.rs:664-668
/// Maximum number of spawned agent threads that
/// can be open concurrently per session.
pub max_concurrent_threads_per_session: Option<usize>,

agent 之间的通信走 core/src/agent_communication.rs 加 context/inter_agent_message.rs：父用 wait 收结果、用 send_message 补充指令，子 agent 的输出作为 inter-agent message 进入父的上下文。对比 Claude Code 那边——subagent 的结果就是一个普通的 tool_result 回填，没有专门的通信层。

v1 和 v2 并存这件事本身也是个信号。v1 的工具集（spawn / send_input / wait / close / resume）是「进程管理」式的词汇，v2 换成了「协作」式的词汇（spawn_agent / send_message / interrupt_agent / followup_task）——从管理对象到对话对象的措辞迁移，说明这套 API 是在真实多 agent 使用中打磨过的，不是设计出来的。代码里还能看到 restore_v2_agent_metadata 这样的函数（在 spawn 链路里恢复 v2 元数据），新旧两代的兼容层被显式维护着。读快速迭代的项目，这种「地层」比任何文档都诚实地记录了演化路径。

Codex 的 subagent 还有一个容易被忽略的维度：角色（role.rs，有 DEFAULT_ROLE_NAME）。spawn 时可以指定角色，角色影响的是子 agent 的系统提示倾向和行为边界——同一个模型套不同的角色皮，出来的是不同工种。配合模型覆盖（每个子 agent 可以用不同模型），Codex 的一个 agent 树可以是异构的：拆解任务的用强模型、跑腿执行的用快模型，成本结构可设计。Claude Code 的 subagent 也有 per-agent 的 model 字段，但「树状异构编排」的完整度差一截——没有角色层，模型覆盖靠定义文件静态写死，改一次编排要动一次定义。

三、恢复能力：内存递归 vs 持久化图

两边差距最大的地方在这里。

Claude Code 的 subagent 活在内存里，是 generator 的递归——进程一退，集体蒸发，中间过程不留底，只剩每人最后一条 tool_result。会话恢复时重放的是主会话的 JSONL，中间过程怎么推导出来的，没了。对短任务无所谓，对「十个 subagent 各跑半小时」的任务，一次误关终端就是灾难。

Codex 为此建了专门设施：agent-graph-store crate 里 store.rs:17 定义了 AgentGraphStore trait，持久化 agent 的 spawn 边（谁派生了谁），支持按 subtree 查询 thread id。配合 rollout 的 JSONL 落盘加 SQLite 索引，重启后能把整棵 agent 树的结构和断点找回来。

为什么一个需要、一个不需要？回到第一篇的分层：单进程内存模型里，「恢复 subagent」这个需求不存在——恢复主会话就够了；多 thread 平台模型里，agent 树是真实存在的调度资源，不持久化就等于每次重启丢失生产资料。需求是架构造出来的，这句话在这里有了最直白的注脚。

拿一个我实际跑过的场景把恢复能力的差距具象化：让 agent 集群重构一个多模块项目——父 agent 拆出五个子 agent 各管一个模块，跑到四十分钟时机器要重启装补丁。Claude Code：重启后 claude --resume 恢复主会话，五个子 agent 的进度只剩五段 tool_result 摘要，哪些文件改了一半、哪些验证没跑，全要靠摘要猜，实际操作是让父 agent 重新盘点现场再补派——半小时的盘点开销。Codex：重启后 agent 树从 agent-graph-store 里读回来，每个 thread 的断点在 rollout 里，逐个 resume 继续跑——盘点成本接近零。一次重启，两种命运，这比任何架构图都更能解释「平台化」三个字值不值——值不值不取决于功能列表，取决于你的任务敢不敢托付给它过夜。我把最长的编排任务（跨夜的批量重构）只交给 Codex 跑，就是从这个场景对比之后开始的——不是偏好，是风险判断——判断的依据全部来自源码，不来自任何一方的宣传。

顺带说一个工程审美上的观察：AgentGraphStore 被定义成 trait，本地实现是 local.rs。也就是说 agent 图的存储位置被抽象出来了——本地是默认，但接口为「存到远端」留着门。配合 cloud-tasks 系列 crate，Codex 的多 agent 是奔着跨机器编排去的。这个抽象在单机用户眼里是过度设计，在平台视角里是必经之路，评价取决于你站在哪——以及你的 agent 两年后要跑到哪里。

四、上限与预算：三个数字的错位

把两边的并发控制数字排在一起，很容易看出设计重心的错位。

Claude Code 有三个相关数字：工具并行池上限 10（硬编码，L416878）；subagent 数量没有独立上限（受主循环串行轮次约束，Task 工具本身免权限检查——checkPermissions 直接返回 {behavior: "allow"}，L411591）；上下文预算按会话算，subagent 各自独立计。实际效果是：你能派的 subagent 数量很多，但每个 subagent 内部的工具并行度封顶 10。

Codex 的数字体系是分层的：agent 数量上限 max_concurrent_threads_per_session（可配置，默认值随版本变）；工具并发由读写锁保秩序（不安全工具天然串行）；token 预算归 compact_token_budget.rs 管，压缩触发独立计算。实际效果是：agent 数量是被显式管起来的资源，工具并发是被动保序的结果。

使用上的推论：在 Claude Code 里「多派几个 subagent 分头查」是低成本操作（无进程开销、免权限），真正的瓶颈是你等不起串行轮次；在 Codex 里派 agent 是申请资源（要过 limiter），但派出去的每个都是完整调度单元，能独立中断、独立恢复、独立换模型。前者把 subagent 当「带配置的函数调用」，后者把 subagent 当「一等公民的执行单元」。

成本结构还有个隐蔽维度，长任务编排时必须拆开看的成本：失败的重试成本。Claude Code 的 subagent 失败了，重派一次就是完整重跑（无状态的代价）；Codex 的子 agent 失败了，可以 send_message 补充信息让它原地继续（thread 还活着），重试成本只是增量。任务越长，这个差距越大——十分钟的子任务失败，一边再付十分钟，一边可能一分钟就续上了。做长任务编排时，这个账必须算。

把 v1 / v2 工具族和两边的机制并排收成一张表：

维度Claude Code TaskCodex multi_agents_v2
载体工具调用，复用主循环独立 thread，完整调度链路
状态无状态，冷启动有历史（fork_mode 可选继承）
通信单向：结果即 tool_result双向：send_message / wait
并发治理工具池上限 10（间接约束）信号量显式限流（直接约束）
中断独立 AbortControllerinterrupt_agent + 恢复
持久化无agent 树 + rollout 断点
模型异构定义文件静态指定spawn 时动态覆盖

这张表横着读是功能对比，竖着读是两套世界观。左列没有任何一行提到「资源」，右列每一行都在管理资源——这就是「函数调用」和「执行单元」的差别在表格里的样子。

五、选型落到任务形状上

这两套 subagent 机制怎么选，我按任务形状给判断。

探索型任务（多方向并行查资料、各自总结）用 Claude Code 顺手：派五六个 general-purpose agent 各查各的，结果汇总回主循环，轻快、无配置成本。我自己在做技术调研时基本都这么跑。

编排型任务（父 agent 拆解、子 agent 长时执行、中途要补指令、跑完要复盘）用 Codex 合适：fork_mode 继承历史省去重复交代，send_message 能中途纠偏，agent 树可恢复意味着长任务敢过夜。这套能力 Claude Code v1.0.88 一个都没有。

还有一类任务两边都别用 subagent：强顺序依赖的流水线。subagent 的价值在并行和隔离，串行流水线用它只会多一层汇总损耗，老老实实在一个会话里顺序跑，上下文还连续。

介于中间的「读多写少的长任务」是灰色地带，我的经验法则是：预计二十分钟以内、结果只消费一次的，Claude Code 的轻量派发划算；超过二十分钟、结果要反复引用、中途可能改主意的，Codex 的重装备回本。这条线不是源码给的，是两个机制的成本曲线交点的大致位置——轻量派发的成本是线性的（每个子任务全价），重装备的成本有固定开销但边际递减（thread 复用、断点续跑）。

给一个探索型任务的实际编排模板，来自我自己的高频用法：目标是「调研五个候选库的技术形态」。主会话先写一份五行的任务清单，明确每个方向要回答的问题和输出格式；然后一条消息里发五个 Task，每个 agent 的 prompt 里带任务行、输出格式约束和「不要修改任何文件」的边界；结果回来后主会话做横向对比收束。三个要点：并行数控制在五个以内（超过并行池 10 的半数，留余量给主会话的收尾工具）、输出格式必须提前定死（否则五个 agent 五种格式，对比成本转嫁给主会话）、边界写进 prompt，别指望 agent 自觉。这个模板的每个细节都能在前面的源码里找到依据——这就是「源码反哺使用」的具体样子。

编排型的模板我也有一个，但先声明它只适用于 Codex：父 agent 拿到需求后先出拆解计划，逐个 spawn_agent（带 fork_mode: FullHistory，省去重复交代上下文），执行中途用 list_agents 巡检、发现偏航就 send_message 纠偏，全部收敛后 wait 收结果做整合。跑这类任务前我会确认 max_concurrent_threads_per_session 的配置值——默认值未必匹配你的机器和 API 配额，限流触发时 spawn 会被 limiter 挡住，表现是任务「卡住不动」，不知道机制的人会以为是模型问题，知道机制的人调一行配置——这类「配置即能力」的细节，是读源码读出来的暗知识。

五点五、调试 subagent：看不见的工人怎么管

subagent 天然是个黑盒——它在自己的上下文里干活，父会话只看到结果。两边给的观测手段差异，又是机制差异的延伸。

Claude Code 这边，subagent 的存在感主要靠两个 hook 事件：SubagentStop（子代理结束时触发，可以阻止草率收尾）和 Task 工具调用本身的 tool_result。中途想看子代理跑哪了，v1.0.88 没有官方界面——transcript 文件里倒是有完整记录（每个 agentId 一段），但要自己翻。实操上我的做法是让每个 subagent 的输出格式里带一行进度摘要（做了几步、跳过了什么），牺牲一点输出 token 换可观测性。

这个「进度摘要」约定比看起来重要，展开说一下为什么。subagent 的结果回填走 tool_result，模型对 tool_result 的注意力分布是不均匀的——开头和结尾的权重高，中间的长篇过程容易被略读。把关键结论压进结果的开头第一行（比如「结论：X 可行，理由三条，详见下文」），父会话的后续决策质量明显更稳。这不是心理学玄学，是上下文工程里被反复验证的常规手段：在注意力的高价值位置放高价值信息。两个工具都适用，因为两个工具的 subagent 结果最终都以工具结果的形式进入父级上下文——这一点上两家倒是完全一致。

Codex 的观测是一等能力：list_agents 让父 agent（和你）随时枚举所有活跃 thread 的状态，配合事件流里每个 thread 的事件（protocol 层面 thread id 是显式字段），跑偏的子 agent 在 interrupt_agent 之前就能被定位。TUI 里还有 agents overview（codex agents 命令直达）——多 agent 运行时开着这个页面，等于有了集群的驾驶舱。

失败模式的排查思路也因此不同。Claude Code 里 subagent 结果不对，第一反应是重派（反正无状态）；Codex 里第一反应是 send_message 问它为什么这么做（上下文还在，能问出真相）。前者锻炼重试的勇气，后者锻炼调试的耐心——听起来像段子，但确实是两个机制塑造出的两种工作习惯。

六、设计反思：subagent 的本质之争

写完这篇我停下来想了一个问题：subagent 这个词，两边指的是同一个东西吗？

表面上是都是「派生出来的子任务执行者」，但源码读下来的感受是：Claude Code 的 subagent 是提示词工程的产物，Codex 的 subagent 是操作系统设计的产物。到这里可以把开头那个招聘比喻正式结案：Claude Code 招的从来不是临时工，是自己换装再入职；Codex 才是真的在盖写字楼招人——一个在控制一次函数调用的成本，一个在管理一组生命周期完整的执行单元。前者的全部机制（精简上下文、无状态、免权限、结果即 tool_result）都能用「怎么让一个循环安全地复用自己」解释；后者的全部机制（thread、注册表、信号量、消息总线、持久化图）都能用「怎么管理一组生命周期完整的执行单元」解释。一个向内压缩复杂度，一个向外扩展能力面。

这个判断还有一个自检方法，读者可以拿来验证我说得对不对：把两个产品 subagent 机制的任何一行，试着反推出它的「上一行」。比如 Claude Code 的「subagent 免权限」反推上去是「权限守在工具层」（第五篇会展开），再往上推是「单进程没有执行环境的隔离层」；Codex 的「spawn 边持久化」反推上去是「thread 是资源」，再往上推是「多进程平台模型」。每条机制都能沿着因果链爬回第一篇的架构图，爬不回去的就是我过度解读了——这六篇的论证结构就是这么互相咬合的，单篇可读，合起来是一张网——每篇的开头钩子也都是这么选的：只挑能被后文源码兑现的那类悬念。

这个分歧往下还有一层：它决定了「多 agent」在这两个产品里的天花板。Claude Code 的多 agent 上限是「一个聪明的调度者带一群临时工」，复杂协作要靠调度者的上下文容量撑；Codex 的上限是「一台能管理的机器跑一群员工」，复杂度由基础设施承接。今天的单人开发场景两者够用度的差距不大，但一旦你要把 agent 集群放进 CI、挂上云端、跨项目复用，只有后一条路走得通。

多说一句这个判断的来路，免得它显得像立场先行：我自己在多 Agent 评审的实践里踩过这个边界的原型——多个评审 agent 并行读代码各自出意见，这个规模 Claude Code 的轻量模型完全够用；但当我想把「评审 agent 常驻、增量跟进一个分支的演进」做下去时，无状态模型的重复交代成本立刻上来，每次都是冷启动，上下文传递靠复制粘贴。那篇实践里我最后用外层脚本硬补了状态管理——现在读 Codex 的源码，它把我要的这些东西（注册表、消息、恢复）全部做成了内置件。个人脚本能补的是缺件，补不了的是缺层。

最后把这篇的判断和前几篇串起来：单进程单体（第一篇）决定了主循环是 generator 递归（第二篇），generator 递归决定了 subagent 只能是「带配置的再入」（本篇）。Codex 的每个选择反过来。没有谁的路线更先进，只有「终端个人工具」和「可部署执行引擎」两种产品定位的差异，一路从架构层渗到 subagent 的实现细节里。下一篇讲上下文管理：同样是「快满了怎么办」，一个先清工具输出、一个双路压缩，差异同样能一路追溯到分层。
