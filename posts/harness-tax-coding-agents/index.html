你的 Claude 不一定需要 Claude Code：成功率只差 1%，账单差 2 倍

先看一组我自己量出来的数。agent-autopsy 是一个专门抓包整理各家 coding agent 提示词的开源仓库，作者把 Claude Code、Codex、antigravity 这些壳运行起来，从实际发出的请求里截获系统提示词和工具定义，按模型分档存档。我把里面 Claude Code（Fable 5.1）那份下载下来量了一遍：系统提示词全文 10.4KB，六个章节；工具定义 37 个，按「单次请求实际发送一份」的口径合计 154KB，其中纯描述性文字 9.1 万字符，占六成。最大的一件是 Artifact 工具，光使用说明就 2.4 万字符，一个工具的说明书，是整个系统提示词的 4.7 倍。

也就是说，Claude Code 每次接活，模型要先读完将近 4 万 token 的「入职材料」才碰得到你的代码。这份材料不便宜：按 token 计价，它是每次请求都要重复支付的首包成本。

它买到智商了吗？2026-09-16，UC Berkeley Sky Computing Lab 和 LMArena 团队发了一项测量，名字起得很直白：HarnessTax（harness 税）。结论是：同一个模型，换个 harness，成功率只动 1 个百分点上下，账单差 2 到 5 倍。

这篇拆三件事：这笔税怎么测出来的、钱花在了哪里、什么情况下交得值。最后回到开头那份 4 万 token 的入职材料，它该不该瘦，答案在测量里。

先把账本摊开：HarnessTax 测了什么

harness 这个词，中文圈常译成「壳」或「执行框架」，指包裹在模型外面的那层工程：系统提示词、工具定义、权限控制、上下文管理、执行循环。Claude Code 是壳，Codex CLI 是壳，Pi 也是壳。模型本身只有一个，壳可以有无数个。

要回答「壳值多少钱」，得把壳和模型的组合拆开量。HarnessTax 的做法是控制变量：7 个模型 × 3 个 harness，组成 21 组配对，跑同一批任务。基准选了两个：SWE-bench Lite 每次跑 30 题、每题重复 3 次；Terminal-Bench 2.0 测终端环境里的真实操作。每个任务给到 100 轮 agent 交互的上限，统一开 high effort 档，用官方评测器判分，价格按 2026-09-01 的固定价目表逐题核算，最后用 1 万次 bootstrap 重采样给出置信区间。

这个设计里有几个细节值得单独说，因为它们决定了读数可不可信。

判分用官方评测器，不用模型自评。agent 自己声称「修好了」的验收风险，我在 DeepSeek Harness 的一次错误验收复盘认真吃过亏，官方测试套件通过才算解决，堵住了这条路。每题跑 3 次取均值，压掉单次采样的运气成分；100 轮上限防止单题无限烧钱把方差拉爆。

价格口径也有讲究。各家壳的订阅价是打包的，不透明也没法逐题分摊，论文统一用 API 牌价核算。这意味着读数时要注意：论文里的成本是「API 重度用户」的成本，包月套餐用户的实际支出结构不同，但税的比例关系不变，因为税来自 token 流量，套餐改变的只是单价。

还有一条容易被忽略的口径：成本里包含失败尝试。你为一道题付的钱，是壳在这道题上烧掉的全部 token，包括那些最后没修好的路径。所以「成本」衡量的是你真实会收到的账单，不是理想路径的最优价。

这个设计最值钱的部分是「同一模型 × 不同壳」的配对本身。模型能力榜已经卷了两年，壳的榜单几乎没有。你在各种测评里看到的分数，都是「某个模型套某个壳」的合体成绩，从来没人把两层拆开分别标价。HarnessTax 干的就是拆标签这件事。

往下读之前，先记住一个简化模型：模型决定能不能解出来，壳决定每一步花多少钱。成功率看模型和任务的匹配，成本看壳的 token 流量。后面所有数据，都是这个两分法在两个基准上的实证，也都会回到它。

发现一：成功率几乎不动，账单翻倍

先看最容易挑战直觉的那组数。同一个 Claude Fable 5，在 SWE-bench Lite 上：套 Claude Code 跑出 97.8% 的解决率，每题成本 $1.33；套 Pi 跑出 96.7%，每题 $0.67。成功率差 1.1 个百分点，价格差 2 倍。

这不是单点侥幸。两个基准、21 组配对全部跑完，harness 的选择对成功率的影响是：SWE-bench Lite 上 ±2%，Terminal-Bench 2.0 上 ±5%。而对成本的影响，组间最大差到 5 倍。按几何平均算，Claude Code 的账单约是 Pi 的 2.0 倍、Codex CLI 的 1.6 倍；换成终端基准 Terminal-Bench 2.0，Claude Code 仍是 Pi 的 1.5 倍。按 API 牌价折算到团队规模：一个月跑 500 道题的工作量，Claude Code 和 Pi 的支出差出六百多美元，人没多干任何活。

成功率那根柱子几乎齐平，成本这根柱子差出一倍，两张图放在一起，就是「税」的形状。你多花的钱没有变成更多的解题能力。

为什么成功率会纹丝不动？机理不难推。SWE-bench 这类任务的瓶颈在模型对代码库的理解和修改规划，三个壳都提供了读写编辑加终端的等价工具面，工具数量的差异被模型的规划能力抹平了。壳能决定的只是「每一步怎么包装」，决定不了「往哪一步走」。

终端基准的 ±5% 比 SWE-bench 的 ±2% 大，这个差异同样有信息量。终端任务里，壳的权限确认流程、超时重试、输出截断策略会直接干预每一次真实操作，壳从包装层变成了操作层的一部分。壳在终端场景里更能帮倒忙，也更可能救场——这解释了为什么选壳不能只看 SWE-bench 分数。

发现二：4 个工具的极简壳，打平 37 个工具的全家桶

Pi 是这三个壳里最极端的一个：整个工具箱只有 read、write、edit、bash 四件，系统提示词短到可以一屏读完。按常识，这种「裸奔壳」遇上复杂任务应该翻车，工具不够用，模型得绕路。

实测轮次打脸了这个常识。同一个 Fable 5，Pi 平均 15.4 轮解完一题，Claude Code 平均 15.3 轮。轮次几乎一样，说明壳的复杂度没有帮模型少走弯路；但成本差一半，因为 Claude Code 每一轮都背着更重的首包上下文。论文给出的测量是：Claude Code 的初始上下文是 Pi 的 10 倍以上。

把这笔开销按轮数展开，10 倍差的来源就清楚了。agent 的每一轮请求都要把系统提示词、工具定义、到当前为止的全部对话历史整体重发一遍，新增量只占这一包的一小截。粗算一下：15.3 轮 × 约 4 万 token 首包，Claude Code 光首包部分就重复发送约 60 万 token 输入；Pi 用不到 4 千 token 的首包跑 15.4 轮，同样部分只有约 6 万。差价主要从这里来，模型调用次数本身几乎不贡献差异。

这就是税的第二个特征：安装费只付一次，这笔税每一轮请求都重复收一遍。15 轮任务，那份 4 万 token 的入职材料就跟着走 15 遍。HN 上有位评论者把这总结得很准：两个壳可以让模型「干一样的活，烧完全不一样的钱」。

税从哪来：说明书，不是护栏

到这里必须正面回应一个质疑，因为它是 HN 讨论里点赞最高的一派：多出来的重量是安全护栏，把这笔开销叫「税」不公平。原话很锋利：「为什么不交垃圾处理费？因为往海里倒免费。」意思是，Claude Code 和 Codex 的体积是为了安全和行为约束付出的必要成本，把它说成纯粹的浪费，等于把不安全当成了免费的外部性。

这个说法可以直接对着数据检验。我前面量的那份抓包里，系统提示词全文 10.4KB，就算把它整个算成安全条款，也只占首包的零头。大头是 37 个工具的 JSON Schema：合计 154KB，其中 9.1 万字符是纯描述文字。占比最大的一件我核对过原文：Artifact 工具，2.4 万字符的说明书，教你什么时候该渲染一个网页 artifact、怎么收集用户输入、页面更新后怎么同步。写得确实细，但它是产品说明书，不是护栏。

HN 上另一位评论者说得更准：他读过 Claude Code 的系统提示词和工具定义，「为了安全」的行数是少数，膨胀的大头就是工具描述。他把抓包仓库的链接贴在了讨论里，我照着量了一遍，数据支持他。

工具清单的构成本身也值得看一眼。37 个工具里，任务管理就占了五件（TaskCreate、TaskGet、TaskList、TaskUpdate、TaskOutput），定时任务三件（Cron 系列），工作树进出两件（EnterWorktree、ExitWorktree）。每一件新功能都自带一份说明书进首包：功能加一件，税率涨一格。这也意味着壳的「功能列表」在选型时是个反向指标，功能越多，你的首包越重，除非壳做了按需加载。

顺手也验证了「安全需要重量」这个前提本身站不住。讨论里有人给 Pi 套了一层运行时沙箱（nono.sh），系统提示词一个字没加。沙箱是运行时的一堵墙，不是说明书里的字数，用 prompt 字数实现安全本来就不牢靠，这一点 DeepSeek Harness 的沙箱设计里拆过更彻底的做法：fail-closed，默认拒绝，权限不靠模型自觉。

顺带一个实用级细节：想给极简壳手动配沙箱工具也有坑。Pi 的 --tools 参数只能在内置工具上做加法，不能替换；而它的扩展默认加载，扩展可以自带工具绕过 --no-tools。想锁死工具面，得把扩展也关干净。这个坑 HN 上有人完整踩过一遍，留给打算给瘦壳补安全层的读者。

最意外的一条：自家模型配自家壳，经常不是最优

前面两条还只是「贵的壳不物有所值」，第三条开始伤感情了。HarnessTax 把「模型厂自家模型 × 自家官方壳」当作一组特殊配对来测，12 组对照里，有 9 组的结果是：换个别的壳，更强或者更便宜。

两个具体数。Claude Sonnet 4.6 在 Codex CLI 里跑出 68.9%，在自家 Claude Code 里是 66.7%，价格相近，Anthropic 的模型套竞争对手的壳，反而高了 2.2 个百分点。更显眼的是 GPT-5.6 Sol：在 Terminal-Bench 2.0 上，Pi 里 83.3%、$0.42；自家 Codex 里 78.9%、$0.76。更强，同时价格接近一半。而 OpenAI 对 GPT-5-Codex 的官方描述是「为 Codex 里的软件工程优化」，同门组合不保证最优配，论文专门把这句写进了标题级结论。

这组数据对选型的含义很直接：「模型和壳是官方一对」不构成任何购买理由。你买模型的能力，壳是工程件，工程件就按工程件的标准验收：首包多重、轮次多少、账单多少，一项项对数。

什么时候这笔开销交得值

把 HarnessTax 读成「Claude Code 不值」，是对它最大的误读。有三条边界，每条都有实测或实证支撑。

第一，小模型的方向是反的。 HN 上被反复引用的一条经验：模型越小，harness 越重要。小模型管不住自己的上下文，需要厚壳替它做记忆、压缩和流程控制；一份塞满细节的说明书对强模型是税，对小模型是拐杖。HarnessTax 测的是强模型档，「壳越瘦越好」只在模型能力足够的区间成立。给小模型上极简壳，大概率翻车。

第二，任务越长，税越薄。 那份 4 万 token 的首包是固定成本，任务 10 轮结束，它占大头；任务跑 500 轮，摊到每一轮就薄了。长任务里壳的工程能力（上下文压缩、断点恢复、权限控制）开始主导结果，首包税退居其次。税的痛感集中在短平快任务，而这恰好是日常用得最多的场景。

第三，说明书贵不贵，还要看缓存。 同一份说明书反复发送，如果前缀稳定，prompt cache 能把重复部分的价格打到一折以下。DeepSeek Harness 的缓存纪律里记过一个 30 倍的差价：同一道题，缓存命中和 miss 的价格差 30 倍，而砸掉缓存的常见原因就是壳改动提示词前缀。所以准确的读法是：首包 token 量决定税率，缓存命中率决定实付。一个首包大但前缀稳定的壳，实付可能比首包小但每轮乱改前缀的壳更便宜。壳的更新策略也直接影响你的支出：每次升级都重排系统提示词的壳，会把存量缓存全砸掉；保证提示词前缀向后兼容的壳，等于替你把重复部分长期锁在折扣价里。

还有一条平衡观点值得记录。HN 上有位用 Pydantic-AI 自己套薄壳的开发者说，harness 很关键，但 harness 之间的差异被高估了：几个主流壳都能把活干完，差异集中在付费方式和权限模型上。这和 HarnessTax 的数据并不矛盾，成功率差异确实小（±2%），这篇论文收的是成本维度，不是能力维度。

心智模型：把模型和壳分开标价

回头看开头那份 4 万 token 的入职材料。量完这一圈，我对「壳」的认知收敛成三句话。

第一句：模型和壳分开付钱。模型的钱买智力，壳的钱买工程：首包说明书、轮次开销、权限与恢复。任何「官方一对」的捆绑都不构成默认理由，21 组配对里自家组合有四分之三被别家壳超了。

第二句：看壳先看首包构成，再看缓存纪律。功能列表决定不了成本，首包里系统提示词和工具说明书各占多少、前缀稳不稳定，才决定你每轮实际付的钱。工具多不是罪，说明书按 token 计价：37 个工具的全家桶和 4 个工具的极简筒解出同样多的题时，多出来的体积就是纯税。

第三句：模型越强，壳越该瘦。模型能力是分母，说明书是分子，分母越大分子的痛感越强；分母小的时候，厚壳反而是在帮模型。所以「该用 Claude Code 还是极简壳」没有全局答案，只有「你的模型多强、任务多长、缓存命中多少」这三个变量代入后的局部答案。

这套变量代入的评估法，也可以反过来用在向上游要东西上。下次评估一个 agent 产品，值得直接问供应商两个数：首包上下文多大、缓存命中率多少。HarnessTax 证明了这两个数对成本的预测力，比任何功能列表都强。

这正是我这半年读 DeepSeek Harness 源码时反复看到的工程取向：提示词按 section 注册、按 profile 装配，工具以插件按需挂载，133 个插件不等于 133 份说明书同时进首包。当时我只当这是干净的架构设计，HarnessTax 把它变成了钱的问题：按需挂载的每一刀，都是从税率上剪下来的。你的下一个 agent 项目不一定照抄 dsh，但「首包里放什么」值得成为设计评审的固定议题，因为测量已经证明，那不是风格问题，是账单问题。
