一条命令 12 秒背后：DeepSeek Harness 插件挂载链路拆解

About 400 words 2 minutes

社区仓库三天从两百多个插件涨到一千四百多个，安装命令却长得一模一样。我在实测那篇里跑过：装一个 JSON 查询工具，从回车到挂载完成，秒表停在 12 秒。

快得让人怀疑它没干活。所以这篇把 12 秒拆开看。先给结论：dsh 没有自己实现任何安装逻辑，这条命令是一次 pnpm 转发加两处文件写入。魔法不存在，存在的恰好是「没有魔法」。

全文按链路顺序走：命令转发、落盘双写、重启组装、profile 组合机制、两条验证路径，最后算两笔容易被忽略的代价——中途插件的缓存钱和 Node 版本的门槛。

一、命令本身：一次 pnpm 转发

实测命令是这个样子：

dsh plugin --profile web add "github:dsh-external/dsh-tool-json#main"

dsh plugin 子命令的第一步，是把自己收到的参数原样转发给 profile 目录里的 pnpm。没有自研的下载器、版本解析器、依赖求解器。指定 --profile web 时，pnpm 的工作目录就是 ~/.dsh/profiles/web。

转发完还没有结束。CLI 源码里这条命令自身只干两件事：跑完 pnpm 之后调 reconcilePlugins()，按安装结果回写 bundles 清单；再用 exportsPatch() 判断装进来的包有没有声明 dsh.bundle 字段，声明了才把它当补丁层对待。安装器自己的代码量小到可以一口气读完，因为它把最难的部分外包了出去。

这个选择跟整个项目气质一致。包管理是 npm 生态几十年踩出来的成熟领域，自己造下载器除了多一段要维护的代码毫无收益。dsh 的做法是把 GitHub 仓库直接当来源（github:user/repo#branch 格式），依赖解析全部交给 pnpm，自己只管转发和记录；插件发现则退化为 npm 加 GitHub topic，给仓库打上 dsh-plugin 标签就能被搜到。

二、落盘：两个文件被同时写入

pnpm 跑完后，profile 目录里有两个文件被动了：

~/.dsh/profiles/web/
├── package.json        # dependencies 多了 @deepseek-ai/dsh-tool-json
└── (dsh.profile.bundles) # bundles 列表追加同一个名字

第一处好理解：依赖表里加了包名，这一步就是标准 pnpm 行为。

第二处才是 dsh 自己维护的归属清单：dsh.profile.bundles 列表追加了同一个名字。bundle 是 dsh 插件树的装配单位。五层拆解那篇讲过，插件树是容器组织代码的方式，一个第三方仓库就是一个 bundle，装进 profile 就成了树上的一层。

为什么必须双写？只写 package.json，pnpm 知道这个包存在，但 dsh 不知道要不要把它挂到树上；只写 bundles，声明了归属却没有实体。两个文件对上号，包才算被「认领」。这个设计和 git submodule 的心智模型很像：.gitmodules 是意愿清单，内容本体放在仓库对象库里，两边都在才算数。

双写之外还有一个容易漏看的分支。包如果在 package.json 里声明了 dsh.bundle 字段，它会自带一份 cordis.patch.yml 补丁层，重启装配时自动参与层序；没有声明的包只是个普通依赖，还得你自己在 cordis.yml 或补丁文件里手动给它挂入口。装上了和激活了始终是两回事，top10 里那个不走常规安装命令的 anchored-standard，走的就是后一种形态。

三、重启那几秒：插件树是怎么组装出来的

12 秒装完的那个瞬间，插件并没有开始工作。这是整条链路里最反直觉的一环：dsh web 重启之前，新装的插件只是一段安静躺在 profile 目录里的配置。原因是架构性的：运行中的插件树不做热插拔，生效动作整体推迟到下一次启动。

启动之后的组装顺序，官方文档写得毫不含糊：先按 profile 列出的顺序应用每个 bundle，然后是 profile 自己的 cordis.patch.yml，接着是 home 级的那份补丁，最后是指定 --patch 传进来的 overlay。patch 按 id 定位某个条目并替换它的整行 config，同 id 后写的胜出。你刚装的包，就排进这条队列里等一个位置。

两个细节来自五层拆解时对 patch 语义的核对。其一，patch 替换的是条目的整行 config，不做字段级合并，想让同一个插件在不同 profile 拿到不同配置，正确做法是拆成各自的 bundle 层，指望 patch 单独覆盖一个字段是行不通的。其二，patch 里各行的先后顺序不承载加载语义，激活由服务可用性驱动，行的排布只为方便人读。「排队亮相」说的是叠加结果，具体哪个插件先活过来，由上一段那台依赖状态机说了算。

队列就位后，Loader 开始逐个处理入口。每个入口的命运是固定的五步：import 模块、unwrap 导出、注入依赖、执行 apply、失败回滚。插件实例在 Cordis 内核里是一个叫 fiber 的状态机，从 pending 走到 active，最终走到 disposed。inject 声明的依赖服务没就绪时，fiber 停在 pending 等待；依赖的满足方式是状态机等待，Service.check 确认可用后才放行，谁也不催谁。

apply 是同步注册一切的位置：挂服务、注册工具、监听事件都在这一步完成，之后插件就退化成一组挂在 Context 上的服务和监听器。卸载走 dispose 语义，清理函数按注册的逆序执行。某一个 fiber 激活失败也只回滚它自己的副作用，其余插件照常工作，一棵树不会被一个坏包拖垮。

启动流程的最后还有一道审计：boot 会逐个检查 entry 的 fiber 是否真的激活，配置里写了却没能激活的插件直接报错。这道检查把「装了但没生效」的灰色地带从系统里赶了出去，要么明确挂上，要么当场报错，不存在第三种安静的状态。

所以「重启」属于组装流程本身。你在那 12 秒里买到的是一个承诺，兑现时间是下次启动：命令行负责把意愿写进配置，启动负责把配置变成一棵真的树。隔开两者的那一次重启，缩短不了。top10 排错清单里「装完没生效九成是没重启」那条结论，根由就在这一段的结构里：生效只发生在启动，重启就没有任何绕开的方式。

四、profile 参数背后是一整套组合机制

回头看安装命令里的 --profile web，它的分量比一个目录参数重得多。官方定义里，profile 是 Harness home 中的一份具名组装：列出自己叠放的 bundle，存放自己安装的树外插件，还保存用户自己的 cordis 补丁文件。web 和 headless 两份模板随发行版交付，初始层来自模板声明：web 版由 dsh-base 打底再叠 dsh-web-app，前者装着模型适配器、工具、持久化、沙箱与审批策略这些底盘能力；headless 版换上的则是一个不带服务器的一次性运行器。

多 profile 并存是官方认可的用法，也成了我的日常分工：web 那棵树装界面增强和视觉全家桶，headless 只保留跑批真正用得上的两三个插件，看板和交互面板挂在无人值守进程上纯属浪费。两棵树互不共享插件，装两遍是常态而非疏忽，两边共用的是配置里的 API key，不必配第二次。

profile 还给得起后悔药。整个 profile 就是磁盘上一个目录，试一堆心里没底的新插件之前，先整目录拷一份当快照，出了问题原地还原，比逐个 remove 快得多。卸载本身和安装完全对称：remove 接的是包名而非仓库地址，卸完同样要重启，才算真正从树上摘掉。

验证哪个 profile 就指定哪个。dsh --profile web --dump-config 是官方文档里的原样命令，下一节的核对动作对 headless 同样成立，换个参数而已。

还有一个长期提醒藏在体验里：每多装一个插件，启动时的树组装就多一分工作量，装到二十个以上启动明显变慢。这台机器挂过 133 个插件，我对这件事的体感非常具体。定期用 remove 做减法，本身就是这套机制的组成部分。

五、验证：说不算就不算

装完重启，最后一步是确认真的挂上了。两条路任选。

命令行走 dsh --dump-config，输出里会多出一节：

# == @deepseek-ai/dsh-tool-json
- id: tool-json
  name: '@deepseek-ai/dsh-tool-json'

每一节对应一个最终生效的插件入口，输出的整体就是组装完成后的那张清单。这条命令还带 --profile 参数，想核对哪棵树就指定哪棵。

清单还有个进阶用法：留意条目出现的先后。顺序是叠加过程的产物，dsh-base 层的底盘入口在前，后装的第三方在后；两层里出现同名 id 时，按「同 id 后写胜出」的规则决定归属，这份输出能让你直接看出覆盖发生在谁身上。

界面走设置页 Plugins → Plugin list，找到新插件，状态显示 Mounted、Enabled 才算数。我本地 133 个插件同挂时就是靠这个列表挨个核对的。

挂载状态之外还值得多做半步：拿新插件开一个最小任务，让它真的执行一次自己的工具或技能。列表只证明树上有它这个节点，功能链路通不通要跑过才知道；这一步和 dump-config 的清单核验是一对，一个对配置负责，一个对行为负责。

顺手补一个装失败时的判断技巧，同样是实测攒下来的：报错只有 WARN 字样、重启后 --dump-config 能看到新插件的，属于 peer 依赖版本的良性警告，忽略即可；直接抛 ERR_PNPM、bundles 列表里也没写进去的才是硬失败，别反复重试，先对比本地 dsh 版本和插件 README 声明的适配版本差了几个 rc。

六、中途装插件，烧的是另一种钱

时机的代价值得单独立成一节，因为它花的钱最隐蔽。KV 缓存按请求前缀做逐字节比对，从第一个字节起任何一处变动，都会让它身后的一切重新计价。dsh 官方价格表上缓存命中和未命中的输入单价能差到三十倍，这份折扣全部押在前缀稳定上。

插件动的偏偏是前缀的源头区域。激活时它会往 system prompt 注册表注入新段落，往工具清单里塞 schema，这两处都位于共享前缀的上游。长任务跑到一半装插件，付出的不止「这一轮没生效」，还有已产生上下文攒下的折扣一次性清零。切换运行模式同理，极简模式和标准模式拼出的 prompt 不同，切换瞬间等效于给会话换了个开头。

对照着看会更清楚这笔钱有多大。同一份架构里，上下文压缩是不废缓存的：旧对话前缀一字未动地保留，压缩指令作为末条消息追加在后面，整趟压缩请求几乎全程命中。同一个设计者给了两种操作完全不同的待遇，区别只在动没动前缀。写代码的人把规则守得这么死，用的人没有理由在中途随手打破它。

所以装插件的正确窗口是任务间隙或阶段收尾。这也反过来解释了官方为什么把生效钉死在重启：把会震动前缀的动作集中到确定性的边界上做，比散落在任务中间便宜得多。前缀稳定的三条源码纪律，我在缓存那篇里逐条核过，中途装插件属于最容易亲手打碎折扣的动作之一。

七、Node 版本这道硬门槛

环境侧只有一道硬门槛，但足够阴。Node 版本低于 22.14 时 dsh 直接起不来，v22.13 实测崩溃，报错信息却完全不提 Node 三个字。根源在会话持久化链路用了 zstd 压缩：createZstdDecompress 是 Node 22.14 才进入 node:zlib 的导出，版本差一步就在加载期断掉。nvm 用户 nvm install 24 切到 LTS 即可解决。

上手篇里有完整的环境清单，动手前值得照着过一遍。这道版本门槛是发布当天实测出来的，别问我怎么知道的。另外 dsh 预览期三天发过六个 rc，插件作者适配的 rc 号和你本地版本的差距，本身就是装配问题的第一大来源，装之前看一眼仓库 README 首屏的适配声明，能省掉大半排错。

走完这条链再看「12 秒」这个词，感受会不太一样：一次标准化的 pnpm 转发，两处明确的文件写入，一次启动组装，两条可验证的确认路径。每一步都有中间产物可以检查，没有任何一步是玄学。

这套朴素是最该学的设计。让专业工具干专业的事（pnpm 管依赖），自己的部分收敛成一份清晰的状态文件（bundles 清单），把生效时机钉死在确定性最高的点（启动组装）。做到这三条，功能再复杂，链路也不会烂。
