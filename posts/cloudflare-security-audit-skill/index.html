我先把 security-audit-skill 的仓库拉下来数了一遍：15 份 Markdown，加 4 份校验脚本和 1 份 JSON Schema，一共 20 个文件，官方博客说它的起点约 450 行。就这么大的一个技能，官方博客给出的内部战绩是：累计报出 20799 个候选漏洞，一路独立验证筛下来，7245 个是可行动的真洞，扫的是 Cloudflare 内部 145 个仓库。

450 行的技能，七千多个真洞。这个落差是我写这篇的原因。

你可能和我一样，早就察觉到一个别扭的现状：AI 写代码的速度越来越快，Claude Code 一个会话能产出几千行，但「查这些代码」这件事，还停留在人肉 review 加几十年前的扫描器。写代码的范式换了，查代码的范式没换。2026-09-21 这天，这个仓库单日涨了 2428 星。对建仓以来日均 195 星的增速，这是 12 倍，市场显然也在等这个答案。

这篇文章分六块把它讲透：它是什么，六个阶段怎么跑，靠哪三条纪律防止「自己骗自己」，结论为什么只分三档，怎么一条命令装上，以及它防不住什么。总览图先放这里，后面逐段展开。

一、它是什么：450 行的种子，七千个洞的出身

security-audit-skill 是 Cloudflare 官方仓库，MIT 协议，2026-06-18 建仓。它出自 Cloudflare 本家：自家漏洞发现系统（vulnerability discovery harness）的种子版本直接开源，官方博客《Build your own vulnerability harness》把来龙去脉交待得很清楚。

账本是这样的。那个约 450 行的技能，在 Cloudflare 内部被长成一整套系统：一个负责发现漏洞的流水线（VDH），加一个负责验证漏洞的系统（VVS），两边用不同的模型互相校验，覆盖了内部 145 个仓库。

运行结果累计报出 20,799 个候选，独立验证筛到约 12,057 个，跨系统合并去重时折叠掉 5,442 个重复、回收 1,154 个打错目标的发现，落定 7,245 个可行动的真漏洞。随着反馈循环转起来，初次验证的拒绝率从 40% 压到 11%，高完整性发现的占比从 35% 提到 58%。

关键在于这句官方原话：技能里的攻击场景和反模式检测，基本原样保留到了现在的系统里。换句话说，你今天从开源仓库拿到的，不是玩具 demo，是那套七千洞系统的核心流程文件。长出去的部分是工程规模：从单仓技能到全公司扫描器花了约六周，worker 池开到 50 到 200 个 agent。而流程本身，450 行里已经写完了。

为什么这事值得单独写一篇？因为市面上 AI 安全工具不少，但把「怎么查」的流程纪律原文开源出来的，我只见过这一个。大多数工具给你一个黑盒扫描器，这个仓库给你的是一份可以逐字阅读的审计方法论。

二、六阶段：一次审计的完整流水线

技能的用法是在项目里对你的 AI 助手说一句「审计这个代码库」，剩下的流程由 SKILL.md 编排，分六个阶段跑。逐个说。

第一阶段，侦察。 助手先画地图：架构图、信任边界、输入口、历史漏洞证据，产出两份文件。architecture.md 记录架构结论，coverage-ledger.json 记录「查了什么」。注意这个账本文件，它是后面所有故事的伏笔。

第二阶段，猎捕。 从账本的单元出发，派出相互隔离的猎手 agent 分头找洞。每个猎手只管自己那一块，查过什么、怎么查的，逐条记回账本。

另有一类「覆盖批评者」agent，专职审账本找盲区：哪里还没人查过，就往哪里加派猎手。

第三阶段，证伪。 每个候选漏洞，交给一个全新的 verifier agent，它的任务只有一个：推翻这个候选。注意是全新的：不带找洞那个 agent 的任何上下文。

第四阶段，落账。 验证完的结论写进 findings.json，分三种标记：确认（confirmed）、待验证（needs_validation）、驳回（rejected）。这个文件要过 report-schema.json 的机检，还有一个零依赖的 Node 脚本 validate-findings.cjs 在关卡上卡格式，写错就过不去。

第五阶段，复核。 再派新 agent，对终版记录逐条核对源码证据。如果核对过程中材料被替换过，这条记录还要再过一道独立 verifier。也就是说，一条结论从出生到落纸，最少经过两拨互不相识的 agent。

第六阶段，报告。 从核实过的记录生成三份交付物：给人看总报告，逐条漏洞明细，以及一份待验证清单。每条都带源码位置，可以直接点过去对。

整个流程里我的观感是：它不像「跑了个扫描器」，更像雇了一个严格遵守流程的审计团队，有分工、有底稿、有交叉复核。下面这三条纪律，是这个团队的灵魂。

附：十一份攻击面手册，决定了它往哪里看

猎手不是凭感觉乱翻代码，每个猎手领到的是预写的攻击手册。仓库把攻击面分成十一份手册：一份核心攻击类清单（常规、通配、显而易见三类），加十份按领域分好的文件。

十份领域手册分别是：内存安全与二进制、AI 与 LLM（提示注入、代理与工具、输出处理）、Web 协议与认证、客户端（DOM 注入、消息信任、原型污染）、供应链与发布（依赖、CI、签名、更新）、云与部署（IAM、基础设施即代码、容器、无服务器）、协议与 RPC（序列化、队列、webhook）、资源耗尽与可用性（配额、队列、成本）、数据隔离与生命周期（租户隔离、缓存、导出、备份、删除恢复）、桌面移动与本地 IPC（深链、webview、守护进程）。

这份清单值得单独列出来，因为它就是「查什么」的完整答案。

两份手册值得多说一句。AI 与 LLM 那份，查的是「你接了大模型的这段代码」本身会不会被提示注入打穿，这在两年前还没有一本正经的工具会查。数据隔离那份，把租户隔离、缓存串数据、导出越权、删除后恢复这些 SaaS 常见事故点全部列成了狩猎条目。你不用逐条读完也能看出编写态度：每一条都对应一类真实事故，不是 OWASP 十项的复制粘贴。

三、三条纪律：怎么防止 AI 自己骗自己

3.1 查漏洞的和找漏洞的，永远是两个助手

这是整套设计里最狠的一条。README 的原话是：验证某个发现的 agent，永远不是发现它的那个 agent。

原因不难想。同一个上下文里，一个 agent 花了半小时论证「这里有洞」，你让它再验证一遍，它会不自觉地把模棱两可的证据读成实锤。人会手软，模型也一样，因为它对这段对话有路径依赖。技能的做法是物理切断：证伪的 verifier 拿到的是干净上下文，只有候选漏洞本身和源码访问权，从零读代码，专职挑毛病。它不知道也不关心前面谁论证了什么。

这一条其实是审计行业的老规矩，spread 到 AI 时代只是执行者换了。人做审计要回避制度，AI 做审计要上下文隔离制度，讲的是同一个道理：检验必须独立于生产。

3.2 承认单次只查一半，用账本叠加

第二个机制在开头埋过钩子，这里兑现。README 原话：在他们的测试里，单次运行大约只能找出反复运行才能找出的全部漏洞的一半。

一半。官方自己把这个数明明白白写在文档里。敢这么写的底气来自覆盖账本的叠加机制，用的正是第一阶段那个 coverage-ledger.json。

每次运行都读写同一本账：哪些单元查过、用什么攻击类查的、结论是什么。下一次运行先读旧账，已经盖过章的地方不重复烧钱，火力全压在没查过的盲区；源码改过的段落，旧结论作废重验。官方内部跑的时候， fleet 级扫描跨 128 个仓库写入了 25472 次攻击意向清单，连续循环让整个生命周期的候选量随时间降了约 65%。账本越厚，单次运行的命中率越高。

落到使用侧：这不是跑一次拉倒的工具。代码改一版，就重跑一轮，让它接着上次的记录往下查。把这个节奏理解成「增量审计」，这个技能才算用对了。

3.3 审计员自己不能变成攻击面

第三条纪律多数人会漏：一个能读你全部代码、能执行构建和测试的 agent，本身就是新的攻击面。技能对沙箱的要求是硬性的：断掉外部网络、环境变量走白名单、限制资源用量、只允许写指定的暂存目录。

条件不满足怎么办？它不硬跑，而是把需要执行目标代码的验证全部标成「待验证」，宁可交不出结论也不在裸环境里执行你项目里的代码。这个取舍我非常欣赏：一个安全工具自己先遵守安全纪律，比多查出一个洞重要。

给任何 agent 放权限之前先圈死它能碰什么，这条纪律不限于这个工具。你往自己的 Claude Code 里装别的 skill 时，问题一样存在，我之前写skill 自身的安全扫描时提过一嘴，两件事是一体的。

四、内部长成的样子：两套系统，不同模型互相校验

450 行的技能在内部到底发展成了什么，官方博客给了结构图。发现侧的流水线分八个阶段：侦察、狩猎、验证、补盲、去重、溯源、反馈、报告，其中补盲到报告四段跑的是连续的生产者-消费者循环：猎手不停产出候选，验证和去重不停消费，所有状态写进一份按运行编号、仓库、阶段做键的 SQLite 底稿，任何一步可以停了重启，不丢现场。

验证侧是另一套系统，三个组件各管一摊。去重组件用确定性倒排索引加 agent，把五万多个原始报告折叠成不重复的真候选；判定组件通过 MCP 拉生产环境的真实上下文，判断「这个洞在生产上到底够不够得着」，代码里有洞但生产配置天然挡住，严重级就要重估；修复组件要求每个修复补丁先过「攻击失效、功能还活着」的双门禁，再加人工审查，不许静默上线。

最值得抄的是跨系统校验的设计：发现侧和验证侧强制使用不同的模型。一个模型找出来的东西，由另一个模型验证，两边不会有共同的路径依赖。模型在这个体系里是可换零件：内部代码库混着 Rust、Go、C、Lua、TypeScript、Python，整套系统没有为任何一种语言做专门调优，也没有绑定任何一家模型。这个「模型即可替换件」的立场，和流程纪律一起，构成这套系统能穿越模型迭代的本钱。

把两套系统的分工摆在一起看，会看到一个刻意的设计：发现侧的目标函数偏「不漏」，宁可多报再被驳；验证侧的目标函数偏「不错」，宁可挂起也不放行。一个候选先被宽松地放进门，再被严格地审出去，两头各自让一步，漏报和误报才同时压得住。前面那组拒绝率从 40% 到 11% 的数字，放在这个语境里才有分量。它不是宣传点，是两个系统互当陪练之后留下的训练痕迹。

还有一个细节能看出工程克制：每个 agent 的上下文用量被压在窗口的 25% 以下。上下文越满，注意力越散。与其塞一个大上下文，不如分成多个小上下文的 agent，每个都只带完成任务必需的材料。这和第三节的上下文隔离纪律是同一套哲学的两个侧面。

五、结论为什么只分三档

流水线跑完，每个候选漏洞的归宿只有三种：确认、待验证、驳回。三档的判据写得极硬，硬到可以直接抄去当自己的 code review 标准：

确认，要求完整的源码追踪链，加一个有边界的观测结果。所谓「有边界」，是指观测到的行为必须在声称的攻击路径上，不能拿一个远房现象去证明邻近的洞。

待验证，必须写清卡在哪个具体事实上，比如「需要执行这段代码才能确认崩溃，当前沙箱不允许」。注意这一档没有严重级。不知道危害多大，就不许标「高危」。

驳回，就是已经被证伪的候选，留着是为了防止下一个猎手把同样的思路再跑一遍。

定级的公式也只有一行：严重级等于可能性乘以影响，不按「偏离了某条检查清单」来定。配套还有一条很多人会拍桌子的规则：纵深防御的缺口不算漏洞。如果 A 层已经拦住了攻击，缺 B 层只能记成加固建议，不是洞。

这套判据的价值，拿它和常见的扫描器报告对比就清楚。后者习惯把所有疑点标红，让读者自己在几百条「高危」里大海捞针，看到最后人对红色已经麻木。三档制把「坐实的」和「没坐实的」钉死分开，报告的每个字都有证据等级。拒绝夸大，才是专业工具该有的样子。这也是我认为它比工具本身更值得抄的部分：你管任何 AI 产出的结论，都可以用这三档来分仓。

六、实操：一条命令装上

安装走 skills 命令行，一条命令：

npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit

加 --global 就是用户级安装，对所有项目生效。卸载也是 skills 命令行管，不多说。

触发是自动的。在项目里对助手说「审计这个代码库」「找出 src 下的安全漏洞」「做一次安全评审，报告输出到指定目录」，命中关键词它自己激活。两种工作模式：完整审计模式出全套报告；你只是问安全问题时走指引模式，不动报告产物。输出目录不指定的话，落在 ~/security-audit-skill/<仓库名>/run-<序号>/，想写进目标仓库必须显式选一个 git 忽略的目录，免得审计底稿污染你的版本库，这个细节想得周到。

跑一次的成本要提前有数。官方博客给过基准：一个约三万行的仓库，单次完整运行 3 到 4 小时，出约 100 个初始发现，去重加判定压缩成 80 个左右高保真的洞；从发现到自动开修复 PR 全程约 14 小时，其中关键漏洞平均 10 个上下，5 天内修复上线。最差的一次运行略超 14 小时。它依赖模型支持工具调用和并行子代理，Claude Code 满足，Node.js 用于那两个校验脚本。

三份交付物的读法也有讲究。总报告先看，统计和关键洞都在最前面；漏洞明细逐条对着源码位置核，别跳过这一步，自己核过一遍的报告才算你的；待验证清单值得留好，每条都写着卡在哪个具体事实上，那个事实被你人工填平的时候，这条记录就自动升级成确认。换句话说，待验证清单就是给你的待办列表，工具把它和「坐实的洞」分开，等于把待办直接递到你手上。

有两个工程细节顺带交代。一是校验脚本的关卡位置：覆盖账本的校验器在建账时跑一次，此后每次账本更新都重跑；结论清单的校验器在第四阶段落账时跑，第五阶段任何一条记录的材料被替换过，再跑一遍。格式错了流水线直接停，问题在哪个文件哪个字段，报错说得清楚。这两份校验脚本加起来不到几百行，零依赖，属于可以直接抄回自己项目的工程件。

二是多次运行之间证据怎么结转：只有源码没变过的证据才允许结转，改过的段落一律按未验证重跑。旧账不会被当成「已经查过」，除非它对应的代码还和上次一模一样。这个细节决定了增量审计可不可信。

我的建议是按目录分批跑，先扫认证、支付、文件上传这类关键路径，别上来就全仓。还有一条前面说过：改一版代码重跑一轮，让它接着账本查增量。单次的产出只是这工具一半的功力。

七、边界：它防不住什么，和谁分工

三个边界要讲清。

第一，它只查和报，不修。报告里给你源码位置和复现路径，改代码还是你自己来（内部系统的自动修复是另一套组件，没有开源在这个技能里）。

第二，它贵在时间不在钱。几十个 agent 跑三四个小时，赶时间的项目用不起全量，分批是常态。

第三，它查的是你的代码库，不管你的 agent 配置。这是两件容易混淆的事：.claude/、mcp.json 这些「给 agent 看的说明书」有没有恶意指令，属于另一个攻击面。我之前分析过 ECC 的 268 条安全规则，那个扫配置，这个查代码，一套组合拳的两个拳峰，别指望其中一个替另一个站岗。

什么样的项目适合它，什么样的不适合，看三样：代码库里有没有值得保护的东西（认证、支付、租户数据，占一样就值得跑一轮）；团队配不配得上它的沙箱要求（做不到断网白名单，它就只会给你一堆「待验证」）；有没有模型支持工具调用加并行子代理（三样缺一，先用传统扫描器顶着，别硬上）。它不适合的场景同样直白：想要「一键安全」的、想要报告里没有待验证项的、想要跑一次管三年的，都不合适。它从头到尾只承诺流程诚实，不承诺结果完美。

还有一个提醒：再好的流程也压不住所有风险。单次一半、叠加补盲的机制说明它的作者对「查不全」保持坦率，你也该保持：过完审计不等于没有洞，等于「以当前账本覆盖的范围，没坐实的新洞」。安全从来不是一个勾选项。

写到这里，回到开头那个 450 行对七千洞的落差。读完整个仓库，我的结论是：这个落差里最值钱的不是漏洞数字，是流程。对抗验证、覆盖账本、三档结论、沙箱纪律，四件事没有一件依赖某个特定模型或框架，全是可以写进任何团队的 review 规范里的普通规则。它们过去管人，现在管 agent，管的东西没变过：怎么让检验独立于生产，怎么让没坐实的话不说满。

工具会过时，模型会换代，这套纪律不会。450 行能传承的是这个，这也回答了开头的问题：AI 写代码的范式已经换了，查代码的范式从这里开始换。你的那部分，从给下一个会话配个安检员开始。
