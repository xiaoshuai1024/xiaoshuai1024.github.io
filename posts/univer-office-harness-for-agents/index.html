程序员接 AI 办公有新路:17,844 星的 Univer 让 agent 自己做表格

GitHub 上有个安静了四年的老项目。它 2022-09-29 建仓,干的还是件苦活:把表格、文档、幻灯片搬进浏览器自己渲染,不借任何现成办公组件。四年里它攒下了一批企业客户,热度始终不温不火。到 2026 年 9 月,趋势雷达抓到它的日增星数冲到 1,142,总星数 17,844(均为 2026-09-24 实查口径)。

代码还是那套代码,仓库门口的牌子换了。官方 README 的定位句现在写作:The Office Harness for AI Agents,给 AI agent 用的办公运行环境。

更硬的证据在官方仓库列表里挂着。DeepSeek Harness 的 Office 插件、腾讯 WorkBuddy 的本地 Office 集成,两个今年热度最高的 AI 办公产品,官方集成建在同一个开源项目上。它叫 Univer,dream-num 出品,Apache-2.0 协议。

这篇文章把 Univer 摊开讲四件事:数据怎么说话、它怎么接得住 agent、生态成形到什么程度、开源边界在哪。判断先放在这里:AI 办公的竞争重心正在从「给人用的界面」挪向「给 agent 用的运行时」,Univer 是把这套定位做完整的开源项目里,眼下还没有第二家。

先看数据:老仓库怎么在四年后翻红

先盘数字。GitHub 实查(2026-09-24):dream-num/univer 总星 17,844,fork 1,540,仓库创建于 2022-09-29,最近一次提交停在 2026-09-24,当天还在 push。趋势侧,选题雷达抓到的日增是 1,142 星(2026-09-24 口径),这个量级把它送进了当期 GitHub Trending 的雷达视野。

看星数有两个口径要分清。官方 API 给的是累计总量,17,844 是四年攒下的家底;日增是趋势信号,1,142 说的是「这两天发生了什么」。家底说明项目不是三周热度的新仓库,趋势说明有事件正在发生。两个口径叠着看,才能把「翻红」和「新火」分开。

翻红的原因在定位换轨,跟运气关系不大。前四年 Univer 把最难啃的部分做完了:自研公式引擎、Canvas 渲染层、跨表格文档幻灯片的统一数据模型。这些活没有 AI 浪潮也得干,干了未必有回报。agent 浪潮来的时候,它手里已经有现成的运行时,缺的只是把定位讲出来。README 的产品线现在写成六件:Spreadsheets、Documents、Presentations、Bases、Boards,PDF 标注 coming soon,一口气从表格铺到了办公全场景。

给追新项目的人一个可复用的判断动作:看定位句什么时候换、生态什么时候齐发,比看星数更早一步。星数是结果,定位句和配套集成才是发令枪。

顺带交代一个背景细节:dream-num 这个团队的前作是 Luckysheet,国内早期最出名的浏览器表格开源项目之一。Univer 相当于吸取 Luckysheet 经验后的重写,架构上按插件拆包,补上文档和幻灯片两条线,目标从「一个表格组件」升级成「一套办公运行时」。老项目磨出来的渲染和公式功底,加上新架构的干净分层,是它敢把产品线一次铺六件的底气。

还有一个身份值得点名:这是一支中文团队做的项目,如今全球 agent 生态里最被看好的办公底座是它。开发者社区里「国产开源只做应用层」的论调流行了很多年,Univer 站的位置是引擎和协议层,公式引擎、渲染引擎、数据模型,一层比一层硬。它站住公共层这件事,对做基础软件的中文团队是个实在的参照:底座不是不能做,是要用四年不追热点换。

AI 办公的两条路:给屏幕,还是给运行时

让 agent 用上办公软件,多数团队的第一反应是给它一块屏幕:截图,找按钮,模拟点击。这条路线能跑通演示,生产环境的问题一张清单写不完:界面改一版,按钮挪一格,脚本全盘失效;点错了下拉菜单,没人第一时间知道;速度按分钟计,任务只能排队串行跑。

验收是这条路线更疼的地方。界面操作完成后,agent 只能再截一张图说「我点完了」,对不对要人盯着屏幕逐格核对。活省了一点,验收一点没省,还多了一层「屏幕上的结果」和「文件里的结果」对不上的风险。

另一条路把 Office 内容做成 agent 能直接读写的结构化数据。语言库是这个思路的初版:openpyxl 能写 xlsx,python-docx 能写文档,但它们只会生成字节,没有公式重算,没有引用更新,写出来的文件常常打开看着对、一算数就错。运行时路线往前多走一步:保留完整的编辑器语义,公式重算、引用联动、格式约束都在,再把每一步开放成 API 给程序调用。

要给路线一说句公道话,它有正当的适用区:软件是别人的、接口一个没有、界面十年不改,这时只剩界面自动化一条路。问题出在拿它当默认方案,把自己产品里的表格也让 agent 点出来。自己的地盘上,内容模型本来可以自己定义,绕道屏幕纯属给自己加了一层不稳定。

Univer 是路线二的完整实现。浏览器里,它是一套可编辑的表格文档界面,Canvas 渲染,公式引擎自研;Node.js 里,同一套数据模型去掉界面继续跑,官方叫 Headless 模式,要求 Node 18.17 以上。agent 读写的是数据结构,人看到的是渲染结果,两层共用一个内核,这是它官方强调的同构设计。

用一个具体场景把两条路的差距摆出来:财务每周要一份对账表,三十个数字、五条公式、固定格式。走屏幕路线,agent 要在界面里逐格输入、逐条写公式、手动调格式,中间弹一个更新提示就可能全盘卡住,跑一遍十分钟起步,结果还得人工复核。走运行时路线,同样的活是三十次单元格写入加五次公式设置,公式重算由引擎完成,最后调一次验证接口拿渲染截图。前者按分钟计还要看运气,后者按秒计且结果可核。

接入的门槛可以先用官方 Quick Start 感受一下,Preset 模式五行装出一个可编辑表格:

import { createUniver, LocaleType, mergeLocales } from '@univerjs/presets'
import { UniverSheetsCorePreset } from '@univerjs/preset-sheets-core'

const { univerAPI } = createUniver({
  locale: LocaleType.EN_US,
  presets: [UniverSheetsCorePreset({ container: 'app' })],
})

univerAPI.createWorkbook({})

一套内核两种形态的设计怎么用在 agent 身上,靠的是三个具体机制,下一节逐个看。

Univer 的三个机制,正对 agent 的三个短板

第一个短板:agent 改文件,容易改坏。让 AI 直接动生产文件,删错一行、拖垮一片引用,是家常便饭。Univer 的应对是把编辑收进结构化 API,官方叫 programmatic editing:agent 通过 Facade API 读写工作簿、区间、公式和命令,每一次修改都走命令体系,改了什么、谁改的、能不能撤,系统里有账。

命令体系这个词,写过编辑器的人不陌生:每个操作封装成命令对象,带参数,可重放,可撤销。agent 改错一处,撤销命令一步回来;出了争议要审计,命令历史就是完整账本。脚本直接改字节流做不到这些,这是工程化编辑和「改文件」的分界线。

Facade API 是这层能力的统一出口,官方的覆盖清单包括工作簿、工作表、区间、公式、命令和事件,浏览器与 Node.js 两端同一套接口。对 agent 集成来说这意味着一套代码两种跑法:开发期在界面里人机同看,生产期在 Headless 里无人值守,业务逻辑不用写两遍。

第二个短板:agent 说改好了,你没法信。大模型的毛病在于做完了不知道自己是对是错,表格这种一格错、全局错的载体尤其致命。Univer 的第二个机制直接对着这条:官方文档列出的验证三件是 content inspection(内容检查)、rendered screenshots(渲染截图)、layout diagnostics(布局诊断)。agent 交活之前先自检,人复核的是验证结果,不是整张表从头划到尾。

三件验证各盯一类错。内容检查管数据对不对,数值、公式结果、引用范围都在检查范围;渲染截图管样子对不对,配色、合并、层级这些「打开才看得见」的问题靠它;布局诊断管排版细节,列宽溢出、内容遮挡,人眼最容易漏的就是这类。三层过完,agent 交活的质量下限被实打实抬高。

第三个短板:不该让 agent 碰正式文件。第三个机制把 git 的 worktree 心智平移进 Office,README 原话是 worktree collaboration:agents work in isolated drafts, then people review their changes and decide what to merge。agent 在隔离草稿里干活,人在正本上审阅,决定合不合并。写代码的人看到这里会认出来,这就是 pull request,只是内容从代码换成了表格。

为什么验证三件之外还要人审一道?举一类真实风险:agent 做报价单,折扣列的公式少乘一个量级,公式自身算得自洽,内容检查不报错;渲染截图排版漂亮,布局诊断也通过。语法全对、语义全错,机器查不出这种错,只有知道这单生意该打几折的人能查出来。验证管住质量下限,人审守住业务判断,两道闸缺一不可。

三个机制合起来看,分工是清楚的:程序化编辑管「怎么改」,输出验证管「信不信」,worktree 管「谁批准」。办公内容的作业流程,第一次有了和代码仓库同构的安全边界。这不是给现有编辑器加个 AI 按钮的思路,是把「AI 是什么」想清楚之后的结构设计。

把 git 协作模型搬进内容工具这件事,DSH 的会话设计里也有同款思路,会话即 git,版本、回滚、分支一应俱全(分析见延伸阅读)。办公域跟进这一步,说明两个域的工程设计正在合流:代码域验证过的协作纪律,内容域照抄就能少走三年弯路。

机制写在文档里,能不能当真,要看有没有人真拿它做产品。下一节看生态,这部分是整篇里我最意外的一段。

生态不是路线图:四个官方集成已经挂出

README 的 Built with Univer Office SDK 一节列了五个开源项目,全是 dream-num 官方维护,两家头部 AI 办公产品在其中。先上清单:

项目干什么关键能力
univer-workspace开源可自托管工作区,人和 agent 在同一份内容上协作agent 生成表格 mini-app,页面指标绑定单元格
dsh-univer-officeDeepSeek Harness 的 Office 插件connected content、validation、isolated worktrees
workbuddy-univer-officeWorkBuddy 的本地 Office 集成MCP 预览、草稿 review,官方标注 development preview
univer-cli命令行工作区agent 用命令行 create、edit、inspect、deliver

univer-workspace 值得多说两句,它是官方放出的完整参考实现:可自托管,人和 agent 在同一份内容上协作。README 给的例子是 agent 直接生成表格形态的 mini-app:决策看板、交互报表、业务仪表盘,页面上的指标、图表、控件绑定到单元格,数据读写和协作更新实时同步。这个形态值得琢磨:表格从「给人填的格子」变成「带界面的轻应用」,开发方式是描述需求,交付物是绑定好数据的活页面。

dsh-univer-office 的介绍只有一行,信息密度不低:connected content、validation、isolated worktrees。上一节讲的三个机制,逐字出现在 DeepSeek Harness 的集成描述里,这不是巧合,是同一套设计语言在两个产品里的复用。读过 DSH 插件系统分析的人知道,那个宿主以 133 个插件的组织方式见长(延伸阅读有分析文),现在它的能力清单里多了 Office 一项,挂的还是同一个开源底座。

WorkBuddy 这边的官方标注要念仔细:development preview,开发预览版。我分析 WorkBuddy 客户端那篇提过它的 MCP 连接器,Univer 给它做的集成正是 MCP 预览加草稿 review,方向与 worktree 协作一致,成熟度还没到稳定版。方向已定、实现未满,这是现在的状态,引用时别把它说成已上线能力。

两件周边值得单独一提。univer-mcp 把 Univer Sheets 接进 MCP 协议,自然语言可以直接驱动作表,这是给所有带 MCP 客户端的 agent 用的通用入口。univer-sdk-skills 更有意思,官方给 agent 写了一套可复用的 instructions,教 AI 怎么正确使用 Univer 做集成、开发插件、跑 Node 后端,Claude Code 的 skill 生态怎么运转,这里原样搬进了办公域。

univer-cli 单独看一眼,它是四个集成里直接对着生产作业的一个:命令行里的 create、edit、inspect、deliver 四个动词,正好是 agent 作业的完整动作集。创建内容、修改内容、检查内容、交付内容,每一步都是可脚本化的命令,不需要界面参与。给 agent 接办公能力又不想动前端的团队,这是成本最低的入口。

一家产品做集成叫合作,五家齐挂加两个通用入口,叫选边。办公域的 agent 生态,Univer 已经站上了公共层的位置,至少在开源侧,眼下没有第二个候选。第 1 节那个「翻红」的疑问,到这里可以合上了:星数追的是这个生态位置,不是那行口号。

开源和 Pro 的边界,接入前先算清

Univer 是 open-core 商业模式:核心开源,增强收费。核心 SDK、公式引擎、渲染引擎、插件系统、Facade API 都在 Apache-2.0 之下,README 明确承诺开源包独立可用,Pro 只是可选的商用增强层。这个承诺对选型的人很重要:开源版不是试用装,是一个能自己站着的产品面。

成本结构分两块看。闭源办公 SDK 按席位或按量收费,数据要过别人的云;Univer 开源版自托管,数据不出自己的基础设施,成本重心从订阅费转成部署与维护的人力。对数据敏感的行业,这一条常常比功能清单更有分量;反过来,没有部署能力的团队,Pro 或闭源方案反而省心。工具没有全优点,只有匹配不匹配。

对照表先收好,接入报价和排期都靠它:

能力开源版Pro 商业版
表格编辑、公式、筛选排序、数据验证、条件格式有有,含引擎增强
Node.js Headless 运行时、RPC 模式有含服务端计算等增强
文档模型与编辑 UI有,演进中含导入导出、打印
实时协作、编辑历史无有
xlsx 导入导出、打印无有
图表、透视表、迷你图无有

表格之外补三个技术事实。视图层建在 React 18 上,支持 React 19,向下兼容到 16.9;浏览器目标从 Chrome 88 和 Safari 14.1 起步,依赖 Intl.Segmenter,老运行时要补 polyfill;仓库开发本身要求 Node 22.18 以上加 pnpm 11,版本门槛不低。

团队适配倒是比想象中轻。界面集成要的是常规 React 技能,公式引擎和渲染层当黑盒用,官方不要求你读懂它们;Headless 侧就是纯 Node 后端技能,常规服务端工程师能接。至于「懂 AI」这项,门槛比很多人预想的低:univer-sdk-skills 那套文档本身就是写给 agent 看的说明书,配好之后,模型侧的活交给 Claude Code 或 Codex 这类编程 agent 就行。

成熟度分布也要心里有数:Sheets 是最成熟的产品面;Docs 共享同一套架构演进中;Slides 还在活跃开发,PDF 只挂了 coming soon。要的是表格,现在是好的接入时点;要全套办公体验,先掂量等待期。

开源表格这个类目里还有别的名字,选型时容易拿来比,类别要先分清。轻量网格组件解决的是「浏览器里渲染和编辑一张表」,够用就好;Univer 这一层解决的是公式引擎、命令体系、验证接口、协作预留的完整运行时,两者不是一个重量级。拿网格组件的轻去比运行时的全,或者反过来,都是选型上的错位。该做的对照是:你要的是部件,还是地基,先答这一问再比参数。

什么情况不该用它

推荐写到这里,边界必须摆出来,不然就是无脑吹。Univer 有清晰的不适用区,选型前对号入座:

你的场景建议
只需脚本生成 xlsx 或 docx,不需要编辑界面openpyxl、python-docx 这类语言库,更轻更稳
要完整办公体验快速上线,有预算闭源商用 SDK,或飞书、WPS 的开放接口
必须开箱即用的实时协作Pro 层或专用协同服务,开源版没有协作
给自己的产品嵌可编辑表格,agent 要读写Univer 的主场
让 agent 操控你已有的办公软件界面自动化路线,Univer 帮不上

风险讲两条。其一,API 稳定政策把接口分成 stable、experimental、internal 三档,experimental 的接口有变动可能,生产接入锁定版本、避开实验段。其二,四年才走到转折点,这个团队的节奏不算快,押注它要有陪跑预期;好处是底子是四年磨出来的,坏处是别指望它下个月就什么都有。

还有一条给所有人的提醒:输出验证三件降低了核对成本,内容对不对最终仍要人确认。agent 自检再完善,也替代不了人对结果的判断,这一点和代码 review 一样,没有例外。

接入姿势上翻车的团队,常见的是三种。第一种,只拿它转格式:花运行时的部署成本,干语言库就能干的活,重装备轻使用,不如直接 openpyxl。第二种,把生产压在 experimental 接口上:稳定政策写得明白,实验段接口说动就动,升个版本全站报错。第三种,跳过 worktree 让 agent 直接改共享正本:安全边界是自己动手废掉的,出了事怪不到工具头上。三种翻车有一个共同根源:按「又一个表格库」理解 Univer,而它是个运行时,用法要按运行时设计。

三句话带走

如果只记三句话,记这三句。第一句,办公内容的下一步是成为数据结构,文件只是它的序列化形态。第二句,agent 需要的是带验证的读写接口,屏幕是给人用的,不是给 agent 用的。第三句,人和 agent 的分工照抄代码仓库:agent 在草稿里干活,人在正本上批准。

Univer 的翻红常被讲成一个转型故事,我更愿意把它读成一个信号:当 AI 成为办公软件的主要用户之一,四十年围着人设计的编辑器必须长出第二张面孔。这张面孔今天叫 harness,明天可能换词,内核不会变:读写有接口,验证有依据,合并要人批。

对要动手的团队,起点在官方文档的 AI SDK 一节:先用 Headless 模式跑通写入、验证、导出三步的最小流程,确认引擎重算和验证接口满足业务口径,再决定界面层接不接。对观察生态的人,盯两件事:协作能力什么时候在开源侧补齐,下一代办公产品会不会把运行时当默认架构。任何一件发生,这个赛道都会拥挤起来,而 Univer 已经站在了位置最好的那一格,等着 traffic 涌进来。

下一支团队要把 AI 接进表格文档时,先别急着写操控界面的脚本,先问一句:我的 Office 内容,有没有运行时。这一问问下去,选型的路就直了。
