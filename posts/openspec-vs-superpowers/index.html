改一行代码别上重型流程：OpenSpec 和 Superpowers 我怎么选

xiaoshuai1024 included in AI 开发
About 400 words 2 minutes 
Contents
  • OpenSpec：给单点修复一个轻量闭环
  • Superpowers：跨子系统的功能不能图省事
  • 判断标准：三个问题决定走哪条路
  • 流程不是越重越好

用 Claude Code 做全栈开发，代码不是难点，流程的轻重才是。

一个项目跑下来，你会遇到两种活：一种是改一行 SQL、修一个测试过时，十分钟就能验证完；另一种是跨前端、BFF、后端、E2E 四个系统的新功能，牵一发动全身。如果这两种活用同一套流程，要么单点修复被一堆文档拖慢，要么跨系统功能没有契约约束，改着改着就乱了。

我在低代码平台项目里同时用了两套流程：OpenSpec 管轻的，Superpowers 管重的。这轮真实开发我跑了五个 OpenSpec change 和一个 Superpowers plan，下面把过程和判断标准写清楚。

OpenSpec：给单点修复一个轻量闭环

OpenSpec 是一个 spec-driven 的轻量变更治理工具。核心想法很简单：每个改动都是一个 change，走 propose（提议）→ apply（实现）→ archive（归档）三步闭环。

它的配置文件里写死了适用边界：单个 change 不超过 3 个文件、不跨子系统、不超过 5 个 task。超过这个边界，它自己会提醒你"考虑用 Superpowers"。

这轮我用 OpenSpec 跑了五个 change，全是测试和缺陷修复：

change改了什么为什么走 OpenSpec
engine 单测修复4 个测试文件同步 API 重构单子系统（engine），纯测试
backend 集成测试1 个测试加 @ActiveProfiles单子系统（backend-java）
form 创建 500 修复1 行 fieldSchema 默认值单文件，缺陷修复
ui test alias1 个 vite.config 补 alias单文件，配置
BFF submit formId1 个 route 加一行注入单文件，BFF 转发

每个 change 的过程都一样：openspec new change 建目录，写 proposal（为什么改）、design（怎么改）、tasks（分几步），然后 apply 改代码、跑测试验证，最后 archive 归档。整个过程在一个对话里闭环，不需要拆分会话。

OpenSpec 的价值不在"流程多规范"，而在它逼你在改代码前写清楚 why 和 how。proposal 三百字以内，design 几句话说清根因和修法，tasks 每个 task 一轮能做完。这个约束刚好——太轻等于没治理，太重一行改动不值得。

拿 form 创建 500 那个 change 举例。表面现象是创建表单报 500，根因是 FormService.create 在 fieldSchema 为 null 时写了 null，而数据库字段是 NOT NULL。修复就是一行：null 时默认给空数组。但如果没有 proposal 这一步，我可能直接改了那一行，不会去想"为什么 submitConfig 已经有默认值而 fieldSchema 没有"——这是 API 设计的不对称，proposal 让我把它说清楚。

Superpowers：跨子系统的功能不能图省事

当改动跨了多个子系统，或者涉及功能实现（不只是修 bug），OpenSpec 的单 change 就不够了。这时候我切到 Superpowers。

Superpowers 是重型契约流程。它要求你先出讨论稿（范围、待确认问题、不做项），用户确认方向后，再出定稿方案——包含完整的 §0 到 §9：需求追溯、页面结构、E2E 用例、验收门禁、安全审查声明、FeatureGate 设计，最后还要并行派发 subagent 去扫描代码库，填出每个子系统的文件映射和 API 契约。

这轮我用 Superpowers 处理两个剩余问题：website SSR 404 和 merge 留资合并。这两个加起来跨了 website、BFF、backend、e2e 四个子系统，而且 merge 那个是功能实现（要把 insert 改成 update 合并），不是简单 bug。

第一轮我出了讨论稿：列出两个问题的根因，给出待确认的问题（路径对齐方向、e2e basePath 配置、merge 合并语义、并发用不用乐观锁），然后等用户拍板。用户确认了方向（并发用乐观锁、不加 FeatureGate），我才进第二轮写定稿。

定稿落到两个文件：一个 Markdown plan（.agents/plans/ 目录），一个 taskGraph JSON（docs/superpowers/tasks/ 目录）。plan 里写清楚五个 task 做什么、验证门是什么、哪些不做。taskGraph JSON 是给 /jx 命令续跑用的——实现阶段可以开新会话，/jx residual-lead-website 会自动读任务图接着干。

Superpowers 重就重在它不让你跳过任何一步。跨子系统改动要声明双后端一致性（Java 和 Go 行为一致），功能实现要声明 FeatureGate 开关设计，涉及敏感数据要列加密策略。这些声明在单点修复里是多余的，但在跨系统功能里是必须的——不然四个子系统改完，没人知道行为对不对得上。

判断标准：三个问题决定走哪条路

我给自己定了三条判断标准，按顺序问：

第一，跨不跨子系统？ 如果改动只在一个子系统里（比如只改 engine 的测试，只改 backend 的一个 Service），走 OpenSpec。如果同时要动 website 和 backend，或者动了 BFF 还要改 e2e 配置，上 Superpowers。这轮的五个 OpenSpec change 全是单子系统，而 Superpowers plan 跨了四个。

第二，是缺陷修复还是功能实现？ 缺陷修复（改错的行为回到对的行为）走 OpenSpec，因为修法明确、范围可控。功能实现（新增一个原来没有的行为）走 Superpowers，因为要定义需求、设计验收标准、考虑 FeatureGate。form 创建 500 是缺陷修复（一行默认值），merge 合并是功能实现（原来根本没这个逻辑），所以前者走 OpenSpec 后者走 Superpowers。

第三，需不需要验收门禁？ 如果改完跑个单测就能确认，OpenSpec 够了。如果需要部署到测试环境、跑 E2E、对照四个子系统的行为，那是 Superpowers 的活。engine 单测修复跑 pnpm test 就完事，website SSR 404 要部署 website、改 e2e 配置、跑 ssr-deep 验证，门禁完全不同。

流程不是越重越好

我见过两种极端。一种是所有改动都走最重的流程，改一行配置也要写九节方案，光文档就花半小时，实际代码三十秒。另一种是所有改动都裸改，不写 proposal 不跑门禁，快是快了，等集成的时候四个子系统对不上。

OpenSpec 和 Superpowers 的分工，本质是让流程的重量匹配改动的重量。单点修复用 OpenSpec 的三件套（proposal + design + tasks）就够了，闭环快、治理够用。跨系统功能用 Superpowers 的全套契约（讨论稿 → 定稿 → 门禁），慢一点但不会漏。

再说一个 OpenSpec 实战的细节。engine 单测那个 change，最初我以为是测试写错了，跑完才发现根因是 useHistory 的 API 整体重构了——从传参式改成了构造时绑定 current。测试还用旧 API 调，自然全挂。OpenSpec 的 propose 步骤让我在改之前先写清楚"根因是 API 重构后测试没跟上"，而不是直接开始改测试代码。这个判断很重要：如果根因是测试过时，改测试就行；如果根因是源码 bug，该改源码。proposal 把这个判断固化下来，后面 apply 的时候不会跑偏。

Superpowers 的定稿里有一段我特别在意：验收门禁表。四个级别——代码审查、编译单测、部署 E2E、安全。website SSR 404 这个问题，改完代码只是第一步，真正验证要部署到测试环境、跑 e2e ssr-deep、确认 SSR3/4 从 200 变成 404。如果门禁表里没写"部署 + e2e"这一级，改完代码就 archive，等于没验证。OpenSpec 的 change 验证跑个单测就完事，Superpowers 必须部署到测试环境跑全链路 E2E。这是轻重流程的核心差异：轻的信任单测，重的要求 E2E 闭环。

这轮开发最有体感的一刻，是 OpenSpec change 改到第四个（BFF submit formId）的时候。那是个一行注入的修复，从 propose 到 archive 不到十轮对话。紧接着切到 Superpowers 处理 website SSR 404，光调研根因就挖了三层（basePath redirect → 端点路径不一致 → createError 时序），讨论稿写完用户还要确认四个问题。两种节奏的切换，让我很清楚自己在处理什么量级的活。

最后说一个踩过的坑：别因为 Superpowers 重就排斥它。我一开始也觉得九个 section 的方案文档太重，想用 OpenSpec 凑合跑跨系统改动。结果 website SSR 404 那个问题，用 OpenSpec 改了 createError 404 就以为修好了，一跑 e2e 发现还有 basePath redirect 和端点路径不一致两层根因没覆盖。OpenSpec 的单 change 装不下三层根因，硬塞进去 proposal 说不清。切到 Superpowers 后，定稿的 design 段把三层根因逐个列出，tasks 对应拆成三步，才真正修干净。跨系统的问题用轻量流程凑合，省下来的流程时间全花在返工上。

别让一行 SQL 修复走完整套重型契约，也别让跨四个子系统的功能裸改上线。流程的工具箱里，重和轻都要有，关键是知道什么时候拿哪一把。
