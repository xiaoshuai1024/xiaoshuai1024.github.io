低代码平台扛 10W QPS:先崩的不是渲染是 schema

xiaoshuai1024 included in 架构
一个低代码平台宣称能扛 10W QPS，往往扛不住的不是渲染——渲染结果早被 CDN 挡掉了。真正先崩的，是 schema 的读写：设计器每 5 秒批量保存、运行时每次渲染都要读 schema，读写瓶颈才是高并发的命门。 本文基于鲁班低代码平台各仓库的既定关系与调用链，推演各系统的部署关系、高并发演进与高可用保障，便于在流量与可用性要求提升时按图演进。 项目归属说明：本文的架构经验与高并发数据（峰值 10 万+ QPS、多级缓存、P0 清零等）来自我大厂时期主导的内部低代码系统"鲁班"；而文章展开的六库架构与代码实现细节，以我个人开源项目 OpenLuban（架构同源、代码全新重写，GitHub）为准。原公司系统源码不公开。 一、系统关系与调用链（现状锚点） 鲁班平台由六个仓库组成，边界固定、契约清晰： 系统 职责 技术栈 下游依赖 luban-ui 组件库 + 设计器 + Render 运行时 Vue3 / Nx 无（被集成） luban 管理后台 Vue3 / Vite / Pinia / Element Plus luban-bff /api/* luban-website 对外站点（SSR） Nuxt 3 luban-bff /api/public/* luban-bff 接入层：认证、聚合、协议适配 Next.js（Node） luban-backend /backend/* luban-backend 主后端：站点/页面/用户/设置 Spring Boot / MyBatis / Redis / MySQL MySQL、Redis luban-backend-go 与主后端同契约的 Go 实现 Go / Gin MySQL、Redis 调用关系可分三层看：
