DeepSeek Harness 裸机是半成品：三类 10 个高 star 插件一次配齐

xiaoshuai1024 included in AI 开发
三天前我上手实测 dsh 的时候，dsh-plugin 话题下是 275 个仓库；写这篇文章的今天，这个数字过了 1400。中间我又把源码从头读了一遍。生态爆发的另一面是泥沙俱下：有给 Web UI 加 2005 年风格广告的整活插件，有「写代码的时候账户不能同时亏钱」的炒股面板，一天写完就没人维护的占了相当比例。 这篇的选稿标准比上一版严了一档：只收高 star 且当天有维护动作的。理由很实际：生态爆发期 star 就是社区的预筛，几百人替你踩过坑的插件，排错时 issue 区里就有答案；而 star 个位数的仓库，哪怕方向再对，装了就是把排错责任全揽到自己身上。10 个插件全部过了 GitHub API 验证，star 数取 2026-08-18 的实测值，当天全部有提交。 按「看 / 点 / 想」三类能力排开。读完之后，你能在 20 分钟内把它们装好，并且知道同类两个插件选哪个、装不上怎么办。 先看全景： 1400 个仓库怎么砍到 10 个 先交代筛法，你可以拿同样的标准自己去筛，不必认我的清单。 第一刀砍 star 不够的。门槛不设固定值，但个位数 star 的直接跳过。不是否认方向，是这个阶段你耗不起排错时间。我上一版清单里有个零 star 的代码地图插件，方向很对，但没人验证过，这次按新标准请出去了。 第二刀砍没有维护动作的。生态爆发期的典型寿命是「发布当天一个 commit，之后永远沉默」。我看仓库先看最近一次提交时间，再看 issue 区有没有人报错、作者有没有回。这次 10 个的最后一次 push 全部在 2026-08-17 或 2026-08-18，跟进 rc 的速度就是生存意愿。 第三刀砍不声明适配版本的。dsh 三天发了 6 个 rc，插件作者如果连「我适配的是 rc 几」都没写，说明他自己也没认真跟。这个信号在 README 第一屏就能看到，两秒钟排除一个。

133 个插件为什么没写成一坨：dsh 插件系统五层拆解

xiaoshuai1024 included in AI 开发
上篇源码深读写完，我又肝了两天两夜，把 deepseek-ai/deepseek-harness 插件系统的源码和机制从头到尾过了一遍——从 vendored 的 Cordis 内核，到 133 个插件包的注册、装配、技能发现、hooks 权限、typert 类型协议，所有结论都带 file:line 引用，你可以拿着仓库对照看。这篇是 DeepSeek Harness 插件系统的源码解析，也是上篇结尾承诺的兑现：typert 和 hooks 的细节值得再开一篇，拆完发现范围可以更大——插件系统不是 dsh 的一个子系统，它 IS dsh。结论先说：插件不是一个文件，是一套五层设计。「一切皆插件」不是宣传语，是它的组织方式本身——133 个插件没写成一坨，是因为每一层只回答一个问题，层与层之间不互相越权。这篇要讲的不是「插件怎么装」，是「插件为什么能成为这个系统的核心」。 一、插件不是文件，是五层 先看一个反直觉的事实：deepseek-harness 的仓库根目录，AGENTS.md 第一行就写着 plugin-based agent harness on vendored Cordis，everything is a plugin——这一行不是背景介绍，是仓库的组织宪法。54 个包、133 个插件包、每个包都是一个 Cordis 插件，包括它自己。但「插件」这个概念在 dsh 里不是一个文件、不是一个 npm 包，而是五层叠加： 生命周期层（Cordis 内核）：插件怎么被实例化、怎么活、怎么死 装配层（profile/bundle）：插件怎么被选进一个运行实例 发现层（skill registry）：插件的子能力怎么被模型找到、怎么排优先级 约束层（hooks 协议）：外部进程怎么参与插件的权限决策 类型层（typert）：插件的服务怎么被别的进程类型安全地调用 这五层不是并列的五个功能，是五个不同的问题域。写插件的人只需要懂第一层（生命周期），装插件的人需要懂第二层（装配），而 skill、hooks、typert 是插件暴露给外部世界的三个面：模型看到的技能、外部进程参与的决策、跨进程调用的协议。读完这篇你会在任何一个点上都说得清「这个机制在哪一层、为什么放在这一层」。 我读源码时数过一遍 packages 目录，133 个插件里真正的「功能插件」不到一半，剩下的是工具注册表、会话、提示词这类基础设施——它们也是插件，也在 cordis.yml 里挂入口，也走同样的生命周期。这个事实本身就是个信号：dsh 把「插件」当成了唯一的组织单元，任何新能力进来都得先回答「你的 apply 是什么」。规范不是写在文档里，是写进架构里的。把这句话再往前推一步就是本篇的立场：插件系统不是 dsh 的一个子系统，它 IS dsh——内核、工具、技能、界面，全部是插件的实例化。 二、直觉：插件是一句话契约 在往下钻之前，先记住插件的最小样子。dsh 官方教程对插件的定义是：导出 apply 函数的 TS 模块（docs/user/develop/basic/index.

Claude 和 Codex 必装的 10 大插件:双持大半年,两边都给我装上了

xiaoshuai1024 included in AI编程
今年我的工作流稳定成了一个固定搭配：白天主力 Claude Code，跑长任务和交叉验证用 Codex。两个 agent 换着用之后遇到一个现实问题——给 Claude Code 精心挑的插件和 skills，切到 Codex 就没了，反过来一样。 好在插件里最有价值的 skill 这层东西天生就是跨端的：一个仓库里放一个 SKILL.md 加几个参考文件，Claude Code 读它，Codex 也读它。2026 年这个生态已经变了样：OpenAI 给 Codex 上齐了 skills 和插件系统，Vercel、Trail of Bits 这些工程团队把内部经验直接开源成 skill 格式，Anthropic 官方仓库涨到 17 万 star。skill 正在变成 agent 界的 npm 包——写一次，全平台装。 这篇是 Claude Code 必装插件的姊妹篇，口径换成双端：Claude 和 Codex 必装的 10 大插件，按 GitHub Star 排行，挑两边都能装、都值得装的。和上篇有五个重合（Superpowers、ECC、karpathy、graphify、Context7）——不是偷懒，是双持之后我对它们的评估又深了一层，安装命令也补了 Codex 侧的写法。Star 数截至 2026 年 8 月，用 GitHub API 现查的，每天在涨，只作量级参考。 先分清三个词 讲插件之前，把三个容易混的词掰开，后面选型才不晕： skill 是一份说明书。一个文件夹，核心是一篇 SKILL.md——告诉 agent 某类任务怎么做，可以带参考文档和脚本。它不改 agent 本身，就是往它的「工作记忆」里塞经验。因为只是文件，谁都能读，所以 Claude 和 Codex 通用。

收藏 80 个 skill 不如写 1 个：Claude Code 从零到能跑

xiaoshuai1024 included in AI 开发
skill 清单我见过太多份了。mattpocock 的、superpowers 的、各种「10 个必装 Claude Code skill」的合集，我自己也装过 80 多个（这件事我写在百万行代码后的 Skills 实战里）。装完的实际情况是，触发频率前 10 的 skill 占了九成调用量，剩下的常年躺在那儿吃灰。 后来我想明白了。清单里别人的 skill，解决的是别人的问题。我自己的问题，比如「AI 写出来的稿子一股 AI 味」，任何清单里都没有答案，因为只有我知道我受不了哪些词、我的改稿流程长什么样。这种事只能自己写。 这篇就带你从零写一个自己的 skill。不推清单，不讲概念，每一步都有真实代码，全部来自我这半年天天在用的 de-ai-smell（一个专治 AI 味的 skill）。你跟着做完，手里会有一个属于自己的、能被 Claude Code 自动触发的东西。 而且这件事的复利比看起来大。清单里的 skill 是别人的经验，你收藏来只能用到别人踩过的坑为止。自己写 skill 的过程，本质是把你自己踩过的坑变成模型的能力，写一个少犯一类错。de-ai-smell 我前后投入不到一天，换回来的是全站五十多篇文章的改稿时间砍半，怎么算都划算。 一、读完你能做出什么 一个最小的 skill 长这样： .claude/skills/ └── my-skill/ └── SKILL.md一个文件夹，一个 Markdown 文件，加起来不到十行，它就能工作了。Claude Code 启动时扫描这个目录，读到你的文件，之后在合适的时机自己决定用不用它。不需要注册，也不用改任何配置，一行代码都不用写。 图 1 是整个机制的示意，你可以先有个地图。 二、前提 装好了 Claude Code，能在终端里跑起来。版本别太旧，太老的版本不认 skills 会写 Markdown。skill 的全部语法就是 Markdown 加 YAML 头，没有第二门语言 手头有一件你重复教过 AI 的事。这是道绕不开的门槛，动手部分的第一步会给判断标准 想深入的话，我之前写过一篇 Claude Code Skills 体系拆解，讲的是整套生态。这篇不管那些，只管「你亲手写出一个」 顺带说一句适用范围。skill 这个格式不是 Claude Code 私有的，它走的是 Agent Skills 开放规范，同一份 SKILL.

Pi Agent 凭什么打赢 Claude Code：极简内核与扩展系统的胜负手

xiaoshuai1024 included in AI 开发
Databricks 前段时间在自家几百万行的真实代码库上，把主流模型和 Coding Agent 工具挨个跑了一遍。结果有点扎眼：性价比最高的那批组合里，一个个人维护的开源项目 Pi 出现了四次，把 Claude Code 和 Codex 挤到了旁边。成本便宜 1.2 到 2 倍，任务通过率基本不动。 这个结果跟我的体感是一致的。过去几个月我把 Pi 当日常主力用，在它上面做过二次开发，把它的扩展系统从头到尾折腾了一遍，也替团队沉淀过一套常驻扩展。这篇文章把「Pi 凭什么」拆成三层讲清楚：数据层发生了什么、上下文这笔账怎么算、扩展系统为什么是结构性的优势。 测试本身先要站得住 先说这份数据凭什么可信。市面上的公开跑分，SWE-Bench、Terminal Bench 这一套，题目是公开的，答案会慢慢泄露进各家模型的训练数据。模型在这些榜上的分数，掺了刷题的水分。 Databricks 的做法不一样：直接拿自家工程师合并过的 PR 当考题。几百万行代码、十几种语言，从每天上千次合并里挑高质量的 PR，原来 PR 里的测试用例就是评分标准。这套题有两个特点，模型没见过这些题目，评分有客观的执行结果做依据。 这种测法其实比看起来苛刻。真实 PR 的需求描述往往很短，缺上下文，模型要靠读代码库自己补齐理解——这正是日常开发的真实难度，而不是考题式的「需求写得很完整，只考实现」。测试用例当评分标准也堵住了另一条作弊路径：没有空间靠花言巧语拿分，测试跑过就是过，跑不过就是不过。 值得注意的是，这类「企业内部数据集」评测正在变多。公开榜的分数通胀让所有人都不再信任榜单，有真实代码库的公司转而用自家数据自测，再把结论公开。对选型的参考价值反而更高：它测的是「干活」，不是「做题」。看这类报告时盯两个细节——横轴是不是每任务成本（而不是 token 单价），任务是不是真实 PR（而不是造出来的需求），满足这两条，数据才值得当决策依据。 看这张图的读法：横轴是每个任务具体花多少钱，纵轴是任务通过率，点越靠左上角越好。性价比前沿线上七个点，Pi 占了四个。全场的最高分也是 Pi 接上 Opus 4.8 开到最高思考档位，通过率 90%。 这张图里还有一条很多人看漏的信息：GPT 5.5、Opus 4.8、GLM 5.2 这些旗舰模型挤在同一层，分数差在三个点以内，但价格差出数倍。开源的 GLM 5.2 质量跟 Opus 打平，单任务成本 1.28 美金对 1.94 美金。 也就是说，模型这层的差距在收窄，Agent 工具这层的差距在被放大。同一个模型、同样的思考强度，换一个 Harness，价格差 1.2 到 2 倍。这正是值得深挖的地方。 模型层：单价是错觉，总账才是真相 先把模型层讲完，因为它最容易选错。看数据时会发现一个反直觉的现象：有的模型单价只有对手的一半不到，每任务的花费反而更高。 原因在 token 效率。模型干活的风格差异很大：有的干脆利落，读一遍文件直接动手；有的谨慎，反复读、反复想、每一步都输出大段分析。谨慎的那个单价便宜，但一个任务跑下来消耗的总 token 是对手的快两倍，两边一乘，总花费反超，分数还更低。Databricks 的测试里就有这样的案例，单价便宜的模型每任务成本更高，通过率还低了六个点。

DeepSeek Harness 源码深读：内核、调度、提示词、上下文一次讲透

xiaoshuai1024 included in AI 开发
三天前我上手实测了 dsh，装完跑了一圈任务，看完插件生态。但实测只能回答「它好用吗」，回答不了「它为什么这样做」。这三天我把 deepseek-ai/deepseek-harness 的源码从头到尾读了一遍——80MB 的 TypeScript monorepo，133 个插件包，外加一套 vendored 的 Cordis 内核。这篇文章是完整的源码笔记，从启动流程一路讲到上下文压缩和定时调度，所有结论都带 file:line 引用，你可以拿着仓库对照看。 我的总体读后感先放这：dsh 是我读过的 Agent harness 里工程约束执行得最彻底的一个。它不是功能最多的，但每一个「容易写歪的地方」——重试、压缩、沙箱、并发、持久化——都用了同一种手法：把决策变成事件，把状态变成投影，把危险变成默认拒绝。这篇文章就是要把这个手法在六七个子系统里怎么落地的拆开看。 版本说明：分析基于我手上的 clone（根 package.json 版本 0.1.0-rc.5，实测文章用的 rc.6），行号以这份代码为准，开发者预览期重构频繁，行号可能漂移。 一、先看地形：仓库结构和那套 vendored 内核 clone 下来第一眼要看的其实是根目录的 vendor/，packages/ 反而可以后看。里面有五个目录：cordis、loader、include、hmr、timer——全部是直接拷进仓库的源码，不走 npm 依赖。 Cordis 是一个「依赖注入 + 插件生命周期」框架（koishi 生态那套思路）：核心概念是 Context（上下文）、Fiber（插件的运行时载体，一个状态机）、Service（命名服务）。插件就是一个对象： { name, inject, Config, apply(ctx) }inject 声明依赖的服务名，apply 在激活时拿到 Context 挂自己的服务。Loader 负责按声明拓扑加载，服务没就绪时依赖方 fiber 停在 pending 状态，Service.check 就绪后放行。 为什么 vendor 而不是装 npm 包？我的看法：harness 对内核的稳定性要求是「每一行都要为我负责」。插件内核是整个系统的地基，升级一个第三方包带来的行为漂移，在 133 个插件的系统里排查成本极高。拷进来，锁死，自己改。这个选择本身就说明了 dsh 团队对「内核」的界定有多严格。 packages/ 下的分组也值得记一下，后面全要用到： packages/boot/* —— 启动、profile、cmdline、app-boot packages/core/* —— agent-loop、session、tools、system-prompt packages/llm/* —— LlmRuntime、deepseek 适配器、重试 packages/context/* —— compaction、spill、todo、plan-mode、goal packages/schedule/*、packages/jobs/* —— 定时调度和后台作业 packages/subagent/、packages/sandbox/、packages/skill/ —— 子代理、沙箱、技能 apps/cli、apps/web —— 启动器和浏览器前端 packages/host/* —— webserver、apiproxy 整棵树的地形是这样的：
