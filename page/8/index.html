Codex 自动剪视频实操：串起 DeepSeek 和开源 Skill，6 条素材变 30 条

xiaoshuai1024 included in AI 编程
让 Codex 自动剪视频，最难的不是让它看懂视频。我跑通这条管线之后回头看，真正决定成败的只有一条纪律：每一步只吃上一步的产物。镜头切分吃 FFmpeg 的帧差输出，配音吃镜头表，成片吃配音时间轴——任何一步越过上游直接碰原始素材，整条管线就开始猜，猜错一次，后面全部返工。 这条管线现在一天能出 30 条，单条配音成本 4-8 毛，产量是手动剪辑的 5 倍。下面是完整搭建过程，从装 Codex 到剪映草稿自动落盘。 前置：装 Codex，权限放到最后一档 Codex 桌面版从官网下载（chatgpt.com/codex/get-started），安装时权限有三档：请求批准、替我审查、完全访问。 自动剪辑要读写素材文件、跑 FFmpeg 和 TTS 脚本，前两档每一步都要人点确认，管线会卡成手动档。完全访问只给盯过的自动化流程，这是它能自动跑的关键，也是别随便给其他会话开的原因。 把模型切到 DeepSeek V4 Flash 剪视频是高频调用场景，默认模型按量计费不划算。~/.codex/config.toml 几行切到 DeepSeek V4 Flash： model = "deepseek-v4-flash" model_provider = "deepseek" [model_providers.deepseek] base_url = "https://api.deepseek.com" wire_api = "responses" [model_providers.deepseek.models] deepseek-v4-flash = { name = "deepseek-v4-flash" }切完别停在欢迎页：让它跑一个真实小任务，比如列出当前目录并统计文件数，确认回复真的来自 DeepSeek。配置文件写对和请求真的通了，是两件事——下面这样带模型头信息的回复才算验证过： 进入剪辑：/video-generation 调 Skill，@ 引素材 工作方式是在对话框输入 /video-generation 调出视频生成 Skill，@ 引用素材文件或目录。剪辑规范、脚本、画面模板都封装在 Skill 里，对话里只给素材和意图：「把这 6 条素材按参考片的节奏混剪」。 Skill 接管后会自动建项目目录：assets 放素材、work 放中间产物、final 放成片。把这套目录约定写进项目的 AGENTS.

同一个问题贵 30 倍？DeepSeek Harness 缓存省钱的三条纪律

xiaoshuai1024 included in AI 开发
同一个问题问两遍，token 数一模一样，开销却可能差 30 倍。多数人把这种价差归因于模型档位或者计费策略，实际的因果链要短得多，贵的那次只是没命中缓存而已。我读 DeepSeek Harness（下称 dsh）源码时确认了更进一步的事实，命中率的高低可以被工程纪律锁死。 背后的结构相当确定：system prompt 分段注册、编号拼接，会话日志只追加不许改，上下文容器等快照变化才写入。三个安排合力保证每一轮请求的前缀逐字节稳定。模型选择只是起点，折扣稳不稳要看前缀。 一、两档价格差在哪 DeepSeek 官方 API 价格表把 v4-flash 的输入拆成两档。缓存命中的输入按 0.05 元/百万 token 计费，高峰时段 0.10；缓存未命中按 1.5 元计费，高峰时段 3.0。两档比值刚好 30 倍，命中那份在服务端复用了上次的计算结果，服务方才有底气给出这种折扣。高峰与平峰各自翻倍，比值保持 30 倍不动，这份折扣比例在任何时段都成立。 二、Agent 为什么天生吃亏 两个前提叠在一起，让 Agent 用户比纯聊天用户难受得多。其一，Agent 每一步都要重发全部历史，读文件、改代码、跑测试，每个动作的输出都追加进上下文，下一轮原样送回服务端。其二，缓存按前缀做逐字比对，从第一个字节开始，中间任何一处变动都会让它身后的一切重新计价。 于是出现一道随轮数增长的重复税：会话越长，每轮重复发送的比例越高；中途动了共享片段，前面攒的折扣一并清零。 用两档价给同一份十万 token 的历史各算一遍：未命中一次付 0.15 元，命中间隔只付 0.005 元，比值正好是价目表上的 30 倍。会话越往深处走，重复段在每轮输入里的占比越高，两种结局的累计差额随轮数线性放大。 三、dsh 的三条源码纪律 上文的吃亏逻辑倒过来读就是工程方案：既然前缀稳定值这么多倍，就把稳定做成架构属性。dsh 在源码里立了三条纪律，分别落在注册顺序、历史改动和增量写入上。 第一条，顺序不许乱。system prompt 由分段对象构成，接口名 PromptSection，每段带 order 编号，框架按编号升序拼出最终提示词。编号的分布也有讲究，harness 身份段 -100，部署人设段 0，工具指导段占 100 到 199，定义和注释都在 packages/core/system-prompt/src/index.ts。注册动作谁先谁后毫无影响，成品序列逐次一致，前缀从第一天起就是稳的。 第二条，历史不许改。会话日志只追加，写入后不存在修订入口。对旧上下文做压缩时，请求体由两部分组成，精确的旧对话前缀，加上作为末条指令的 COMPACTION_INSTRUCTION。前缀一字未动，这趟压缩请求几乎全程命中缓存，近乎免费。日志凭什么敢这么设计，我在会话当 git 那篇里拆过底座：事件流是唯一真源，改写被结构性禁止。 第三条，能不动就不动。上下文容器 PromptContext 被文档明确标为缓存安全结构，docs/subsystems/system-prompt.zh.md 第 73 行原话是 agent loop 仅在完整当前快照发生变化或被压缩移除时才记录到保留模型历史之后。快照平稳时就不去碰保留历史，前缀原样等着被下一轮整段复用。

Windows 用户的 DeepSeek Harness：一条刚铺好正变稳的路

xiaoshuai1024 included in AI 开发
网上的 Agent CLI 教程几乎都有一个隐藏前提：你在用 mac 或 Linux。而 dsh 最新一版更新日志的白纸黑字是 persistent PowerShell sessions on Windows PTY，发布方亲手把 Windows 写进了一线名单。 这篇沿三条线展开：Windows 在这个项目里的真实地位，只在 Windows 平台冒头的一小簇坑，再给一套用最少动作绕开它们的用法。标题里那句「刚铺好正变稳」，每一节都会给出对应的证据。 一、Windows 已经是官方一线平台 证据是版本日志原文：rc.8 的 changelog 里出现了 persistent PowerShell sessions on Windows PTY。持久 PowerShell 会话从这一版起进入 PTY 支持序列，与跨平台功能同批交付，排位就是核心迭代的正席。 「一线平台」这个词平时听得多，这次的分量由代码结构给出。终端子系统把 PTY 后端定义成按类型注册、可整体替换的一层，Windows 的 PowerShell 就是往同一张注册表里补的一种后端类型。文档同时写明：会话在后端或工具插件重载期间保持存活，PTY 状态与原始字节始终留在进程内。拿到这种结构性的座位，才算一线。发布、清理、关闭这些生命周期环节，由同一个服务统一接管，三条平台的会话在管理面上没有主客之分。 同一个版本里还有一条必须看清的提醒：SQLite 存储格式发生 breaking change，升级前要按说明处理已有数据文件。功能推进和数据迁移同时出现在一个 rc 版本里，说明这个项目的迭代节奏快得不容你跳版本升级。 对 Windows 用户的意义很直接：你可以名正言顺地把它当本机工具用，不用再绕 WSL 或者虚拟机。 二、Windows 版沙箱走的是哪条链 沙箱篇列过四条平台链，这里只取 Windows 那一行： Linux: bwrap → Landlock macOS: Seatbelt (sbcl) Windows: ACL restricted-token runnerWindows 不用 bwrap 或 Landlock，也不借用 macOS 的 Seatbelt，走的是 NT 权限模型自带的 ACL 受限令牌：创建进程时剥掉不需要的权限，让它带着一张打了折的令牌运行。隔离材料和另外两家不同，能力接缝完全相同，confine 接口换成哪条实现都不影响上层调用。选原生机制还省下一层依赖负担：隔离随系统自带的安全组件走，不往机器里再引进独立的第三方运行器。

装个插件就能干掉宿主？DeepSeek Harness 的信任边界现状

xiaoshuai1024 included in AI 开发
对 dsh 插件市场做安全扫描的人，扫出一个尴尬结果：排在 critical 榜首的插件，本职工作是安全评估。dsh-cyber-sec，自己身上挂着 11 个 critical 发现。 这篇不复述惊吓，只拆两件事：装进来的插件实际拿到多大的执行面，以及这条边界现在由谁守。答案可以先放在这里：契约有、隔离无，剩下的环节靠人。 一、官方自己的示例，也只敢用受限模式跑 bash 判断一个框架的野心和它的克制程度，看官方示例就够了。dsh 面向开发者的示例代码里，执行类工具自始至终只有一个 bash，而且开工前要先想清楚把哪些能力放进受限模式。沙箱那篇拆过这套默认组合的设计动机：发播方自己都不敢默认裸奔，说明执行面的危险性在项目内部是有共识的。 这里先把 bash 工具的处境立起来当参照物：它每执行一步，身边都跟着一个按次携带的策略对象，权限细到每一次调用。记住这个刻度，下一节你会看到插件这条路拿到的待遇，跟它完全不在一个量级。 二、插件的执行面究竟有多大 外部公开分析已经把结论说破：SSD Nodes 中文页对 dsh 插件机制的梳理口径里，插件以 agent 权限运行第三方代码，且没有进程隔离。这两半句分别是能力和权限维度的事实，拼在一起才算完整：插件能做 agent 能做的一切，并且和宿主共用同一个操作系统身份。 把「agent 权限」翻译成日常动作，awesome 目录在自己的声明里给过对照：dsh 插件可以读写你的文件、跑命令、连网络。文件、进程、网络，这三样正好是操作系统权限的主干；那句「没有进程隔离」落到桌面上，指的就是它们全部敞开。 ctx.dynamicCordisRunner # Dynamic Cordis package host runner cordis-host-runner # 宿主侧：承载包的动态装载 cordis-client-runner # 客户端侧：连接运行中的容器源码证据同样是明牌。插件树由 ctx.dynamicCordisRunner 这条接缝承载包的动态装载，仓库的 docs/capability-seams.zh.md 里明确列出了 cordis-host-runner 与 cordis-client-runner 两端 runner 包。动态装一条包进来不需要越过任何特权检查点，同机同权执行属于设计内行为，原理见接缝架构那篇。 同机同权四个字在桌面环境的含义，也值得停一下细想：你的下载目录、剪贴板、浏览器会话、云盘客户端的凭据缓存，全在这一权的射程之内。第一节里 bash 每走一步都有策略对象跟着，而这条路径上第三方代码拿到的，是一张没有策略对象的完整通行证。 而且这条装载路径是 API 化的，不是运维动作。扩展子系统的文档里，define() 接口接收会话归属、插件元数据与源码本身，由宿主铸造插件和包的身份；run() 按不可变的包版本激活一次运行。整条流程能在模型自己的会话里发起，第三方代码进你的机器，从「管理员敲了一条命令」降格为「一次方法调用」。 设计者当然权衡过：把动态性给足，灵活性的上限才高。但工程上的等价换算是，每个插件的作者都拿到了和你本人几乎相同的机器权限。 三、契约上能声明什么，批准之后又覆盖了什么 权限给到这个程度，契约层总该留下可核对的凭据。通读扩展子系统的接口文档，声明和检查的能力确实设计过，只是各自的覆盖范围值得逐条看清。 先看审批的门。client 半区的包在未授权状态下要等用户点头才拿得到运行许可，这条路是真实存在的。但审批条款里有一句写得非常坦率：plugin 级的授权自动覆盖同一插件后续的版本。也就是说你批准的对象是一个身份，内容却可以流动——上游仓库发一个新版本，新包默认继承你当初批出去的那份信任，不需要你再确认一次。

一个退出码 1 的误诊：DeepSeek Harness 沙箱故障乌龙复盘

xiaoshuai1024 included in AI 开发
一次什么都没搜到的 ripgrep 查询，能让整台机器拉响沙箱故障的警报。名单上的嫌疑人有 Landlock、有 runner、有整套文件系统搜索，实际上全员无辜。这桩冤案的卷宗就躺在 DeepSeek Harness（下称 dsh）仓库的 postmortem 目录里。 翻开它的过程挺有意思：故障不是环境坏了，两套各自合理的设计撞在一起，撞出了一个谁都没想到的结论，合法的非零退出会被当成基础设施塌方上报。这种误诊比漏报更伤人，因为它消耗的是你对告警本身的信任。 一、ripgrep 空结果引发的全家桶报错 现场长这样。在 Landlock ABI 较旧的内核上，glob 和 grep 返回的合法结果会被 harness 标成 SANDBOX_UNAVAILABLE，用户看到的是一整套基础设施级的报错。环境没有坏，文件也没少，报警已经响成一片。 源头藏在 ripgrep 的一个约定里：退出码 1 表示搜索成功执行但没有任何匹配项。目录里没有东西满足 pattern，它正常结束并返回 1。也就是说，非零退出在这个工具的世界里可以代表好消息，而 harness 侧的分类规则恰好没把这层含义接住。 蒙冤的还不止这一个退出码。分类口径放宽到「任意非零退出加这条子串」之后，false 直接以非零收场、无效 pattern 时 ripgrep 以退出码 2 结束、甚至子进程自己挑了个退出码 125 收尾，这些发生在约束与执行全部成功前提下的普通结局，都可能被登记成沙箱基础设施故障。最讽刺的冲突在最后一个数字上：launcher 真失败的约定退出码恰好也是 125，子进程完全可以从容选走同一个号码。 这篇复盘的内容全部出自仓库 docs/postmortem 目录的 0004 号文档，下面按原文展开。 二、一行子串匹配的两类人 误诊的机制集中在一条 stderr 判定规则上。原生 launcher 往标准错误里写的行有两种身份：一种叫部分强制执行通知，内容形如 landlock-run: partial enforcement (older Landlock ABI)，打印之后 launcher 继续正常执行子进程；另一种是真失败，此时打印诊断信息并以退出码 125 终止，子进程根本不会被执行。麻烦在于两种行共用同一个前缀。 harness 的判定用的却是不区分大小写的 landlock-run: 子串匹配，两类情况在这把尺子底下长得一模一样。消费方接着接力：看到非零退出码加上这个子串，就把整次调用登记为 runner 失败。于是每一次返回空结果的 rg 全都蒙了冤，iglob、grep 一个都没跑掉。

AI 说修好了？DeepSeek Harness 的一次错误验收复盘

xiaoshuai1024 included in AI 开发
模型在消息里写下「验证通过」，语气笃定；用户面前的页面是一片白屏，浏览器控制台的报错和这份成功毫无关系。更荒诞的是，模型后来报出的成功 URL，和用户从始至终开着的页面根本不在同一个端口。 这是 DeepSeek Harness 官方复盘 0003 记录的真实事故（docs/postmortem/0003-web-agent-gui-feedback-loop.zh.md，下文事实全部出自这份一手材料）。它暴露的结构很清晰：Agent 的「验收成功」一旦拿环境里碰巧存在的信号当证据（HTTP 200、构建产物、另一个恰好起得来的服务），就会把错误自信地交还给用户；解药只有一个，让验收对象本身可查证。 一、它到底验收了谁的页面？ 先把端口摆清楚。这场会话运行在 3081 端口的 DeepSeek Harness Web GUI 里，用户选的 Workspace 是一个空的 test/ 目录，事件日志头部记录的 cwd 指向本地的 deepseek-harness-gui-master/test。而发给模型的请求里，既没有说明这个 GUI 的存在，也没附上它的源码检出目录、URL、承载进程或更新模式。 仓库里的选项倒不少。apps/web 提供了 Vite 开发脚本，完整的浏览器组合则由 dsh web 命令提供，两条路都真实存在。缺的信息只有一条：你现在改的主题，最终要呈现在哪个进程、哪个 origin 上。项目目录被当成了应用目录，后面所有的混乱都从这里开始。 这里有个容易被忽略的结构事实：Web GUI 在这个架构里并不属于 agent loop 主干，它是一层可选能力。文档对 client 模块系统的定位写得很直白：它是 Web GUI 栈的一项可选能力，消费 HTTP 载体插件提供的前缀路由和 index 转换。也就是说，「GUI 存在、跑在 3081、由完整宿主承载」这套信息完全住在模型请求之外的世界里，模型没有任何制度化的通道能读到它。 二、三步是怎么一路走偏的？ 第一步是把传输层就绪当成了应用就绪。第 2 轮 agent 改完主题，在序列 30939 的消息里让用户自己去跑 pnpm run demo:tui 或打开一个没说清地址的 Web 应用，对组装后的应用没做任何验收。第 3 轮它读 apps/web/package.
