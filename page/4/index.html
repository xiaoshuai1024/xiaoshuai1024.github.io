同样的 Claude Code,三个月把你甩开三倍的是这群人

xiaoshuai1024 included in AI编程
我观察到一个现象：两个水平差不多的开发者同时开始用 Claude Code，三个月后效率能差出三倍。 工具一样，模型一样，差距在哪？不是提示词写得花不花哨——提示词的边际收益在第一个月就到顶了。真正拉开差距的，是对 Claude Code 作为工程工具的完整理解。 很多人用 Claude Code 的方式，本质上还是 Chat 那套：在一个会话里不断提问，上下文越滚越胀，然后会话崩了、模型开始胡扯，就关掉重开。这不是用工具，这是在把 IDE 当 ChatGPT 用。 而真正用得好的人，理解这套工具的完整能力面： 命令是给 AI 套纪律边界，不是「问它一个问题」 Skill 是把经验固化成可复用的命令，不是写一次性提示词 Subagent 是一个人指挥一群 AI，不是一次只做一件事 打断与恢复是效率杠杆，不是失败 这篇文章把这套技能树拆开讲。每条都不是「技巧」，是工作方式的切换——从被动响应到主动编排，这才是高手和新手的真正差距。 一、Claude Code 使用金字塔 我对 Claude Code 的使用深度分了三个层级。大多数人停在第一层，高手在第二层和第三层之间切换。 第一层，对话级。把 Claude Code 当高级 ChatGPT 用——打开就聊，问问题、写代码、修 bug，一个会话从头跑到尾，跑崩了就重开。这一层能解决日常 60% 的问题，但你永远在给 AI 当助理——每次重复上下文、每次重新描述项目结构、每次等着它慢慢推理。 第二层，命令级。开始用 /command、Skill、Task 这些结构化接口。这一层的核心变化是：你不写提示词了，你调用预定义的流程。命令像 API 一样有输入输出契约，Skill 像函数一样封装了可复用的逻辑。这一层效率提升不是线性的，是乘法——写一次命令，反复用几百次。 第三层，编排级。同时启动多个 Subagent，各自做独立任务，你在中间做决策和收敛。用到 Workflow 做多阶段自动化：审查、修复、验证全部并行，最后一轮收敛才叫你。这一层你从「AI 的操作员」变成了「AI 的指挥官」。 这个金字塔得先讲明白，因为后面每一节都是在讲「怎么从当前层爬到上一层」。 二、内置命令与工具：先弄清楚有什么 Claude Code 的「命令」其实分三类：斜杠命令（/xxx 在会话里输入）、工具（内置函数，AI 在后台调用）、CLI 子命令（终端里输入 claude xxx）。三者的区别决定了你用什么方式控制 AI，这点得先搞清再往下讲。 斜杠命令（Slash Commands） 在会话里直接输入 /xxx 调用。这是你作为用户主动控制 AI 的主要方式。

还在说「agent 就是调一次 LLM」?你理解的方向就是错的

xiaoshuai1024 included in AI编程
Agent 不等于"调一次 LLM 拿结果"。当任务需要多步推理、需要外部资源、需要校验产物、需要人参与决策时，单次 LLM 调用搞不定，你需要一个编排层：一套把目标拆成多步、按状态机推进、每步有降级有回退的设计。 这篇文章讲 agent 编排要解决的五个工程问题。全部基于我在 luban 项目里写的 Agent（Python + LangGraph 风格的状态机）的真实代码。代码在 app/agent/，每个节点都是纯函数 (state, deps) -> state，依赖通过 dataclass 注入、可 mock。 状态机骨架：五个节点 + 一个回环 agent 编排的核心是显式状态机。我的 Agent 状态机长这样： understand → retrieve → [generate → validate]循环 → hitl 或 feedbackunderstand 和 retrieve 各跑一次，是前置准备；generate 和 validate 是循环主体；三种出口：hitl（等人确认）、feedback（回环重试）、failed（超限或硬错）。 主循环代码非常克制： async def run(self, state: AgentState) -> AgentState: state = await self.nodes["understand"](state, self.deps) state = await self.nodes["retrieve"](state, self.deps) while True: state = await self.

还在拿「工具升级」看 AI?你正在错过第四次工业革命

 included in AI编程
先把结论摆在这:这一轮以大模型为核心的 AI 浪潮,就是第四次工业革命。判断依据不是某家公司的估值,也不是模型评测分数的高低,而是回到"工业革命"这个词最硬的定义——让生产某一类东西的成本掉一个数量级。前三代都是这么定义自己的,这一代也一样,只不过它降的不是纺纱、炼钢或装配的成本,而是"预测"和"生成"的成本。 我写这篇,是因为过去一年和我聊过的人里,大多数还在用"工具升级"的眼光看 AI,把它当成又一个能提效的软件。这种视角会让人持续低估它。一个工具升级不会改写一个行业的研发流程,也不会凭空造出一批新岗位。但工业革命会。 一、回到标尺:什么样的技术变革才算工业革命 “工业革命"被用滥了,每出新东西都有人喊。我用的标尺来自经济史学家:一项技术要被称为工业革命,它得让某一种基础生产要素的成本出现一个数量级以上的下降,并且这种下降会外溢到几乎所有行业。 前三次都符合。蒸汽机让动力的成本掉了一个数量级——工厂不再建在河边。电力让能源传输的成本掉了一个数量级——福特把装配工时从 12 小时压到 1.5 小时。计算机和自动化让信息处理的成本掉了一个数量级——打字员大面积消失,互联网把信息分发边际成本压到零。三次的共同特征:它们降的不是某一种产品的成本,而是一类基础能力的成本。能力变便宜后,所有用到它的行业都被重排,人的重心从"执行"挪到"指挥机器执行”。 按这个标尺看 AI,它降的是预测和生成的成本。一份靠谱的需求预测过去要养一支数据分析团队,现在几分钟出结果;一段能用的代码过去要工程师写一天,现在 AI 代理几分钟写完。我的体感锚点是:过去一年我用 Claude Code,一个带分页和条件筛选的查询接口从实体类到 Controller 调通,从至少半小时压到10 分钟。端到端任务上——研发账本里 4 个人 2 个月干出近百万行代码——这事在 AI 之前需要至少 4 倍人力。当单人产出被放大 4-10 倍,这在经济学意义上就是工业革命级别的。 二、传统行业:验证流程被 AI 改写 AI 不只影响软件业。传统行业里最先被改写的,不是生产本身,而是验证和测试这一段。 制造业、新能源、材料、医药这些行业,研发周期大头不在"设计"而在"验证"。一辆新车从设计到量产,碰撞和耐久测试好几年;一个新材料从配方到量产,小试中试再加老化,每个环节几个月。这些验证慢是因为物理实验有不可压缩的时间成本——得真的造出来、真的跑、真的等它老化。 AI 的核心思路是用预测替代一部分物理实验:代理模型(surrogate model)几秒给出近似结果替代几小时的高保真仿真;数字孪生在虚拟空间跑耐久测试,物理测试只保留关键节点;AI 从历史数据直接预测"这个设计大概率会过还是会挂"。背后的共同模式:AI 不是替代物理实验,而是把物理实验从"全量验证"降级为"关键点确认"。过去造 10 台样机跑 2 年,现在 AI 预判后造 2 台跑 6 个月,剩下 8 台的预算和 1.5 年的时间被省掉。这种砍法,和流水线砍掉装配工时是同一个量级的降本。 三、软件业:冲击最大,也在长出新岗位 软件业被冲击得最直接,因为它本身就是"生成"的密集区——代码、测试用例、文档、设计图都是 AI 降本最狠的领域。初级前端、CRUD 后端、写单测的测试,这些"执行层"工种正在被快速压缩。过去软件业扩张靠"堆人头",现在 AI 让单兵产出翻倍,堆人头的杠杆失灵了。 但我观察到另一个现象:新岗位在长出来,而且不是一一对应。消失了 3 个写 CRUD 的初级,长出来 1 个要求更高的新角色。软件业这轮的代表性新角色是 FDE(Forward Deployed Engineer,前线部署工程师)——一个既懂模型能力、又懂客户业务、还能上手写代码把两者接起来的人。FDE 最早由 Palantir 系统化,现在 OpenAI、Anthropic、Scale AI、Databricks 都在招。因为瓶颈已经从"模型能力"变成了"模型怎么接进具体业务"。模型公司自己做不过来(他们做通用能力),传统 IT 外包也做不过来(他们不懂模型),只能靠 FDE。

学了就忘不是你不努力,是你的学习根本没有反馈回路

xiaoshuai1024 included in AI 开发
我在 front-end → 全栈 → AI 开发这条路上走得很早,也很清楚一件事:技术人的成长从来不是线性的,而是被"市场需求 × 自我认知 × 学习方法"三个变量反复拉扯。多数人卡在第二个和第三个——不知道自己在市场上值多少钱,也不知道该怎么把短板补到及格线。 这篇文章讲的就是我怎么用 Claude Code 把一个私有的"学习系统"搭成一个可运行、可量化、可复盘的知识库。不是讲考试技巧,而是讲「在 AI 时代,一个技术人该怎么组织自己的学习」。整套东西都在本地跑,所有数据都是真实可验证的,所有流程都是一条命令触发的。 先看结论:古法学习的核心问题是没反馈回路;AI 驱动学习的核心优势是把反馈回路压到分钟级。 一、古法学习的三个致命缺陷 我过去十年的学习方式和大多数工程师一样:刷掘金 / 看官方文档 / 跟着教程写个 demo / 放到收藏夹里吃灰。这种"查资料式学习"有三个结构性缺陷,不是靠努力能弥补的。 先算一笔我自己的账。我在学 RAG 的时候,把 LlamaIndex 官方文档、几篇高赞博客、一个 GitHub 上的 demo 项目都过了一遍,笔记做了不少,本地还 clone 了 demo。那两周我觉得自己"掌握 RAG 了"。后来有次技术选型会,同事问我"RAG 里 chunk 大小和 overlap 在生产环境怎么定,你们踩过什么坑",我支吾了半天,只说出"按经验来"。回去翻收藏夹,文章还在,但具体数字全忘了,那个 demo 项目也早就没跑过。 这不是个例,这是古法学习的结构性失败。 第一个:学什么靠拍脑袋。 看到 RAG 火了就去学 RAG,看到 LangGraph 出新版就去翻文档,完全是被社区热点牵着走。结果半年下来,收藏夹里堆了几百篇文章,简历上写不出任何一项"市场需要、我精通"的技能。学到最后,自己觉得都会,一被追问就全露馅。 更要命的是,这种学法容易陷入"低难度重复"。人天然喜欢学自己已经会的东西——因为那种"我又看懂一篇"的成就感很爽。结果就是:精通的更精通,薄弱的永远薄弱。没有外部信号告诉你"你该学什么",你永远在自己的舒适区打转。 第二个:学了=会了是幻觉。 看文档时觉得自己懂了,写 demo 时照着抄一遍跑通了,就给自己打个勾。这种"理解"是经不起追问的——别人问"为什么这么设计"“生产环境出过什么问题"“和另一方案相比差在哪”,多半答不上来。看十遍文档不如被追问一次,但古法学习里根本没有"被追问"这个环节。 我自己有次被戳穿的经历:学 Vite 的时候,我照着官方文档配了一遍 plugin,跑通了,心里想"懂了”。后来有次技术讨论,对方问我"Vite 的 pre-bundle 阶段用的什么工具,为什么 dev 比 webpack 快这么多",我只答出"用了 esbuild",但说不清楚 esbuild 做了什么、为什么不直接裸跑 ESM、生产构建为什么又要切回 Rollup。回去看文档才发现,那些内容都在第 3 段,但我当时"看懂了"就跳过去了。

补了正规 CI/CD,那三条土法命令行我反而不删了

xiaoshuai1024 included in AI编程
跟同行聊 CI/CD，对方都默认你至少有个 GitLab Runner 或者 GitHub Actions。我接手的一个全栈项目，那段日子什么都没有：没有流水线，没有自动化测试，没有提交规范，连 PR 流程都是口头说一声「我推上去了你看下」。部署是本地 mvn package 出 jar，再 scp 拷到服务器，运营后台的 dist 目录手动传。 按教科书，这种状态就该立刻上 CI 平台。但我做了个反直觉的决定：先不碰平台，用三条 AI 命令把 CI、CD、DevOps 三阶段全跑通了。这三条命令是 /pr-all、/deploy（加 /prod-testing）、/prod-debug——挂在 Claude Code 上，每次发版一条龙走完。 更反直觉的是后面的事。一年后，我们补了一套基于阿里云云效的正规 CI/CD 系统。按常理，正规系统上线，土法命令行该退役了。但我一条都没退，因为这一年跑下来我发现：在「需要判断」的环节上，命令行比系统化流水线更强。云效流水线只会报红等人，命令行能让 AI 自己修完再合并；流水线进不去生产现场，命令行能连生产库调试；流水线没有「停下来问人」这个状态，命令行有。 这篇文章讲的就是这件事：怎么从一无所有搭起三阶段，以及为什么补了正规系统之后，土法命令行反而成了不可替代的那层。结论是——它不是 CI 系统的替代品，是 CI 系统够不着的那层「判断力」的载体，是流水线进不去、又必须有人盯的那些环节的把关。 一、荒芜之地：没有 CI 的研发长什么样 先把现状摆清楚，不美化。 那时候改完代码，流程是这样的：自己机器上 mvn clean package 编译，过就推到远端；没单测、没集成测，过不过全靠手点页面，点过就算过；评审是口头一句「帮我看看那个接口」，没人真看就合了；部署是 scp jar 包到生产服务器，运营后台的 dist 目录手动传；回滚靠记忆——出问题翻聊天记录找「上次能跑的那个 jar 在哪」，没有制品库，没有版本号。 举个真实的场景。有一次改了佣金结算的接口，编译过了、手点了几下没问题就推了。第二天运营来报障，说某个商家的佣金算出来是负数。排查发现是新代码里一个边界条件没处理，但这个 bug 在「手点几下」的阶段根本触发不到——它得某个商家当月刚好有一笔退款，金额恰好等于某笔佣金，才会撞上那个边界。这种 bug，没有系统化的测试覆盖，靠人手点是抓不到的。 更要命的是部署的不透明。jar 包 scp 上去，systemctl restart，进程起来了就觉得「上线成功」。但有一次上线后，新代码其实根本没生效——旧进程没杀干净，还占着端口，新进程绑端口失败静默退出，健康检查命中的是旧进程。我们盯着日志以为一切正常，直到用户开始报障才发现线上跑的还是上一版。 这套流程最伤的不是慢，是不透明。谁改了什么、推上去的是哪个版本、现在线上到底能不能用，全是黑盒。半夜发完版，第二天用户报障，你才知道某个接口昨晚就挂了。 有人会说，这阶段直接上 GitLab CI 不就行了？算过账不划算。我们当时是 3 个人、单机部署、流量可预期，养一套 Runner、写 pipeline YAML、处理证书和并发缓存，投入产出比很差。更要命的是，CI 平台解决的是「自动跑测试」，但我们当时连测试都没有——上了 CI 也不知道让它跑什么。更需要的是一套轻量、能立刻拦住「黑盒」的机制，而不是一套重型平台。

从大厂跳进一片荒芜,我那套工程化当场全废

 included in 工程化
我从前公司带过来一套完整的工程化体系——监控告警、自动化测试、CI 流水线、Code Review 流程,什么都有。跳到初创团队的第一天,打开电脑,什么都没有。 没有监控系统,线上出没出事全靠用户投诉。没有自动化测试,改一行代码心里没底。没有 CI,部署靠手动 mvn package 打个 jar 包再 scp 到服务器。没有敏捷流程,需求口头传达,排期拍脑袋。 更难受的是,团队里没人觉得这些是问题。业务在跑,功能在加,「先把功能做出来」是唯一的优先级。 这种「一片荒芜」的局面,是很多从大厂跳到初创的人都会遇到的情况。难的不是「工程化有哪些东西」——这个大厂都教过你了。难的是:这么多东西都要做,先做哪个?后做哪个?什么能缓一缓? 我自己花了半年,一点一点把这套基建搭起来。现在回头看,如果让我重来一次,我会用一套完全不同的顺序。 结论是:优先级不按重要性排,按投入产出比 + 阻塞解除排 很多人排工程化优先级,默认按「重要性」排:测试最重要(质量是生命)、监控也重要、CI 也重要、敏捷也重要……最后发现什么都重要,什么都想做,半年过去什么都没落地。 我的做法是换一个维度:不看这东西「重不重要」,看它「能多快见效 + 不做它会卡住什么」。 这套顺序的逻辑是:先做投入产出比最高的,再做能放大前面效果的。 监控第一:投入最小(一周搭完),见效最快(立刻能看到线上有没有事)。不做它,你后面做的所有东西都是瞎的——你不知道测试有没有跑、CI 有没有生效、部署有没有出问题。 测试第二:投入中等(一个月搭框架),但它解除的阻塞最大——没有测试,你不敢重构、不敢升级、不敢让新人碰核心代码。 流水线第三:投入较大(两周配 CI/CD),但它把前两步放大——监控的数据靠流水线部署的探针采集,测试的价值靠流水线自动执行才不会变成摆设。 敏捷第四:投入最持续(一直在磨合),但它放大团队协作效率——前面三步是技术基建,敏捷是让团队用起来这些基建的流程保障。 这四块落在一张投入产出比矩阵上,位置是这样的: 下面四节,我按这个顺序,逐个讲每一层我做了什么、为什么这么排、踩过什么坑。 第一层:监控——不是因为重要,是因为一周就能看见效果 荒原里最怕什么 初创项目最可怕的不是「有 bug」,是「不知道有 bug」。 我刚去的时候,有一次用户反馈「页面打不开」。运维去服务器看了一眼,说「CPU 正常啊」。开发去看日志,日志只有 console.log,什么有用信息都没有。最后排查了三个小时,发现是某个接口超时——但没有任何监控告诉我「这个接口超时了」。 这种「靠用户投诉发现问题」的模式,在大厂是不可想象的。大厂的监控体系会主动告诉你「P99 延迟涨了 50ms」,甚至在你之前就告警了。初创团队没有这个,所以问题永远是滞后发现的——等用户受不了来投诉,问题已经发酵了几小时甚至几天。 先搭什么,后搭什么 监控也分层,不能一上来就搞全链路追踪。我的顺序是: 基础设施监控先上(2 天):服务器 CPU、内存、磁盘、网络。用 Prometheus + Node Exporter,或者更轻量的方案(初创团队可以直接用云厂商的监控)。这一步解决「服务器还活着吗」的问题。 应用存活 + 核心接口监控(3 天):健康检查接口、核心业务接口的响应时间和错误率。这一步解决「服务能用吗、好不好用」的问题。 RequestId 链路追踪(1 周):给每个请求打一个 ID,串起网关、服务、数据库的日志,一条 RequestId 贯穿整条后端调用链。这一步解决「出了问题怎么查」的问题。 详细怎么搭,我写过一篇可观测性:RequestId 与监控告警,这里不重复。 我要强调的是为什么这个顺序:从粗到细。先确保「能发现有问题」(基础设施监控),再确保「能定位到哪个服务」(应用监控),最后确保「能查到具体哪次请求」(链路追踪)。反过来做的话,你会在还没搞清楚「服务器活没活」的时候,就去折腾分布式追踪——那是本末倒置。 告警降噪:比加监控更重要的事 监控搭起来之后,最容易犯的错是告警太多。 我刚加完监控那一周,告警群一天响几百次。CPU 超过 80% 告警、某个接口慢了告警、磁盘用了 70% 告警……一周之后,所有人都把告警群设成免打扰。然后某天凌晨服务挂了,没有一个人看到告警。
