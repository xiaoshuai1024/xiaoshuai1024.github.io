1024 工程笔记

全栈架构 × AI 研发实战

AI 什么都会之后,会写代码的人先被推平了

xiaoshuai1024 included in AI编程
当 AI 变得全知全能，「我会你不会」这道优势就塌了。那研发到底还靠什么吃饭?这是序章留下的一个问题,转型篇讲我往哪转,这篇要讲一个更底层的判断。 一、知识,曾经是研发最硬的优势 干过几年研发的人都清楚,以前这行最值钱的就是知识储备。 一段冷门配置怎么写、某个框架的坑在哪、一个诡异报错怎么解——这些没有捷径,全是时间和血泪堆出来的。趟过才记得住,趟过才有发言权。 我见过很多资深工程师,核心竞争力就是「我踩过的坑比你走过的路还多」。初级查一个 Nginx rewrite 要一下午,资深张口就来。信息差直接换算成工资差。 学习周期也长。一门新语言从入门到能写生产代码,少说半年;一个新框架,把生态摸熟又要几个月。知识壁垒高,掌握它的人才值钱。这套逻辑过去十年都成立。 这套逻辑还有个隐性产物:「知识壁垒」制造了职业安全感。你会的别人不会,公司就得用你;你踩过的坑别人没踩,出事就得靠你。这种「不可替代性」是过去工程师最大的心理保障——「我会的东西不是随便能找人替代的」。所以大家拼命学、拼命囤知识,本质上是在囤「不可替代性」。AI 把这道墙推平,直接动摇了这个心理保障——如果 AI 也会,你就不再是「不可替代」的了。这也是为什么很多老兵对 AI 有本能的抗拒:不是 AI 不好用,是 AI 动摇了他们安全感的根基。 但安全感从「我会别人不会」挪到「我能判断别人(含 AI)做对没有」,其实更稳。前者的不可替代性建立在「信息差」上,信息差会被 AI 抹平;后者的不可替代性建立在「判断力」上,判断力不会被抹平。所以与其抗拒 AI,不如主动把安全感的基础从「信息差」挪到「判断力」——前者注定贬值,后者长期保值。 二、AI 把这道墙推平了 现在不成立了。 我的日常主力是 Claude Code,配 Cursor 做编辑,OpenCode 做补充。一个最直观的感受:以前要翻一天文档的事,现在一句话。 不熟的语法,问一句直接给; 冷门框架的用法,它比翻官方文档还快; 诡异报错,贴过去它不光解释原因,还顺手把改法写了。 当人人都能「问出答案」,「我会你不会」这道优势就塌了。 这不是说知识没用,而是「知识的储备量」不再是稀缺品——它从你脑子里的库存,变成了工具里的自来水,谁都能拧开。 这里要补一个重要的区分:「知识」和「理解」不是一回事。AI 把知识的获取推平了(语法、API、用法随取随有),但「理解」没被推平——「这个设计为什么这么选」「这个方案在什么场景下会崩」,这些需要理解原理和上下文,AI 给的是「通用答案」,你结合自己的场景理解后,才能变成「对的答案」。知识是素材,理解是把素材变成方案的能力。AI 提供了无限的素材,但「把素材变成对的方案」这步,还是人来做。所以 AI 推平的是「知识储备」,不是「理解能力」——后者反而因为素材充足,变得更值钱了:以前素材少,理解能力再强也巧妇难为无米之炊;现在素材无限,理解能力强的人能把无限素材组合出最优方案。 三、值钱的东西,往上挪了一层 墙塌了,但人还得吃饭。价值没消失,只是挪了地方。 执行层的知识被削平之后,真正值钱的能力往上挪了一层。具体是三样。 架构能力。 系统怎么分层、边界划在哪、哪一步该做、哪一步该砍。这种取舍 AI 给不了答案,因为它取决于你的业务、团队和约束。这部分我专门拆过。 判断力。 一个需求该不该做、做到什么程度、哪条路是死的。这是决策的活,AI 只能给选项,拍板得你来。 经验嗅觉。 一眼看出这段代码迟早出事、这个方案上线必挂。这种东西 AI 学不会,它来自亲身趟过的坑,不在任何文档里。 这三样有个共同点:它们都建立在大量知识之上,但本身不是知识。知识是地基,AI 帮你把地基铺平了;可上面那栋楼怎么盖,还得你自己设计。 这三样还有个共性值得点出:它们都是「慢能力」。知识是快能力——学一个 API,几分钟;记一个配置,一次就记住。但架构能力、判断力、经验嗅觉,都是慢能力——它们靠真实项目喂出来,没有捷径,不能靠「问 AI」速成。AI 时代,快能力被推平了(谁都能问),慢能力反而成了真正的壁垒——因为慢能力 AI 也帮不了你,它只能靠你在真实场景里一趟趟趟出来。这和「老兵最受益」是同一个逻辑的另一个面:老兵的慢能力攒得久,AI 推不平,所以反而最保值。 慢能力的积累还有个特点:必须亲身经历,不能二手获得。你可以问 AI「分布式锁有哪些坑」,AI 给你列十几个,但「哪个坑在你的业务里最可能踩到」「踩了之后是什么表现、怎么救」,这些只有亲身趟过才知道。老兵的优势不在「知道有这些坑」(AI 也能列),在「知道这些坑里哪个最可能出现在当前场景」——这种场景化的判断,只能靠亲身经历,不能靠二手信息。所以老兵的经验不是「知道坑的清单」,是「知道哪个坑在什么时候最危险」,后者比前者值钱得多。

AI研发实战研发认知职业成长

研发的瓶颈从来不是技术:从前后端到产品开发专家

xiaoshuai1024 included in AI编程
跟同行聊下来,大家的状态出奇地一致:越干越累,产出却没见涨。问题不在努力程度,在分工切得太碎。 研发的真正瓶颈:不是技术,是分工 跟同行聊下来,大家的状态出奇地一致:越干越累,产出却没见涨。问题不在努力程度,而在分工切得太碎。 一个功能从想法到上线,链路是这样的:产品写文档,前端做页面,后端写接口,测试补用例,运维发版,中间还夹着一堆评审和对接。 链路一长,沟通成本就高得吓人,而每个人都只看得见自己那一段。后端不知道前端为什么这么调,前端不知道后端为什么这么返,测试不知道这块改动到底影响谁。 这套分工,在业务稳定、需求可预测的年代是高效的。但现在需求又快又碎,它就显得特别笨重。真正的瓶颈早就不是你会不会某个技术,而是你能不能把一条链路从头到尾串起来。 碎分工还制造了一种隐形成本:信息在传递中必然损耗。产品把需求写进文档,后端读完文档理解成自己的版本,前端再读一遍又理解成另一个版本,到测试那里又多一层诠释。四个人对同一个需求的理解,往往是四个不同的版本。最后联调时冒出来的「这不是我理解的」「文档不是这么写的」这类扯皮,根因都在这层层传递里的损耗。一个人把链路打通,最大的收益不是省了沟通的会,是消除了这种损耗——需求在一个人脑子里,只有一个版本,没有传话游戏。 碎分工还有一个被低估的副作用:没有人对整条链路负责。后端对自己接口的代码负责,前端对页面负责,测试对用例负责,但「这个功能从用户角度看,到底跑不跑得通」这种贯穿全程的问题,反而成了所有人的盲区——每个人都只对自己的那段负责,没人对整体负责。结果就是,每个环节都「交付了」,但拼起来给用户用的时候总有磕绊,而这些磕绊因为不属于任何一个人的职责范围,长期没人解决。产品开发专家的价值,有一半就体现在填补这个「无人负责的整链路盲区」。 从前后端,到全栈,再到「产品开发专家」 我自己这几年的路径,可以划成三段。 第一段,纯后端。 Java 那一套,接口、库表、并发,管好自己这一摊。 第二段,碰前端,长成全栈。 从一个页面到一整套小程序,慢慢变成别人嘴里的「全栈」。全栈这词儿被用滥了,但落到我身上,它解决了一个真问题:一个人能把前后端打通,沟通成本直接砍掉一大半。很多以前要开三个会才能扯清楚的事,自己脑子里跑一遍就定了。 第三段,从全栈,到产品开发专家。 光打通「前端 + 后端」还不够。一个真正能闭环的工程师,得能从产品定义开始,一个人扛下整条链路:产品定义(解决什么问题、长什么样、怎么验证)、全栈开发、自动化测试、DevOps(怎么发版)、线上运营(看数据、迭代)。 我给这个角色起了个名,叫「产品开发专家」。它不是「什么都会一点」的万金油,而是对一条业务链路有掌控力的人。万金油靠广度堆,产品开发专家靠掌控力撑。 产品开发专家的能力地图 「产品开发专家」听起来玄,拆开就是五条具体能力,每条都能练、能评: 能力 具体含义 AI 怎么放大它 产品定义 想清楚"解决什么问题、怎么验证成功" AI 帮你把模糊需求逼成 PRD(brainstorming / grill-me skill) 全栈开发 前端 / 后端 / 中间件打通一条链路 AI 补你不熟的那一端(后端同学写前端不再卡壳) 质量保障 测试纪律、契约闸、验证门禁 AI 写测试、AI 评审、自动收敛 DevOps 构建 / 部署 / 监控 / 回滚 AI 写部署脚本、生成监控配置 数据运营 看数据、定迭代优先级 AI 做数据清洗、出可视化 关键洞察:这五条过去是五个岗位的事,现在一个人扛得动,前提是 AI 把每条能力的"门槛"都削平了。但要注意——AI 削平的是执行门槛,不是判断门槛。AI 能帮你写一份 PRD,但"这个需求该不该做"的判断仍然是你脑子里的事。 万金油 vs 产品开发专家 这点必须讲透,否则「产品开发专家」会被理解成「啥都会一点」:

AI研发实战研发转型全栈

把「AI 保障」焊进系统骨架,让 AI 想跑偏都难

xiaoshuai1024 included in AI编程
我们项目用 AI 协同开发两个月,产出近百万行代码,同时也产出了几百个被保障层拦住的隐患——跨租户查询、漏带权限校验、静默删行为代码、迁移版本撞车。这些隐患每一个溜进生产都是事故。保障层拦住的不是「AI 偶尔抽风」,是「AI 日常产出里必然包含的系统性风险」。 AI 让代码产得快,也让坏代码产得快。一个能稳定输出代码的系统,如果骨架本身兜不住,产能越高、负债累积越快。所以我现在反而比以前更花时间在那些"无聊"的基础设施上——多租户隔离、权限过滤器、契约扫描、迁移治理、可观测。不是因为它们新,因为它们旧、因为它们"枯燥",才成了 AI 时代最值钱的东西。架构师的活儿从"设计能跑的系统",变成了"设计能兜住 AI 的系统"。 我们这个项目的底座 我们做的是一个多租户 SaaS,典型的三段式结构:C 端小程序 + 运营后台 + Java 后端。规模不算夸张,但因为是多租户,出了事影响面大,所以对隔离和契约特别较真。 架构底座就这么几样,说出来都是老生常谈: 多租户行级隔离,每张业务表都带 tenant_id,查询自动带过滤; RBAC 权限过滤器链,权限校验不靠人记得加,而是在过滤器里强制走; 契约驱动,前端调的 URL、后端的路由注解、SQL 引用的表、Flyway 的建表 DDL,两两对得上才算数; Flyway 迁移治理,版本号唯一、有 seed 数据、不许手改线上表结构; 可观测,Prometheus / Grafana / ELK 一套,出问题能追溯。 这里有个值得展开的设计取舍:多租户隔离我们没有用 MyBatis-Plus 的 TenantLineInnerInterceptor(自动给每条 SQL 拼 tenant_id)。不是不知道有这个,是有意不用。原因是它太「隐式」了——自动拼 WHERE 条件,开发者看不到,一旦某个复杂查询需要跨租户(比如平台超管看全量),要写特殊注解绕过,绕过逻辑又成了新的隐患。 我们选了「显式带」:每条业务 SQL 手动带 tenant_id 条件,配合 ArchUnit 规则强制检查 Repository 层 SQL 是否都带了租户过滤。显式的好处是每条 SQL 的租户边界都看得见,review 时一眼能确认;坏处是依赖人记得带——这就是为什么要配 ArchUnit 规则把关,人忘了机器抓。 TenantFilter 的实现也值得展开。它是个 OncePerRequestFilter,从 X-Tenant-Id 请求头取租户,塞进 ThreadLocal(TenantContext),请求结束 finally 里 clear。关键是它按 path 前缀白名单:不是所有接口都要租户(比如登录、健康检查、静态资源),白名单内的直接放行。AI 加新接口时,如果忘了把需要租户的接口放进白名单外,过滤器会拦——这又是一道隐式保障。

AI研发实战架构质量保障

从光标补全到流水线:一条跑通的 AI 研发链路

xiaoshuai1024 included in AI编程
大多数人用 AI 写代码,还停留在「光标后面补两行」,出 bug 了再问一句「这怎么报错了」。这跟当年用 IDE 自动补全区别不大,只是更聪明了点。 真正让玩法变了的,是把整条研发链路摊开,让 AI 在每一步都进场,把它当成流水线上的工位,而不是高级补全。下面这套,是我们团队跑了一年、产出近百万行代码之后沉淀下来的工作流,每一步都经过真实项目验证。后面讲评审、测试、契约的文章,都拿它当地图。 全链路总览 整条链路长这样: 确认需求 → HTML 原型 → 计划 → 多轮并行头脑风暴 → TDD 执行(红/绿/重构)→ 自治多 Agent 评审 → 提交/MR。 每一步都不是「问 AI 一句话」那么简单。每一步都对应一个明确的把关目的:消歧、一致性、效率、质量、语义正确性、仓库门禁。如果某一步的把关目的你能用别的方式达到,完全可以替换——但目的不能省,流程可以变。 第一步:需求之后,先出 HTML 原型 确认需求之后,先出 HTML 原型,而不是直接开写。 原因很直接:对着空气写需求,人和 AI 都容易跑偏。需求文档里的「支持商品管理」「首页可配置」这种描述,十个人能脑补出十种界面。先把界面用 HTML 画出来,需求和实现的歧义在原型阶段就消掉了大半。 具体做法是:需求一确认,丢给 AI 让它先出一版静态 HTML 原型。不用漂亮,关键是把关键页面、关键交互画出来。这个 HTML 后面会被丢掉,但它的价值不在产物本身,而在「强迫双方把模糊的需求变成具体形状」。 我们踩过一次坑:一个「会员权益」的需求,文档写得清清楚楚「会员可见专属价格」,直接让 AI 写代码,实现成了所有商品都展示会员价、非会员看不到价格——但实际需求是所有用户都看得到原价,只有会员额外看到优惠价。这种歧义,如果先出 HTML 原型,5 分钟就能在原型上发现。 原型还有个衍生用法:它后面会变成验收的参照物。功能做完,AI 把实现界面跟原型摆一起比对,缺了哪个按钮、哪个状态没体现,一目了然。比起读需求文档逐条核对,对着原型检查快得多也更直观——原型本来就是把需求具象化的产物,验收时复用它,等于让原型在整个链路里服务两次:一次消歧,一次验收。产出物复用,是流水线设计里很值得抠的细节。 原型阶段的产出不是代码,是共识。 这一步省下来的成本,是后面返工的好几倍。 第二步:计划阶段,确立唯一事实源 计划阶段是整个工作流里我最强调的一环。 做法是做两轮计划,产出一份任务图 JSON,并约定它是唯一事实源。两轮计划分别是: 粗计划:让 AI 把需求拆成大块(「前端」「后端」「数据迁移」三层),每块标个范围。 细计划:在大块内,把任务拆到半天到一天可完成的粒度,每个任务标明:输入是什么、输出是什么、依赖谁。 最终的产物是一份任务图 JSON,长这样: { "tasks": [ { "id": "T-001", "title": "订单详情接口", "layer": "backend", "input": ["订单 schema (T-000)"], "output": ["GET /api/orders/:id"], "depends": ["T-000"], "status": "todo" }, { "id": "T-002", "title": "订单详情页", "layer": "frontend", "input": ["GET /api/orders/:id (T-001)"], "output": ["订单详情.

一条 CI 都没有,代码质量靠一套 Agent 评审回路兜住

xiaoshuai1024 included in AI编程
跟同行聊起质量保障,大家第一反应都是「你们 CI 怎么配的?跑多少分钟?」。我的回答每次都让对方愣一下:我们的仓库,一条 CI 流水线都没有。 没有 GitHub Actions,没有 GitLab CI,没有 Jenkins。.yml 里一个 job 都找不到。 那质量靠谁?靠一套自治多 Agent 评审回路,我已经稳定跑了一年多。这篇把它拆开:它兜住了什么,又诚实地讲一句,它替代不了什么。 为什么一开始就没配 CI,不是嫌麻烦。这个项目是 4 个人 + AI、两个月冲百万行代码的节奏,代码改动密度极高,一天几十次提交是常态。传统 CI 跑一轮完整测试要十几分钟,等它绿了黄花菜都凉了——AI 协同研发的节奏根本等不起串行流水线。 其次,CI 抓的问题有限。流水线擅长抓「编译过不过、测试红不红、lint 报不报」,但抓不了「这段代码的设计对不对」「跨模块的契约对不对」「这坨改动有没有引入语义错误」。而 AI 写代码最容易犯的就是后者——编译能过、测试能绿,但逻辑是错的(270 行静默蒸发就是典型)。我需要一道能读语义的关,CI 给不了。 这两个动机合在一起,就催生了这套 Agent 评审回路:用并行的、能读代码的 Agent 替代 CI 的静态检查和人工评审,用双计数器收敛让它自治,用硬测试门禁兜住动态行为。它不是「省掉 CI」,是「换一种更适合 AI 协同节奏的质量保障形态」。 回路全貌:从「人盯」到「流程把关」 整条回路长什么样,先看一眼,后面再展开关键设计: scope 分桶 → 并行只读评审 → 流式自动修复 → 双计数器收敛 → 硬测试门禁 → 放行提交。 整个评审回路是我们那条 AI 研发工作流 的最后一道关。前面 TDD 已经把红/绿/重构走完了,到这里要决定「这坨改动能不能进仓库」。 关键的判断是:既然能开并行 subagent,就尽量多开。这是团队写进硬约束的一句话。所以这套回路从设计第一天起,就是奔着「并行扇出」去的,不是排队串行。 scope 分桶:并行扇出的第一步 很多人把并行评审理解成「开 N 个 Agent 同时看一坨代码」,这是错的。N 个 Agent 看同一份 diff,要么互相重复(都说同一个问题),要么互相打架(一个说要加锁一个说不用)。并行的前提是scope 不重叠。

AI研发实战代码评审质量门禁

编译能过 ≠ 代码正确:一次 AI 静默删 270 行的事故复盘

xiaoshuai1024 included in AI编程
mvn compile 通过 ≠ 代码正确。 这条铁律挂在评审回路最显眼的位置,起因是一次 AI 改动静默删了 270 行并发守卫,编译照样绿。 过去那些年,我们把"编译绿了"默认等同于"代码对了"。这个默认在人工时代勉强成立,代码换成 AI 大规模产出后,代价会被成倍放大。 一句话讲完整件事:编译器只认语法契约,不校验行为;AI 删一段并发守卫时,编译照样绿、它还底气十足说"已完成"。所以门禁不能停在"能编译",得升级到"得过 verify";任何"我搞定了"必须自带证据(Proof-of-Work),焊进门禁,不靠自觉。 一次看起来无害的"搜索优化" 事情起因是一次很普通的提交,说明写的是"搜索优化"。diff 拉出来看也没问题:搜了什么、优化了什么,逻辑闭环,命名干净,像是 AI 认真做的一次重构。没人会为这种提交专门去翻一遍并发模块——毕竟提交说明里一个字都没提并发。 我们当时的评审回路已经跑起来了,流程走得很顺: Agent 评审 → 自动修复 → 收敛; 然后本地 mvn compile 一把过,绿灯; 提交,合进去。 直到后来有人回头去看那段并发相关的核心代码,才发现不对劲——整整 270 行,没了。不是改坏,是静默删除。那是一处并发安全的守卫逻辑,平时不出声,但在高并发路径上是兜命的。 整个事故链在事后看一目了然,但当时却是潜伏了好几天才爆: 排查过程:从「功能正常」到「定位到删代码」花了 4 天 事故是潜伏 4 天后,大促放量才爆的。复盘时回头去查排查过程,前三天全是弯路——这才是踩坑型该写的部分,因为弯路本身就是经验。我把每天的判断、走错的岔路、最后怎么转向的都记下来,这才是能被复用的东西。 弯路一(第 1 天):先怀疑是「重构改坏了功能」。 按功能回归测一遍——下单、查询、退款,全过。这是最自然的怀疑方向,因为事故现象是「下单异常」,自然往「下单逻辑」上靠。整整一天盯着订单 service 翻,没找到任何异常。这步走错的关键:把"现象发生在 X 模块"误判为"根因在 X 模块",但实际根因在并发守卫层。 弯路二(第 2 天):怀疑是数据库脏数据 / 缓存击穿。 让 DBA 翻 binlog,清 Redis 集群,压一遍灰度环境。压测时偶尔复现一次超卖,但很难稳定重现。这天最有价值的一个动作是压测时偶发了一次「同一订单扣减两次库存」,当时没重视,以为是测试数据污染,其实是关键线索。 弯路三(第 3 天):用 arthas 在线摸并发路径。 把所有可能并发的方法都加上监控,压测一段时间才偶发超卖。这天终于确认了:这不是「业务逻辑 bug」,是「并发安全 bug」——单线程跑永远不会复现,只有并发抢同一资源时才暴露。但具体哪段代码错了,还是定位不到。
