18 份归档 spec 的两种寿命：AI 编程时代怎么决定文档去留

 included in AI 开发
上周末清理文档目录，我数了一下仓库归档区：18 份 spec，最早的一份是几个月前的一次管线重构，最新的还带着上周的日期。清理过程颇为狼狈：有两份相邻变更的 proposal 内容八成重合，分不清哪份是最终版；有一份过程稿记录的方案早就被推翻，却在地窖里躺了三个月，任何人看了都会被它误导；还有几份只有半页，写到验收就断了，连当时为什么停笔都想不起来。我几乎从不回看这些文档，但每次开新变更，我依然规规矩矩先写 proposal 再动手。 写的时候视若珍宝，写完束之高阁。这两件事同时成立，说明我对 spec 的写作标准和留存标准根本不是一套。是我在形式主义，还是归档区里躺着的真的是资产？把这个问题想透花了我一点时间，结论值得写下来：spec 有两种寿命，一种活在写的过程，一种活在后续的读者手里。两种都合法，混着用才是灾难。 一、spec 到底解决什么问题 先退回到最朴素的场景。没有 spec 的开发长什么样：脑子里有个方向，开口说个大概，AI 动手，做到一半发现理解偏了，纠正，再偏，再纠正。小改动两轮收敛，大改动能来回一下午，最后交付物和最初嘴上说的那个东西已经是两回事。 三个老问题反复出现。上下文是半成品的：你脑子里那幅完整图景，对方只拿到口头的一角。口径是漂移的：第一轮说的「简单做一下」和第三轮理解出的边界，中间隔了无数次即兴补充。验收靠回忆：做完了对不对，全凭双方各自记得当初说了什么，而记忆是不可靠的。 spec 是给这三个问题的同一个答案：把「想清楚」外化成一份双方都能引用的文本。需求方写下来的过程会逼自己补上跳掉的步骤；AI 拿到完整输入；验收时逐条对照，不靠回忆。 有人会问，这些坑 AI 之前也存在，为什么没见人人手一份 spec？因为口头校正曾经很便宜：会议室、白板、工位上喊一嗓子，五秒钟修正一次理解，写文档的时间成本远高于收益。AI 时代供需反转了，校正变贵了：每一轮对话都有延迟和 token 成本，模型还不会主动追问，你不说它就猜。当修正一次理解的价格高于写下一次理解的价格，spec 就从仪式变成了刚需。 AI 编程把这件事的权重放大了。以前的「对方」是同事，还有频繁的口头校正兜着；现在的对方是模型，每次会话都是新人，没有记忆继承，输入质量直接决定输出质量。模型落笔的能力越强，需求的模糊就越成为瓶颈，这也是近两年 spec 驱动开发忽然人人都在谈的原因：不是理念变新了，是执行端变强了，供应端的模糊成了新的短板。 顺便划清一个容易混淆的界线：spec 和笔记不是一回事。笔记是思考的草稿，允许混乱、允许未收敛；spec 是承诺的载体，每一个句子都会被当成「已经确认的事实」去执行。把自己的思考笔记直接丢给模型当需求，是新手最常见的错误之一。模型不会替你区分哪些是结论、哪些是还没想完的中间态。 二、立场光谱：三种做法各有各的理 观察身边的团队和公开的工程实践，对 spec 的态度大致站成三派，谁也说服不了谁。 一派可以叫删光派：spec 是脚手架，楼盖起来就该拆。他们的仓库里代码之外几乎不留过程文档，写完即弃，理由是文档和代码天然会分叉，留一份过期的文档比留空白更危险。 另一派是轻量派：spec 要有，但重流程必死。他们用最简的文件命名约定跑状态机，文件名前缀就是阶段，改一个字也要走的流程和跨系统的需求走同一套，方法是把仪式感压到零。 第三派是地基派：spec 是共识资产，是整套工程方法的第一块基石。他们的经验是纪律必须先达成共识，没有一份彼此认可的设计文档，后面的自动化工具会被搭歪，返工的成本远超写文档的时间。 三派看起来水火不容，我在自己的仓库里把三种都试过之后发现，他们吵的从来不是同一个问题。删光派谈的是「写完之后文档还有什么价值」，地基派谈的是「动手之前如何强迫共识」，轻量派谈的是「中间过程如何不压垮执行」。各自都对，混着谈才吵。 换个视角看更清楚：三派各自守着文档生命周期的不同阶段。地基派守写前，共识不达成不动手；轻量派守写中，过程不添堵；删光派守写后，垃圾不清走。一份 spec 从诞生到死亡要经过全部三段，三派把每一段的极端化主张各拿了一个。所以我后来不再问「该信哪一派」，改问「这份文档现在处于哪一段」。三派还有一个共同的盲区值得点破：它们都把「文档」当主语，谈的是文档该不该存在，读者只是被动接受方。而真正决定文档命运的是读者，谁在读、什么时候读、读它解决什么问题。把读者放回主语，很多争论会自动消解。 三、核心模型：spec 的两种寿命 把三派的分歧拆到最小单位，我得到一个模型：spec 有两种寿命。 第一种是过程稿。它的使命发生在写的过程中：逼你把模糊的想法变成清晰的句子，把跳掉的步骤补上，把自以为想清楚的地方暴露出来。写完的那一刻，它的使命已经完成了。它关于「将要发生的事」，而一旦事情发生，它记录的方案细节随时可能被现实修正。这种 spec 的自然结局是被替换、被删除，删了项目照跑，因为它承载的价值，也就是想清楚这个过程，已经兑现进代码和你的脑子里。 第二种是设计说明。它关于「已经存在的事」：这块代码为什么这样设计，当初考虑过哪些方案，哪些坑已经踩过。它的读者是下一个要改这块代码的人，也可能是未来完全失忆的你自己，或者是每次会话都从零开始的 AI。它的自然结局是跟着代码走，代码在它在，代码改它跟着改。 两种 spec 长得几乎一样，都是 Markdown 文件，都有小节和验收项，躺在同一个目录里。寿命完全不同：前者是耗材，用完即弃；后者是资产，跟代码同生共死。 灾难发生在把两者混用的时刻。把过程稿当资产留下来，仓库里堆满和现实分叉的过期方案，误导每一个信它的读者；把设计说明当耗材随手扔，下一个改代码的人从零考古，AI 每次都把已经踩过的坑重新踩一次。判断一份文档的去留，第一个问题不是「写得好不好」，是「它是哪一种寿命」。 两种寿命之间还存在一条单行道：过程稿可以在项目结束时「转正」为设计说明。做法是把时态从将来时改成过去时，把「计划怎么做」改写成「实际怎么做的、中途改了哪些决定、为什么」，删掉那些被现实推翻的部分。转正的判据就一条：内容描述的是事实而非意图。没经过这一步转正的草稿，永远按耗材对待；转正过的，按资产养。我仓库里那 18 份归档，清理时按这条线一划，哪些留哪些删几乎不需要犹豫。 四、AI 带来了第三个读者 传统语境里 spec 的读者是人：协作者、评审、接手的新人。AI 编程加了一个字面意义上的读者：模型。这个读者有三个特点，直接改变了 spec 的写法。

AI 原生研发不需要团队：三层骨架的一个人版本

xiaoshuai1024 included in AI 开发
常有人以为这个仓库背后有个团队。也难怪：同一周里，它在写技术长文、往公众号草稿箱排队、给四个平台挂视频定时、采集各平台的数据回数、还维护着一份随时更新的生产台账。这个产能密度，靠一个人手点是不可能的，靠「很会用 AI」也不够。 答案在仓库本身的形态。它是一个 AI 原生的仓库：几乎所有能力都以 AI 可以直接调度的形态存在，命令、清单、台账、规则，全部长在文件里。这篇把它拆成三层讲——基础设施、工程护栏、协作机制，每一层给足实物，最后连这套体系自己的维护成本也一起交代，不带美化的。 先给结论：AI 原生研发的门槛从来不在编制，在文件结构。团队有团队的搭法，一个人有一个人的搭法，骨架是同一副。区别只在每一层的厚度，不在层数本身。 一、什么叫 AI 原生：三道自测题 「AI 原生」这个词被用得很泛，我给它一个可操作的判断：一个仓库是不是 AI 原生，看三道题。 第一道，你的能力存在哪里？如果「怎么完成一次交付」的完整步骤只存在于你和 AI 的某次聊天记录里，换一次会话就清零，那不算能力，只算回忆。能力必须是文件：脚本、清单、配置，机器可执行，人可审计。 第二道，一个全新的 agent 接手你的仓库，靠读还是靠问？打开仓库先读几份文件就能正确干活，说明知识在仓库里；必须有人坐在旁边解释，说明知识在你脑子里。AI 原生仓库对新会话友好，因为规矩都写在明面上。这一题顺便检验文档的浓度：文件不少但读不懂，照样过不了。 第三道，出了事故，修的是一次还是一类？手工作业模式下，修完这次就完了；AI 原生的做法是把事故固化成一条规则或一个检查项，同类问题永不再犯。这道题最能拉开差距：前两道考验的是整理，这一道考验的是复盘意愿，而复盘意愿没法临时补课。事故的残值能不能留存下来，是两种工作方式的高下之分。 三道题全过，这个仓库才有资格谈后面三层。自报一下家底：能力层面，仓库里躺着上百个脚本和二十份技能文档，构建、发布、采集、审查各有入口；接手层面，一个新的 agent 会话打开仓库，读一份入口规则加对应技能就能正确干活，不需要任何人在旁边解释；事故层面，每一条重要规则旁边都标注着它来自哪次事故。过不了也别慌，三层就是按顺序补这三道题的路线图。 二、基础设施层：命令化与台账化 这一层回答「AI 干活要用的水电煤从哪来」。我的形态是两件小事：所有管线命令化，所有状态台账化。 命令化的载体是 Makefile。文章的构建和校验、公众号的内容准备和发布、视频的合成与多平台分发、平台数据的定时采集、待办清单的拉取和分析，全部收进一条条 make 命令。举几个真实的目标感受一下颗粒度：待办族有列清单、拉快照两条命令；公众号族有准备内容和推送草稿两条；台账族有状态推进和看板重生成；数据族有一条定时采集多平台指标进 SQLite。好处在三个层面：对 AI，命令是零歧义的接口，它不需要理解内部实现就能正确调用；对人，命令是活文档，make 一下列表就知道这个仓库会什么；对体系，命令是收敛点，底层实现随便重构，入口不变。反面教材也见过：散落在各目录的临时脚本，作者本人都要靠翻历史会话回忆用法，AI 调用更是碰运气。散脚本和命令的差别，就在「能力有没有登记」这一条。 台账化解决的是另一个问题：状态。多平台、多环节、长周期的生产流程，最怕的是「现在到底什么在跑」说不清。我的做法是单一事实源：每部视频从选题、成文、合成、定时到归档的全部状态，落在一个 JSON 台账里。字段是固定的：每条记录带唯一标识、当前所处阶段、各平台的定时与发布状态、历史轨迹，异常的还会打上阻塞标志。阶段枚举从选题 backlog 一路到归档 archived，每一步的推进都走脚本，脚本顺手把 Markdown 看板重新生成。看板由台账生成而不走手写，这一步很关键：手写看板和真实状态必然漂移，漂移的看板比没有更误导。 命令化不是一天完成的，最早的仓库里也只有构建和部署两条，每一条新命令的诞生都是某次重复劳动的固化：同一类操作人肉重复到第三遍，就固化成一条目标。半年下来按族组织，同一业务的操作收进同一个前缀，新增能力先问一句「这能不能是一条 make 目标」，能就不写成散脚本。台账的历史轨迹字段也有意外价值：回看任何一支视频从立项到归档的全周期耗时，排期就有了自己仓库的数据基准，不再拍脑袋。 基础设施在 solo 语境下就是这两样：命令给 AI 可调度的手柄，台账给所有人可信任的现状。没有需要说服的同事，命令本身就是制度，台账本身就是现状。 三、护栏层：规则分层，能力预装，裁判独立 这一层回答「AI 怎么保证不干坏、干得像样」。先交代护栏的哲学：护栏不是不信任 AI，是不高估语言和记忆。语言可以被解释，记忆会衰减，只有结构和脚本不商量。三个组件各守一段：分层规则管边界，预装技能管方法，独立验收管结果。 规则分三级，各管一段，判别标准是「这条规则影响几个仓库、几个场景」。用户级配置管跨仓库的全局约定，比如命令输出的压缩方式、回复的语言偏好、汇报的详略偏好，写一次全局生效，换仓库不用重背。这一级的要点是克制：只放真正全局的东西，仓库特有的规范一旦上浮到这一级，就会污染其他仓库的会话。仓库级规则管内容规范和事故定规，这一级最重，因为每一条几乎都对应一次真实教训。完整走查一条定规的来历：有条平台的审核把简介里的站外链接判成了风险导流，作品被砍了推荐。复盘时发现，同一条简介是多平台共用的，最宽松平台能接受的内容在严格平台就是雷。于是定规落了三条：站外链接只放在明确允许的平台；通用简介按最严格平台的口径写；口播里连口头指路的话都禁掉。一次判罚长出三条定规，同一类雷从此排掉。另一条：早期有篇无封面的视频发出去纯亏，定规从此写成封面缺失一律阻断发布，连降级的分支都从脚本里删掉。skill 级规则最具体，每个技能自带触发条件和检查清单，只在被调用时加载。 预装技能是护栏的另一半。仓库的技能目录下有 20 个，按职能分布如下： 类别 数量 覆盖职责 写作 4 选题分析、成文流程、去机器味、应用截图 发布 5 公众号、多平台视频分发、评论承接、元信息优化 数据 3 平台数据采集、趋势报表、生产台账 视频 4 视频生成、封面、定时链路、图文卡片 专项 4 画图、合规检查、爬虫规范、抓取选题 每个技能是一份结构化文档，三段式：什么时候触发、按什么步骤走、完工前过哪些检查。AI 在对应场景自动加载对应技能，不需要人每次口述流程。技能之间还能互相引用，成文技能会在指定步骤指引发布技能和检查技能，管线因此成网。技能清单每季度复查一次：长期没被触发的，要么是描述写得触发不了，要么真没用了，二选一处理；职责重叠的合并；最近手工重复了三遍的事，直接孵化成下一个新技能。技能目录和生物种群一样，需要定期新陈代谢。

AI 不说「我做砸了」：收回解释权的四道门禁

 included in AI 开发
AI 不说「我做砸了」。这句话不是我抬杠，是我三次真实事故换来的观察。 第一次，定时发文界面显示失败，弹窗响应是空的，我当作失败处理，结果那篇文章静默上线了主页，一个粉丝都没通知，等发现时已经挂了很久，无法撤回。第二次，给未来日期挂定时，确认链路悄悄切成了立即发布，同一天群发一次、免费发布一次，重复上线，而界面上看起来还是失败。第三次，想撤掉一张平台侧的定时卡，撤卡工具报「找不到」，状态检查工具也「看不见」任何定时卡，连当晚必发的那张都查无此卡，可它是真实存在的。那一晚我是靠手动刷新平台面板确认的：卡在，工具瞎。人工核对的结果和两个工具的结论都不一致，三方对不上的场面，比任何单一失败都更让人对「自动化」起疑。 三次事故有一个共同结构：失败和成功的外观是错位的，而我最初都把「外观」当成了事实。传统管线里这种错位少得多，因为传统管线的判定源只有一个：进程退出码。退出码是零就是成功，非零就是失败，几乎没有解释空间。AI 参与之后，管线里多出了好几个「成功」的来源：界面上提前弹出的成功横幅、脚本里自己写的上报语句、响应体里藏得很深的嵌套字段、平台侧异步刷新的状态卡，外加被吞掉异常后照常返回零的退出码。判定源从一个变成五六个，每个都长着一张像成功的脸，事故的原料就这么备齐了。这篇文章把三次事故和后续的修复拆开讲，最后收敛成四道门禁。它们解决的是同一个问题：在 AI 参与的管线里，把「完成」的判定器从流程手里收回来。 一、解释性执行：叮嘱为什么注定失效 被坑之后的第一反应，人人都是加叮嘱。在提示词里写「务必确认发布成功」「失败必须报告」「不许跳过封面」，写得越诚恳越没用。原因不在 AI 态度不好，在语言的结构：自然语言的每一条规则都可以被解释执行。「我确认过了」可以是它看了眼界面没报错；「没有失败」可以是它没等到报错就退出了；「跳过封面是为了不阻塞发布」甚至是一句为你着想的话。 每句解释单独看都可能是真的，你不可能每次都翻会话记录逐条验证。我后来把管线里的叮嘱全部数了一遍，留下的只有一类：描述事实和偏好的，比如「发布时间用北京时间」。凡是约束行为的，全部下沉成了脚本和门禁。判定这种事，交给会执行判定的东西，不会执行判定的语言。 二、第一道门禁：判据前置，把成功定义成机器可查的三条件 第一次事故的完整时间线是这样的：我给一篇文章挂定时发布，脚本走完界面流程，弹窗的响应是空串，脚本按「失败」上报。我按失败处理，没有再管。几天后才发现，那篇文章被静默免费发布上了主页：没有推送、没有粉丝通知，但对外可见，且错过了撤销窗口。脚本眼里的失败，平台眼里的成功，两边都没说谎，说谎的是「成功」这个词本身没有定义。 修复动作不是让脚本更聪明地看界面，是把成功的判据写成三个硬条件：请求层抓到 time_send 动作，参数里 isFreePublish 等于 false，响应码为零。三条全中才算成功，缺任何一条按未成功处理，宁保守勿乐观。配套加了一条后置核对：流程结束后必须到平台的发表记录页做只读检查，记录里没有就是没有，脚本的自我报告不作为依据。 这三条判据值得单独解剖，因为它们过了「好判据」的三道关卡。第一，外部可取：三个信号全部来自请求层和响应体，不用打开界面看文案，界面文案会变，协议参数稳定得多。第二，不可被生产者伪造：判据的取证方是网络层拦截器，生成请求的流程自己没有办法让自己的报告变得合格，取证人和服务人分离。第三，失败有名字：三条任何一条不满足，流程都会得到一个明确的「未成功」；空串、超时、含糊观感，一律不算数。第一次事故里那个空响应之所以危险，就是它属于没有名字的状态，没有名字的失败对人等于没有信息，对流程等于凭空消失。事后我在管线里补了一条通用规矩：任何异步动作的回执，要么拿到有名有姓的成功，要么拿到有名有姓的失败，含糊状态一律视为未完成并进入人工队列，绝不允许静默放下。这套规矩的落地形态是一份回执登记表：每个异步动作记下标识、判据结果、时间戳，含糊状态进人工队列每天清一次。登记表还有个意外收获，排障时它就是完整的时序原料，哪一步含糊、哪一步双写，一目了然。 这组判据后来又救过一次场。批量排期的一批定时卡里，有一张平台侧显示的状态和脚本记录的不一致，按老流程「脚本说成功就是成功」就直接过了；按新判据去平台侧核对，确认了卡真实存在、时间正确，才敢签字。判据前置的价值不在平时，在两边不一致的那一刻，你得知道信谁。 三、第二道门禁：请求熔断，让错误的路物理走不通 第二次事故最值得复盘，因为它的根因藏得最深。时间线：我挂的是未来日期的定时，界面弹出了确认框，确认之后请求发出去了——但这条请求的路径已经悄悄变成了「立即发布」，参数里带着免费发布的标记。同一天，这篇文章被群发通知了一次，又被免费发布上主页一次，重复上线。界面在整个过程里表现得像失败了，响应是空的。 事后逆向才发现，确认弹窗在某些状态下会切换到另一种发布变体，请求的目标和参数都变了，定时参数虽然还在表单里，但免费发布的标记让服务端按立即发布处理。修了三轮都是修症状，最后只能承认：这种前端状态机我控制不了，能控制的只有请求出口。 于是加了请求熔断：在网络层挂一个拦截器，凡是发往群发接口的请求，请求体里带免费发布标记的一律直接掐断，流程报错退出、草稿保留在箱里。这条熔断上线后，那种变体路径再触发时，结果是干净利落的失败。静默的成功从此绝迹。从那以后我有个改不掉了的偏好：能熔断就别劝说。劝说把判定权留在对方手里，熔断把那条路物理上封掉。两类手段的差别在时效上同样明显：劝说依赖对方每次都想起，熔断不依赖任何记忆。 熔断这个模式可以通用化。它有三个安装位：网络层，拦截特定接口和特定参数，本次事故用的就是这一层；文件系统层，比如锁住某个不许改的配置文件；流程层，比如持续集成里直接不给危险命令授权。三层的拦截强度递增，安装成本也递增，选择标准看你防的那次事故发生在哪一层。熔断也有自己的代价：误伤。这次事故里同一条群发接口还承担着正常的立即群发，熔断条件写得过宽会把正常路径也掐死，所以拦截器里留了豁免机制，豁免的添加需要二次确认并在日志里留痕。熔断规则本身也进了前文说的拆路清单，定期复查有没有该拆未拆、该建未建的。 四、第三道门禁：路障替代叮嘱，把降级路径拆掉 熔断是定点清除，这一道是面上扫荡：把所有「出错时的方便之门」逐个拆掉。 第一个拆的是封面降级。早先的发布脚本在封面上传失败时会记一条警告然后继续发布，理由是「别让封面阻塞主流程」。定规改掉之后是硬阻断：封面不在，发布中止，修复封面的辅助脚本常备。配套这条定规的是一条朴素的认知——无封面的视频在任何平台都是纯亏的，这条路的尽头没有可接受的终点，那就别让这条路存在。定规落地的那天我把降级分支从脚本里删掉时还犹豫过两分钟，怕万一哪天急需；后来的经验是，真到急需的那天，现写一个分支也就十分钟，而它平时替你挡下的每一次侥幸，都比这十分钟值钱。 第二个拆的是「今天」。定时发表选「今天」时，前端会把请求降级成免费发布，这正是第一次事故的同族病根。守卫现在直接拒绝「今天」和当日日期的表述，只接受未来的配额日。第三个拆的是「先发出去再说」：某些主题在某平台有内容级拒绝的前科，每次被拒都会消耗账号信用，现在的做法是选题期直接不排这个平台，省得发出去等平台教我做人。 这一道门禁的通用形态是一张拆路清单：列出管线上所有已知的降级路径和容错分支，逐个问「这条路的尽头有没有可接受的终点」，没有的，拆。剩下的每一条自动降级路径，都必须能说清它的终点长什么样。 五、第四道门禁：人按口子，口子要少而准 前三道管机器，这一道管人和机器的交接。有些判定机器给不了：这篇稿子算不算写完了，这个语音档位的情绪对不对，这张定时卡该不该撤。我的管线里这些口子全部留给人，而且写成了流程，没托付给默契：文章发布前必须过人，不确认不发；语音的发布档位上限由盲听决定，机器分再高也推不动；撤掉一张定时卡之后，必须到平台侧只读复核到数量归零，复核本身也是独立通道，不复用之前的任何脚本状态。 拿两个实际口子展开。语音发布的档位口子：合成管线会给每个候选档位打分，机器分只做排序，最终发哪个档由人耳盲听决定，评分和档名在试听前是隐藏的，避免先入为主；听感不过关，机器分再高也不发。定时卡的撤销口子：撤卡之后必须到平台侧的面板里只读复核数量归零，复核用的是独立通道，不复用之前脚本的任何状态，因为撤卡工具自己也可能说谎。复核动作还有一个隐藏收益：它逼人真的去看一眼平台侧的现状，别只在脚本日志里找安心。这两个口子的共同点是判定标准长在人身上，机器可以辅助取证，拍板只能是签字的人。 但口子的数量同样要管。我给自己立过一个约束：人不该被机器频繁打断。每一个口子都要问一句，这个判定真的机器做不了吗，还是只是做起来麻烦？做不了的留下，做起来麻烦的想办法自动化。口子越少，每个口子上人的判断质量越高；满屏都是确认按钮的时候，人会把所有确认都变成无脑点击，包括那一个真正要命的。再举一个内容口的例子：发布窗口冲突时的取舍，中午和晚上各只发一条，新卡撞旧卡时是顺延旧卡还是改新卡，涉及对两条内容流量的预判，机器给不了，人来定。这类口子的共同特征是答案随业务目标变化，写不成常量。 六、门禁自己的病：两笔诚实的欠账 这套门禁不是免费午餐，它自己就带着两种病，都得认。 第一种是误报伤人。判定器自己也是软件，判定条件写歪了，代价不是多看一眼，是人为了过检查把东西做变形。我的文章元信息检查器就是活例：上线以来规则表改过好几轮，每轮修订的起因都是一次误报或漏报，修订记录留在变更归档里。其中有几条规则从上线起就只做警告不做阻断，原因写在规则边上：误报率压不下去，一旦阻断，作者会为了过检查把标题改得更差。硬门禁宁少不多，每加一条都要回答「它误报的时候，我会不会为了它改坏东西」。 第二种是机制自身的失效，这种更隐蔽。最近登记在案的一个问题：撤定时卡的辅助工具在某次平台改版后找不到入口了，状态检查工具也匹配不到任何定时卡，而卡片是真实存在的。这意味着「撤卡后复核到零」这道门禁暂时执行不了，不是我不想执行，是执行通道断了。这个案例留了两条教训：其一，门禁失效比门禁缺失更危险，缺失时人还知道要小心，失效时人以为自己在被保护；其二，每道门禁都需要一个「门禁的自检」，定期用已知的真实目标验证通道还通着，我后来的做法是每次批量操作前先拿一张确定存在的卡当试金石：让通道先报这张卡的态，报得出来才继续，报「找不到」就说明匹配规则被改版破坏了，当次所有复核结论全部作废，先修通道再干活。试金石的成本是一次多余的查询，换来的是对整条复核通道的信任，这笔交换怎么算都值。 还有一个绕不开的问题：门禁越多，管门禁的成本越高。它的上限在哪里？我的答案是挂在第三道门禁的拆路清单上：每条存在着的路都有说得清的终点，每道存在的门禁都防着一个见过的真实事故。防「想象中事故」的门禁，就是该拆的下一个对象。这道复查我自己执行过一次：早期给视频发布流程加过一条「发布前检查磁盘剩余空间」的门禁，本意防渲染中断，实际那段管线根本不吃本地磁盘，检查永远绿着，纯属仪式。拆掉那天没有任何后果，仪式性门禁的存在感就是零。 七、三层模型：四次事故、四道门禁，结论却很朴素，把它收进一张图 回头看，四道门禁其实在搬同一件东西：判定的位置。 AI 的工作产物有三层。第一层是声明，它说做完了、说成功了、说没问题了。第二层是产物，文件存在、日志落盘、状态翻到了完成。第三层是事实，独立通道验证过，平台侧核对过，退出码亲眼看过。声明可以错，产物可以假，只有第三层可以作为下游流程的输入。 四道门禁干的就是搬运工作：判据前置把「成功」从界面观感搬到请求参数，熔断把「不许做」从提示词搬到网络出口，拆路把「别降级」从叮嘱搬到结构，人按把「价值观判断」从模型的模仿搬到人的签字。搬完之后再看这条管线，它对「声明」的依赖已经降到了最低：AI 可以随便说，反正说了不算，算数的是拦截器、退出码、平台侧复核和那几个签字的口子。能搬的全搬上去，搬不动的，留给按按钮的人。 如果你也在跑一条 AI 参与的管线，可以直接拿走这份最小清单。清单不神秘，神秘的是它为什么总要在事故之后才被想起——人对自己搭建的流程有一种天然信任，总觉得声明过的都会被遵守，验证是给不信任预留的。承认这一点，清单就不再是防 AI，是防自己过度信任：第一，给「成功」写出机器可查的判据，写不出判据的动作不许进流程，判据要过外部可取、不可伪造、失败有名字三道关卡；第二，已知会出错的路径加熔断，别靠提示词劝，劝一次没用的路径再劝一百次也一样；第三，清点所有降级路径，终点说不清的拆掉，这张清单值得单独一份文件存放，跟代码一起进版本管理；第四，把真正需要价值观的判定留给人，但把口子压到最少；第五，每道门禁配一个自检，定期拿已知目标验证通道。清单的前两条保成功是真的，中间两条保失败是响的，最后一条保门禁自己活着，五条缺一，体系就有暗门。 补一个维护节奏作参考。判据和熔断这类硬结构，跟着事故走，出一次补一次，不预设；拆路清单和口子列表，跟着版本走，每次管线升级后过一遍；门禁自检跟着时间走，固定周期拿试金石跑一轮。三种节奏错开，维护成本就摊平了，不会出现「门禁攒了一个季度没管、一管管一天」的集中还债。五条全是事故换的，原文出处都在我这几次事故的登记里，可查。落地顺序也有讲究：收益最快的是判据前置，一个下午就能给全管线的异步动作补齐硬判据；其次是熔断，专打已经见过的变体路径；拆路和口子要动结构，放到第三步；门禁自检等门禁成规模之后再补。顺序错了的代价是半途而废，一口气上四道门禁的团队，通常在误报扎堆的第二天全数回退，然后得出「门禁没用」的错误结论。 我维护着一个多端全栈项目：一个小程序承载 C 端交易，外加商家后台和运营后台两个 Web 端。所有代码由 AI 在我的工作流里产出，人负责提需求、定方案、做验收。这个形态下最尖锐的问题不是「AI 写得快不快」，是「改完了」这三个字怎么证明。 口号式的回答是加测试。但测试覆盖有个恼人的灰区：改了支付回调的一个分支，单元测试全绿，端到端的小程序下单流程挂没挂，没人知道。传统团队靠人肉回归，一个人维护三端，回归是奢侈品。 我的答案是一张九百五十行的 YAML 注册表，加上一套围绕它运转的交付管线。核心机制是一台自动追责机：git diff 里的每个文件都会被映射到业务域，命中的业务流去注册表里查端到端测试，查不到就拒绝提交。改哪，就必须测哪。这篇把整条管线从设计到验证到收口逐环拆开，附真实的取舍和教训。 一、管线全景：八环相扣 先把整条管线摆出来，每一环消费上一环的产物： 设计源头：一份设计规范 PDF，人定的视觉基准。 可执行单源：把 PDF 落成 HTML 实现稿，色板、圆角、栅格、控件全部定义成 Token。 Agent 摘要：一份给 AI 的规范摘要，指明阅读顺序和裁决规则。 工单创建：每次功能开发先在项目管理系统建工作项，MCP 直连。 四步工作流：方案讨论、写计划、实现、验证，每步产物落盘。 E2E 门禁：git diff 反查注册表，强制测试对应。 多端验证：小程序自动化加两个后台的 Playwright 测试。 PoW 收口：一键脚本跑构建和测试，退出码非零即未完成。 八环里前两环管「做什么样子」，中间四环管「怎么做到、怎么证明」，最后两环管「怎么交付」。为什么是八环，不是三环？因为每一环都是上一环产物的一次「改写」：设计 PDF 被改写成 Token 表，Token 表被改写成 Agent 摘要，需求被改写成工单，方案被改写成计划，计划被改写成代码和测试，最后全部改写成一条合并请求。改写链上任何一环缺失，下游就会拿含糊的输入自行脑补，脑补的误差逐环放大，到交付那一环已经是指数级。逐环展开之前记住这个结构，后面每一环讲的都是「它消费什么、生产什么」。 下面按顺序展开，每一环都讲清楚「为什么需要它」和「不做会怎样」。 二、设计这一环：不解析设计稿，指定单源 行业里处理设计稿的主流思路是解析：把设计文件里的画板、图层、样式抽成结构化数据喂给 AI。思路是对的，但解析管线本身就是一个需要持续维护的工程，个人项目养不起，也不必养。 我的替代方案绕开解析，直接指定单源。设计源头是设计师给的 PDF，我不动它，而是把它翻译成一份 HTML 实现稿：所有视觉决策——色板、圆角半径、间距栅格、玻璃拟态控件的参数——在 HTML 里定义成设计 Token，再按业务组件分章节平铺。这份 HTML 是唯一可执行真源，PDF 降级为存档。 然后是给 AI 的接口：一份摘要文档，内容短得出奇，主要是一张表——规范来源的阅读顺序，HTML 各章节的锚点索引，外加一条裁决规则：PDF 和 HTML 冲突时，以 HTML 里的 Token 为准。

AI 编程省 token 技能：rtk 实测 9 天与完整用法

 included in AI 开发
AI 编程的账单里，最不被看见的一项是命令输出。模型每跑一条 ls、git log、grep，返回的原始文本会整体进上下文：一次全量目录列表几万字节，一轮排查下来几十条命令，token 就这么漏掉了。 rtk（Rust Token Killer，开源仓库 rtk-ai/rtk）是堵这个漏洞的工具：一个 Rust 写的 CLI 代理，官方口径是压缩 60% 到 90%。装上之前我对这类数字是存疑的，压得越狠语义丢得越多，这是这类工具的物理规律。全局跑了 9 天之后，我机器上的留存数据是：2301 条命令，输入 360 万 token，吐回 27.6 万，省下 330 万，压缩率 92.3%，比官方口径的上限还高。 但这个数字不值得直接羡慕。它成立的条件、它的收益构成、它的风险面，才是这篇要拆的东西。我的结论先给：输出压缩不是一个装上就完事的工具，是一项要练的技能——练什么、怎么练、什么时候不该用，文末附完整使用方式。 一、先搞清它站在哪：上下文的第一道闸 普通工作流里，AI 助手执行 Bash 命令，返回值原样进上下文窗口。装上 rtk 之后，命令会先被改写，输出在进入上下文之前过一道过滤器。位置画出来就一条线：命令产生原始输出，过滤器裁剪压缩，模型看到的是瘦身版。 有人会问：让模型自己总结输出不行吗？位置不对。输出一旦进了上下文，占用的窗口就已经花了，模型再怎么总结都是花完之后的补救。过滤器的位置价值在于「进上下文之前」，省下的是窗口本身，顺带把模型的注意力从找行里解放出来。这也是它和「提示 AI 挑重点读」的区别：一个省资源，一个花资源。 它压缩的手段归起来五类。裁剪：ls -la 的权限位、属主、日期列直接砍掉，只留文件名和大小。分组：搜索结果按文件归拢，重复前缀合并。截断：超长输出保留头尾，中间留一行「[N more lines]」标记。去重与浓缩：日志去重、diff 只留变更行。摘要：对特定场景直接给两行技术结论。 五类手段不是均质的。裁剪和分组是结构性收益，砍掉的列模型本来就不需要，接近零损失；截断和摘要有损，是风险集中区。同一份输出可能同时吃到多类手段，git log 就是截断加去重的组合。判断一条输出会被怎么处理，看它的命令家族落在哪一类，这也是分清探索类和核对类的依据。 过滤器按命令家族建，rtk --help 里能数出一百多个子命令：文件类的 ls、tree、read、find，搜索类的 grep、rg，版本控制的 git、gh、glab、diff，测试类的 test、jest、vitest，运维类的 docker、kubectl、psql、aws，还有 err（只显示错误和警告）、json（只看键）、smart（两行技术摘要）这类专门的收敛命令。子命令虽多，选择逻辑只有一条：看输出的最终用途。要看全貌的（ls、tree）重裁剪，要看命中的（grep、rg）重分组，要看过程的（git log、diff）重截断与浓缩，要结论的（smart、summary）直接摘要。记住用途逻辑，一百多个子命令不用背。 这套设计决定了它的收益模式：命令家族覆盖得越广，你的会话里被压的面越大。同时它留了一条硬后路，rtk proxy <命令> 直通原文，一个前缀的事。这个后路后面会反复出现，它是这项技能能放心练的前提。 二、9 天留存数据：钱省在哪一天、哪类命令 rtk gain 是它的统计入口，按天、周、月、命令四个维度留存。先交代口径：这是全局维度，覆盖本机所有工作区的助手会话；tracking 由 rtk 自带，历史默认留九十天，我拉的是 2026-08-20 到 2026-08-28 的完整留存期。总量构成如下：

DeepSeek Harness 桌面版和 CLI 装机实录：10 步装好，绕开三个真坑

xiaoshuai1024 included in AI 编程
装 DeepSeek Harness（DSH）失败的人，大多数不是网络问题——是包名就抄错了。npm 里 @deepseek-ai/dsh-tui 是 404，正确的包名是 harness-tui；再加上 Node 版本不达标，两道门槛拦下了大部分第一次安装的人。 这篇是全程真机实录：桌面版 6 步 + CLI 4 步装到能用，三个真坑提前绕开。 环境门槛：先过这两条 Node 22.19 以上，或 24 系：node -v 先看一眼，不达标先升级； 包管理用 pnpm 10+：npm i -g pnpm@latest 一步到位。 版本不够也能装上，但运行期会出各种说不清的怪问题。装机问题先查环境，再查别的。 桌面版六步 第 1 步，下载：官网 www.dshdesktop.cn，macOS 和 Windows 各一个按钮。GitHub Release 直连下载慢还容易断，直接走官网。 第 2 步，安装向导：选「仅为我安装」，目标文件夹保持默认，点安装。 第 3 步，首次启动：欢迎页先选一个工作区文件夹。它会自动准备 Profile 并在后台起服务——独立窗口，不用开浏览器。 第 4 步，配 API Key：key 在 platform.deepseek.com 申请，进「设置 → 模型 → DeepSeek」粘贴。两条纪律：key 不截图、不进 Git。 第 5 步，跑第一条任务：输入框直接问，回车发送。回答流式输出，带 token 统计——能看到统计，说明请求链路全通。
