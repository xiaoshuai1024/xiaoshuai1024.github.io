全栈架构 × AI 研发实战

你只想加个缓存，AI 想送你一个新系统：先写计划再动手

xiaoshuai1024 included in AI 工程
问你一个问题：为什么你让 AI 写代码，它越写越偏？我拿一个最常见的场景给你复盘。需求只有一句：需求只有一句：「查询太慢，加个缓存。」话音刚落，AI 已经把重构方案写到一半了——它它抽象出一层通用的缓存管理器，引入了消息中间件做失效通知，顺手把查询层的目录结构也重新规划了一遍，末尾还附了一份三阶段的迁移计划和一份技术选型对比表。你只想加个缓存，它想送你一个新系统。 这种跑偏有它的机制原因：模型对「帮你想全」有天然倾向，需求里的每个空白都会被它用「常见做法」填上。空白越多，填出来的东西离你的本意越远。这种热情的破坏力在于，它的每一步单看都合理，连起来是一场没有人要的改造，在你只给了一句需求，却期待它读心。这句话里至少藏着四个没回答的问题：缓存的粒度是查询结果还是整页？数据多久变一次？缓存穿透要不要处理？查询分布在几个实例？每个答案都指向不同的方案，而你一个都没给。AI 不会停下来问，它会把不确定全部猜成默认值，然后高速地把猜出来的东西建完。 解法是把顺序反过来：动手之前，先让它把话说清楚。这套流程我用了几个月，覆盖了从博客工具链到业务系统的各种改动，核心是四步——explore 摊开问题、propose 生成四件套、apply 照规格施工、archive 归档留档。这套流程跑顺之后的最大变化，是每个改动都有据可查：对的地方能指到哪条规格，错的地方能定位到哪一步走偏，改起来有明确靶子。整条流程没有一步依赖运气，也没有一步省掉判断。 先立一条总纲，后面全部展开都挂在它上面：规格是合同，不是文档。文档写完给人看，看过就过期；合同是给人和 AI 共同执行的验收基准，谁签字谁负责兑现。四步流程，本质就是把这份合同从酝酿、签订、履行到归档的完整生命周期。 一、第一步 explore：想清楚，顺便问掉一半需求 explore 是个思考环节，不写代码、不建文档，目标只有一个：把模糊的想法摊开，变成可以立项的共识。它的做法是读代码、画结构、列问题——把「查询太慢」落到「到底是哪一层慢、调用链什么样」，问题就从一句抱怨变成一张图。 explore 的动作路径很具体：让它读相关模块的代码、画出调用链、列出待决策问题。它不写实现，但读代码不算越界——把事实摸清正是这一步的全部产出。那四个悬而未决的问题，就是在这一步被逐个逼出答案的。第一问，缓存的粒度选查询结果还是整页，决定了改动的边界；第二问，数据变化频率决定失效策略选过期时间还是主动失效； 第三问，要不要处理穿透和雪崩，两种答案的实现复杂度差一个量级；第四问，服务部署在单机还是多实例，决定进程内缓存会不会各自为政。四问问完，「加个缓存」从一句愿望变成一份带边界的技术决策，每个选项后面都站着一个你亲手给过的理由，别让一个默认选择替你拍板——拍板权从一开始就该在你手里。顺带一提，这四个问题的答案没有标准答案，只有「你的系统的答案」——照抄别人博客的缓存方案翻车的案例，大多是把别人的答案抄给了自己的问题。这四个问题的答案没有对错高低，但每个答案都会把方案推向不同方向。四个答案凑齐，方案的骨架基本就定了；凑不齐，后面的每一步都在替这句模糊的需求还债。想清楚，四件套就好写；不想，规格里每个场景都得靠猜。我印象最深的一次：同样是加缓存，一次探讨完发现查询每天只有几十次，命中率撑不起缓存的维护成本，需求当场作废——那一刻的如释重负，比任何一次顺利上线都难忘。省下的不只是编码时间，还有往后每一次维护这段缓存时要重新理解它的脑力。 这一步还有个隐藏价值，我称之为最省钱的一步：它经常帮我问掉一个变更。摊开一算，查询频率低到缓存根本攒不住热度，收益覆盖不了引入的成本，直接不做了。一个需求在最便宜的阶段死掉——什么都不用改、不用测、不用回滚，血赚。动手之前最贵的一步是「没想清楚就动手」，explore 就是给这一步上保险。探不明，别立项。这话反过来说更硬：探明了才发现压根不值得做，是这个流程里回报率最高的时刻——你用半小时的对话，省下了几天的实现加无止境的维护。被问掉的需求不丢人，硬着头皮做上线才是事故的开始。 和 AI 一起做探讨还有一个容易忽略的收益：它把「我以为我想清楚了」变成「我真的想清楚了」。人脑里的方案都是压缩过的，摊开的过程就是解压缩，解出来的细节里总有几处经不起追问——而这些细节，正是 AI 自由发挥的温床。 二、第二步 propose：一次交出四件套 想清楚了就立项，AI 一次生成四份文件。先把缓存方案的结论摆出来，方便对照：查询结果级缓存、带过期时间的被动失效、暂不处理穿透、多实例共享一份集中式缓存。基于这个结论，它把探索结论固化成四份文件，构成你和 AI 之间的合同：proposal 管为什么改、改什么、明确不做什么；spec 管系统必须做什么，是行为契约；design 管怎么做、为什么这么做，是决策留痕；tasks 管按什么顺序施工，是排期表。 四份里最讲究的是 spec，它最容易写错，也最值钱。正确的写法是只写行为，不写实现，用固定的条件加结果格式： ### Requirement: 缓存查询结果 #### Scenario: 命中缓存 - WHEN 查询键在缓存中存在 - THEN 返回缓存值，不执行底层查询 #### Scenario: 缓存未命中 - WHEN 查询键不存在 - THEN 执行底层查询，并把结果写入缓存一个场景就是一个最小验收用例：AI 实现完，你照着场景逐条测，能过就是改对了。同一份规格，是指令，也是试卷。最容易犯的错是把实现细节塞进去——「用哪个缓存组件、调什么命令」那是姿势不是行为，写进去有两个坏处：AI 照着字面抄，你换存储它不会跟着变；你验收时核对的是姿势，效果反而没人看。规格只写做什么，怎么做留给设计和代码。这条分界线画清了，验收才有稳定的锚点：你测的是行为，不改技术栈它就成立。 另外三份各有一个要点。proposal 的灵魂在不做什么那一节。为什么改、改什么写起来顺手，真正起约束作用的是明确不做什么：写清「不做整页缓存」「不处理跨节点一致性」，才能拦住 AI 自作主张扩大战场。design 的灵魂是理由而非结论：「选了集中式缓存，因为查询分布在多个实例，单机会各自为政」——理由比结论值钱，下次接手的人靠理由理解系统，不靠结论。tasks 的灵魂是把摸清事实排在最前面：第一步不是写代码，是确认查询入口在哪、有哪些调用方、数据变更怎么通知失效。AI 编程里最贵的事故，都是没搞清事实就动手酿成的。四份文件还有一条依赖链：先立边界，再写契约，再谈权衡，最后排顺序。顺序反了——先想怎么做再想为什么——写出来的每份文件都在跟其他三份打架。

让 3 个 AI 同时开工不打架：git worktree 隔离并行工作法

 included in AI 工程
问你一个问题：一台电脑，怎么同时让三个 AI 干三个活？这个问题的第一步不是选哪个模型，是想清楚它们坐在哪——座位没安排妥当，再强的模型也只是更强的肇事者。座位没安排妥当，能力越强闯的祸越大；座位安排好了，并行是白送的。这篇文章讲我用 git worktree 组织 AI 并行的完整方法，从车祸现场讲起，到磁盘账和清理纪律收尾。先给结论：隔离是 AI 并行的第一块基石，且它的全部成本只是一条命令加一点磁盘。 一、先看车祸现场：共用目录为什么必炸 反面教材先上。三个 AI 会话挤在同一个目录里，改同一批文件：A 改到一半，B 读走了 A 的半成品，随手把文件盖掉；C 基于两人混合的中间态继续动手，再把两个人的成果一起踩掉。这不是协作，这是车祸现场——而且是最难定责的那种，每辆车都坚称自己有路权。 先别急着怪 AI。换成人也一样：两个同事共用一台电脑的同一个工作区，你改到一半他去保存了，结果一样是灾难，只不过人会喊一嗓子，机器不会。深层原因是文件系统没有会话隔离。AI 会话的工作单位是「当前目录里的文件」，两个会话共享同一份磁盘状态，一个会话的未完成动作对另一个会话完全可见。人肉协作时有「我在改这个文件你说一声」的默契，AI 之间没有这道社交缓冲，它看到什么就基于什么干活。半成品被当成输入，是并行出事故的标准路径。 顺着车祸往下走，还有一个更隐蔽的坑：会话的「当前认知」会过时。A 会话基于上午的文件状态给了你一套方案，B 会话中午改了文件，A 下午继续干活时，它对世界的理解和磁盘上的现实已经不一致。单会话时代这个问题不存在——唯一的会话就是现实本身；共用目录的并行让每个会话都活在自己的缓存里。顺带一提还有一层隐性损失：三个会话的历史搅在同一份 git 记录里，哪个 AI 改了什么、以哪个版本为准，事后根本理不清。事故之后想要回滚，发现要回滚的并不是一次提交，是一场混战——你分不清哪个改动属于哪个会话，只能全部推倒。并行出的事故按乘法计价：一个会话出错损失一份工作，三个会话共享目录出错，损失的是全部在途工作加当天心情。这也是为什么隔离值得在动手之前做：它是唯一一个成本在事故之前、收益在事故之后的动作。 二、解法：一条命令开几间独立工作间 解法是 Git 自带的功能：worktree。一条命令，从同一个仓库里开出多间独立工作间： git worktree add ../blog-article -b article/ep08 git worktree add ../video-scripts -b feature/pipeline git worktree list # 查看所有工作间每间工作间有自己的目录、自己的分支、自己的暂存区，互不打扰。全套命令就三个，五分钟能上手： 命令 干什么 git worktree add 路径 -b 分支名 开一间新工作间并建新分支 git worktree list 列出所有在册工作间 git worktree remove 路径 拆掉一间（干净的话直接删） git worktree prune 清掉已手动删除目录的失效记录 用完一间，remove 拆掉即可。它和再 clone 一份仓库有本质区别，重点在历史这一层：clone 是把整个仓库连同全部历史复制一遍，磁盘直接翻倍；worktree 的所有工作间共享同一套仓库历史和对象库，各自只有一份工作区文件。开五间工作间的磁盘开销，约等于五份源码加一份历史；换成 clone，就是五份完整仓库。共享的还有分支名录和标签——任何一间工作间里建的新分支，其他工作间立刻可见，跨工作间的进度随时一目了然，不需要任何额外的同步机制。

你的 E2E 测的是页面还是业务：三条铁律抓静默失败

 included in AI 工程
问你一个问题：你的 E2E 测试全绿，用户为什么还在投诉？我审过的项目里，十有八九的 E2E 长一个样：一个用户登录，点几个按钮，断言页面出现某段文字，通过。写的人很认真，跑得也很勤，覆盖率报表年年涨。这种测试有个更诚实的名字——摆拍。它只能证明页面没崩，证明不了业务没崩，更证明不了角色的状态在正确流转；它抓住了「按钮不见了」这类前端问题，放跑了最贵的一类 bug：界面全绿，业务已经错了。 这套摆拍式测试我以前也写，直到社交模块的一次用户投诉让我看清了它的盲区：A 给 B 点赞，B 应该收到通知，测试里只有 A，B 的通知列表从来没人查过。后来我换成一套多角色互转的写法，跑了半年多，抓出十几条点 UI 永远碰不到的 bug。这篇把这套方法拆开，三条铁律、几个真实的坑、以及怎么判断你的 E2E 有没有牙齿。 一、点赞之后，谁去看通知 先讲那个让整套方法立起来的案例。社交模块，A 给 B 点赞，B 应该收到一条通知。这个需求简单到没人在意，但单用户 E2E 永远测不出它的问题——因为测试里只有 A，A 点完赞，根本没有人去看 B 的通知列表。投递链路断没断、通知入没入库、@提醒丢没丢，全都无人知晓。测试报告上是一个漂亮的勾，现实里是一次沉默的失联。这类 bug 的性格是静默潜伏，潜伏到用户替你发现。 顺着这个案例再看一遍传统 E2E 的动作：登录、点击、断言文本。每个动作都在 A 的世界里，B 的世界从头到尾没有出现过。它代表的是一整类错误：跨角色、跨端、跨时间的业务流转出错。B 的通知没人查只是最直观的形态，同类还有静默后端失败——前端弹着「成功」，后端数据根本没落库；还有跨端数据断裂——小程序下的单，运营后台查无此单。三种形态共性一致：UI 层看着全绿，业务事实是错的。它们也共享同一种贵法：静默，用户不说你不知道；影响面大，从上线到发现已经波及一批人；排查贵，没有失败现场，只能靠时间倒推。普通的前端 bug 用户一眼看见立刻反馈，反而是这三类「表面健康」的病灶最烧钱。 这种盲区的根源值得说透：单用户测试的结构性缺陷不是「写得少」，是「视角只有一个」。业务流转的本质是状态在角色之间流动，单用户测试天然只有一个视角，流动的另一端在它的世界之外。测试报告全绿，只说明视角之内的世界正常；视角之外的那一半业务，从来没被看过一眼。 先划清这套方法的适用边界，它不是万金油。它适用于有明确角色划分、角色间有状态流转的系统：社交的互动通知、电商的买家下单卖家发货平台结算、SaaS 的租户管理员和普通成员。纯展示型网站、无状态工具类应用没有业务流转可言，单用户点 UI 就够用，硬套这套是过度设计——给一个官网首页上多角色编排，投入和产出完全不成比例。 二、铁律一：多真实角色，别自己考自己 第一条铁律：涉及 A 到 B 业务流转的测试，必须用两个独立登录态模拟两个真实用户。A 发起动作，B 感知结果，两边都走真实接口。一个用户假扮两个角色，等于自己考自己，怎么考怎么过——它永远测不出角色间状态隔离和通知投递的问题。 让两个角色低成本登场，靠 mock-login 机制：接口传入用户 ID 和昵称，返回这个用户的真实 token。用之前有个我亲手踩的坑：测试里把租户 ID 硬编码成了 1，而项目默认租户是另一个值，后端回了一句 Tenant not found，所有登录全挂。查了半天，代码没有任何问题——是测试自己压根不在那个村。从此定死一条：租户 ID 永远从项目配置取，不硬编码。mock-login 本身只该在开发与测试环境开放，生产环境不存在这个入口，这个前提也要在部署配置里显式核对，别让「方便测试」的口子开到线上。

你的 AI 代码全绿也不代表能上线：407 个疑点只 4 个为真

xiaoshuai1024 included in AI 工程
问你一个问题：AI 写的代码，编译过了、测试全绿，你敢直接上线吗？以前我敢，直到某个周二下午。前端调的接口是 orders，带 s 的；后端一重构，路由改成了单数 order。一个字母的差别，编译两边却都绿，单测各自都过，然后运营走过来，轻描淡写地说：小程序白屏了。 这个下午让我把「验收」两个字重新想了一遍，最后落成两道关：代码这道关用四道契约闸拦接缝错误，长相这道关用代码审计判 vision 的真伪。全绿和能上线之间，隔着的就是这两道关。绿灯只是起点，可复核的绿灯才是通行证，这一句是全文的总纲，后面两道关全部从它展开论述的部分。这篇把它们各自拆开，连它们自己翻过的车也一并讲——门禁也是代码，是代码就会骗人，这话后面有实锤为证。 一、错在层与层的接缝上 白屏那种 bug 最烦的地方，是这种 bug 最烦的地方在于每一层单看都对。前端按约定调 orders，后端按重构计划改 order，谁都没有做错什么，错在层和层的接缝上——编译器只保证语法契约成立，保证不了前端发的请求真的能落到后端注册的那个路由上。这就像拼音输入法永远查不出你在骂人，字全对，意思全错。排查它也格外磨人：日志里没有报错，监控里没有异常，每次都从「前端说后端改了接口」「后端说没动过约定」的对峙开始，最后靠一个字母一个字母对出来。 跨层契约一共四类，每一类都让我们吃过亏：URL 对路由、SQL 表名对建表脚本、权限 key 对种子数据、迁移版本号唯一。它们的共同点是编译器一个都不管，而且都是声明式的——路由是注解声明、表名是 SQL 声明、权限是注解声明、版本号是文件名声明。 声明式这个属性是整件事的支点。声明写在固定位置，事实源就固定、可解析，脚本能从权威位置读出「正确答案」，再去和实际引用做比对。权限 key 拼错一个字母，权限等于没配，接口对全网裸奔，这种事故只能靠声明比对拦，靠 review 靠运气都不行。四类里最不起眼的是迁移版本号：两个分支各加了一个 V12，各自环境都好好的，合并到主干，迁移框架启动失败，整个服务趴窝。这是合并冲突的另一种形态，编译器同样不管。 顺带说一个被人低估的成本：靠人验收，结论既不可复现也不可传承。同一个页面，今天的小张说可以，明天的老王说间距不对，没有客观标准，验收质量取决于当时谁在审；人审过的页面出了问题，你没法回溯「上周验收时这个间距到底量过没有」。自动化验收的深层价值，就是把「当时谁在看、什么标准算过」固化成可复跑的脚本和可留存的报告，验收从一次性人工判断变成可追溯的工程产物。 AI 在这类错误面前格外脆弱，原因不是它笨，是它的上下文天生局部。它改后端 Controller 的时候，视野里是 Controller 的代码，前端 axios 调用了什么它根本看不见；它改前端的时候，后端路由注解同样不在视野里。两个文件同时打开都未必对得上，何况 AI 一次只看一个文件。它改了路由却不同步前端，不是偷懒，是它压根不知道前端在调这个。四类契约逐一套上去全是同一个形状：改后端看不见前端，加权限看不见种子，写 SQL 看不见建表，每个 Agent 都不知道别的 Agent 加了什么迁移。 二、第一道关：四道契约闸 既然 AI 不知道，就让脚本替它知道。我在提交之前架了四道闸，全部挂在 pre-commit，四道全过才允许提交。 闸 守什么 拦过什么 一 前端 URL 必须有后端路由接住 少个 s 的路由改名 二 SQL 里的表名必须在 DDL 里建过 Mapper 拼错表名，运行时才炸 三 权限 key 必须在种子数据里注册过 key 拼错导致接口裸奔 四 迁移版本号不许重复 两个 V12 撞号，服务起不来 原理很朴素：prompt 是建议，AI 可能忘；脚本是法律，它忘不了。AI 不需要知道前端在调什么，脚本替它查，查不过就拦下，拦下就逼它补全。在 prompt 里反复叮嘱「改路由记得同步前端」，可靠性远不如一道闸——建议会被忘，强制不会。

你敢让 AI 通宵修代码吗：夜间 daemon 的三条边界与 8 步回归

 included in AI 工程
问你一个问题：你睡觉的这几个小时，你的代码在干嘛？我的在打工，而且干得比白天还规矩。每天凌晨，一个夜间巡检 daemon 自己拉最新代码、跑 8 步全量测试，挂了就让 Claude Agent 读日志、找根因、切分支、修代码，修完回归验证，通过才提 MR——然后去飞书叫醒我。 这套东西跑了半年，第二天早上我只剩三种开场：全过，接着睡；已修复，花 20 分钟看 MR；修不动了，才真正动手。没有第四种「昨晚合的代码炸了」。但今天这篇不讲怎么搭，搭建过程在之前那篇拆过了，这篇讲更要紧的事：凭什么敢让它通宵无人值守。答案是三条边界，每一条都是拿真实教训换的。 什么叫夜间巡检？一个专上夜班、全年无休的守护进程，工资是电费。不领工资的员工随叫随到，可没人管它怎么干活，所以边界比能力重要，这是全文的主张。不领工资的员工最大的好处是随叫随到，最大的风险是没人管它怎么干活。所以边界比能力重要，这是全文的主张。 一、边界一：你的工作区它碰不得 第一个要防的，是 daemon 伤到开发者本人。巡检要切分支、拉代码，而你下班时可能正卡在某个 feature 分支上，改到一半的东西摊在工作区。多少夜间脚本在这一步变成了事故：早上来一看，分支被切走了，改动没了。 这类事故其实在圈子里有个固定剧本：夜间任务切走分支、开发者的未提交改动被冲掉、第二天找回损失的时间比写脚本的时间还长。所以我的做法分三层。第一层，动手之前先记现场：把每个仓库当前的分支名写进状态文件，这一步是后面一切还原的依据。第二层，切 dev 之前，把你没提交的改动用 stash 包起来。这里有个值得展开的选择：放着自动 commit 不用，为什么选 stash？commit 会往你的分支塞一个 wip 提交，就算后面能撤，reflog 里也留了痕，提交树被搞乱；stash 是 Git 原生暂存，用完 pop 回来，干干净净。源码注释里写得直白：避免污染任何分支的历史。翻译成人话：它帮你收拾屋子，但绝不碰你抽屉里的私人物品。 第三层，跑完必还原。不管测试过没过、修没修，最后一定把每个仓库切回最初记录的分支，fix 分支清理掉，后端进程停掉，锁释放。脚本被正常终止时 trap 也会补执行；退出、中断、终止信号三类事件都挂了清理逻辑，正常用到的路径全覆盖。第二天你打开电脑，工作区和你昨晚离开时一模一样，分支还是你下班时那个分支，一行都没少。 这层边界里还藏着一个可爱的工程细节：抢锁。daemon 要防两个实例同时跑，我没用 flock（跨平台麻烦），用的是 mkdir 当锁——同一个目录下 mkdir 要么成功要么失败，天生原子。更妙的是僵尸锁自愈：每次抢锁先检查上一个持有者的进程还活着没，进程死了锁没清，就自动清掉重抢。连报错文案都给人留了退路，告诉你手动删除哪个目录。自动化系统的每一层，都得假设上一层的操作者是个会手滑的人类，包括深夜里那个可能迷迷糊糊爬起来敲命令的你自己。 stash 这条路还有个不起眼的前置动作：执行前先确认状态目录在 .gitignore 里。漏了这步会出什么事故？日志目录会被 stash 一起打包带走，接下来脚本想写状态文件，写不进去，整条链路跟着哑火。这种坑不踩不知道，踩过才会写进代码。边界设计的难度从来不在主路径，在主路径旁边这些不起眼的小沟坎。 顺带一个反例警示：这套 trap 机制拦得住 Ctrl-C、拦得住 kill，唯独拦不住 kill -9。那是操作系统级的强制终止，任何脚本逻辑都来不及执行。所以停 daemon 用 stop 命令或者普通 kill，永远别上来就 kill -9；真被强杀了，去状态目录里看当时记录的分支名，手动切回去。自动化再周全，也要给操作系统留面子。 二、边界二：修好了也不许合并 第二条边界管的是 Agent 的手。修复流程长这样：读日志、定位根因、从 dev 切出 fix 分支、改代码。到这里不算完，最关键的一步在后面——把 fix 分支拉回来，跑完整 8 步测试回归，全绿才由脚本提 MR。注意主语：提 MR 的是脚本，从来就不是 Agent。

你的 AI 员工工资按字算：952 万 token 账单与 30 倍折扣的管法

 included in AI 工程
我雇了一群不领工资的员工：写稿的、配音的、剪片的、写代码的，全都不拿月薪。代价是他们的工资按字算，每读一个字、每写一个字，都在计费。这个发薪方式决定了整篇文章要讲的事：你的数字员工，账单形状和人类员工完全不同。 先给最反直觉的那个数字。我做一条视频，从稿子到成片，本地管线跑完，一个月成本不到一杯奶茶；而同一个月里，一条 Codex 会话记录显示，单个会话吃掉 952 万 token。最便宜的和最贵的，在同一张工资单上。 这篇把管饭方法拆成四块：先盘家底，看哪些成本可以压到电费级；再认大胃王，看清 952 万 token 的账单形状；然后拆那张 30 倍的价签，讲清折扣从哪来；最后是三条家规和月底对账的习惯。每一步的数字都能自己复现，文末给了入口。 一、先盘家底：哪些员工可以只付电费 数字员工分两类，发薪方式天差地别。一类跑在你自己家里：配音、转写、渲染，吃你的电，不找你收费；另一类跑在云上，按 token 计费，字字要钱。管饭的第一步，是把能搬回家的搬回家。 我自己的产线长这样：配音用 IndexTTS-2，一张 8GB 显卡本地合成，音色是我自己的克隆；转写用 whisper，同样本地跑；渲染在本地机器直接出片。这三样没有月费、没有订阅、没有按量计费，成本只有电费。 岗位 方案 计费方式 月成本量级 配音 IndexTTS-2 本地克隆 电费 一杯奶茶的分项 转写 whisper 本地 电费 同上 渲染 本地出片 电费 同上 写作 / 编码 Codex + DeepSeek 通道 按 token 大头，见后文 这张表的含义不在省了多少，在结构：本地岗位的边际成本接近零，我可以放开了让它干活，不用担心哪一步多花一分钱。云端岗位相反，每一步都在走表。把「不计费的岗位」最大化，是数字员工成本管理里杠杆最大的一步，做完这一步，剩下的战场只剩 token。 搬家有代价，得说实话。本地意味着自己管环境：8GB 显存是 IndexTTS-2 的及格线，而且要以 fp16 方式加载、关掉 CUDA kernel 编译，否则一张 8GB 卡会卡在 JIT 编译上十几分钟没有产出。这些摩擦是真实存在的，但它们是一次性的、可积累经验的；token 账单是按量的、随使用线性上涨的。一个买设备，一个交房租，我选买设备。 哪些活适合搬回家，我的验收标准就一条：这一步的输出，你能不能低成本地亲自验收。配音听一遍就知道行不行，转写对着时间轴扫一眼，渲染成片直接看。输出可检验的岗位，本地模型的水平够用，出了问题你当场就能发现。反过来，开放性生成的活（文章初稿、代码方案）不适合搬：验收成本高、迭代轮数多，云端模型的推理质量仍是主要生产力，硬搬是省小钱误大事。 还要留一条退路。克隆链路依赖的环境偶尔会出状况，我配了备链：edge-tts 出播音腔底稿，Seed-VC 换声。备链的音质不如主链，但它保证了「设备出问题的那几天，产线不停摆」。管成本的前提是产线活着，退路的费用是保险费，不是浪费。
