全栈架构 × AI 研发实战

线上告警自动修完还提 PR:五层架构搭自愈体系

xiaoshuai1024 included in AI编程
告警凌晨 3 点炸,值班被叫醒、排查、改代码、验证、发版,一圈走下来一上午没了。线上 MTTR 的下限,卡在人响应的速度上——告警再快,最后还是要人去排查、去改、去发版。 我在运维侧做过一次最彻底的重构,就是把"告警 → 人处理"升级成"告警 → AI 诊断 → 自动修复 → 自动提 PR → 人只做确认"。它建立在可观测性体系、监控告警、夜间自动巡检那套稳定性基建之上,但往上走了一层:让 AI 把从发现到修复的整条链路跑通。把人的环节替换成 AI,MTTR 才能从"小时级"压到"分钟级"。 这篇文章拆解一套五层智能监控与缺陷自愈架构,从指标定义到 changelog 生成,每一步讲清楚怎么设计、为什么这么设计。 一、这套体系适用于什么场景 先划边界。这套五层自愈架构不是万能药，它有明确的适用条件： 适用的场景： 技术栈相对统一（前后端框架固定、部署方式标准化），AI 能理解代码上下文； 已有基础的监控和日志体系（至少日志可检索、指标可查询），不是从零搭； 团队有 CI/CD 流水线和代码评审机制，自动化修复的结果能进正常研发流程； 故障模式有一定重复性——同一类问题出现过多次，有规律可循。 不适用的场景： 基础设施层面的问题（磁盘满、网络分区、K8s 节点挂了）——这类问题 AI 修不了代码，要靠运维自动化； 业务逻辑错误（“算出来的价格少了个零”）——AI 看不出"对错"，只能看出"异常"； 安全事件——不能自动修，必须人工介入评估影响面。 一句话定性：这套体系解决的是应用层的、可复现的、有日志/指标佐证的缺陷。不是替代 on-call，是把 on-call 从"救火"变成"审批"。 二、核心原则：五条铁律 在设计这套体系之前，我先定了五条原则。每一条都是踩过坑之后才确认的——不是拍脑袋的设计偏好，而是"不这么干就会出事"的底线。 原则 1：AI 的权限边界必须是硬的 AI 能做的事和不能做的事，要用代码锁死，不能靠 prompt 约束。 具体来说：AI 能读日志、能读代码、能创建 fix 分支、能提交 commit、能提 PR。但 AI 不能直接合代码到 main、不能直接操作生产环境、不能修改权限配置。这些硬边界不是写在 prompt 里的"建议"，是 API 权限层面和 CI 流水线配置层面锁死的。

睡一觉起来 bug 修好了:我的夜间巡检 daemon 怎么搭

你睡的时候,机器没睡。 我给项目搭了一套夜间全量测试 + 自动修复的 daemon。每天凌晨 00:00,它自己拉 dev 最新代码,跑 8 步全量测试——后端单测、集成测、运营单测、运营 E2E、前端 H5 E2E、小程序编译验证。挂了,Claude Agent 自动诊断日志、切 fix 分支改代码、用完整测试套件回归一遍,过了才提 MR(不合并),飞书推个「已修复 + MR 链接」叫醒你。 第二天你打开飞书,要么是「全过」,要么是「已修复待 review」,要么是「修不动了快来」。没有「早上来发现昨晚合的代码炸了」这个选项。 这篇拆开讲这套系统怎么设计的、为什么这么设计。 整体流程:五个阶段 每次触发(定时或手动 --once)跑五个阶段,核心逻辑是:测试归测试,开发者的工作区不能动。 Phase 0·预检:先把现场记下来 平台检测、Node 初始化、抢运行锁(防两个 daemon 同时跑)。关键是 save_state——把每个仓库当前的分支名记到文件里。这一步是后面无损还原的伏笔。 Phase 1·工作区准备:切到 dev,但你的改动不丢 开发者可能正卡在某个 feature 分支,有未提交的改动。脚本切 dev 之前,先把这些改动 stash 保护起来(git stash push -u -m "nightly-test: <repo>"),再 checkout dev 拉最新。你的活儿一条都不会丢。 这里特意用 stash 而不是 auto-commit,代码注释写得很直白:用 stash 而非 commit,避免污染任何分支的历史。auto-commit 会往你当前的分支塞一个 wip 提交,即便后面能回退,也会在 reflog 里留痕、搞乱提交树;stash 是 Git 原生的暂存机制,用完 git stash pop 恢复,干干净净。stash 前还会自动确保 .

「我们不养闲 Agent」:名字像段子的 skill 里全是方法论

xiaoshuai1024
当 AI 开始大面积写代码,「让 AI 别糊弄」本身成了一件需要工程化解决的事。前阵子我在项目里装了个叫 PUA 的 skill,它的开场白是这样的: 你正处于一个高绩效文化的研发团队中。你的每一次 AI 协同都在被评估——用结果说话,拿数据闭环。 当初给你定级 P8,是高于你实际水平的——因为信任所以简单。现在,证明你配得上这个级别。 名字一看就是整活——「我们不养闲 Agent」。装之前我以为是个情绪价值玩具,装之后发现,它确实在 PU,但 PU 得有理有据。AI 写代码那几个老毛病——半途而废、张口甩锅、动辄自嗨——它没跟你商量,直接固化成了三条硬性行为协议。 这篇不是软文。我用了几个月,把这个 skill 到底在干什么、凭什么有用,拆开讲讲。 先把丑话说前面:这 skill 的名字和开场白确实在搞噱头,P8、3.25、L4 这些词都是大厂黑话,带着浓浓的段子味。但抛开这层包装,它里面的设计是认真做过工程化沉淀的。下面我按「它在管什么、用什么机制管、实际用起来怎样」的顺序,逐层拆。 🚫 它在 PU 什么:三条红线,碰了就是 3.25 AI 写代码最常见的三个毛病,PUA 没跟你讲道理,直接定义成红线: 红线一:闭环意识。 你说做完了?数据在哪? 声称「已修复」之前,跑验证、贴输出,一样不能少。没有证据的完成叫自嗨——线上炸了写复盘,来不及。 闭环意识这一条,治的是 AI 最让我头疼的习惯:口头完成。它改完代码、跑一次测试通过,就敢说「已完成」。但「测试通过」和「问题修复」不是一回事——测试通过只能证明它写的代码没语法错,证明不了它修的就是真正的问题。要求贴证据(commit、测试输出、复现入参验证后的结果),等于把「完成」的定义从「我跑通了」收紧到「我能证明问题没了」。 红线二:事实驱动。 「可能是环境问题」「API 不支持」——你验证了吗?未验证的归因不是诊断,是甩锅。根因没写到源码级,不许收手。 事实驱动这一条,反的是 AI 的归因惰性。AI debug 时的第一反应经常是一句模糊归因——「可能是缓存」「应该是环境差异」「这个 API 可能不支持」。这些话听着像在分析,其实是甩锅:把责任推给一个不具体的「环境」,自己就不用继续挖了。要求归因必须标证据来源、必须挖到源码级,等于逼它把「可能」换成「就是」,把猜的换成验过的。 红线三:穷尽一切。 「我无法解决」——通用方法论的 5 步走完了吗?没走完就说不行,那不叫能力边界,叫缺乏韧性。 穷尽一切这一条最容易引起误解。它不是逼 AI 解决所有问题——有些问题它真解决不了。它逼的是:在承认解决不了之前,先把该试的方法都试过。没走完 5 步就说「我搞不定」,那不是诚实,是偷懒。走完了再说搞不定,才是真正的能力边界——这种情况下我会接管,而不是怪它。 听起来像段子。但你被 AI 忽悠过几次「应该是缓存问题」之后,你会觉得这三条简直是刚需。 我把这三条对到自己踩过的事故里,条条对得上。前阵子一个分润接口联调,AI 改完主逻辑说「跑通了,可以提交」。我问它验证了吗,它回「逻辑上没问题」。合上去当晚,分润金额按商户号取值时取错了字段,有一笔多算了一倍。 事后复盘,问题就出在这三条上:声称完成没跑验证(红线一)、把字段错配归因为「数据库设计不清晰」而不是去 diff 两个实体类(红线二)、diff 出来之后只修了这一处、没扫同名字段还有几处(红线三)。单看哪条都不致命,叠在一起就是一个要手动对账才能收场的线上事故。 这三条红线不是道德训诫,是事故归因之后能直接对应上的行为缺口。AI 不会因为你讲道理就不糊弄,但你把它糊弄的那几个动作定义成红线、碰了就判 3.

6 层缓存扛住 10W QPS,11W 就崩了:一次大促复盘

xiaoshuai1024 included in 架构
讲一次大促前夕刚做完缓存优化、活动开闸后被现实教做人的事。整个故事一句话:我把缓存放 cache(缓存)这件事做得很扎实,却忘了还有另一类流量叫 attack(攻击),它压根不走缓存。 我那时在京东云做官网架构。大促前的几个月,我主导了一轮缓存改造——把吞吐量从 200 QPS 干到 2 万常态,大促峰值能扛到 10W。结果活动当天流量叠了一波 DDoS 冲到 11W,缓存架构被绕过,连接池打满,服务响应缓慢。最后靠 WAF 清洗和限流把系统拉回来。 这篇复盘整个过程,核心教训一句话:多级缓存解决的是流量效率问题,解决不了流量安全问题。 大促前夕:多级缓存怎么搭的 改造前的官网是单层 SSR,峰值 200 QPS 就顶不住。大促一开闸,服务直接拖地。 “200 QPS 就顶不住"听着夸张,但单层 SSR 的瓶颈很真实:每个请求都要服务端完整渲染 HTML,渲染过程要查数据、拼模板、跑逻辑,全是 CPU 活;而且 SSR 实例的本地资源(CPU、内存)是有限的,扛不住并发渲染。200 QPS 不是网络带宽的极限,是单实例渲染能力的极限。要扛更多,要么加实例(贵),要么减少回源(缓存)。 我搭了一条 6 层多级缓存链路,让流量逐层消化,尽量少回源: 每层各管一段: ① CDN:边缘节点缓存静态资源,降级静态页。绝大部分请求在这一层消化。 ② WAF:页面级缓存 + 流量清洗 + 限流 + 安全策略。当时这层只在大促专项开启,平时不常驻。 ③ Nginx:反向代理 + 健康检查,故障节点自动摘除。 ④ SSR 实例本地 LRU:渲染好的 HTML 缓在本地,后端全挂时降级。 ⑤ Node BFF:接口聚合层缓存,减少后端回源。 ⑥ Redis:分布式缓存热点数据,带互斥锁防击穿。 降级也做了:SSR 渲染的静态页 CI 构建后上传 OSS 并刷新 CDN,后端真全挂时降级展示 CDN 静态页。

3 人两月交付 512 个功能,靠 30 条命令锁死纪律

xiaoshuai1024 included in AI编程
我主导的一个全栈项目(Java 后端 + Vue 小程序 + 运营后台,多模块多仓库),3 个人两个月交付了 512 个功能点。 这个数字不是堆人堆出来的,也不是靠加班。我把研发流程里每一步该守的纪律,都固化成了 AI 可执行的命令。最终沉淀了 31 条命令、3400 多行,挂在研发流程的每个环节上。 背后是两条工程主线,我先把它们说清楚,后面每一节都是它们的展开: harness 自治:人只定规则,把执行全权交给 AI。人不在审查的每一轮里,只看最终报告。harness(线束/约束)的意思是——命令不是"让 AI 做事",是"给 AI 套上纪律边界,让它在边界内自治"。 loop engineering:把审查、修复、验证都做成自动循环,直到收敛(零问题)才退出。能循环的就不让人介入,把"等同事有空"这类串行等待彻底消掉。 这是 「一切皆可脚本化」那篇的延续——那篇讲「为什么该脚本化」,这篇讲「具体沉淀了什么、怎么用命令的形态落地」。 一、命令不是脚本,是「流程契约」 先澄清一个概念。很多人把 AI 命令理解成「一段能跑的脚本」,这是低估了它。 我项目里这 31 条命令,是流程契约:每条命令规定了一个研发环节里「AI 该怎么做、必须守什么纪律、什么时候停」。脚本只负责执行,命令还要负责约束 AI 的行为边界。 举几个对比: 脚本:「跑一下测试」→ AI 跑了,失败也不知道怎么处理。 命令:/tdd → 锁定红绿重构、缺服务先探测再启动、跑通后必须汇报证据。AI 的行为被约束在 TDD 纪律内。 这个区别决定了命令体系能不能撑住 512 个功能的交付量。光会跑脚本,AI 跑偏了你拉不回来;有了契约,AI 在每个环节的行为都可预期。 再补一个对比,体会会更深。脚本版的「部署」是 ./deploy.sh,跑完就算,中间哪步挂了 AI 甩一句「脚本报错了」就停在那。命令版的 /deploy-prod-be-ops 把「构建产物 → 上传 → 重启 → 冒烟验证」串成一条带验证的链,任何一步失败都明确报出是哪一环,部署完还强制跑 /prod-testing 冒烟。区别在于:脚本只描述「做什么」,命令还描述「做完之后怎么确认做对了」。前者 AI 执行完就走人,后者 AI 执行完必须自证。512 个功能能交付,靠的就是这种「自证」嵌在每一步里。

380 页 UI 靠人走不过来:视觉验收里,AI 也会骗你

最近一个项目 380 个页面,每个页面停留十秒就是一个多小时,还不算记录、复现、回归。第二次改完再走一遍。第三次。靠人走 UI 验收根本不现实。 我的做法是按场景分两条路(和测试纪律、契约闸是一套,前面讲「代码对不对」,这篇讲「长得对不对」): 新功能:有高保真原型锚点,做像素级比对——保证 PRD 里的每个功能都被实现、样式和设计稿一致。 老功能:没有原型可比对,做 vision 巡查 + 代码审计交叉——保证改动不破坏兼容性,顺便扫历史遗留问题。 这两条路用的工具不一样、判断标准不一样、能回答的问题也不一样。混在一起做,要么新功能漏检样式偏差,要么老功能因为没有原型而无从下手。 为什么 UI 走查最难自动化 功能测试有断言,性能测试有指标,UI 走查靠的是人眼——主观、慢、还容易漏。 380 个页面,每个页面停留十秒就是一个多小时,还不算记录、复现、回归。第二次改完再走一遍。第三次。没人扛得住。 丢给 vision 模型批量看图,听起来很美。实际跑下来,它会自信地报错,其中相当一部分是幻觉。直接采信,要么误报一堆不存在的 bug,要么漏掉真问题。 所以问题不是"要不要用 AI",是分场景用对工具。 人眼走查还有个被低估的成本:结论不可复现、不可传承。同一个页面,今天的小张说「可以」,明天的老王说「间距不对」,没有客观标准,验收质量完全取决于当时谁在审。更要命的是,人审过的页面出了问题,你没法回溯——「这个间距上周验收时到底量过没有?」没人答得上来。自动化验收的深层价值之一,就是把「当时谁在看、什么状态算过」固化成可复跑的脚本和可留存的报告,让验收从「一次性的人工判断」变成「可追溯的工程产物」。 这也是为什么我一直坚持验收结果要落成代码里的断言或扫描规则,而不是停留在一份 markdown 报告里。报告会丢、会过时,断言和规则每次跑 CI 都会执行,问题一冒头就拦下来。视觉验收只有沉淀成可执行的东西,才算真正嵌进了研发流程,否则就只是一次性的走过场。 视觉验收三原则 往下展开之前,先把这套方法的底层判断收敛成三条原则。后面所有的工具选择、流程设计,都是这三条的落地: 原则一:分场景用对工具。 有原型就用像素 diff(确定性高),没原型才用 vision(会幻觉)。混用等于把不确定性引入确定性场景,得不偿失。 原则二:真相源必须机器可读。 设计稿不能只活在 Figma 里(人能看,代码扫不到),必须沉淀成 design token——颜色、圆角、渐变都在 variables.css 里定义,代码能直接读。这一层是「正确答案」的物理载体,没有它,代码审计无从谈起。 原则三:vision 只提疑问,不下结论。 vision 的输出永远是「疑点列表」,不是「bug 列表」。每个疑点必须经代码审计交叉验证,才能升级为 bug。这条治的是 vision 的过度自信——它越自信,越要警惕。 这三条是后面所有流程的根。任何视觉验收方案,只要违反其中一条,迟早翻车。 值得强调的是,这三条原则的排列顺序也是优先级顺序。团队资源有限时,该先建哪一层?答案是从原则二(真相源)开始。没有 design token 这层机器可读的基线,vision 巡查(原则三)无处交叉验证,像素 diff(原则一)也没有稳定的颜色锚点。我们项目就是先花了两个版本把全站颜色、圆角、渐变收敛进 variables.css,统一切到 token 引用,之后才谈得上做 diff 和 vision 巡查。基线没建好就上自动化验收,等于在沙地上盖楼,跑出来的结果不可信,反而会让团队对自动化验收失去信心。
