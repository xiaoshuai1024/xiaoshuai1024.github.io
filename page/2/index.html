全栈架构 × AI 研发实战

改一行代码别上重型流程：OpenSpec 和 Superpowers 我怎么选

 included in AI 开发
用 Claude Code 做全栈开发，代码不是难点，流程的轻重才是。 一个项目跑下来，你会遇到两种活：一种是改一行 SQL、修一个测试过时，十分钟就能验证完；另一种是跨前端、BFF、后端、E2E 四个系统的新功能，牵一发动全身。如果这两种活用同一套流程，要么单点修复被一堆文档拖慢，要么跨系统功能没有契约约束，改着改着就乱了。 我在低代码平台项目里同时用了两套流程：OpenSpec 管轻的，Superpowers 管重的。这轮真实开发我跑了五个 OpenSpec change 和一个 Superpowers plan，下面把过程和判断标准写清楚。 OpenSpec：给单点修复一个轻量闭环 OpenSpec 是一个 spec-driven 的轻量变更治理工具。核心想法很简单：每个改动都是一个 change，走 propose（提议）→ apply（实现）→ archive（归档）三步闭环。 它的配置文件里写死了适用边界：单个 change 不超过 3 个文件、不跨子系统、不超过 5 个 task。超过这个边界，它自己会提醒你"考虑用 Superpowers"。 这轮我用 OpenSpec 跑了五个 change，全是测试和缺陷修复： change 改了什么 为什么走 OpenSpec engine 单测修复 4 个测试文件同步 API 重构 单子系统（engine），纯测试 backend 集成测试 1 个测试加 @ActiveProfiles 单子系统（backend-java） form 创建 500 修复 1 行 fieldSchema 默认值 单文件，缺陷修复 ui test alias 1 个 vite.config 补 alias 单文件，配置 BFF submit formId 1 个 route 加一行注入 单文件，BFF 转发 每个 change 的过程都一样：openspec new change 建目录，写 proposal（为什么改）、design（怎么改）、tasks（分几步），然后 apply 改代码、跑测试验证，最后 archive 归档。整个过程在一个对话里闭环，不需要拆分会话。

TypeScript 教父开源 21 万 Star 的 25 个 Skill：把工程师自律焊进 AI 流程

 included in AI编程
让 AI 写代码的人，大概率见过这三种翻车： 需求只说了一半，AI 就敢往下编，编出来的代码「看着像回事、一跑就露馅」。 方向错了，它一路错到底。你让它做 A，它从第一步就走偏，之后每一步都在给错误的方案补细节，全程不喊停。 改 bug 也是。你让它改，它就改。改完复测，旧 bug 没了，新 bug 冒出来，来回三轮，代码已经看不出原样。 遇到这种问题，多数人的第一反应是换模型、调提示词、改温度。我的做法不一样：先搞清楚翻车的根源在哪，再找对应的工具。这篇文章讲的就是我在这个过程中挖到的一个项目，它把「资深工程师为什么不会翻车」这件事，拆成了 25 个可执行的 skill。 一、翻车不怪模型，怪流程里没有「停」 先看 AI 的工作方式。它是「续写器」：接收输入，预测最合理的下一步。这个机制决定了两个天性：有输入就输出，有错误就继续。 需求含糊，它不会停下来问「你说的 A 具体指什么」，而是开写它最熟悉的那个 A。测试没过，它不会停下来承认失败，而是分析一下「可能哪里不对」，改两行继续跑。 这些行为放在人身上很好理解：没人喊停，就一直干。AI 比人更顺从，人累了会停，AI 不会。 所以问题不在模型聪明不聪明，在流程里有没有「停」这个环节。资深工程师和新手的差别就在这里：新手拿到需求就写，写错了再改；老手会先盘问需求、先写测试、先把 bug 复现出来。不是老手写得快，是老手停得准。 这个认知不新鲜，但把「停得准」变成 AI 绕不过的流程，最近有个项目做到了极致。 二、mattpocock/skills：一个 21 万 Star 的开源技能库 这个项目是 mattpocock/skills，作者 Matt Pocock，TypeScript 社区的知名教育者（Total TypeScript 作者）。他把自己日常写代码用的整套 Agent 技能库开源了，MIT 协议，GitHub 上 21 万 Star。 仓库简介一句话：Skills for Real Engineers，给真实工程师用的技能，不是 vibe coding（瞎写）用的。 先看整体结构。25 个 skill 按两大轴组织：一类是 Engineering（工程向），一类是 Productivity（通用向）；按触发方式又分两种，用户主动敲的（/grill-me）和模型自动触发的（/tdd）。 安装简单到不像一个 21 万 Star 的项目：

别再背 AI 黑话了：一条主线串起大模型、Agent、Skill、MCP

xiaoshuai1024 included in AI编程
一个前端朋友发我一篇 AI 教程，说看不懂。我点开一看，满屏的大模型、Agent、RAG、MCP、Harness，标题写着「零基础入门」。他把原文念给我听，我笑不出来。我刚碰 AI 开发那会儿，也是这个表情。 那之后我把 Claude Code、Cursor、OpenCode 用进了每天的工作流，博客的写作、发布、配图全部交给 AI 跑。现在回头看，这些词没有一个是孤立的。这篇把我用下来的理解讲一遍，你会发现 AI 黑话就一条主线，串起来之后，教程里的每个词都有了落点。 主线：AI 从「只会回答」到「越来越能自己干活」 AI 圈的词看着多，实际就一条线：AI 从只会回答，到越来越能自己干活。 每个黑话都是这条线上的一站。站在起点，后面每个词都在回答同一个问题：AI 能多独立地把活干完？ 大模型决定它聪不聪明。提示词决定它听不听得懂。Agent 让它自己动手。Skill 让它按你的流程干活。MCP 让它够得着你的工具。Harness 让它进得了大项目。 这张图是全文的地图。下面每一节讲一站，从最底层开始往上叠。每节我都会先用人话讲它是什么，再讲它解决什么问题，然后说我实际怎么用，最后拆一个常见误解。 六层不是六个并列的选项，是叠加的关系。底下几层是地基，上面几层是增量：没有模型，一切免谈；有了模型不会问，白搭；会问了还得一层层指挥，累；指挥明白了，还想让它记住你的规矩。一路叠上去，才是一个能独立干活的 AI。 这条线不是画死的，它还在往前长。多模态让 AI 看得见图和声音，记忆让 AI 跨会话记住你，这些都是主线上的新站点。以后看到新词，先别慌着学，拿主线对一下它补的是哪一层，就明白它为什么会出现。 举个完整的例子。我让 AI「把这篇新文章发布到公众号」： 底层模型负责理解我的意图。提示词告诉它「走 wechat 发布流程」。Agent 接单后自己拆步骤。Skill 提供发布流水线（封面、高亮、内链）。MCP 让它真实登录公众号后台、上传素材。如果这个项目代码量大，Harness 保证它按规矩来。你看，一句话的指令，六层全都参与了。 大模型：AI 的智商底座 它是什么 大模型（LLM）是 AI 的大脑。GPT、DeepSeek、Claude、豆包、Kimi，这些都是大模型。它们本质上是同一个东西：用海量文本训练出来的神经网络，擅长的是「预测下一个词」。你现在读到的这些文字，如果是 AI 写的，也是这么一句句「猜」出来的。 区别只在脑子好不好使。模型的能力上限，决定了 AI 干活的天花板。后面所有黑话，都建立在这个底座上：模型不行，提示词写得再好也白搭。 聊大模型时还会碰到两个词，一起讲掉。一个是上下文窗口，指 AI 一次能记住多少内容。窗口小的模型，你跟它聊长了它就忘了开头；窗口大的，几十万字的代码库它能一次读完。另一个是推理能力，指 AI 处理复杂逻辑的能力。简单问答用不着推理，改业务代码、写复杂 SQL，推理能力的差距就出来了。 它解决什么问题 AI 圈聊「换模型」，本质是换大脑。DeepSeek 出来那阵，很多人把代码从 GPT 换到 DeepSeek，体验是「便宜了但变笨了」；后来又换回 Claude，发现「贵但真能干活」。这不是工具差异，是智商差异。 我用一个场景演示给你看。想象你雇了个员工，让他把桌子擦干净： 你（演老板）：把桌子擦一下。 员工 A（演一个笨模型）：好的。（原地不动，开始幻想自己已经擦完了）

那就和前端、后端好好道个别吧

 included in 职业思考  AI 开发
这两年，「前端已死」的论调隔几个月就刷一波。但这话没说到点子上，该告别的不是前端，是「我只做一端」这个身份本身。 Claude Code、Codex 这些工具，能把一个页面、一个接口、一段 SQL 直接生成出来，前后端的边界正在被抹平。纯前端、纯后端这两个身份，正在同时失效。能活下来的研发，底线是全栈：一个人把想法从界面跑到数据库再跑到部署。比全栈更要紧的，是持续学习的能力。这套工具栈半年一换，今天熟的框架，明年可能就被模型生成替代，停下来就会被甩下。 一、AI 对前后端的冲击，正从不对称走向收敛 为什么是「前后端一起告别」，而不是只有前端？ 最早被冲击的确实是前端。UI 是最容易被 AI 直出的东西，给它一条指令，React 组件、样式、交互就出来了，前端「画界面」那部分最先被压扁。 但后半句很少有人说：后端正被快速追上。我现在让 Claude Code 写一个 Spring Boot 接口、配好 JPA、连上 MySQL、写迁移脚本、再补 JUnit 测试，它干得比我带过的大多数实习生快。SQL、Dockerfile、部署脚本，同样一个指令的事。 一年前我还敢说，后端的复杂度（事务、并发、状态机）AI 撑不起来。现在不敢了。它写出来的事务边界和并发处理，大部分时候是对的，错的地方它还能照着我给的测试自己改。前端中招早，只是因为 UI 更直观、训练样本更多；后端正以同样的曲线被追上。 前后端被冲击的时间差，正在被抹平。死守「我只做前端」或「我只做后端」，等于守一段两端都在塌的墙。 二、价值不在单点，在能把整条通路串起来 这是个简单的经济学问题。 AI 把「写一个组件」「写一个接口」的成本压到接近零，单点技能的溢价就消失了。一个只会切页面的前端、一个只会写 CRUD 的后端，可替代性变得极高。替代他们的不是另一个更便宜的人，是一个不要钱的模型。 零成本的单点，撑不起一份工资；能把零成本的单点串成可用产品的人，才撑得起。 价值挪到了另一头：能把整条通路串起来的人。从用户点一下按钮，到前端响应，到接口，到业务逻辑，到数据库，到部署和监控，谁能在每个节点都用 AI 当杠杆产出，又在关键节点留得住判断力，谁就端走了大部分价值。 举个具体的：同样是做个内部工具，只会前端的人要等后端给接口、等运维给环境，卡在排期里出不去；能把通路走通的人，一个下午用 AI 把界面、接口、数据库、部署都生成出来，自己跑通、自己上线。前者是流水线上的一道工序，随时能换；后者是能直接交付一个产品的人，议价权在自己手里。市场给这两者的定价，差着一个数量级。 全栈这个词，得重新定义。AI 之前，全栈是个高门槛的褒义词，因为一个人手动精通两端太难。现在门槛换了。全栈的意思是：端到端能负责，AI 当杠杆，关键处有深度。 三、组织和人，都在往这个方向滑 不是只有我一个人这么感觉。 身边不少前端的轨迹，这两年都在变：纯前端 → 被逼全栈 → 转去做 Agent 或 AI 应用，越来越多的代码让模型写。他们没失业，是被推着进化了。我自己也在这条线上，博客里一路从前端写到全栈，再写到 AI 开发，不是年初规划出来的，是被一次次需求推出来的。前端做着做着要碰接口，接口做着做着要碰部署，部署做着做着开始用 AI 批量生成，回头一看，已经回不去「只做一端」了。 组织层面的信号更硬，而且不止一家。美团 CLC 食杂零售 Keemart 研发团队已经把前端和后端团队正式合并；InfoQ 的判断是，字节、阿里都在推进同样的整合，AI Coding 把跨栈门槛压下去之后，「前后端一起消失」正在从口号变成组织动作。阿里支付宝体验技术部被拆进各个业务部门，独立的前端部门在消解，工程师按业务目标负责，不再按「切图」负责。 合并还在往上下游蔓延。字节 Data 部门已经灰度内测 QA 转研发序列，要求测试掌握 AI Coding，不再做纯测试；测试左移、研发自测、自动化覆盖率进考核，已经是大厂标配。独立测试团队的边界，正在和研发合到一起。

RAG 召回率上不去,先别怪 embedding 模型

 included in AI编程
RAG 答不准,大部分人的第一反应是换 embedding 模型。换完还是不准,再调阈值,再换更大的模型——循环两轮,准确率原地踏步。 这不奇怪。文档要被检索命中,得先走完四步:切片 → 向量化 → 匹配 → 分级。切片把文档拆成语义单元,向量化把语义表达成数值,匹配把 query 和文档对起来,分级决定这些结果怎么用。四步各管一段,任何一步做错,后面的步骤都救不回来。 这篇把「怎么把四步分别做对」讲透。线上做过的讲做法,还没做的(混合检索、重排)讲原理和决策,不装作上线过。 结论先放这:召回率上不去的瓶颈,通常不在模型,在切片边界和检索结构。 一、先对现象:换了模型,准确率纹丝不动 运营文档问答,基准集准确率早期在 60% 上下。我们调了两周提到 85%,贡献最大的两件事都跟模型无关: 切片从"照搬英文 500 token"改成"中文 400 字 + overlap 100 字"。 检索从"只调 topK 和阈值"改成"四步链路分别做对"。 embedding 模型最后才换了一次,换完的收益远小于前两件事。这背后是个反直觉的事实:embedding 模型对中文的理解差异能带来约 20% 的准确率差,但切片切碎了,模型再好也拼不回被切成两半的信息。 顺着这条线,把四步逐段拆开。 二、切片:让每个 chunk 是一个完整语义单元 为什么必须切片 大模型上下文有限,不能整篇塞。但更关键的是检索的粒度问题:query 往往只有一句,文档却有几百句。整篇文档只对应一个向量,这个向量是几百个句子压缩出来的"平均脸",每个句子的特征都被稀释了,query 和它算相似度,没有哪个单句能"冒尖"。切片把文档拆成多个语义单元的向量,query 才有机会打准某一句具体的话。 token 切片和中文的坑 切片的做法是按 token 滑窗,贴着自然边界走。我们用的 Spring AI TokenTextSplitter: new TokenTextSplitter(500, 50, 50, 100, true) // chunkSize=500, overlap=50, keepSeparator=true(保留段落分隔符)keepSeparator: true 让切片尽量贴着段落走,而不是纯按 token 硬切。这是初步的结构感知,它在标点和段落附近找切点,代价最小。 中文切片的第一坑:不能照搬英文的 token 数。英文一个 token 约 0.

省掉订阅费的 Codex,把国产模型用明白了

 included in AI编程
省掉订阅费,是这篇文章的出发点。OpenAI 的 Codex 桌面版是当前最能打的 AI 编程 agent 之一,但官方使用路径绕不开两件事:一个 ChatGPT 账号和一笔订阅费。我在 AI 开发这条线上已经全量跑了小半年的 agent 工作流,这次把 Codex 的模型层整个换掉——用开源的 CcSwitch 把 DeepSeek 接进 Codex,配置完直接跳过官方登录,打开就是能用的状态,模型走国产 DeepSeek,按量付费。 读完你能做到:在一台 Windows 机器上装好 Codex 桌面版,不注册 ChatGPT 账号、不交订阅费,双击图标就能聊;用真实任务验证 DeepSeek 确实在响应。 适用人群与前提 这篇教程面向会用桌面软件、能看懂终端报错的开发者。不需要懂命令行,配置全程图形界面: 系统:Windows 10 / 11(本教程实测 Windows 10)。macOS 上的 Codex 桌面版同样支持,CcSwitch 配置思路一致。 工具版本:Codex 桌面版(本文实测 build 26.730.8199.0)、CcSwitch 最新版、DeepSeek API。 CcSwitch 获取:到它的 GitHub 仓库(farion1231/cc-switch)下载最新版 Windows 安装包,装好后首次打开是空供应商列表,配置完就有东西了。 科学上网:下载 Codex 桌面版安装包和后续更新需要。工具自备,这里不展开。 账号准备:一个 DeepSeek 开放平台的 API key。平台充值后按量付费,个人写代码一个月几块钱。不需要 OpenAI / ChatGPT 账号。 整体思路 核心分工:Codex 客户端是壳,模型供应商是芯,CcSwitch 负责换芯。
