全栈架构 × AI 研发实战

Codex 用法分 5 级：90% 的人卡在第 2 级，你在哪级

xiaoshuai1024 included in AI
刷到一条视频：18 天跑 400 个任务，总结出 Codex 的 5 级用法。框架我认，数字我怀疑——不是怀疑他吹，是怀疑那个用法层级对普通开发者太远。我把这条视频的分级框架拿来，用我自己这一年的全仓实测重新填了一遍血肉：每一级的坑、每一级的升级判据，都是我真实翻过车的地方。 先给结论：90% 的人卡在 2 级。不是能力问题，是没人告诉你 2 级往上还有明确的台阶，以及每级台阶的判据长什么样。这篇就是那份判据清单。 L1 会提问：把 Codex 当问答机 第一级的特征就一条：打开就问，问完就关。「这段代码什么意思」「这个报错怎么修」，一轮对话解决一个小问题，不超过五行改动。 这级没有问题，人人都从这来。坑在于停在这级的原因：你只把模型当更快的搜索。同样一个报错，L1 的问法是「这个错怎么修」，拿到答案就走；更好的问法是「这个错的根因是什么，同类还有哪些」——多问半句，一次交互变一次学习。 升级判据很好测：你最近的 10 次对话里，有没有超过 3 次是连续追问同一个问题。全是「一问一答就散」，你还在 L1；开始连续追问，你已经往 L2 走了。 L2 喂上下文：让 Codex 读你的规矩 第二级开始有工程味：你会主动给上下文了。项目背景、代码规范、技术栈约束，写进对话开头或者项目根的 AGENTS.md，让模型带着你的世界观数活。 本仓就是活例子。仓库根有一份 AGENTS.md，写死的都是边界类条目：Hugo 锁 0.124.1 勿升级、源码仓和 Pages 仓是分离架构别混淆、画图一律 draw.io 禁 mermaid、部署走 deploy.sh 四步流程别自创。任何 agent 进来干活，第一眼读的就是它。效果直接：没有这份文件时，让 agent 改构建配置，它十有八九建议升级 Hugo 到最新版（升了主题就崩）；有了这份文件，「勿升级到更高版本」六个字省掉一轮来回纠正。 这份文件现在三千多字，但它不是一次写成的。第一版只有两百字，写着写着发现 agent 反复在三个地方翻车，就把这三处的边界补进去；后来又翻两次，再补两轮——所谓「改过三轮才站稳」，就是这个循环：跑，翻车，把翻车原因写成禁令，再跑。规则文件不是文档，是事故记录本。 L2 的坑是喂错方向。多数人拼命往上下文里塞业务背景，塞了三千字，模型改代码还是我行我素。模型缺的往往不是背景，是边界：哪些不许动、哪些必须保持、改完要过什么检查。三百字的禁令清单，比三千字的项目介绍更改变行为。 升级判据：你的项目里有没有一份 agent 每次都会读的规则文件。没有，你是 L2 的门外汉；有了，并且改过至少三轮（第一版一定不够用），L2 站稳了。 L3 拆任务：从「帮我做」到「帮我做这一步」 第三级开始拉开差距。特征：你不再把一个完整需求丢给模型，而是拆成有序的小步，每步有明确的完成标准和验收方式。 那条视频说 18 天 400 个任务，平均一天 22 个。我的实测账更糙也更有参照性：这个仓库目前 97 篇文章、全套发布管线，每一篇从选题到发布平均要过 9 个阶段——选题分析、骨架、正文、配图、验证、构建、发布、回填、复盘。一个「写文章」的模糊指令，agent 做出来的是四不像；拆成 9 个带门禁的步骤，每步确认再进，产出才稳定可控。其中两道门禁是硬的：文章草稿必须经我确认才准发布，视频的口播稿和分镜必须完整过目才准渲染——就是这套流程，多次拦下「内容跑偏但表面完工」的半成品。任务数量不重要，任务有没有「完成判据」才重要：400 个没判据的任务，不如 40 个有判据的。

3 份拷贝看懂 QKV：Transformer 1750 亿参数拆到矩阵这一层

 included in AI
把 Transformer 整张网络摊开看，里面没有循环、没有卷积，没有任何称得上「结构」的东西——矩阵乘法、加法、softmax，三种运算翻来覆去叠几十层，就是 GPT 这类模型的全部。一个能写代码、改 Bug、陪你聊到深夜的程序，骨架朴素到让人愣神。 QKV 是另一处被讲玄学的地方。评论区一半人卡在「QKV 到底是什么」，我当年也卡过，卡住的原因只有一个：总想把它当成高深概念去背。把话说白就通了——QKV 不是概念，是同一个矩阵乘了三个权重矩阵得到的三份拷贝。 这篇我把一个 token 从输入到输出的完整旅程走一遍，每一步都落到矩阵形状上。看完你不光能在脑子里徒手推演整张网络，还能拿到开头那个反差的答案：奇迹不在运算本身，在运算的堆法和次数。 一、先看全景：数据在 Transformer 里走一趟 设一段输入有 n 个 token，每个 token 被表示成 d 维向量（GPT-3 小版本里 d 取 12288，教学场景常取 512）。整句话就是一个 n×d 的矩阵，从现在起你只需要盯着这个矩阵的形状变化。 它先过嵌入层拿到初始值，加上位置编码，然后进入编码器堆叠的 N 层结构。每层做三件事：自注意力（token 之间互相看一眼）、残差连接加归一化（把结果稳定地传下去）、前馈网络（每个 token 自己再深挖一次）。三层做完进下一层，N 层之后从顶端取输出。 走到嵌入层之前还有一步：分词。模型不认识字，只认识 token id。主流方案是 BPE（字节对编码）：从单个字符开始，统计语料里最常出现的相邻对，反复合并成新词元，直到词表达到目标规模。中文一个常用字多半是独立 token，英文一个长单词可能拆成两三段，数字、代码、标点各有各的拆法。「unbelievable」可能是 un+believ+able 三块，每块查嵌入表得到一个向量。分词质量直接影响一切：同样的文本，分词差劲的模型等于戴着一副度数不对的眼镜读书，而且没有「词汇必须成词」的硬约束，模型对拼写错误、混排中英的容忍度反而更高。GPT 系列词表约五万，LLaMA 系列十几万（多语言更友好），这个数字在第七节算参数量时还会回来。 一张图记住形状就够了：任何时刻数据都是 n×d，变的只是内容。注意力层让 token 之间交换信息，FFN 层让每个 token 独自消化信息，两者交替，这就是 Transformer 的全部节奏。 训练和推理时这张图的走法不一样。训练是「整句并行」：n 个 token 一次性送进去，掩码保证第 t 个位置只能看见前 t-1 个，然后每个位置同时算一遍「下一个词预测的对错」，效率极高。推理是「逐字串行」：生成一个词，把它拼回输入再算一遍，你在对话框里看到模型一个字一个字往外蹦，就是这一轮轮矩阵乘法在跑。同样生成 100 个 token，训练时一遍前向就处理完的上百个位置，推理要重复一百次前向——这就是为什么推理贵，也是后面 KV cache 这类优化存在的理由。

一个会话吃掉 952 万 token：我的 Codex 账单拆解与三条省法

xiaoshuai1024 included in AI工程
翻开 ~/.codex/sessions 里我自己的会话记录，有一条让我坐直了：2026-08-20 16:45:36（UTC+8）开始的那个 session，54 次模型调用，总输入 952 万 token，总输出 6.6 万。输入是输出的 144 倍。这中间我没换模型、没改配置，就是正常干了一个下午的活。 起因说来简单：我给频道挑选题，把市面上省 token 的攻略翻了一遍，清一色是「关思考、开压缩、勤开新会话」的口诀，没有一篇贴过自己每一轮的真实流水。口诀对不对、在自己的通道上灵不灵，全靠信。我不太想信，就想亲眼看，于是有了这篇逐轮拆解。 这篇文章就是把这 952 万拆到每一轮，看它从哪来、被什么放大、怎么砍。全部数据来自我本机的 codex-cli 0.140.0（deepseek-v4-flash 通道），8 个真实会话加一组受控 A/B 实验，没有任何估算。 这套方法适用谁，不适用谁 适用：用 Codex CLI 干活、按 token 计费或被限额卡脖子的人。不管你走官方 API 还是像我一样用 cc-switch 切到 DeepSeek，下面讲的机制一模一样。团队协作的仓库更该看——AGENTS.md 是随仓库分发的，你写在里面的每一个字，都会乘以全组每个人的每一轮会话，一份松散的文档就是全组的持续成本。 不适用：纯订阅制（ChatGPT Plus 内的 Codex 用量）的用户——你不直接付 token 钱，但限额消耗是同一套逻辑，看懂机制一样能少撞墙。 先交底数据来源，这也是本文的方法论价值：Codex 的每个会话都在本地存了一份 JSONL 流水（~/.codex/sessions/年/月/日/rollout-*.jsonl），每次模型调用都记录了 token_count 事件，输入、缓存命中、输出、思考 token 四项分開记。你不依赖任何后台报表，就能把自己的账单拆到每一轮。文末清单里有现成的挖掘脚本核心逻辑，十行以内。 三条原则，先记住再往下看 一、上下文是复利负债。 模型不记得你，Codex 每一轮都把全量历史重新发给它。你在第 30 轮为第 3 轮的文件内容付钱，这是账单的结构性来源。操作口径：会话按任务切，文档按「违背会出错」删。 二、缓存是放大器，不是免单。 重发的大头会被供应商的上下文缓存按折扣价接住——但命中率取决于你的前缀稳不稳定。同样 952 万的重发量，命中率 98% 和 46%，实付差出一个数量级。管缓存，比重发本身更值得花精力。操作口径：AGENTS.md 进稳定期后上锁，要改集中批量改。 三、开关要先验证再信任。 我把推理档位从 high 调到 low，一分钱没省，思考 token 反而更多——这个通道根本没把参数透传给模型。配置文件里写了不等于生效，省钱的动作必须用数据验证过才算数。操作口径：任何参数改动，当周跑一次 A/B 对账。

Codex 桌面端零基础教程：装好它，用中文说出第一个项目

xiaoshuai1024 included in AI编程
装好 Codex 要多久？从下载安装包到浏览器里看到 25:00 的倒计时，我在这台 Windows 机器上实测用了不到二十分钟。但多数人卡住的地方不是写代码，是开头五分钟——安装和登录。网上教程一抓一大把，功能章节讲得都很全，唯独「装好、登进去」这一步默认你会，多少人倒在这道门槛前。这篇文章把我这台机器上的 Codex 桌面端从头到尾跑了一遍，每步都有真机截图，专门解决开头那五分钟，再往下走完整个实操闭环。 读完你能做到：装好 ChatGPT 桌面应用，登录进 Codex，认清楚界面和两种工作模式，用一句中文让 Codex 从零做一个番茄钟网页，验证它真的能跑，最后把模型供应商切到 DeepSeek，月成本掉一个量级。 适用人群与前提 这篇教程写给两类人：完全没装过 Codex、想用自然语言做东西的新手；装了但卡在登录或不会用的半新手。 前提四样： 系统：Windows 10 / 11。本文实测 Windows 10，macOS 桌面端流程一致，安装包格式不同 ChatGPT 账号：登录用。没有账号或不想注册的，看第六步，跳过官方登录直接接 DeepSeek 网络：能访问 openai.com 和 GitHub。工具自备，本文不展开 版本：ChatGPT 桌面应用（含 Codex 模式）build 26.x、Codex CLI 0.140.0（本文验证环境）、CcSwitch v3.20.0、DeepSeek V4 Flash 有个背景先交代：Codex 桌面端底层就是开源的 Codex CLI（Apache 2.0），官方把它包进了 ChatGPT 桌面应用。桌面端的好处是零命令行，文件操作、diff 审查、图片生成都有图形界面，适合不碰终端的用户；CLI 自由度更高，适合脚本化和远程场景。这篇走桌面端。 两条路选哪条，我的判断看你的使用场景：只在编辑器旁边干活、想要可视化 diff 和图形界面，桌面端够用且零学习成本；要批量跑任务、要接进自己的自动化脚本、要在服务器上干活，CLI 才是正路。多数人从桌面端入门，用到一定深度自然知道什么时候该切 CLI——两个是同一个 Codex，配置、会话、模型选择完全互通，切换没有迁移成本。 顺便回答常被问到的问题：Codex 和「豆包」「文心一言」这类聊天助手有什么区别？区别在于它是智能体，能直接读写你电脑上的文件、执行命令、改完自己验证。聊天助手给你贴一段代码让你自己搬，Codex 自己把活干完再让你验收。这个区别贯穿后面所有步骤，看实操部分就明白了。 整体思路 五步主线，一条省钱支线： 安装：下载 ChatGPT 桌面应用安装包，装上 登录：ChatGPT 账号登录，进入 Codex 认界面：功能区、工作区、两种模式、权限三档 实操：用一句中文发任务，全程看它干活 成品：审查 diff，确认文件落盘，浏览器打开验证 走完五步之后，如果你想省订阅费，第六步用 CcSwitch 把模型切到 DeepSeek——这正是本文区别于网上大多数教程的地方：不止教你怎么用，还教你怎么把成本打下来。

装完 Codex 只会写代码？6 个 skill 让它开始剪视频

 included in AI 开发
做一条技术视频，从选题到发布，你亲手操作的步骤有几个？ 我的答案：0 个。这句话听起来像凡尔赛，但它有一个确切的工程含义：我给 Codex 装了 6 个 skill，让它接管整条视频生产。我的视频管线里根本没有「剪辑」这个动作。整条生产被拆成了 6 个环节：选题、文案、配音、画面、合成、发布，每个环节对应一个脚本或一个 skill，人只做两件事：做判断、审结果。视频不是剪出来的，是跑出来的。 Codex 本身能写代码不稀奇，稀奇的是装上这 6 个 skill 之后，它干的活从写代码变成了剪视频。 这套管线不是一天搭成的。它从 2026-08 起在我这里稳定跑了几十条视频，环节之间全部用结构化数据（JSON）衔接，中间没有任何手动搬运。 「0 次操作」也不是口号，它是可验证的：每条视频的产物目录里有一份 metadata，记录口播稿迭代、渲染参数、验收结果。管线里每多一个手动步骤，metadata 里就多一个缺口。全自动不是宣称，是日志。 下面我把每个环节拆开讲：它接管了什么操作、用了什么参数、为什么这么选。 先把话说死：视频生产是工程活，不是创意活 大多数人做视频慢，是因为把它当创意活来干：灵感来了才动手，素材随手拖进剪辑软件，边剪边改。这条路线的问题在于：创意判断只占一条视频的 10%，剩下 90% 是确定性操作。删停顿、加字幕、调色、排版、生成封面、上传发布，这些动作的结果是确定的，确定的事就该交给脚本。 我的三条原则： 判断和操作分离。人管「这条选题行不行」「这句口播拗不拗口」「这版画面节奏对不对」，脚本管「怎么执行」。操作环节一个都不要手动做。 视频是合成的，不是剪的。剪辑意味着从素材里挑、修、拼，而合成是把确定性的原料（文案、音频、卡片）程序化装配。我走的是后者，所以每一步都能重跑、能验收、能回放。 中间产物是数据，不是文件。每个环节的输出是 JSON：字幕时间戳、场景定义、口播分句。数据比文件好处理：能校验、能重排、能拿给下一个环节直接吃。 这套做法有适用边界。它适合的内容是「有信息密度、结构可预期」的技术视频：速报、教程、知识图谱。它不适合表演型的视频：真人出镜的口播、需要临场发挥的测评，脚本接管不了「人」的部分。边界划清楚，才不会被无脑套用。 三条原则落地成一张总览图，后面每个环节都对应图上的一个格子： 下面按生产顺序，逐个环节说。 环节一：选题——让数据替我决定拍什么 第一个环节管的是「拍什么」，它的自动化程度常常被低估。我的选题由 douyin-topic skill 接管，输入是三个真实数据源： 抖音搜索热榜接口：免登录免签名，51 个热搜词 + 5 个上升热点，覆盖率高 蚁小二热点事件：热榜 + 真实播放量（千万级），已绑定账号 方向内话题搜索：在垂直方向里搜话题，验证「这个方向有没有人看」 三源之间还有降级逻辑：热榜接口异常时自动降级到蚁小二数据源，结果缓存 10 分钟。抓取行为带反风控扰动：UA 池随机取、请求间隔加抖动、浏览器行为人性化（随机滚动步长、概率回滚）。固定节奏加固定指纹是自动化最容易被识别的组合，抓数据的代码本身也要按「真人」的标准写。 三源数据汇到一起后，按一条潜力分公式打分： 潜力分 = 0.4 × 热度增速 + 0.3 × 垂直匹配 + 0.2 × 竞争度（反向） + 0.

Claude Code 与 Codex 的 Skill 与 MCP 加载源码对比：装上不等于用上

xiaoshuai1024 included in AI 开发
我装过一个很不错的 Claude Code skill，用一次之后它就再也没被触发过。我以为是我描述写得不好，调整了好几轮 frontmatter 都没用。直到读了两边的加载源码，我才发现自己的预期从根上就错了：skill 不是「装上就进入工作区」的东西，它是「被发现、按需注入、特定时机触发」的三段式机制——Codex 的源码里，skill 的加载要过 selection 和 invocation 两道闸；MCP 更直接，连 server 连接都是按需的。装 20 个 MCP 不用，一个都不连；装 5 个 skill 不提，它们就只是躺在磁盘上。 这是系列最后一篇必做篇。前五篇见架构分层、主循环、subagent、上下文、权限门控。 先交代这篇的证据等级，比前几篇复杂，因为 skill 部分横跨了 CC 的两个时代：Codex 侧照旧是源码确证（commit 63b268c81b）；Claude Code 侧分两段——v1.0.88 没有 skill 系统（全文件搜索 skill 只命中一处 Arma 语法定义的关键字表，是假阳性），skill 的分析基于 2.1.229 的 claude.exe 二进制字符串勘察加官方口径；MCP 两侧都有 1.0.88 的行号级确证。每处结论我会标明来源。 一、Codex 的 skill：三道闸的按需机制 Codex 把 skill 做成了独立 crate（skills/），职责拆得很清楚：parser.rs 解析 SKILL.md 的 frontmatter（代码注释原话：Validated metadata parsed from a SKILL.md frontmatter block），loading.rs 负责发现和加载（load_roots 扫描各个 skill 根目录，LoadedSkillRoot 带快照缓存，不是每次都重扫磁盘），selection.
