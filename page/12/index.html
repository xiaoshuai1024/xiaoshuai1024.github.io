低代码渲染引擎揭秘:schema 驱动到可编辑画布

xiaoshuai1024 included in 架构
拿一份 JSON 渲个页面发个 demo，这类项目 GitHub 上一抓一把。真正卡人的是后面三件事：能编辑、能扩展、能演进。我主导的低代码平台「鲁班」核心就是一个自研的渲染引擎 + 设计器，这篇把它拆开——schema 怎么设计、渲染器怎么递归、设计器怎么拖拽编辑。 项目归属说明：渲染引擎的设计经验源自大厂时期主导的内部系统"鲁班"，本文代码实现以个人开源项目 OpenLuban（架构同源、代码全新重写，GitHub）为准。 schema:一棵树 + 一个表单值字典 低代码引擎的起点是 schema。我把它设计得很薄,有意压到最小: interface NodeSchema { id: string type: string // 组件类型,如 'LubanButton' props?: Record<string, unknown> children?: NodeSchema[] } interface PageSchema { root: NodeSchema formState?: Record<string, unknown> // 表单值绑定容器 }一个关键决定:表单控件的值不挂在每个节点上,而是统一放在顶层 formState 字典里,以控件的 props.name 为 key。运行时只要一个扁平字典就能驱动整页所有表单字段,提交、校验、回填都简单。 老实讲这步我纠结过。每个节点自己存自己的值,直觉上更「自然」,写 schema 的人也省心。但一落地就发现问题:提交时要遍历整棵树去收集,校验时要在树里找控件,后端回填要把值塞回各自的 props——三个环节都要重新爬树。换成顶层一个字典,提交是 JSON.stringify(formState),校验是对字典跑规则,回填是 Object.assign。一个数据结构,省掉三处脏活。 还有一个更隐蔽的取舍:schema 要薄,但版本治理要从第一天留口子。PageSchema 现在没显式的 version 字段,不是忘了,是早期的 demo 还不值得为它背兼容包袱。但 NodeSchema 的结构我刻意没塞多余东西,留出加 version / compatibility 的余地。一旦真有存量页面要演进,加个字段、走个 migrator 就能接住。第一天就把 schema 塞满,后面想改一处得动全身——这种坑我见太多了。

一份代码变成每个租户的小程序:代开 vs 按租户打包

xiaoshuai1024 included in 架构
做过 SaaS 多租户 Web 的人，第一反应都是「运行时识别租户就行」。但这套在微信小程序上直接死——manifest.json 里的 appid 在构建期就被烧死进产物，运行时改不了。这篇就讲这个硬约束逼出来的两种解法：按租户打包（构建期注入 AppId）和平台代开（一份模板 + ext_json 注入 tenantId）。 先把结论丢出来: 按租户打包:构建期把租户的 AppId 烧进 manifest.json,一份代码跑 N 次构建,产 N 个小程序包。简单直接,但租户越多构建成本越线性涨。 平台代开:基于微信开放平台第三方能力,一份代码模板给所有租户用,差异完全靠 ext_json 在 commit 时注入 tenantId。租户再多代码也只有一份,这是首选。 代开才是 SaaS 多租户小程序的正解,按租户打包是后备。下文会展开为什么。 难点:微信小程序的 AppId 是构建期常量 做 SaaS 多租户 Web 的同学,第一反应通常是:“运行时识别租户不就行了?根据请求里的 tenantId 加载不同配置、走不同租户的数据。” 在浏览器里这套没问题,但在微信小程序里直接行不通。 原因藏在微信的约束里:manifest.json / project.config.json 里的 appid 字段,在构建期就被烧死进产物,运行时改不了。微信开发者工具、上传、提审、发布,整套流程都认这个 AppId——它对应的是微信开放平台里一个独立的小程序实体。 也就是说,“一份代码多个租户"在 Web 上成立,在小程序上必须在构建期(或发布期)就把租户的 AppId 注入进去。这是 SaaS 多租户小程序所有架构决策的前提,绕不开。 我们最初的设计也想"运行时识别”,做了两周发现走不通,才老老实实回到构建期注入这条路上。这个弯路本身值得单独说一节,因为很多人都在这里栽。 我们走过的弯路:运行时识别为什么死 最初的想法是用一个通用 AppId(开发者自己的)打底,运行时再根据用户登录的租户去走租户的逻辑。这个思路在"开发期"是成立的——本地用开发者 AppId 调试没问题。 但一上审核就崩了: 微信审核认的是包里烧死的 AppId,你挂羊头卖狗肉,审核驳回。 即使审核过了,用户搜不到这个小程序——它对应的微信实体是开发者自己的 AppId,不是租户的。 业务上要求"每个租户有自己的品牌入口、自己的小程序码、自己的搜索结果",这就要求每个租户在微信侧是一个独立小程序实体。 所以最终只能回到"构建期注入 AppId"这条路。区别只是:为每个租户单独打一份包(模式一),还是用第三方平台代开,一份模板包走遍所有租户(模式二)。

RAG 没那么神:Spring AI + ES 搭多租户知识库

xiaoshuai1024 included in AI编程
RAG 在网上被讲得玄之又玄,什么"企业知识大脑"“智能问答中枢”。说穿了就是一句话:在问大模型之前,先从你的私有文档里检索出相关片段,塞进 prompt,让它"看着资料"回答。 它的价值不在魔法,在让大模型基于你的私有、可更新、可追溯的知识回答,而不是只靠训练时的旧记忆。 上一篇《构建一个多租户 AI 助手》讲了整体架构,这篇把其中最被神话的一块——RAG 知识库单独拆开,从 0 到 1 讲它到底怎么落地。 这篇不讲概念,讲工程:多租户怎么隔离、切片怎么配、向量库怎么选、入库失败的文档怎么重试、改了切片策略怎么重建。代码全部来自生产系统。 一、要解决的核心问题 运营后台的 AI 助手要能基于每个租户的私有运营文档回答问题——A 租户问"我们店铺的商品上下架流程",助手得去查 A 租户的运营手册,不能拿 B 租户的文档乱答。 需求拆成四个硬约束: 多租户隔离:A 绝对检索不到 B 的文档,这是底线,不是优化项。 文档可管理:运营能在后台上传、编辑、发布、删除文档,不是只能命令行灌库。 检索有质量闸:不相关的片段不能塞进 prompt,否则反而拉低回答质量。 可演进:切片策略、embedding 模型变了,得能批量重建,不能推倒重来。 RAG 的是四步:切片 → 向量化 → 存储 → 检索。但工程上远不止这四步,下面逐层展开。 二、整体设计 先看全貌。一篇文档从上传到被检索命中的完整链路: 几个关键设计决策,后面逐个展开: 双存储分工:MySQL 存可编辑的业务数据(标题/正文/标签/状态),ES 存向量做检索,两边各司其职。 多租户靠 metadata filter:所有租户共用一个 ai_knowledge 索引,检索时按 tenant_id 过滤。 质量闸在检索层:similarityThreshold(0.7) 卡掉不相关结果。 生命周期可重建:DRAFT/PUBLISHED 状态机 + es_indexed 标记 + 批量 rebuild。 一次入库的时序 文字不如图清楚。运营点"发布",一篇文档被切片入库的完整时序: 注意 vectorStore.add(chunks) 这一行把 embedding 和写 ES 两件事打包了——embedding 由 starter 注入的 EmbeddingModel 完成,业务代码不碰向量细节。写成功后才回 MySQL 标 es_indexed=1,这个标记后面会反复用到。

业务代码一行框架 API 都不写:@AiTool 桥接 Spring AI

xiaoshuai1024 included in AI编程
AI 助手要"能干活"而不只是"能聊天",靠的就是 Tool Calling(工具调用)。这篇讲我怎么把工具定义和 Spring AI 解耦:业务同学写起来零框架负担,换框架一行不动,写操作有确认门禁,每次调用全审计。 一、要解决的核心问题 我们的多租户 AI 助手要服务运营同学。运营同学说的不是"帮我查订单"这种结构化指令,而是自然语言:“今天的订单怎么样"“把这几个待审的代下单批一下"“这几个订单统一备注成已沟通”。 对模型来说,这些话背后是不同的业务动作。难的不是对话,是怎么把自然语言安全地落到真实业务方法上。这中间有几个工程问题必须先回答: 谁决定调哪个工具? 不能写 if 用户问订单就查订单 的硬编码分支。自然语言的组合空间是无限的,if-else 永远写不完。 工具怎么定义? 业务同学写一个工具,要不要被 AI 框架的 API 绑架?今天用 Spring AI,明天换 LangChain4j,要不要把所有工具重写一遍? 多租户怎么穿透? A 租户的运营说话,工具只能查 A 租户的订单,这个隔离边界怎么从对话层一路传到业务 service? 写操作怎么拦误操作? 模型要是手一抖调错写操作(比如批量改错订单),怎么拦?Agent 直接改生产数据,谁来背锅? 这篇就是回答这四个问题。核心思路一句话:调度交给模型,工具实现交给业务,中间架一层自研桥接,把两边彻底解耦。 这四个问题里,第四个(写操作安全)是最容易被新手忽略、却最先在真线上出事的。很多人做 Agent 工具调用,demo 阶段全用只读工具,觉得一切都很美好;一旦上写操作,模型一个理解偏差,批量改错一批订单,善后成本极高。所以这套设计从一开始就把「写操作和只读操作分开,写操作必须过确认门禁」当硬约束,而不是事后补丁。这个意识有没有,决定了你的 Agent 是 demo 还是生产系统。 二、整体设计 先看全貌。一次"运营问一句话、模型决定调工具、框架自动执行、结果回喂模型续生成"的完整链路: 几个关键设计决策,后面逐个展开: 不自研 Agent 框架,只桥接工具。工具调用循环交给 Spring AI,业务只实现工具本身。 工具定义和 Spring AI 解耦。自研 @AiTool + ToolHandler 一层,业务代码看不到任何框架类型。 租户上下文用 toolContext 透传,多租户隔离从对话层穿透到工具层。 写操作走确认门禁。Redis token + 参数哈希 + 消费即删,防重放防误触。 一次工具调用的时序 文字描述不如一张时序图清楚。运营问"今天订单怎么样”、模型决定调 query_orders、框架自动执行、结果回喂续生成的完整链路:

每个租户用自己的大模型:动态 ChatModel 工厂怎么落地

xiaoshuai1024 included in AI编程
多租户 AI 助手里最难的一块,不是 RAG、不是 Agent,是让每个租户用自己的大模型。这篇专门讲怎么用"动态 ChatModel 工厂"把这件事做扎实——从表设计、加密脱敏,到工厂的缓存与失效,再到为什么不用 Spring AI 的 starter 自动装配。 一、问题:为什么不能写死一个全局 ChatModel 随便找一个 Spring AI 的入门 demo,大概率是这样:在 application.yml 里配一个 spring.ai.openai.api-key,启动时由 starter 自动装配出一个全局 ChatModel bean,业务里 @Autowired 直接用。单租户、单 Key、单模型,这样没问题。 但我们的平台是多租户的。同一个 AI 助手,服务几十个租户,每个租户: 用自己的供应商(A 用 DeepSeek、B 用通义千问、C 用智谱 GLM); 用自己的 API Key(各自的账单、各自的额度、各自的限流); 用自己的模型参数(温度、max_tokens、具体模型型号都不一样); 在运营后台随时改这些配置,改完要立刻生效。 一个全局 ChatModel bean 在第一点上就垮了——它的 apiKey 在启动时定死,运行时拿不到租户上下文。这就是多租户 AI 和单租户 AI 最本质的区别:模型实例必须按租户动态创建、缓存、失效。 方案 能否多租户 配置生效 复杂度 全局单 ChatModel bean(starter 装配) 不能(只有一个 Key) 改配置要重启 低 每次请求都 new 一个模型 能 实时 极高(每次建连,性能不可接受) 动态 ChatModel 工厂 + 缓存 + 失效(本文) 能 配置变更 evict 后实时生效 中 结论很清楚:需要在两者之间取一个平衡点——按租户懒加载,建好后缓存复用,配置变了再失效重建。这就是下面整个设计的起点,也是多租户 AI 和单租户 AI 最根本的区别所在。

组件库从单包到 Monorepo:三层演进的踩坑复盘

xiaoshuai1024 included in 工程实践
做企业级组件库,难点从来不是写组件,是组织组件。一个按钮谁都会写,但当组件库膨胀到几十个组件、跨多个对外包、要兼顾内部联调和外部 npm 发布时,怎么组织代码、怎么编排构建测试发布流水线才是真正工程难题。 本文以 luban-ui 为例,讲透两件事:Monorepo 怎么分层、工程化流水线怎么编排。技术栈清单不是重点,背后的取舍才是。技术栈是 Vue 3 + TypeScript + Vite + Nx + pnpm,但这套判断换成 React + Webpack + Turborepo 同样成立。 本文以 luban-ui 为例,讲透两件事:Monorepo 怎么分层、工程化流水线怎么编排。技术栈清单不是重点,背后的取舍才是。技术栈是 Vue 3 + TypeScript + Vite + Nx + pnpm,但这套判断换成 React + Webpack + Turborepo 同样成立。 为什么不直接用 Element Plus / Ant Design 这是被问得最多的一个问题。直接回答:因为我们的组件库不只是基础组件,还有低代码设计器和运行时渲染。 Element Plus 这类成熟库解决的是「基础 UI 组件」——按钮、表单、表格。但 luban-ui 的定位是: 基础组件(luban-base):按钮、表单、布局等。 低代码组件(luban-low-code):设计器、运行时渲染、schema、组件注册表。 这两层耦合度极高——设计器要识别基础组件的元信息、运行时要按 schema 渲染基础组件。如果用第三方基础组件库,设计器和运行时就只能"猜"组件的 props,没法精确控制。自己造基础组件,是为了让基础组件天然带「可被设计器识别」的元信息。 这是架构决策的根本出发点:选型不是看哪个库功能多,是看你的场景需要哪些约束。如果你只做基础组件库,直接 fork Element Plus 改皮就行,别造轮子;如果你要做低代码平台,基础组件必须自己掌握。 这个选型判断还有个延伸:造基础组件的成本,远不止「写几十个组件」这一次性投入,还有长期的维护成本——浏览器升级了要适配、无障碍标准变了要跟、新交互范式出来了要加。第三方库有社区帮你摊这些成本,自研就全压在自己团队头上。所以自研基础组件这个决策,隐含的前提是「团队有持续投入的预算和意愿」。如果只是短期项目、做完就丢,fork 第三方库反而更划算。我们做这个决策时,算过一笔账:自研前两年维护成本高于 fork,但到第三年,因为基础组件天然带设计器元信息、低代码层不用做适配,总成本反而反超 fork。这个决策是面向长期的,短期看是亏的。
