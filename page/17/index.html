装完 OpenSpec 的 skill 不会用,等于往仓库扔白纸

xiaoshuai1024 included in AI编程
装上 OpenSpec 的 skill 只是开始,真正的问题是怎么用对它们。 我见过太多人装完 OpenSpec 的 skill 就放着——知道有 /opsx:propose 建变更,剩下五个 skill 全在吃灰,或者用错时机。skill 装得全不等于会用,就像买了全套工具,不等于每把都摸过。 我在「前端 → 全栈 → AI 开发」这条线上一路走过来,OpenSpec 的 skill 是我唯一真正放进日常流程的规格驱动工具。这篇文章就把这六个 skill 按真实使用顺序逐个讲透:每个解决什么问题、产出什么、什么时候用、怎么和前后衔接。 结论是:这六个 skill 不是六个独立工具,是一条流水线。 想法进来,经过 explore → propose → update → apply → sync → archive 六道工序,变成主规格里沉淀下来的能力。每一步的产物,都是下一步的输入。 下面我用一条真实的改动走完整条流水线:给一个查询功能加缓存。它不涉及任何具体业务,就是个最常见的编程场景——查询太慢,想加一层缓存。这条改动小到看得懂,又完整到每一步 skill 都有对应动作。 先认识四个产出物 讲 skill 之前,得先认识它们操作的对象。OpenSpec 把一次改动固化成一个 change,里面是四个文件,放进仓库的 openspec/changes/<名字>/ 目录。四件套是流水线反复操作的工件: proposal.md——为什么改、改什么、影响什么,相当于立项报告 specs/<能力>/spec.md——系统必须做什么,是增量规格,只声明本次改的行为 design.md——怎么做、权衡了什么,是决策留痕 tasks.md——按什么顺序做,是执行计划 四件事混在一份文档里,就是一份没人能维护的巨型需求书;拆开,每一件都能单独演进、单独 review、单独归档。四个产出物是你和 AI 之间的合同,后面的 skill 全部围着它们转。 第一个:explore——想清楚再动手 流水线的入口不是建变更,是 explore。它是个思考模式,不写代码、不建 change,只做一件事:把模糊的想法摊开,变成可以写进 proposal 的共识。 什么时候值得先 explore?

DeepSeek 便宜到骨折还拿了世界第二,但我劝你先别切

xiaoshuai1024 included in AI编程
做 AI 开发，选模型是每周都在做的决策。7 月 31 日 DeepSeek 上线 V4 Flash 正式版 API，我第一时间翻的是榜单——Terminal-Bench 2.1 拿了 82.7 分，超过 GLM-5.2，只比 Opus 4.8 低 2.3 分。 这个数字本身很漂亮，但漂亮得不等于该立刻切过去。一个模型值不值得换，要看三件事：能力是真的强还是测出来的强、强在哪、代价是多少。这篇就把 V4 Flash 这三件事拆开讲。 结论是：这是国产模型第一次在编程榜上摸到第一梯队的边，成本结构更是碾压级。但榜单数字带着官方测试的水分，真实生产表现还得等第三方验证。 该试的可以试，该等的别急。 82.7 分的含金量：真的进了第一梯队 Terminal-Bench 2.1 测的是 AI 在真实命令行环境里，能不能独立完成端到端的复杂任务——不是写一段函数，是从拿到需求到跑通结果的全流程。这个榜比单纯写代码难，也更接近 Agent 的真实工作。 V4 Flash 的 82.7 分，排在它前面的只有 Opus 4.8 的 85.0。后面是 GLM-5.2 的 81.0、自家 V4-Pro 预览版的 72.1、V4 Flash 预览版的 61.8。 2.3 分的差距意味着什么？在这种百分制的综合评测里，2-3 分经常落在测量误差和抽样波动的范围内。换句话说，V4 Flash 和 Opus 4.8 在这个榜上的差距，已经小到不能说"明显落后"了。这是一个质变——之前国产模型在这个层级总是差一档，现在站到了同一条线上。 但要注意一个细节：Opus 是 Anthropic 的闭源旗舰，价格不便宜；V4 Flash 是 DeepSeek 的速度成本优先版本。一个堆料旗舰和一个性价比型号打到了一起，这本身就是 V4 Flash 成本结构的胜利。

一个商户号绑死一个 AppId,多租户收款差点当场翻车

xiaoshuai1024 included in 架构
做过 SaaS 多租户 Web 的人，第一反应都是「一个商户号收钱就行，后台记一下是哪个租户的，月底对账分钱」。在浏览器里这套没问题，但在微信小程序上直接死——商户号绑定 AppId，一个小程序只能挂一个商户号。你一个平台商户号，对应的是自己小程序的 AppId，收不了租户小程序的款。 这篇就讲这个硬约束逼出来的两种解法：直连商户（每个租户独立签约微信支付，用户付的钱直接到租户的商户号）和服务商模式（平台注册为微信支付服务商，统一收银 + sub_mch_id 标记每笔资金的归属）。 先把结论丢出来： 服务商模式：平台统一收银，sub_mch_id 区分资金归属，一份接入走遍所有租户。租户越多收益越大，这是首选。 直连商户：每个租户自己签商户号，资金不经平台手，合规最干净。租户少、合规严的场景下反而更省心。 和上篇（代开 vs 按租户打包）不同，直连商户在特定场景下优于服务商模式。支付架构的选择不是"哪个更先进"，而是"哪个更适合你的租户画像"。下文会展开为什么。 难点：微信支付的商户号绑定 AppId 约束 做 SaaS 多租户 Web 的同学，第一反应是：「一个商户号走天下，后台记 tenant_id 不就行了？」在 PC/H5 支付里，这套确实跑得通——一个商户号可以登记多个公众号/H5/App 的支付能力，同一个商户号收所有渠道的钱。但在小程序侧，这个绑定关系是反过来的： 一个小程序的 AppId，只能绑一个微信支付商户号。 微信支付的商户号产品登记逻辑是这样的：一个商户号可以在开放平台登记多个 AppId（公众号、小程序、H5、App 各一个），但反过来看——一个小程序只能登记一个商户号作为自己的支付能力。这意味着： 你开发了一个 SaaS 平台，自己也注册了商户号（平台商户号） 这个平台商户号只能绑到你自己的小程序上 你绑不了租户的小程序——因为租户的小程序是一个独立的微信实体，它要绑的商户号必须是这个租户自己签约的商户号（直连模式），或者通过服务商模式用你的平台商户号代收 换句话说，“一个商户号收所有租户的钱"在小程序上直接走不通——你收不了租户小程序的钱。这个约束和上篇的 AppId 构建期烧死是同一个性质：微信平台的底层绑定关系，绕不开。 我们走过的弯路：一个商户号想解决所有问题 我们最初的设计也和大部分人一样：「一个平台商户号收钱，反正后端的订单表里有 tenant_id，月底对账按租户分钱。」甚至画了一个很漂亮的资金流图——用户付到平台，平台按比例分给各租户，觉得完美。 两周后才发现哪里都走不通。 第一道墙是微信结算的粒度。微信支付 T+1 打款，不是按订单维度打的，是按商户号维度汇总的。用户付了你 100 块，微信 T+1 把 100 块打到你商户号绑定的银行账户——你不可能让微信把其中的 30 块直接打到租户A的账户，20 块打到租户B的账户。微信不提供"按订单分账到不同银行账户"这个能力。分账 API 只能把资金分到sub_mch_id（子商户号）或 openid（个人零钱），不能分到任意银行账户。 第二道墙是退款路由。用户在租户A的小程序买了东西要退款，钱应该从租户A的商户号余额退。但如果所有钱都进了你的平台商户号，退款时你就要判断"这笔钱是哪个租户的”——听起来简单，但线上情况复杂得多：租户A余额不足了怎么办？平台先垫？垫了租户A不认账怎么办？ 第三道墙是合规。平台一次性经手所有租户的资金流，在央行支付体系里这叫「二清」（二次清分）风险。微信支付的服务商资质本身就要求平台不能碰资金，所有资金必须通过微信结算体系直接到租户账户。 走通这些墙之后，我们发现只有两条路可以选。没有第三条。 模式一：直连商户（每个租户独立签约） 每个租户自己向微信支付申请一个商户号（像任何一个独立商家一样走签约流程），平台只负责在技术层面帮租户完成入驻和配置。用户在租户A的小程序付钱，钱直接到租户A的商户号，微信 T+1 结算到租户A的银行账户。平台不碰资金，只传递订单信息。

同样的 Claude Code,三个月把你甩开三倍的是这群人

xiaoshuai1024 included in AI编程
我观察到一个现象：两个水平差不多的开发者同时开始用 Claude Code，三个月后效率能差出三倍。 工具一样，模型一样，差距在哪？不是提示词写得花不花哨——提示词的边际收益在第一个月就到顶了。真正拉开差距的，是对 Claude Code 作为工程工具的完整理解。 很多人用 Claude Code 的方式，本质上还是 Chat 那套：在一个会话里不断提问，上下文越滚越胀，然后会话崩了、模型开始胡扯，就关掉重开。这不是用工具，这是在把 IDE 当 ChatGPT 用。 而真正用得好的人，理解这套工具的完整能力面： 命令是给 AI 套纪律边界，不是「问它一个问题」 Skill 是把经验固化成可复用的命令，不是写一次性提示词 Subagent 是一个人指挥一群 AI，不是一次只做一件事 打断与恢复是效率杠杆，不是失败 这篇文章把这套技能树拆开讲。每条都不是「技巧」，是工作方式的切换——从被动响应到主动编排，这才是高手和新手的真正差距。 一、Claude Code 使用金字塔 我对 Claude Code 的使用深度分了三个层级。大多数人停在第一层，高手在第二层和第三层之间切换。 第一层，对话级。把 Claude Code 当高级 ChatGPT 用——打开就聊，问问题、写代码、修 bug，一个会话从头跑到尾，跑崩了就重开。这一层能解决日常 60% 的问题，但你永远在给 AI 当助理——每次重复上下文、每次重新描述项目结构、每次等着它慢慢推理。 第二层，命令级。开始用 /command、Skill、Task 这些结构化接口。这一层的核心变化是：你不写提示词了，你调用预定义的流程。命令像 API 一样有输入输出契约，Skill 像函数一样封装了可复用的逻辑。这一层效率提升不是线性的，是乘法——写一次命令，反复用几百次。 第三层，编排级。同时启动多个 Subagent，各自做独立任务，你在中间做决策和收敛。用到 Workflow 做多阶段自动化：审查、修复、验证全部并行，最后一轮收敛才叫你。这一层你从「AI 的操作员」变成了「AI 的指挥官」。 这个金字塔得先讲明白，因为后面每一节都是在讲「怎么从当前层爬到上一层」。 二、内置命令与工具：先弄清楚有什么 Claude Code 的「命令」其实分三类：斜杠命令（/xxx 在会话里输入）、工具（内置函数，AI 在后台调用）、CLI 子命令（终端里输入 claude xxx）。三者的区别决定了你用什么方式控制 AI，这点得先搞清再往下讲。 斜杠命令（Slash Commands） 在会话里直接输入 /xxx 调用。这是你作为用户主动控制 AI 的主要方式。

还在说「agent 就是调一次 LLM」?你理解的方向就是错的

xiaoshuai1024 included in AI编程
Agent 不等于"调一次 LLM 拿结果"。当任务需要多步推理、需要外部资源、需要校验产物、需要人参与决策时，单次 LLM 调用搞不定，你需要一个编排层：一套把目标拆成多步、按状态机推进、每步有降级有回退的设计。 这篇文章讲 agent 编排要解决的五个工程问题。全部基于我在 luban 项目里写的 Agent（Python + LangGraph 风格的状态机）的真实代码。代码在 app/agent/，每个节点都是纯函数 (state, deps) -> state，依赖通过 dataclass 注入、可 mock。 状态机骨架：五个节点 + 一个回环 agent 编排的核心是显式状态机。我的 Agent 状态机长这样： understand → retrieve → [generate → validate]循环 → hitl 或 feedbackunderstand 和 retrieve 各跑一次，是前置准备；generate 和 validate 是循环主体；三种出口：hitl（等人确认）、feedback（回环重试）、failed（超限或硬错）。 主循环代码非常克制： async def run(self, state: AgentState) -> AgentState: state = await self.nodes["understand"](state, self.deps) state = await self.nodes["retrieve"](state, self.deps) while True: state = await self.

还在拿「工具升级」看 AI?你正在错过第四次工业革命

xiaoshuai1024 included in AI编程
先把结论摆在这:这一轮以大模型为核心的 AI 浪潮,就是第四次工业革命。判断依据不是某家公司的估值,也不是模型评测分数的高低,而是回到"工业革命"这个词最硬的定义——让生产某一类东西的成本掉一个数量级。前三代都是这么定义自己的,这一代也一样,只不过它降的不是纺纱、炼钢或装配的成本,而是"预测"和"生成"的成本。 我写这篇,是因为过去一年和我聊过的人里,大多数还在用"工具升级"的眼光看 AI,把它当成又一个能提效的软件。这种视角会让人持续低估它。一个工具升级不会改写一个行业的研发流程,也不会凭空造出一批新岗位。但工业革命会。 一、回到标尺:什么样的技术变革才算工业革命 “工业革命"被用滥了,每出新东西都有人喊。我用的标尺来自经济史学家:一项技术要被称为工业革命,它得让某一种基础生产要素的成本出现一个数量级以上的下降,并且这种下降会外溢到几乎所有行业。 前三次都符合。蒸汽机让动力的成本掉了一个数量级——工厂不再建在河边。电力让能源传输的成本掉了一个数量级——福特把装配工时从 12 小时压到 1.5 小时。计算机和自动化让信息处理的成本掉了一个数量级——打字员大面积消失,互联网把信息分发边际成本压到零。三次的共同特征:它们降的不是某一种产品的成本,而是一类基础能力的成本。能力变便宜后,所有用到它的行业都被重排,人的重心从"执行"挪到"指挥机器执行”。 按这个标尺看 AI,它降的是预测和生成的成本。一份靠谱的需求预测过去要养一支数据分析团队,现在几分钟出结果;一段能用的代码过去要工程师写一天,现在 AI 代理几分钟写完。我的体感锚点是:过去一年我用 Claude Code,一个带分页和条件筛选的查询接口从实体类到 Controller 调通,从至少半小时压到10 分钟。端到端任务上——研发账本里 4 个人 2 个月干出近百万行代码——这事在 AI 之前需要至少 4 倍人力。当单人产出被放大 4-10 倍,这在经济学意义上就是工业革命级别的。 二、传统行业:验证流程被 AI 改写 AI 不只影响软件业。传统行业里最先被改写的,不是生产本身,而是验证和测试这一段。 制造业、新能源、材料、医药这些行业,研发周期大头不在"设计"而在"验证"。一辆新车从设计到量产,碰撞和耐久测试好几年;一个新材料从配方到量产,小试中试再加老化,每个环节几个月。这些验证慢是因为物理实验有不可压缩的时间成本——得真的造出来、真的跑、真的等它老化。 AI 的核心思路是用预测替代一部分物理实验:代理模型(surrogate model)几秒给出近似结果替代几小时的高保真仿真;数字孪生在虚拟空间跑耐久测试,物理测试只保留关键节点;AI 从历史数据直接预测"这个设计大概率会过还是会挂"。背后的共同模式:AI 不是替代物理实验,而是把物理实验从"全量验证"降级为"关键点确认"。过去造 10 台样机跑 2 年,现在 AI 预判后造 2 台跑 6 个月,剩下 8 台的预算和 1.5 年的时间被省掉。这种砍法,和流水线砍掉装配工时是同一个量级的降本。 三、软件业:冲击最大,也在长出新岗位 软件业被冲击得最直接,因为它本身就是"生成"的密集区——代码、测试用例、文档、设计图都是 AI 降本最狠的领域。初级前端、CRUD 后端、写单测的测试,这些"执行层"工种正在被快速压缩。过去软件业扩张靠"堆人头",现在 AI 让单兵产出翻倍,堆人头的杠杆失灵了。 但我观察到另一个现象:新岗位在长出来,而且不是一一对应。消失了 3 个写 CRUD 的初级,长出来 1 个要求更高的新角色。软件业这轮的代表性新角色是 FDE(Forward Deployed Engineer,前线部署工程师)——一个既懂模型能力、又懂客户业务、还能上手写代码把两者接起来的人。FDE 最早由 Palantir 系统化,现在 OpenAI、Anthropic、Scale AI、Databricks 都在招。因为瓶颈已经从"模型能力"变成了"模型怎么接进具体业务"。模型公司自己做不过来(他们做通用能力),传统 IT 外包也做不过来(他们不懂模型),只能靠 FDE。
