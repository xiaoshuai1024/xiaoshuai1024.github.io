全栈架构 × AI 研发实战

从大厂跳进一片荒芜,我那套工程化当场全废

xiaoshuai1024 included in 工程化
我从前公司带过来一套完整的工程化体系——监控告警、自动化测试、CI 流水线、Code Review 流程,什么都有。跳到初创团队的第一天,打开电脑,什么都没有。 没有监控系统,线上出没出事全靠用户投诉。没有自动化测试,改一行代码心里没底。没有 CI,部署靠手动 mvn package 打个 jar 包再 scp 到服务器。没有敏捷流程,需求口头传达,排期拍脑袋。 更难受的是,团队里没人觉得这些是问题。业务在跑,功能在加,「先把功能做出来」是唯一的优先级。 这种「一片荒芜」的局面,是很多从大厂跳到初创的人都会遇到的情况。难的不是「工程化有哪些东西」——这个大厂都教过你了。难的是:这么多东西都要做,先做哪个?后做哪个?什么能缓一缓? 我自己花了半年,一点一点把这套基建搭起来。现在回头看,如果让我重来一次,我会用一套完全不同的顺序。 结论是:优先级不按重要性排,按投入产出比 + 阻塞解除排 很多人排工程化优先级,默认按「重要性」排:测试最重要(质量是生命)、监控也重要、CI 也重要、敏捷也重要……最后发现什么都重要,什么都想做,半年过去什么都没落地。 我的做法是换一个维度:不看这东西「重不重要」,看它「能多快见效 + 不做它会卡住什么」。 这套顺序的逻辑是:先做投入产出比最高的,再做能放大前面效果的。 监控第一:投入最小(一周搭完),见效最快(立刻能看到线上有没有事)。不做它,你后面做的所有东西都是瞎的——你不知道测试有没有跑、CI 有没有生效、部署有没有出问题。 测试第二:投入中等(一个月搭框架),但它解除的阻塞最大——没有测试,你不敢重构、不敢升级、不敢让新人碰核心代码。 流水线第三:投入较大(两周配 CI/CD),但它把前两步放大——监控的数据靠流水线部署的探针采集,测试的价值靠流水线自动执行才不会变成摆设。 敏捷第四:投入最持续(一直在磨合),但它放大团队协作效率——前面三步是技术基建,敏捷是让团队用起来这些基建的流程保障。 这四块落在一张投入产出比矩阵上,位置是这样的: 下面四节,我按这个顺序,逐个讲每一层我做了什么、为什么这么排、踩过什么坑。 第一层:监控——不是因为重要,是因为一周就能看见效果 荒原里最怕什么 初创项目最可怕的不是「有 bug」,是「不知道有 bug」。 我刚去的时候,有一次用户反馈「页面打不开」。运维去服务器看了一眼,说「CPU 正常啊」。开发去看日志,日志只有 console.log,什么有用信息都没有。最后排查了三个小时,发现是某个接口超时——但没有任何监控告诉我「这个接口超时了」。 这种「靠用户投诉发现问题」的模式,在大厂是不可想象的。大厂的监控体系会主动告诉你「P99 延迟涨了 50ms」,甚至在你之前就告警了。初创团队没有这个,所以问题永远是滞后发现的——等用户受不了来投诉,问题已经发酵了几小时甚至几天。 先搭什么,后搭什么 监控也分层,不能一上来就搞全链路追踪。我的顺序是: 基础设施监控先上(2 天):服务器 CPU、内存、磁盘、网络。用 Prometheus + Node Exporter,或者更轻量的方案(初创团队可以直接用云厂商的监控)。这一步解决「服务器还活着吗」的问题。 应用存活 + 核心接口监控(3 天):健康检查接口、核心业务接口的响应时间和错误率。这一步解决「服务能用吗、好不好用」的问题。 RequestId 链路追踪(1 周):给每个请求打一个 ID,串起网关、服务、数据库的日志,一条 RequestId 贯穿整条后端调用链。这一步解决「出了问题怎么查」的问题。 详细怎么搭,我写过一篇可观测性:RequestId 与监控告警,这里不重复。 我要强调的是为什么这个顺序:从粗到细。先确保「能发现有问题」(基础设施监控),再确保「能定位到哪个服务」(应用监控),最后确保「能查到具体哪次请求」(链路追踪)。反过来做的话,你会在还没搞清楚「服务器活没活」的时候,就去折腾分布式追踪——那是本末倒置。 告警降噪:比加监控更重要的事 监控搭起来之后,最容易犯的错是告警太多。 我刚加完监控那一周,告警群一天响几百次。CPU 超过 80% 告警、某个接口慢了告警、磁盘用了 70% 告警……一周之后,所有人都把告警群设成免打扰。然后某天凌晨服务挂了,没有一个人看到告警。

你的 E2E 只是在点 UI:真实业务多角色闭环测试

xiaoshuai1024 included in 测试
我审过很多项目的 E2E 测试,十有八九长一个样:一个用户登录,点几个按钮,断言页面出现某个文本,通过。这种测试我称之为「单用户点 UI」——它能抓住「页面崩了」「按钮不见了」这类前端问题,但抓不住最危险的一类 bug:跨角色、跨端、跨时间的业务闭环出错。 举个真实的例子。社交模块里,A 给 B 点赞,B 应该收到一条通知。单用户 E2E 永远测不出这个——因为它只有一个用户,A 点赞后没人去查「B 的通知列表有没有多一条」。这种 bug 会静默潜伏,直到用户投诉才暴露。(这篇和测试纪律、覆盖率诚实是一套:那两篇讲「测试要不要写够」,这篇讲「写出来的测试到底有没有抓住真 bug」。) 我定了一套写 E2E 的标准做法,核心是让多个真实角色互操作,把断言落在数据上,跨端用握手衔接。这套 SOP 在我的多租户 SaaS 项目里跑了大半年,抓出过十几条单用户测试根本碰不到的闭环 bug。这篇按标准 SOP 文档的格式写明白。 一、这套 SOP 要解决什么问题 先划清边界——它只解决一类特定问题。 痛点:传统 E2E 测试以「单用户点 UI」为主,抓不住以下三类 bug: 跨角色业务闭环出错(A 操作 → B 应感知,但 B 没感知) 静默后端失败(前端显示成功,后端数据没落库或落错) 跨端数据传递断裂(小程序下单 → 运营后台查不到订单) 这三类 bug 的共性是:UI 层看着全绿,业务事实是错的。单用户、纯 UI 断言的 E2E 对它们完全失明。 这套 SOP 的目标:用「多真实角色 + 数据落库断言 + 跨端握手」组合拳,让 E2E 能抓住业务闭环级的错误,而不只是页面渲染错误。 适用范围:有明确业务角色划分、且角色间存在状态流转的系统。典型如社交(用户互相关注/互动)、电商(买家下单→卖家发货→平台结算)、SaaS(租户管理员→普通成员→平台运营)。 不适用:纯展示型网站、无状态工具类应用。这类没有业务闭环可言,单用户点 UI 就够了,套这套是过度设计。 二、核心原则:三条铁律 整套 SOP 由三条原则支撑,每条都对应一类传统 E2E 的盲区。

备份 ≠ 能恢复:3-2-1 备份 + 每月强制演练

xiaoshuai1024 included in 架构
我见过太多团队对「备份」的理解停留在「mysqldump 定时跑一下」。这种理解会害死人。备份和恢复是两件事,而真正决定数据安全的,是恢复——更准确地说,是你能不能在灾难发生时,确定性地把数据救回来。 (这篇和多租户数据隔离、事故即规范是一组:那两篇讲「怎么不让数据出问题」,这篇讲「万一出了,怎么救得回来」。) 我主导的多租户 SaaS 项目有一次差点翻车:一个清理 OSS 孤儿图片的定时任务,因为差集逻辑写反,批量物理删了一批用户图片。那次之后我定了一条规矩:任何数据资产,都必须有一套可执行的恢复 SOP,而且每月真刀真枪演练一次。这套 SOP 我跑了快一年,这篇按标准运维文档的格式把它拆开。 一、这套 SOP 的目的与边界 目的:保证 MySQL 数据库、OSS 对象存储、秘钥配置这三类核心数据资产,在任何单一故障(磁盘损坏、误删、云厂商区域故障、勒索软件)下,RPO ≤ 5 分钟,RTO ≤ 1 小时。 边界——什么不纳入这套 SOP: Redis:缓存和会话,可从 MySQL 重建,自身有 RDB+AOF 持久化保险 Elasticsearch:业务索引可从 MySQL reindex 重建;AI 向量库重建成本高但属非事务数据 把边界划清楚很重要。什么都想备份等于什么都没备份好——资源有限,精力有限,必须聚焦在「丢了真的会死」的数据上。MySQL(交易数据)、OSS(用户内容)、秘钥(服务能不能启动)这三类是命脉,其它都能从它们重建。 适用场景:单实例或主从架构的中型 SaaS(日均 API 百万级、OSS 日增 GB 级)。如果你已经是多活架构,这套方案是降级的;如果你只是个人项目,这套是过度设计。 二、核心原则:3-2-1 与「演练即门禁」 整套 SOP 立在两条原则上,缺一条就垮。 原则一:3-2-1 备份原则。 这是备份领域的经典铁律,含义是: 3 份副本(生产数据 + 2 份备份) 2 种不同介质(比如本地磁盘 + 对象存储) 1 份异地(不同可用区,最好不同云厂商) 3-2-1 的精神是消除单点:任何一种介质、任何一个机房、任何一家云厂商出问题,都至少还有一份能用的副本。我的项目里,MySQL dump 同时存「异地从库本地磁盘 + 七牛 OSS + 阿里云 OSS」三份,OSS 对象在「七牛主 bucket + 七牛备用 bucket + 阿里云冷备」三处。这就是 3-2-1 的落地。

换一个 AI 助手就重配一遍?一处配置同步五个 IDE

xiaoshuai1024 included in AI编程
我用 AI 编码助手做全栈项目两年,主力是 Claude Code,但同一个项目里 Cursor、OpenCode、Codex、Trae 都会切着用。每个 IDE 都要配 rules、commands、skills,第一年里我反复在做同一件事:改一份 rules,去五个目录同步五遍。 这篇讲的就是怎么把这块最底层地基——配置怎么不重复——解决掉(和命令体系是配套的:那篇讲「有哪些命令」,这篇讲「这些命令怎么在多个 IDE 之间不重复地维护」)。 为什么不能只守着一个 IDE?没有一个 AI 助手在所有任务上都最优。我的体感:Claude Code 做长链路规划(写方案、拆任务)最强,Cursor 改 bug 时定位相关文件最顺手,Codex 适合挂后台跑批量重构,Trae 在某些中文语境下理解更准。任务不同,用的工具就不同。 这种重复不只是烦。它的真正代价是配置会漂移:Cursor 里的命令修了 bug,Trae 里还是旧的;Codex 加了新 skill,Reasonix 不知道。漂移积累到一定程度,AI 的行为就不可预测了——同一个 /kd-review 命令,在 Cursor 里收敛,在 Codex 里死循环。更隐蔽的是,漂移往往是静默的:你以为五个 IDE 行为一致,其实早就不一致了,直到某天在某个 IDE 里踩了坑才发现。 我把这套重复彻底干掉,沉淀成一套 SOP:一个 .agents/ 目录作单一事实源,五个 IDE 用不同策略同步,锁文件保证可复现。这篇按标准 SOP 文档的格式写,你照着能在自己的项目里复现。 一、这套 SOP 要解决什么 它只解决什么问题,得先讲清,避免你套用到不合适的场景。 痛点:一个项目同时用多个 AI 编码助手时,rules(项目规则)、commands(自定义命令)、skills(技能)这三类配置需要在每个 IDE 的约定目录里都存在。手动复制会导致: 配置漂移:改了 A 处忘了改 B 处,行为不一致 版本失控:没有锁文件,换台机器装出来的 skill 集合不一样 心智负担:每次新增命令,要记得「同步到哪些地方」 这套 SOP 的目标是:改一处,全 IDE 生效,且可复现安装。

E2E 最贵的不是写脚本,是让 Agent 替你点完整条旅程

xiaoshuai1024 included in AI编程
一个「下单」按钮点了没反应,可能是前端没绑事件、可能是后端端点 405、可能是小程序和 H5 的 DOM 结构根本不一样。人在这上面耗的时间,远多于写那几行 page.click()。 E2E 测试最贵的不是写脚本,是搞清楚用户旅程到底断在哪一端。 我的做法是把整个流程交给 Agent(和测试纪律、视觉验收是一套,前面讲「分层怎么守、样式怎么验」,这篇讲端到端这一层在 AI 时代怎么写):它拿着一份业务描述,自己分析业务逻辑、自己决定从哪一端进入、自己跨系统点到点地跑完整条旅程,跑挂了自己读日志定位卡点。整个过程的副产物——它点过的每一步——沉淀成 Playwright 脚本,下次回归直接复用。 我的做法是把整个流程交给 Agent:它拿着一份业务描述,自己分析业务逻辑、自己决定从哪一端进入、自己跨系统点到点地跑完整条旅程,跑挂了自己读日志定位卡点。整个过程的副产物——它点过的每一步——沉淀成 Playwright 脚本,下次回归直接复用。 下面拆开讲这套方法怎么落地,以及它和普通 E2E 到底差在哪。 为什么 E2E 这一层最该让 Agent 接手 先把范围说清楚。单元测试盯函数,集成测试盯模块边界,E2E 盯的是用户旅程——一个真实用户从进系统到完成目标的全过程。这件事的天花板不取决于代码能力,取决于对业务的理解深度:你得知道用户会怎么走、会卡在哪、前端后端小程序各自承担了什么角色。 这是 Agent 的强项。它不是来替你写 expect() 的,是来替你做业务逻辑分析的。 具体看普通 E2E 在多端全栈项目里的三个死结: 死结一:旅程横跨多个系统,人很难一眼看穿断点。 一个完整的「下单 → 支付 → 分账」旅程,要经过 H5 前端、运营后台、Spring Boot 后端、微信支付、定时任务分账。任何一环挂了,现象都是「页面上没反应」。人要定位,得翻前端日志、看后端日志、对账数据库、查定时任务执行记录——这是个体力活,但更是个信息整合活,是 Agent 最擅长的事。 死结二:多端的 DOM 结构根本不一样,脚本没法复用。 同一个「商品详情」页,在 H5 里是 <uni-input> 包着 <input>,在小程序里是裸 <input>,在运营后台是 Element Plus 的 el-input。普通 E2E 给每个端写一套定位策略,维护成本翻倍。Agent 不靠固定 selector,它读页面文本和语义来定位,一套业务理解能跨端复用。 死结三:测试脚本和业务理解是两张皮。 普通写法里,业务知识留在 PRD 和人的脑子里,测试脚本只是这些知识的一层「代码投影」。PRD 一改,人要先理解改动、再翻译成脚本改动,中间隔着一层翻译损耗。Agent 主导的做法,是让业务理解本身成为可执行的东西——它读 PRD、读代码、读数据库,直接产出测试动作,翻译这一层被压缩掉了。

让研发长出产品脑:从需求到全自动开发的命令系统

xiaoshuai1024 included in AI编程
团队里有个后端,技术很硬,自己写了个挺酷的功能——一个商家可以批量给商品打标签的工具。代码干净,接口规范,自己测了几遍都很顺。 上线两周,DAU 是 0。 不是功能不好用,是没人需要。商家真正卡住的,是商品太多找不到要改的那一批,不是打标签本身慢。他做的是「让一件不该做的事变快」。 这就是研发做产品最容易栽的地方:技术没问题,价值判断是空的。这个后端不是能力不行,他的工程能力是团队顶尖的。问题出在他思考的起点——他从「我能做什么」出发,而不是从「商家需要什么」出发。技术越强的人,越容易掉进这个坑,因为他总有办法把一个不该做的事做得又快又漂亮。 后来我花了大半年,在这个多租户项目里把一套「让研发长出产品脑」的方法磨出来。核心不是教他们画原型、写文档——那些 AI 都能干。核心是逼他们想清楚三件事:给谁、解决什么问题、值多少钱。这套方法现在固化成了一套命令系统,研发对着命令走一遍,产品逻辑就自然逼出来了。 这条转型路径有个前提我得讲清楚:不是让研发替代 PM,而是让研发具备「产品定义」这一环的能力。在 AI 之前,产品定义是 PM 的专属领地,研发只管接需求;现在一个能闭环的工程师,必须自己能定义产品,否则他永远是个执行者,价值锚在别人手里。我团队现在的状态是:研发能独立把一个需求从模糊逼到可评审的 PRD,然后交给全自动工作流去实现——PM 这个角色,在很多场景下被拆解进了研发的流程里。 研发做产品,最容易犯的 6 个错 先看反面。没接触过产品设计的研发,做产品时会稳定地掉进同样几个坑。我把它们列出来,不是为了吐槽,是因为认清这 6 个错,就等于认清单合格 PM 该补什么。 错一:把功能当价值。 「我做完了」不等于「有人用」。功能是手段,价值是目的。研发容易盯着功能完成度——接口写好了、测试过了、性能也优化了,就觉得这事闭环了。但 PM 盯的是另一件事:这个功能有没有把某个真实问题解决掉。一个完成度 100% 的功能,如果解决的本来就是伪需求,完成度越高,浪费越大。 错二:没有整体观。 研发习惯只看自己这一摊——后端管接口,前端管页面,中间靠文档对接。但产品是端到端的。一个商家批量打标的功能,牵涉选品页的筛选条件、列表页的批量选择、操作后的状态回流、权限校验、操作审计日志。只看自己这一摊的人,做出来的东西一定在某个接缝处漏水——要么前端选完了发现接口不支持批量,要么后端改了数据审计没记。产品是缝出来的,不是拼出来的。 错三:对商业模式不敏感。 一个功能上线,要么帮赚钱(GMV、转化率、客单价),要么帮省钱(自动化、降人工),要么帮留存(复购、活跃)。研发做产品时很少问「这个功能让哪个指标变好」,结果做了一堆「技术上正确但商业上没用」的东西。判断一个功能值不值得做,先问它动的是哪个指标;答不上来,就是不该做。 错四:不理解需求,只接字面意思。 业务方说「我要一个导出按钮」,研发就给一个导出按钮。但业务方真正的意图可能是「月底要给老板看数据,现在手动拼表太累」——他要的是一份能直接交付的报表,不是一个按钮。接需求字面意思,是这个行业最普遍的浪费。多问一句「你拿这个导出来的数据去做什么」,能挡掉一半的伪需求。 错五:从自身出发开发系统。 「我觉得这样好用」是研发的口头禅。但你不是用户。我们的商家很多是四五十岁的店主,在小屏手机上单手操作,网络还可能不稳。你那个「鼠标 hover 才出现的快捷菜单」「需要双击触发的批量模式」对他就是不存在。研发是产品里最不像用户的那个人,却最爱替用户做决定——这是最危险的反向代入。 错六:不验证假设。 上线了不知道对不对,没有埋点,没有指标,没有反馈循环。三个月后回头看,没人用,但已经分不清是「需求错了」还是「实现错了」,因为根本没有数据。没埋点的功能上线,等于没上线——你既证明不了它成功,也证明不了它失败,下次迭代只能继续拍脑袋。 这 6 个错有一个共同根源:研发把产品当技术题,但产品是判断题。技术题有标准答案,判断题没有,得用方法和流程逼出来。 合格 PM 到底在做什么 搞清楚研发错在哪,反过来看合格 PM 该干什么就清楚了。 很多人(包括很多 PM)对 PM 的误解是:画原型、写文档、开评审会。这些都是表象,而且是 AI 最能替代的那部分。 PM 真正在做的,是三件事: 动作 具体含义 研发最容易缺的 定义价值 想清楚「给谁、解决什么问题、值多少钱」 给谁(用户画像模糊)、值多少钱(不连商业指标) 设计验证 怎么知道这个功能做对了(指标、AC、反馈循环) 没有验收标准,只有「能跑」 收敛范围 明确「不做什么」比「做什么」更难 全都要,结果什么都做不深 这三件事里,收敛范围是研发最难学的一件。研发的天性是「能做就做」,需求来了恨不得全实现,显得自己能力强。但好 PM 的标志相反——他砍需求砍得狠。一个功能要不要做,判断标准不是「能不能做」,是「不做会不会死」。不会死的,大概率是伪需求,砍掉省下的精力用来把真正重要的做深。
