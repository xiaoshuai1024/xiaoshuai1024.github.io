1024 工程笔记

全栈架构 × AI 研发实战

那就和前端、后端好好道个别吧

xiaoshuai1024 included in 职业思考  AI 开发
这两年，「前端已死」的论调隔几个月就刷一波。但这话没说到点子上，该告别的不是前端，是「我只做一端」这个身份本身。 Claude Code、Codex 这些工具，能把一个页面、一个接口、一段 SQL 直接生成出来，前后端的边界正在被抹平。纯前端、纯后端这两个身份，正在同时失效。能活下来的研发，底线是全栈：一个人把想法从界面跑到数据库再跑到部署。比全栈更要紧的，是持续学习的能力。这套工具栈半年一换，今天熟的框架，明年可能就被模型生成替代，停下来就会被甩下。 一、AI 对前后端的冲击，正从不对称走向收敛 为什么是「前后端一起告别」，而不是只有前端？ 最早被冲击的确实是前端。UI 是最容易被 AI 直出的东西，给它一条指令，React 组件、样式、交互就出来了，前端「画界面」那部分最先被压扁。 但后半句很少有人说：后端正被快速追上。我现在让 Claude Code 写一个 Spring Boot 接口、配好 JPA、连上 MySQL、写迁移脚本、再补 JUnit 测试，它干得比我带过的大多数实习生快。SQL、Dockerfile、部署脚本，同样一个指令的事。 一年前我还敢说，后端的复杂度（事务、并发、状态机）AI 撑不起来。现在不敢了。它写出来的事务边界和并发处理，大部分时候是对的，错的地方它还能照着我给的测试自己改。前端中招早，只是因为 UI 更直观、训练样本更多；后端正以同样的曲线被追上。 前后端被冲击的时间差，正在被抹平。死守「我只做前端」或「我只做后端」，等于守一段两端都在塌的墙。 二、价值不在单点，在能把整条通路串起来 这是个简单的经济学问题。 AI 把「写一个组件」「写一个接口」的成本压到接近零，单点技能的溢价就消失了。一个只会切页面的前端、一个只会写 CRUD 的后端，可替代性变得极高。替代他们的不是另一个更便宜的人，是一个不要钱的模型。 零成本的单点，撑不起一份工资；能把零成本的单点串成可用产品的人，才撑得起。 价值挪到了另一头：能把整条通路串起来的人。从用户点一下按钮，到前端响应，到接口，到业务逻辑，到数据库，到部署和监控，谁能在每个节点都用 AI 当杠杆产出，又在关键节点留得住判断力，谁就端走了大部分价值。 举个具体的：同样是做个内部工具，只会前端的人要等后端给接口、等运维给环境，卡在排期里出不去；能把通路走通的人，一个下午用 AI 把界面、接口、数据库、部署都生成出来，自己跑通、自己上线。前者是流水线上的一道工序，随时能换；后者是能直接交付一个产品的人，议价权在自己手里。市场给这两者的定价，差着一个数量级。 全栈这个词，得重新定义。AI 之前，全栈是个高门槛的褒义词，因为一个人手动精通两端太难。现在门槛换了。全栈的意思是：端到端能负责，AI 当杠杆，关键处有深度。 三、组织和人，都在往这个方向滑 不是只有我一个人这么感觉。 身边不少前端的轨迹，这两年都在变：纯前端 → 被逼全栈 → 转去做 Agent 或 AI 应用，越来越多的代码让模型写。他们没失业，是被推着进化了。我自己也在这条线上，博客里一路从前端写到全栈，再写到 AI 开发，不是年初规划出来的，是被一次次需求推出来的。前端做着做着要碰接口，接口做着做着要碰部署，部署做着做着开始用 AI 批量生成，回头一看，已经回不去「只做一端」了。 组织层面的信号更硬，而且不止一家。美团 CLC 食杂零售 Keemart 研发团队已经把前端和后端团队正式合并；InfoQ 的判断是，字节、阿里都在推进同样的整合，AI Coding 把跨栈门槛压下去之后，「前后端一起消失」正在从口号变成组织动作。阿里支付宝体验技术部被拆进各个业务部门，独立的前端部门在消解，工程师按业务目标负责，不再按「切图」负责。 合并还在往上下游蔓延。字节 Data 部门已经灰度内测 QA 转研发序列，要求测试掌握 AI Coding，不再做纯测试；测试左移、研发自测、自动化覆盖率进考核，已经是大厂标配。独立测试团队的边界，正在和研发合到一起。

RAG 召回率上不去,先别怪 embedding 模型

xiaoshuai1024 included in AI编程
RAG 答不准,大部分人的第一反应是换 embedding 模型。换完还是不准,再调阈值,再换更大的模型——循环两轮,准确率原地踏步。 这不奇怪。文档要被检索命中,得先走完四步:切片 → 向量化 → 匹配 → 分级。切片把文档拆成语义单元,向量化把语义表达成数值,匹配把 query 和文档对起来,分级决定这些结果怎么用。四步各管一段,任何一步做错,后面的步骤都救不回来。 这篇把「怎么把四步分别做对」讲透。线上做过的讲做法,还没做的(混合检索、重排)讲原理和决策,不装作上线过。 结论先放这:召回率上不去的瓶颈,通常不在模型,在切片边界和检索结构。 一、先对现象:换了模型,准确率纹丝不动 运营文档问答,基准集准确率早期在 60% 上下。我们调了两周提到 85%,贡献最大的两件事都跟模型无关: 切片从"照搬英文 500 token"改成"中文 400 字 + overlap 100 字"。 检索从"只调 topK 和阈值"改成"四步链路分别做对"。 embedding 模型最后才换了一次,换完的收益远小于前两件事。这背后是个反直觉的事实:embedding 模型对中文的理解差异能带来约 20% 的准确率差,但切片切碎了,模型再好也拼不回被切成两半的信息。 顺着这条线,把四步逐段拆开。 二、切片:让每个 chunk 是一个完整语义单元 为什么必须切片 大模型上下文有限,不能整篇塞。但更关键的是检索的粒度问题:query 往往只有一句,文档却有几百句。整篇文档只对应一个向量,这个向量是几百个句子压缩出来的"平均脸",每个句子的特征都被稀释了,query 和它算相似度,没有哪个单句能"冒尖"。切片把文档拆成多个语义单元的向量,query 才有机会打准某一句具体的话。 token 切片和中文的坑 切片的做法是按 token 滑窗,贴着自然边界走。我们用的 Spring AI TokenTextSplitter: new TokenTextSplitter(500, 50, 50, 100, true) // chunkSize=500, overlap=50, keepSeparator=true(保留段落分隔符)keepSeparator: true 让切片尽量贴着段落走,而不是纯按 token 硬切。这是初步的结构感知,它在标点和段落附近找切点,代价最小。 中文切片的第一坑:不能照搬英文的 token 数。英文一个 token 约 0.

OpenSpec 和 Superpowers 别二选一,它们管的是两件事

xiaoshuai1024 included in AI编程
OpenSpec 装上了，Superpowers 也装上了，项目照样乱。 打开项目目录，openspec/changes/ 和 docs/superpowers/plans/ 两个目录都在，真要让 AI 动手，它还是直接改、改完不归档，下次那批约定又得从头再来。你手上两套工具，等于两套都只装了没跑。 还有一种更隐蔽的误区：以为两套都装上了，就是「规格化开发」了。结果只是多出一堆没人读的文档，AI 的产出还是无规格、无计划的状态。 问题不在工具，在于没搞清这两套东西管的是两件不同的事。这两套是唯一同时放进我日常流程的规格化工作流，反复迭代的视频管线、公众号发布、站内搜索都是它们管出来的。核心分工是：OpenSpec 管「一次变更的规格」，Superpowers 管「一个项目的计划」。 粒度不同、产物不同、驱动方式不同，配起来才完整。 为什么一个规格工具不够 先看 OpenSpec 解决什么。它把一次变更固化成 change，放进仓库的 openspec/changes/<名字>/，里面是四件套：proposal.md（为什么改、改什么、影响什么）、specs/<能力>/spec.md（系统必须做什么，增量规格）、design.md（怎么做、权衡了什么）、tasks.md（按什么顺序做）。六个 skill 组成流水线：explore 想清楚 → propose 生成四件套 → apply 照 tasks 施工 → sync 预览合并效果 → update 回炉修订 → archive 归档并合并进主规格。 这套东西管到的最小单位是一次变更。它把「加个缓存」「加个封面自动上传」这种改动定义得清清楚楚，AI 照着 spec 施工，改完归档，能力攒进主规格。我在 /posts/ai-dev-openspec-spec-driven/ 里用一条加缓存的改动把六个 skill 走了个遍，这里不重复。 但一整个项目目标不是 change 的粒度。「把公众号自动发布做出来」这个目标，涉及账号对接、定时发送、封面上传、失败重试、群发通知，拆开是几十个变更。OpenSpec 能把每一个变更定义明白，却管不了这几十个怎么排、阶段怎么分、跨变更的依赖是什么、整个目标收敛没有。那不是变更规格层的事。 再看 Superpowers 管什么。仓库里 docs/superpowers/plans/ 下每个 plan 长这样：Goal（定目标）、Architecture、Tech Stack、Spec 引用、文件结构表、checkbox 任务清单。由 superpowers:subagent-driven-development 按计划逐条执行，勾完一个推进一个。它管到的最小单位是一个项目的落地：目标怎么拆、任务怎么排、进度怎么跟踪。 但 plan 不承担变更规格。plan 里写「做站内搜索」，不会细到每个接口的验收场景。这些细节天然该落在变更规格层，而不是塞进项目计划。 两套粒度不同，一个管项目计划（大），一个管变更规格（小）。只用任一个，就有一层没人管：只上 OpenSpec，项目级的目标没人拆解跟踪；只上 Superpowers，变更级的行为没人定义验收。这不是二选一，是缺一半。

Claude Code 又被封号？CcSwitch 切国产模型，省 99%

xiaoshuai1024 included in AI编程
做 AI 开发，主力客户端我用 Claude Code。Skills、MCP、subagents 这套框架能力，目前没有对手。但官方账号绕不开一个问题：我的号就封过。 Anthropic 不向中国地区提供服务，注册只能借其他地区的通道。中国地区封号极频繁，Claude Code 源码里直接写了地区判断，识别到国内环境就视为违规。个人号如此，团队共享 key 风险更大。被封那天，我一点都不慌。 后来我换了一条路。Claude Code 客户端本身是开源的，模型供应商可以换。用 CcSwitch 把 DeepSeek、Qwen、Kimi、GLM 这些国产模型接进同一个客户端。封号之后，我全量切到国产模型，切一次就不回官方。 读完后你能做到：一套 Claude Code 客户端全量跑国产模型；月账单从官方 $100+ 掉到几美元；账号也不再随时面临封号风险。 Claude Code 强在哪，官方号为什么容易封 为什么离不开 Claude Code，答案在框架层。它和「填提示词的工具」是两代产品，差别在下面四样能力： Skills：把常用工作流封装成可复用的技能，一个命令执行整套流程 MCP：接任意外部工具，数据库、浏览器、设计稿都能连 subagents：按角色派多个子代理并行干活，主会话只做收敛 多会话编排：一个任务拆成多个会话并行跑，最后合流 这套能力属于客户端的框架层，不是某个大模型的独有能力。模型是发动机，客户端是底盘。底盘好用，换个发动机照样开。 问题出在根本上：Anthropic 根本不向中国地区提供服务。想用官方号，只能借非中国地区的通道注册。 账号一回到中国地区网络，封号就成了高频事件，源码里就有地区判断，识别到国内环境就视为违规。封号和你的使用模式无关，是你所在的地区本身就不在服务范围内。对重度用户来说，这等于脖子上一直悬着一把刀。 适用人群与前提 这篇文章适合两类人： 重度用 Claude Code / Codex，但官方号被风控或快被风控的人 想用 Codex 但接不上官方模型、想换国产模型的人 前提不多，三样东西： 已装 Claude Code 或 Codex CLI 一个国产模型平台的 API key（DeepSeek / Qwen / Kimi / GLM 任选） 一个桌面小工具，macOS 或 Windows 都行 版本我用的：Claude Code 最新稳定版、CcSwitch v3.
