Claude CodeCodexAgent源码分析MCPSkill

Claude Code 与 Codex 的权限门控源码对比：hooks 改写决策和沙箱硬隔离

xiaoshuai1024 included in AI 开发
有一天我翻 Claude Code 的混淆代码翻到一段名单，愣了一下：["mkdir","touch","rm","rmdir","mv","cp"]——在 acceptEdits 模式下，这六个命令是免审直通的（L378700 到 L378740，decisionReason 标注 type: "mode", mode: "acceptEdits"）。我一直以为这个模式只是「少点几次确认」，边界比我想的宽：它放行的不只是编辑，还有一组文件系统命令，其中 rm 和 mv 都在。这个发现让我把两边的权限门控源码完整读了一遍，这篇就是结论。 系列第五篇。前四篇见架构分层、主循环、subagent、上下文管理。版本锚定不变。权限和前四篇的性质不太一样：主循环、压缩、subagent 出问题损失的是效率和 token，权限出问题损失的是数据和信任——它是这个系列里唯一「错了难以回滚」的议题，所以这篇的每个使用建议我都写得比前面几篇更保守。 一、Claude Code：模式加 hooks 的双轨 Claude Code 的权限决策有两条轨：模式轨决定默认行为，hooks 轨允许运行时改写。 模式轨是四个字符串常量（L378725 等处确证）：default（逐次询问）、acceptEdits（编辑类放行）、bypassPermissions（全放行，dangerouslySkipPermissions 开关就是往这切，L364292）、plan（只读规划）。模式之外还有规则语法：allowedTools 列表支持带参数的规则（L416466 的快照示例 Read(~/**)、Edit(~/.claude/settings.json)），粒度到「工具加路径模式」。 这套规则语法的表达力是 Claude Code 权限体系里最精细的部分。一条规则三要素：工具名、参数模式、来源（allow / ask）。Read(~/**) 放行家目录下所有读取，Edit(docs/**) 放行文档目录的编辑，Bash(npm run *) 覆盖一类命令。实践里我建议「窄开正门」：把信任的高频操作逐条开白（读、文档编辑、固定的几个构建命令），而不是用宽模式开侧门——正门越具体，异常越显眼。规则配好后 default 模式能覆盖九成日常，弹出来的询问本身就是异常信号，而不是噪音。 整体看，这套体系的取向是把权限决策变成可声明的配置：四模式是预设档位，allowedTools 是档位上的精调，hooks 是配置之外的编程出口——三层从粗到细，分别覆盖「大多数人」「讲究的人」「有组织策略的人」。个人用户停在前两层就够，团队要走到第三层。 四个模式里最没存在感的 plan 值得替它说句话。只读规划模式下 agent 不能改任何东西，产出的是计划而不是代码——听起来是残血模式，实际上是高风险任务的前置关卡：先让 agent 在 plan 模式下出完整方案，人审方案（审「它打算干什么」比审「它干了什么」便宜一个数量级），认可后切回执行模式。我的夜间批处理任务全部走这个流程，方案错杀在纸面，执行阶段的审批量也小了——方案已经把要做的事说清，异常操作反而更醒目。Codex 有对应的 plan.rs handler，机制是现成的，用不用在习惯。 开头那六个命令的白名单就是模式轨的实现细节。设计逻辑说得通：acceptEdits 的语义是「我信任它改文件」，而 rm/mv/cp 在 agent 的日常工作流里和编辑文件是一回事——模型改完代码清理临时文件、挪个构建产物，如果每次都要人点确认，这个模式就失去意义了。但风险同样真实：一次错误的 rm -rf 在这个模式下没有人拦。

Claude CodeCodexAgent源码分析安全

Claude Code 与 Codex 的上下文管理源码对比：先清工具输出还是先做摘要

xiaoshuai1024 included in AI 开发
有一次长会话压缩之后，我让 Claude Code 继续改一个之前读过的文件，它把文件重新读了一遍。当时我以为是它忘了，读完源码才明白：压缩的时候对话原文一个字没动，被清掉的是旧的工具输出——那个文件的完整内容是作为 Read 的 tool_result 存在的，microcompact 把它替换成了 [Old tool result content cleared]。所以它记得需求（对话还在），丢了文件细节（工具输出没了），只能重读。这不是 bug，是精确设计的取舍。 这是系列第四篇。前四篇见架构分层、主循环、subagent 调度。版本锚定不变：Claude Code v1.0.88，Codex commit 63b268c81b。 上下文是这个系列里离每个用户最近的议题——不管你用什么姿势用 Agent，压缩都在你背后发生。这篇的目标是把那件「背景里的事」拉到前台：触发线在哪、清什么留什么、压缩后你的会话变成了什么样、哪些损耗可以靠使用习惯找回来。开头的「记得需求丢了细节」，读完你会知道它精确发生在哪一行、为什么被设计成这样、以及怎么和它相处。 一、Claude Code 的两级压缩 Claude Code 的上下文管理是两级火箭，都在主循环入口处检查（L416898 到 L416912：先 Kv 做 microcompact，再 hRB 做 auto-compact）。 第一级 microcompact：便宜、激进、只动工具输出。实现逻辑是把旧的 tool_result 内容替换成占位符，原文在 v1.0.88 里是明文的 [Old tool result content cleared]（L394465 一带）。配套的埋点 tengu_microcompact 携带的字段能说明它清理了什么：toolsCompacted（清了几个工具的结果）、totalUncompactedTokens、tokensSaved、triggerType（manual 还是 auto）。 为什么先动工具输出？看一眼长会话的构成就有答案：一轮「读三个文件改一处」的交互里，对话文本可能只有两百 token，三个文件的完整内容加上 diff 输出能到几万。长会话的体积大头永远是工具输出，清它性价比最高。而且工具输出有「时效性」——早期读的文件大概率已经改过了，留着旧内容反而误导模型。 第二级 auto-compact：贵、彻底、做全文摘要。microcompact 救不回来时触发，走一次独立的摘要请求，prompt 原文在 L392454 / L392550（「Your task is to create a detailed summary of the conversation so far…」两个变体），摘要完成后用续接 prompt 重新开场（L392681：「This session is being continued from a previous conversation that ran out of context…」）。摘要请求有独立的流式配置（promptCategory: "compact"），失败时打点 tengu_compact_failed，reason 是 no_summary——摘要没生成出来就继续用旧上下文硬撑。

我每天在用的 Claude Code，上个月被我拆开看了一眼，结果发现一个没人告诉我的事实：npm 包里的 cli.js 早就没了。2026-08-18 我升级到 2.1.229 后解开安装目录，里面只剩一个 307MB 的 claude.exe——你天天在用的这个「Node 脚本」，现在是一块编译好的原生二进制，JS 源码被整个焊死在可执行文件里。 这个发现还只是开胃菜。往下读我陆续撞见一串反常识的东西：Claude Code 的 subagent 根本不开新进程，只是同一个函数的递归调用；它并行执行工具的上限是写死的 10，就藏在 L416878 一个不起眼的变量里；而 Codex 那边，agent 的父子关系居然有专门的数据库存着，重启都能把整棵 agent 树恢复回来。这些事用一年也感受不到，翻开源码十分钟就能确认。 于是我决定把两边的源码完整读一遍，这个系列就是这个决定的产物。不是出于收藏癖——是我发现自己对这两个工具的所有判断都来自体感，而体感经常是错的。我一直以为两者的差距主要在模型，读完才知道，调度层面的工程路线差异比模型差异大得多。 先交代本文范围：讲架构分层和发布物形态，是系列的地基。Claude Code 侧的分析锚定 v1.0.88（2025 年中，npm 包里还是纯 cli.js，展开后约 43 万行），2.x 的演进用官方发布物和本机行为验证补充；Codex 侧锚定 2026-08-18 的最新代码（commit 63b268c81b）。所有行号和文件路径都来自这两个版本，后续版本可能对不上。 一、先说清楚：闭源的东西怎么读 Claude Code 闭源，但它的发布物是可分析的。v1.0.88 的 cli.js 是一个 esbuild 风格的单文件 bundle：混淆了函数名和变量名，但字符串常量不混淆。工具名 "Task"、hook 事件名 "PreToolUse"、压缩标记 "[Old tool result content cleared]"，这些都是明文。 我的做法是先用 prettier 把 9MB 压缩文件展开成 43 万行可读格式，然后拿字符串当锚点 grep 行号，顺着调用关系往外扩。这个方法不新鲜，社区里 Dingjz 的 v1.
