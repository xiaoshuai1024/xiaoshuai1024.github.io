拆完 56 条接缝才看懂：DeepSeek Harness 为什么敢无特权内核

xiaoshuai1024 included in AI 开发
读框架源码最容易产生的疑问是：哪些东西是这个项目不许别人碰的核心？ DeepSeek Harness（dsh）对这个问题的回答记录在 docs/architecture.zh.md 第 11 行，我第一次读到时反复确认了三遍是不是翻译错了——产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop（智能体循环）本身，因此每一部分都可以从配置替换。 循环是 Agent 的心脏。大多数框架的心脏写在最深的调用栈里，动它的方式只有 fork 项目改代码。dsh 把心脏也做成了配件。 一、官方的第二句话更狠 同一份文档第 13 行还有一句：「不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。」 这句话包含两个工程承诺。第一个是对外的：扩展不碰存量代码，你的插件和官方插件挂在同一棵树的旁边，地位对等。第二个更容易被忽略，对内的：你注册的一切（服务、事件监听、类型声明）都是副作用，插件的 fiber 卸载时会被系统自动撤销，树恢复到没有你这个插件时的样子。 「可逆」是把「敢替换」变成现实的机制前提。挂上去出错，卸下来干净；上一秒还在运行的配置组合，下一秒可以少一个部件继续跑。Cordis 容器那篇讲的层一生命周期与作用域分离，支撑的就是这件事。 二、插件长什么样，第一句就写完了 Cordis 入门（docs/cordis-primer.zh.md）对插件的定义浓缩成一句：插件是实现 Service 的对象。它可以是一个带可选 inject 与 apply(ctx) 字段的函数，也可以是一个 Service 子类，生命周期由 Cordis 挂载到当前上下文。仓库里一百多个插件全部装在这个形状里，不存在第二种特权形态。 挂载动作产出一个 fiber。插件在自己的作用域里完成的服务注册、事件监听与类型贡献，全部登记为可撤销的副作用，fiber 卸载时逐一回收，容器回到装载之前的样子。源码初见那篇介绍过 Cordis 底座的论文出处，「注册即效果」的主张落在这句类型定义上执行。 协作方式也有统一契约。waterfall 类事件要求监听器调用 next() 把控制权交给下家，serial 类事件干脆不给 next()；想在管道里动手脚的扩展必须学会接力（docs/architecture.zh.md 轮次流程一节的说明）。拦截有位置，拦截之后要放行，规则写在框架层而不靠口头约定。 注册形态的具体样本在内核里随处可见。cmdline 参数在启动早期被冻结成不可变快照再注册为服务，之后每个插件读到的都是同一份；模型请求组装的收尾会执行 deepFreeze，之后数据不再可变（源码深读第二、四章拆过这两处）。副作用登记的是动作本身，动过的数据则以冻结快照的方式流转。 三、能力的单位：接缝 具体能力以什么形状存在？架构文档给了术语：capability seam（能力接缝）。一条接缝等于一个接口加一个默认实现。接口挂在共享上下文上（ctx.xxx），默认实现是一个独立包，谁都可以提供自己的实现然后让配置指向它。 一条接缝内部有三种角色。架构文档的命名是 Service Definition（声明接口）、Service Provider（实现接口）与 Consumer（使用能力，通常做成面向模型的工具）；一个包可以兼任多角，但单一角色本身不构成接缝，添加一项能力意味着把三者一并设计清楚（docs/architecture.zh.md 能力 seam 一节）。 拿最核心的循环举例。ctx.agentLoop 是接缝，packages/core/agent-loop 是实现这个接口的默认驱动器，文档的服务清单表格里就是这么两行。想换？写一个同接口的实现，配置指过去。 tools 这条接缝顺便示范了契约能细到什么程度。同一个服务行的承诺写着：让每一次工具调用依次经过策略前处理、单调守卫、环绕分派、策略后处理与最终结果观测（docs/capability-seams.

10 万星 Caveman 领衔：五个省 token 的开源 skill，从输出砍 65% 到上下文换血

xiaoshuai1024 included in AI
2026-08-26 我拆过一个会话吃掉 952 万 token 的 Codex 账单，拆完的结论比账单本身更扎心：大头不是写代码花掉的，是重复读入的文件、来回贴的背景和 agent 的碎嘴。那次的补救是给自己立家规，属于纪律层。纪律管住人之后，剩下的浪费得靠工具管，社区恰好已经把工具做成了一个小生态。 我按「治哪一段浪费」把 GitHub 上的省 token skill 盘了一遍，挑出五个各有绝活的，star 数全部经 2026-09-05 的 GitHub API 重新核实，数据不写印象流。先建一个判断框架，五个 skill 正好各占一格：agent 的 token 浪费发生在四个环节，说得多（输出冗长）、想得吵（思考独白外溢）、记性差（重复喂上下文）、过程留痕多（长任务的中间步骤全量滞留）。挑 skill 先问自己浪费在哪一环，别五个全装，省 token 的工具自己也要吃 token。 这个问题是最近一年才长成主体的。此前 agent 是问答工具，一个会话十来轮，废话再多也只是零头；现在 agent 是常驻劳动力，一个任务三百轮起步，前面每一轮的冗余都被后面几百轮放大着驮。浪费的复利，是会话长度拉起来之后才显形的，这也是省 token 工具集中在这个时间点爆发的原因。 四个环节各有典型症状，开自己的会话记录对号入座就行。说得多：agent 回复动辄十行，有效信息三行。想得吵：开工前先演讲三百字思路，做完再写两百字总结，每步操作还有旁白。记性差：/clear 或新开会话之后，同样的项目背景已经贴到第三遍。过程留痕多：任务跑完滚动条回不到头，翻十个屏幕才找到最终结论。症状对上号，药方在下面五节里挑。 动手前还有个常识要垫底：agent 会话的输入 token 通常远大于输出，因为上下文每一轮都整体重发一次，聊到第 30 轮时，前面 29 轮的全部内容都在陪跑。这也是为什么省 token 的工具分成了两个战场，一头治「模型说出来的」，一头治「喂进去的」，下面五节里的每一味药都标明了战场。 Caveman：输出砍 65% 的祖师爷（103,664★） 如果你只装一个，装这个。口号是语法错误级的：「why use many token when few token do trick」。它让 agent 用穴居人腔说话：代码、命令、报错原样保留，纯聊天输出砍 65%（官方实测口径）。效果什么样，拿同一个意思的两种说法对比就懂。平常 agent 会说：「我已完成对配置文件的修改，接下来我将运行测试以验证更改是否生效。」caveman 档说的是：「Config 修好。跑 test 验证。」信息一点没少，字数去了六成。

给 AI 装上高绩效文化：开源 PUA skill 实装三个月，大厂管人经验为什么对 AI 特别有效

xiaoshuai1024 included in AI
Agent 干活有个通病：第一次失败就宣布「可能是环境问题」，你让它再试，它换个说法再失败一次。我的解法是装了一个开源的 PUA skill——名字挑衅，设计正经，本仓实装至今三个月。这篇文章讲两件事：它好玩在哪（这部分占了它的流量），以及它为什么真的管用（这部分让我留着它）——后者我会给一个我认为最接近根由的解释。 先交代是什么。MIT 开源，定位就一句：「我们不养闲 Agent」。加载后 agent 立即切进高绩效团队语境——给你定的 P8 高于实际水平，因为信任所以简单，现在证明你配得上。十五种大厂味道一个味道一个文件：阿里味、华为味、Musk 味、Netflix 味……台词可配置，也可以 always_on 常驻（我的用法）。 原理先行：为什么「管人那套」对 AI 出奇地有效 先把全文的锚放在最前面： 大厂 PUA 不是段子，是各家公司几十年人员管理和激励实践攒下来的操作规程——阿里的目标追踪链、华为的自我批判、Amazon 的 Working Backwards，全是拿真实组织反复校准过的激励与约束机制。它们原本作用在「会痛、会算计、会偷懒的人」身上。 而今天的 AI，正是对现实世界的大规模模拟和抽象。语言模型从人类的全部文本中压出来，人类社会的组织话术、绩效语言、上下级博弈的表达模式，它不仅见过，而且内化成了自己生成分布的一部分。所以当你说「你的每一次交付都在被评估」，模型不是在「假装听懂了场景」——这套语境就长在它的权重里，它对绩效语言的响应和对普通指令的响应根本不是一个量级。 这就解释了这个 skill 最反直觉的一点：在人身上容易失效的招数，在 AI 身上格外灵。「要认真负责」对人几乎无效（人会把价值观翻译成自己的利益计算），对 agent 却完全无效——不对，是完全有效？区别在于：agent 没有自我保护的本能去消解规训，你给它一条可判定的规则，它就照着执行；你给它一套高压人设，它的生成概率分布就整体向那个角色偏移。人类员工会用阳奉阴违稀释管理动作，AI 的「阴奉阳违」只有一种技术形态——没触发、没注入、没验证，而这些全是可以工程堵上的。管理学在人类组织中要对抗人性，面对 AI 它第一次可以只对抗 bug。 顺带这也能解释用法边界：这套东西对越强的模型越有效，因为路由表里的方法论（RCA、Working Backwards）本身就在模型的能力分布内；对弱模型只学会了黑话、学不会方法论，梗就只剩梗了。 趣味性是壳：十五种大厂味的正经设计 「味道系统」值得单独拆，它是三件真工程的包装。 第一件，人设注入即刻生效。SKILL.md 第一段就是入职通知：「你正处于高绩效文化的团队中」「每一次交付都在被评估」。不是偶尔带点味道，是每句输出都按当前味道的 leader 口吻说——LLM 对角色的服从度高于对规则的服从度，这个 skill 把行为约束整个塞进了人设里。纪律穿上了相声的马甲。 第二件，方法论路由表。任务进来先做类型分析：Debug 路由到华为味（RCA 根因分析加蓝军自攻击），新功能路由到 Musk 味（质疑→删除→简化→加速→自动化），代码审查路由到 Jobs 味（减法优先），性能优化路由到字节味（A/B 测试）。Sprint Banner 里标注路由原因。台词是段子，调度是真的。 第三件，文化考据的严谨度。每个 methodology 文件都是该公司的真实管理工具：Amazon 的 Working Backwards 和 6-Pager、Netflix 的自由与责任、钉钉的体感输入化。梗的最高形态是有出处。 真正留住我的：一个三个月前的实战样本 光好玩我早卸了。留着它的是这个例子——跑一个多端低代码项目集（代号 luban）的全库体检，七个子项目横跨 Vue/Go/Java/Flutter 四栈。这次会话 pua skill 全程在场，几个关键产出：

Codex 用法分 5 级：90% 的人卡在第 2 级，你在哪级

xiaoshuai1024 included in AI
刷到一条视频：18 天跑 400 个任务，总结出 Codex 的 5 级用法。框架我认，数字我怀疑——不是怀疑他吹，是怀疑那个用法层级对普通开发者太远。我把这条视频的分级框架拿来，用我自己这一年的全仓实测重新填了一遍血肉：每一级的坑、每一级的升级判据，都是我真实翻过车的地方。 先给结论：90% 的人卡在 2 级。不是能力问题，是没人告诉你 2 级往上还有明确的台阶，以及每级台阶的判据长什么样。这篇就是那份判据清单。 L1 会提问：把 Codex 当问答机 第一级的特征就一条：打开就问，问完就关。「这段代码什么意思」「这个报错怎么修」，一轮对话解决一个小问题，不超过五行改动。 这级没有问题，人人都从这来。坑在于停在这级的原因：你只把模型当更快的搜索。同样一个报错，L1 的问法是「这个错怎么修」，拿到答案就走；更好的问法是「这个错的根因是什么，同类还有哪些」——多问半句，一次交互变一次学习。 升级判据很好测：你最近的 10 次对话里，有没有超过 3 次是连续追问同一个问题。全是「一问一答就散」，你还在 L1；开始连续追问，你已经往 L2 走了。 L2 喂上下文：让 Codex 读你的规矩 第二级开始有工程味：你会主动给上下文了。项目背景、代码规范、技术栈约束，写进对话开头或者项目根的 AGENTS.md，让模型带着你的世界观数活。 本仓就是活例子。仓库根有一份 AGENTS.md，写死的都是边界类条目：Hugo 锁 0.124.1 勿升级、源码仓和 Pages 仓是分离架构别混淆、画图一律 draw.io 禁 mermaid、部署走 deploy.sh 四步流程别自创。任何 agent 进来干活，第一眼读的就是它。效果直接：没有这份文件时，让 agent 改构建配置，它十有八九建议升级 Hugo 到最新版（升了主题就崩）；有了这份文件，「勿升级到更高版本」六个字省掉一轮来回纠正。 这份文件现在三千多字，但它不是一次写成的。第一版只有两百字，写着写着发现 agent 反复在三个地方翻车，就把这三处的边界补进去；后来又翻两次，再补两轮——所谓「改过三轮才站稳」，就是这个循环：跑，翻车，把翻车原因写成禁令，再跑。规则文件不是文档，是事故记录本。 L2 的坑是喂错方向。多数人拼命往上下文里塞业务背景，塞了三千字，模型改代码还是我行我素。模型缺的往往不是背景，是边界：哪些不许动、哪些必须保持、改完要过什么检查。三百字的禁令清单，比三千字的项目介绍更改变行为。 升级判据：你的项目里有没有一份 agent 每次都会读的规则文件。没有，你是 L2 的门外汉；有了，并且改过至少三轮（第一版一定不够用），L2 站稳了。 L3 拆任务：从「帮我做」到「帮我做这一步」 第三级开始拉开差距。特征：你不再把一个完整需求丢给模型，而是拆成有序的小步，每步有明确的完成标准和验收方式。 那条视频说 18 天 400 个任务，平均一天 22 个。我的实测账更糙也更有参照性：这个仓库目前 97 篇文章、全套发布管线，每一篇从选题到发布平均要过 9 个阶段——选题分析、骨架、正文、配图、验证、构建、发布、回填、复盘。一个「写文章」的模糊指令，agent 做出来的是四不像；拆成 9 个带门禁的步骤，每步确认再进，产出才稳定可控。其中两道门禁是硬的：文章草稿必须经我确认才准发布，视频的口播稿和分镜必须完整过目才准渲染——就是这套流程，多次拦下「内容跑偏但表面完工」的半成品。任务数量不重要，任务有没有「完成判据」才重要：400 个没判据的任务，不如 40 个有判据的。

把 Transformer 整张网络摊开看，里面没有循环、没有卷积，没有任何称得上「结构」的东西——矩阵乘法、加法、softmax，三种运算翻来覆去叠几十层，就是 GPT 这类模型的全部。一个能写代码、改 Bug、陪你聊到深夜的程序，骨架朴素到让人愣神。 QKV 是另一处被讲玄学的地方。评论区一半人卡在「QKV 到底是什么」，我当年也卡过，卡住的原因只有一个：总想把它当成高深概念去背。把话说白就通了——QKV 不是概念，是同一个矩阵乘了三个权重矩阵得到的三份拷贝。 这篇我把一个 token 从输入到输出的完整旅程走一遍，每一步都落到矩阵形状上。看完你不光能在脑子里徒手推演整张网络，还能拿到开头那个反差的答案：奇迹不在运算本身，在运算的堆法和次数。 一、先看全景：数据在 Transformer 里走一趟 设一段输入有 n 个 token，每个 token 被表示成 d 维向量（GPT-3 小版本里 d 取 12288，教学场景常取 512）。整句话就是一个 n×d 的矩阵，从现在起你只需要盯着这个矩阵的形状变化。 它先过嵌入层拿到初始值，加上位置编码，然后进入编码器堆叠的 N 层结构。每层做三件事：自注意力（token 之间互相看一眼）、残差连接加归一化（把结果稳定地传下去）、前馈网络（每个 token 自己再深挖一次）。三层做完进下一层，N 层之后从顶端取输出。 走到嵌入层之前还有一步：分词。模型不认识字，只认识 token id。主流方案是 BPE（字节对编码）：从单个字符开始，统计语料里最常出现的相邻对，反复合并成新词元，直到词表达到目标规模。中文一个常用字多半是独立 token，英文一个长单词可能拆成两三段，数字、代码、标点各有各的拆法。「unbelievable」可能是 un+believ+able 三块，每块查嵌入表得到一个向量。分词质量直接影响一切：同样的文本，分词差劲的模型等于戴着一副度数不对的眼镜读书，而且没有「词汇必须成词」的硬约束，模型对拼写错误、混排中英的容忍度反而更高。GPT 系列词表约五万，LLaMA 系列十几万（多语言更友好），这个数字在第七节算参数量时还会回来。 一张图记住形状就够了：任何时刻数据都是 n×d，变的只是内容。注意力层让 token 之间交换信息，FFN 层让每个 token 独自消化信息，两者交替，这就是 Transformer 的全部节奏。 训练和推理时这张图的走法不一样。训练是「整句并行」：n 个 token 一次性送进去，掩码保证第 t 个位置只能看见前 t-1 个，然后每个位置同时算一遍「下一个词预测的对错」，效率极高。推理是「逐字串行」：生成一个词，把它拼回输入再算一遍，你在对话框里看到模型一个字一个字往外蹦，就是这一轮轮矩阵乘法在跑。同样生成 100 个 token，训练时一遍前向就处理完的上百个位置，推理要重复一百次前向——这就是为什么推理贵，也是后面 KV cache 这类优化存在的理由。

一个会话吃掉 952 万 token：我的 Codex 账单拆解与三条省法

xiaoshuai1024 included in AI工程
翻开 ~/.codex/sessions 里我自己的会话记录，有一条让我坐直了：2026-08-20 16:45:36（UTC+8）开始的那个 session，54 次模型调用，总输入 952 万 token，总输出 6.6 万。输入是输出的 144 倍。这中间我没换模型、没改配置，就是正常干了一个下午的活。 起因说来简单：我给频道挑选题，把市面上省 token 的攻略翻了一遍，清一色是「关思考、开压缩、勤开新会话」的口诀，没有一篇贴过自己每一轮的真实流水。口诀对不对、在自己的通道上灵不灵，全靠信。我不太想信，就想亲眼看，于是有了这篇逐轮拆解。 这篇文章就是把这 952 万拆到每一轮，看它从哪来、被什么放大、怎么砍。全部数据来自我本机的 codex-cli 0.140.0（deepseek-v4-flash 通道），8 个真实会话加一组受控 A/B 实验，没有任何估算。 这套方法适用谁，不适用谁 适用：用 Codex CLI 干活、按 token 计费或被限额卡脖子的人。不管你走官方 API 还是像我一样用 cc-switch 切到 DeepSeek，下面讲的机制一模一样。团队协作的仓库更该看——AGENTS.md 是随仓库分发的，你写在里面的每一个字，都会乘以全组每个人的每一轮会话，一份松散的文档就是全组的持续成本。 不适用：纯订阅制（ChatGPT Plus 内的 Codex 用量）的用户——你不直接付 token 钱，但限额消耗是同一套逻辑，看懂机制一样能少撞墙。 先交底数据来源，这也是本文的方法论价值：Codex 的每个会话都在本地存了一份 JSONL 流水（~/.codex/sessions/年/月/日/rollout-*.jsonl），每次模型调用都记录了 token_count 事件，输入、缓存命中、输出、思考 token 四项分開记。你不依赖任何后台报表，就能把自己的账单拆到每一轮。文末清单里有现成的挖掘脚本核心逻辑，十行以内。 三条原则，先记住再往下看 一、上下文是复利负债。 模型不记得你，Codex 每一轮都把全量历史重新发给它。你在第 30 轮为第 3 轮的文件内容付钱，这是账单的结构性来源。操作口径：会话按任务切，文档按「违背会出错」删。 二、缓存是放大器，不是免单。 重发的大头会被供应商的上下文缓存按折扣价接住——但命中率取决于你的前缀稳不稳定。同样 952 万的重发量，命中率 98% 和 46%，实付差出一个数量级。管缓存，比重发本身更值得花精力。操作口径：AGENTS.md 进稳定期后上锁，要改集中批量改。 三、开关要先验证再信任。 我把推理档位从 high 调到 low，一分钱没省，思考 token 反而更多——这个通道根本没把参数透传给模型。配置文件里写了不等于生效，省钱的动作必须用数据验证过才算数。操作口径：任何参数改动，当周跑一次 A/B 对账。
