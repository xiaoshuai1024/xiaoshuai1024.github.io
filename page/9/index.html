178 个测试全绿，真实编辑器一连就崩

xiaoshuai1024 included in AI 开发
一个 ACP 服务器接上真实编辑器 Zed，第一个请求 session/new 就当场返回 Internal error，而此刻 CI 里 178 个单元测试全绿、行覆盖率 100%。DeepSeek Harness 的官方复盘文档记录过这次事故，它值得每个写测试的人花十分钟看一遍。行覆盖打满的项目，照样会在用户走的路上翻车。 一、Zed 连上来的一瞬间发生了什么？ 报错稳定得像刻进去的。ACP bridge 启动一切正常，Zed 发来第一个 session/new，服务器直接返回： Internal error: cannot get property "agents" without inject Internal error: cannot get property "sessionPersistence" without inject前一条出现在建新会话时，后一条出现在恢复旧会话的 session/load 里。属性名不同，句式相同：读取某个属性时发现从头到尾没人注入过它。 影响面也由入口位置决定：建新会话与恢复会话恰好是编辑器接入后最先调用的两个 RPC，任何想把 agent 挂进 Zed 的人都会当场撞墙。复盘顺带记下一句止损结论：崩溃前没有任何内容被持久化，数据零丢失；代价集中在功能完全不可用，加上先后两轮定位各自烧掉的调试时间。 时机上还有个反直觉的细节：异常抛在插件加载阶段，而不在任何请求处理器内部。session/new 只是恰好成了触发器，真正引爆的是加载过程本身。这解释了失败为何稳定到毫无波动：编辑器接入的入口链路每一次都会装载同一批插件，雷埋在必经之路上，谁路过谁触发。 二、178 个绿和一个报错 反差摆在一起才有杀伤力。同一份代码，单元测试 178 个全绿、行覆盖率 100%；换真实编辑器进来，第一次握手就断在两组属性上。完成度指标和存活能力之间那段距离，就藏在插件系统的挂载方式里。 测试给插件安排的是一条温室路径：手工把插件对象装进容器，依赖项提前备好，inject 天然就在。Zed 走的才是用户的路：Loader 读入口模块、辨认导出形态、动态装配服务，一步都不能少。 两条通路在源码地图上几乎不相交。走不到的那条路上埋着什么，全绿的测试给不出任何线索。 178 这个数字也值得拆开看成色。复盘记载的测试清单相当体面：codec、内存传输、生成的协议消息、失败路径、HMR 各有专属单测；另有一条需要 key 的真实 API e2e 和一条无需 key 的 stdout 纯净性 e2e。规模与形态都在水准线上，唯独形态这个维度出了问题：清单里的每一项都没打算伪装成真实 Loader。

快照测试把 bug 认成标准答案：DeepSeek Harness 事故复盘

xiaoshuai1024 included in AI 开发
全绿的测试套件也会替故障背书：DeepSeek Harness 有一次合入，单元测试、覆盖率、快照、文档、构建、hygiene 检查全数通过，实际情况是文件系统工具栈从未注册，七个场景调用的都是注册表里不存在的工具。此后的每一次 CI 绿灯，都在给这个 bug 作证。 事故记在官方复盘 0002（docs/postmortem/0002-js-expression-disabled-filesystem-tools.zh.md，本文细节全部出自这份一手材料）。最危险的回归就藏在绿灯里：测试没抓到 bug 还有救，bug 的输出一旦被刷新成新基准，往后每一条全绿的流水线都在为故障站台。 一、七个场景同时调用不存在的工具 先交代这组组合的出身。默认的 ACP（Agent Client Protocol）组合有意只启用 bash，因为它的沙箱约束不了进程内的文件系统提供方；可文件系统快照场景又需要 read、write、edit 三个工具，于是这些插件被放进默认的 cordis.yml，附带一个 disabled 表达式，意图是只在全权限启动和快照模式下放开它们。 实际运行结果是任何一个模式都没放开。表现相当齐整：七个文件系统场景加一个混合工作区编辑场景，全部调用了注册表中不存在的工具。结构化会话日志里带着这样的错误： ToolNotFoundError, code = UNKNOWN_TOOL而 stdout 上渲染出来的，只是一张通用的失败工具卡片，失败原因被完全抹平。 两类记录的落差值得单独停留一会。日志保留的是事实层：工具解析不到，代码 UNKNOWN_TOOL，指向注册表层面的缺席；stdout 渲染出的是表情层：一张谁都长得一样的失败卡片。事故后期能够定案，靠的全是前者；如果整个系统只剩后者，这桩事连被发现的资格都没有。 二、全绿流水线放行了什么？ 时间线短得可疑。PR #261 做了三件事：整合 ACP 组合、刷新文件系统快照、引入条件式文件系统配置项。合入门禁逐一亮灯：单元测试、覆盖率、快照、文档、构建、hygiene，六类检查全部通过。按这套门槛自己的口径，这次合入找不出毛病。 拦下它的力量来自人工评审，此前所有自动门禁一路放行。翻看刷新后的文件系统预期输出时，两种异样浮出来：通用的失败卡片，配上结构化的 UNKNOWN_TOOL 结果。随后的一次真实 Loader 启动给出确认级证据：每个 disabled 字段拿到的仍是表达式对象，每个文件系统 fiber 都从未被创建过。 六类检查各管一段辖区：函数行为、覆盖数字、输出形状、文档、构建产物、仓库规范。合起来看像一张严密的网，但「这些场景依赖的工具究竟进了注册表没有」这个疑问，不在任何一类的提问范围里。事后重读这份清单，缺掉的那一格比填满的格子更有信息量。 这层分工很值得多看一眼。CI 只回答「回归能否按原样回放」，「行为是否正确」被默认留给了人眼，等价的自动判定在当时并不存在。人这道防线挡住了故障随合入扩散，但它太贵、也太不稳定；此后仓库补下的每一条守卫都指向同一个方向：把这层判断从人的眼睛里搬进检查器。 三、一个 truthy 对象的杀伤半径有多大？ 源头是一个想当然的假设。作者想用 disabled: !!js 这类 JS 表达式按启动模式开关 fs 插件，默认认为 !!js 标签在整个 Loader 配置项上都生效；实际实现里只有 entry.options.config 字段经过 Entry.

三个人要删会话，DeepSeek Harness 为什么就是不做

xiaoshuai1024 included in AI 开发
在 DeepSeek Harness 的 GitHub Discussions 里搜「删会话」，能同时翻出三条独立请求。三个互不相识的用户先后开口，要的都是让某个会话从磁盘上彻底消失。维护者三次都没有交出一个删除命令。 结论我直接放在前面：删不掉排在模型约束那一栏，backlog 上等不来它的修复。合理出路是给管理诉求另开一个出口，这个出口眼下还没出现。依据是我把会话当 git 用那篇拆过的设计重新读了一遍，下面从头讲。 一、同一条请求为什么会来三次？ 出处可以自己核对（github.com/deepseek-ai/deepseek-harness/discussions）：#3339 要一条原生 /delete 命令，把会话永久删掉；#2861 提议加 session.delete RPC；#2642 提议 workspace.deleteSession。三个编号彼此隔着相当长的距离，提的人互不相识，要点的东西一模一样。 时间跨度本身就带着信息量。三条讨论横跨了好几个 rc 版本的开发期，短期的热度撑不了这么久；隔那么长时间还有人说出一模一样的诉求，说明它长在真实的使用路径上。测试期攒下的垃圾会话越积越多、共享机器上不想留对话痕迹、项目收尾想清场，每一种都是正当的管理诉求。 更难得的是三条请求的措辞各不相同、抽象层级互补：命令面的 /delete、协议层的 RPC、工作区对象的方法，从用户入口到内部接口各来了一票，最后撞的却是同一扇门。需求表达得这么完整，回应却始终缺席，这才值得往下挖。 它们从不同方向涌向同一个动作，又一起撞上同一堵墙：仓库里找得到 resume、fork、replay，唯独找不到 remove。 二、不给删除按钮的系统长什么样？ 要看清墙在哪，得先看地基。dsh 的核心设定只有一条：Session 是一份由类型化 SessionEvent 组成的仅追加日志，同时是智能体完整交互历史的唯一真源。模型每轮看到的消息历史、界面渲染的对话、调试用的记录，全部从这条日志当场派生。写入方向只留了 append 一个，seq 单调递增，修改旧事件的路径从来就没开过——这层校验做在持久化层，细节我在源码深读里逐段核过。 「派生」两个字值得多看一眼。界面上的一切既然都来自日志的当场投影，「删掉会话里的某段内容」在这个模型里就失去了句法位置：改事件的字段？事件不可变。改投影里的显示？那叫隐藏，数据还躺在磁盘上。唯一真源的设定换来了确定性重放能力，代价是「删除」这个词在接口词汇表里没有对应动词。 标题子系统把这个原则演得很彻底。会话标题本身就是一条 log-only 的 session/title 事件：自动生成也好，用户手动改名也好，都只是往后追加一条新记录，折叠规则取最新一条；显式改名还会钉住标题，让自动生成停摆。标题改得掉，靠的却是对旧数据的零次写入。 工具层同样如此。todo 插件的待办列表没有一个可变的「当前状态」字段，它的最新值从历史里的每条 todo/write 事件现场推导出来；要看现在的清单，系统就把事件流重新折一遍。整个系统里，「现在」永远是日志的函数。 三、删掉一个事件，会破什么？ 推演一下维护者的视角。假如给 session.delete 开口子，真删掉一段事件，日志中间会出现空洞，后面所有事件的 seq 和内容仍指向被删段落。resume、fork、replay 三个核心操作都以「同一组事件可以逐条重演」为前提：fork 从第 k 个事件处截种子，回放要求复盘时的上下文和当时模型看到的完全一致。允许删除，等于让这三个保证在生产环境里悄悄失效。 回放的严格程度放在事故复盘的场景里最容易体会。你想证明某个 bug 在当时的上下文里必然发生，前提就是模型当时看到的那串输入能够一字不差地重建；任何一次事后修补都让这份证明降级成推测。 压缩功能的选型最能说明问题。上下文窗口要省空间，直觉做法是把旧对话抹掉，dsh 给出的却是投影 replace： { op: 'replace', start, end }区间 [start, end) 的事件被折进替换结果，原始事件原封不动移入 shadowedSeqs 影子区。看起来像删除，实际是换视界：审计时原文照样翻得出来。宁可多花一份存储也要留住原文，守的就是上一节那条确定性底线。

Agent 改炸了怎么救？DeepSeek Harness 把会话当 git 用

xiaoshuai1024 included in AI 开发
让 Agent 跑一个真实任务，最怕的不是它慢，是它自信。第十七轮修改把你那段能跑的代码改成了不能跑的版本，你盯着屏幕想按 Ctrl+Z，发现这个键只对你的编辑器有效，Agent 在磁盘上做的每一笔改动都不会退回去。 我在读 DeepSeek Harness（dsh）源码的时候意识到，它的作者们把这个场景当成了一等公民来设计。解决方案写在架构文档第一页：产品的每一部分都是插件，包括会话日志本身。而会话日志的设计，用过 git 的人一眼就能认出来。 直接给结论：dsh 把整个会话做成一条只追加的事件日志，模型每轮看到的消息历史都是这条日志当场投影出来的。于是「回到过去」不需要备份，只需要换个投影方式或者从任意一轮重新分叉。 一、会话是一条日志，不是聊天记录 打开 docs/subsystems/session.zh.md 第 5 行，原话是：Session 是一份由类型化 SessionEvent 组成的仅追加日志，是智能体完整交互历史的单一真源。LLM 消息历史从日志派生而来，从不单独存储；回放即从同一组事件重新派生。 这句话有三层信息，值得一句句抠。 第一层，「仅追加」。事件只能往尾部加，编号 seq 单调递增，接口上不存在修改和删除旧事件的路径。你在界面上打的每个字、模型的每次回复、每一次工具调用及其返回值，落盘时全部是事件。这份设计我在源码深读那篇里从 packages/core/session/src/index.ts 一路验证过：seq 校验做在持久化层，乱序事件直接拒绝写入。 第二层，「单一真源」。没有第二份数据。模型看到的对话、界面渲染的历史、调试时翻的记录，源头都是同一条日志。 第三层，「派生」。这是整套机制最反直觉的地方：你以为模型在「聊天的上下文里续聊」，实际上每一轮请求的消息数组都是当下从日志重新算出来的。会话不是一个容器，是一台能随时重演的机器。 二、两套视界：模型看投影，你看日志 既然日志不可改，那上下文压缩怎么办？把旧对话压成摘要，不就等于改了历史吗？ dsh 的解法是在日志上面架一层投影。deriveMessages() 不直接遍历日志，而是遍历 session.surface.nodes 这个投影结构。投影的更新原语只有一个： { op: 'replace', start, end }含义是：把 seq 区间 [start, end) 的事件替换成新内容。执行之后发生三件事：新内容写进折叠结果 folded.replacements[]，被替换的原事件记入 shadowedSeqs，日志本体一个字节都不动。 于是出现了一个很干净的分工。模型请求时走投影，看到的是「当前视界」：摘要替代了旧对话，窗口不爆。你想审计完整历史时读日志本体，被替换的原文全都在，界面上照样能翻。一套数据，两种视界，中间靠 replace 操作切换。文档把这层叫 surface 回放，配合上一节说的派生机制，压缩这件事从「危险地改历史」变成了「安全地换视界」。 三、fork：从任意一轮重新分叉 杀手锏在 fork()。签名带三个关键字段：parentSession 指向母会话，seedLength 标记种子长度，delegationDepth 记录委派层级。它的语义是：从母会话的第 k 个事件处截断，前面全部事件作为种子送进新会话，后面的一概不带。 这就是 git 里 branch 的动作。项目在第十七轮被改炸了？回到第十五轮 fork 一个新会话，三条路线各跑各的。老的留在原地可以对照 diff，新的随便试错，两边互不污染。

一条命令 12 秒背后：DeepSeek Harness 插件挂载链路拆解

xiaoshuai1024 included in AI 开发
社区仓库三天从两百多个插件涨到一千四百多个，安装命令却长得一模一样。我在实测那篇里跑过：装一个 JSON 查询工具，从回车到挂载完成，秒表停在 12 秒。 快得让人怀疑它没干活。所以这篇把 12 秒拆开看。先给结论：dsh 没有自己实现任何安装逻辑，这条命令是一次 pnpm 转发加两处文件写入。魔法不存在，存在的恰好是「没有魔法」。 全文按链路顺序走：命令转发、落盘双写、重启组装、profile 组合机制、两条验证路径，最后算两笔容易被忽略的代价——中途插件的缓存钱和 Node 版本的门槛。 一、命令本身：一次 pnpm 转发 实测命令是这个样子： dsh plugin --profile web add "github:dsh-external/dsh-tool-json#main"dsh plugin 子命令的第一步，是把自己收到的参数原样转发给 profile 目录里的 pnpm。没有自研的下载器、版本解析器、依赖求解器。指定 --profile web 时，pnpm 的工作目录就是 ~/.dsh/profiles/web。 转发完还没有结束。CLI 源码里这条命令自身只干两件事：跑完 pnpm 之后调 reconcilePlugins()，按安装结果回写 bundles 清单；再用 exportsPatch() 判断装进来的包有没有声明 dsh.bundle 字段，声明了才把它当补丁层对待。安装器自己的代码量小到可以一口气读完，因为它把最难的部分外包了出去。 这个选择跟整个项目气质一致。包管理是 npm 生态几十年踩出来的成熟领域，自己造下载器除了多一段要维护的代码毫无收益。dsh 的做法是把 GitHub 仓库直接当来源（github:user/repo#branch 格式），依赖解析全部交给 pnpm，自己只管转发和记录；插件发现则退化为 npm 加 GitHub topic，给仓库打上 dsh-plugin 标签就能被搜到。 二、落盘：两个文件被同时写入 pnpm 跑完后，profile 目录里有两个文件被动了： ~/.dsh/profiles/web/ ├── package.json # dependencies 多了 @deepseek-ai/dsh-tool-json └── (dsh.

万一 AI 想删库？DeepSeek Harness 沙箱的 fail-closed 底线

xiaoshuai1024 included in AI 开发
给 Agent 授权是最拧巴的事：权限给小了活干不成，给大了心里发毛。模型哪天抽风输出一条 rm -rf 类的命令，谁来拦？ DeepSeek Harness（dsh）在沙箱这件事上的答案短得像句口号：拦不住，就不跑。这篇把这句话背后的机制拆开：沙箱是一个能力接缝、四条平台实现链、三档按次携带的策略，外加上周刚刚补掉的一个真逃逸。全部内容对着 packages/sandbox 源码讲。 一、底线只有一条：失败即关闭 安全领域有个词叫 fail-closed，失败即关闭：防护组件自己出问题时，系统的反应是拒绝服务，防线绝不撤掉。dsh 把这条原则写进了类型定义。 packages/sandbox/sandbox/src/index.ts 的第 119 行附近定义了一个专用错误码，语义是「请求了受限模式但找不到可用的沙箱后端」。这个错误会作为 tool/result 返回给调用方，让人分得清两种完全不同的情况：命令没跑（缺沙箱）和 命令跑了但失败了（执行错误）。注释里专门强调区分二者，因为混淆它们意味着一种静默降级：后端缺失时悄悄裸跑命令，用户还以为一切正常。 裸跑这条路在 dsh 里被堵死了：探测不到可用后端，就报错，任务失败。宁可这一单干不成，不开一道没有护栏的门。 二、一个动作：confine 包一层 沙箱能力暴露为一个极小的接口：SandboxProvider.confine(argv, policy)。输入是你原本要执行的命令和一个策略对象，输出在第 91 行注释里写得直白：「the argv to spawn in place of」——替换原命令的包装版参数。 也就是说沙箱不拦截、不代理、不监控，它只干一个活：把你的命令包进一层受约束的外壳再交还给你。隔离由这层外壳完成。接口简单到只有签名本身，这正是接缝架构的风格：能力用最小接口声明，实现随便换。 返回值也不止一层 argv。ConfinedArgv 还携带两样配套事实：所选后端的强制执行完整度，以及这家后端自己的否决方言。同一类文件拒绝在不同方言里拼写不同，bwrap 报 EROFS，Landlock 报 EACCES，Seatbelt 报 EPERM；消费方按自家后端的方言匹配，不拿跨后端并集去猜（docs/subsystems/sandbox.zh.md）。 三、平台链：不造轮子 包装用什么材料？packages/sandbox/sandbox-local/src/index.ts 开头几行列出了全部家底： Linux: bwrap → Landlock（内核级，原生 launcher） macOS: Seatbelt（sbcl） Windows: ACL restricted-token runner选择顺序按平台来：Linux 上先用 bubblewrap 容器化封装，不行就落到内核级的 Landlock LSM；macOS 用系统自带的 Seatbelt 沙箱描述文件；Windows 走 ACL 受限令牌。启动时还会对每条链做功能探测（probe），探测结果决定这次会话实际用的是哪条。注意这里同样适用第一节的原则，探测不到就明说，不带病运行。
