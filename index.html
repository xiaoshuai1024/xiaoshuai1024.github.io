DeepSeek Harness 插件 90% 是玩具，实测筛完我只留这 10 个

 included in AI 开发
三天前我上手实测 dsh 的时候，dsh-plugin 话题下是 275 个仓库；写这篇文章的今天，这个数字过了 1400。中间我又把源码从头读了一遍。生态爆发的另一面是泥沙俱下：这里面有给 Web UI 加 2005 年风格广告的整活插件，有「写代码的时候账户不能同时亏钱」的炒股面板，一天写完就没人维护的占了相当比例。 这篇文章的目标很具体：读完之后，你能在 20 分钟内把 10 个真正值得装的插件装好，并且知道先装哪个、后装哪个、装不上怎么办。筛选标准不是 star 数，是「解决什么痛点」——没有明确痛点的，再火也不进清单。 先看全景，10 个插件按三档排： 1400 个仓库怎么砍到 10 个 先交代筛法，你可以拿同样的标准自己去筛，不必认我的清单。 第一刀砍没有维护动作的。生态爆发期的典型寿命是「发布当天一个 commit，之后永远沉默」。我看仓库先看最近一次提交时间，再看 issue 区有没有人报错、作者有没有回。三天内没有任何动静的仓库，装了就是把排错责任揽到自己身上。 第二刀砍不声明适配版本的。dsh 三天发了 6 个 rc，插件作者如果连「我适配的是 rc 几」都没写，说明他自己也没认真跟。这个信号在 README 第一屏就能看到，两秒钟排除一个。 第三刀砍痛点不明的。回到那个标准：这个插件解决什么问题，一句话说不清的不要。「一切皆插件」的架构降低了写插件的门槛，也就降低了写玩具的门槛——dsh-ads 给 Web UI 加 2005 年风格广告，dsh-stock-market 的卖点是「写代码的时候账户不能同时亏钱」，这类整活作品 star 再高也不是生产力的菜。 三刀下去，1400 个仓库剩下的百来个才有看的价值。下面的 10 个，是从这百来个里按「解决真实痛点 + 维护活跃」再排出来的。 你需要先准备好的东西 这篇是系列第三篇，前两篇的结论直接沿用，这里只列清单： Node 22.14+，建议直接上 24 LTS。这是硬门槛：会话持久化插件用了 zstd 压缩，createZstdDecompress 是 Node 22.14 才进的 node:zlib。v22.13 启动会直接崩，而且报错信息完全看不出跟 Node 版本有关。nvm 用户 nvm install 24 切过去 dsh 0.

DeepSeek Harness 源码深读：内核、调度、提示词、上下文一次讲透

 included in AI 开发
三天前我上手实测了 dsh，装完跑了一圈任务，看完插件生态。但实测只能回答「它好用吗」，回答不了「它为什么这样做」。这三天我把 deepseek-ai/deepseek-harness 的源码从头到尾读了一遍——80MB 的 TypeScript monorepo，133 个插件包，外加一套 vendored 的 Cordis 内核。这篇文章是完整的源码笔记，从启动流程一路讲到上下文压缩和定时调度，所有结论都带 file:line 引用，你可以拿着仓库对照看。 我的总体读后感先放这：dsh 是我读过的 Agent harness 里工程约束执行得最彻底的一个。它不是功能最多的，但每一个「容易写歪的地方」——重试、压缩、沙箱、并发、持久化——都用了同一种手法：把决策变成事件，把状态变成投影，把危险变成默认拒绝。这篇文章就是要把这个手法在六七个子系统里怎么落地的拆开看。 版本说明：分析基于我手上的 clone（根 package.json 版本 0.1.0-rc.5，实测文章用的 rc.6），行号以这份代码为准，开发者预览期重构频繁，行号可能漂移。 一、先看地形：仓库结构和那套 vendored 内核 clone 下来第一眼要看的其实是根目录的 vendor/，packages/ 反而可以后看。里面有五个目录：cordis、loader、include、hmr、timer——全部是直接拷进仓库的源码，不走 npm 依赖。 Cordis 是一个「依赖注入 + 插件生命周期」框架（koishi 生态那套思路）：核心概念是 Context（上下文）、Fiber（插件的运行时载体，一个状态机）、Service（命名服务）。插件就是一个对象： { name, inject, Config, apply(ctx) }inject 声明依赖的服务名，apply 在激活时拿到 Context 挂自己的服务。Loader 负责按声明拓扑加载，服务没就绪时依赖方 fiber 停在 pending 状态，Service.check 就绪后放行。 为什么 vendor 而不是装 npm 包？我的看法：harness 对内核的稳定性要求是「每一行都要为我负责」。插件内核是整个系统的地基，升级一个第三方包带来的行为漂移，在 133 个插件的系统里排查成本极高。拷进来，锁死，自己改。这个选择本身就说明了 dsh 团队对「内核」的界定有多严格。 packages/ 下的分组也值得记一下，后面全要用到： packages/boot/* —— 启动、profile、cmdline、app-boot packages/core/* —— agent-loop、session、tools、system-prompt packages/llm/* —— LlmRuntime、deepseek 适配器、重试 packages/context/* —— compaction、spill、todo、plan-mode、goal packages/schedule/*、packages/jobs/* —— 定时调度和后台作业 packages/subagent/、packages/sandbox/、packages/skill/ —— 子代理、沙箱、技能 apps/cli、apps/web —— 启动器和浏览器前端 packages/host/* —— webserver、apiproxy 整棵树的地形是这样的：

GLM-5.3 发布实测：编程暴涨 50%，开源第一的成色拆开看

 included in AI 开发
2026-08-14，智谱发布新一代基座模型 GLM-5.3。官方通稿的关键词很直白：编程能力最强的开源模型。这个月的国产大模型赛道已经卷成一锅粥——一个月内三家厂商先后完成关键版本迭代，智谱这一发是其中最受程序员关注的一发。 我盯 GLM 系列有段时间了。从 GLM-5 到 5.1、5.2 再到 5.3，半年四代，每一代都在编程榜上往前拱一截。5.1 那代在 SWE-Bench Pro 上超过 Claude Opus 4.6 的时候，我还专门跑过对比；这次 5.3 的通稿数字更猛：内部体感评测较 5.2 提升 50%。 数字越猛，越要拆开看。这篇我把 GLM-5.3 的每项成绩按口径归类——哪些是公开榜、哪些是内部评测、哪些是第三方对比，再串起 GLM-5 系列这半年的榜单轨迹，最后落到最实际的问题：这套能力怎么接进日常工作流，Coding Plan 的钱花得值不值。 先看清这是一次什么发布 GLM-5.3 的发布节奏分两步。API 在 2026-08-14 当天上线，全量用户可用，同时纳入 GLM Coding Plan；模型权重在发布约两周后开放，开源地址在 zai-org/GLM-5 仓库，MIT 权重协议——这是智谱一贯的打法，先服务后权重，商业化和开源声誉两头都要。 能力参数这边，GLM-5 系列的基础规格是 200K 上下文窗口、128K 最大输出；从 5.2 开始，Coding Plan 用户在编程场景下可以用到 1M 上下文。1M 这个数字对 agent 工作流是有实际意义的：把一个完整中型工程连同依赖清单、构建脚本塞进同一条推理链路，200K 会勉强，1M 才算从容。 128K 最大输出这个参数值得单独说一句，因为它经常被上下文窗口的光环盖住。输出窗口决定了模型单次能产出的代码量上限——重构一个大文件、一次性生成完整的脚手架、输出一整份带注释的迁移脚本，这些任务真正吃的是输出 token 而不是输入。很多模型的输出上限卡在 8K 到 32K，遇到大文件就得拆着写，拆的过程就是出错的过程。128K 意味着绝大多数单文件任务可以一口气写完，配合 1M 上下文读入整个工程，一来一回都留足了余量。 定位上，5.3 没有换架构叙事，通稿强调的重点是三个：AI 编程、Agent、长程任务。这三个词不是并列的口号，是一条递进链——编程是单点能力，Agent 是把单点串成多步骤执行，长程任务是串起来之后还能稳定跑完。评测成绩的分布也印证了这个重心：最强的项全在终端执行和持续工程这一侧。

黑客松冠军开源 24 万星的 ECC：把 agent 工程做成了操作系统

 included in AI编程
让 agent 干活的都见过这类场面：让它改个配置，它顺手动了测试文件；让它加个功能，它把三个模块的重构一起做了；让它查个问题，它给出两套自相矛盾的结论。 遇到这种问题，多数人的第一反应是换更强的模型、写更细的提示词。我的做法不一样：先搞清楚翻车的根源在哪。根源不在模型——模型聪明得很。根源在环境：agent 干活的每一步，没有人在旁边立规矩。 这篇文章讲的就是我在这个过程中挖到的一个项目。它把「给 agent 搭环境」这件事，做成了一座能安装的仓库。 一、翻车不怪模型，怪环境里没有「停」 资深工程师干活为什么不翻车？他周围的工程环境在替他踩刹车——规范文档告诉他边界在哪，代码审查在他出错时拦住他，测试在他改坏时叫醒他。刹车踩得准的人，干得不一定快，但翻不了车。agent 缺的正是这套环境。给 agent 搭这套环境，就是 harness 这个词的全部含义。 2026 年上半年，skill 仓库扎堆冲上 10 万星：官方 anthropics/skills 16.7 万，mattpocock/skills 21 万，ECC 24 万——三个 20 万级仓库一年之内全冒出来。这在前端框架身上见过，在配置仓库身上是头一回。星数把「怎么用 AI 干活」推成了现象级话题，也让 skill 仓库从个人经验分享变成了一场生态竞赛。ECC 是这场竞赛里跑得最快的那个。 二、ECC：一个 24 万星的 agent 工程操作系统 这个项目是 affaan-m/ECC，全称 everything-claude-code，作者 Affaan Mustafa，在 Anthropic 黑客松上用 Claude Code 8 小时做出产品夺冠的开发者——冠军奖是 1.5 万美元的 API 额度，他拿它继续打磨这套工作流。打磨了 10 个月之后开源，MIT 协议，GitHub 上 24 万 Star，8 个月超过 Linux 内核。 仓库简介一句话：the agent harness performance optimization system——agent 运行环境的性能优化系统，给 agent 搭运行环境，让它每一步都有人管。

大模型是裸 CPU，我花一年给它装了个操作系统

xiaoshuai1024 included in AI 开发
写了十二年代码，前六年在前端，中间补成全栈，去年开始把 AI 真正用进研发。这轮转型里我见过最多的场景，是有人拿着一个模型在聊「AI 能不能干这活」，聊完发现长任务干不动、规矩守不住、换模型也没用。 我的体感是：问题不在模型，在视角。大模型是一块裸 CPU——算力强，但没有内存管理、没有文件系统、没有进程调度。你往裸 CPU 上怼程序，指望它稳定跑一个企业级服务，跑不动才是正常的。可绝大多数人把它当成了「一台装好系统的电脑」，缺了哪块就抱怨「这个 AI 不行」，然后去换一台。 我这一年的演进，本质是在给它补操作系统。过程分成四段：先是把话说清楚（Prompt 工程），再是管好它看什么（Context 工程），然后是让规矩焊死在流程里（Harness 工程），最后是让它在边界里自己干（自治体系）。每上一层，都是被下一层的天花板逼出来的。这个「裸 CPU → 操作系统」的类比不是修辞，它精确对应了每一段工程在补哪块系统能力——这也是我写这篇的动机：把这条线完整画出来，你看完能自己判断，手头的 AI 卡在哪一层。 这篇文章把这条演进线完整讲一遍。每一段我都会说：当时怎么做、撞到什么天花板、为什么下一段必须出现。结论先放在这——AI 工程化的每一步，都是在为「稳定地、大规模地让 AI 干活」清障碍。这条线和 《别再背 AI 黑话了》里那条主线是同一条：那篇讲每个词是什么，这篇讲这些词背后，工程是怎么一层层长出来的。 先看清裸 CPU 的四个先天缺陷 动手之前，先认识对手。大模型的四个缺陷不会因为模型变大而消失，所有工程手段都是在跟它们周旋。这四个缺陷不是我从论文里读来的，是我在真实项目里一个一个撞出来的。 缺陷一：有输入就输出，没人喊停就一直干。 AI 本质是续写器：接收输入，预测最合理的下一步。需求只说了半句，它不会停下来问「你说的 A 具体指什么」，而是开写它最熟悉的那个 A；测试没过，它不会承认失败，而是改两行继续跑。这个天性我后来总结成「翻车三连」：需求含糊就往下编、方向错了错到底、改 bug 越改越乱。资深工程师和新手的差别就在这——不是老手写得快，是老手停得准，而 AI 天生不会停。项目里所有「加一个停字」的设计，都是从这个缺陷长出来的。 缺陷二：上下文窗口是稀缺资源，长任务必然掉质量。 同一个任务，3 步的时候干得干净利落，加到 15 步就开始胡说。不是模型变笨了，是窗口里塞满了前面步骤的中间产物——一次工具调用返回几万字符的 JSON，三步之后窗口就被历史占满，后面真正有用的信息被稀释。我在长链路任务里反复踩这个，最初以为是模型不行，换了几轮模型指标纹丝不动，后来把上下文里的大 JSON 挪出去，指标立刻回升。物理容量和有效容量是两回事。 缺陷三：无状态，每次对话都是新生。 昨天踩过的坑，今天换个会话继续踩。规则在上一轮说得清清楚楚，新会话里它又按自己的理解来一遍。跨会话的知识完全靠人肉搬运——把踩坑结论复制粘贴进下一段提示词，粘漏一次就重蹈覆辙。这个问题在一个人用的时候还能忍，团队用起来就是灾难：每个人都在跟 AI 重复教一遍同样的东西。 缺陷四：指令遵从率随链路衰减。 规则写在提示词里，短任务时遵从率能到九成以上，链路一长，规则就从「必须遵守」退化成「仅供参考」。你没法在每一步都提醒它一次，提醒本身也在占用上下文。更隐蔽的是，模型会「礼貌性忽略」——它不反驳你的规则，只是不执行，你以为它记住了，它其实早忘了。 这四个缺陷对应操作系统的四块缺失：没有内存管理（上下文膨胀）、没有文件系统（知识无法持久化）、没有进程调度（长任务不可控）、没有中断机制（没人喊停）。我后面的每一段工程，都是在补其中一块。 顺带说一个观察：这四个缺陷在网上被讨论的程度差别很大。上下文窗口聊得最多，无状态也常被提起；「有输入就输出」和「遵从率衰减」几乎没人当回事——但它们恰恰是后面三、四段工程的直接原因。讨论度高的缺陷有人给你方案，讨论度低的缺陷只能自己撞出来。所以我后面几段的工程，重点全压在没人讨论的那两个上。 还有人会问：为什么不一步到位直接上命令体系？因为每一段工程都有前置条件——命令要管住的是长任务，长任务的前提是上下文管得住；上下文管得住的前提是知道哪些信息值得保留、哪些可以丢；这些判断全依赖前面撞出来的认知。跳过任何一段，都是在不知道问题长什么样的时候造解决方案。 一、Prompt 工程：一切从一段对话开始 第一段演进最朴素：把该说的都写进提示词。角色、业务规则、行为约束、项目路径映射，一股脑塞进 System Prompt 和 CLAUDE.md。 刚开始效果是惊艳的。3 到 5 步的小任务，规则写清楚后几乎不会出错，写页面、改接口、补测试，速度比我自己写快一个量级。我把项目里的目录结构、部署命令、代码规范全部写进 CLAUDE.md，感觉像是在给这个 AI「上岗培训」。那段时间我的判断是：AI
